## Findings

### #1 🟡 Medium: Idle watchdog keys on raw byte arrival, not progress — trickle/keepalive traffic defeats it

| | |
|---|---|
| **File** | `extensions/copilot/src/platform/networking/common/fetcherService.ts:343-356` |
| **Category** | resource-management / availability |
| **Confidence** | 75 · **validated: confirmed** |
| **Found by** | security-reviewer (Medium), adversarial-reviewer (High) — *severity dissent; validator recommends Medium* |

**Issue:** `withStreamIdleTimeout` re-arms its watchdog on *every* result from `iterator.next()` (`clearTimer()` at :356, then `startTimer()` at :353 next loop), with no notion of forward progress and no absolute wall-clock cap. It wraps `response.body` (raw bytes) / `this.body` (a `TextDecoderStream`-piped stream) — SSE parsing happens **downstream** of the wrapper, so SSE keepalive/comment lines (e.g. `:\n`), empty deltas, and heartbeats reset the timer as ordinary chunks before they're ever recognized as non-progress. A misbehaving, malicious, or BYOK-configured upstream that emits any byte within each idle window (60s inter-chunk / 120s first-chunk) keeps the client wedged forever — the exact "hung stream" the PR targets, merely slowed to just inside the window. The validator confirmed no absolute/total-duration cap exists elsewhere on this path (`nodeFetcher.ts:119` is itself idle-only).

This is an **incomplete mitigation, not a regression** — pre-change, total silence hung forever too, so this is strictly better. Impact is bounded to a single wedged request/socket. That is why the validator (and one of the two finders) rate it Medium rather than High.

**Fix:** Add an absolute end-to-end deadline (max total stream duration) independent of the per-chunk idle timer, and/or require forward progress (a usable token / non-comment event) within a bounded number of chunks — reset on *meaningful* progress rather than raw byte arrival. Consider doing the progress check at the SSE-parse layer, which can distinguish comments/heartbeats from data.

### #2 🟡 Medium: Slow socket close after a complete response throws a spurious `StreamIdleTimeoutError`

| | |
|---|---|
| **File** | `extensions/copilot/src/platform/endpoint/node/messagesApi.ts:596`, `extensions/copilot/src/platform/endpoint/node/responsesApi.ts:537` |
| **Category** | error-handling / API-contract |
| **Confidence** | 50 (2 finders) · **validated: confirmed** |
| **Found by** | broad-reviewer (Medium), design-reviewer (Medium) |

**Issue:** In `processResponseFromMessagesEndpoint` and `processResponseFromChatEndpoint` the loop is `for await (const chunk of withStreamIdleTimeout(response.body)) { parser.feed(chunk); }` with **no early break** — the SSE end sentinel (`[DONE]` / Anthropic `message_stop`) is consumed inside the `SSEParser` callback and does not terminate the loop. Termination relies entirely on the server closing the HTTP body. After the final event is delivered, the loop issues one more `iterator.next()` awaiting `done`, with the idle watchdog armed. If the connection lingers open ≥ `SSE_IDLE_TIMEOUT_MS` (60s) without closing (buggy proxy / keepalive-without-close), that terminal read trips the watchdog and the wrapper throws — converting a fully-delivered response into a hard error. The validator confirmed `AsyncIterableObject` surfaces this rejection on the consumer's next `next()` even after a complete `ChatCompletion` was emitted.

By contrast, `SSEProcessor.processSSEInner` (`stream.ts:340-342`) does `return` on `[DONE]` *before* the terminal read, so that call site is **not** exposed — the asymmetry is the tell.

**Fix:** Have the two endpoint loops stop once the application-level end marker is observed (break/return on the terminal sentinel, matching `SSEProcessor`), or have the wrapper resolve gracefully when data has already terminated rather than unconditionally throwing after the last chunk.

### #3 🟡 Medium: Undocumented load-bearing contract — the timeout only fires because `destroy()` cancels the in-flight read

| | |
|---|---|
| **File** | `extensions/copilot/src/platform/networking/common/fetcherService.ts:344-373` |
| **Category** | knowledge-preservation / maintainability |
| **Confidence** | 75 |
| **Found by** | knowledge-reviewer (SHOULD) |

**Issue:** The timer callback only sets `timedOut = true` and calls `stream.destroy()` (it cannot throw). `StreamIdleTimeoutError` is reached solely because the pending `await iterator.next()` (:355) resolves `{done:true}`, which happens *only* because `destroy()` → `reader.cancel()` cancels the active reader created in `DestroyableStream[Symbol.asyncIterator]`. Nothing in `withStreamIdleTimeout` records that its correctness hinges on `destroy()` unblocking the currently-awaited read. If `DestroyableStream.destroy()` is later changed (or a stream type is passed whose `destroy()` doesn't cancel the in-flight read), the pending `next()` never resolves, the loop never breaks, and the watchdog **silently hangs forever** — defeating the exact protection this code adds, with no error surfaced. Multiple reviewers independently traced this mechanism and agreed it is correct today; the gap is that the dependency is invisible to a future maintainer editing either function.

**Fix:** Add a comment at the timer callback (near :346) stating the dependency, e.g. *"destroy() must cancel the active reader so the awaited iterator.next() resolves done — that unwinding is what reaches the post-loop throw; without it the watchdog hangs."* Optionally note the reciprocal invariant on `DestroyableStream.destroy()`.

### #4 🟡 Medium: Timeouts are hardcoded module constants — no injection, no `AbortSignal`, tests bound to real durations

| | |
|---|---|
| **File** | `extensions/copilot/src/platform/networking/common/fetcherService.ts:303-310` (used at 353) |
| **Category** | design / evolution-readiness |
| **Confidence** | 50 |
| **Found by** | design-reviewer (Medium) |

**Issue:** `withStreamIdleTimeout` takes no per-call timeout override, no `AbortSignal`/`CancellationToken`, and no hook into the extension's configuration/experimentation services (the codebase convention is to prefer injected config over hard-coded values). This prevents runtime tuning for slow models/networks, prevents composing the watchdog with a caller's existing cancellation, and forces tests to reference the real 60s/120s constants rather than injecting a small timeout. A network timeout shipped as a compile-time constant is a standing evolution constraint on a value likely to need tuning.

**Fix:** Accept the timeouts (and optionally an `AbortSignal`) as parameters defaulting to the constants, so call sites and tests can inject values and the timeouts can later be sourced from configuration without a signature change.

### P1 🟡 Medium (pre-existing): SSE processors accumulate unboundedly — the idle timeout does not bound total memory

| | |
|---|---|
| **File** | `extensions/copilot/src/platform/networking/node/stream.ts` (SSEProcessor accumulators) |
| **Category** | resource-management / availability |
| **Confidence** | 50 |
| **Found by** | security-reviewer |

**Issue:** `SSEProcessor.solutions[].text[]`, `StreamingToolCall.arguments`, and the Anthropic `textAccumulator`/`toolCallAccumulator`/`thinkingAccumulator` grow per chunk with no size cap. The new idle timeout does **not** bound this: as long as chunks keep arriving within the window, an upstream that streams forever (never sends `[DONE]`) drives unbounded memory growth in the extension host. The timeout gives a false impression of bounding stream resource cost while only covering total silence. Not introduced by this PR (the accumulators predate it), but adjacent to the hardening the PR is trying to provide, and compounded by finding #1.

**Fix:** Cap total accumulated response size (bytes/tokens) and/or total output items per request; abort when exceeded. Treat the model/proxy stream as an untrusted-length input at this boundary.

### Residual Risks

- `extensions/copilot/src/platform/networking/node/stream.ts:323` — teardown is now driven by two owners over two different `DestroyableStream` instances (the watchdog destroys `this.body`; `maybeCancel`/`cancel` and the `onReturn` path destroy `response.body`). Correct today only because single-hop `pipeThrough` forwards `pipedHead`; a change to the piping topology could leave the watchdog destroying a stream that no longer forwards to the live reader. (design-reviewer)
- Downstream handling of the new `StreamIdleTimeoutError` is unverified — whether callers classify it for retry/telemetry or treat it as an opaque failure was outside the diff. If nothing special-cases it, hung-stream timeouts surface as generic errors with no retry. (broad-reviewer)
- No `CancellationToken`/`AbortSignal` integration: a hung read is only escapable via the timeout (up to 2 min). Matches pre-change behavior (not a regression), but the bounded timeout is now the sole escape hatch. (broad-reviewer)

## Specialist Notes

### Threat Model Notes (security-reviewer)

- **Trust boundary**: the SSE byte stream from the model endpoint / CAPI proxy is the untrusted-length input. For standard users it is GitHub's proxy over TLS (semi-trusted); under **BYOK** the endpoint is user-configured and can be arbitrary. Threat actor for the resource-bound findings (#1, P1) is a compromised, malicious, or merely malfunctioning upstream.
- **Attack-surface change**: net improvement — previously a totally-silent upstream hung the client forever. The residual is that the control measures *byte arrival*, not *progress* or *total cost* (findings #1 and P1). Two non-malicious triggers (heartbeat-only proxy; never-terminated stream) reach the gap without an attacker.
- **Info exposure**: `StreamIdleTimeoutError` carries only the timeout duration and a generic string — no URL, headers, request ID, or body. No new sensitive sink.

### Probe Results (run by orchestrator after the review wave)

Two revert-probes nominated by `test-reviewer` were run serially while the orchestrator was the only actor on the tree; the tree was snapshotted, mutated by a single precise inline edit, and restored byte-identical (verified `git status` clean, full spec green 7/7 afterward).

- **Probe #1** — removed `clearTimer()` at `fetcherService.ts:356` and ran the `"consumer processing time longer than idle timeout does not cause false timeout"` test → the test **failed** (threw `StreamIdleTimeoutError`). The PR's headline behavior ("timer runs only during `iterator.next()`, not while the consumer holds a yielded value") is genuinely guarded, **not** a vacuous test. This **refuted** `test-reviewer`'s Medium finding that the slow-consumer test might be vacuous.
- **Probe #2** — disabled the `if (timedOut) throw` block → both positive timeout tests **failed** with "Missing expected rejection". The two positive guards genuinely bite.

### Considered But Not Flagged (all agents)

- **Late-chunk race / latched `timedOut` yields a value then spuriously throws** (raised by design-reviewer at anchor 50): independently **refuted** by broad-, adversarial-, and typescript-reviewers via microtask/macrotask ordering — a ready `read()` resolves as a microtask and runs `clearTimer()` before the `setTimeout` macrotask can fire; if the timer wins, `cancel()` forces the pending read to `{done:true}` so no real chunk is yielded. A chunk and `timedOut=true` cannot both come from one `await`.
- **Cleanup hang on early `return` after `[DONE]`** (adversarial-reviewer, anchor 50, claimed pre-existing): **refuted by validator** — when the consumer returns after consuming a chunk, the inner `DestroyableStream` generator is suspended at its `yield`, not at a pending `read()`, so `iterator.return?.()` runs the inner `finally` (`releaseLock`) synchronously and does not hang.
- **`void stream.destroy().catch(() => {})` unhandled rejection / synchronous throw**: swallowed correctly; throwing from a timer callback would crash the extension host, so fire-and-forget is right. (Was a prior bot comment; already fixed.)
- **Timer-vs-chunk race on normal completion, double `destroy()`, event-loop kept alive by a live timer**: all traced and found benign (timer cleared on every chunk and in `finally`; `destroy()` idempotent).
- **Per-chunk `clearTimeout`+`setTimeout` churn and extra async-generator hop** (performance-reviewer): real but immaterial — the path is network-gated (inter-chunk 5–20ms), timer work is single-digit microseconds, dwarfed by existing per-chunk `JSON.parse`/`splitChunk`. Suppressed as premature-optimization.
- **`ReturnType<typeof setTimeout>` timer typing, manual `Symbol.asyncIterator` driving, shared mutable closure state** (typescript-reviewer): all verified idiomatic/correct; the manual iterator is *necessary* to arm/clear the timer around only the `next()` await. No TOCTOU (single-threaded; timer callback runs only while suspended at `await`).
- **Sibling-consistency of the error-class shape, the `N * 1000` literals, the bare suite name, and the three identical call-site swaps** (consistency-reviewer): all match dominant repo conventions; nothing met the reporting bar.
