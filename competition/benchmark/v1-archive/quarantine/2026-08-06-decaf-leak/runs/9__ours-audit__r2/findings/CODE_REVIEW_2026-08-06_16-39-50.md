## Findings

### #1 🟠 High: Exit paths dropped `klog.FlushAndExit` for `klog.Flush(); os.Exit(1)` — bounded-flush guarantee lost; maintainer-reported log truncation / cluster-creation regression

| | |
|---|---|
| **File** | `pkg/proxy/node.go:154,170,178` |
| **Category** | reliability / observability |
| **Confidence** | 100 (corroborated ×8 + a maintainer's on-PR regression report) |
| **Found by** | prior-feedback (High), broad (High), security (Medium), knowledge (SHOULD), design (Medium), adversarial (Medium), go (Medium), quick (Medium) |

**Issue:** All three intentional-exit sites in `NodeManager` (PodCIDR change, NodeIP change, node deletion) replaced the idiomatic `klog.FlushAndExit(klog.ExitFlushTimeout, 1)` with `klog.Flush()` followed by `n.exitFunc(1)` (= `os.Exit(1)` in production, `newNodeManager(..., os.Exit, ...)`). `FlushAndExit` performs a **timeout-bounded** flush of all klog sinks before exiting; the replacement drops that timeout guard. On the merged code, maintainer **@nojnhuh reported (thread `pkg/proxy/node.go:155`, unresolved)** that this broke cluster creation and left kube-proxy logs truncated (only a few lines survive), and believed the previous `FlushAndExit` path was more robust.

The `exitFunc` injection seam itself is legitimate (it makes the crash paths unit-testable without hijacking `klog.OsExit`). The problem is the *production default*: a bare `klog.Flush()` + `os.Exit` rather than a `FlushAndExit`-equivalent.

- **[Verified]** the code change (idiom replaced) and the persistence of the change in the merged tree.
- **[Verified]** a maintainer filed a regression report pointing at exactly this change.
- **[Unverified / Inference]** the precise mechanism by which logs truncate — this is expected-behavior reasoning about buffered-sink flushing under `os.Exit`, not a guarantee. It warrants a runtime repro.

**Fix:** Route the production exit through a `FlushAndExit`-equivalent while keeping the test seam, e.g. default `exitFunc` to `func(code int){ klog.FlushAndExit(klog.ExitFlushTimeout, code) }`, and drop the separate `klog.Flush()` calls.

### #2 🟠 High: `os.Exit(1)` fired directly from informer events with no debounce/backoff — node deletion and NodeIP change are newly fatal, broadening the cluster-wide restart surface

| | |
|---|---|
| **File** | `pkg/proxy/node.go:159,167,176` (`OnNodeChange` / `OnNodeDelete`) |
| **Category** | availability / behavioral regression |
| **Confidence** | 100 (corroborated ×4 across independent lenses) |
| **Found by** | security (High, THREAT_ATTACK_SURFACE), broad (High + Medium), adversarial (High + Medium, cascade), knowledge (SHOULD, rationale) |

**Issue:** `NodeManager` terminates the process straight from an API-server-driven informer callback, with no debounce, confirmation read, backoff, or rate limit. Two of the three fatal paths are **new behavior** (verified against the removed code in the diff):

- **Node deletion** was previously non-fatal: the old `NodeEligibleHandler.OnNodeDelete` → `SyncNode` set `hs.nodeEligible = false` (health server reports `/healthz` 503, keeps serving rules); the old `NodePodCIDRHandler.OnNodeDelete` only logged. Now `OnNodeDelete` unconditionally `os.Exit(1)`s.
- **NodeIP change** was never watched: the old `getNodeIPs` fetched IPs once at startup. Now any `reflect.DeepEqual` difference in derived NodeIPs crashes the process — and `GetNodeHostIPs` is **ordering-sensitive** (picks the first address per family), so a benign kubelet/cloud status re-report that only *reorders* addresses triggers a crash.

Blast radius: per-node, one Node write = one proxy exit; cluster-wide, one synchronized Node write/delete (or a spurious relist `Delete` during an API-server/etcd disruption) restarts the **entire dataplane at once**, each replica then re-polling for up to 5 minutes. An oscillating input (flapping IP order, delete/recreate) becomes an unthrottled CrashLoopBackOff. Only PodCIDR-change-crash is carried over unchanged from the prior code.

The PodCIDR-restart rationale used to be anchored by `// https://issues.k8s.io/111321`; that reference is now gone (verified via grep), and no comment records *why* a crash-restart is chosen over in-place reconfiguration for delete/NodeIP changes — a future maintainer will reasonably "soften" `OnNodeDelete` back to a drain with no signal that the crash is deliberate. On the live PR, `/kind cleanup` is the only label, yet this is a functional expansion.

**Fix:** Don't exit directly from the event handler for delete/NodeIP-change. Options: debounce/confirm the change (re-read via lister, require it to persist across N events) before exiting; compare NodeIPs as an order-independent set; restore graceful ineligibility on delete; add jittered backoff so oscillating inputs can't drive an unbounded crash-loop. At minimum, document the crash-vs-reconfigure decision and its blast radius on `OnNodeChange`/`OnNodeDelete`, and restore the 111321 reference on the PodCIDR path. (This audit does not assert crash-on-change is wrong — kube-proxy binds much startup config to NodeIPs — only that it is undebounced, newly broadened, and undocumented.)

### #3 🟡 Medium: Baseline poisoning — `OnNodeChange` replaces `n.node` before validating NodeIPs, causing a spurious crash on recovery from a transient un-parseable node status

| | |
|---|---|
| **File** | `pkg/proxy/node.go:145` |
| **Category** | correctness / error-handling |
| **Confidence** | 75 — **validator CONFIRMED** |
| **Found by** | adversarial (High) — *unique* |

**Issue:** `n.node = node` (line 145) executes unconditionally under the lock **before** `nodeIPs, err := utilnode.GetNodeHostIPs(node)` and its error return at lines 159-163. An independent validator traced the chain against `pkg/util/node.GetNodeHostIPs` (returns an error when no `NodeInternalIP`/`NodeExternalIP` parses) and confirmed it end-to-end:

1. `n.node` holds a node with valid IP `X`.
2. A transient Update carries a node whose addresses don't parse → `oldNodeIPs`=`[X]` is computed correctly, then `n.node` is **poisoned** to the bad node; `GetNodeHostIPs` errors → handler logs and returns at line 162 (no crash *yet*).
3. A later Update restores IP `X` → `oldNodeIPs` now derives from the poisoned `n.node` (→ `nil`), `nodeIPs`=`[X]`, `reflect.DeepEqual(nil, [X])` is false → `n.exitFunc(1)` fires — **a spurious crash even though the NodeIP never actually changed from `X`.**

Rated Medium (not High) because the trigger — a node status update with no parseable host IP that then recovers — is uncommon; the consequence is one unnecessary restart, amplified into a crash-loop only if the flapping persists (see #2). Adversarial rated it High.

**Fix:** Only overwrite `n.node` after validating the new node yields IPs. Compute `nodeIPs` first; on `GetNodeHostIPs` error, log and return **without** replacing `n.node`, so the baseline stays the last-good value.

### #5 🟡 Medium: `NodeEligible()` takes an exclusive write lock and deep-copies the whole Node on every `/healthz` probe — hot-path regression; the lock now guards nothing

| | |
|---|---|
| **File** | `pkg/proxy/healthcheck/proxy_health.go:176` |
| **Category** | performance / concurrency |
| **Confidence** | 100 (corroborated ×5) |
| **Found by** | performance (Medium), consistency (Medium), quick (Low), broad (Low), design (Low) |

**Issue:** The rewrite regressed `NodeEligible()` from an O(1) cached-bool read under `RLock` to a full `v1.Node` **DeepCopy** under an **exclusive** `hs.lock.Lock()`, recomputed per request. `healthzHandler.ServeHTTP` calls `NodeEligible()` on every probe; it now (a) takes the write lock even though it touches no `hs.lock`-protected field (the `nodeEligible` field it used to guard was removed in this same diff — the sibling reader `Health()` correctly uses `RLock`), and (b) calls `nodeManager.Node()` which `DeepCopy()`s the entire Node (Status.Images, Conditions, Labels/Annotations, ManagedFields — potentially hundreds of entries) just to read `DeletionTimestamp` and iterate `Spec.Taints`. kube-proxy `/healthz` (:10256) is the node health check fanned in by cloud load balancers fronting LoadBalancer Services, so on a busy node it is probed at tens–hundreds/sec, and the exclusive lock serializes every probe against the `Updated()`/`QueuedUpdate()` data-plane path.

**Fix:** Drop `hs.lock` from `NodeEligible()` (it protects nothing here), and avoid the DeepCopy: either have `NodeManager` compute an `eligible bool` inside `OnNodeChange`/`OnNodeDelete` (the rare write path) and expose a lightweight accessor, or add a `NodeManager` method that reads `DeletionTimestamp`/`Taints` directly under `nodeManager.mu` without copying.

### #7 🟢 Low: `newNodeManager` returns `err` instead of `pollErr` — fragile invariant; latent nil-manager/nil-error → panic one refactor away

| | |
|---|---|
| **File** | `pkg/proxy/node.go:107` |
| **Category** | error-handling |
| **Confidence** | 50 (not a live bug; latent + maintainer-raised) |
| **Found by** | broad (Medium), adversarial (Low), go (Low), prior-feedback (Low), quick (dismissed) |

**Issue:** The poll does `pollErr := wait.PollUntilContextCancel(...)` but on failure does `if pollErr != nil { return nil, err }` — checking one variable, returning another. This is **safe today**: `immediate=true` guarantees the closure runs ≥1 time and every non-success branch assigns `err` non-nil, so `err` is non-nil whenever `pollErr` is. But the coupling is invisible and fragile — a future `return false, nil` path leaving `err` nil would make `newNodeManager` return `(nil, nil)`, and the caller `newProxyServer` then dereferences `s.NodeManager.NodeIPs()` with no nil guard → nil-pointer panic at boot. Maintainer **@danwinship flagged this pattern** (thread `node.go:108`) and, while conceding it's currently correct, called it weird; the merged code is unchanged.

**Fix:** Return `pollErr` directly (or `if pollErr != nil { if err != nil { return nil, err }; return nil, pollErr }`) to sever the reliance on the outer-var invariant, and/or add a nil guard at the `server.go` call site.

## Specialist Notes

### Threat Model Notes (security-reviewer)

- **Trust boundary**: kube-proxy ingests Node objects (`Spec.PodCIDRs`, `Status.Addresses`, `metadata.labels`) from the API server. Writers relative to kube-proxy: the local kubelet (own Node status, bounded by NodeRestriction admission), controller-manager IPAM (PodCIDR), and any principal with cluster-wide `update/patch/delete nodes`.
- **RBAC surface unchanged**: the new node-scoped informer uses a `metadata.name` field selector — a server-side performance optimization, not a new permission. `system:node-proxier` already holds cluster-wide get/list/watch on Nodes. No new client verbs in the diff (verified).
- **Attack/failure surface change**: two events that were graceful (NodeIP change — previously unwatched; node deletion — previously degraded eligibility) now terminate the process, with no debounce/backoff/rate limit. The sharpest concern is **self-inflicted**: a spurious informer `Delete` or a routine address re-order can crash proxies fleet-wide with no attacker. Not rated Critical because triggering it needs Node write/delete authority (already node-local or admin-level).
- **Positive control**: the topology-label allow-list (`NodeTopologyConfig` extracts only `topology.kubernetes.io/zone`) is good input-minimization — it shrinks the attacker-influenced data reaching `CategorizeEndpoints` and suppresses full resyncs on irrelevant label churn.

### Considered But Not Flagged (all agents)

- **Missing `AddFunc` on `NodeConfig`** (flagged High by quick + consistency) — **validator REFUTED as a defect.** `NewNodeManager` captures the initial node via its startup poll of the same lister/cache, so the dropped Add-replay loses nothing at startup; genuine post-start changes arrive as `UpdateFunc`, deletes as `DeleteFunc`, and the periodic resync (`ConfigSyncPeriod`, validated > 0, default 15m) re-delivers current state via `UpdateFunc` → `OnNodeChange`. Worst case is a **bounded detection delay (≤ ConfigSyncPeriod)** for a change landing in the tiny window between poll and handler registration — not a permanent silent miss. The `NodeTopologyConfig` asymmetry (it *does* register `AddFunc`) is justified: it has no baseline poll and starts from an empty label map. Recorded here rather than as a finding.
- **`rawNodeIPs` nil/empty on poll timeout with nothing logged** (context concern) — resolved by the wiring: `newNodeManager` returns `nil, err` on any poll failure (`node.go:107-108`) before `NodeIPs()` is ever called in `newProxyServer`, and the poll only returns `true` after `GetNodeHostIPs` succeeds. prior-feedback confirmed the author's reasoned decline holds against the code.
- **`server.go` "knows too much about NodeManager internals"** (@danwinship, unresolved) — partially addressed: `WaitForNamedCacheSync` moved into `newNodeManager`; remaining wiring is minimal. Design preference, not a boundary defect.
- **5-minute timeout not configurable** (@adrianmoisey, unresolved) — author declined with reasoning (avoids a "configure everything" pattern, cites precedent). Reasoned decline.
- **Data race on `n.node`** — all accessors take `n.mu`, informer delivery is serialized, `Node()` returns a deep copy; `go test -race` clean. No race.
- **ipvs `OnTopologyChange` not setting `needFullSync`** — the ipvs `Proxier` has no `needFullSync` concept at all (pre-existing architectural difference), not drift introduced here.
