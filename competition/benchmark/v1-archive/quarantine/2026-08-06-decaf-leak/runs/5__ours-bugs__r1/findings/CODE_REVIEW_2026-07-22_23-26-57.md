## Findings

### #1 🔴 Critical: 60 s idle timeout rests on an undocumented, unverified liveness contract with the streamed endpoints

| | |
|---|---|
| **File** | `extensions/copilot/src/platform/networking/common/fetcherService.ts:305` |
| **Category** | knowledge-preservation / unvalidated-assumption |
| **Confidence** | 100 (promoted from 75 — 3 finders incl. specialists; validator confirmed) |
| **Found by** | knowledge-reviewer (MUST → Critical), adversarial-reviewer (Medium — dissenting), broad-reviewer (Low — dissenting) |
| **Validation** | confirmed |

**Issue:** The `SSE_IDLE_TIMEOUT_MS` comment asserts "gaps this long indicate a hung connection" without recording its basis. The safety of 60 s depends on facts recorded nowhere in the code: (a) the maximum legitimate inter-chunk gap for the three wired endpoints — reasoning-model pauses and server-side tool turns can legitimately exceed 60 s unless the server emits keepalives; (b) the watchdog operates on raw transport chunks **below** the SSE parser, so SSE keepalive/comment lines (which `stream.ts:336` explicitly discards at parse level) DO reset the timer — the real invariant is *"every wired endpoint must emit data or keepalive bytes more often than 60 s during legitimate silence,"* and that invariant is uncaptured. Failure directions (adversarial): **false kill** — legit >60 s silence behind a proxy that doesn't forward pings destroys a healthy stream mid-response; **missed detection** — a proxy emitting keepalives while the model-level stream is hung never times out, and no total-duration bound exists (1 byte per 59 s holds the request open indefinitely). The rationale for the specific values lives only in the PR-linked internal issue vscode-internalbacklog#7390, which is inaccessible outside Microsoft. There is also no configuration lever to retune the constants without a release (see #5).

**Fix:** Extend the `SSE_IDLE_TIMEOUT_MS` doc comment to record: (1) the basis for 60 s / 2 min (recover it from internal issue #7390 while reachable; otherwise state "operational estimate, not derived from measured gap/keepalive data"); (2) the invariant: "Liveness is measured on raw transport chunks, so SSE keepalive comment lines reset the timer even though downstream parsers ignore them. Any endpoint wired to withStreamIdleTimeout must emit data or keepalives more often than SSE_IDLE_TIMEOUT_MS during legitimate pauses (e.g., extended thinking, server-side tool turns)." Optionally: verify the heartbeat contract with the wired backends; consider a generous total-stream deadline as a slow-trickle backstop.

### #2 🔴 Critical: The timeout-signaling mechanism (destroy → read resolves `{done: true}` → flag → post-loop throw) is entirely undocumented

| | |
|---|---|
| **File** | `extensions/copilot/src/platform/networking/common/fetcherService.ts:344-373` |
| **Category** | knowledge-preservation / comprehension-risk |
| **Confidence** | 75 |
| **Found by** | knowledge-reviewer (MUST → Critical) |
| **Validation** | confirmed |

**Issue:** The design hinges on a non-obvious WHATWG Streams fact: `stream.destroy()` → `reader.cancel()` **resolves** the in-flight `read()` with `{ done: true }` — it does not reject. A timed-out stream is therefore indistinguishable inside the loop from a normally completed one: the timeout path exits through the very same `if (result.done) break` as clean EOF, and the `timedOut` flag plus the post-`finally` throw are what convert that apparent completion into an error. Nothing in the code states this. The two existing comments cover timer scope only, not the signaling mechanism. A maintainer reading `result.done → break` as "normal end of stream" could plausibly "simplify" the odd-looking post-loop throw (e.g., move it into the timer callback, where it would become a silently lost unhandled rejection) and break the timeout path. Validator confirmed the mechanism trace against `DestroyableStream.destroy()` (fetcherService.ts:284-294) and the spec's `ReadableStreamCancel`/close steps.

**Fix:** Add a comment at the destroy call or above `if (result.done)`:
```typescript
// destroy() resolves the pending iterator.next() with { done: true } rather than
// rejecting it (Streams spec: cancel settles in-flight reads as done). A timed-out
// stream therefore exits the loop through the same break as normal EOF — the
// timedOut flag is what turns that apparent completion into a
// StreamIdleTimeoutError after cleanup.
```

### #3 🟠 High: False-positive test — "consumer break releases the underlying reader lock" cannot detect the regression it names

| | |
|---|---|
| **File** | `extensions/copilot/src/platform/networking/test/node/streamIdleTimeout.spec.ts:142` |
| **Category** | test-quality / false-positive-test |
| **Confidence** | 75 |
| **Found by** | test-reviewer (High) |
| **Validation** | confirmed (validator empirically reproduced both states in an isolated Node script against the production logic) |

**Issue:** The test's title and trailing comment claim it verifies that breaking out of the `for await` loop releases the underlying reader lock, but the only post-break check is that `await stream.destroy()` doesn't throw. `DestroyableStream.destroy()` resolves on **both** branches: `reader.cancel()` on a still-locked reader is a normal non-throwing operation, and `stream.cancel()` on an unlocked stream also resolves. Validator reproduction: with the `await iterator.return?.()` forwarding present, break leaves `locked === false` and destroy takes the unlocked branch; with the forwarding removed (the exact regression the test names), break leaves `locked === true`, destroy takes `reader.cancel()` and **still resolves** — the test passes identically in both worlds.

**Fix:**
```typescript
assert.deepStrictEqual(collected, ['a', 'b']);
// Actually assert the lock was released, not just that destroy() doesn't throw
assert.strictEqual(stream.toReadableStream().locked, false);
```
(`toReadableStream()` exists at fetcherService.ts:253-255; the validator confirmed this assertion discriminates the two states.)

### #4 🟡 Medium: `StreamIdleTimeoutError` is classified only by accident — users get a misleading "check your firewall rules" message for a server-side stall

| | |
|---|---|
| **File** | `extensions/copilot/src/extension/prompt/node/chatMLFetcher.ts:1997` (processError); also `fetcherService.ts:312` (error definition), `fetcherServiceImpl.ts:196` (isFetcherError) |
| **Category** | error-handling / API contract |
| **Confidence** | 100 (promoted from 75 — two specialists; validator confirmed) |
| **Found by** | design-reviewer (Medium), adversarial-reviewer (Medium), quick-reviewer (examined, not flagged — dissenting) |
| **Validation** | confirmed, with the trace corrected |

**Issue:** No code anywhere catches, `instanceof`-checks, or name-matches `StreamIdleTimeoutError` (full-repo grep: only its definition and tests reference it). The PR introduces a named error type precisely so it can be identified, then never wires the identification. Validated actual path (design-reviewer's trace; identical for all three wired call sites): any error thrown while iterating completions gets tagged `err.fetcherId = response.fetcher` (chatMLFetcher.ts:1295/1302) → `isFetcherError()` short-circuits on any truthy `fetcherId` (fetcherServiceImpl.ts:196) → classified `ChatFetchResponseType.NetworkError` → `getUserMessageForFetcherError` finds no fetcher that recognizes the error (they check `e.code`, which this error lacks) and falls back to the generic message: *"Please check your firewall rules and network connection then try again. Error Code: SSE stream timed out after 60000ms…"* — misattributing a server-side hang to the user's firewall, and riding an incidental tagging mechanism a future refactor could silently change. (Adversarial-reviewer's alternative trace — generic `Failed`, retry never engages — was refuted by the validator: classification is NetworkError, and the RetryNetworkErrors experiment defaults to true, gated on caller-supplied `enableRetryOnError`.)

**Fix:** Add an explicit branch in `processError` (name-based, matching the `isAbortError` convention) mapping `StreamIdleTimeoutError` to a retry-eligible category with an accurate user message ("The connection stalled while receiving the response; please try again"), decoupling its classification from the `fetcherId` side channel.

### #5 🟡 Medium: Fixed module-level timeouts with no per-call-site or experiment-based configurability — BYOK/local endpoints with long TTFT get force-killed with no lever

| | |
|---|---|
| **File** | `extensions/copilot/src/platform/networking/common/fetcherService.ts:303` |
| **Category** | design / evolution-readiness |
| **Confidence** | 75 |
| **Found by** | design-reviewer (Medium); knowledge-reviewer examined and dismissed ("parametrizing later is a safe, obvious change" — dissenting); broad-reviewer raised the missing lever inside finding #1 |
| **Validation** | confirmed |

**Issue:** `withStreamIdleTimeout` takes no options: the 2 min/60 s budgets are fixed constants shared by three different API families, with no configuration or experiment gate — contrary to the adjacent convention (retry-on-network-error next door is experiment-gated via `ConfigKey.TeamInternal.RetryNetworkErrors`, configurationService.ts:855). Validator traced the concrete harm path: BYOK local providers (e.g., `OllamaLMProvider` → `AbstractOpenAICompatibleLMProvider` → `OpenAIEndpoint` extends `ChatEndpoint` → `processResponseFromChatEndpoint`, chatEndpoint.ts:359-378 → `SSEProcessor.processSSE` → the wrapped loop at stream.ts:323). A large local model on modest hardware can legitimately exceed 2 minutes of prompt-eval before the first chunk; those streams are force-destroyed with no per-endpoint or remote lever — tuning requires editing shared constants affecting every consumer, or a new release.

**Fix:** Accept an optional `{ firstChunkTimeoutMs, idleTimeoutMs }` parameter defaulting to the current constants, and thread an endpoint-level or experiment-based override through the three call sites.

### P3 🟡 Medium: Watchdog-triggered kills are recorded as outcome `'cancel'` in per-fetch telemetry — indistinguishable from user cancellations

| | |
|---|---|
| **File** | `extensions/copilot/src/platform/networking/common/fetcherService.ts:346` (no-reason destroy) → `:104-107` (outcome classification), `:284-296` (destroy signature) |
| **Category** | observability / data-model |
| **Confidence** | 100 |
| **Found by** | broad-reviewer (Medium), design-reviewer (Low — dissenting) |
| **Validation** | confirmed; validator reattributed pre_existing → true (destroy()'s reason-less API and the outcome classifier predate the PR; the PR adds the new caller that falls into the existing blind spot) |

**Issue:** `DestroyableStream.destroy()` takes no reason and always calls `cancel()` with no argument; the counting TransformStream's cancel handler computes `outcome = reason && !isAbortError(reason) ? 'error' : 'cancel'`, so every watchdog kill records `'cancel'` — identical to a routine user cancellation. Validator verified the reason propagates (as `undefined`) through the `pipeThrough` chain for all three call sites, and that the `FetchEvent`/`onDidFetch` channel carries the outcome field. Caveat that supports the Low dissent: the only production consumer of `onDidFetch` found is a debug-gated status-bar display, not a backend telemetry pipeline — the higher-level `sendGHTelemetryException` in chatMLFetcher does capture the named error, so timeout frequency is not entirely unobservable.

**Fix:** Extend `destroy()` to accept an optional reason forwarded to `cancel()`; have the watchdog pass the `StreamIdleTimeoutError` (its name ≠ 'AbortError', so outcome flips to `'error'`), or add a distinct `'idle-timeout'` outcome.
