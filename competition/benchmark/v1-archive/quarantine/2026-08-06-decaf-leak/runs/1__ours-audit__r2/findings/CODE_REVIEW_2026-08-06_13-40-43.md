## Findings

### #1 🟠 High: `Debug.Assert(rowIdForOrdinal != null)` fires on the legitimate no-rowid path

| | |
|---|---|
| **File** | `src/Microsoft.Data.Sqlite.Core/SqliteDataRecord.cs:393` |
| **Category** | error-handling / logic-regression |
| **Confidence** | 100 |
| **Found by** | quick-reviewer (High), broad-reviewer (High), knowledge-reviewer (High), design-reviewer (High), adversarial-reviewer (Medium), dotnet-reviewer (Low) |

**Issue:** In the old code, `_rowidOrdinal` was assigned `-1` at the top of the scan block, so `Debug.Assert(_rowidOrdinal.HasValue)` was *always* true — a tautology. The new code leaves `rowIdForOrdinal` as `null` whenever the scan finds neither a `rowid` column nor a single-column integer PK, and the very next lines (396–399) explicitly treat `null` as a legitimate, supported outcome (return an in-memory `MemoryStream`). The re-added assert therefore encodes a false invariant ("a rowid ordinal is always found") that the surrounding code immediately contradicts, and it fires on ordinary queries: any blob column whose source has no usable rowid — an expression/computed column, an aggregate, a `WITHOUT ROWID` table, or a composite-PK table. `broad-reviewer` notes existing tests already drive this path (`GetStream_works_with_text`/`_int`/`_float`, `GetStream_works_when_composite_pk`).

**Scope caveat:** `Debug.Assert` compiles out of Release builds, so production Release consumers are unaffected. The impact is on **Debug** configurations — the EF Core / Microsoft.Data.Sqlite test suite and any consumer debugging — where a failed `Debug.Assert` with no debugger attached calls `Environment.FailFast` and aborts the host. The change's own added test does not catch this (it covers only the integer-PK rowid case).

**Fix:** Remove the assertion — `null` is now a valid, explicitly-handled result meaning "no rowid mapping for this table". If an invariant is still wanted, assert the loop's own postcondition (e.g. that a *found* ordinal is in range) rather than non-nullness.

### #2 🟡 Medium: Self-join of one table under two aliases returns the wrong rowid → silently wrong blob bytes

| | |
|---|---|
| **File** | `src/Microsoft.Data.Sqlite.Core/SqliteDataRecord.cs:328` (key), `:339-349` (scan) |
| **Category** | correctness (residual limitation of the fix) |
| **Confidence** | 100 (validator-confirmed; finders rated Medium) |
| **Found by** | test-reviewer (Medium), spec-compliance-reviewer (Medium) — independently; **validator: confirmed** |

**Issue:** The cache key `$"{blobDatabaseName}_{blobTableName}"` and the inner candidate scan both use `sqlite3_column_table_name`, which returns the **base table name**, not the query alias. For a self-join such as `SELECT x.VALUE, y.VALUE FROM A x JOIN A y ON …`, both blob columns resolve to the same key `main_A`, and the scan (which filters candidates by base db+table name only) can pair alias `x`'s blob with alias `y`'s id column. The second blob column then hits `RowIds.TryGetValue` first and reuses the first alias's cached ordinal without re-scanning. Net effect: `GetInt64(rowIdForOrdinal.Ordinal)` reads the rowid from the wrong alias's id column, and `SqliteBlob` opens against the wrong (but still valid) row. Because both aliases' rowids are valid rows in table A, this typically returns **silently wrong bytes** rather than throwing — the same failure class the PR set out to fix (#32747), left unresolved for aliased same-table joins, reachable with plain SQL (no attached databases required).

**Fix:** Make rowid resolution alias-aware — include the blob column's own result ordinal (or resolved alias) in the cache key and in the candidate-column search, so two aliases of the same base table resolve independently. See also #5: an unused `TableName` guard already exists on the cache entry but is never checked.

### #3 🟡 Medium: Ambiguous `_`-separated cache key collides across distinct (database, table) pairs → wrong cached rowid

| | |
|---|---|
| **File** | `src/Microsoft.Data.Sqlite.Core/SqliteDataRecord.cs:328` |
| **Category** | correctness / data-model |
| **Confidence** | 100 (validator-confirmed; finders rated Low–High, dissent noted) |
| **Found by** | adversarial-reviewer (High), quick-reviewer (Medium), knowledge-reviewer (Medium), design-reviewer (Medium), broad-reviewer (Low), dotnet-reviewer (Low); security-reviewer examined and classed it correctness-not-security; **validator: confirmed** |

**Issue:** The key joins database and table names with a bare `_`, which is itself a legal identifier character in SQLite. Distinct pairs collapse to one key: `db="a", table="b_c"` and `db="a_b", table="c"` both yield `"a_b_c"`; adversarial-reviewer's concrete case is `ATTACH … AS main_a` (holding table `b`) plus a main-schema table `a_b`, both selected as blob columns → identical key `"main_a_b"`. The first-resolved column caches a `RowIdInfo` (a result-set ordinal); the second colliding column hits `TryGetValue` and reuses that ordinal **without re-scanning**, so the rowid is read from the wrong table's column and `SqliteBlob` is bound to a mismatched row → silently wrong bytes or a `no such rowid` error. The validator confirmed there is no read-time guard (`RowIdInfo.TableName` exists but is never compared).

**Realistic reachability is narrow** — it requires attached databases or underscore-containing identifiers deliberately arranged to collide — which is why this is rated Medium despite adversarial-reviewer's High. It is nonetheless a real correctness defect through legal SQLite features, and shares a root cause with #2 (the cache does not uniquely identify, nor validate, the source of a cached rowid).

**Fix:** Key the dictionary on a composite that cannot be flattened ambiguously — a `(string database, string table)` `ValueTuple` (correct structural equality, no delimiter), a small equatable struct, or a nested dictionary — instead of a delimiter-joined string.

### #4 🟡 Medium: "No rowid found" result is no longer cached — full scan + `pragma_table_info` query re-runs on every `GetStream`

| | |
|---|---|
| **File** | `src/Microsoft.Data.Sqlite.Core/SqliteDataRecord.cs:396` |
| **Category** | performance (regression) |
| **Confidence** | 100 |
| **Found by** | adversarial-reviewer (High), performance-reviewer (High/Medium), quick-reviewer (Medium), broad-reviewer (Medium), knowledge-reviewer (Medium), design-reviewer (Medium) |

**Issue:** The old code memoized the negative result (`_rowidOrdinal = -1`, a persistent field), so the expensive discovery ran at most once per reader for a no-rowid table. The new code calls `RowIds.Add(...)` **only** on the two success branches (355, 387); when no rowid ordinal is found, nothing is inserted, so `RowIds.TryGetValue` misses on every subsequent `GetStream` call for that (db, table). For a blob column whose table has no usable rowid (expression/computed blob, `WITHOUT ROWID` table, composite-PK table) read across many rows, the entire `FieldCount` scan — including native `sqlite3_table_column_metadata` calls and a `SELECT COUNT(*) FROM pragma_table_info($table)` query per integer-PK candidate (`pkColumns` is a per-call local, so its guard resets each call) — re-executes per read. `GetBytes`/`GetChars` call `GetStream` on every invocation (and the null-buffer length probe calls it too), converting a once-per-reader cost into once-per-row on the no-rowid path. Correctness is unaffected; throughput regresses versus the prior design.

> **Dissent, resolved:** dotnet-reviewer asserted the old design "likewise never memoized the negative result, so it is not a regression." This is a misreading of the diff — the old code set the persistent field `_rowidOrdinal = -1` at the top of the scan block, so `HasValue` short-circuited every later call. Six other reviewers read it correctly; the regression is genuine (though the old memoization was itself globally over-broad, which was part of the original bug).

**Fix:** Cache the negative outcome too — store a sentinel/null-valued entry (or a `RowIdInfo` with `Ordinal = -1`) under `rowidkey` when the scan completes without a hit, mirroring the old `-1` short-circuit, so the scan/metadata/COUNT work runs at most once per (db, table) per reader. (One design decision: nullable dictionary value vs. sentinel.)

### #5 🟢 Low: `RowIdInfo.TableName` is written but never read (dead field — and the missing guard for #2/#3)

| | |
|---|---|
| **File** | `src/Microsoft.Data.Sqlite.Core/SqliteDataRecord.cs:23` |
| **Category** | unused-code / data-model |
| **Confidence** | 100 |
| **Found by** | quick-reviewer (Low), broad-reviewer (Low), knowledge-reviewer (Low), design-reviewer (Low), spec-compliance-reviewer (Low), dotnet-reviewer (Low, nullability angle) |

**Issue:** `RowIdInfo.TableName` is set in the constructor and at both call sites (354, 386) but never read anywhere — only `.Ordinal` is consumed (402); the `SqliteBlob` uses the local `blobTableName` instead (404). The PR's stated intent was to "carry both Ordinal and Table," but the table is already encoded in the dictionary key and the property is inert. It is dead state on every cached entry, misleads a maintainer into believing per-entry table validation exists (it does not — precisely the guard that would catch #2 and #3), and, as a non-nullable `string` populated from `utf8_to_string()` (which can return `null`, per the null-check at `GetName`, line 126), its type annotation is also inaccurate.

**Fix:** Either drop `TableName` and reduce the cache value to the ordinal (`Dictionary<string, int>` / a `ValueTuple` key), **or** actually use it — validate the cached entry's `TableName` against the requested `blobTableName` before reuse, which would defend against the #2/#3 wrong-rowid outcomes.

### Threat Model Notes (security-reviewer)

Negligible security surface. The cache key is used only as an in-memory `Dictionary` key, never in SQL, a path, a command, or a log. The `pragma_table_info($table)` query is safely parameterized via `AddWithValue`; `sqlite3_table_column_metadata` receives db/table/column as discrete C-API args, not interpolated SQL. No trust boundary is crossed — `RowIds` is a per-`SqliteDataRecord` instance field scoped to one query on one connection; a wrong-row read (findings #2/#3) returns data the same caller already has rights to, so the impact is data *correctness*, not cross-principal *exposure*.

### Considered But Not Flagged (all agents)

- **Thread-safety of `RowIds`** (multiple agents) — `SqliteDataRecord` is internal, per-reader, single-threaded; all sibling caches (`_blobCache`, `_typeCache`, `_columnNameOrdinalCache`) follow the same unsynchronized single-owner pattern. No new concurrency contract introduced. Not an issue.
- **`RowIds` never cleared on `Read()`** (broad, design) — the cached value is a column *ordinal*, a function of the statement's stable column layout, so it is correctly row-invariant (matches the old single-field behavior). Correct by design.
- **Unbounded dictionary growth** (performance) — bounded by the distinct (db, table) pairs in one reader's result set (typically 1). Not a leak.
- **Empty-name key `"_"` for expression/computed blob columns aliasing distinct sources** (adversarial) — traced to the negative (MemoryStream) path, not a wrong-rowid path; collapses into finding #4, no separate data-corruption scenario survives.
- **`Dictionary.Add` throw on duplicate key** (dotnet) — reached only inside the `if (!TryGetValue)` miss block, at most once per call (loop `break`s after Add); not reachable as a throw in single-threaded use.
- **Ordinal, case-sensitive default string comparer for the key** (dotnet, raised then dismissed) — key and in-loop filters both derive from the same API on one handle, so casing is internally consistent; no spurious miss/collision from case alone.
- **`RowIdInfo` as a nested class / value-tuple suggestion** (prior-feedback) — ajcvickers suggested a value tuple; the author declined in-thread ("only for readability"). A reasoned human decline, not an unaddressed item. (The resulting unused `TableName` is captured as finding #5.)
- **"Re-add Assert" thread** (prior-feedback) — the assert is present in the final code; the requested change was honored. (That the re-added assert now fires on a legit path is captured as finding #1.)
- **No probes run** — two probes were nominated (test-reviewer: neutralize the key to a constant and confirm the test fails; broad-reviewer: run the no-rowid tests against a Debug build to confirm the assert aborts). Both require building/running; **probe not run: no dotnet SDK available in the environment.** Findings were set from static reasoning and validator confirmation.
