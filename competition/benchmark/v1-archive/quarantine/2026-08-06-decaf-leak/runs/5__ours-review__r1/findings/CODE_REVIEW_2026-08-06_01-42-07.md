## Specialist Notes

### Considered But Not Flagged (all agents)

All four raised candidates are recorded here with the reasoning that removed them from the primary list. Under `evidence=strong` a candidate is tiered down rather than deleted; none of these clear the strong bar (screen ≥80, or ≥60 with two independent finders).

**f01 — REFUTED — `iterator.next()` throws on timeout, so the consumer receives a raw cancellation error instead of `StreamIdleTimeoutError`** (quick-reviewer, High, anchor 75; `fetcherService.ts`, `withStreamIdleTimeout`).
The finding's premise is that the timer's `stream.destroy()` → `reader.cancel()` causes the *pending* `reader.read()` to **reject**, so the error propagates out of the `try` before the trailing `if (timedOut)` check runs. This is incorrect. Per the WHATWG Streams standard, `ReadableStreamDefaultReader.cancel()` **closes** the stream and **resolves** every pending read request with `{ value: undefined, done: true }` — it does not reject them. The actual flow on timeout is: timer fires → `timedOut = true` → `destroy()` → `reader.cancel()` → the pending inner `read()` resolves `{done:true}` → the inner `DestroyableStream` generator breaks and completes → the wrapper's `await iterator.next()` resolves `{done:true}` → `break` → `finally` → `if (timedOut) throw new StreamIdleTimeoutError(...)`. The intended error IS thrown.
This is corroborated directly by the change's own tests: `throws StreamIdleTimeoutError when first chunk never arrives` and `throws StreamIdleTimeoutError when a subsequent chunk stalls` advance fake timers past the deadline and assert `err.name === 'StreamIdleTimeoutError'`. Those assertions can only pass if `cancel()` resolves-as-`done`; had the pending read rejected, the raw cancellation error would surface and the assertions would fail. The PR merged with these tests. [Inference — grounded in WHATWG Streams `cancel()`/`ReadableStreamClose` semantics and the shipped, passing test suite; not executed in this review.]

**f02 = f04 — COLLAPSED — timeout error message reports the wrong timeout type because `isFirstChunk` may be stale at throw time** (broad-reviewer Low anchor 50; typescript-reviewer Medium anchor 50; same underlying claim, `withStreamIdleTimeout` throw site).
For the message to mismatch the timer that fired, `isFirstChunk` would have to change *after* that timer fired. It cannot: `isFirstChunk` is set to `false` only immediately after a chunk is yielded, and yielding only happens on a read for which `clearTimer()` already ran — so (a) a first-chunk timeout can never fire after a chunk has been yielded, and (b) an idle timeout only fires when `isFirstChunk` is already `false` and no further chunk is yielded afterward (the reader is cancelled). The timer↔`isFirstChunk` mapping is therefore always consistent at the throw. The proposed race (a buffered chunk resolving the read *after* the timer fired) is precluded because `cancel()` resolves the post-timeout read as `done` with no value, and in Node the timers phase precedes the poll phase, so a due timer's `destroy()` runs before network data is delivered. Adversarial-reviewer traced this same scenario end-to-end and collapsed it (anchor 0). Worst case even if it could occur: cosmetic message-text only, no behavioral effect. Below the strong bar.

**f03 — COLLAPSED — floating `void stream.destroy().catch(() => {})` is never awaited and races `iterator.return?.()` in the finally** (typescript-reviewer, High, anchor 75; `startTimer` callback + `finally`).
The fire-and-forget `destroy()` with a no-op `.catch()` is intentional watchdog cleanup and cannot produce an unhandled rejection (the `.catch` guards it). The alleged race with the finally's `iterator.return?.()` does not materialize: after a timeout, `reader.cancel()` has already resolved the pending read as `done`, so the inner `DestroyableStream` generator has completed and released its lock before the wrapper's `finally` runs — `iterator.return()` on an already-completed generator is a no-op. `releaseLock()` therefore never sees a pending read, and there is no observable ordering hazard. broad-reviewer independently examined and dismissed the same fire-and-forget call as intentional; adversarial-reviewer traced the cleanup path (scenarios 4–5) and collapsed both. Single surviving finder after that cross-check; below the strong bar.

**f05 — COLLAPSED — concurrent cleanup: `iterator.return?.()` races an in-flight `destroy()` over the reader lifecycle** (typescript-reviewer, Medium, anchor 50).
Same root cause and same resolution as f03 — the two cleanup operations are serialized in practice because the inner generator has already run its `finally` (`releaseLock`, `reader = undefined`) by the time the wrapper's `finally` executes. `destroy()`'s returned promise may still be settling, but it only signals cancel completion and touches no shared state after the lock is released. Adversarial-reviewer's scenario (4) collapsed this at anchor 0.

**Other items dismissed by reviewers and confirmed sound during consolidation:**
- `ReturnType<typeof setTimeout>` portability — resolves to the environment-specific timer type (`NodeJS.Timeout` in the node context); `clearTimeout` accepts it. No unsoundness. (typescript-reviewer)
- `timedOut` one-way latch — intentional: a timeout at any point should surface at the end. Sound. (typescript-reviewer, broad-reviewer)
- Early consumer `break`/`return` (e.g. `stream.ts`'s `return` after `maybeCancel`) — the generator's early-return runs `finally` but correctly skips the trailing `if (timedOut) throw`, so no spurious throw; and no timer is pending at a yield point, so no late `destroy()` of an already-returned stream. (adversarial-reviewer)
- `pipeThrough`/`pipedHead` forwarding of `destroy()` — verified correct at both call-site shapes today (`response.body` has `pipedHead === undefined`; `stream.ts`'s `this.body` is the pipe *result*, not the source). A future caller passing a pipe *source* would get a watchdog that cancels the wrong stream — noted as latent fragility, not a current defect and out of `narrow` reach. (adversarial-reviewer)
- Timeout throw surfacing mid-parse where callers previously saw only clean completion — replacing an indefinite hang with a distinguishable `StreamIdleTimeoutError` is the feature's intent; the changed `for await` loops have no surrounding `try/catch` that would swallow it, so a timeout cannot masquerade as a truncated-but-successful completion. Retry-layer classification of the new error is a question about unchanged code, out of `narrow` reach. (adversarial-reviewer)
