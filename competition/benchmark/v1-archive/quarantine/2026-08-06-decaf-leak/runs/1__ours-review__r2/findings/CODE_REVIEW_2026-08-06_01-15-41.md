## Findings

### #1 🟠 High: `Debug.Assert(rowIdForOrdinal != null)` contradicts the null-check fallback — fires in Debug/CI builds on a reachable path

| | |
|---|---|
| **File** | `src/Microsoft.Data.Sqlite.Core/SqliteDataRecord.cs:393` |
| **Category** | logic / error-handling |
| **Confidence** | 100 — corroborated ×2 (validation waived) |
| **Found by** | broad-reviewer (Critical), dotnet-reviewer (Critical) |

**Issue:** The scan loop only matches a rowid/single-INTEGER-PK column that belongs to the blob's *own* table (`if (tableName != blobTableName) continue;`, line 346). When that column is not present in the result set — e.g. `SELECT blobcol FROM t` with no PK column selected, a `WITHOUT ROWID` table, or a composite-PK table — the loop completes with `rowIdForOrdinal == null`. The very next statement, `Debug.Assert(rowIdForOrdinal != null)` (line 393), then fails, even though line 396 (`if (rowIdForOrdinal == null) return new MemoryStream(...)`) is explicitly designed to handle that null case.

This is a regression introduced by the refactor. The old code set `_rowidOrdinal = -1` at the top of the block, so `Debug.Assert(_rowidOrdinal.HasValue)` always held; the tri-state was `null` = uncomputed, `-1` = computed-but-none, `≥0` = found. The new dictionary only represents "found," so the "computed-but-none" state was lost and the assert now asserts something the code itself knows can be false.

**Severity note:** both reviewers rated this **Critical** (anchor 100). Downgraded to **High** here because `Debug.Assert` is compiled out of Release builds — the shipped NuGet package is unaffected and falls through to the correct fallback. The impact is confined to Debug/CI builds (developer runs, the EF Core/Sqlite test suite), where a reachable, supported query pattern now throws instead of returning the cached-blob fallback. It should still be fixed before merge.

**Fix:** remove the assertion (the null case is legitimate and already handled), or make it reflect reality:
```csharp
// Remove — null is a valid, handled outcome (fallback at line 396):
// Debug.Assert(rowIdForOrdinal != null);
```
(If the negative result is memoized per finding #2, restore the old form `Debug.Assert(rowIdForOrdinal != null)` only after an entry — including a negative sentinel — is guaranteed to exist.)

### #2 🟡 Medium: Negative "no rowid found" result is no longer memoized — repeated O(FieldCount) re-scan (+ a `pragma_table_info` query)

| | |
|---|---|
| **File** | `src/Microsoft.Data.Sqlite.Core/SqliteDataRecord.cs:329` |
| **Category** | performance / behavior regression |
| **Confidence** | 75 — validator: confirmed |
| **Found by** | broad-reviewer (High), dotnet-reviewer (High) |

**Issue:** An entry is added to `RowIds` **only** when a rowid/single-INTEGER-PK column is found (lines 354–355 and 386–387). When the scan finds nothing, `rowIdForOrdinal` stays null and nothing is cached. On every subsequent `GetStream`/`GetBytes` call for the same `(database, table)` blob column, `RowIds.TryGetValue(rowidkey, ...)` misses again and the full O(FieldCount) scan re-runs — including, for INTEGER-PK candidates, a `pragma_table_info` query (line 377). The pre-fix code memoized the negative via the `-1` sentinel, so the scan ran at most once per record. Same root cause as #1: the refactor dropped the "computed-but-none" state.

Scoped to the no-usable-rowid path (which is exactly the fallback-blob scenario), so real but not on the hot path for most queries — hence Medium rather than High.

**Fix:** cache a negative sentinel and test the ordinal, mirroring the old behavior:
```csharp
// after the scan loop, before leaving the `if (!RowIds.TryGetValue(...))` block:
if (rowIdForOrdinal == null)
{
    rowIdForOrdinal = new RowIdInfo(-1, blobTableName);
    RowIds.Add(rowidkey, rowIdForOrdinal);
}
...
if (rowIdForOrdinal.Ordinal < 0)   // instead of `== null`
{
    return new MemoryStream(GetCachedBlob(ordinal), false);
}
```

## Minor Findings

### Consistency

- `src/Microsoft.Data.Sqlite.Core/SqliteDataRecord.cs:328` — **Composite key built by delimiter-join with an in-band separator**: `$"{blobDatabaseName}_{blobTableName}"` can collide when a database or table name contains `_` (e.g. db `foo_bar`/table `baz` vs db `foo`/table `bar_baz` both → `foo_bar_baz`), returning the wrong table's rowid. Latent and low-probability (requires attached databases with underscore names both surfaced as blob columns in one query), so below the strong bar, but a real correctness nit introduced by the change. Prefer a `Dictionary<(string,string), RowIdInfo>` composite key. (quick-reviewer)
- `src/Microsoft.Data.Sqlite.Core/SqliteDataRecord.cs:39` — Field `RowIds` is PascalCase with no explicit access modifier; sibling caches are `_camelCase` private (`_blobCache`, `_columnNameCache`, `_columnNameOrdinalCache`). Rename to `private readonly Dictionary<string, RowIdInfo> _rowIds = new();`. (dotnet-reviewer)
- `src/Microsoft.Data.Sqlite.Core/SqliteDataRecord.cs:28` — Dead member: `RowIdInfo.TableName` is set (lines 354/386) but never read. Because line 346 forces `tableName == blobTableName`, it is always redundant with the key. Remove it (and the `tableName` ctor arg). (broad-reviewer; also noted by dotnet-reviewer)
- `test/Microsoft.Data.Sqlite.Tests/SqliteDataReaderTest.cs:171` — Leftover `Console.WriteLine($"A.ID=... B.ID=...")` debug output in a committed test. Remove it, or replace with real assertions on the non-blob integer reads. (test-reviewer)
- `test/Microsoft.Data.Sqlite.Tests/SqliteDataReaderTest.cs:173` — Comment `//get len of abuff` does not match the code (`var abuff = new byte[2];` allocates a buffer, it does not get a length). (test-reviewer)

## Specialist Notes

### New test — regression-guard validity (test-reviewer)

The new `GetBytes_works_streaming_join` is a genuine regression guard, not a false positive. Pre-fix, the first `GetBytes(1,…)` on `A.VALUE` cached A's rowid ordinal (A.ID=1); the second `GetBytes(3,…)` on `B.VALUE` reused it, so it read table B at rowid 1 — but B's row has ID 1000, so the `Assert.Equal([0x06,0x07], bbuff)` check receives wrong/empty bytes and fails. Distinct rowids (1 vs 1000) and distinct blob contents make the mix-up deterministically observable. The test exercises the table-name dimension of the fix; it does not (and under narrow reach need not) exercise the database-name dimension.

**Probe not run**: the test-reviewer nominated a revert-probe (remove the fix, confirm the test fails). Skipped — building the `Microsoft.Data.Sqlite.Tests` project in this monorepo was out of scope for a static review. Static reasoning above already confirms the guard would fail pre-fix; finding #2's validator independently confirmed the caching behavior.

### Considered But Not Flagged (all agents)

- **`RowIdInfo` is a mutable class with public get/set props** (dotnet-reviewer) — dismissed: it is `internal` and never mutated after construction; a `record`/readonly would be cleaner but is not a defect. Reasonable dismissal; not promoted.
- **Threading / unsynchronized `RowIds` dictionary** (dotnet-reviewer) — dismissed: `SqliteDataRecord` is per-reader and already single-threaded; the dictionary is no worse than the prior scalar field. Reasonable dismissal.
- **No coverage for the no-usable-rowid / `WITHOUT ROWID` case** — noted by broad/test reviewers. Under `reach=narrow` this missing-test observation is out of scope (not reported as a finding); it is the same code path finding #1 shows is broken in Debug.
