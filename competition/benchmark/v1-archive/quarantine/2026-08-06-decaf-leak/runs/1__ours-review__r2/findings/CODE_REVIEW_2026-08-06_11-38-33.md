## Findings

### #1 🟠 High: `Debug.Assert(rowIdForOrdinal != null)` fires on a legitimate, already-handled no-rowid path

| | |
|---|---|
| **File** | `src/Microsoft.Data.Sqlite.Core/SqliteDataRecord.cs:393` |
| **Category** | correctness / null-safety |
| **Confidence** | 100 (validator: confirmed) |
| **Found by** | quick-reviewer (High), broad-reviewer (High), dotnet-reviewer (High), prior-feedback-reviewer (Medium) |

**Issue:** After the cache-miss column scan, the code asserts `rowIdForOrdinal != null`. The scan only assigns `rowIdForOrdinal` inside the `columnName == "rowid"` branch and the `pkColumns == 1L` branch; if the blob's table exposes neither a `rowid` alias nor a single-column INTEGER PRIMARY KEY among the selected columns, the loop falls through with `rowIdForOrdinal` still `null`. This is a **supported** outcome — the very next statement handles it:

```csharp
Debug.Assert(rowIdForOrdinal!=null);           // line 393 — asserts the opposite of...
if (rowIdForOrdinal == null)                    // line 396 — ...the case this branch exists to handle
    return new MemoryStream(GetCachedBlob(ordinal), false);
```

Before this PR, `_rowidOrdinal` was set to `-1` *before* the scan, so the old `Debug.Assert(_rowidOrdinal.HasValue)` was a tautology and could never fire (a `Nullable<int>` assigned `-1` always `HasValue`). Removing that sentinel while keeping the assert flipped it from "always true" to "false on the fallback path." Reachable cases include: a blob column selected without its table's rowid/PK column (`SELECT VALUE FROM A`), `WITHOUT ROWID` tables, composite-PK tables, non-integer PKs, and views/computed columns. Impact is scoped to **Debug builds** (`Debug.Assert` is `[Conditional("DEBUG")]`, stripped in Release), which still includes local dev and `dotnet test` runs.

**Fix:** Remove the assert (the following `if (rowIdForOrdinal == null)` already documents and handles this outcome), or restore an explicit negative-cache sentinel so the invariant genuinely holds again:

```csharp
// Debug.Assert(rowIdForOrdinal != null);   // remove — null is the designed MemoryStream-fallback signal
```

### #2 🟠 High: Negative ("no rowid") result is no longer cached — full scan + `pragma_table_info` query repeats on every `GetStream` call

| | |
|---|---|
| **File** | `src/Microsoft.Data.Sqlite.Core/SqliteDataRecord.cs:328-393` |
| **Category** | performance (regression) |
| **Confidence** | 100 (validator: confirmed, incl. pre-change git history) |
| **Found by** | performance-reviewer (High), broad-reviewer (High), quick-reviewer (Medium), dotnet-reviewer (Medium) |

**Issue:** `RowIds.Add(rowidkey, …)` is only reached inside the two "found a rowid" branches (lines ~355 and ~387). When the scan loop completes **without** a match, `rowIdForOrdinal` stays `null` and nothing is stored under `rowidkey`. Because the outer guard is `if (!RowIds.TryGetValue(rowidkey, out …))`, the next `GetStream` call for the same `{db}_{table}` misses the cache again and re-runs the entire `for (i < FieldCount)` scan — native `sqlite3_column_*` calls per column, `sqlite3_table_column_metadata` per candidate INTEGER column, and a `SELECT COUNT(*) FROM pragma_table_info($table)` command execution. `GetStream` is the streaming-blob path, typically called once per row inside `while (reader.Read())`, so for any blob column whose table lacks a single-column integer PK this turns a once-per-reader cost into a **per-row** cost (an N+1 SQL round-trip pattern) for the life of the reader.

The pre-change code cached the negative result as `_rowidOrdinal = -1` (confirmed against git history), so the scan ran at most once per reader regardless of table shape. This is a regression introduced by the caching-strategy change.

**Fix:** Cache the miss too, so "searched, found nothing" is distinguishable from "never searched":

```csharp
readonly Dictionary<string, RowIdInfo?> RowIds = new();
...
if (!RowIds.TryGetValue(rowidkey, out var rowIdForOrdinal))
{
    ... // unchanged scan
    RowIds[rowidkey] = rowIdForOrdinal;   // cache the miss even when it stays null
}
```

### #3 🟡 Medium: Cache key built by `_`-concatenation can collide across distinct (database, table) pairs

| | |
|---|---|
| **File** | `src/Microsoft.Data.Sqlite.Core/SqliteDataRecord.cs:328` |
| **Category** | correctness / data-integrity |
| **Confidence** | 50 (validator: confirmed mechanism; low real-world probability) |
| **Found by** | broad-reviewer (Medium), quick-reviewer (Low) |

**Issue:** `string rowidkey = $"{blobDatabaseName}_{blobTableName}";` uses a bare `_` separator with no escaping. Two distinct `(database, table)` pairs can produce the same key — e.g. database `main`, table `Foo_Bar` and database `main_Foo`, table `Bar` both yield `"main_Foo_Bar"`. On collision, `RowIds.TryGetValue` returns the `RowIdInfo` computed for the *other* table, so `GetInt64` reads a wrong ordinal and a wrong rowid is passed to the `SqliteBlob` constructor — silently returning the wrong blob data (or an exception). This is the same defect class the PR fixes, re-introduced through key encoding.

Reachability is **low** in practice: it requires an `ATTACH DATABASE … AS <alias>` whose alias plus another table name collide under the underscore delimiter — but underscores are legal and common in both aliases and table names, so it is not impossible. Severity dissent noted (broad Medium vs quick Low); held at Medium because the consequence is silent wrong data.

**Fix:** Use a non-collidable composite key:

```csharp
readonly Dictionary<(string Database, string Table), RowIdInfo> RowIds = new();
...
var rowidkey = (blobDatabaseName, blobTableName);
```

### #4 🟢 Low: `RowIdInfo.TableName` is written at both construction sites but never read

| | |
|---|---|
| **File** | `src/Microsoft.Data.Sqlite.Core/SqliteDataRecord.cs:21` |
| **Category** | unused-code / dead-state |
| **Confidence** | 100 (deterministic — quotable dead-state) |
| **Found by** | broad-reviewer (Medium), quick-reviewer (Low), dotnet-reviewer (Low), spec-compliance-reviewer (Low) |

**Issue:** `RowIdInfo` stores `TableName` (set via the constructor at both cache-insertion sites), but nothing ever reads it back — only `.Ordinal` is consumed (line ~402). The table identity is already encoded in the dictionary key, so `TableName` is redundant dead state carried on every cache entry. It also has a public mutable setter (`{ get; set; }`), overstating its role as a write-once cache record and inviting a future maintainer to assume it is load-bearing (e.g. for cache-hit validation).

**Fix:** Drop `TableName` and store just the ordinal (a plain `Dictionary<…, int>` would suffice), or — if a hit-validation use is intended — make `RowIdInfo` a `readonly record struct` and actually read it back to sanity-check cache hits.

### P1 🟡 Medium: Self-join maps both table aliases to one cache key (still broken after this fix)

| | |
|---|---|
| **File** | `src/Microsoft.Data.Sqlite.Core/SqliteDataRecord.cs:328` |
| **Category** | spec-compliance (uncovered scenario) |
| **Confidence** | 75 |
| **Found by** | spec-compliance-reviewer (Medium, `pre_existing`) |

**Issue:** The key `{db}_{table}` is built from `sqlite3_column_database_name`/`sqlite3_column_table_name`, which return the underlying table's real name, not the query alias. A self-join (`SELECT a.VALUE, b.VALUE FROM T a JOIN T b ON …`) produces two blob columns that both map to the identical key `main_T`. The scan caches one rowid ordinal under that key (the first matching column found), and the second blob read reuses it — the same "wrong rowid reused across a join" failure the bug reports, surfacing for self-joins rather than distinct tables. This scenario was broken before the PR as well (the old single global `_rowidOrdinal` was even weaker), so it is pre-existing; the fix improves distinct-table joins but does not address the self-join shape.

**Fix (future work):** Disambiguate repeated underlying tables — e.g. key the cache by the blob column's own ordinal, or include a per-alias discriminator — or document the self-join limitation. Worth a follow-up issue.
