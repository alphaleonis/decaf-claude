## Findings

### #1 🟠 High: `Debug.Assert(rowIdForOrdinal != null)` fires on the legitimate "no rowid found" path

| | |
|---|---|
| **File** | `src/Microsoft.Data.Sqlite.Core/SqliteDataRecord.cs:393` |
| **Category** | error-handling / production-reliability |
| **Confidence** | 100 (validator: confirmed) |
| **Found by** | dotnet-reviewer (Critical), broad-reviewer (High), quick-reviewer (noted in CBNF) |

**Issue:** Before this change, `_rowidOrdinal` was set to `-1` *before* the search loop, so the old `Debug.Assert(_rowidOrdinal.HasValue)` always held (even when no rowid was found, the value was `-1`, which `HasValue`). The new code starts with `RowIdInfo? rowIdForOrdinal = null;` and only assigns it inside the loop when a `rowid` column or a single-column INTEGER PRIMARY KEY is found for the blob's table. When the result set exposes neither (e.g. `SELECT VALUE FROM A` — a blob column selected without its table's rowid/PK), the loop completes with `rowIdForOrdinal == null`, and the new `Debug.Assert(rowIdForOrdinal != null)` at line 393 fires.

This is a *supported* path — the immediately-following `if (rowIdForOrdinal == null) { return new MemoryStream(GetCachedBlob(ordinal), false); }` is exactly the intended fallback for it. So the assertion now claims an invariant the very next line contradicts. Impact is scoped to DEBUG builds (validator confirmed `Debug.Assert` is `[Conditional("DEBUG")]` and stripped in Release), which includes efcore's own test runs and any consumer building against Debug.

> Severity dissent: dotnet-reviewer rated this Critical. Held at High here because the assert is stripped in Release, so it cannot crash shipped/NuGet consumers — the failure surfaces in Debug/test builds only. Still verdict-blocking.

**Fix:** Remove the assertion (the null case is legitimate and already handled below), or make the invariant genuinely hold by caching a negative sentinel (see #2, whose fix resolves both):
```csharp
// Option A — drop the now-false invariant:
// Debug.Assert(rowIdForOrdinal != null);   // remove

// Option B — cache a "not found" sentinel so the invariant holds AND #2 is fixed:
if (rowIdForOrdinal == null)
{
    rowIdForOrdinal = new RowIdInfo(-1, blobTableName);
    RowIds.Add(rowidkey, rowIdForOrdinal);
}
Debug.Assert(rowIdForOrdinal != null);   // now always true
...
if (rowIdForOrdinal.Ordinal < 0)         // was: rowIdForOrdinal == null
{
    return new MemoryStream(GetCachedBlob(ordinal), false);
}
```

### #2 🟠 High: Negative result no longer memoized — rowid scan + `pragma_table_info` query re-runs on every call for keyless-blob tables

| | |
|---|---|
| **File** | `src/Microsoft.Data.Sqlite.Core/SqliteDataRecord.cs:327-394` |
| **Category** | performance / production-reliability |
| **Confidence** | 100 (corroborated ×2 incl. specialist — validation waived) |
| **Found by** | broad-reviewer (High), performance-reviewer (High), quick-reviewer (noted in CBNF) |

**Issue:** The old code memoized the "no rowid found" outcome by storing `_rowidOrdinal = -1`, so the expensive discovery ran at most once per record. The new code adds an entry to `RowIds` **only when a rowid is found** — the not-found case leaves the dictionary unchanged. Consequently, for a blob column whose table exposes no rowid / single-column INTEGER PK in the result set, every `GetStream` / `GetBytes` / `GetTextReader` call re-executes the full `O(FieldCount)` scan (with a `sqlite3_table_column_metadata` call per candidate) and, for INTEGER-PK candidates, the SQL query `SELECT COUNT(*) FROM pragma_table_info($table) WHERE pk != 0;`.

Reading such a blob column row-by-row across N rows turns a one-time cost into an N× repeated scan-plus-SQL-query — a regression introduced directly by the caching restructure. (Correctness is preserved; this is a throughput defect. In Release builds the Debug.Assert in #1 is stripped, so this path is fully reachable there.)

**Fix:** Cache the negative result too (Option B in #1). Storing a sentinel `RowIdInfo(-1, blobTableName)` under `rowidkey` and switching the fallback test from `== null` to `.Ordinal < 0` restores the single-scan behavior and fixes #1 in the same edit.

## Minor Findings

### Consistency

- `src/Microsoft.Data.Sqlite.Core/SqliteDataRecord.cs:39` — new field `readonly Dictionary<string, RowIdInfo> RowIds` breaks the class's field convention: every sibling field is `private` and `_camelCase` (`_connection`, `_addChanges`, `_blobCache`, `_typeCache`, `_columnNameCache`, `_stepped`, …). Should be `private readonly … _rowIds`. (dotnet-reviewer, Medium — quotable-fact convention violation)
- `src/Microsoft.Data.Sqlite.Core/SqliteDataRecord.cs:23` — `RowIdInfo.TableName` is set in the constructor but never read anywhere in `GetStream` (or elsewhere); the only field used is `Ordinal`. Dead property — remove it (and simplify the constructor), or document why it is retained. (dotnet-reviewer, Low — quotable-fact dead code)

### Residual Risks

- `src/Microsoft.Data.Sqlite.Core/SqliteDataRecord.cs:328` — the cache key `$"{blobDatabaseName}_{blobTableName}"` uses `_` as a separator with no escaping, so distinct `(database, table)` pairs can collide (e.g. db `main_b` + table `c` vs db `main` + table `b_c` → `main_b_c`). A collision inside one result set would stream a blob using another table's rowid ordinal (wrong data). Low probability (needs underscore-bearing schema/table names colliding within a single query) but a genuine latent correctness bug introduced by the new keying scheme. Prefer a composite key — `RowIds` keyed by `(string database, string table)` value tuple — over string concatenation. (quick-reviewer, flagged High; tiered to Minor under `evidence=strong` as a single-finder, low-probability finding)
