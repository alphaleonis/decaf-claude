## Findings

### #1 🟠 High: Node informer event handlers registered after the informer is already running — data race on `eventHandlers`/`topologyLabels`

| | |
|---|---|
| **File** | `pkg/proxy/config/config.go:510` (and `:528`–`535`); same pattern in `NodeConfig` at `:303`/`:333` |
| **Category** | concurrency (data race) |
| **Confidence** | 100 (validator: confirmed) |
| **Found by** | quick-reviewer (High), go-reviewer (High/Medium), adversarial-reviewer (High/Medium), broad-reviewer (High — related init-order framing) |

**Issue:** The refactor moved node-informer startup into `NewNodeManager` — `newNodeManager` calls `thisNodeInformerFactory.Start(wait.NeverStop)` and waits for cache sync (`pkg/proxy/node.go:76-77`). `NewNodeManager` is invoked early during proxy-server construction (`cmd/kube-proxy/app/server.go:211`), so the shared node informer is **already started and cache-synced** by the time handlers are registered much later in `Run()`:

```go
// cmd/kube-proxy/app/server.go:608-611  (runs long after server.go:211)
nodeConfig := config.NewNodeConfig(ctx, s.NodeManager.NodeInformer(), ...)
nodeConfig.RegisterEventHandler(s.NodeManager)
nodeTopologyConfig := config.NewNodeTopologyConfig(ctx, s.NodeManager.NodeInformer(), ...)
nodeTopologyConfig.RegisterEventHandler(s.Proxier)   // appends n.eventHandlers, main goroutine
```

`NewNodeTopologyConfig` registers `handleNodeEvent` via `AddEventHandlerWithResyncPeriod` on that already-synced informer (`config.go:485`). client-go schedules **asynchronous** delivery of the cached Node object to the new listener on a separate goroutine, which runs `handleNodeEvent`:

```go
// pkg/proxy/config/config.go:515-537  (runs on an informer listener goroutine)
if reflect.DeepEqual(n.topologyLabels, topologyLabels) { return }   // :528 read
n.topologyLabels = topologyLabels                                   // :532 write
for i := range n.eventHandlers {                                    // :533 range
    n.eventHandlers[i].OnTopologyChange(n.topologyLabels)           // :535
}
```

Neither `NodeTopologyConfig` (`config.go:465-470`) nor `NodeConfig` (`config.go:276-280`) has a mutex, yet `RegisterEventHandler` (main goroutine) appends to `eventHandlers` while `handleNodeEvent`/`handleChangeNode` (informer goroutines) range over it and mutate `topologyLabels`. That is an **unsynchronized concurrent slice/map access** — a data race the Go race detector will flag. The sibling `ServiceCIDRConfig` (`config.go:367-372`) guards the identical pattern with `mu sync.Mutex`, so this is an inconsistency, not a codebase-wide "informers serialize everything" assumption.

The old code enforced the safe ordering explicitly and the PR **removed** it (diff, removed hunk):

```go
// This has to start after the calls to NewNodeConfig because that must
// configure the shared informer event handler first
currentNodeInformerFactory.Start(wait.NeverStop)
```

**Secondary consequence (the unlikely tail):** if the async cached-node delivery wins the race and runs `handleNodeEvent` *before* `RegisterEventHandler(s.Proxier)` appends the proxier, the proxier is not yet in `eventHandlers`, so it misses the initial `OnTopologyChange`. `n.topologyLabels` is then set to the current value, and the `reflect.DeepEqual` guard at `config.go:528` suppresses every subsequent same-zone event — leaving the proxier with nil topology labels and topology-aware routing effectively disabled for its lifetime (graceful fallback to cluster-wide endpoints, but the optimization silently off). The data-race half is reliable and timing-independent; this lost-notification half is the scheduler-dependent tail.

**Fix:** Restore the ordering invariant the PR removed — register all node handlers (`NodeConfig`, `NodeTopologyConfig`) **before** the node informer factory is started — or guard `eventHandlers`/`topologyLabels` with a mutex (as `ServiceCIDRConfig` does) **and** have `RegisterEventHandler` replay the current `topologyLabels` to a newly-registered handler so a late registration cannot miss the initial state:

```go
type NodeTopologyConfig struct {
    mu             sync.Mutex
    listerSynced   cache.InformerSynced
    eventHandlers  []NodeTopologyHandler
    topologyLabels map[string]string
    logger         klog.Logger
}

func (n *NodeTopologyConfig) RegisterEventHandler(handler NodeTopologyHandler) {
    n.mu.Lock()
    defer n.mu.Unlock()
    n.eventHandlers = append(n.eventHandlers, handler)
    handler.OnTopologyChange(n.topologyLabels) // replay current state to the late handler
}
// ...and take n.mu in handleNodeEvent around the topologyLabels read/write and the eventHandlers range.
```
Apply the equivalent guard to `NodeConfig` (`config.go:303`/`:333`).

## Specialist Notes

### Considered But Not Flagged (all agents)

Consolidated below with the reason each was tiered down. Under `evidence=strong` + `reach=narrow` + `bugs`, only defects introduced by the changed lines and clearing the strong bar are reported as primary; the following are correct/benign, below the bar, or intentional design.

- **Stale/ambiguous error on `newNodeManager` poll timeout** (`pkg/proxy/node.go:107-108`, broad-reviewer, single finder). Analysis: every `return false` branch in the poll closure (node.go:89-102) sets `err` non-nil first, and the only `return true` path leaves `err` nil; with `immediate=true` the condition always runs at least once. So on timeout `err` is reliably non-nil and reflects the actual reason polling never succeeded — which matches the code's own comment ("we return the actual error in case of poll timeout"). Intentional and correct; not wrapping with timeout context is a diagnosability nit, not a defect. Not flagged.
- **`OnNodeChange` skips the NodeIP-change check when `GetNodeHostIPs(node)` fails after `n.node` was already updated** (`pkg/proxy/node.go:159-163`, broad-reviewer, single finder). Real but low-probability: `GetNodeHostIPs` only errors when the node has no addresses at all (unusual for a live node); on that transient failure `n.node` is left as the address-less node and a subsequent IP change could be measured against a broken baseline. Below the `strong` bar (single finder, rare trigger); recorded here rather than reported. Worth a defensive fix if this area is revisited.
- **Missing explicit nil check on `nodeLister.Get` result** (`pkg/proxy/node.go:88-93`, broad-reviewer, single finder). The client-go lister contract guarantees a non-nil object when `err == nil`; adding a nil guard is defensive only. Benign — not flagged.
- **Shared `topologyLabels` map handed by reference to multiple handlers without copying** (`pkg/proxy/config/config.go:532/535`, go-reviewer, confidence 75). Verified benign by broad-reviewer and adversarial-reviewer independently: each event allocates a *fresh* map (`config.go:522`), and consumers only read it — no post-publish mutation, so no aliasing race today. Speculative ("future modifications could…"), so not an introduced defect. Not flagged.
- **`NodeManager.OnNodeDelete` → `os.Exit(1)`** (`pkg/proxy/node.go:176-180`, adversarial-reviewer). A genuine behavioral change (the old per-proxier/eligibility path tolerated node-object deletion and went 503-ineligible; the new code hard-exits), but this is the PR's explicit, documented intent — a design decision, out of "introduced defect" reach. Not flagged.
- **`NodeTopologyConfig` has no `Run()`/cache-sync wait like `NodeConfig`** (broad-reviewer, framed as its own High). Folded into finding #1 — it is the same root cause (handlers active against an already-started informer with no synchronization/replay), not a separate defect.
