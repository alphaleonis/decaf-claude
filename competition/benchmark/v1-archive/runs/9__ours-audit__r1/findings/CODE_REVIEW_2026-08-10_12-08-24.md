### #1 🟠 High: NodeTopologyConfig handler is registered *after* the node informer is already started — data race on `eventHandlers` and the initial topology labels can be permanently lost

| | |
|---|---|
| **File** | `cmd/kube-proxy/app/server.go:610-611` (wiring); `pkg/proxy/config/config.go:515-537` (`handleNodeEvent`), `:508-511` (`RegisterEventHandler`); `pkg/proxy/node.go:76-77` (informer `Start`) |
| **Category** | async / concurrency |
| **Confidence** | 100 (validator **CONFIRMED**) |
| **Found by** | adversarial-reviewer (High), design-reviewer (Medium) |

**Issue:** `NewNodeManager` calls `thisNodeInformerFactory.Start(...)` and `WaitForNamedCacheSync` **inside `newProxyServer`** — the node informer is running before `Run()` is entered. `NewNodeTopologyConfig` then calls `AddEventHandlerWithResyncPeriod` on that already-started informer, so client-go asynchronously replays the cached Node as a synthetic `Add` on a newly-spawned processor goroutine. `RegisterEventHandler(s.Proxier)` (a plain `append` to `n.eventHandlers`, no mutex) runs on the main goroutine *after* that. Two defects fall out:

1. **Data race** — the informer goroutine ranges `n.eventHandlers` in `handleNodeEvent` while the main goroutine appends to it in `RegisterEventHandler`, with no synchronization (`NodeTopologyConfig` has no mutex). `go test -race` over the real registration-after-start sequence would flag this.
2. **Lost initial labels** — if the replayed `Add` runs before the proxier is registered, `handleNodeEvent` sets `n.topologyLabels` to the current zone but notifies no handler; every later resync then hits the `reflect.DeepEqual` dedup early-return (`config.go:528`), so the proxier **never** receives the initial topology labels until the zone label actually changes — silently disabling topology-aware routing (`PreferSameZone`/`TopologyAwareHints`) at startup.

The validator confirmed the old code did the opposite and safe thing: it created the node informer factory, called `RegisterEventHandler` first, and only then `Start()`, with the comment *"This has to start after the calls to NewNodeConfig because that must configure the shared informer event handler first."* The sibling `ServiceConfig`/`EndpointSliceConfig` paths still register-then-start. This PR broke that invariant for the node path by hoisting `Start` into `NewNodeManager`. The added `TestNewNodeTopologyConfig` registers the handler *before* `Start`, so it exercises the safe ordering and does not cover the production sequence.

**Fix:** Restore the register-before-start ordering for the node informer (do not `Start` inside `NewNodeManager`, or defer the topology handler registration until after `RegisterEventHandler`), OR guard `eventHandlers` with a mutex **and** re-emit the current `topologyLabels` to any handler registered after an event was already processed, gated behind a `Run()`/`WaitForNamedCacheSync` step (see #5). This finding and #5 share a root cause and can be fixed together.

### #2 🟡 Medium: kube-proxy now hard-exits (`os.Exit`) on **any** NodeIP change — a new, undebounced restart trigger

| | |
|---|---|
| **File** | `pkg/proxy/node.go:159-172` (and `:176-180` for node delete) |
| **Category** | reliability / resource-management / availability |
| **Confidence** | 100 (validator **CONFIRMED**) |
| **Found by** | broad-reviewer (Medium), security-reviewer (Medium), adversarial-reviewer (Medium), quick-reviewer (residual) |

**Issue:** Pre-PR, node IPs were fetched **once** at startup (`getNodeIPs`, now deleted) and never watched — a post-startup NodeIP change produced no restart. `OnNodeChange` now calls `n.exitFunc(1)` (== `os.Exit`) whenever `!reflect.DeepEqual(oldNodeIPs, nodeIPs)`, with no debounce, cooldown, or minimum-uptime guard, and `OnNodeDelete` now exits unconditionally (previously delete only marked the health endpoint). Consequences: legitimate NodeIP churn (gaining/losing a second-family Internal/External IP) forces a restart; because `GetNodeHostIPs` preserves `Status.Addresses` order, any reordering of an equivalent address set compares unequal and triggers a spurious exit ([Inference] whether kubelet/cloud providers reorder in practice — not verifiable from this repo); repeated triggers drive the DaemonSet into CrashLoopBackOff, during which Service/EndpointSlice updates are not reconciled. Node addresses are influenceable across a trust boundary (kubelet under NodeRestriction; any principal with `update/patch nodes`).

Exit-on-change is intentional design (the `NodeManager` doc says it "crashes kube-proxy… on changes"); the **no-dampening / spurious-change** concern is a separate, valid reliability layer on top.

**Fix:** Add application-level dampening — a minimum-run-time / restart budget, a short debounce collapsing rapid flaps, and/or require the change to persist across a resync before exiting; and/or compare only the proxy-relevant IP set order-insensitively so reordering isn't a "change." At minimum document the availability trade-off and the NodeRestriction/RBAC assumptions the design relies on.

### #3 🟡 Medium: `OnNodeChange` advances the baseline (`n.node = node`) before validating NodeIPs → spurious `exit(1)` after a transient bad-address update

| | |
|---|---|
| **File** | `pkg/proxy/node.go:140-172` |
| **Category** | error-handling / correctness |
| **Confidence** | 75 (validator **CONFIRMED**) |
| **Found by** | adversarial-reviewer (Medium) |

**Issue:** Under the lock, `n.node = node` (line 145) executes unconditionally **before** the NodeIP validation at lines 159-163; when `GetNodeHostIPs(node)` errors it logs and returns without exiting, but `n.node` is already poisoned with the bad node. On the next event, `oldNodeIPs` is recomputed from that poisoned node → `nil`; if that event restores the original IPs `[A]`, `reflect.DeepEqual(nil, [A])` is false → spurious `exitFunc(1)`, even though the real IPs went `A → (transient empty) → A`. `GetNodeHostIPs` returns `(nil, error)` when `Status.Addresses` has no parseable Internal/External IP, so a transient kubelet address clear is a real trigger. `TestNodeManagerOnNodeChange` only tests single-event transitions, so nothing guards this.

**Fix:** Only advance `n.node` after NodeIPs are successfully retrieved (validate `GetNodeHostIPs(node)` before storing), or compute `oldNodeIPs` from a stored last-*valid* IP set rather than re-deriving from a possibly-invalid `n.node`.

### #4 🟡 Medium: startup now hard-fails (blocking up to 5 minutes) when the node has no usable NodeIP — graceful loopback fallback lost; timeout comment only mentions PodCIDR

| | |
|---|---|
| **File** | `pkg/proxy/node.go:56-61`, `:84-109`; `cmd/kube-proxy/app/server.go:210-220` |
| **Category** | reliability / evolution |
| **Confidence** | 75 |
| **Found by** | quick-reviewer (Medium), broad-reviewer (Medium) |

**Issue:** The removed `getNodeIPs` retried ~1 min then returned `nil` **without error**, letting `Run` continue and fall back to the bind address (loopback). `NewNodeManager` now blocks in `wait.PollUntilContextCancel` and, on timeout, returns an error that aborts startup. Two sub-points: (a) the timeout is hard-coded `5*time.Minute` for all cases but its comment only justifies PodCIDR allocation — when `watchPodCIDRs` is false, that 5-minute wait now also gates NodeIP availability, lengthening the old ~1-minute NodeIP wait; (b) if the informer never syncs, `WaitForNamedCacheSync` returns false → hard startup abort with no retry. A slow-to-get-an-IP node now CrashLoopBackOffs until it has an IP where it previously started degraded.

**Fix:** Document that startup now requires a NodeIP within the timeout (a real semantic change), and either give the NodeIP wait its own shorter timeout distinct from the PodCIDR-allocation timeout, or update the comment to state the timeout now also bounds NodeIP availability.

### #5 🟡 Medium: `NodeTopologyConfig` diverges from every sibling `*Config` — no `Run()`, dead `listerSynced`, no cache-sync gate

| | |
|---|---|
| **File** | `pkg/proxy/config/config.go:464` (struct), `:503` (`listerSynced = handlerRegistration.HasSynced`); `cmd/kube-proxy/app/server.go:607-614` |

| **Found by** | consistency-reviewer (Medium), design-reviewer (Medium), quick-reviewer (Low) |

**Issue:** `ServiceConfig`, `EndpointSliceConfig`, `NodeConfig`, and `ServiceCIDRConfig` each expose a `Run()` that calls `cache.WaitForNamedCacheSync` on their `listerSynced`, and server.go starts each with `go X.Run(...)`. `NodeTopologyConfig` has **no** `Run()`; its `listerSynced` is written in `newNodeTopologyConfig` but **never read**; server.go calls only `RegisterEventHandler`, no `Run`. ### #6 🟡 Medium: the exit-on-change contract and its supervisor-restart assumption are undocumented; crash-on-NodeIP-change is new

| | |
|---|---|
| **File** | `pkg/proxy/node.go:41-51` (doc), `:140-180` |
| **Category** | knowledge-preservation |
| **Confidence** | 75 |
| **Found by** | broad-reviewer (Medium), knowledge-reviewer (SHOULD) |

**Issue:** The whole `NodeManager` design crashes the process on NodeIP/PodCIDR change and node deletion. The doc records the *behavior* ("crashes kube-proxy") but not the load-bearing assumption that makes it safe — that kube-proxy runs under a supervisor (DaemonSet/static pod/systemd) that restarts it so new node config is picked up at startup — nor the rationale for restart-over-live-reconfigure. Crash-on-NodeIP-change is a *new* decision (old code fetched NodeIPs once and never watched). A future maintainer could "improve" this into live reconfiguration not realizing crash-and-restart was deliberate, or run kube-proxy without a restarting supervisor, where `os.Exit(1)` on a routine refresh permanently removes proxying.

**Fix:** State the assumption and rationale in the `NodeManager` doc comment (why exit rather than reconfigure; that a supervisor is expected to restart the process).

### #11 🟢 Low: `handleNodeEvent` hands its internal `topologyLabels` map by reference to every handler (co-owned mutable map, undocumented immutable-after-publish contract)

| | |
|---|---|
| **File** | `pkg/proxy/config/config.go:532-536` |
| **Category** | api-contract / design |
| **Confidence** | 50 |

**Issue:** `handleNodeEvent` sets `n.topologyLabels = topologyLabels` and passes that same map instance to each proxier, which stores the reference; `metaProxier` shares one instance across its ipv4/ipv6 proxiers. ### #16 🟢 Low: `TestNewNodeManager` couples correctness to wall-clock sleeps vs. the poll interval (flaky/slow under load)

| | |
|---|---|

| **Confidence** | 50 |

## Specialist Notes

### Threat Model Notes (security-reviewer)

- **Trust boundary:** kube-proxy consumes the Node object from the API server. Writers of the relevant fields: kubelet (own Node `status.addresses`, some labels, under NodeRestriction), node-ipam controller (`spec.podCIDRs`), and any RBAC principal with `update/patch nodes`. `spec.podCIDRs` is not kubelet-settable, so PodCIDR-triggered exits realistically require control-plane actors.
- **Net direction of this PR:** topology-label narrowing (full `nodeLabels` → zone-only `topologyLabels`) is a genuine **attack-surface reduction**. The `os.Exit` centralization is an **availability surface increase**: a previously-ignored condition (NodeIP change after startup) becomes a process crash. Safety rests on (a) kubelet CrashLoopBackOff as incidental rate-limiting and (b) NodeRestriction+RBAC — neither enforced by the changed code. See #2.
- No secrets, PII, crypto, new listeners, or untrusted-payload deserialization introduced.

### Considered But Not Flagged (all agents)

- **Prior-feedback / nojnhuh report — REFUTED, kept informational.** A human reviewer (`nojnhuh`) commented post-merge on the actual PR that it "seems to have broken creating clusters," suspecting the change from `klog.FlushAndExit(klog.ExitFlushTimeout, 1)` to `klog.Flush()` + `os.Exit`. The diff is real, but validation **refuted the suspected mechanism**: `FlushAndExit` runs `Flush()` in a goroutine and *races it against a timeout* (can truncate and exit early), whereas sequential `klog.Flush(); os.Exit(1)` blocks until `Flush()` fully returns — i.e. at least as thorough at preserving output. The finding's secondary "silent poll-timeout path" claim is also wrong: `newNodeManager` returns an error on timeout that is logged by `opts.logger.Error(err, "Error running ProxyServer")` in `cmd/kube-proxy/app/server.go` RunE (pre-existing, unchanged). The unresolved human report is recorded here for follow-up, but there is no verifiable code-level log-loss regression. `[Inference]` on klog internals; the thread's existence is verified from the PR.
- **`newProxyServer` returning `(nil, nil)` → nil-deref** — traced: every poll-false branch sets `err` non-nil, and `PollUntilContextCancel(immediate=true)` runs the condition at least once, so `return nil, err` cannot yield `(nil, nil)`. Unreachable (multiple reviewers).
- **Hollow-proxy nil `NodeManager`** — `HealthzServer` stays nil on the hollow path and `Run` nil-guards node config; `NodeEligible()` is never reached with a nil manager. Latent implicit non-nil contract only.
- **`topologyLabels` empty-map vs nil / torn map read** — `handleNodeEvent` always builds a non-nil map and replaces the reference wholesale (never mutates in place); proxier reads under `proxier.mu`, writes under the same lock. No torn read; nil-map index in `CategorizeEndpoints` is a safe read returning "".
- **winkernel `OnTopologyChange` no-op (TODO)** — carries forward the pre-existing `NoopNodeHandler` behavior; not a regression introduced here.
- **ipvs `OnTopologyChange` not setting `needFullSync`** — ipvs has no `needFullSync` concept; consistent, not an omission.
- **`reflect.DeepEqual(nil, []string{})` PodCIDR edge (node.go:151)** — apiserver JSON decoding yields nil consistently for an omitted field; not realistically triggerable (anchor 25).
- **Performance** — no findings at bar; the change is net cost-neutral-to-positive (no additional node watch — `NodeConfig` and `NodeTopologyConfig` share the one `NodeManager` informer; the old full-label `DeepEqual`+copy on every node update is replaced by a 0–1-entry topology-map compare that suppresses spurious full resyncs).
