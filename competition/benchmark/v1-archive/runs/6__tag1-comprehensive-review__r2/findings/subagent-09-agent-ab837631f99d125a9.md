## Adversarial Review

### Summary

This PR wires up a cross-window remote FS proxy plus a "download remote files to local temp on copy" behavior, but the copy path is unbounded and eager, and the proxy routing has no timeout/readiness handling. The single worst problem: **every Ctrl+C/Ctrl+X on a remote file or folder now synchronously downloads the entire tree into the user-data directory, with no size bound, no progress UI, and no cancellation — even for a plain copy-within-the-same-remote that never needed a local copy.** A close second is a silent correctness regression where **cut (move) of a remote file no longer removes the original.**

### Findings

#### Critical

- **[other]** Eager, unbounded, synchronous remote download on every copy/cut — `src/vs/workbench/contrib/files/browser/explorerService.ts:298-316`
  - **What's wrong/missing:** `setToCopy` (called by both `copyFileHandler` and `cutFileHandler`, `fileActions.ts:1059/1068`) awaits `resolveClipboardResources`, which for any non-`file://` resource runs `fileService.copy(resource, target, true)` for each selected item. Confirmed: `copy` recurses over folders (`fileService.doCopyFolder`) and streams every file in 256 KB chunks across the remote→local provider boundary, writing into `environmentService.cacheHome` = `URI.file(userDataPath)` (the user profile dir, not OS temp). There is no size cap, no file-count cap, no `progressService` wrapping, and no cancellation token. The copy command's `await` does not resolve until the whole download completes.
  - **Why it matters:** Copying a large remote file or an entire remote folder blocks the copy gesture for as long as the download takes, with zero UI feedback, and can fill the user-data volume with a full local duplicate of the remote tree. It fires on *every* copy/cut of a remote resource — including the overwhelmingly common case of copy-and-paste *within the same remote window*, which needs no local copy at all — and it happens even if the user never pastes. On metered/slow links this is real cost and latency for an action the user thinks is instantaneous.
  - **Fix:** Do the download lazily/on-paste rather than on-copy, or gate it behind a size/count threshold with a cancelable `progressService.withProgress` and a user-visible notification. Only materialize a local copy when the paste target actually requires `file://` (native paste). Rejected alternative: keeping eager download but adding a progress bar — still pays full download cost on same-remote paste and on copies that are never pasted, so it does not address the core waste.
  - **Confidence:** 90/100

#### High

- **[other]** Cut (move) of a remote file silently becomes a copy — the original is never removed — `src/vs/workbench/contrib/files/browser/explorerService.ts:275` + `src/vs/workbench/contrib/files/browser/fileActions.ts:1190-1224`
  - **What's wrong/missing:** `cutFileHandler` sets `pasteShouldMove = true` and calls `setToCopy(stats, cut=true)`. For remote items the clipboard is now populated with **local temp `file://` copies**, not the remote URIs. On paste, `getFilesToPaste` reads those temp URIs (`fileActions.ts:1318`), and the move edit is built as `new ResourceFileEdit(pair.source = tempFile, pair.target = remoteDest, …)`. The move therefore operates on the *temp copy*; the original remote file (a URI never referenced in the edit) is left in place. Before this PR, `setToCopy` wrote the remote URIs directly, so cut+paste was a true remote move that deleted the source.
  - **Why it matters:** "Cut" silently degrades to "copy" for remote files. The user believes they moved a file; the original remains behind. This is a silent behavior/correctness regression on a destructive-feeling operation, with no error surfaced.
  - **Fix:** Do not substitute temp copies for cut operations; keep remote URIs on the clipboard when `cut === true`, or special-case move so the original remote resource is the move source. Rejected alternative: deleting the original after paste from the temp path — fragile (paste can target another window/process; the explorer that did the cut may be gone), and easy to turn into actual data loss.
  - **Confidence:** 80/100

- **[edge-case]** Partial download failure mid-loop duplicates resources on the clipboard — `src/vs/workbench/contrib/files/browser/explorerService.ts:308-323`
  - **What's wrong/missing:** The loop pushes each successfully-copied `target` (temp `file://`) into `result`. If copy N throws mid-loop, the `catch` does `result.push(...remoteResources)` — appending **all** remote resources, including the ones already pushed as temp copies. `result` ends up as `[…locals, temp0, remote0, remote1, …]` where `remote0` is a duplicate of `temp0`. Because the set is now mixed (has a non-`file://` entry), `writeResources` takes the `code/file-list` path and writes every entry.
  - **Why it matters:** Paste then materializes the same file twice (once from the temp copy, once via the proxy), producing duplicate files (`index.ts` + `index copy.ts`) and a confusing mixed temp/remote result. The failure that triggered this is invisible to the user beyond a `logService.warn`.
  - **Fix:** In the fallback, push only the remotes that were *not* already copied (track successes), or discard partial temp results entirely and fall back to the full remote set with no temp entries. Rejected alternative: leaving the partial temp files and just appending remotes — that is exactly the current duplicating behavior.
  - **Confidence:** 85/100

- **[edge-case]** Proxy call hangs forever if the target window closes or reloads between lookup and call — `src/vs/platform/files/electron-main/remoteFileSystemProxyMainHandler.ts:34-44`
  - **What's wrong/missing:** `call` resolves a `targetWindow` from `getWindows()`, then calls `electronIpcServer.getChannel(name, client => client.ctx === 'window:{id}')` and invokes `.call(command, arg)`. Confirmed in `ipc.ts` `IPCServer.getChannel`: the client filter is evaluated *at call time*; if no connected client matches, the code falls to `Event.toPromise(Event.filter(onDidAddConnection, filter))` — it **waits indefinitely** for a matching client to (re)connect, with no timeout and no rejection. If the target renderer closes, or is mid `Reload Window` (the window stays in the map with the same id while its renderer restarts), the routed `.call()` never resolves.
  - **Why it matters:** Any proxy `stat`/`readdir`/`readFile` in the local window (e.g. a cross-window paste that fell back to the proxy) hangs forever with no error, no timeout, and no cancellation — a wedged paste/DnD with no diagnostic.
  - **Fix:** Wrap the routed call with a `CancellationToken`/timeout, and reject fast when no matching connection is present rather than waiting on `onDidAddConnection`. Rejected alternative: relying on the existing 1000ms `ChannelServer` timeout — that only fires once a connection is found but the *channel* is missing; it does not cover the "no matching connection at all" wait.
  - **Confidence:** 85/100

- **[other]** Proxy provider is re-registered on every `vscode-remote` activation → throws, spams errors, and leaks provider instances — `src/vs/platform/files/electron-browser/remoteFileSystemProxyClient.ts:110-123`
  - **What's wrong/missing:** The `onWillActivateFileSystemProvider` listener registers a new `RemoteFileSystemProxyClient` each time the event fires for `vscode-remote`. Confirmed: `FileService.activateProvider` fires this event **unconditionally on every resource access** (the "already registered" early-return happens *after* the fire), the listener is never removed after a successful registration, and there is no `fileService.getProvider(vscode-remote)` guard. `registerProvider` **throws** if a provider for the scheme already exists. So the second and every subsequent activation constructs a provider, `disposables.add(provider)`, then throws in `registerProvider` — caught and logged as `error`. Concurrent activations before the first registration completes hit the same throw.
  - **Why it matters:** After the first remote access, every further `vscode-remote` access in a local window logs an error and leaks a constructed provider (with its `Emitter`) into the window-lifetime `DisposableStore`. Over a session this is unbounded log noise plus a slow memory leak.
  - **Fix:** Guard with `if (fileService.getProvider(Schemas.vscodeRemote)) return;` before constructing, and dispose the listener after the first successful registration (or register once eagerly). Rejected alternative: swallowing the "already registered" error silently — hides the leak and still constructs a provider per access.
  - **Confidence:** 80/100

#### Medium

- **[edge-case]** Routing ignores window readiness / reload state — `src/vs/platform/files/electron-main/remoteFileSystemProxyMainHandler.ts:46-54`
  - **What's wrong/missing:** `findWindowForAuthority` returns the first window whose `remoteAuthority` matches, with no `isReady` check. Confirmed: `getWindows()` returns windows that are created-but-not-yet-loaded and windows that are closing, and two windows can share the same `remoteAuthority` (`getRandomElement` in `getChannel` then picks one arbitrarily). Routing to a window whose renderer hasn't yet registered the `remoteFileSystemProxy` server channel yields a 1000ms channel timeout; routing to a still-connecting/closing window yields the indefinite hang above.
  - **Why it matters:** Non-deterministic failures/timeouts when more than one matching window exists or when a window is starting up/reloading, with no fallback to a healthy sibling window.
  - **Fix:** Filter to `window.isReady` windows and, among multiple matches, prefer a ready one; fall back to another match on failure.
  - **Confidence:** 78/100

- **[other]** Temp-dir cleanup is racy and leak-prone — `src/vs/workbench/contrib/files/browser/explorerService.ts:300-306, 565-576`
  - **What's wrong/missing:** (a) `dispose()` calls `cleanupRemoteClipboardTempDir()` without `await` (diff line 605) — a fire-and-forget async `del` during shutdown that may never complete, leaking the temp tree in the user-data dir. (b) A subsequent *all-local* copy has `remoteResources.length === 0`, so cleanup is skipped and the previous remote temp dir is orphaned until the next remote copy or dispose. (c) `setToCopy` is not serialized: two rapid copies race on the single `this.remoteClipboardTempDir` field, so one copy can `del` the directory the other just wrote and is about to place on the clipboard.
  - **Why it matters:** Accumulating orphaned copies of remote files in the profile directory, plus a window where the clipboard references a directory that a concurrent copy is deleting.
  - **Fix:** Track temp dirs in a set and clean all on dispose (awaited via a proper disposable), clean on every copy regardless of remote-count, and serialize `setToCopy` (or key temp state per-invocation).
  - **Confidence:** 78/100

- **[observability]** No visibility into the download; failure silently disables native paste — `src/vs/workbench/contrib/files/browser/explorerService.ts:317-323`
  - **What's wrong/missing:** The only signal for the whole download is a single `logService.warn` on failure. There is no progress indicator, no telemetry on size/duration/failure rate, and on failure the user is silently downgraded to "cross-window paste only" with no notification. There is also no operational way to tell that the eager-download feature is running or how large the copies are.
  - **Why it matters:** In production this feature is invisible: a stuck copy, a filled disk, or a failed native paste all look like "nothing happened." Diagnosing requires adding logging after the fact.
  - **Fix:** Add progress + a warn-level notification on fallback, and telemetry counters for download size/duration/failure.
  - **Confidence:** 75/100

#### Low

- **[other]** Paste order no longer matches selection order — `src/vs/workbench/contrib/files/browser/explorerService.ts:288-316`
  - **What's wrong/missing:** `resolveClipboardResources` pushes all `file://` resources first, then appends remote temp copies, discarding the original selection order (e.g. `[localA, remoteB, localC]` → `[localA, localC, temp_B]`).
  - **Why it matters:** For ordered/multi-file pastes the user-visible order changes for mixed local/remote selections.
  - **Fix:** Preserve input order by mapping each resource in place instead of partitioning.
  - **Confidence:** 80/100

### Additional risks worth testing (below reporting confidence — flagged, not asserted)

- **Stale-format shadowing [Unverified]:** `readResources` always checks `code/file-list` first, but `writeResources` only writes `code/file-list` in the mixed/fallback case (all-local writes only the native format). If Electron's `clipboard.writeBuffer(format, …)` does **not** clear other formats (I cannot verify Electron's clearing semantics from this repo), a prior mixed copy's `code/file-list` could shadow a subsequent all-local copy, causing paste of the *previous* selection. Worth an explicit round-trip test across consecutive mixed→local copies.
- **`hasResources` vs `readResources` divergence:** `hasResources` returns true when a native format is merely present (e.g. `NSFilenamesPboardType` from Finder, which is typically a *binary* plist), but `plistToFiles`' XML regex returns `[]` for binary plists — so Paste is enabled yet no-ops. Same concern for reading foreign `text/uri-list`/`FileNameW` producers.
- **DnD text suppression (`dnd.ts:238-248`):** for an all-remote drag, `nativeResources` is empty so no `text/plain` is set at all; dropping a remote file into an in-app text target now inserts nothing (previously inserted the label). Likely intended, but a behavior change.
- **Proxy `readFile` buffers whole files in memory** across IPC (`remoteFileSystemProxyServer.ts:263-266`) — unbounded for large files on the proxy fallback path.

### Most Critical Gap

The eager, unbounded, synchronous download of remote files/folders into the user-data directory on *every* remote copy/cut (`explorerService.ts:298-316`) — no size bound, no progress, no cancellation, triggered even for same-remote paste that needs no local copy. Bound it, make it lazy/cancelable, and gate native materialization on the paste actually needing it, before merge.

### Positive Observations

- The main-process handler correctly restricts routing to `vscode-remote://` and rejects other authority-bearing schemes (e.g. UNC), with a focused unit test for the no-match and scheme-mismatch cases.
- Each remote file is placed in its own UUID subfolder to avoid basename collisions — a real edge case handled deliberately.
- The proxy provider is correctly declared read-only, and the client avoids the self-routing loop by not registering when the window already owns a remote authority.
