## Critical

**1. Partial-download failure duplicates clipboard entries — `explorerService.ts:308-323`**
```ts
for (const resource of remoteResources) {
    ...
    await this.fileService.copy(resource, target, true);
    result.push(target);                      // line 315
}
} catch (error) {
    this.logService.warn('Failed to download remote files for clipboard', error);
    result.push(...remoteResources);           // line 322 — pushes ALL remote resources
}
```
If `fileService.copy` succeeds for the first N remote resources (each pushed into `result` as a local temp URI) and then throws on resource N+1, the `catch` block pushes **all** of `remoteResources` — including the ones already successfully downloaded and already in `result`. The clipboard ends up with duplicate entries for those files: one as the downloaded `file://` temp URI, one as the original remote URI. Fix: track only the resources not yet processed (e.g. iterate with an index/slice, or wrap each resource's copy in its own try/catch and only fall back per-resource) rather than re-adding the whole original list in the shared catch. Confidence: 95.

**3. `Uint16Array` alignment bug on the Windows clipboard read path — `clipboardService.ts:247`**
```ts
const u16 = new Uint16Array(buffer.buffer.buffer, buffer.buffer.byteOffset, Math.floor(buffer.byteLength / 2));
```
`buffer` here is a `VSBuffer` returned from `nativeHostService.readClipboardBuffer(...)` over IPC. Tracing the RPC path: `deserialize()` for a `VSBuffer` argument does `reader.read(readIntVQL(reader))` (`src/vs/base/parts/ipc/common/ipc.ts:311`), which is `BufferReader.read()` → `this.buffer.slice(this.pos, this.pos + bytes)` (`ipc.ts:217-221`), and `VSBuffer.slice()` explicitly uses `subarray` — a **zero-copy view**, by design ("use subarray instead of slice because ... slice creates shallow copy" — `src/vs/base/common/buffer.ts:136-141`) — into the single combined message buffer (`BufferWriter.buffer = VSBuffer.concat(...)`, `ipc.ts:228-230`). Because a 1-byte type tag plus a variable-length varint size prefix precede the payload in that combined buffer, the resulting `VSBuffer`'s backing `Uint8Array.byteOffset` is essentially arbitrary and frequently **odd**. Constructing a `Uint16Array` directly over such an `ArrayBuffer`/`byteOffset` throws `RangeError: start offset ... is not a multiple of the element size` whenever the offset is odd — which the surrounding `try/catch` silently swallows, returning `[]`. Net effect: pasting a file copied from Windows Explorer (`FileNameW` format) into VS Code would very likely fail silently on this path. The codebase already has the alignment-safe primitive for exactly this: `readUInt16LE(source: Uint8Array, offset: number)` in `src/vs/base/common/buffer.ts:251-256`, which VSBuffer's own methods use internally instead of a typed-array view. `fileNameWToFile` should read the null-terminated UTF-16LE string via that byte-oriented helper (looping `readUInt16LE(buffer.buffer, i)`) rather than casting to `Uint16Array`. Confidence: 85 (the throwing behavior is derived from tracing the actual serialization code; I can't run the real Windows/Electron binary to observe the exact byte offset at runtime, so flagging as [Inference] on the precise reproducibility rate, but the mechanism is verified in this repo's code).

**5. Hand-rolled, weaker plist parser duplicates an existing full-featured one — `clipboardService.ts:151-176` (`filesToPlist`/`plistToFiles`)**
The repo already has `src/vs/workbench/services/themes/common/plistParser.ts`, a complete, tested XML-plist parser handling arrays/strings and full entity decoding (`&amp;`, `&lt;`, `&gt;`, `&quot;`, `&apos;`, numeric `&#NN;`/`&#xNN;` refs). (Relocating the existing parser to a non-themes-specific module, rather than importing across the themes/clipboard boundary, would be the appropriate fix rather than a direct cross-import.)
