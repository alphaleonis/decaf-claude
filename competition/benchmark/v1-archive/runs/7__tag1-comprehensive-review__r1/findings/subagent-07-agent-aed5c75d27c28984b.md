### Pass 2: Validated Findings

#### Critical

- **[Race condition / resource cleanup]** `getChunkSeriesSet` closes the `ChunkQuerier` via `defer` before its caller ever consumes the returned `ChunkSeriesSet`, releasing the reader's lifetime-tracking token before use — reintroducing a use-after-close/use-after-unmap race with concurrent block deletion (and a parallel isolation-watermark race on the head path) — `storage/remote/read_handler.go:247-265` (and caller `storage/remote/read_handler.go:205`)
  - **Unhandled path:** `getChunkSeriesSet` returns `querier.Select(ctx, true, hints, filteredMatchers...)` at line 265; the `defer func(){ querier.Close() }()` registered at line 247 fires when `getChunkSeriesSet` returns — i.e. immediately after `Select()` produces the (lazy, unconsumed) `ChunkSeriesSet`, not after it is iterated. The caller only checks `chunks.Err()` (which is nil for a normal series set) and then hands `chunks` to `StreamChunkedReadResponses` (storage/remote/codec.go:234), which lazily calls `ss.Next()/ss.At()/iter.At()/chk.Chunk.Bytes()` — reading actual chunk bytes — *after* `Close()` has already run.
    For the TSDB block path this is concretely unsafe: `blockBaseQuerier.Close()` (tsdb/querier.go:103-115) calls `q.chunks.Close()`, which is `blockChunkReader.Close()` (tsdb/block.go:567-570) — this only calls `r.b.pendingReaders.Done()`, decrementing the block's `pendingReaders sync.WaitGroup` (tsdb/block.go:305). It does not itself close the file, but it releases the very refcount that protects the block from concurrent teardown: `Block.Close()` (tsdb/block.go:378-390) does `pb.pendingReaders.Wait()` then calls `pb.chunkr.Close()`, and `chunks.Reader.Close()` (tsdb/chunks/chunks.go:665-667) does `tsdb_errors.CloseAll(s.cs)`, closing (munmap-ing) the underlying `fileutil.OpenMmapFile` segments. `Block.Close()` is invoked from `DB.reloadBlocks()` (tsdb/db.go:1428 ff.) on blocks marked deletable (retention expiry / post-compaction obsolescence), which per the code's own comment runs roughly every minute ("Now that we reload TSDB every minute..."). Because this PR's `Close()` now runs *before* `StreamChunkedReadResponses` finishes reading chunk bytes, the WaitGroup can reach zero and let a concurrent `reloadBlocks()` actually munmap the chunk segment while the streaming goroutine is still mid-iteration reading `chk.Chunk.Bytes()` from that same mmap'd region.
    On the head-block path, `headChunkReader.Close()` (tsdb/head_read.go:318-323) calls `h.isoState.Close()`, releasing the read's isolation low-watermark early; head garbage-collection/truncation uses that watermark to decide which samples/chunks are safe to reclaim, so an early release opens a window for the in-flight iteration to read data that concurrent truncation is now free to garbage-collect.
    Pre-PR, `defer querier.Close()` was scoped to the enclosing anonymous function that itself called `StreamChunkedReadResponses` synchronously as an argument expression — so `Close()` unconditionally ran only *after* full consumption completed, which is exactly the pattern still used by the sibling non-streamed path (`remoteReadSamples`, read_handler.go:137-140, where `ToQueryResult(querier.Select(...))` fully consumes the series set before the deferred `Close()` fires). This PR's refactor breaks that ordering guarantee for the streamed/chunked path specifically.
  - **Consequence:** Under realistic production conditions — periodic block reload/retention/compaction (default cadence ~1 minute) racing with a chunked remote-read request that streams for any nontrivial duration (exactly the "misbehaving"/long-running chunked read scenario this PR's own commit message cites as motivation) — the streaming goroutine can read chunk bytes from an already-unmapped memory region: a crash (SIGSEGV) or corrupted/garbage chunk data returned to the remote-read client. On the head path, the analogous race can silently return data that violates the isolation snapshot the read was supposed to observe.
  - **Remediation:** Do not close the querier before the returned `ChunkSeriesSet` has been fully consumed. Either (a) return the `querier` alongside the `ChunkSeriesSet` from `getChunkSeriesSet` and let the caller `defer querier.Close()` after `StreamChunkedReadResponses` returns (matching the pre-PR ordering and the sibling `remoteReadSamples` pattern), or (b) if the goal is bounding memory by not holding the whole result set, wrap `Close()` so it only fires once the returned set has been fully iterated (e.g., a small wrapper `ChunkSeriesSet` that closes the querier when `Next()` returns false or on error), rather than closing immediately after `Select()` returns.
  - **Alternative considered:** Closing the querier inside `getChunkSeriesSet` right after building the (fully materialized) results, as `remoteReadSamples` does for the non-chunked path — rejected as the fix here because the whole point of the streamed/chunked path is to avoid materializing all series/chunks in memory at once, so full eager consumption inside `getChunkSeriesSet` would defeat the memory-bounding goal the PR is chasing; hence the wrapper-close-on-exhaustion approach is preferable to reverting to eager consumption.
  - **Confidence:** 85/100
