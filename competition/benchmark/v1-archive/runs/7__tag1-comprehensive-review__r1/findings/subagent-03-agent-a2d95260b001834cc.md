## Architectural Analysis

### Design Assessment

This one-file refactor extracts querier acquisition + `Select` into `getChunkSeriesSet`, whose `defer querier.Close()` fires when the function returns — i.e. **before** `StreamChunkedReadResponses` iterates the returned `ChunkSeriesSet` and reads chunk bytes. The stated goal (release querier resources early so a stuck/broken remote-read stream stops pinning blocks and causing resource pileup) is genuinely achieved, but it inverts a resource-ownership invariant: the returned set is lazily backed by the block `ChunkReader` that Close just released. This trades a resource-retention problem for a memory-safety/correctness race that is triggerable by exactly the misbehaving client the PR targets.

### Findings

#### High

- **[Coupling / Resource-lifecycle]** `getChunkSeriesSet` closes the `ChunkQuerier` before its returned `ChunkSeriesSet` is consumed — breaking the block-reader refcount invariant that keeps mmap'd chunks valid — `storage/remote/read_handler.go:239` (the `defer querier.Close()` inside `getChunkSeriesSet`; consumer at `storage/remote/codec.go:235`)
  - Why it matters: `blockChunkQuerier.Select` returns `NewBlockChunkSeriesSet(...)` holding the block's `ChunkReader` (`tsdb/querier.go:195`), and chunk bytes are read **lazily during iteration** via `p.cr.ChunkOrIterable(...)` (`tsdb/querier.go:721`) → `chk.Chunk.Bytes()` (`storage/remote/codec.go:261`), which for persistent blocks is a **zero-copy view into the mmap'd chunk file** (only the in-memory head chunk is copied, via `copyHeadChunk`/`ChunkWithCopy` at `tsdb/querier.go:714-719`). The only thing that keeps that mmap alive is the block's `pendingReaders` refcount: `Block.Close()` calls `pb.pendingReaders.Wait()` before `pb.chunkr.Close()`/munmap (`tsdb/block.go:378-390`), and `blockChunkReader.Close()` does `pendingReaders.Done()` (`tsdb/block.go:567-568`). Closing the querier decrements that refcount to zero **before** streaming reads the bytes. Under the PR's own scenario — a long-lived/broken stream — a concurrent compaction/block-deletion can now `Block.Close()` → munmap the file mid-stream, turning the subsequent `chk.Chunk.Bytes()` into a use-after-free: a remotely-triggerable SIGBUS/SIGSEGV crash of the Prometheus process, or silently corrupted chunk data returned to the client. That is arguably worse than the OOM it aims to avoid.
  - Recommendation: Keep the querier open for the full lifetime of the `ChunkSeriesSet` consumption (the pre-PR structure, with `defer querier.Close()` at the handler scope around the `StreamChunkedReadResponses` call). Address the actual resource-pileup problem via a different mechanism — bound the stream via `ctx` cancellation/timeout on the broken client, or materialize (copy) chunk bytes before releasing the block reader. Rejected alternative: making block chunks copy-on-read would fix safety but defeats the zero-copy design that makes remote read cheap, so it is not the right lever here.
  - Confidence: 82/100

#### Medium

- **[Public API / Interface design — evolution readiness]** The change depends on a `ChunkSeriesSet`-remains-valid-after-`Close` contract that the storage interfaces do not state — `storage/interface.go:436-446` (`ChunkSeriesSet`) and `:161`,`:171-172` (`LabelQuerier`)
  - Why it matters: `ChunkSeriesSet.At()` only promises the series is "iterable even after `Next` is called" — nothing about after `Close`. `LabelQuerier.Close` is documented as "releases the resources of the Querier," and the sibling `LabelValues` explicitly warns "It is not safe to use the strings beyond the lifetime of the querier." So post-`Close` iteration is an undocumented implementation detail of today's block reader (Close ≠ immediate munmap). The new comment on `getChunkSeriesSet` ("to ensure timely release of the querier resources") encodes this as if it were safe, with no note of the invariant it silently relies on. Any future `ChunkQuerier` implementation that frees eagerly on `Close` (or a block reader refactor) breaks remote read with no compile-time signal.
  - Recommendation: Do not merge behavior that relies on an unspecified contract. If the pattern is intended to be legal, first amend the `ChunkSeriesSet`/`ChunkQuerier` interface docs in `storage/interface.go` to define the lifetime relationship between a returned set and its querier's `Close`, and make TSDB honor it (e.g. copy-on-Close or defer munmap). Otherwise keep the querier alive until consumption completes.
  - Confidence: 78/100

### Positive Observations

- The extraction boundary of `getChunkSeriesSet` is itself cohesive — acquisition, hints construction, `Select`, and cleanup in one place — and the error path is handled idiomatically by returning `storage.ErrChunkSeriesSet(err)` and having the caller check `.Err()`, matching the existing sentinel-set pattern in `storage/interface.go:402`.
- The intent (stop a broken remote-read stream from indefinitely pinning block resources) is a real, correctly-identified problem.

### Recommendations

1. Revert the early-close behavior: keep `querier.Close()` deferred at the handler scope so it runs after `StreamChunkedReadResponses` returns. The extracted helper can stay, but it must not own the querier's lifetime independently of the streamed set.
2. Solve the resource-pileup problem the safe way — context/timeout-driven cancellation of stuck streams, or copy chunk bytes before releasing the block reader.
3. If early release is genuinely wanted, first define and enforce the `ChunkSeriesSet`-vs-`Close` lifetime contract at the interface level before relying on it in a consumer.

### Architectural Insights

The core design decision is unsound as written, and the reason is an **ownership inversion**, not a style issue. Before this change, the querier and the streamed `ChunkSeriesSet` had coincident lifetimes: `defer querier.Close()` sat in the handler and fired only after `StreamChunkedReadResponses` had drained the set. That coincidence was load-bearing — it is the mechanism by which the TSDB block-reader refcount (`pendingReaders`) transitively guarantees the mmap'd chunk segments stay mapped for the entire duration bytes are read from them. `getChunkSeriesSet` severs that: the returned set now outlives its backing resources, and nothing in the type system or the interface contract signals it.

On the contract question the task asked specifically: **no, "a `ChunkSeriesSet` remains valid after its querier is `Closed`" is not guaranteed anywhere.** `storage/interface.go` extends `At()`'s validity only across `Next()` calls, documents `Close()` as "releases the resources of the Querier," and — in the closest analogous statement — explicitly warns that `LabelValues` strings are "not safe to use beyond the lifetime of the querier." The change is therefore leaning entirely on an implementation detail: that `blockChunkReader.Close()` merely decrements a refcount rather than munmapping. That detail holds only in the absence of a concurrent block deletion — and the PR's whole premise is long-lived streams, which is precisely the window where compaction lands.

On goal-vs-cost: the goal *is* achieved — releasing the block reader early does let compaction/cleanup proceed instead of being blocked by a wedged stream, so the resource-retention/OOM pressure is relieved. But the cost is a memory-safety race that is strictly a correctness/availability regression, and it is remotely triggerable by the same broken client. Trading a bounded, self-healing memory-pressure problem for an unbounded use-after-free is a bad trade at the architecture level.

On the extraction's cohesion/evolution-readiness: the function boundary itself is fine and even tidy — the problem is entirely in the semantics of *when* Close runs relative to consumption. The right seam, if early release is truly desired, is at the interface layer: define the set-vs-`Close` lifetime contract in `storage/interface.go` and make TSDB honor it (defer munmap, or copy-on-close), *then* let consumers exploit it. Encoding the assumption in a single consumer's `defer`, justified by a comment that asserts safety the contract doesn't provide, is the maintainability trap here.
