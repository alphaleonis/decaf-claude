### [LLM_COMPREHENSION_RISK SHOULD]: NodeConfig silently drops AddFunc with no rationale
- **RULE**: 0/2 (comprehension risk)
- **Location**: pkg/proxy/config/config.go:288-293 (`NewNodeConfig`)
- **Issue**: The handler registration was restructured to register only `UpdateFunc` and `DeleteFunc`; `AddFunc` is gone. To a reader this looks like a bug — an informer delivers the initial/existing object (and, on a pre-synced informer, cache replay) as Add events, so the local Node's initial state appears to never reach `OnNodeChange`. The load-bearing knowledge — that the initial Node is captured earlier via the poll loop in `NewNodeManager`, so Add delivery here is intentionally unnecessary — lives only in a different file (`pkg/proxy/node.go`) and is nowhere near this registration. Compounding the confusion, `handleChangeNode` contains `DeletedFinalStateUnknown` tombstone handling, which is normally an Add/Delete concern, not Update.
- **Failure Mode / Rationale**: A future maintainer either (a) "restores" `AddFunc` believing an event path is missing, or (b) spends effort reconstructing how initial Node state reaches handlers because the code as written implies it does not. The reconciling fact (initial state comes from the poll in `NewNodeManager`) is not derivable from this file.
- **Suggested Fix**: Add a one-line comment at the registration explaining the omission, e.g. `// AddFunc is intentionally omitted: the initial Node state is captured via the poll in NewNodeManager; only later changes need to be observed here.`

### [LLM_COMPREHENSION_RISK COULD]: NodeIPs()/PodCIDRs() comments claim frozen poll values, but read the live mutable node
- **RULE**: 0 (comprehension risk / comment-code mismatch)
- **Location**: pkg/proxy/node.go:118 and pkg/proxy/node.go:126
- **Issue**: Both doc comments state the value was "polled in NewNodeManager()". After the refactor these methods no longer return a stored `nodeIPs`/`podCIDRs` snapshot; they recompute from `n.node`, a field mutated on every `OnNodeChange` under `n.mu`. The comment describes a startup-frozen value; the code returns whatever the latest observed Node holds.
- **Failure Mode / Rationale**: A maintainer trusting the comment may treat these accessors as cheap immutable startup constants — e.g. call them off the lock, cache the result, or reason that they can never change at runtime — when in fact they reflect live, lock-guarded state. The "always equals startup value" appearance only holds because the process crashes on a detected change; that invariant is not stated here.
- **Suggested Fix**: Update both comments to reflect reality, e.g. `// NodeIPs returns the NodeIPs of the most recently observed Node object.` (and likewise for PodCIDRs).
