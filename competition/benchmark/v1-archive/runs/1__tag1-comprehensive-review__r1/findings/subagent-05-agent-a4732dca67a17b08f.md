## Adversarial Review

### Summary

The PR fixes the reported multi-table join case, but the redesign silently dropped the old negative-result cache (`_rowidOrdinal = -1` sentinel), and that one omission produces three regressions at once: a `Debug.Assert` that now fires on legitimate, explicitly-handled fallback paths (including at least five pre-existing tests in this very file), a full column-scan plus pragma sub-query re-executed on *every* `GetStream`/`GetBytes` call for tables without a usable rowid, and new per-call allocations in a hot path. The cache key design (`$"{db}_{table}"` string, mutable `RowIdInfo` with a dead field) is also sloppier than the surrounding code.

### Findings

#### High

- **[other]** `Debug.Assert(rowIdForOrdinal!=null)` fires on legitimate fallback paths that the very next statement handles — `src/Microsoft.Data.Sqlite.Core/SqliteDataRecord.cs:393`
  - **What's wrong/missing:** The old assert `Debug.Assert(_rowidOrdinal.HasValue)` was vacuously true because `-1` was assigned before the loop. The new code leaves `rowIdForOrdinal` null when no rowid/single-INTEGER-PK column is found — a designed outcome, handled by the `if (rowIdForOrdinal == null)` MemoryStream fallback at line 396. The assert directly contradicts the branch that follows it. Verified reachable by *existing* tests: `GetStream_works` (`SELECT x'427E5743'` — expression column, no other columns to scan), `GetStream_works_with_text/int/float`, and `GetStream_works_when_composite_pk` (composite PK → `pkColumns == 2L`, never breaks). It also fires in the PR's own feature area whenever the joined table's rowid/PK isn't projected (e.g., `SELECT A.ID, A.VALUE, B.VALUE FROM A JOIN B ...`).
  - **Why it matters:** In Debug builds the assertion fails on ordinary queries. [Inference — framework behavior, not verified in this repo] Under .NET Core's default trace listener a failed `Debug.Assert` terminates the process, so a Debug-configuration test run of this suite crashes; Release builds are unaffected because asserts compile out. Either way, an assert whose negation is the documented next branch is a logic contradiction.
  - **Fix:** Delete the assert, or make it meaningful again by caching a negative sentinel (see next finding) and asserting an actual invariant. Alternative considered: restoring the old pre-loop sentinel assignment so the assert stays vacuously true — rejected, a vacuous assert documents nothing.
  - **Confidence:** 95/100 (assert reachability verified from code and existing tests; only the exact process-termination mechanics are inference). Note: overlaps code-reviewer's correctness lane; reported per GOVERNANCE adjacent-harm rule because it emerges only from comparing against the removed design.

- **[other]** Negative lookup results are no longer cached — full column scan + pragma sub-query re-executed on every `GetStream` call — `src/Microsoft.Data.Sqlite.Core/SqliteDataRecord.cs:329-394`
  - **What's wrong/missing:** The removed design cached "searched, found nothing" via `_rowidOrdinal = -1`. The new `RowIds` dictionary is populated only on success (`RowIds.Add` at lines 355 and 387; no add on the fall-through before line 393). For any blob column whose table has no usable rowid in the projection (composite PK, `WITHOUT ROWID` table, rowid/PK not selected, expression columns), *every* `GetStream` call — and therefore every `GetBytes`/`GetChars`/`GetTextReader` call, since all route through it — re-runs the O(FieldCount) scan with `sqlite3_column_database_name/table_name/origin_name` interop per column, `sqlite3_table_column_metadata` per matching column, and (when an INTEGER member of a composite PK is projected) a fresh `CreateCommand` + `ExecuteScalar` against `pragma_table_info` (lines 375-381, `pkColumns` is reset to `-1L` per call).
  - **Why it matters:** The documented chunked-read pattern — `GetBytes` in a loop with increasing `dataOffset` — now executes an SQL sub-query per chunk per row on these tables. Previously this cost was paid once per result set. Silent perf regression in a data-access primitive, invisible until someone profiles.
  - **Fix:** Store a sentinel entry (e.g., `Ordinal = -1` or a null-value `Dictionary<key, RowIdInfo?>`) on lookup failure and check it before use — this also restores a meaningful assert site. Alternative considered: reverting to the single nullable field — rejected, that reintroduces bug #32747.
  - **Confidence:** 90/100

#### Medium

- **[edge-case]** Self-join: two aliases of the same table share one cache key, so the wrong alias's rowid is used — silently wrong blob bytes — `src/Microsoft.Data.Sqlite.Core/SqliteDataRecord.cs:328`
  - **What's wrong/missing:** `sqlite3_column_table_name` returns the origin table, not the alias, so for `SELECT a1.rowid, a2.rowid, a1.data, a2.data FROM t a1 JOIN t a2 ...` both blob columns produce key `"main_t"`. The first lookup caches `a1.rowid`'s ordinal; `GetStream` on `a2.data` then opens a `SqliteBlob` at a1's rowid and returns a1's row's bytes as a2's data — no error, wrong data. This is pre-existing (the old single-field design and the new scan order pick the first matching rowid identically), but the PR's stated purpose is making blob streaming work across joins, and this join shape still silently returns wrong data with no test documenting the limitation.
  - **Why it matters:** Silent wrong-data is worse than the exception the original bug produced. First-Law relevant; reported despite being pre-existing.
  - **Fix:** During the scan, detect ambiguity — more than one rowid-candidate ordinal resolving to the same (db, table) — and fall back to `MemoryStream(GetCachedBlob(ordinal))`, which reads the actual result column and is always correct. Alternative considered: resolving aliases — rejected, the SQLite C API does not expose column aliases' source-alias mapping.
  - **Confidence:** 85/100

- **[edge-case]** Cache key `$"{db}_{table}"` collides when names contain underscores — `src/Microsoft.Data.Sqlite.Core/SqliteDataRecord.cs:328`
  - **What's wrong/missing:** Database `"main_foo"` + table `"bar"` and database `"main"` + table `"foo_bar"` both key as `"main_foo_bar"`. On collision the cached `Ordinal` from the other table is fed to `GetInt64` and used as the rowid for a `SqliteBlob` opened on the current table — wrong row's bytes or a runtime SqliteException. Requires `ATTACH`ed databases with such names, which is uncommon but entirely legal.
  - **Why it matters:** Another silent wrong-data path, and the fix is free.
  - **Fix:** Key by `Dictionary<(string db, string table), ...>` (value-tuple). Alternative considered: escaping the separator in the string key — rejected, the tuple also eliminates the per-call string allocation below.
  - **Confidence:** 85/100

- **[other]** Eager `Dictionary` allocation per record + per-call string-key allocation, against the class's lazy-cache convention — `src/Microsoft.Data.Sqlite.Core/SqliteDataRecord.cs:39,328`
  - **What's wrong/missing:** `RowIds` is allocated in the field initializer for every `SqliteDataRecord` — one per result set of every query, blob or not — while every sibling cache in the class (`_blobCache`, `_typeCache`, `_columnNameOrdinalCache`, `_columnNameCache`) is a lazily-allocated nullable field. Additionally, line 328 builds an interpolated string key on *every* `GetStream` call, including cache hits; the replaced design was an allocation-free nullable-int check. Chunked `GetBytes` streaming now allocates a string per chunk.
  - **Why it matters:** This is a hot-path ADO.NET primitive in a codebase that treats allocations as regressions; the deviation from the established lazy pattern also suggests the convention wasn't noticed.
  - **Fix:** Make the field `private Dictionary<(string, string), int>? _rowIdOrdinals`, allocate on first `GetStream`, and use the tuple key directly. Alternative considered: keeping the string key but caching it — rejected, tuple key solves this and the collision finding at once.
  - **Confidence:** 88/100

- **[test-gap]** New test covers only the happy path; none of the paths this PR degraded are tested — `test/Microsoft.Data.Sqlite.Tests/SqliteDataReaderTest.cs:149-183`
  - **What's wrong/missing:** `GetBytes_works_streaming_join` tests two distinct tables, both with projected single INTEGER PKs. Missing: (1) a join where one table hits the fallback (composite PK, `WITHOUT ROWID`, or rowid not projected) — exactly the case that trips the assert and the repeated scan; (2) a self-join documenting current behavior; (3) unlike sibling tests (`GetStream_Blob_works` asserts `Assert.IsType<SqliteBlob>`), the new test never verifies which stream type was produced — it would pass identically if the fix silently regressed to the materialized `MemoryStream` fallback for table B.
  - **Why it matters:** The regression suite can't distinguish "streaming works in joins" from "fallback happens to return the right bytes."
  - **Fix:** Add the two join-variant tests and use `GetStream` + `Assert.IsType<SqliteBlob>` for at least the B-table column. Did not consider an alternative.
  - **Confidence:** 85/100

#### Low

- **[other]** `RowIdInfo.TableName` is dead — stored, never read — and the class is over-built — `src/Microsoft.Data.Sqlite.Core/SqliteDataRecord.cs:20-30`
  - **What's wrong/missing:** Grep of the repo shows `RowIdInfo` appears only in this file; `TableName` is assigned in the constructor (from a value already encoded in the dictionary key) and consumed nowhere. The class is mutable (`get; set;`) for no reason; the only live payload is one `int`.
  - **Why it matters:** Dead fields invite future misuse ("it's there, must be meaningful") and the class adds a heap object per cached table.
  - **Fix:** Replace `RowIdInfo` with the ordinal `int` as the dictionary value. Alternative considered: keeping the class but making it a readonly record — rejected, a bare `int` suffices.
  - **Confidence:** 92/100

### Most Critical Gap

The dropped negative-result cache: it simultaneously makes `Debug.Assert` at `SqliteDataRecord.cs:393` fire on paths already covered by five existing tests in Debug builds and turns every fallback-path `GetBytes` chunk into a full column scan plus an SQL pragma sub-query. One sentinel dictionary entry on lookup failure resolves both before merge.

### Positive Observations

- The per-(database, table) cache is the structurally correct generalization of the single-ordinal design and genuinely fixes #32747 for distinct-table joins.
- A regression test was added that fails against the pre-fix code (the old code would open the blob on table B with table A's rowid and throw), so the core fix is guarded.
- The pre-existing lookup loop's filtering (skip blob's own ordinal, match db and table before the metadata call) was preserved intact rather than rewritten.
