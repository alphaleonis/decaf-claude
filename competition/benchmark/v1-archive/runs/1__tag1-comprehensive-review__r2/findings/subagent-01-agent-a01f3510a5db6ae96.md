I have everything I need. Both claims I wanted to verify checked out: `RowIdInfo.TableName` is write-only, and two existing tests (`GetStream_works`, `GetStream_works_when_composite_pk`) drive `GetStream` down the exact path where the new `Debug.Assert` fires.

## Adversarial Review

### Summary

The fix addresses the reported two-table join case, but the rewrite of the not-found path is regressive in two independent ways: the re-added `Debug.Assert` now fires on legitimate, test-asserted fallback scenarios (it was trivially true before; now it is genuinely false), and the deliberate negative caching of "no rowid found" was silently dropped, so fallback-path blob reads now re-run a full column scan plus a SQL query on every single `GetStream`/`GetBytes` call. The fix is also incomplete for the very bug class it targets: self-joins still silently return the wrong row's blob.

### Findings

#### High

- **[edge-case]** Re-added `Debug.Assert(rowIdForOrdinal != null)` fires on legitimate fallback paths — `src/Microsoft.Data.Sqlite.Core/SqliteDataRecord.cs:393`
  - **What's wrong/missing:** The old assert (`Debug.Assert(_rowidOrdinal.HasValue)`) was trivially true because `_rowidOrdinal` was set to `-1` before the scan. The commit message says "assert readded," but the re-added form asserts a condition that is genuinely false whenever no rowid is resolvable — which is a supported, intentional path (the `MemoryStream` fallback at line 396–399). Existing tests hit it directly: `GetStream_works` (`SELECT x'427E5743'` — expression column, scan finds nothing, `SqliteDataReaderTest.cs:373-385`) and `GetStream_works_when_composite_pk` (composite PK → `pkColumns == 2`, never assigned, `SqliteDataReaderTest.cs:516-540`). Both tests explicitly `Assert.IsType<MemoryStream>` — i.e., the codebase itself declares the null outcome valid.
  - **Why it matters:** [Inference] On .NET Core, a failed `Debug.Assert` without an attached debugger terminates the process (FailFast). Any Debug-configuration build — the dev inner loop, and CI legs that test Debug — will crash the test host on tests that passed before this change. Even if some CI legs run Release, shipping an assert that fires on a valid path converts the documented fallback into a debug-build crash.
  - **Fix:** Delete the assert, or cache the not-found result and assert on the cache invariant instead (see next finding — a `Dictionary<(string, string), int?>` with `null`/`-1` meaning "scanned, not found" makes the assert unnecessary). Rejected alternative: guarding the assert with "only when a rowid should exist" — there is no cheap way to know that a priori; that is exactly what the scan computes.
  - **Confidence:** 92/100

- **[other]** Negative caching removed: fallback-path reads now re-scan and re-query per call — `src/Microsoft.Data.Sqlite.Core/SqliteDataRecord.cs:329-394`
  - **What's wrong/missing:** The old code cached `_rowidOrdinal = -1` before scanning, so the scan (per-column `sqlite3_table_column_metadata` calls plus the `SELECT COUNT(*) FROM pragma_table_info($table)` command at lines 375–381) ran at most once per result set. The new code only inserts into `RowIds` on success; when nothing is found, nothing is cached, so every subsequent `GetStream` on that table repeats the entire scan including executing a fresh SQL command on the connection.
  - **Why it matters:** `GetBytes` (line 274–286), `GetChars`, and `GetTextReader` all route through `GetStream`. The standard streaming pattern — reading a large blob in fixed-size chunks via repeated `GetBytes` — calls `GetStream` once per chunk. For any table on the fallback path (composite PK, `WITHOUT ROWID`, PK not in the projection), that is now one full metadata scan plus one SQL command execution per chunk per row, where the old code did it once per reader. This is an unacknowledged operational regression hidden inside a correctness fix; nothing in the PR narrative or tests mentions it.
  - **Fix:** Restore negative caching: store a sentinel for "scanned, nothing found" — e.g., change the cache to `Dictionary<(string dbName, string tableName), int?>` and insert `null` (or `-1`) after an unsuccessful scan, checking `TryGetValue` result separately from the value. This also resolves the assert finding above. Rejected alternative: keeping the current dictionary and adding a separate `HashSet<string>` of scanned-but-not-found keys — works, but two collections tracking one state will drift.
  - **Confidence:** 88/100

- **[edge-case]** Fix is incomplete: self-joins still silently return the wrong row's blob — `src/Microsoft.Data.Sqlite.Core/SqliteDataRecord.cs:328`
  - **What's wrong/missing:** The cache is keyed by origin database + table name. `sqlite3_column_table_name` returns the *origin* table, not the FROM-clause alias, so in `SELECT a1.ID, a1.VALUE, a2.ID, a2.VALUE FROM A a1 JOIN A a2 ON ...` all four columns report table `A` and share one cache key. The first `GetStream` resolves the rowid to whichever `A.ID` ordinal the scan finds first (a1's), and that ordinal is then reused for a2's blob — `SqliteBlob` opens with a1's rowid and silently returns a1's row data for a2's column. This is the identical bug class as #32747 (one cached rowid reused across distinct row sources), just one join shape further out; the PR title claims to handle "joins with multiple rowids/tables" but only handles *distinct* tables. Scope note: silent wrong-data is harm-relevant, so I'm reporting it even though single-case bug analysis is nominally code-reviewer territory.
  - **Why it matters:** Wrong user data returned with no error — the worst failure mode. The pre-fix code had the same flaw, so it is not a regression, but a fix explicitly targeting "single cached rowid reused across row sources" that leaves the alias variant broken is a completeness gap that should at minimum be documented and tracked.
  - **Fix:** SQLite exposes no alias information through the column-metadata API, so exact per-alias resolution isn't achievable with this scan. The defensible remediation: during the scan, detect when more than one distinct result-set ordinal for the same (db, table) qualifies as a rowid candidate (e.g., two columns whose origin is the same `A.ID`), and in that ambiguous case fall back to `MemoryStream` rather than guessing. Rejected alternative: keying the cache by blob-column ordinal instead of table — it doesn't help, because the scan still cannot tell which `ID` ordinal belongs to which alias.
  - **Confidence:** 82/100

#### Medium

- **[other]** Brittle string cache key `$"{db}_{table}"` — ambiguous delimiter, collision returns wrong data — `src/Microsoft.Data.Sqlite.Core/SqliteDataRecord.cs:328`
  - **What's wrong/missing:** `_` is a legal identifier character in both database aliases (`ATTACH ... AS main_a`) and table names, so (`main`, `A_B`) and (`main_A`, `B`) produce the identical key `main_A_B`. Null database/table (expression columns) both collapse to `"_"`. Structured data flattened into a delimited string where a composite key belongs.
  - **Why it matters:** On collision, the second table's blob reuses the first table's cached rowid ordinal — `GetInt64` of an unrelated column fed into `SqliteBlob` → wrong blob data or a spurious "no such rowid" error, silently and only under specific ATTACH naming. Low probability, but the failure is silent wrong data and the fix is trivial.
  - **Fix:** Key the dictionary on `(string?, string?)` (`Dictionary<(string?, string?), ...>`) — no formatting, no collisions, no per-lookup string allocation. Rejected alternative: an unprintable delimiter like `'\0'` — fixes collisions but keeps the allocation and remains a convention someone can break later.
  - **Confidence:** 88/100

- **[test-gap]** New test does not pin the streaming path, contains debug debris, and misses the adjacent scenarios — `test/Microsoft.Data.Sqlite.Tests/SqliteDataReaderTest.cs:149-181`
  - **What's wrong/missing:** (a) The test is named `GetBytes_works_streaming_join` but never asserts the stream type. Every neighboring test pins the path with `Assert.IsType<SqliteBlob>` / `Assert.IsType<MemoryStream>` (e.g., lines 478, 533); this one only checks byte values, so a regression that silently degrades the join case to the `MemoryStream` fallback (materializing whole blobs — the very thing "streaming" avoids) passes green. (b) Line 168 is a `Console.WriteLine` whose comment says "reading fields that does not involve blobs should be ok" — an assertion intent with no assertion; it should be `Assert.Equal(1, ...)` / `Assert.Equal(1000, ...)` or deleted. (c) No coverage for: reading B's blob before A's (cache-population order), the mixed case where one table's PK is projected and the other's is not (which would have immediately exposed the `Debug.Assert` finding), multiple rows (cache reuse across `Read()`), or a self-join.
  - **Why it matters:** The single added test covers exactly the reported repro and nothing around it; the two High regressions above sail through this suite in Release builds.
  - **Fix:** Use `GetStream` with `Assert.IsType<SqliteBlob>` on both columns, remove the `Console.WriteLine` in favor of real asserts, and add at least the reverse-order and mixed (one-table-fallback) variants.
  - **Confidence:** 90/100

#### Low

- **[lint]** `RowIds`/`RowIdInfo` break every established pattern in the file; `TableName` is dead — `src/Microsoft.Data.Sqlite.Core/SqliteDataRecord.cs:20-30,39`
  - **What's wrong/missing:** `RowIdInfo.TableName` is stored and never read anywhere (grep-verified) — dead weight with public mutable setters. The field `RowIds` lacks `private`, is PascalCase where every sibling is `_camelCase` (`_blobCache`, `_typeCache`, `_columnNameOrdinalCache`), and is eagerly allocated per `SqliteDataRecord` (i.e., per result set of every query, blob or not) while all sibling caches are lazily created nullable fields. There's also a stray whitespace-only line at line 17 and unspaced `rowIdForOrdinal!=null` at line 393. The whole `RowIdInfo` class is an overbuilt solution: with the dead field removed it is a boxed `int`, and a `Dictionary<(string?, string?), int?>` replaces class, field, and negative-cache sentinel in one move.
  - **Why it matters:** Style drift in a file with otherwise uniform conventions; the eager allocation is a small per-query cost added to a hot type.
  - **Fix:** Collapse to a lazily-created `Dictionary<(string?, string?), int?>? _rowIdOrdinals` — which simultaneously resolves the negative-caching and key-collision findings.
  - **Confidence:** 90/100

### Most Critical Gap

Fix the not-found path before merge: restore negative caching and remove (or make trivially-satisfiable) the `Debug.Assert` — as written, Debug builds crash on scenarios the existing test suite explicitly asserts as valid (`GetStream_works`, `GetStream_works_when_composite_pk`), and Release builds pay a per-chunk SQL query on every fallback-path blob read.

### Positive Observations

- The per-(database, table) caching approach is the right structural direction for the bug — it correctly scopes rowid resolution to the blob column's own row source instead of a single record-wide ordinal.
- A regression test reproducing the reported issue (#32747) was added, with realistic schema and byte-level value assertions on both tables' blobs.
- The scan logic itself (rowid detection, `sqlite3_table_column_metadata`, single-PK check) was left intact rather than rewritten, keeping the diff reviewable.
