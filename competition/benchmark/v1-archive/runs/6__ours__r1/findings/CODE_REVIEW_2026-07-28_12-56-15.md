### #1 🟠 High: Windows `fileNameWToFile` throws `RangeError` on odd IPC buffer offset → native paste silently returns nothing

| | |
|---|---|
| **File** | `src/vs/workbench/services/clipboard/electron-browser/clipboardService.ts:247` |
| **Category** | runtime-boundary / silent-failure |
| **Confidence** | 75 (anchor) — **validated: confirmed** (validator reproduced the slice algorithm and observed an odd `byteOffset` in every sampled case) |
| **Found by** | broad-reviewer (High), typescript-reviewer (Medium) |

**Issue:** `const u16 = new Uint16Array(buffer.buffer.buffer, buffer.buffer.byteOffset, Math.floor(buffer.byteLength / 2));`. `Uint16Array`'s constructor throws `RangeError` when `byteOffset` is not a multiple of 2. `buffer` is the `VSBuffer` returned by `readClipboardBuffer(...)` across the renderer↔main IPC boundary; `BufferReader.read()` → `VSBuffer.slice()` (`base/common/buffer.ts`) uses `Uint8Array#subarray` (a view, not a copy), so the delivered buffer's `byteOffset` is the accumulated position within the deserialized message — dependent on preceding header/length bytes (the shared `ChannelClient.lastRequestId` VQL length) and therefore **frequently odd**. The validator re-implemented the exact serialize/`BufferReader`/`VSBuffer.slice` path and measured `byteOffset === 9` across 84 sampled realistic cases. On an odd offset the `RangeError` is swallowed by the empty `catch` and the function returns `[]`, so `readResources()` reports zero pasteable files with no error — i.e. pasting a Windows-Explorer-copied file into the VS Code explorer silently does nothing much of the time.

**Fix:** Do not view the source buffer directly. Decode with a `DataView` (no alignment requirement) or copy into a zero-offset buffer first:
```ts
const view = new DataView(buffer.buffer.buffer, buffer.buffer.byteOffset, buffer.byteLength);
const units: number[] = [];
for (let i = 0; i + 1 < view.byteLength; i += 2) { const u = view.getUint16(i, true); if (u === 0) { break; } units.push(u); }
```
(Also see #— the sibling `String.fromCharCode(...spread)` decode is separately fragile; the `DataView` loop avoids both.)

**Dissent:** typescript-reviewer rated Medium; broad-reviewer and the validator's empirical reproduction support High (frequent, silent failure of a feature the PR introduces).

### #2 🟠 High: Remote download on copy is serial, blocks the copy gesture, and is unbounded

| | |
|---|---|
| **File** | `src/vs/workbench/contrib/files/browser/explorerService.ts:308` (`resolveClipboardResources`, called from `setToCopy:266`) |
| **Category** | performance / hot-path |
| **Confidence** | 100 (anchor) — **validated: confirmed** (all three sub-claims independently re-derived) |
| **Found by** | performance-reviewer (High), broad-reviewer (Medium, no-progress-feedback aspect), prior-feedback-reviewer (maintainer `mjbvz` unresolved) |

**Issue:** The loop over `remoteResources` awaits `createFolder` + `fileService.copy` **one item at a time** (no `Promise.all`/`Promises.settled`), so wall time is the *sum* of per-file transfer times. `setToCopy` is `await`ed by the Ctrl+C/Ctrl+X command handlers (`copyFileHandler`/`cutFileHandler`), so the whole copy gesture blocks until every remote file has finished downloading. Copying a remote **folder** routes through `fileService.copy` → `doCopyFolder`, a full recursive download with **no size/count cap and no confirmation** — copying a large remote directory (thousands of files / GBs) freezes the copy gesture while the entire tree is pulled to local disk, and the work is discarded if paste never happens (`cleanupRemoteClipboardTempDir` deletes the prior download before the next copy). On failure the branch only `logService.warn`s — no progress UI and no user-visible error (contrast the sibling `FileDownload` flow, which wraps the transfer in `IProgressService` and surfaces `notificationService.error`).

This is exactly the maintainer `mjbvz`'s **unresolved** concern: *"we create the file eagerly on copy and BLOCK the copy on this."*

**Fix:** Parallelize the top-level downloads (`Promises.settled`), and/or defer the download to paste-time so an unused/superseded copy costs nothing; cap or confirm very large selections; wrap in cancellable `progressService.withProgress(...)` and surface failures.

### #3 🟠 High: Proxy provider buffers whole files in memory over IPC (no streaming; capability under-declared)

| | |
|---|---|
| **File** | `src/vs/platform/files/electron-browser/remoteFileSystemProxyClient.ts:81` (`capabilities`), server read at `remoteFileSystemProxyServer.ts:69` |
| **Category** | performance / memory |
| **Confidence** | 100 (anchor) — confirmed by orchestrator source inspection of `fileService.doCopyFile` |
| **Found by** | performance-reviewer (High) |

**Issue:** `RemoteFileSystemProxyClient` declares only `FileReadWrite` (not `FileOpenReadWriteClose`). `fileService.doCopyFile` branches on capabilities: without open/read/close it routes to `doPipeUnbuffered`/`doPipeUnbufferedToBuffered`, both of which do `await sourceProvider.readFile(source)` — the **entire file into a single buffer**, no chunking, no size limit. The server side (`readFile` → `fileService.readFile`) also materializes the whole file, and there is no `readFileStream` command on the proxy channel. A file copied/dragged through this proxy is fully buffered in memory in **three processes** (source renderer → main IPC hop → target renderer) simultaneously, unbounded — unlike the direct `RemoteFileSystemProviderClient`, which streams in fixed chunks via `FileOpenReadWriteClose`. A multi-GB remote file (log, dataset, VM image) spikes memory across processes with no upper bound.

**Fix:** Implement `open`/`read`/`close` on the proxy client and add matching commands to the server/main-handler so transfers use the chunked `doPipeBuffered` path; or add a size guard that rejects/warns before proxying files above a threshold.

### #4 🟠 High: Proxy provider re-registers on every `vscode-remote` activation → duplicate-registration errors + provider leak

| | |
|---|---|
| **File** | `src/vs/platform/files/electron-browser/remoteFileSystemProxyClient.ts:110` (the `onWillActivateFileSystemProvider` listener) |
| **Category** | resource-management / production-reliability |
| **Confidence** | 100 (anchor) — confirmed by orchestrator source inspection of `fileService.ts:99-108, 53-55` |
| **Found by** | quick-reviewer (High), design-reviewer (High), adversarial-reviewer (Medium) |

**Issue:** `FileService.activateProvider` fires `onWillActivateFileSystemProvider` **unconditionally at line 99, before** the `if (this.provider.has(scheme)) return` guard at line 106 — and `activateProvider` runs before *every* file operation on the scheme (`canHandleResource`/`withProvider`). The listener creates a **new** `RemoteFileSystemProxyClient`, adds it to the long-lived `disposables` store, and calls `fileService.registerProvider(vscodeRemote, provider)` **each time it fires**. After the first success, every subsequent `vscode-remote` operation hits `registerProvider`'s duplicate guard (`throw 'already registered'`, fileService.ts:53-55), which is swallowed by the local `try/catch` and logged as an error — while the freshly constructed provider is already in the store (leaked until window teardown). Copying a remote folder = many `stat`/`readdir`/`readFile` operations = a burst of error logs and leaked provider objects. The feature still works (via the first registration), but this diverges from the established sibling `RemoteFileSystemProviderClient.register`, which memoizes a single registration and has the listener just `e.join(promise)`.

**Fix:** Register once — guard with `if (fileService.getProvider(Schemas.vscodeRemote)) { return; }` before constructing, or memoize a single registration promise the listener joins, mirroring `RemoteFileSystemProviderClient`. This repo's own guideline (`.github/copilot-instructions.md`) explicitly warns against registering a disposable created in a repeatedly-called method.

### #5 🟠 High: Main-handler routing can hang forever — `getChannel` waits without timeout, no liveness check, cancellation dropped

| | |
|---|---|
| **File** | `src/vs/platform/files/electron-main/remoteFileSystemProxyMainHandler.ts:62` (`call` → `getRendererChannel` → forward) |
| **Category** | async / concurrency-design |
| **Confidence** | 75 (anchor) — confirmed by orchestrator source inspection of `ipc.ts:900-916` |
| **Found by** | design-reviewer (High), adversarial-reviewer (High) |

**Issue:** Routing is a TOCTOU sequence: `findWindowForAuthority` reads `windowsMainService.getWindows()`, then `getRendererChannel(id).call(...)`. `IPCServer.getChannel(name, clientFilter).call()` (ipc.ts:900-916) resolves against `getRandomElement(connections.filter(filter))`, and **when no connection currently matches it falls back to `Event.toPromise(Event.filter(onDidAddConnection, filter))` — an unbounded wait with no timeout.** A window can be present in `getWindows()` while its IPC connection is gone or not yet registered (closing/reloading — the TOCTOU gap), so the forwarded `stat`/`readFile` **hangs forever** and the copy/paste spinner sticks. Additionally the handler's `call(_, command, arg)` ignores the `cancellationToken` (4th `IServerChannel.call` param) and forwards `targetChannel.call(command, arg)` without it, so an in-flight large read cannot be canceled across the hop. Routing also commits to the first matching window with no failover to a healthy sibling sharing the same authority.

**Fix:** Verify a live connection exists for the target window before forwarding and reject with a defined error otherwise; wrap the forwarded call in a timeout; thread the received `cancellationToken` through to `targetChannel.call(command, arg, token)`; consider failover across windows with the same authority.

### #6 🟡 Medium: Overlapping `setToCopy` calls race on the shared `remoteClipboardTempDir` → wrong file pasted / orphaned temp dir

| | |
|---|---|
| **File** | `src/vs/workbench/contrib/files/browser/explorerService.ts:302` (shared `this.remoteClipboardTempDir`) |
| **Category** | concurrency / async |
| **Confidence** | 75 (anchor) — **validated: confirmed** |
| **Found by** | adversarial-reviewer (High) |

**Issue:** `setToCopy` is async and mutates the shared field `this.remoteClipboardTempDir` with no serialization (no queue/mutex; the copy/cut commands have no busy `when`-gate). If a user presses Ctrl+C again while a first (slow, large) remote download is in flight, the second `setToCopy` runs `cleanupRemoteClipboardTempDir()`, which **deletes the first call's temp dir while the first call is still copying into it** → the first call's `fileService.copy` throws → it falls back to the original remote URIs → whichever call resolves *last* writes the clipboard, which may be the *earlier* copy. Result: the wrong file is on the clipboard and a temp dir is orphaned.

**Fix:** Serialize `setToCopy` (queue/mutex) or scope each invocation to its own local temp-dir variable rather than a shared field, and only delete dirs owned by the current invocation.

**Dissent:** adversarial-reviewer rated High; downgraded to Medium given the specific timing required (slow in-flight download + a second copy) — but the race's presence in the code is unconditional.

### #7 🟡 Medium: Partial download failure duplicates entries in the clipboard resource list

| | |
|---|---|
| **File** | `src/vs/workbench/contrib/files/browser/explorerService.ts:315` (loop) / `:322` (catch) |
| **Category** | correctness / data-integrity |
| **Confidence** | 100 (anchor) — confirmed by orchestrator inspection (diff-evident) |
| **Found by** | broad-reviewer (High), quick-reviewer (Medium), adversarial-reviewer (Medium), typescript-reviewer (Medium) |

**Issue:** In `resolveClipboardResources`, each successfully-copied remote file's temp `target` is pushed into `result` inside the loop. If a later `fileService.copy` throws (a realistic flaky-SSH failure past the first item), the `catch` unconditionally does `result.push(...remoteResources)` — appending **all** original remote URIs, including the ones already present as temp copies. The returned array then holds two URIs for each already-succeeded file (temp `file://` + original `vscode-remote://`), which `writeResources` puts on the clipboard, producing duplicate/conflicting paste results.

**Fix:** Track which resources were already copied and push only the *remaining, un-downloaded* remote URIs in the catch (e.g. iterate with an index and `remoteResources.slice(failedIndex)`), and delete the just-created temp dir when fully falling back.

**Dissent:** broad-reviewer (a floor/volume agent) rated High; the three specialists that flagged it rated Medium — hence Medium.

### #8 🟡 Medium: Temp download deleted on window dispose while the OS clipboard still references it → native paste yields nothing after the window closes

| | |
|---|---|
| **File** | `src/vs/workbench/contrib/files/browser/explorerService.ts:568` (`dispose` → `cleanupRemoteClipboardTempDir`) |
| **Category** | resource-management / lifecycle (narrow spec regression) |
| **Confidence** | 75 (anchor) — **validated: confirmed** (severity Medium–High; Medium defensible) |
| **Found by** | adversarial-reviewer (High), design-reviewer (Medium), spec-compliance-reviewer (Medium), broad-reviewer (Medium) |

**Issue:** On remote copy, the temp files under `cacheHome/remote-clipboard/<uuid>` are written to the OS clipboard as local `file://` paths. `dispose()` calls `cleanupRemoteClipboardTempDir()` → `fileService.del(tempDir, {recursive:true})`, deleting the download; the **OS clipboard outlives the ExplorerService/window**. So: copy a remote file → close/reload the source window → paste into the native file manager → the clipboard points at a now-deleted temp path → the paste produces nothing. This narrowly **reintroduces the zero-byte-file symptom issue #2008 set out to fix**, once the source window is closed. The `dispose()` cleanup is also `async` but **not awaited** (fire-and-forget), so on a fast window close the delete may not even complete; the established codebase pattern for cleanup that must finish before shutdown is `lifecycleService.onWillShutdown(...).join(...)`.

**Fix:** Don't delete on dispose while the clipboard may still reference the temp files — reap on next copy / age-out, or tie the temp lifetime to an awaited `onWillShutdown` join, or write remote-source URIs (not temp paths) into the VS Code custom format so cross-window paste survives cleanup. At minimum, document that native paste is only valid while the copying window is open.

**Dissent:** adversarial-reviewer rated High (silently defeats the PR's purpose); the other three finders and the validator lean Medium given it requires window-close-before-native-paste.

### #9 🟡 Medium: Remote file contents (potential secrets) are materialized in plaintext in the local user-data cache

| | |
|---|---|
| **File** | `src/vs/workbench/contrib/files/browser/explorerService.ts:573` |
| **Category** | security / data-at-rest |
| **Confidence** | 75 (anchor) — **validated: confirmed** |
| **Found by** | security-reviewer (Medium), prior-feedback-reviewer (maintainer `mjbvz` "leaking the /tmp file path", unresolved) |

**Issue:** On copy, remote files are downloaded via `fileService.copy(resource, target)` into `joinPath(environmentService.cacheHome, 'remote-clipboard', <uuid>, <uuid>, basename)`. `cacheHome` resolves to `URI.file(userDataPath)` — the **persistent user-data directory** (e.g. `~/.config/Code`), **not** `/tmp` (the same class exposes a distinct, unused `tmpDir` getter). Remote content that may never have touched local disk (SSH `.env`, keys, tokens) is thereby written in plaintext to the local machine. Cleanup is best-effort (only next remote copy or `dispose()`, and `dispose()` is fire-and-forget with a swallowed error), so after a crash/force-quit the plaintext copies persist indefinitely. The folder is created via `createFolder` → `mkdir` with **no `mode`** — inheriting the umask (commonly 0755, world-readable) rather than 0700. This maps to `mjbvz`'s unresolved concern about leaking the temp file path onto the clipboard.

**Fix:** Treat as sensitive data-at-rest — create the temp root with 0700, prefer `tmpDir` over the persistent `cacheHome`, register process-exit/startup sweep of stale `remote-clipboard/*`, and consider retention limits; document that remote content is materialized locally.

### #10 🟡 Medium: Window remote-authority matched with `===` instead of the case-insensitive `isEqualAuthority()` helper

| | |
|---|---|
| **File** | `src/vs/platform/files/electron-main/remoteFileSystemProxyMainHandler.ts:68` (`findWindowForAuthority`) |
| **Category** | correctness / convention |
| **Confidence** | 100 (anchor; quotable-fact) — **validated: confirmed as functional, not style-only** |
| **Found by** | consistency-reviewer (High) |

**Issue:** `if (window.remoteAuthority === authority)` uses raw `===`. The codebase's `isEqualAuthority(a, b)` (`base/common/resources.ts` — `a === b || equalsIgnoreCase(a, b)`) is the established convention for exactly this comparison; `windowsMainService.ts` — the very service injected into this handler — uses `isEqualAuthority` for remote-authority matching at ~12 sites (587, 871, 1793, …), never raw `===`. `URI.authority` is **not** case-normalized at parse/revive time (the only `toLowerCase` is inside `_asFormatted`, used solely by `toString()`), so an authority differing in case/form fails `===`, `findWindowForAuthority` returns `undefined`, and `call()` throws `No window found with remote authority` — silently breaking cross-window remote copy/paste for that authority.

**Fix:** Use `isEqualAuthority(window.remoteAuthority, authority)`.

**Dissent:** consistency-reviewer rated High; kept Medium (a real but conditional correctness gap — depends on a non-canonical authority reaching the handler).

### #11 🟡 Medium: Hand-rolled, untyped proxy IPC contract across three files, with dead `exists`/`resolve` commands and inconsistent delegation

| | |
|---|---|
| **File** | `src/vs/platform/files/electron-browser/remoteFileSystemProxyServer.ts:42` (+ client call sites, main-handler forward) |
| **Category** | design / evolution-readiness |
| **Confidence** | 75 (anchor) — corroborated ×3 (validation waived) |
| **Found by** | design-reviewer (Medium), consistency-reviewer (Medium), broad-reviewer (Low, dead-code aspect) |

**Issue:** The renderer↔main↔renderer contract is a hand-rolled string-command + positional-arg switch duplicated independently in the server, the client call sites, and the main handler's blind forward — no shared interface, zero compiler enforcement; adding/renaming an operation requires editing all three in lockstep. The codebase standard is `ProxyChannel.fromService` (used throughout `app.ts`). The server exposes `exists` and `resolve` commands **no client ever calls** (the only holder, `RemoteFileSystemProxyClient`, issues only `stat`/`readdir`/`readFile`) — dead, speculative surface. Delegation is also inconsistent: `stat`/`readdir` call `provider.*` directly while `readFile`/`exists`/`resolve` go through `fileService`, mixing abstraction levels on one channel.

**Fix:** Define one shared typed interface driving both ends (ProxyChannel or an explicit interface implemented by client and server); remove `exists`/`resolve` until a caller exists; make the server delegate uniformly.

### #13 🟢 Low: Unguarded `URI.revive(args[0])` at the IPC boundary could dereference `undefined`

| | |
|---|---|
| **File** | `src/vs/platform/files/electron-main/remoteFileSystemProxyMainHandler.ts:44`; `src/vs/platform/files/electron-browser/remoteFileSystemProxyServer.ts:39` |
| **Category** | type-safety / robustness (latent) |
| **Confidence** | 75 (anchor) — **validated: confirmed; validator recommends Low** |
| **Found by** | typescript-reviewer (High) |

**Issue:** `URI.revive(args[0] as UriComponents)` — `IServerChannel.call(ctx, command, arg?)` makes `arg` optional and `URI.revive` returns `undefined` for falsy input; the `as UriComponents` cast erases that, so a caller sending empty/malformed args would make `uri.scheme` throw. **Not reachable by current callers** (the only caller always sends `[resource]`), the thrown error is caught by `ChannelServer.onPromise` and returned as a rejection (non-fatal), and the same unguarded `URI.revive(args[0])`-then-dereference idiom is **pervasive and pre-existing** across the codebase's other IPC handlers — so this is a latent robustness gap following existing convention, not a PR-specific defect.

**Fix (optional):** Validate `args?.[0]` before reviving, or type it `UriComponents | undefined` and guard before `.scheme`.

**Dissent:** typescript-reviewer rated High; downgraded to Low per the validator (latent, unreachable, established idiom).

### Threat Model Notes (security-reviewer)

The new cross-window read primitive (local window → main-process handler → remote-connected window → its FS providers) crosses meaningful boundaries **within** one VS Code instance: (a) workspace trust — a restricted/untrusted-workspace window can read a trusted remote window's files; (b) credential ownership — a window borrows another window's remote connection it never authenticated to; (c) extension trust — a compromised extension in a local window gains a read path into a remote FS the local window holds no credentials for. Caller authorization is **absent**: `RemoteFileSystemProxyMainHandler.call` ignores the connection context and derives authority solely from the (attacker-supplied) URI. The `vscode-remote` scheme allow-list is single-layered (only the main handler gates it; the renderer server would serve any scheme, incl. `file://`). These were **not** raised to primary findings — three reviewers judged them within VS Code's established same-OS-user, single-main-process trust model (which the new code's own doc comment says it follows, per `ElectronRemoteResourceLoader`/`NodeRemoteResourceRouter`), and security-reviewer itself rated them anchor 50 (below the confidence gate). They are surfaced here as design considerations / defense-in-depth candidates: independent scheme enforcement in the server, per-copy capability scoping instead of whole-provider exposure, an audit trail on cross-window reads, and a size/rate bound.

> **PathCaseSensitive (finding, Medium):** `remoteFileSystemProxyClient.ts:135` hard-codes `PathCaseSensitive`, whereas the direct sibling `RemoteFileSystemProviderClient` derives it from the remote OS (`pathCaseSensitive: remoteEnv.os === Linux`). For a case-insensitive remote (Windows/macOS host), the local proxy declares paths case-sensitive while the owning window treats them case-insensitively, so the two windows disagree on path identity (`isEqual`/`FileChangesEvent` handling). Found by knowledge-reviewer (MUST — the divergence is undocumented), design-reviewer (Medium), and prior-feedback-reviewer (copilot thread resolved-but-uncorrected). Corroborated ×3 — validation waived. ### Considered But Not Flagged (all agents)

- **Cross-window confused-deputy / no caller authorization** (security, High@50) — suppressed by the confidence gate and dismissed by broad/quick/design per VS Code's same-instance trust model. See Threat Model Notes.
- **Server has no independent scheme allow-list** (security, Medium@50), **no audit trail** (Medium@50), **no rate/size bound** (Low@50) — defense-in-depth, anchor 50, suppressed. See Threat Model Notes.
- **`plistToFiles` may fail on a *binary* `bplist00` plist written by real Finder** (quick, Medium@50) — the mac **read** path (`NSFilenamesPboardType`) parses `<string>` via regex over `buffer.toString()`; modern macOS commonly serializes this pasteboard type as binary plist, which the regex would silently match nothing → `[]`. **Unverifiable without a macOS runtime; warrants manual verification** — could silently break Finder→VS Code paste. Suppressed at anchor 50.
- **`String.fromCharCode(...spread)` on the whole FileNameW payload** (typescript, Medium@50) — a very large clipboard value could throw `RangeError: Maximum call stack size exceeded`; caught → `[]`. The `DataView` fix in #1 also resolves this.
- **`dnd.ts` drops `DataTransfers.TEXT` for remote resources on all platforms** (broad, Medium@50) — the comment justifies only the macOS `.webloc` case; adversarial-reviewer judged it intended (internal DnD uses `CodeDataTransfers`, not TEXT). Suppressed; consider widening the comment.
- **`resolve()` cast to `Promise<IFileStatWithMetadata>` when `resolveMetadata` may be false** (typescript, Low@50) — latent; `resolve` is never called by any client.
- **`window:${id}` ctx contract has no shared constant** (knowledge, SHOULD@50) — consistency-reviewer verified it matches the codebase-wide convention (`mainProcessService`, `windowTracker`, `electronRemoteResourceLoader`); dissent → not flagged.
- **plist XML escape/unescape ordering** and **`filePathToUtf16LE` surrogate handling** — multiple reviewers traced round-trips and confirmed correct. No bug.
- **Confidence-gate suppressions:** ~8 findings at anchor 50 (High×1, Medium×4, Low×3) suppressed as above; probes not run (build env unprovisioned) recorded per finding.
