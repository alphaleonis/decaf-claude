## Findings

### #1 🟠 High: kube-proxy self-terminates on any NodeIP change and on Node deletion, with no debounce/rate-limit and an undocumented crash-to-restart contract

| | |
|---|---|
| **File** | `pkg/proxy/node.go:167` (NodeIP), `:154` (PodCIDR), `:178` (`OnNodeDelete`) |
| **Category** | security / reliability / knowledge |
| **Confidence** | 75 |
| **Found by** | security-reviewer (High), broad-reviewer (Medium), knowledge-reviewer (SHOULD) · **validator: confirmed** |

**Issue:** `NodeManager.OnNodeChange` calls `exitFunc(1)` (prod `os.Exit`) on any observed change to this node's `Status.Addresses`, and `OnNodeDelete` calls it unconditionally, with no debounce, backoff, or rate-limit. This is **net-new** self-termination surface: pre-change, NodeIP was read once at startup (never fatal on change) and node deletion only marked the node ineligible via the health server (503), not exit (validator confirmed both the mechanism and the before/after contrast against git history). A principal able to write this node's `Status.Addresses` (its kubelet, scoped by NodeRestriction) or, more significantly, any cluster-scoped `nodes` update/delete grantee (cloud-controller-manager, node-lifecycle controller, an over-broad operator SA) can drive a kube-proxy restart loop; a cluster-scoped writer can flap every node's dataplane at once. Mitigating factor (why High not Critical): programmed iptables/nftables/ipvs rules persist in the kernel while kube-proxy is down, so existing Service connectivity is not immediately severed — only reconciliation of new changes stops.

Two secondary gaps share this code and fix: the new crash-to-restart contract and its load-bearing "an external supervisor restarts us" assumption are undocumented at the exit sites, and the removal of the `https://issues.k8s.io/111321` anchor drops the only rationale pointer for the PodCIDR-restart mechanism.

**Fix:** The exit-on-change is intended design; the actionable parts are the missing controls. (a) Gate self-exit behind a debounce / restart rate-limiter so a single actor cannot drive an unbounded dataplane restart loop; (b) document the crash-to-restart contract and supervisor assumption at the exit sites and re-add the 111321 reference; (c) see #12 for the observability half.

### #2 🟠 High: `NewNodeConfig` registers no `AddFunc` — a NodeIP/PodCIDR change during the startup registration gap is dropped, leaving a stale baseline for up to `ConfigSyncPeriod` (default 15 min)

| | |
|---|---|
| **File** | `pkg/proxy/config/config.go:289` (handler registration) · `cmd/kube-proxy/app/server.go` (`Run`, late registration) |
| **Category** | correctness / concurrency |
| **Confidence** | 75 |
| **Found by** | adversarial-reviewer (High), design-reviewer (Low) · **validator: confirmed** |

**Issue:** `newNodeManager` captures the baseline `n.node` via a startup poll, then the informer is Started/synced — and only later, in `Run()`, is the `NodeConfig` handler registered on that already-synced informer. client-go replays the current cached Node to a late-registered handler as a synthetic **Add** event, but `NodeConfig` wires only `UpdateFunc`/`DeleteFunc` (no `AddFunc`), so that replay is silently dropped (validator confirmed via client-go `shared_informer.go` replay + nil-`AddFunc` no-op). `NodeTopologyConfig`, by contrast, *does* register `AddFunc`. Consequently, a NodeIP or PodCIDR change that lands in the informer cache **between** the startup poll and handler registration is delivered only as that dropped Add — `OnNodeChange` never sees it, so kube-proxy does not exit and runs on a stale baseline until a genuinely new Update or the next resync. The resync bound is `ConfigSyncPeriod`, whose default is **15 minutes** — a non-trivial window that directly undermines the watch-and-crash guarantee this PR exists to provide.

**Fix:** Register an `AddFunc` on `NodeConfig` that routes the initial/replayed Node to `OnNodeChange` (mirroring `NodeTopologyConfig`), so the baseline is reconciled against current cache state at registration; or otherwise re-derive and compare the baseline immediately after registration. Document why, so a maintainer does not "restore" the current behavior.

### #3 🟡 Medium: `NodeEligible()` acquires an exclusive lock that now guards nothing and deep-copies the whole Node on every `/healthz` request

| | |
|---|---|
| **File** | `pkg/proxy/healthcheck/proxy_health.go:176`–`190` |
| **Category** | concurrency / performance |
| **Confidence** | 75 |
| **Found by** | quick-reviewer (M), consistency-reviewer (M), broad-reviewer (L), design-reviewer (L), performance-reviewer (L) · corroborated ×5 — validation waived |

**Issue:** The old `NodeEligible()` read the `nodeEligible bool` field under `RLock`. That field was removed; the method now takes the exclusive `hs.lock.Lock()` — which no longer protects any `ProxyHealthServer` field it touches — and calls `hs.nodeManager.Node()`, which does a full `DeepCopy` of the Node (dominated by `Status.Images`, potentially hundreds of entries) purely to read `DeletionTimestamp` and `Spec.Taints`. The lock needlessly serializes `/healthz` against `Updated()`/`QueuedUpdate()` (sibling read accessor `Health()` correctly uses `RLock`), and the per-request deep copy is avoidable allocation on a path polled by load balancers.

**Fix:** Drop the `hs.lock` acquisition in `NodeEligible()` (node state is already synchronized inside `NodeManager`), and add a `NodeManager` accessor that evaluates eligibility (or returns just `DeletionTimestamp` + `Taints`) under `n.mu` without a full `DeepCopy`.

| | |
|---|---|

| **Category** | design / coupling |

### #5 🟡 Medium: `PodCIDRs()` returns the shared informer-cache slice without a defensive copy (asymmetric with `Node()`/`NodeIPs()`)

| | |
|---|---|
| **File** | `pkg/proxy/node.go:131` |
| **Category** | concurrency / data-model |
| **Confidence** | 75 |
| **Found by** | design-reviewer (100), go-reviewer (50) · corroborated ×2 (incl. stack specialist) |

**Issue:** `PodCIDRs()` returns `n.node.Spec.PodCIDRs` directly. `n.node` is a shared object (from `nodeLister.Get` at construction and the raw `*v1.Node` handed to `OnNodeChange`), never deep-copied in. `Node()` deep-copies out precisely to honor client-go's "never mutate shared cache objects" contract, and `NodeIPs()` returns a freshly-allocated slice, but `PodCIDRs()` hands out an alias of informer-cache-owned memory. A caller that `append`s to or mutates the returned slice would corrupt shared informer state seen by every other consumer. The sole current caller only reads it (`s.podCIDRs = s.NodeManager.PodCIDRs()`), so the defect is latent — but the ownership model is incoherent and an easy trap for future callers.

**Fix:** Return `append([]string(nil), n.node.Spec.PodCIDRs...)` so all three accessors uniformly hand out caller-owned data.

### #6 🟡 Medium: `OnNodeChange` overwrites the baseline before validating IPs, and its `GetNodeHostIPs`-error path returns without exiting — two inconsistent error behaviors

| | |
|---|---|
| **File** | `pkg/proxy/node.go:145` (assign-before-validate), `:159`–`163` (error path) |
| **Category** | correctness / error-handling |
| **Confidence** | 50 |
| **Found by** | adversarial-reviewer, prior-feedback-reviewer, quick-reviewer · **validator: both facets confirmed** |

**Issue:** `OnNodeChange` assigns `n.node = node` (line 145) *before* checking whether the new node has usable IPs. Two consequences, both validator-confirmed:
- **(a) Spurious restart on a transient blip.** If an update briefly carries no `Status.Addresses`, `GetNodeHostIPs` errors and the function returns early — but `n.node` is already the IP-less node, so the next event's `oldNodeIPs` is empty. When addresses are restored (even to the *original* values), `reflect.DeepEqual(nil, restored)` is false → `exitFunc(1)`: a needless restart from a blip that ended unchanged.
- **(b) No restart when arguably one is warranted.** The `GetNodeHostIPs`-error path logs and returns without `exitFunc`, unlike the NodeIP/PodCIDR/delete paths. A PR reviewer (danwinship) flagged that this case "should probably be exiting too." Because `NodeManager.NodeIPs()` is read only once at startup, the real impact is "kube-proxy fails to restart-and-recover when its derived IPs become unparseable," not "serves traffic on stale IPs."

Reachability of a zero-address update is plausible but not certain, hence Medium/conf-50.

**Fix:** Do not advance `n.node` until the new node has valid NodeIPs (validate first, then assign), so a transient empty-address state cannot corrupt the baseline; and explicitly decide whether a `GetNodeHostIPs` failure on a watch event should exit like the sibling cases (record the decision either way).

### #7 🟡 Medium: `newNodeManager` waits for cache sync on the unbounded parent context — an unreachable API server at startup hangs kube-proxy before healthz starts

| | |
|---|---|
| **File** | `pkg/proxy/node.go:76`–`77` (sync wait) vs `:85` (timeout ctx created after) |
| **Category** | reliability / resource-management |
| **Confidence** | 50 |
| **Found by** | adversarial-reviewer · **validator: confirmed** |

**Issue:** `cache.WaitForNamedCacheSync(...)` is called with the **parent** `ctx.Done()`; the 5-minute `context.WithTimeout` is only created afterward. The parent ctx traces up to `context.Background()` (validator followed the chain through `Options.Run` → cobra `RunE`), which has no deadline. So if the API server is unreachable at startup, the informer never syncs and `WaitForNamedCacheSync` blocks indefinitely — not the "at most 5 minutes" the function comment claims — and `newProxyServer` never returns, so `healthz`/`livez` (started only after `newProxyServer` completes) never comes up. The old bounded `getNodeIPs` exponential-backoff path did not have this failure mode.

**Fix:** Apply the poll timeout (or a dedicated cache-sync deadline) to the context passed to `WaitForNamedCacheSync`, and correct the comment to reflect that the 5-minute bound does not currently cover the cache-sync wait.

### #9 🟢 Low: `newNodeManager` returns the inner `err` instead of `pollErr` — a latent `(nil, nil)` trap

| | |
|---|---|
| **File** | `pkg/proxy/node.go:107`–`109` |
| **Category** | error-handling / maintainability |
| **Confidence** | 50 |
| **Found by** | broad-reviewer · **validator: confirmed (latent, not reachable today)** |

**Issue:** On poll failure the function returns the closure-scoped `err`, not `pollErr`. This is correct **only** because every `return false` branch first assigns a non-nil `err`, and `PollUntilContextCancel(..., immediate=true, ...)` runs the condition at least once — so `(nil, nil)` is unreachable in the current code (validator confirmed via `loop.go`). But the invariant is unenforced and undocumented: a future `return false, nil` without setting `err` would make `newNodeManager` return `(nil, nil)`, and `newProxyServer` only checks `err != nil`, then nil-derefs at `s.NodeManager.NodeIPs()`.

**Fix:** Return a value that can never be nil-when-failing, e.g. `return nil, fmt.Errorf("timed out waiting for node %q to be ready: %w (last error: %v)", nodeName, pollErr, err)`, preserving both the timeout and the last cause.

### #10 🟢 Low: Startup poll dropped the `DeletionTimestamp` skip the old `waitForPodCIDR` had

| | |
|---|---|
| **File** | `pkg/proxy/node.go:87` |
| **Category** | correctness (narrow) |
| **Confidence** | 50 |
| **Found by** | quick-reviewer · **validator: confirmed** |

**Issue:** The removed `waitForPodCIDR` explicitly kept waiting on a node with a non-zero `DeletionTimestamp` ("don't consider the node if is going to be deleted"). The new poll only checks existence + NodeIPs (+ PodCIDRs), so a node already marked for deletion at startup is accepted and `NewNodeManager` returns successfully. Because `OnNodeDelete` fires only on final removal (not when `DeletionTimestamp` is merely set), there is a drain/finalizer window where the old code would wait but the new code runs normally until the eventual hard-delete exit. Narrow blast radius, self-heals on delete.

**Fix:** If intentional, note it in the poll's comment; otherwise restore a `DeletionTimestamp.IsZero()` check in the poll condition.

### #12 🟢 Low: No metric or event distinguishes an intentional NodeManager restart from a crash

| | |
|---|---|
| **File** | `pkg/proxy/node.go:179` (and the other two exit sites) |
| **Category** | observability / security |
| **Confidence** | 50 |
| **Found by** | security-reviewer |

**Issue:** The three self-induced exits emit only an Info log immediately before `os.Exit(1)`. ## Specialist Notes

### Threat Model Notes (security-reviewer)

- **Trust boundary**: kube-proxy consumes the Node object from the API server. The change moves an *availability* decision (process life-or-death) onto data written at that boundary: `Status.Addresses` (this node's kubelet, scoped by NodeRestriction), `Spec.PodCIDRs` (node-ipam/allocator), and deletion (node-lifecycle / cloud-controller-manager, plus any `nodes` update/delete grantee).
- **Blast radius**: a compromised kubelet affects only its own node's kube-proxy (bounded). A compromised cluster-scoped `nodes` writer can now flap **every** node's kube-proxy — the meaningful escalation.
- **No new data-confidentiality surface**: `klog.KObj` emits only namespace/name (RFC1123-constrained), IPs are parsed `net.IP`, PodCIDRs are validated CIDRs — no practical log-injection vector.
- **Mitigating factor**: kernel dataplane rules persist while kube-proxy is down; only reconciliation of new changes stops — which is why #1 is High, not Critical.

### Prior-Feedback Coverage (prior-feedback-reviewer)

Of 46 human review threads, 44 were satisfied in the merged source (spot-checked the regression-prone ones: deepcopy-vs-document, `callback` rename, topology zone-only filter, `(*FakeProxier)` receiver style, `NoopNodeHandler` removal — all hold). Two were carried forward as findings: nojnhuh's flush-robustness suspicion (thread `node.go:155`) → investigated and the log-loss mechanism **refuted** (see below), leaving only the idiom-drift consistency note; danwinship's "should be exiting in this case too" → primary #6(b).

### Considered But Not Flagged (all agents)

- **`klog.Flush()` + `os.Exit` loses buffered logs** — **refuted by validator**: `klog.Flush()` → `lockAndFlushAll()` performs `flushAll()` + `syncAll()` synchronously on the caller's goroutine before returning, so `exitFunc(1)` runs strictly after the flush completes. `FlushAndExit` only adds a 10 s timeout *guard* against a hanging flush; it does not prevent truncation the plain path would suffer. No log-loss regression. (Idiom drift retained as a Consistency minor.)
- **Cluster-wide restart storm correlated across nodes** — refuted: each kube-proxy's informer is field-selected to `metadata.name==nodeName`, so one node's IP/PodCIDR change cannot correlate exits across the fleet (a cluster-scoped *writer* still can, per #1).
- **Resync re-delivering an unchanged node → spurious exit** — safe: resync passes the same cached object; `GetNodeHostIPs`+`DeepEqual` compare equal → no exit (multiple reviewers).
- **Nil `nodeManager` panic in `NodeEligible()`** — not reachable: the only production constructor (`newProxyServer`) always has a non-nil `NodeManager` (or errors first); hollow-proxy leaves `HealthzServer` nil with a nil-guard.
- **`NodeConfig` missing `AddFunc` is intentional/harmless** (broad-reviewer's read) — superseded by validated primary #2: the startup-gap window is real and bounded only by the 15-min default resync.
- **Import cycle from `healthcheck` → `proxy`** — compiles today (no file in root `pkg/proxy` imports `healthcheck`); captured as coupling finding #4, not a build defect.
- **`reflect.DeepEqual` on `[]net.IP` for change detection** — stable: both sides come from deterministic `GetNodeHostIPs`; spurious-exit risk from re-encoding is low.
- **Per-event `GetNodeHostIPs` + `DeepEqual` cost / removed backoff loop → API load** — not a regression: field-selected single-object events; the new 1 s poll reads the informer *cache* (lister), not the API server, so startup API load is strictly lower than the old repeated GETs (performance-reviewer).
