## Findings

I traced the history of `withStreamIdleTimeout`, `DestroyableStream`, and the error-classification code in `chatMLFetcher.ts` beyond the two-commit local checkout by pulling commit history for the changed files from GitHub (`gh api .../commits?path=...`), fetching full patches for key commits, and reading the linked issues. The most important discovery: **this exact PR (ba8d730b) was reverted the very next day**, and a much more conservative re-implementation landed two months later. Both are strong, directly-applicable historical evidence.

**Issue 1**
- File: `extensions/copilot/src/platform/networking/common/fetcherService.ts`
- Lines: 310 (`SSE_IDLE_TIMEOUT_MS = 60 * 1000`), 342-347 (timer callback sets `timedOut = true` and calls `void stream.destroy()`), 371-373 (throws `StreamIdleTimeoutError` after destroying)
- Description: A 60-second gap between SSE chunks is treated as a hung connection and the stream is destroyed immediately/unconditionally. In production this false-positived on legitimate long-running (non-hung) generations — e.g. models buffering a large tool-call payload for over 60s before emitting more bytes even though the connection was healthy.
- Historical evidence: This very commit (`ba8d730bd0ebf0c6b8b65cfee3016dffbe1592c9`, PR #308517) was reverted the next day by `5a67f6723697ece0b4a3915af0adcfbc28775aa5` ("Revert 'Support timing out hung streams (#308517)' (#308779)", merged 2026-04-09), closing issue #308627. The PR author confirmed in that issue: *"The second error is because I pushed a change to try and prevent the model from hanging but it seems like it is too aggressive. I'm reverting that now."* A later re-implementation, `f8574878be86c229f5d9710cdde25354bff25dde` ("Add idle watchdog + telemetry to Anthropic Messages streaming (#321432) (#321671)", 2026-06-17), used a **5-minute** threshold instead of 60s for the same purpose.
- Category: historical git context

**Issue 2**
- File: `extensions/copilot/src/platform/networking/common/fetcherService.ts`, lines 342-347 (destroy-on-timeout)
- Description: On timeout the wrapper unconditionally destroys the underlying stream and throws, aborting the whole in-flight response the instant the watchdog fires. The team's own follow-up fix explicitly avoided this: it fires telemetry but leaves the stream running, specifically because they weren't yet confident "idle" implies "hung."
- Historical evidence: `f8574878be86c229f5d9710cdde25354bff25dde`'s commit message states: *"For now this only observes the stall so we can measure how often it happens in the wild; it does not abort the request."* and the code comment: *"This intentionally does not abort the stream — we only want to observe how often this happens before changing behavior."* This is a direct repudiation of the destroy-on-timeout approach used in ba8d730b, motivated by the exact revert in Issue 1.
- Category: historical git context

**Issue 3**
- Files: `extensions/copilot/src/platform/networking/node/stream.ts:323`, `extensions/copilot/src/platform/endpoint/node/responsesApi.ts:537`, `extensions/copilot/src/platform/endpoint/node/messagesApi.ts:596`
- Description: The idle-timeout wrapper is applied uniformly to all three independent SSE-consuming code paths (OpenAI-style Chat Completions via the generic `SSEProcessor`, the Responses API, and the Anthropic Messages API), rather than being scoped to the endpoint where hangs were actually observed. This maximizes the blast radius of the false-positive problem in Issue 1 — it can kill any streaming completion across every provider, not just the one known to hang.
- Historical evidence: The eventual accepted fix (`f8574878be86c229f5d9710cdde25354bff25dde`) touches **only** `messagesApi.ts`, scoped narrowly to the Anthropic Messages streaming path per issue microsoft/vscode#321432 ("Agent turn hangs indefinitely when a streaming response stalls (no idle timeout in messagesApi/responsesApi SSE read loop)"). That issue itself notes the same unguarded loop exists in the Responses API path "in principle," yet the landed fix still declined to touch `responsesApi.ts` or `stream.ts`.
- Category: historical git context

**Issue 4**
- File: `extensions/copilot/src/extension/prompt/node/chatMLFetcher.ts`, method `processError` (lines ~1949-2013: checks at 1957 `isAbortError`, 1965 `isCancellationError`, 1973-1981 `'Premature close'`/`ERR_STREAM_PREMATURE_CLOSE`, 1989 `isInternetDisconnectedError`, 1997 `isFetcherError`, falling through to `ChatFetchResponseType.Failed` at ~2009)
- Description: `StreamIdleTimeoutError` (new in this PR) is not recognized anywhere in this classification chain, so it falls into the generic `else` branch: logged via `sendGHTelemetryException` as a hard error and returned as `ChatFetchResponseType.Failed`. Since the automatic-retry path (`retryNetworkError` in `chatMLFetcher.ts` ~line 575) only fires for `ChatFetchResponseType.NetworkError`, a timed-out (but recoverable) stream is not auto-retried for non-WebSocket transports, and the user sees a generic "Error on conversation request" instead of a distinguishable/retryable timeout.
- Historical evidence: Commit `4922ed10342130a5b1d6864b5e8906a42523fb00` (PR #411, "ChatMLFetcher: fix: stop reporting cancelled requests are errors & handle `ERR_STREAM_PREMATURE_CLOSE` as cancellation, not error") established the precedent/invariant that every new way a stream can terminate abnormally must be taught to `processError`, specifically because failing to do so caused legitimate/expected terminations to be misreported as hard errors in telemetry and to the user. This PR introduces a brand-new termination mode (`StreamIdleTimeoutError`) without updating that classification, reintroducing the same category of bug PR #411 fixed for a different termination mode.
- Category: historical git context
