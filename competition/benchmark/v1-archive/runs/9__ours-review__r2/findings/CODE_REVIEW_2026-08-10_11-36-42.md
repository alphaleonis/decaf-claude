### #1 🟠 High: Node IP/PodCIDR change during startup window is silently missed (crash-on-change safety bypassed until next resync)

| | |
|---|---|
| **File** | `pkg/proxy/config/config.go:288` (NewNodeConfig) · `cmd/kube-proxy/app/server.go:608` · `pkg/proxy/node.go` |
| **Category** | correctness / race-condition |
| **Confidence** | 100 (validator-confirmed) |
| **Found by** | adversarial-reviewer (High), broad-reviewer (High), quick-reviewer (Medium) |

**Issue:** `NewNodeManager` creates, starts, and cache-syncs its node-scoped informer early (in `newProxyServer`), capturing a baseline node snapshot by polling. Much later, in `Run()`, `config.NewNodeConfig` registers handlers on that **same, already-synced** informer — but registers only `UpdateFunc` + `DeleteFunc`, **no `AddFunc`**. Per client-go (`shared_informer.go` — verified in-tree), adding a handler to an already-synced informer replays the store contents to the new handler as synthetic `OnAdd` notifications, and `ResourceEventHandlerFuncs.OnAdd` is a no-op when `AddFunc` is nil (`controller.go`). Therefore any real NodeIP/PodCIDR change that lands in the window between the constructor's poll and this later registration is delivered only as a dropped Add and never reaches `NodeManager.OnNodeChange`; the manager keeps its stale baseline and the crash-on-change safety is skipped. The pre-PR code registered node handlers **before** starting its informer, so this window did not exist. The exposure is bounded — the periodic resync (`ConfigSyncPeriod`, default ~15 min) eventually redelivers current state as an `Update` and triggers the correct exit — so the worst case is up to one resync period of operating on stale NodeIPs (wrong NodePort/masquerade rules), not a permanent miss.

**Fix:** Give `NodeConfig` an `AddFunc` that routes into the same `handleChangeNode` path, so a post-registration replay is compared against `NodeManager`'s baseline:
```go
cache.ResourceEventHandlerFuncs{
    AddFunc:    func(obj interface{}) { result.handleChangeNode(obj) },
    UpdateFunc: func(_, newObj interface{}) { result.handleChangeNode(newObj) },
    DeleteFunc: result.handleDeleteNode,
}
```
(Alternatively, register the handler before the shared informer is started, or re-seed `NodeManager.node` from the lister at registration time.)

### #2 🟠 High: `NodeTopologyConfig` handler registered before consumers — data race on `eventHandlers` and a lost-initial-topology window

| | |
|---|---|
| **File** | `pkg/proxy/config/config.go:510` (RegisterEventHandler) · `:528` (DeepEqual short-circuit) · `cmd/kube-proxy/app/server.go:610` |
| **Category** | concurrency-design |
| **Confidence** | 100 (validator-confirmed) |
| **Found by** | design-reviewer (High) |

**Issue:** `newNodeTopologyConfig` registers its informer event handler (with an `AddFunc`) at **construction**, on the `NodeManager` informer that is already started and cache-synced. Consumers call `RegisterEventHandler(s.Proxier)` **afterward**. `NodeTopologyConfig.eventHandlers` has **no mutex** and there is no `Run()`/sync barrier — unlike the sibling `ServiceCIDRConfig`, which guards its handler set with `mu`. Two consequences:
- **(a) Data race:** the informer's replay/listener goroutine runs `handleNodeEvent`'s `for i := range n.eventHandlers` concurrently with the main goroutine's `n.eventHandlers = append(...)` in `RegisterEventHandler`, with no synchronization edge between them.
- **(b) Lost initial delivery:** if the replayed Add's `handleNodeEvent` runs before the proxier is registered, it sets `n.topologyLabels` but notifies zero handlers; because `handleNodeEvent` short-circuits on `reflect.DeepEqual(n.topologyLabels, topologyLabels)`, the identical labels are never re-delivered (not on resync, not on any future non-zone change). The proxier then routes with an empty topology map (`zone == ""`), silently disabling zone/topology-aware routing (PreferSameZone / TrafficDistribution) until an actual zone-label change occurs.

The race is timing-dependent (registration usually wins the immediately-following line), but the data race exists regardless of who wins, and the lost-delivery outcome is a real functional regression when the replay goroutine wins.

**Fix:** Guard `eventHandlers` with a mutex (as `ServiceCIDRConfig` does) **and** give newly-registered handlers an explicit initial delivery of the current `topologyLabels`, rather than relying on the informer's Add replay racing against `RegisterEventHandler`.

### #3 🟠 High: `NodeEligible()` deep-copies the whole Node on every health request, under a lock that now guards nothing

| | |
|---|---|
| **File** | `pkg/proxy/healthcheck/proxy_health.go:176` |
| **Category** | performance / concurrency |
| **Confidence** | 100 · corroborated ×3 (validation waived) |
| **Found by** | performance-reviewer (High), go-reviewer (Medium), design-reviewer (Low) |

**Issue:** `NodeEligible()` now calls `hs.nodeManager.Node()`, which takes `NodeManager`'s mutex and performs a **full `*v1.Node` DeepCopy** (labels, annotations, status conditions, addresses, `Status.Images`) on **every invocation** — and it is invoked once per `/healthz` request. Before this PR, eligibility was a push-model cached bool computed once per node event; `NodeEligible()` was an `RLock` + bool read with no allocation. This turns an O(1) cached read on the primary health path (polled continuously by kubelet probes and, for `externalTrafficPolicy=Local` services, by cloud LB health checks at sub-10s intervals) into a per-request whole-node clone. Compounding it: `NodeEligible()` now takes `hs.lock.Lock()` (exclusive), but after this refactor it reads **no** `ProxyHealthServer`-guarded field (the node comes from `NodeManager`'s own mutex) — so the write lock protects nothing yet serializes all concurrent `/healthz` requests against each other and against `Health()`'s readers, and it is held **across the DeepCopy**, extending the critical section.

**Fix:** Keep computing/caching the eligible bool inside `NodeManager` (push model, as before) and expose a cheap `NodeManager.IsEligible() bool`; or add a `NodeManager` accessor that inspects `DeletionTimestamp`/`Taints` under its internal mutex **without** `DeepCopy()` (the node is only read, not retained). Drop the now-dead `hs.lock` acquisition from `NodeEligible()`.

### #4 🟡 Medium: Startup now hard-fails (CrashLoopBackOff) when the node has no usable IP, where it previously started degraded

| | |
|---|---|
| **File** | `pkg/proxy/node.go:63` (newNodeManager) · `cmd/kube-proxy/app/server.go:210` |
| **Category** | reliability / behavior-change |
| **Confidence** | 100 (validator-confirmed) |
| **Found by** | adversarial-reviewer (Medium) |

**Issue:** `newNodeManager` polls up to **5 minutes** and returns a non-nil error if the node never has a usable host IP; that error propagates out of `newProxyServer` and fails kube-proxy startup → CrashLoopBackOff. The removed `getNodeIPs` used a ~6-step exponential backoff (~60s) and returned an **empty slice without error**, letting startup proceed to `detectNodeIPs` (which falls back to loopback defaults). So a node whose kubelet/cloud-provider is slow or fails to publish an InternalIP now blocks startup entirely instead of continuing. (Caveat: the old fallback was loopback `127.0.0.1`/`::1`, which is itself of limited use — so this may be a deliberate tightening. It changes a startup-time failure mode and deserves an explicit decision + comment.)

**Fix:** If hard-fail is intended, document it (and consider separating the NodeIP timeout from the 5-min PodCIDR-allocation timeout). Otherwise, fall back to `detectNodeIPs` on NodeIP poll timeout as before rather than aborting startup.

### #5 🟡 Medium: Startup poll dropped the `DeletionTimestamp` guard the old `waitForPodCIDR` had

| | |
|---|---|
| **File** | `pkg/proxy/node.go:87` (poll condition in newNodeManager) |
| **Category** | regression / error-handling |
| **Confidence** | 100 (validator-confirmed) |
| **Found by** | broad-reviewer (Medium) |

**Issue:** The removed `cmd/kube-proxy/app/server_linux.go:waitForPodCIDR` explicitly skipped nodes with a non-zero `DeletionTimestamp` (`if !n.DeletionTimestamp.IsZero() { return false, nil }`) before accepting PodCIDRs. The new consolidated poll validates only that `GetNodeHostIPs` succeeds and (when `watchPodCIDRs`) that `PodCIDRs` is non-empty — no `DeletionTimestamp` check anywhere in the startup path. If kube-proxy restarts while its own Node already carries a `DeletionTimestamp` (node drain/replace race), it adopts that terminating node's IPs/PodCIDRs as its immutable baseline instead of waiting for a fresh node. Runtime guards limit the blast radius (`NodeEligible` checks `DeletionTimestamp`; `OnNodeChange` crashes on later change), but the startup baseline itself is now taken from a deleting node.

**Fix:** Reinstate the guard inside the poll condition:
```go
if !node.DeletionTimestamp.IsZero() {
    err = fmt.Errorf("node %q is being deleted", nodeName)
    return false, nil
}
```

### #6 🟡 Medium: `OnNodeChange` does not exit when `GetNodeHostIPs` fails on an update (silently continues on stale IPs)

| | |
|---|---|
| **File** | `pkg/proxy/node.go:159` (GetNodeHostIPs error branch in OnNodeChange) |
| **Category** | correctness / unaddressed-prior-feedback |
| **Confidence** | 100 (validator-confirmed) |
| **Found by** | prior-feedback-reviewer (Medium) |

**Issue:** In `OnNodeChange`, if `GetNodeHostIPs(node)` returns an error, the code logs and `return`s **without** calling `exitFunc` — unlike the sibling PodCIDR-change and NodeIP-change branches, which exit. The type doc states the intent is to "crash kube-proxy if there are any changes in NodeIPs or PodCIDRs"; a retrieval failure is exactly the anomaly that prevents verifying the baseline is still valid, yet the manager keeps operating on its stale NodeIPs. The human reviewer danwinship flagged this exact line during review ("by the end of the PR we should be exiting in this case too probably"), and the merged code did not act on it.

**Fix:** Decide the intended behavior on IP-retrieval failure and make it explicit — either exit (consistent with the crash-on-change contract) or add a comment explaining why a failure is tolerated here while a change is not.

### #7 🟡 Medium: `OnNodeDelete` crashes unconditionally — a transient relist blip can trigger a needless exit / CrashLoopBackOff

| | |
|---|---|
| **File** | `pkg/proxy/node.go:176` (OnNodeDelete) |
| **Category** | reliability |
| **Confidence** | 100 (validator-confirmed) |
| **Found by** | adversarial-reviewer (Medium) |

**Issue:** `OnNodeDelete` unconditionally calls `exitFunc(1)` with no check that the delete is real (e.g. `DeletionTimestamp`). Client-go's `DeltaFIFO.Replace()` emits `Deleted` deltas for store objects absent from a fresh LIST, so a transient apiserver/relist blip where the field-selected node LIST momentarily returns empty drives `DeleteFunc` → `OnNodeDelete` → process crash. A single such event is recoverable (restart re-polls up to 5 min and continues), but sustained apiserver flapping yields CrashLoopBackOff with a stale dataplane. Crash-on-*genuine*-delete may be intended, but the spurious-delete case is not distinguished. (`NodeTopologyConfig` deliberately uses a no-op `DeleteFunc`, showing the delete path is not always meant to be fatal.)

**Fix:** Distinguish real deletions from relist artifacts before exiting — e.g. confirm absence via a direct lister `Get`, or gate on `DeletionTimestamp` — or at minimum document that a spurious delete-driven restart is acceptable.

### #8 🟢 Low: NodeIP/PodCIDR change detection uses order-sensitive `reflect.DeepEqual`, so a pure reordering can trigger a spurious crash

| | |
|---|---|
| **File** | `pkg/proxy/node.go:154`, `:167` (OnNodeChange comparisons) |
| **Category** | reliability |
| **Confidence** | 50 (static reasoning; not validated) |
| **Found by** | adversarial-reviewer (Medium → tiered to Low) |

**Issue:** `OnNodeChange` compares old vs. new NodeIPs and PodCIDRs with `reflect.DeepEqual` on slices. `GetNodeHostIPs` derives its result from the order of `Status.Addresses`; if a controller reorders the same set of addresses (or PodCIDRs are reordered), `DeepEqual` reports a change and the process exits even though the effective set is unchanged. Impact is a recoverable restart, and reordering of an unchanged set is uncommon — hence Low.

**Fix:** Compare as order-independent sets (e.g. `sets.New(...)`), so a pure reordering does not trigger a crash.

### P1 🟡 Medium: `PodCIDRs()` returns a live alias into the shared informer Node object (no defensive copy)

| | |
|---|---|
| **File** | `pkg/proxy/node.go:128` |
| **Category** | resource-management / aliasing |
| **Found by** | go-reviewer (Medium, `pre_existing`) |

**Issue:** `PodCIDRs()` returns `n.node.Spec.PodCIDRs` (a slice aliased into the `*v1.Node` stored in `NodeManager`) after releasing the lock, and `n.node` is assigned straight from informer/lister objects without a DeepCopy. This is inconsistent with the sibling `Node()` accessor, which deep-copies before returning, and with the client-go convention that informer objects are shared read-only. Harmless today (the only caller reads it once at startup), but a future caller that mutates or `append`s into the returned slice would corrupt the shared source of truth used by `OnNodeChange`'s comparisons. The aliasing pattern predates this PR (carried over from `NodePodCIDRHandler`) but is newly exposed via a public getter.

**Fix:** `return slices.Clone(n.node.Spec.PodCIDRs)`, matching `Node()`'s defensive-copy discipline.
