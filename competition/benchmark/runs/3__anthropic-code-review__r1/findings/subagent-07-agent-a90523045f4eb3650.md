## Finding 1 (confirmed regression, not speculative) — canon-equivalence added directly to the general-purpose `CanCastTo` family

**File:** `src/coreclr/tools/Common/TypeSystem/Common/CastingHelper.cs`
**Lines:** 176 (`IsCanonicalCastTarget` in `CanCastToInternal`), 426/433 (`CanCastToNonVariantInterface`, adds `IsCanonEquivalent`), 477 (`CanCastByVarianceToInterfaceOrDelegate`, adds `IsCanonicalTypeArgMatch`), 552 (`CanCastToClass`, adds `IsCanonEquivalent`)

**Description:** The PR makes `I<__Canon>.CanCastTo(I<object>)` (and similar canon-vs-concrete-reference-type cases) return `true` by adding canon-wildcard matching straight into `CanCastTo`'s interface/class walk. `CanCastTo` is a general-purpose API used well beyond reflection/constraint-checking — notably by the JIT's `CorInfoImpl.compareTypesForCast`, which treats a positive `CanCastTo` result as "this cast **must** succeed for every concrete instantiation the shared generic code could see" and uses that to fold `isinst`/cast checks away entirely during crossgen2/R2R compilation of shared generic code. That invariant is false for the new canon-equivalence rule: `I<__Canon>` is compatible with *some* concrete instantiations (e.g. `I<object>`) but not others (e.g. `I<string>` is not castable to `I<object>` since `I<T>` here is non-variant), so folding the cast to "always true" is a miscompilation.

**Historical evidence:**
- Issue #127259 (R2R test failures across essentially every platform: `JIT/opt/Casts/shared_Casts.dll`, `Assert.Equal() Failure: Expected 100, Actual 0`), root-caused by @AndyAyersMS on 2026-04-22: *"This is a regression from #127146... `fromType.CanCastTo(toType)` is `I<__Canon>.CanCastTo(I<object>)`. Before #127146 that returned `false`; after #127146 it returns `true`, because the new `IsCanonEquivalent` check in `CanCastToNonVariantInterface` treats any `I<__Canon>` as matching `I<X>` for any reference type `X`... Note: the VM path (`TypeHandle::CanCastTo` in jitinterface.cpp) was **not** touched by #127146, so non-R2R runs are unaffected. The bug only reproduces under crossgen2/R2R."*
- PR #127301, "Revert 'Handle canonical types in casting logic'" (merged 2026-04-23), reverting 127146 directly, with the author's own comment: *"It doesn't match CanCastTo in the VM... I started #127146 with the logic not being in the CanCastTo (the first commit has that), but copilot wasn't able to come up with anything reliable... I lost confidence in being able to do it reliably there and moved it to CanCastTo."* And on issue #127259: *"Copilot lied to me that CoreCLR CanCastTo says yes for anything canonical and the managed implementation was actually more precise. I really didn't want to read C++. Looks like I still need to read C++ in the AI age."*
- PR #129278, "Handle canonical types in constraints checks" (merged 2026-06-18) is the eventual accepted fix. It explicitly separates the two casting semantics instead of merging them: *"an update to the casting logic so that we can have both casting logic that treats `__Canon` as a `class __Canon : object` and nothing else (this is compatible with how casting in CoreCLR VM works), but also another casting logic that treats `__Canon` as 'some reference type, could be something that does cast'. Then update constraints check to use this flavor of the casting logic."* Concretely, it adds a **new, separate** `CanCastToWithCanon(this TypeDesc, TypeDesc)` entry point in `CastingHelper.cs`, and only `TypeSystemConstraintsHelpers.cs` calls it — the general `CanCastTo`/`CanCastToNonVariantInterface`/`CanCastByVarianceToInterfaceOrDelegate`/`CanCastToClass` are left untouched, exactly matching AndyAyersMS's suggested minimal/long-term fix ("scope the canon-equivalence additions... via an explicit `CanCastToWithCanonEquivalence` entrypoint... `DevirtualizationManager`, `MetadataVirtualMethodAlgorithm`, and `ILImporter.StackValue` also call [CanCastTo] and have the same trust assumption").

**Conclusion:** as authored (i.e. as it stands in this checkout), the PR's approach is the exact one that was found to miscompile shared-generic-code casts under R2R/crossgen2 and had to be reverted. The subsequently-merged fix keeps this PR's constraint-check improvements but explicitly does **not** put canon-equivalence logic inside `CanCastTo` itself.

## Finding 2 (plausible, lower-confidence gap — not proven to be a live bug)

**File:** `src/coreclr/tools/aot/ILCompiler.Compiler/Compiler/Dataflow/HandleCallAction.cs`
**Lines:** 766–773 (`MakeGenericMethodSite.InstantiateDependencies`) vs. 776–794 (`MakeGenericTypeSite.InstantiateDependencies`, the one the PR patches)

**Description:** The PR adds `instantiatedType = instantiatedType.NormalizeInstantiation();` before `CheckConstraints()` only in `MakeGenericTypeSite` (line 788), with the comment "InstantiateSignature could end up with a denormalized shape (Foo\<object, \_\_Canon\>) so normalize." The sibling `MakeGenericMethodSite` (constructed symmetrically at line 163, right next to `MakeGenericTypeSite` at line 90) builds `instantiatedMethod` via the identical `_method.InstantiateSignature(...)` call and then calls `CheckConstraints(...)` directly, with no normalization. Since `MethodDesc.InstantiateSignature` (`src/coreclr/tools/Common/TypeSystem/Common/MethodDesc.cs:760`) computes `instantiatedOwningType = owningType.InstantiateSignature(...)` — the exact same `TypeDesc.InstantiateSignature` call that produces the denormalized shape being guarded against — and `CheckConstraints(MethodDesc)` (`TypeSystemConstraintsHelpers.cs:210`) checks `method.OwningType.CheckConstraints(context)` first, the same "denormalized shape" scenario looks structurally reachable via `MethodInfo.MakeGenericMethod()` too, just left unfixed here.

**Historical evidence:** `NormalizeInstantiation` is a pre-existing, long-established helper (`src/coreclr/tools/Common/Compiler/TypeExtensions.cs:678`, present since at least the 2020-2021 CoreRT/crossgen2 merges) used defensively in many places before dependency/constraint computations on constructed types (`Compilation.cs`, `RootingHelpers.cs`, `UsageBasedMetadataManager.cs`, `SubstitutedILProvider.cs`, etc.) — so calling it here is consistent with established usage, but the PR's own fix only applies it to one of two structurally identical call sites. Notably, the later accepted fix (PR #129278) reinstates the *exact same* one-sided fix (only `MakeGenericTypeSite` gets `NormalizeInstantiation()`), and the added test `TestMakeGenericConstrainedDataflow` in `src/tests/nativeaot/SmokeTests/TrimmingBehaviors/Dataflow.cs` only exercises `MakeGenericType`, not `MakeGenericMethod`. This makes it hard to say for certain whether this is a genuine live gap (never triggered/never tested) or a deliberate scoping decision — worth a direct question to the author rather than a confirmed bug claim.

No reintroduction of the #119102 bug found.

- `NormalizeInstantiation` itself is not new; it's a well-established helper used the same way elsewhere, so its use in `HandleCallAction.cs` is idiomatic (see Finding 2 for the one-sided application caveat).
