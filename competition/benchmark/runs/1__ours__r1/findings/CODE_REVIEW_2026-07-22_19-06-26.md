## Findings

### #1 🔴 Critical: Cache key `$"{blobDatabaseName}_{blobTableName}"` is not collision-free across (database, table) pairs

| | |
|---|---|
| **File** | `src/Microsoft.Data.Sqlite.Core/SqliteDataRecord.cs:328` |
| **Category** | other (correctness — wrong-data association) |
| **Confidence** | 100 (validated: confirmed) |
| **Found by** | adversarial-reviewer (High), knowledge-reviewer (MUST→Critical), spec-compliance-reviewer (Medium — dissenting), quick-reviewer (Medium — dissenting), broad-reviewer (Medium — dissenting) |

**Issue:** The new per-table rowid-ordinal cache keys on naive string concatenation with `_`, a character legal and idiomatic in both SQLite ATTACH aliases and table names. Distinct pairs collide: (db `archive_v2`, table `data`) and (db `archive`, table `v2_data`) both key `"archive_v2_data"`. If one query streams blob columns from both colliding pairs, the second lookup silently reuses the first table's cached rowid ordinal — `SqliteBlob` is then opened with the correct db/table strings but the **wrong rowid value**, yielding silently wrong blob data or `SqliteException: no such rowid`. This is the same defect class the PR fixes, resurrected via key encoding. The validator confirmed the harm path end-to-end: `RowIdInfo.TableName` is stored but never read back to sanity-check a cache hit, and the cache persists across every row of the result set, so a collision corrupts all rows of that statement. Trigger requires multi-database queries with underscore-coincident names (narrow — the dissenting Medium ratings reflect this), but the encoding ambiguity is verifiable by inspection.

**Fix:** Key the dictionary on a value tuple — no string encoding needed:
```csharp
private readonly Dictionary<(string? Database, string? Table), RowIdInfo> _rowIds = new();
...
if (!_rowIds.TryGetValue((blobDatabaseName, blobTableName), out var rowIdForOrdinal))
```

### #2 🔴 Critical: Negative lookup outcome is no longer cached — full metadata rescan on every GetStream call

| | |
|---|---|
| **File** | `src/Microsoft.Data.Sqlite.Core/SqliteDataRecord.cs:329` |
| **Category** | performance (+ undocumented-decision aspect) |
| **Confidence** | 100 (validated: confirmed) |
| **Found by** | performance-reviewer (High), adversarial-reviewer (High), knowledge-reviewer (MUST→Critical), quick-reviewer (Medium — dissenting) |

**Issue:** Pre-change, `_rowidOrdinal = -1` was assigned unconditionally **before** the scan loop, memoizing "no usable rowid" — the scan ran at most once per reader. Post-change, `RowIds.Add` is only called in the two "found" branches (lines 355, 387); when the loop completes without a match (composite PK, WITHOUT ROWID table, expression columns), nothing is stored. Every subsequent `GetStream` call for that table — i.e. every `GetBytes`/`GetChars`/`GetString`/`GetTextReader` call, per chunk of a streamed blob and per row — re-runs the O(FieldCount) scan including per-column native `sqlite3_table_column_metadata` calls and, when a same-table INTEGER PK-flagged column exists, re-prepares and executes a fresh `SELECT COUNT(*) FROM pragma_table_info($table) WHERE pk != 0;` command against the live connection (line 377). Adversarial-reviewer's amplification example: a 1 GB blob read in 4 KB chunks ≈ 262k hidden pragma queries where the old code issued exactly 1. The validator confirmed the reader reuses the same `SqliteDataRecord`/`RowIds` instance across rows (only `NextResult()` renews it). Knowledge-reviewer additionally notes nothing (comment or commit message) records that negative caching was dropped, so a maintainer cannot tell whether it was deliberate.

**Fix:** Cache the negative outcome too — store the result unconditionally after the scan (nullable-value dictionary or sentinel), restoring the pre-change once-per-table cost:
```csharp
// after the loop, even when nothing was found:
RowIds[rowidkey] = rowIdForOrdinal;   // with Dictionary<string, RowIdInfo?>
```

### #3 🔴 Critical: `Debug.Assert(rowIdForOrdinal!=null)` fires on legitimate no-rowid code paths (Debug builds)

| | |
|---|---|
| **File** | `src/Microsoft.Data.Sqlite.Core/SqliteDataRecord.cs:393` |
| **Category** | error-handling |
| **Confidence** | 100 (validated: confirmed) |
| **Found by** | knowledge-reviewer (MUST→Critical), quick-reviewer (High), broad-reviewer (High), spec-compliance-reviewer (High), dotnet-reviewer (High), adversarial-reviewer (Medium — dissenting) |

**Issue:** The pre-change code set `_rowidOrdinal = -1` before the scan, so `Debug.Assert(_rowidOrdinal.HasValue)` was tautologically true and could never fire. The rewrite drops the sentinel: `rowIdForOrdinal` stays `null` unless a `rowid` alias or single-column INTEGER PK is found, and the assert now fires on a legitimate, designed path — the very next lines handle `null` as the MemoryStream fallback. The validator traced reachability on **existing in-repo tests**: `GetStream_works_when_composite_pk` (`PRIMARY KEY (Id1, Id2)` → `pkColumns == 2`, no assignment) and even the basic `GetStream_works` (`SELECT x'427E5743'` — the loop's only iteration hits `i == ordinal` and skips, so the body never executes). Both pass today only because the old sentinel made the assert vacuous. Release builds are unaffected (`[Conditional("DEBUG")]`; CI builds Release per `azure-pipelines.yml`), so the blast radius is Debug-configuration test runs and Debug consumers — where a failed assert can fail-fast the process ([Inference] under default trace listeners; expected behavior, not executed here). The assert also encodes an invariant the adjacent `if (rowIdForOrdinal == null)` branch contradicts — a maintainer cannot tell which is intended.

**Fix:** Delete the assert (null is an expected, handled outcome), or — combined with the fix for #2 — assert the true invariant instead (e.g. that the cache now contains the key):
```csharp
// Debug.Assert(rowIdForOrdinal != null);   // removed: null is the designed MemoryStream-fallback signal
```

### #5 🟡 Medium: `RowIds` dictionary allocated unconditionally per record, unlike every sibling cache in the class

| | |
|---|---|
| **File** | `src/Microsoft.Data.Sqlite.Core/SqliteDataRecord.cs:39` |
| **Category** | performance (structural consistency) |
| **Confidence** | 75 (validated: confirmed) |
| **Found by** | broad-reviewer (Medium) |

**Issue:** `readonly Dictionary<string, RowIdInfo> RowIds = new Dictionary<string, RowIdInfo>();` allocates on every `SqliteDataRecord` construction — one per SELECT result set (`SqliteDataReader.NextResult()`, line 180, constructs the record for any statement returning columns), whether or not the query touches a BLOB. All four sibling caches (`_blobCache`, `_typeCache`, `_columnNameOrdinalCache`, `_columnNameCache`) are nullable and lazily initialized (`??=`) — verified at their initialization sites by the validator. The replaced `int? _rowidOrdinal` cost nothing until assigned. `RowIds` is used only inside `GetStream`, so lazy init there is straightforward with no thread-safety obstacle.

**Fix:**
```csharp
private Dictionary<string, RowIdInfo>? _rowIds;
...
_rowIds ??= new Dictionary<string, RowIdInfo>();
```

### #6 🟡 Medium: New interpolated key string allocated on every GetStream call, including cache hits

| | |
|---|---|
| **File** | `src/Microsoft.Data.Sqlite.Core/SqliteDataRecord.cs:328` |
| **Category** | performance (allocation) |
| **Confidence** | 75 (validated: confirmed) |
| **Found by** | performance-reviewer (Medium) |

**Issue:** `string rowidkey = $"{blobDatabaseName}_{blobTableName}";` executes unconditionally before the `TryGetValue`, so a fresh key string is allocated on every `GetStream` invocation — even on the hit path, where the pre-change code did a zero-allocation `_rowidOrdinal.HasValue` check. `GetBytes` (line 276) and `GetChars` (line 290) call `GetStream` fresh per invocation, so chunked blob reads and multi-row iteration multiply the allocation (the same reader/record instance is reused across rows). **Fix:** Use the value-tuple key from finding #1 — the two component strings are already materialized; tuple keys allocate nothing extra.
