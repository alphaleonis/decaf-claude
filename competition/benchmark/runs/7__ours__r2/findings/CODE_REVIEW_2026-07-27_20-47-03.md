## Findings

### #1 🔴 Critical: `getChunkSeriesSet` closes the querier before the returned lazy `ChunkSeriesSet` is iterated (use-after-close)

| | |
|---|---|
| **File** | `storage/remote/read_handler.go:247` (the `defer querier.Close()`, firing at the `return querier.Select(...)` on line 265) |
| **Category** | resource-management / concurrency (use-after-close) |
| **Confidence** | 100 (independently corroborated ×6; validator-confirmed) |
| **Found by** | quick-reviewer (Critical), broad-reviewer (Critical), performance-reviewer (Critical), go-reviewer (Critical), design-reviewer (Critical), adversarial-reviewer (Critical) |

**Issue:**

The new helper releases the querier before its output is consumed:

```go
func (h *readHandler) getChunkSeriesSet(...) storage.ChunkSeriesSet {
	querier, err := h.queryable.ChunkQuerier(...)
	if err != nil { return storage.ErrChunkSeriesSet(err) }
	defer func() { querier.Close() ... }()   // fires when the function returns
	...
	return querier.Select(ctx, true, hints, filteredMatchers...)  // lazy ChunkSeriesSet
}
```

The caller iterates the returned set **after** the helper returns:

```go
chunks := h.getChunkSeriesSet(ctx, query, filteredMatchers) // querier.Close() has already run
if err := chunks.Err(); err != nil { return err }
ws, err := StreamChunkedReadResponses(NewChunkedWriter(w, f), int64(i), chunks, ...) // iterates here
```

The evidence chain was traced end-to-end through the source (not executed) by six independent reviewers and re-verified by a validator:

1. **Iteration happens after `Close()`.** `remoteReadStreamedXORChunks` receives `chunks` only after `getChunkSeriesSet` has returned (and thus after its `defer querier.Close()` ran). `StreamChunkedReadResponses` (`storage/remote/codec.go:235-266`) drives `ss.Next()` / `series.Iterator()` / `iter.Next()` / `iter.At()` during streaming.
2. **Chunk reads are lazy.** `blockChunkQuerier.Select` (`tsdb/querier.go:174-196`) returns a `blockChunkSeriesSet` that retains the block's `IndexReader`/`ChunkReader` by reference. `At()` returns a `chunkSeriesEntry{chunks: b.chunks}`, and bytes are read on iteration via `populateWithDelChunkSeriesIterator` → `cr.ChunkOrIterable()` (`tsdb/querier.go:721`), a **zero-copy** view into the mmap'd block segment files (`tsdb/chunks/chunks.go:665-704`).
3. **`Close()` releases exactly those resources.** `blockBaseQuerier.Close()` (`tsdb/querier.go:103-115`) → `blockChunkReader.Close()` (`tsdb/block.go:567-569`) calls `Block.pendingReaders.Done()`. `Block.Close()` — invoked by compaction/retention via `reloadBlocks`/`deleteBlocks` (`tsdb/db.go`) — does `pendingReaders.Wait()` **before** unmapping the chunk files (`tsdb/block.go:378-390`). Closing the querier early drops the only guard keeping the mmap alive during the stream.
4. **Head path, same root cause.** For head-backed queries, `headChunkReader.Close()` → `isoState.Close()` unregisters the read from the isolation list that `Head.Truncate`'s `WaitForPendingReadersInTimeRange` waits on, so head truncation can delete a chunk segment the stream still needs (adversarial-reviewer, corroborated by design/performance).
5. **The sibling `remoteReadSamples` is unaffected.** It fully materializes via `ToQueryResult(querier.Select(...))` (`read_handler.go:161`) *inside* the same closure that holds `defer querier.Close()` — the correct pattern, and the shape the streamed path had before this PR (confirmed via `git diff` of the pre-PR revision).

**Consequence:** For any streamed chunked read touching a persistent (mmap-backed) block, if a concurrent compaction/retention/head-truncation completes during the streaming window, the handler reads unmapped memory → process crash (SIGSEGV/SIGBUS) or corrupt chunk bytes streamed to the client. The **resource-lifecycle contract violation is directly verified from the code**; the exact runtime manifestation (crash vs. corruption vs. nothing) is `[Inference]` and depends on the timing of a concurrent block deletion. The PR's own target scenario — a slow/broken client holding the stream open for minutes — *maximizes* this race window, so the change trades a bounded, recoverable OOM risk for an unbounded-consequence memory-safety hazard.

**Note on the stated goal:** For persistent blocks, `querier.Close()` is largely bookkeeping (a `pendingReaders` decrement), not a synchronous memory release, so closing early frees little/no memory — it mainly moves resource release ahead of the point the resource is still needed. The genuine OOM lever is the *head isolation state* (holding it blocks head truncation during a stall), but the change releases the entire reader rather than just that watermark.

**Fix:** Keep the querier open until `StreamChunkedReadResponses` has fully consumed the set. Return the querier (or a closer) from the helper and `defer querier.Close()` in `remoteReadStreamedXORChunks`'s per-query closure *after* streaming — restoring the pre-PR / `remoteReadSamples` lifetime while keeping the extracted helper and the early `chunks.Err()` check:

```go
func (h *readHandler) getChunkSeriesSet(ctx context.Context, query *prompb.Query, filteredMatchers []*labels.Matcher) (storage.ChunkQuerier, storage.ChunkSeriesSet) {
	querier, err := h.queryable.ChunkQuerier(query.StartTimestampMs, query.EndTimestampMs)
	if err != nil {
		return nil, storage.ErrChunkSeriesSet(err)
	}
	var hints *storage.SelectHints
	if query.Hints != nil { hints = &storage.SelectHints{ /* ... */ } }
	return querier, querier.Select(ctx, true, hints, filteredMatchers...)
}

// caller:
querier, chunks := h.getChunkSeriesSet(ctx, query, filteredMatchers)
if querier != nil {
	defer func() {
		if err := querier.Close(); err != nil {
			level.Warn(h.logger).Log("msg", "Error on chunk querier close", "err", err.Error())
		}
	}()
}
if err := chunks.Err(); err != nil { return err }
// ... StreamChunkedReadResponses(..., chunks, ...) still within this closure ...
```

If bounding resource hold time for broken/slow clients is the real objective, do it with a write/iteration deadline or byte budget on the stream (or release only the head isolation state) — not an early `Close()` on a lazily-consumed series set.

### #2 🟠 High: `getChunkSeriesSet` doc comment documents a false safety guarantee ("ensure timely release")

| | |
|---|---|
| **File** | `storage/remote/read_handler.go:239-241` |
| **Category** | knowledge-preservation / misleading documentation (doc-vs-code contradiction) |
| **Confidence** | 100 (deterministic-claim re-anchor; validator-confirmed) |
| **Found by** | broad-reviewer (High), knowledge-reviewer (MUST ≈ High) |

**Issue:** The comment reads:

> `getChunkSeriesSet executes a query to retrieve a ChunkSeriesSet, encapsulating the operation in its own function to ensure timely release of the querier resources.`

It frames the extraction as *ensuring* correct/timely resource release. Per finding #1, the helper's `defer querier.Close()` releases the querier **before** the returned lazy set is consumed — releasing resources streaming still depends on, i.e. *premature*, not "timely." The comment also omits the load-bearing precondition a maintainer needs: whether iterating the returned `ChunkSeriesSet` after `Close()` is safe. The validator confirmed the codebase has an established convention for exactly this hazard class — `LabelQuerier.LabelValues` (`storage/interface.go:161`) explicitly warns "It is not safe to use the strings beyond the lifetime of the querier," with the same phrasing recurring in `tsdb/block.go` and `tsdb/index/index.go` — yet `ChunkQuerier`/`ChunkSeriesSet` carry no such caveat, and this new comment asserts the close-early pattern unconditionally. A maintainer reading it has no reason to suspect the lazy-iteration hazard and could copy the "helper returns a lazy set after a deferred Close" pattern into a path where the result *is* tied to querier lifetime, propagating a real fault.

**Fix:** Once the lifetime bug (#1) is fixed, rewrite the comment to state what the helper actually does and the precondition it relies on — e.g. that chunk reads happen lazily during iteration, so the caller must not close the querier until the returned set is fully consumed. Consider adding the post-`Close()` validity caveat to the `ChunkSeriesSet` / `ChunkQuerier.Select` docs in `storage/interface.go` so the contract lives at its source. Do not ship a comment claiming "timely release" is safe while the lazy-consumption hazard stands.

## Specialist Notes

### Considered But Not Flagged (all agents)

- **Duplicated `SelectHints` construction** between `remoteReadSamples` (`:147-158`) and `getChunkSeriesSet` (`:253-264`) — byte-for-byte identical. Multiple reviewers (broad, knowledge, consistency) verified via `git diff` that this duplication *pre-existed* the PR (the block was already inline in the old streamed path); the PR relocated rather than introduced it. Pre-existing DRY nit, not attributable to this changeset — not flagged.
- **`chunks.Err()` as the only pre-stream error check** (`:206`) — not a regression. `storage.ChunkQuerier.Select` has no `error` return; surfacing construction/postings errors via `.Err()` is the existing interface contract, and iteration-time errors are still caught by `StreamChunkedReadResponses` via `ss.Err()`/`iter.Err()`. Error type is preserved (`storage.ErrChunkSeriesSet` returns the original unwrapped error, so `errors.As(err, &httpErr)` still works). Dismissed by quick/broad/design/go — sound.
- **Open head chunk / defensive-copy paths** — the currently-appended head chunk is copied (`ChunkWithCopy`/`copyHeadChunk=true`), and `ChunkDiskMapper.Chunk` copies + locks against truncation, so the head path degrades to a `CorruptionErr`/panic rather than a silent torn read (adversarial). Folded into #1's head variant, not a distinct finding.
- **Loop-var shadowing** `for _, w := range ws` shadowing the `w http.ResponseWriter` param — functionally correct, pre-existing pattern also in `remoteReadSamples`; below the anchor-50 bar (go-reviewer).
- **Confidence-gate suppressions**: none — all surfaced findings cleared the gate.

### Probe Requests (nominated, not run)

Several reviewers (adversarial, design, go) nominated probes to convert the crash `[Inference]` into a runtime confirmation:
1. A **deterministic** unit test injecting a fake `SampleAndChunkQueryable` whose `ChunkQuerier.Close()` poisons the buffer its `ChunkSeriesSet` reads from, then driving `remoteReadStreamedXORChunks` → `StreamChunkedReadResponses` and asserting the streamed bytes equal the pre-close bytes.
2. An **integration** test streaming a chunked read over a persistent block, stalling the writer mid-stream, then triggering `db.reloadBlocks()`/`deleteBlocks`/`head.Truncate` to race `Block.Close()`→`pendingReaders.Wait()` against the in-flight iteration.
3. Adding `store.DB.Compact()` to the existing `TestStreamReadEndpoint` to force the fixture data into an mmap-backed block.

**Not run.** These are all *new-test-authoring*, not line-removal revert probes, and none is both safe and reliable here: probe (3) would **not** reproduce, because a unit test triggers no concurrent `Block.Close()`/`deleteBlocks`, so `pendingReaders.Done()` leaves the mmap valid (the fault needs a concurrent deletion); probes (1)/(2) require substantial new scaffolding and, for (2), a nondeterministic SIGSEGV/race that risks destabilizing the shared working tree. The finding is already at anchor 100 with six independent, fully-traced static corroborations and a confirming validator pass, so no probe was executed. (`probe not run: nominated probes require authoring new tests; simplest one does not reproduce without a concurrent block deletion.`)
