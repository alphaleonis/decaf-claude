Three findings reported via `ReportFindings`, most severe first:

1. **`SqliteDataRecord.cs:393`** — `Debug.Assert(rowIdForOrdinal!=null)` now asserts an invariant that is routinely false: any table without a single-column INTEGER PRIMARY KEY (WITHOUT ROWID tables, composite/non-integer PKs) legitimately leaves `rowIdForOrdinal` null and falls through to the existing `if (rowIdForOrdinal == null)` cached-blob branch. The old assert (`_rowidOrdinal.HasValue`) was always trivially true because `_rowidOrdinal` was pre-seeded to `-1`, so it never fired — this diff turned a no-op check into one that can genuinely fail on normal input.

2. **`SqliteDataRecord.cs:329`** — the "no rowid found" outcome is never written into the new `RowIds` dictionary (only the two `RowIds.Add(...)` calls on the found-rowid paths populate it), unlike the old `_rowidOrdinal = -1` sentinel which cached the negative result. This means every `GetStream`/`GetBytes` call on a blob column of a table lacking a rowid alias re-runs the full column scan and re-executes the `pragma_table_info` query each time, defeating the caching this refactor was built around.

3. **`SqliteDataRecord.cs:328`** — the cache key `$"{blobDatabaseName}_{blobTableName}"` is built by naive string concatenation with `_` and can collide across distinct (database, table) pairs (e.g. database `main_orders`/table `items` vs. database `main`/table `orders_items` both produce `main_orders_items`), which could cause the wrong `RowIdInfo` to be reused for blob streaming in attached-database scenarios. Lower likelihood since it requires attached databases with colliding names, but it's a genuine logic flaw in the new keying scheme.
