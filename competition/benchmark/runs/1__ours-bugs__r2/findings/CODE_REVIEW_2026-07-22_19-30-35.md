## Findings

### #1 🔴 Critical: Cache key `$"{blobDatabaseName}_{blobTableName}"` is not injective — distinct (database, table) pairs can collide

| | |
|---|---|
| **File** | `src/Microsoft.Data.Sqlite.Core/SqliteDataRecord.cs:328` |
| **Category** | correctness (undocumented load-bearing assumption) |
| **Confidence** | 100 |
| **Found by** | knowledge-reviewer (Critical), quick-reviewer (Medium — dissenting), broad-reviewer (Medium — dissenting), spec-compliance-reviewer (Medium — dissenting), adversarial-reviewer (Medium — dissenting) |
| **Validation** | confirmed (pre_existing: false confirmed — the key scheme is new in this PR) |

**Issue:** The new rowid cache is keyed by string concatenation with `_` as the delimiter. `_` is a legal and common character in SQLite database aliases (`ATTACH ... AS`) and table names, so the mapping is not injective: database `a_b` + table `c` and database `a` + table `b_c` both produce key `"a_b_c"`. If a single streamed query touches blobs from both pairs, the second lookup reuses the first pair's cached `RowIdInfo` ordinal — `GetInt64` reads a rowid from the wrong column and `SqliteBlob` opens the wrong row: either `SqliteException: no such rowid` or **silently wrong blob bytes** — the same bug class this PR exists to fix, reintroduced at the key boundary. Nothing in code or comments records the assumption that the delimiter cannot create ambiguity. The validator confirmed the collision is constructible with ordinary application-controlled SQL (ATTACH semantics permit it).

**Dissent recorded:** four finders rated Medium, citing the narrow trigger (requires underscore-ambiguous naming across attached databases within one streamed query). Critical kept per the specialist's rating and the silent-wrong-data outcome.

**Fix:** Key the dictionary on the pair itself — delimiter-free, structurally hashed:
```csharp
private readonly Dictionary<(string Database, string Table), RowIdInfo> _rowIds = new();
...
var rowidKey = (blobDatabaseName, blobTableName);
if (!_rowIds.TryGetValue(rowidKey, out var rowIdForOrdinal))
```

### #2 🔴 Critical: `Debug.Assert(rowIdForOrdinal != null)` asserts a false invariant — fires on the supported no-rowid fallback in Debug builds

| | |
|---|---|
| **File** | `src/Microsoft.Data.Sqlite.Core/SqliteDataRecord.cs:393` |
| **Category** | error-handling |
| **Confidence** | 100 |
| **Found by** | knowledge-reviewer (Critical), quick-reviewer (High), broad-reviewer (High), dotnet-reviewer (High), adversarial-reviewer (Medium — dissenting), spec-compliance-reviewer (Medium — dissenting) |
| **Validation** | confirmed |

**Issue:** The pre-change code seeded `_rowidOrdinal = -1` before the discovery scan, so `Debug.Assert(_rowidOrdinal.HasValue)` was vacuously true. The new code assigns `rowIdForOrdinal` only when a rowid/single-INTEGER-PK column is actually found; when the scan legitimately finds none (composite primary key, expression/view columns, blob selected without its PK, WITHOUT ROWID tables), it stays `null` — precisely the state the very next statement (`if (rowIdForOrdinal == null) return new MemoryStream(...)`) handles as a designed fallback. The assert and the branch now contradict each other: one of them lies about the contract. The **pre-existing, unmodified test `GetStream_works_when_composite_pk`** (SqliteDataReaderTest.cs:516) statically reaches this assert with `null` — any Debug-configuration build/test run (the local default) trips it on an already-passing scenario. CI builds Release (`_BuildConfig: Release`), so shipped binaries strip the assert; the impact is Debug builds, dev loops, and the assert permanently mis-documenting the invariant (a future maintainer trusting it may remove the "unreachable" null branch, destroying the fallback).

**Fix:** Delete the assert — the null branch below is the correct contract — or replace it with a comment: `// null = no usable rowid in this projection; fall back to cached in-memory blob`. (Caching the negative result per finding #4 with a sentinel also restores a truthful assertable invariant.)

### #4 🟠 High: Negative rowid-lookup result is never cached — full column scan plus a `pragma_table_info` SQL query re-run on every GetStream/GetBytes call

| | |
|---|---|
| **File** | `src/Microsoft.Data.Sqlite.Core/SqliteDataRecord.cs:327-396` |
| **Category** | performance (behavioral regression vs. pre-change code) |
| **Confidence** | 100 |
| **Found by** | broad-reviewer (High), knowledge-reviewer (High), adversarial-reviewer (High), performance-reviewer (High) |
| **Validation** | confirmed (all four sub-claims verified against working tree + HEAD~1) |

**Issue:** The old code set `_rowidOrdinal = -1` **before** the discovery scan, permanently caching the "no usable rowid" outcome; the scan — including the `SELECT COUNT(*) FROM pragma_table_info($table) WHERE pk != 0` command execution — ran at most once per record. The new code adds to `RowIds` only on the two found branches (lines 355, 387); on the fall-through path nothing is cached. Every subsequent `GetStream` call — and `GetBytes`/`GetChars`/`GetTextReader` route through it unconditionally, i.e. every chunk of a chunked blob read and every row of a read loop — re-runs the O(FieldCount) scan including per-column `sqlite3_table_column_metadata` calls and a fresh `command.ExecuteScalar()` (`pkColumns` is a per-call local). A `SqliteDataRecord` persists for a whole result set (created once per statement in `SqliteDataReader.NextResult()`), so a large scan streaming blobs from a composite-PK or WITHOUT ROWID table executes one extra SQL command per row/chunk (adversarial-reviewer's example: a 100 MB blob read in 8 KB chunks ≈ ~12,800 extra command executions mid-read). Neither code, commits, nor the PR discussion records dropping negative caching as a deliberate trade-off.

**Fix:** Cache the negative outcome too, restoring one-scan-per-table semantics — e.g. `Dictionary<(string, string), RowIdInfo?>` storing `null` for "no rowid" (treat a present-but-null entry as the `MemoryStream` fallback), or a sentinel `RowIdInfo(-1, ...)`. This also makes the finding-#2 assert question moot.

## Pre-existing Issues

### P1 🟠 High: Self-join (same table referenced twice) resolves the wrong rowid — deterministic silently wrong blob data

| | |
|---|---|
| **File** | `src/Microsoft.Data.Sqlite.Core/SqliteDataRecord.cs:328` (key granularity; scan at 339-390) |
| **Category** | correctness |
| **Confidence** | 100 |
| **Found by** | adversarial-reviewer (High, pre-existing), spec-compliance-reviewer (Medium — dissenting, pre-existing), broad-reviewer (Medium — dissenting, marked new) |
| **Validation** | confirmed; **reattributed pre_existing: true** — the validator replayed the identical query against the pre-PR code (`HEAD~1`) and got the byte-identical wrong outcome, overriding broad-reviewer's dissent |

**Issue:** `sqlite3_column_table_name` returns the underlying schema table name, never the SQL alias. For `SELECT a1.ID, a1.VALUE, a2.ID, a2.VALUE FROM A a1 JOIN A a2 ON ...`, both blob columns map to cache key `"main_A"`: the first `GetStream` caches a1.ID's ordinal (0), the second reuses it for a2's blob — `SqliteBlob` opens table A at **a1's rowid** while serving a2's column. Because a1's own rowid always exists in the table, the open **always succeeds and silently returns a1's bytes for a2's stream** (deterministic, per the validator's trace — not merely on rowid coincidence). This is the same failure class as issue #32747 ("multiple Blob colums"), which the fix does not extend to; the PR's key granularity cannot distinguish aliases of one table. The write-only `RowIdInfo.TableName` field suggests an unfinished attempt at exactly this. Informational: the change did not introduce it (the old single-field cache failed identically), but it also leaves the issue's generalized case open.

**Fix (from finders):** During the scan, if multiple candidate rowid columns for the same (db, table) exist at distinct ordinals, don't cache — fall back to the always-correct eager `MemoryStream` path; at minimum, document the limitation at the key construction site.
