### #1 🔴 Critical: Proxy provider re-registers on every `vscode-remote` activation → unbounded provider/emitter leak + error-log spam

| | |
|---|---|
| **File** | `src/vs/platform/files/electron-browser/remoteFileSystemProxyClient.ts:56` (the `onWillActivateFileSystemProvider` listener in `static register`, line 38) |
| **Category** | resource-management / error-handling |
| **Confidence** | 100 |
| **Found by** | broad-reviewer (Critical), quick-reviewer (High), adversarial-reviewer (Medium) |
| **Validation** | confirmed |

**Issue:** `register()` subscribes to `fileService.onWillActivateFileSystemProvider` and, **inside the callback**, constructs a *new* `RemoteFileSystemProxyClient`, does `disposables.add(provider)` (line 61), then calls `fileService.registerProvider(Schemas.vscodeRemote, provider)` (line 62) — with no memoization outside the listener. Verified against `fileService.ts`: `activateProvider()` fires `onWillActivateFileSystemProvider` **unconditionally at line 99, before** the `provider.has(scheme)` short-circuit at line 106, and `withProvider`/`withReadProvider` call it on essentially every operation (`stat`, `readFile`, `readdir`, `copy`). `registerProvider` **throws** on a duplicate scheme (fileService.ts:52-54). So every `vscode-remote` operation after the first, in a window without its own remote connection: (a) builds a new provider + `Emitter` and permanently adds it to the window-lifetime `DisposableStore` (unbounded leak), then (b) throws on `registerProvider` → caught → logged as `logService.error('...Failed to register proxy provider')`. The genuine registration-failure signal thus fires on every normal use, becoming meaningless noise. The sibling `RemoteFileSystemProviderClient.register()` avoids this by memoizing a single registration promise **outside** the listener and only `e.join(promise)`-ing on each firing.

**Fix:** Build the provider + `registerProvider` once (a memoized promise outside the listener) and have the listener only `e.join(registrationPromise)` on each firing — mirroring `RemoteFileSystemProviderClient.register()`.
```typescript
const registrationPromise = (async () => {
	try {
		const provider = new RemoteFileSystemProxyClient(mainProcessService, logService);
		disposables.add(provider);
		disposables.add(fileService.registerProvider(Schemas.vscodeRemote, provider));
	} catch (error) {
		logService.error('RemoteFileSystemProxyClient: Failed to register proxy provider', error);
	}
})();
disposables.add(fileService.onWillActivateFileSystemProvider(e => {
	if (e.scheme === Schemas.vscodeRemote) { e.join(registrationPromise); }
}));
```
> Dissent noted: rated Critical by broad, High by quick, Medium by adversarial. Kept at highest per consolidation policy — an unbounded leak triggered by ordinary use that also defeats error observability.

### #2 🟠 High: Concurrent `setToCopy` calls race on the shared `remoteClipboardTempDir` field

| | |
|---|---|
| **File** | `src/vs/workbench/contrib/files/browser/explorerService.ts:287` (`resolveClipboardResources`; field mutated at :306, cleanup at :302, copy at :314) |
| **Category** | concurrency / race-condition |
| **Confidence** | 100 (corroborated ×5) |
| **Found by** | broad (High), design (High), adversarial (High), typescript (High), quick (Medium) |
| **Validation** | waived — corroborated ×5 including a design specialist; each traced the same mechanism |

**Issue:** `remoteClipboardTempDir` is a single instance field read/written across `await` points with no serialization. Two overlapping copies (copy a remote selection, then quickly copy a different one — both routed through `fileActions.ts` `copyFileHandler`/`cutFileHandler` awaiting `setToCopy`) interleave: copy B's `cleanupRemoteClipboardTempDir()` (line 302) recursively deletes copy A's `tempDir` while A is still `await`-ing `fileService.copy` into it (line 314), then B overwrites the field — orphaning A's dir. Whichever `writeResources` resolves **last** wins the OS clipboard, so the older selection can silently replace the user's most recent copy, and A's in-flight copies fail into the fallback (see #12).

**Fix:** Serialize the operation with the codebase's `Sequencer` (`base/common/async.ts`), and capture each operation's temp dir in a local variable (tracked in a set for cleanup) rather than a shared field.

### #3 🟠 High: Eager, blocking, unbounded remote download on the copy gesture (unresolved human-review concern)

| | |
|---|---|
| **File** | `src/vs/workbench/contrib/files/browser/explorerService.ts:266` (`setToCopy` → `resolveClipboardResources`, download at :314) |
| **Category** | performance / production reliability |
| **Confidence** | 100 |
| **Found by** | performance (Critical), broad (High), design (Medium), adversarial (Medium), prior-feedback (Medium) |
| **Validation** | confirmed |

**Issue:** `setToCopy` (awaited by the Ctrl+C / Ctrl+X command handlers) now `await`s `resolveClipboardResources`, which `fileService.copy(resource, target, true)`s every selected **remote** resource to a local temp dir **before** the clipboard write returns. Confirmed: (a) the gesture blocks until download completes; (b) a remote **folder** recurses the entire subtree (`doCopyFolder`) with no file-count/size cap; (c) `IProgressService` is injected but unused on this path (contrast `applyBulkEdit` in the same class, which wraps slow work in `withProgress` + a `CancellationTokenSource`), and no `CancellationToken` is threaded through, so the download cannot be canceled; (d) the loop is sequential. Files are downloaded even if the user never pastes. This is exactly the **unresolved mjbvz thread** ("creating the file eagerly on copy and blocking the copy on this").

**Fix:** Defer download to paste time (the lazy `ClipboardItem`/`Promise<Blob>` direction mjbvz suggested), or at minimum cap size, download concurrently (`Limiter`), and wrap in `progressService.withProgress({ cancellable: true }, ...)` with a `CancellationToken`.
> Dissent noted: performance rated Critical; design/adversarial/prior-feedback Medium. Kept High.

### #4 🟠 High: Temp download deleted while the OS clipboard still references it → later native paste yields an empty file (reintroduces #2008)

| | |
|---|---|
| **File** | `src/vs/workbench/contrib/files/browser/explorerService.ts:302` (cleanup on next remote copy) and `:568` (cleanup in `dispose()`) |
| **Category** | resource-management / lifecycle |
| **Confidence** | 75 |
| **Found by** | adversarial-reviewer (High) |
| **Validation** | confirmed |

**Issue:** On a remote copy, the file's **local temp path** is written to the OS clipboard. Native-OS paste is lazy — it can happen much later. But `cleanupRemoteClipboardTempDir()` recursively `del`s that temp dir on (a) the next remote copy (line 302) and (b) window `dispose()` (line 568). There is no mechanism tying temp lifetime to clipboard lifetime, so after a second remote copy or a window close the user pastes into Finder/Explorer and gets an empty/zero-byte or missing file — the exact vscode-remote-release#2008 symptom this PR set out to fix.

**Fix:** Do not delete a temp dir while it may still back the OS clipboard — use age/refcount-based cleanup, or clear the OS clipboard when deleting the dir.

### #5 🟡 Medium: Remote-clipboard temp dir leaks on disk — cleanup skipped after a local-only copy, and fire-and-forget in a synchronous `dispose()`

| | |
|---|---|
| **File** | `src/vs/workbench/contrib/files/browser/explorerService.ts:299`/`:302` (gated cleanup) and `:567`-`:568` (sync `dispose` calls async cleanup unawaited) |
| **Category** | resource-management (leak) |
| **Confidence** | 75 |
| **Found by** | broad-reviewer (High), typescript-reviewer (Medium) |
| **Validation** | confirmed |

**Issue:** Two lifecycle leaks: (1) `cleanupRemoteClipboardTempDir()` is only called **inside** the `if (remoteResources.length > 0)` branch, so copying a remote file once and then only local files never reclaims the prior temp dir until dispose — a deterministic leak from ordinary use. (2) `dispose(): void` calls the `async cleanupRemoteClipboardTempDir()` **without awaiting** it (floating promise), then immediately runs `this.disposables.dispose()`; if the window/process tears down concurrently the pending `fileService.del` may never complete.

**Fix:** Run cleanup at the start of `resolveClipboardResources` unconditionally, and hook durable cleanup into `lifecycleService.onWillShutdown(e => e.join(...))` rather than a fire-and-forget call in a sync `dispose()`.
> Also confirms the "leak the /tmp path/dir" half of the mjbvz concern (disk-space angle; the privacy/path-broadcast angle is #16). Rated High by broad; kept Medium given the modest impact (orphaned temp files under `cacheHome`).

### #6 🟠 High: Proxy `readFile` buffers whole files in memory across two IPC hops — no streaming capability, no size cap

| | |
|---|---|
| **File** | `src/vs/platform/files/electron-browser/remoteFileSystemProxyServer.ts:69` (`readFile`) and `remoteFileSystemProxyClient.ts:84` (`capabilities`) |
| **Category** | performance / resource bounds |
| **Confidence** | 100 |
| **Found by** | performance-reviewer (High), security-reviewer (Medium) |
| **Validation** | confirmed |

**Issue:** The proxy client advertises only `FileReadWrite | Readonly | PathCaseSensitive` — **no** streaming (`FileOpenReadWriteClose`/`FileReadStream`) capability. Confirmed against `fileService.ts`: a copy whose source provider lacks open/read/close falls into `doPipeUnbufferedToBufferedQueued` / `doPipeUnbuffered`, which reads the **entire** file into one `VSBuffer` (`sourceProvider.readFile`) — never the chunked 256 KB pipe. `RemoteFileSystemProxyServer.readFile` returns `content.value` whole with no `limits.size`, and the main handler forwards it as a single IPC message across two hops (owning renderer → main → requesting renderer). A large remote file fully materializes in memory at each hop → memory amplification / potential OOM.

**Fix:** Implement an open/read/close streaming capability on both proxy client and server so `copy` uses the chunked pipe, and enforce a max size (or stream) for proxied reads.

### #7 🟠 High: Cross-window proxy grants any renderer arbitrary read of another window's entire remote filesystem (confused deputy — no caller authorization or resource scoping)

| | |
|---|---|
| **File** | `src/vs/platform/files/electron-main/remoteFileSystemProxyMainHandler.ts:42` (`call`); `remoteFileSystemProxyServer.ts:53`-`80`; `remoteFileSystemProxyClient.ts:56` (whole-scheme registration) |
| **Category** | security (privilege / trust boundary) |
| **Confidence** | 75 |
| **Found by** | security-reviewer (High; "arguably Critical") |
| **Validation** | confirmed |

**Issue:** `RemoteFileSystemProxyMainHandler.call(_, command, arg)` **ignores the caller's connection context** (`_`) and routes purely on the URI authority in the payload; the target `RemoteFileSystemProxyServer` then reads **any** `vscode-remote://` path via `fileService`, not scoped to the copied resources, with no Workspace-Trust check. Combined with the client registering the proxy for the **entire** `vscode-remote` scheme in every connectionless window, resolving a crafted `vscode-remote://<victim-authority>/etc/passwd` (or `~/.ssh/id_rsa`) in a local window is served by whichever window owns that remote connection. Before this PR a local window had no `vscode-remote` provider (the bug), so this is newly-introduced arbitrary cross-window remote read. The read-only write-guards constrain the wrong axis — **read** is the sensitive capability. Rated High (not Critical) because the direct caller is first-party workbench code; realistic exploitation needs a malicious/untrusted workspace that can cause such a URI to be resolved, or a compromised renderer. (Renderer→renderer is reachable only via the main handler — but the main handler performs zero authorization with the context it holds.)

**Fix:** Add per-operation scoping/authorization — a short-lived allow-list of the exact copied URIs the server validates before serving, and/or a Workspace-Trust gate on the requesting window, and/or target opt-in. Consider an audit log on the serving side.

### #8 🟠 High: Proxy provider hard-codes `PathCaseSensitive`, contradicting the real remote provider (case-insensitive remotes treated as case-sensitive) with no recorded rationale

| | |
|---|---|
| **File** | `src/vs/platform/files/electron-browser/remoteFileSystemProxyClient.ts:84` (`capabilities` getter) |
| **Category** | design / consistency / knowledge-preservation |
| **Confidence** | 100 (quotable, corroborated ×5) |
| **Found by** | knowledge (MUST), consistency (High), broad (Medium), design (Medium), prior-feedback (Medium) |
| **Validation** | waived — quotable deterministic fact corroborated by 5 finders incl. 2 specialists at anchor 100 |

**Issue:** `capabilities` unconditionally ORs in `FileSystemProviderCapabilities.PathCaseSensitive`. The real `RemoteFileSystemProviderClient` derives it from the remote OS (`pathCaseSensitive: remoteAgentEnvironment.os === OperatingSystem.Linux`). For a non-Linux remote (SSH-to-Windows, macOS remote — both case-insensitive), the local window's proxy and the remote-owning window's real provider disagree on case-sensitivity for the same authority, risking path-identity/equality/caching divergence in `FileService.isPathCaseSensitive` consumers. A single local window can also proxy multiple authorities of differing OS, so no one hard-coded value is correct. This was raised in a prior (bot) review thread, marked resolved, but the code is unchanged and carries no comment explaining whether the hard-coding is a deliberate safe simplification (read-only, transient use) or an oversight.

**Fix:** Plumb the remote OS (or a precomputed `pathCaseSensitive`) from the owning window through the proxy channel and compute the bit as `RemoteFileSystemProviderClient` does; if the hard-coding is intentional, document precisely why at the getter.
> Severity range noted: knowledge framed it MUST (missing rationale), consistency High@100 (verifiable deviation), broad/design/prior Medium (narrow blast radius for the clipboard use). Kept High.

### #9 🟠 High: `fileNameWToFile` throws `RangeError` on an odd IPC buffer offset → Windows native paste silently returns nothing

| | |
|---|---|
| **File** | `src/vs/workbench/services/clipboard/electron-browser/clipboardService.ts:240` (`fileNameWToFile`) |
| **Category** | type-safety / runtime boundary / silent failure |
| **Confidence** | 100 |
| **Found by** | typescript-reviewer (High), quick-reviewer (Low) |
| **Validation** | confirmed — validator re-derived the wire format and reproduced odd offsets in 45/84 realistic (id, length) combinations, plus the live `RangeError` |

**Issue:** `new Uint16Array(buffer.buffer.buffer, buffer.buffer.byteOffset, ...)` requires `byteOffset` to be a multiple of 2. The buffer comes from `readClipboardBuffer` over the IPC ChannelServer/ChannelClient transport; `BufferReader.read()` returns a zero-copy `subarray` view whose offset is the cumulative length of a variable-length header (type/array tags + VQL-encoded response type and per-connection id + the body length prefix) — not guaranteed even. On an odd offset the constructor throws `RangeError`, which the surrounding `try/catch` swallows into `return []` → paste silently does nothing on Windows.

**Fix:** Copy the bytes into a fresh 0-offset buffer before viewing as `Uint16Array`, or decode with `new TextDecoder('utf-16le')` and trim at the first `\0`.
> Dissent noted: typescript High, quick Low. Kept High — the validator confirmed the offset can realistically be odd.

### #10 🟡 Medium: `hasResources()` and `readResources()` disagree on Linux → Explorer "Paste" appears enabled but silently does nothing

| | |
|---|---|
| **File** | `src/vs/workbench/services/clipboard/electron-browser/clipboardService.ts:133` (`hasResources`) vs `:206` (`uriListToFiles`) |
| **Category** | logic / silent failure |
| **Confidence** | 75 |
| **Found by** | quick-reviewer (Medium) |
| **Validation** | confirmed |

**Issue:** On Linux, `hasResources()` returns true from a content-agnostic `hasClipboard('text/uri-list')` (Electron's `clipboard.has()` — format presence only). But `readResources()` → `uriListToFiles()` filters entries to `uri.scheme === Schemas.file`. `text/uri-list` is a generic freedesktop format many apps populate with non-file URIs (e.g. a browser link). So `hasResources()` reports true — enabling the Explorer Paste affordance via `fileCopiedContextKey` (explorerView.ts) — while `readResources()` returns `[]`, and the paste handler skips with no error/notification.

**Fix:** On Linux, have `hasResources()` read and filter the buffer the same way `uriListToFiles` does (or share one implementation), rather than trusting raw format presence.

### #11 🟡 Medium: Main-handler routing has no liveness check or timeout and picks the first authority-match — hangs indefinitely if that window is closing / not yet connected

| | |
|---|---|
| **File** | `src/vs/platform/files/electron-main/remoteFileSystemProxyMainHandler.ts:65` (`findWindowForAuthority`) / `:75` (`getRendererChannel`) |
| **Category** | resilience / concurrency |
| **Confidence** | 75 |
| **Found by** | adversarial-reviewer (High), design-reviewer (Medium) |
| **Validation** | confirmed |

**Issue:** `findWindowForAuthority` returns the **first** window whose `remoteAuthority` matches, with no liveness check or preference for an active window. `getRendererChannel` then uses `electronIpcServer.getChannel(name, clientFilter)`; confirmed against `ipc.ts` (`IPCServer.getChannel`, lines 891-917): when no current connection matches the filter, it falls back to `Event.toPromise(Event.filter(onDidAddConnection, filter))` — an **unbounded wait** for a future matching connection, with no timeout. `call` doesn't accept or forward a `CancellationToken`. So if the matched window is closing (or hasn't connected yet), the proxied paste/read hangs with no failure or fallback, even when another same-authority window could serve.

**Fix:** Prefer a live window among matches, verify the target connection is present before forwarding, and bound routing with a timeout/cancellation that rejects (so the flow can degrade).

### #12 🟡 Medium: On download failure the catch pushes all original remote URIs — duplicate/mixed clipboard entries, and a silent native-paste regression

| | |
|---|---|
| **File** | `src/vs/workbench/contrib/files/browser/explorerService.ts:317`-`322` (catch block) |
| **Category** | correctness / silent failure |
| **Confidence** | 75 |
| **Found by** | spec-compliance (Low), adversarial / typescript / performance (noted) |
| **Validation** | confirmed |

**Issue:** The remote-download loop pushes each successful temp `target` into `result` **before** the `catch`. On a mid-loop failure (e.g. 3rd of 5 items), the catch does `result.push(...remoteResources)` — re-adding **all** original `vscode-remote://` URIs, so already-succeeded items appear twice (once as a temp `file://` target, once as the remote URI). This flows to `writeResources`, where any mix of `file://` + `vscode-remote://` makes `allLocal` false → only the VS-Code-internal `code/file-list` format is written; a native Finder/Explorer/Nautilus paste then gets no usable file data (the #2008 symptom), with the only signal a `logService.warn`.

**Fix:** On failure, don't mix already-added temp targets with a blanket re-push of remote URIs; surface a user-visible warning (or avoid writing native formats for unresolved remote URIs) instead of a phantom empty paste.

### #13 🟡 Medium: Remote-authority matched with strict `===` instead of the case-insensitive `isEqualAuthority()` used everywhere else

| | |
|---|---|

| **Found by** | broad-reviewer (Medium), adversarial-reviewer (Medium) |

**Issue:** `window.remoteAuthority === authority`. ### #16 🟡 Medium: Remote file contents materialized in plaintext in the local cache, and the temp path broadcast to the OS clipboard

| | |
|---|---|
| **File** | `src/vs/workbench/contrib/files/browser/explorerService.ts:302`-`315` (temp write under `cacheHome`) → `clipboardService.writeResources` |
| **Category** | security / data-at-rest / privacy |
| **Confidence** | 75 |
| **Found by** | security-reviewer (Medium) |
| **Validation** | not sent to wave (single-finder) — mechanism is directly verifiable from the code; independently corroborated by the prior review run (2026-07-28_12-56-15, #9) |

**Issue:** Copying a remote file writes its contents to `environmentService.cacheHome/remote-clipboard/<uuid>/<uuid>/<name>` in plaintext (readable by other same-user processes) and writes that local `file://` path into the OS-clipboard native formats — broadcasting both the potentially sensitive remote content location and the local path (username/cache layout; the privacy half of mjbvz's "leak the /tmp path" concern) to any app that reads the clipboard. ### Consistency

### Residual Risks

- `remoteFileSystemProxyClient.ts:119` — `watch()` returns `Disposable.None` with no comment on whether remote change-notifications are intentionally unsupported vs a TODO (broad-reviewer, Low).
- `clipboardService.ts` (writeResources) — Electron's `writeBuffer` writes one format without clearing others; a mixed/remote copy after an all-local copy may leave a **stale** native format, so a native paste could paste the previously-copied files. Suppressed at anchor 50 (depends on unverified Electron `writeBuffer` clearing semantics) — see probe (adversarial-reviewer, High@50).
- `clipboardService.ts:170`/`:187` — macOS `NSFilenamesPboardType` is written/parsed as an XML-plist **string** + `<string>` regex, but Finder typically delivers/expects a **binary** plist (`bplist00`); if so the macOS copy/paste bridge (the crux of #2008's native-paste expectation on macOS) may not work at all. Unverifiable statically; suppressed at anchor 50 — see probe (adversarial-reviewer Medium@50, spec-compliance@25).
- `clipboardService.ts:240` — `String.fromCharCode(...u16.subarray(...))` spreads an externally-sized array; a `FileNameW` payload lacking a null terminator makes the argument count unbounded → possible `RangeError` swallowed to an empty paste (typescript-reviewer, Low@50).
- `remoteFileSystemProxyServer.ts` / handler — the proxy protocol is stringly-typed across three files with no shared interface (a renamed method fails only at runtime), and the server exposes `exists`/`resolve` commands no client calls (dead surface) (design-reviewer, Medium@50).
- `remoteFileSystemProxyMainHandler.ts:44` / `remoteFileSystemProxyServer.ts:37` — `URI.revive(args[0] as UriComponents)` indexes an unvalidated `arg` cast from `any`; a call with a missing/malformed arg yields a raw `TypeError` instead of a clear error (typescript-reviewer, Medium@50).

### Threat Model Notes (security-reviewer)

- **New trust boundary**: a local (possibly untrusted) window can now read a connected remote host's filesystem via the main-process router (#7). Routing trusts the **payload authority**, not the caller; there is no per-resource scoping, no Workspace-Trust gate, and no audit trail on the serving side. "Read-only" guards constrain the wrong axis.
- **Data sensitivity**: remote file **contents** are written to the local cache in plaintext and the local path is broadcast to the OS clipboard (#16).
- **Attack-surface delta**: new IPC channels `remoteFileSystemProxyHandler` (main; reachable by every renderer) and `remoteFileSystemProxy` (per renderer; reachable only via the main handler), transitively exposing `stat/readdir/readFile/exists/resolve` for any open `vscode-remote` authority.
- **Not exposed to XXE**: `plistToFiles` uses a naive `<string>` regex, not a real XML parser, so no entity/DOCTYPE expansion (safer here than a full parser).

### Considered But Not Flagged (all agents)

- **Refuted under construction** (adversarial + typescript): UTF-16 surrogate-pair handling in `filePathToUtf16LE`/`fileNameWToFile` (correct — operates on code units); plist `&`/`<`/`>` escape round-trip (correct ordering); `text/uri-list` split vs newlines in filenames (`URI.toString()` percent-encodes control chars). Not defects.
- **Deliberate, not a defect**: `RemoteFileSystemProxyMainHandler`'s narrow `IRemoteFileSystemProxyWindowsService`/`IRemoteFileSystemProxyIPCServer` constructor interfaces (instead of concrete `IWindowsMainService`) — a testability choice praised by broad/design and the reason the router has the PR's only real unit coverage.
- **Correctly addresses prior (bot) feedback — verified fixed**: per-item `generateUuid()` temp subfolders (basename collisions), `uriListToFiles` filtering to `file://`, and the main-handler `vscode-remote` scheme check. (The PathCaseSensitive bot thread was marked resolved but the code is **unchanged** → primary #8.)
- **Suppressed by the confidence gate (anchor 50)** and moved to Residual Risks with probes: stale-native-format-not-cleared, macOS binary-plist, `fromCharCode` spread limit, stringly-typed protocol, unguarded `URI.revive`.
