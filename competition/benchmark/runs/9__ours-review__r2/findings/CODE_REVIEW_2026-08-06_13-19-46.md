### #1 🟠 High: `NodeConfig` registers no `AddFunc`, so the initial node event is silently dropped

| | |
|---|---|
| **File** | `pkg/proxy/config/config.go:290` (with `pkg/proxy/node.go:76-79`, `cmd/kube-proxy/app/server.go:211,608-609`) |
| **Category** | data-loss / async |
| **Confidence** | 100 (validated: confirmed) |
| **Found by** | quick-reviewer (High), broad-reviewer (High), go-reviewer (High), adversarial-reviewer (Medium) |

**Issue:** `NewNodeConfig` wires a `cache.ResourceEventHandlerFuncs` with only `UpdateFunc` and `DeleteFunc` — no `AddFunc`. `NodeManager` starts its informer and calls `cache.WaitForNamedCacheSync` **inside `NewNodeManager`** (node.go:76-79), which runs in `newProxyServer` — well before `Run()` builds `NodeConfig` and calls `RegisterEventHandler(s.NodeManager)` (server.go:608-609). When a handler is added to an already-synced informer, client-go replays the current store contents as synthetic `Add` notifications to that handler; with `AddFunc` nil, `ResourceEventHandlerFuncs.OnAdd` is a verified no-op (vendored `client-go/tools/cache/controller.go`), so the replay is dropped. Every sibling config in the same file (`ServiceConfig`, `EndpointSliceConfig`, `ServiceCIDRConfig`, and the new `NodeTopologyConfig`) wires `AddFunc`; `NodeConfig` is the lone outlier, and `handleChangeNode` still carries tombstone-unwrapping logic consistent with an accidental omission.

**Consequence:** a NodeIP/PodCIDR change occurring in the window between the initial poll in `NewNodeManager` and handler registration in `Run()` (client construction, proxier setup, iptables/ipvs programming all happen in between) is not delivered to `OnNodeChange` at that time. It is only caught later, when kubelet's periodic Node status heartbeat produces an `Update` — during which the proxier can run on stale NodeIP/local-detect assumptions. Downgraded from Critical because the miss is not permanent (a later Update re-triggers the comparison against the still-stale `n.node`).

**Fix:** Register the `NodeConfig` handler before the informer is started (as the removed code did — its dropped comment even stated *"This has to start after the calls to NewNodeConfig because that must configure the shared informer event handler first"*), or add an explicit `AddFunc` that also calls `handleChangeNode`/`OnNodeChange` so the post-registration replay is honored.

### #2 🟠 High: Data race on `NodeTopologyConfig.eventHandlers`; initial topology label may reach zero handlers

| | |
|---|---|
| **File** | `pkg/proxy/config/config.go` (`NodeTopologyConfig` register/dispatch) + `cmd/kube-proxy/app/server.go:610-611` |
| **Category** | concurrency |
| **Confidence** | 100 (validated: confirmed) |
| **Found by** | design-reviewer (High) |

**Issue:** Same root cause as #1 — the informer is already `Start()`ed and synced when `Run()` registers handlers. Unlike `NodeConfig`, `NodeTopologyConfig` **does** wire an `AddFunc`, so client-go asynchronously replays the initial node as an `Add` on the informer's listener goroutine, which runs `handleNodeEvent` and ranges over `eventHandlers`. Meanwhile the main goroutine executes `RegisterEventHandler(s.Proxier)` on the very next line (server.go:611), which does a bare `append` to that same slice. `eventHandlers` is a plain unguarded `[]NodeTopologyHandler` (config.go — verified: `RegisterEventHandler` appends without a lock; the dispatch loop ranges without a lock), so this is an unsynchronized concurrent read+write — a data race that `go test -race` would flag, and undefined behavior in production.

Secondary effect: if the replayed `Add` is processed before the Proxier handler is appended, the initial topology labels are delivered to zero handlers, and the subsequent `reflect.DeepEqual` short-circuit then suppresses re-delivery — so the Proxier may never receive the node's initial zone label until it next changes.

**Fix:** Register all handlers before the informer is started (shared fix with #1), or guard `eventHandlers` with a mutex and emit the current topology snapshot to a handler on first registration.

### #3 🟠 High: `NodeEligible()` does a full-node `DeepCopy` under an exclusive lock on every `/healthz` request

| | |
|---|---|
| **File** | `pkg/proxy/healthcheck/proxy_health.go:177-190` (DeepCopy at `pkg/proxy/node.go:189`) |
| **Category** | performance / concurrency |
| **Confidence** | 100 (validated: confirmed) |
| **Found by** | performance-reviewer (High), broad-reviewer (Medium), quick-reviewer (Low), design-reviewer (Low) |

**Issue:** `NodeEligible()` takes `hs.lock.Lock()` — a full **exclusive** write lock — and calls `hs.nodeManager.Node()`, which performs a full `*v1.Node` `DeepCopy` (Status, Conditions, Addresses, Capacity/Allocatable maps, Annotations, Labels, Taints). `healthzHandler.ServeHTTP` calls this on **every `/healthz` request** (which external load balancers poll frequently). The body touches none of the state `hs.lock` actually protects (`lastUpdatedMap`, `oldestPendingQueuedMap`) — eligibility now lives entirely in the independently-locked `nodeManager`. Worse, `hs.lock` is the same lock the proxier's hot sync path takes via `Updated()`/`QueuedUpdate()` (called from every iptables/ipvs/nftables sync), so the per-request DeepCopy's hold time serializes health signaling against rule-sync on every kube-proxy in the cluster, for the life of the process.

**Note:** four independent reviewers flagged the unnecessary exclusive lock, and this item recurs across 6 of 7 prior review runs of this PR. The claim that the pre-PR path read a cached bool under `RLock` is plausible but **could not be git-verified** in this single-commit checkout; the current-code cost (exclusive lock + per-request DeepCopy on a shared hot-path lock) is confirmed and is sufficient on its own.

**Fix:** Drop the `hs.lock` acquisition from `NodeEligible()` (`nodeManager.Node()` is already internally synchronized), and avoid the full `DeepCopy` for a read-only eligibility check — inspect `DeletionTimestamp`/`Taints` directly under `NodeManager`'s own lock, or restore a cached-eligibility bool updated from the `OnNodeChange`/`OnNodeDelete` handlers.

### #4 🟡 Medium: Exit paths use `klog.Flush()` + `os.Exit` instead of `klog.FlushAndExit()`; undocumented test seam

| | |
|---|---|
| **File** | `pkg/proxy/node.go:154-155, 170-171, 178-179` (construction at :60) |
| **Category** | reliability / knowledge |
| **Confidence** | 75 (validated: confirmed at code level) |
| **Found by** | knowledge-reviewer (High/SHOULD), prior-feedback-reviewer (High) |

**Issue:** All three exit paths call `klog.Flush()` then `n.exitFunc(1)` (`os.Exit` in production, an injected stub in tests) rather than the previous idiom `klog.FlushAndExit()`. Two concerns:
- **Log robustness [Unverified consequence]:** `os.Exit` bypasses klog's overridable `OsExit`, and `klog.Flush()` lacks `FlushAndExit`'s bounded flush behavior — logs may be truncated on exit. An **unresolved PR review thread from nojnhuh** reports this PR "broke creating clusters" and suspects the prior `klog.FlushAndExit()` was more robust at ensuring logs are written on exit. The causal link cannot be confirmed from code and is labeled **[Unverified]** — it is an external report, not a verified defect.
- **Undocumented test seam:** the `Flush()`+injectable-`exitFunc` split exists so tests can substitute a non-exiting stub, but nothing records this. A maintainer "simplifying" it back to `klog.FlushAndExit(1)` would bypass the stub and kill the test binary. In tests the stub *returns*, so control falls through past the exit call (e.g. after the PodCIDR-change exit, execution continues into the NodeIP check) — non-obvious and undocumented.

**Fix:** Add a comment at the `exitFunc` field documenting that it is an injectable seam (`os.Exit` in prod, faked in tests), that it must follow an explicit `klog.Flush()` rather than `klog.FlushAndExit`, and that it may return in tests so subsequent code must not assume termination. Separately, investigate nojnhuh's report to confirm/deny the log-truncation regression.

| | |
|---|---|

| **Category** | error-handling / design |

### #6 🟡 Medium: `OnNodeDelete` unconditionally exits on any node delete — transient-delete crashloop risk

| | |
|---|---|
| **File** | `pkg/proxy/node.go:175-179` |
| **Category** | reliability |
| **Confidence** | 75 · **unvalidated** (validator verdict: uncertain) |
| **Found by** | adversarial-reviewer (Medium) |

**Issue:** `OnNodeDelete` unconditionally calls `exitFunc(1)` (→ `os.Exit(1)`) on any delete event for the watched node. A transient or erroneous node-object delete (autoscaler, cloud-controller-manager, an etcd hiccup, or `kubectl delete node` followed by re-registration) therefore terminates kube-proxy; a flapping node object drives CrashLoopBackOff, and `/healthz` becomes connection-refused rather than a graceful 503 that lets load balancers drain.

**Validation note:** the *current behavior* (unconditional exit) is confirmed. The stronger claim that this is a **regression** from pre-PR behavior (where the process stayed alive and reported the node ineligible/503) **could not be verified** — this checkout is a single squashed commit with no base history, and the referenced `NodeEligibleHandler.OnNodeDelete` symbol is not present to compare against. Treat the "worse than before" framing as **[Unverified]**; the operational concern about unconditional exit on transient deletes stands on the current code alone. This may well be an intentional design choice.

**Fix:** Consider debouncing/confirming the delete (re-`Get` via the lister) before exiting, so a transient delete-then-recreate does not terminate the daemon; or document that hard exit on delete is intended and why.

### #7 🟡 Medium: `PodCIDRs()` returns an aliased mutable slice, inconsistent with `Node()`/`NodeIPs()`

| | |
|---|---|
| **File** | `pkg/proxy/node.go:128-131` |
| **Category** | api-contract / concurrency |
| **Confidence** | 75 (corroborated ×3 — validation waived) |
| **Found by** | design-reviewer (Low), go-reviewer (Medium), prior-feedback-reviewer (Medium) |

**Issue:** The accessor family is inconsistent about ownership of returned data. `Node()` returns a `DeepCopy`; `NodeIPs()` returns a freshly-allocated slice; but `PodCIDRs()` returns `n.node.Spec.PodCIDRs` directly — an alias into the shared, informer-owned node object, released from the lock on return. The mutex guards only the pointer read, not the returned data, giving a false impression of a defensive copy; a caller that mutates the returned slice would corrupt the shared cache object. It is safe today only because the sole caller (server.go:218) assigns without mutating and `OnNodeChange` replaces `n.node` wholesale rather than mutating in place — but the contract makes no such promise. This maps to the **unresolved danwinship thread** requesting a *"You must not modify it"* doc contract, which was applied to `Node()` but not here.

**Fix:** Return a defensive copy (`append([]string(nil), n.node.Spec.PodCIDRs...)`) for symmetry with `Node()`, or document the aliasing/ownership contract on all three accessors.

### #8 🟡 Medium: Node informer started with `wait.NeverStop`, not tied to the passed `ctx`

| | |
|---|---|
| **File** | `pkg/proxy/node.go:76` |
| **Category** | async / goroutine-leak |
| **Confidence** | 75 (validated: confirmed) |
| **Found by** | go-reviewer (Medium) |

**Issue:** `newNodeManager` accepts a `ctx context.Context` (used for cache-sync and the poll timeout) but starts its dedicated informer factory with `thisNodeInformerFactory.Start(wait.NeverStop)` instead of `ctx.Done()`, so the informer's reflector/processor goroutines are tied only to process exit, not to the caller's context. Harmless for the single-shot kube-proxy daemon, but it violates the idiomatic expectation that a `ctx`-accepting constructor's background goroutines are cancelable via that `ctx`, and it is concretely exercised by this PR's own tests: `healthcheck_test.go` calls `proxy.NewNodeManager(...)` in `TestHealthzServer`/`TestLivezServer`, each leaking a permanently-running informer for the remainder of the test binary. This recurs across 6 of 7 prior review runs of this PR.

**Fix:** `thisNodeInformerFactory.Start(ctx.Done())` so context cancellation stops the informer goroutines.

### #9 🟡 Medium: Crash-on-change rationale is undocumented (why crash rather than reconcile)

| | |
|---|---|
| **File** | `pkg/proxy/node.go:41-43` (type doc), `148-172` |
| **Category** | knowledge-preservation |
| **Confidence** | 75 (validated: confirmed) |
| **Found by** | knowledge-reviewer (SHOULD), broad-reviewer (High) |

**Issue:** The `NodeManager` doc comment states *what* happens ("crashes kube-proxy if there are any changes in NodeIPs or PodCIDRs") but never *why* exiting is chosen over reconciling in place. The load-bearing constraint — that NodeIPs/PodCIDRs are consumed once at startup and baked into proxier configuration with no safe runtime-reconfiguration path — lives only in the author's head and the PR discussion. A future maintainer could "fix" the unconditional `exitFunc(1)` into a graceful in-place update, silently reintroducing the stale-configuration class of bug the restart avoids. Extending crash-on-change to NodeIP drift (previously only PodCIDR drift) is new here and has no rationale recorded at all.

**Correction from validation:** broad-reviewer proposed restoring the dropped `// https://issues.k8s.io/111321` link. Validation established (corroborated by a **resolved** danwinship thread) that the link removal was **intentional** — the reviewer asked *"Don't link to an issue … just explain what it's doing and why."* So the fix is **not** to restore the link but to add the missing *why*.

**Fix:** Add one sentence to the `NodeManager` doc explaining that NodeIPs/PodCIDRs are consumed once at startup and cannot be safely reconfigured at runtime, so a restart is the required response to a change.

### #10 🟡 Medium: Healthcheck tests wire the real `os.Exit` via `NewNodeManager` (fragile hidden invariant)

| | |
|---|---|
| **File** | `pkg/proxy/healthcheck/healthcheck_test.go:481, 561` (also ~887, 935) |
| **Category** | testing |
| **Confidence** | 75 (corroborated ×2 — validation waived) |
| **Found by** | broad-reviewer (Medium), test-reviewer (Medium) |

**Issue:** `TestHealthzServer`/`TestLivezServer` build the manager via the exported `proxy.NewNodeManager(...)`, which hardwires `exitFunc = os.Exit`. The tests then call `nodeManager.OnNodeChange(makeNode(...))` several times; they only avoid killing the test binary because every `makeNode()` in this file produces the same hardcoded IP, so the NodeIP-drift check never trips. Nothing documents this required invariant. A future edit to `makeNode`/its tweaks that varies the IP — a very plausible change — would call `os.Exit(1)` mid-test, terminating the whole `go test` binary with no assertion message, and skipping the remaining tests in the binary. `node_test.go` already established the right pattern (unexported `newNodeManager` with an injected no-op `exitFunc`); the healthcheck package (a different package) has no access to it.

**Fix:** Expose a test-only constructor from `pkg/proxy` that lets `healthcheck_test.go` inject a recording/no-op `exitFunc`, or at minimum comment that node IPs must stay constant across `makeNode()` calls in this file because the real `os.Exit` is wired in.

### #11 🟢 Low: `if pollErr != nil { return nil, err }` returns the wrong error and is fragile

| | |
|---|---|
| **File** | `pkg/proxy/node.go:108` |
| **Category** | error-handling |
| **Confidence** | 75 (corroborated ×2) |
| **Found by** | go-reviewer (Low), prior-feedback-reviewer (Low) |

**Issue:** On poll timeout the constructor returns the closure-captured `err` rather than `pollErr`. This is correct **only** because `wait.PollUntilContextCancel` is called with `immediate=true` (the condition runs at least once) and every `return false, nil` inside the closure is preceded by an assignment to the outer `err`. That invariant is implicit and compiler-unenforced: a future edit adding an early `return false, nil` without setting `err` would make `NewNodeManager` return `(nil, nil)` on timeout, and callers only check `err != nil` before dereferencing `s.NodeManager` — a nil-pointer panic on the first `NodeIPs()`/`PodCIDRs()`. Matches the **unresolved danwinship thread** calling this pattern "weird."

**Fix:** Return the actual poll error with the last observed condition error wrapped for context, e.g. `return nil, fmt.Errorf("timed out waiting for node %q: %w (last error: %v)", nodeName, pollErr, err)`.
