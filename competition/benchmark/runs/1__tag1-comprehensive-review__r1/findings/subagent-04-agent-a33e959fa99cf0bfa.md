### Findings

#### Medium

- **[data confusion / cache-key collision]** The rowid-ordinal cache key is built by string concatenation with an ambiguous `_` separator: `string rowidkey = $"{blobDatabaseName}_{blobTableName}"` — `src/Microsoft.Data.Sqlite.Core/SqliteDataRecord.cs:328`. SQLite database names (via `ATTACH`) and table names may themselves contain `_`, so distinct (database, table) pairs collide: db `a_b` + table `c` and db `a` + table `b_c` both produce key `a_b_c`. On a collision, `RowIds.TryGetValue` (line 329) returns the other table's cached `RowIdInfo`, and line 402 (`var rowid = GetInt64(rowIdForOrdinal.Ordinal);`) reads a rowid value from the wrong table's column, then opens `SqliteBlob(_connection, blobDatabaseName, blobTableName, blobColumnName, rowid)` positioned at that foreign rowid — silently returning a different row's blob (or throwing if the rowid doesn't exist). Honest impact framing: this is a client library where the app author controls SQL and attach names, so this is not directly attacker-triggerable in most deployments; the harm is silent wrong-row data returned to the application, which becomes a disclosure issue when blob rows are per-user data served downstream.
  - **Remediation**: Key the dictionary on the pair, not a concatenated string — e.g., `Dictionary<(string Database, string Table), RowIdInfo>` with key `(blobDatabaseName, blobTableName)`. Rejected alternative: escaping/length-prefixing the names inside the string key — works but hand-rolls what a value-tuple key provides, and any separator choice remains fragile since SQLite identifiers may contain arbitrary characters.
  - **Confidence**: 85/100 (collision is deterministic from the code as written; triggering requires colliding schema names plus blob reads on both tables in one statement)

- **[data confusion / self-join alias conflation]** The cache (and the underlying scan) cannot distinguish two aliases of the same table. `sqlite3_column_table_name` returns the origin table name, not the SQL alias, so in `SELECT p.ID, p.VALUE, c.ID, c.VALUE FROM T p JOIN T c ON ...` both blob columns map to the same key `main_T` — `src/Microsoft.Data.Sqlite.Core/SqliteDataRecord.cs:328-357`. The first `GetStream` caches alias `p`'s pk ordinal (line 355/387); a subsequent `GetStream` on alias `c`'s blob hits the cache and calls `GetInt64` on `p`'s ordinal (line 402), opening the blob at `p`'s rowid — the caller receives the wrong row's blob content for alias `c`, silently. Note the scan loop itself (`break` at first (db,table) match, lines 332-357) has the same first-alias bias even without the cache, and the pre-change single `_rowidOrdinal` was worse — but this diff rewrites exactly this logic with the stated purpose of making blob streaming correct for joins, and the self-join case still yields wrong data. The PR's new test (`GetBytes_works_streaming_join`) covers only the two-distinct-tables case.
  - **Impact**: Cross-row blob disclosure within the app's own query — wrong row's data handed to application logic (e.g., wrong user's document streamed) with no error signal.
  - **Remediation**: Counter-argument first: the fallback below sacrifices true incremental streaming for self-joins, a real cost for large blobs — but silent wrong data is strictly worse than slower correct data. Recommendation: detect ambiguity — if more than one rowid-candidate ordinal maps to the same (database, table) in the result set, do not cache or use a rowid; fall back to the existing `GetCachedBlob` `MemoryStream` path (line 398), which reads the correct column value for the requested ordinal. Rejected alternative: heuristically correlating the blob ordinal with the "nearest" rowid ordinal (assuming alias columns are contiguous in the SELECT list) — rejected because SELECT-list order is arbitrary and the heuristic fails silently, reproducing the same class of bug.
  - **Confidence**: 82/100 (reasoned from the visible code plus documented SQLite semantics that `sqlite3_column_table_name` returns the real table name for aliases; not executed)

The unqualified `pragma_table_info($table)` query at `SqliteDataRecord.cs:377-378` (unchanged in this diff, but feeding the new caching logic) resolves the table name against the schema search order (`main` first, then attach order), not against `databaseName`. [Inference from documented SQLite name-resolution behavior.] If an attached database's table shares a name with a differently-keyed table in `main`, `pkColumns` is computed against the wrong table, which can misclassify a composite-PK column as a rowid alias and open the blob at a non-rowid value. Fix would be qualifying the pragma with the schema (e.g., `pragma_table_info` has a two-argument form, or `"SELECT COUNT(*) FROM {schema}.pragma_table_info($table)..."` needs schema-identifier quoting since it cannot be parameterized).
