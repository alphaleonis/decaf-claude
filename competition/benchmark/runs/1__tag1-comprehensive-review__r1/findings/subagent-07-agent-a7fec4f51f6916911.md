# subagent agent-a7fec4f51f6916911

## Architectural Analysis

### Design Assessment

The change correctly identifies that the old single-`_rowidOrdinal` cache could not serve multi-table joins, and the per-(database, table) dictionary is the right shape of generalization with the right lifetime (per `SqliteDataRecord`, i.e. per result set, where the column→table mapping is fixed for the statement's life, so no invalidation is needed). However, the generalization is incomplete: it silently drops the old design's negative-result caching, converts a previously-vacuous `Debug.Assert` into one that is false on common supported paths, and encodes the cache key as a `_`-joined string that can collide. The new `RowIdInfo` class carries dead data and could be an `int`.

### Findings

#### High

- **[Scalability / Design Patterns]** Negative-result caching was removed; every no-rowid lookup now re-runs the full metadata scan — `src/Microsoft.Data.Sqlite.Core/SqliteDataRecord.cs:329-394`
  - Why it matters: The old design cached the sentinel `-1` in `_rowidOrdinal`, so "searched, not found" was remembered for the record's lifetime. The new code only calls `RowIds.Add(...)` on success, so when no rowid is locatable (expression columns, single-column selects, composite/non-INTEGER PKs, WITHOUT ROWID tables) **every** `GetStream` call re-runs the O(FieldCount) interop scan, up to one `sqlite3_table_column_metadata` call per candidate column, plus a `SELECT COUNT(*) FROM pragma_table_info(...)` command execution (line 375-381). `GetBytes` and `GetChars` call `GetStream` on every invocation (`SqliteDataRecord.cs:276,290`), and chunked `GetBytes` reads are the standard streaming pattern — so this is a per-chunk SQL round-trip regression. Existing tests `GetBytes_works` (`SELECT Value FROM Test`, called once per row) and `GetStream_works` (`SELECT x'427E5743'`, called twice) already exercise this exact path.
  - Recommendation: Cache negative results too — e.g., store `int?` (or a nullable entry) in the dictionary with null/sentinel meaning "searched, not found," mirroring the old sentinel semantics per key. This is safe because a statement's column metadata cannot change within the record's lifetime, so a negative can never become positive. Rejected alternative: keep the re-scan on the grounds that the fallback path caches the blob bytes anyway (`GetCachedBlob`) — rejected because the metadata scan and the `pragma_table_info` sub-query still execute per call, which is avoidable pure overhead. Strongest counter-argument: the hot success path is unaffected and the regression only hits the fallback; that reduces urgency, not validity.
  - Confidence: 90/100

#### Medium

- **[Maintainability]** `Debug.Assert(rowIdForOrdinal != null)` asserts a condition that is false on supported, immediately-handled paths — `src/Microsoft.Data.Sqlite.Core/SqliteDataRecord.cs:393`
  - The old `Debug.Assert(_rowidOrdinal.HasValue)` was vacuously true (the sentinel was assigned unconditionally before the loop); the rewrite changed its semantics to "a rowid is always found," which is false for expression columns (`GetStream_works`: `SELECT x'427E5743'`), single-column selects (`GetBytes_works`: `SELECT Value FROM Test`), and composite-PK tables — and directly contradicts the `if (rowIdForOrdinal == null)` fallback three lines below (396-398). In debug builds of the library, existing tests hit the failing assertion. [Inference] Exact runtime consequence (FailFast vs. logged message) depends on trace-listener configuration; I did not build to verify — but an assert whose condition is expected-false in supported scenarios is wrong regardless.
  - Recommendation: Delete the assert (the null case is a designed fallback, not an invariant violation). Alternative considered: keep it and gate on `blobTableName != null` — rejected, since the search also legitimately fails for real tables (composite PK, rowid not selected).
  - Confidence: 92/100

- **[Coupling / key design]** String-concatenation cache key `$"{blobDatabaseName}_{blobTableName}"` is collision-prone and allocates per call — `src/Microsoft.Data.Sqlite.Core/SqliteDataRecord.cs:328`
  - `_` is legal in SQLite database (via `ATTACH`) and table names, so `("a_b", "c")` and `("a", "b_c")` produce the same key; on collision the cached rowid ordinal of one table is used for another, `GetInt64` reads the wrong column as a rowid, and `SqliteBlob` silently returns the wrong row's data — a data-correctness harm. The interpolated key also allocates a string on every `GetStream`/`GetBytes` call. Occurrence likelihood is low (requires attached databases with colliding names), hence Medium.
  - Recommendation: Key the dictionary on a value tuple `(string?, string?)` — collision-free, allocation-free, and handles null table names (expression columns) cleanly. Rejected alternative: escaping the separator — more code, still allocates, still ad-hoc.
  - Confidence: 85/100

- **[Design generalization — self-joins]** The cache bakes in "one rowid per (database, table) per statement," which is wrong for self-joins — `src/Microsoft.Data.Sqlite.Core/SqliteDataRecord.cs:332-357`
  - [Inference, from the SQLite C API contract] `sqlite3_column_table_name` reports the base table name for both aliases in `t AS a1 JOIN t AS a2`, so the scan cannot distinguish aliases: a blob column from `a2` resolves to whichever alias's rowid column scans first, and `SqliteBlob` reads the wrong row's blob. This limitation pre-exists (the old single-ordinal design had it too), but the new keyed dictionary structurally encodes the one-rowid-per-table assumption without documenting it, making it look intentional to future maintainers.
  - Recommendation: Document the assumption at the dictionary declaration; optionally detect two rowid candidates for the same (db, table) in the select list and fall back to `GetCachedBlob` for that table. Alternative considered: resolving by alias — rejected, the SQLite column-metadata API does not expose aliases, so it is not implementable at this layer.
  - Confidence: 78/100

- **[Over-engineering / conventions]** `RowIdInfo` is a single-use mutable class carrying dead data — `src/Microsoft.Data.Sqlite.Core/SqliteDataRecord.cs:17-27,39`
  - `TableName` is assigned in both construction sites (354, 386) and read nowhere; only `.Ordinal` is consumed (402). The old design stored a bare `int?`; the generalization needs only `Dictionary<key, int>` (or `int?` per the negative-caching fix) — the class, its settable properties, and its per-lookup allocation add nothing. The field declaration `readonly Dictionary<string, RowIdInfo> RowIds` also breaks the file's uniform `private ... _camelCase` field convention (every sibling field follows it), which the conventions lens flags even though broader style is code-reviewer scope.
  - Recommendation: Replace `RowIdInfo` with the value type in the dictionary (`Dictionary<(string?, string?), int?>` combines this with the two findings above) and rename the field `_rowIdOrdinals` with `private`. Alternative considered: keeping the class but making it a readonly record struct — rejected, it still carries a never-read field.
  - Confidence: 92/100

### Positive Observations

- Cache lifetime is correctly scoped: the dictionary lives on `SqliteDataRecord`, which `SqliteDataReader.NextResult()` recreates per result set, and a statement's column→table mapping is fixed for that lifetime — so no invalidation logic is needed and none was added. Right call.
- The fix is minimal and targeted: the existing per-column database/table filtering in the scan loop (lines 339-349) is reused unchanged; only the cache granularity changed. No public API surface changed; `GetStream`/`GetBytes` behavioral contract is extended (joins now stream) without breaking existing behavior on the success paths.
- A regression test for the multi-table join scenario was added (`GetBytes_works_streaming_join`).

### Recommendations

1. Restore negative-result caching (High) — fold into a single change: `Dictionary<(string? db, string? table), int?>` where null value = "searched, not found." This simultaneously fixes the key-collision risk, removes the `RowIdInfo` class and its dead `TableName`, and restores the old design's negative caching.
2. Remove the now-incorrect `Debug.Assert` at line 393.
3. Add a comment documenting the self-join limitation (one rowid per (db, table) per statement) at the dictionary declaration.
