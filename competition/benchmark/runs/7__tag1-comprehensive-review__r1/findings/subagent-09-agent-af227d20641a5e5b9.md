## Critical (confidence 90)

**Use-after-close race: `getChunkSeriesSet` releases the block reader's "pending reader" hold before `StreamChunkedReadResponses` finishes lazily reading chunk bytes from it, defeating the exact mechanism Prometheus TSDB uses to keep compaction/retention from deleting a block while it's being read.**

- `storage/remote/read_handler.go:247-251,265` — `defer func() { querier.Close() ... }()` is declared inside `getChunkSeriesSet`, so it fires when `return querier.Select(ctx, true, hints, filteredMatchers...)` at line 265 completes — i.e. before `getChunkSeriesSet` even returns to its caller.
- `storage/remote/read_handler.go:205-214` — the caller does `chunks := h.getChunkSeriesSet(...)` (querier already closed at this point) and only afterward passes `chunks` into `StreamChunkedReadResponses(...)`.
- `storage/remote/codec.go:235-266` — `StreamChunkedReadResponses` consumes `ss` lazily: `for ss.Next() { series := ss.At(); iter = series.Iterator(iter); ... chk := iter.At(); ... Data: chk.Chunk.Bytes() ... }`. This is where chunk bytes are actually pulled from the underlying block reader, and it happens entirely after the querier from `getChunkSeriesSet` was closed.
- `tsdb/querier.go:174-196` (`blockChunkQuerier.Select`) returns `NewBlockChunkSeriesSet(q.blockID, q.index, q.chunks, q.tombstones, ...)`, and `tsdb/querier.go:1158-1180` shows `blockChunkSeriesSet.At()` returns a `chunkSeriesEntry{chunks: b.chunks, ...}` holding a direct reference to the block's `ChunkReader` — confirming the returned series set reads from the reader on demand rather than eagerly copying data at `Select()` time. `tsdb/querier.go:877-914` (`populateWithDelChunkSeriesIterator.Next`) confirms the pull: each `Next()` call invokes `p.cr.ChunkOrIterable(p.currMeta)` against that same reader.
- `tsdb/block.go:436-441` (`Block.Chunks()`) — `pb.startRead()` (`pb.pendingReaders.Add(1)`, line 419-424) then returns `blockChunkReader{ChunkReader: pb.chunkr, b: pb}`, i.e. all readers of a block share the *same* mmap'd `chunks.Reader`.
- `tsdb/block.go:567-569` (`blockChunkReader.Close()`) does `r.b.pendingReaders.Done()` — it does not close anything itself; it only decrements the block's outstanding-reader count.
- `tsdb/block.go:377-389` (`Block.Close`) — doc comment: *"Close closes the on-disk block. It blocks as long as there are readers reading from the block."* It calls `pb.pendingReaders.Wait()` before actually closing (unmapping) `pb.chunkr`/`pb.indexr`. `Block.Close()` is invoked from compaction/retention paths (`tsdb/db.go:1472,1662`, inside `reloadBlocks`), which run periodically/concurrently with query serving and can delete a block once its `pendingReaders` count drains to zero.
- `tsdb/db.go:2022-2024` — explicit comment on this exact contract: *"Getting the querier above registers itself in the queue that the truncation waits on. So if the querier is currently not colliding with any truncation, we can continue to use it and still won't run into a race later since any truncation that comes after will wait on this querier if it overlaps."*

Putting these together: by calling `querier.Close()` inside `getChunkSeriesSet` before the returned `ChunkSeriesSet` is consumed, this PR decrements `pendingReaders` for the underlying block(s) as soon as `getChunkSeriesSet` returns — while `StreamChunkedReadResponses` (which may run for a while, especially while streaming to a slow HTTP client, which is the OOM scenario the PR is trying to mitigate) is still lazily pulling chunk bytes from that same, now-"released" block reader. If a compaction/retention cycle runs concurrently and decides that block is eligible for deletion, `Block.Close()`'s `pendingReaders.Wait()` will return immediately (since this reader already called `Done()`), and the block's mmap'd files can be unmapped/deleted while `StreamChunkedReadResponses` is still reading from them — a use-after-free that can crash the process (SIGSEGV/SIGBUS on the unmapped region) or, if the address space is reused, return corrupted data.

Contrast with the pre-refactor code (left side of the diff): `defer querier.Close()` there was scoped to the per-query IIFE that itself contained the `StreamChunkedReadResponses(...)` call, so `Close()` only ran after that query's full streaming completed — the pre-refactor code respected the `pendingReaders` contract; this diff breaks it.

**Fix recommendation:** Don't close the querier until the returned series set has actually been fully consumed. Concretely, either (a) go back to deferring `querier.Close()` around the full `StreamChunkedReadResponses` call (i.e. keep the querier's lifetime matching the series set's lifetime, as before), or (b) if the goal is genuinely to free the block/head reader before the (potentially slow) HTTP write phase, fully drain `querier.Select(...)` into an in-memory representation (labels + already-extracted chunk bytes) *inside* `getChunkSeriesSet`, close the querier only after that drain completes, and hand `StreamChunkedReadResponses` the now self-contained, already-materialized data instead of a lazy `ChunkSeriesSet` backed by the closed reader.

**Rejected alternative:** keeping the current lazy `ChunkSeriesSet` but closing the querier via `sync.Once` triggered from within `StreamChunkedReadResponses` after its loop finishes — rejected because it still requires threading a close-callback across a public API boundary in `codec.go` shared by other callers, and doesn't fix the fact that other code paths reusing `getChunkSeriesSet`'s pattern would have the same trap; the materialize-before-close approach in (b) is more directly aligned with the PR's own stated goal (release querier resources before/independent of the slow write) without violating the `pendingReaders` contract.

**Counter-argument worth surfacing:** this is a genuine data race that requires two things to overlap in time — a chunked remote-read request slow/large enough that streaming outlives the moment compaction/retention decides to delete the specific block(s) it's reading. In practice this window can be narrow, which is presumably why it passed review upstream. But given First-Law priority on data-loss/crash risk in a production monitoring system, and that the PR's own motivation ("avoid OOMs when [remote-read requests are] broken," implying slow/large responses are the target scenario) directly increases the likelihood of that overlap, this should not be dismissed as theoretical.
