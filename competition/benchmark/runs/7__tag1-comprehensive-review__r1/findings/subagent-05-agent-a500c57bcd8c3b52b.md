## Adversarial Review

### Summary
This 1-file change moves the `ChunkQuerier.Close()` from "after streaming" to "before streaming" by wrapping the querier acquisition + `Select()` in `getChunkSeriesSet`, whose `defer querier.Close()` fires when it *returns* — i.e. before `StreamChunkedReadResponses` lazily iterates the returned `ChunkSeriesSet`. The code I read confirms this closes the exact read-lifetime protection that both the head (`WaitForPendingReadersInTimeRange` via the querier's `isoState`) and persistent blocks (`Block.Close` → `pendingReaders.Wait`) rely on to keep mmap-backed chunk bytes alive while they are still being read. The change trades a recoverable OOM for an unrecoverable use-after-free, and it is precisely the slow/broken client the PR cites that widens the crash window.

### Findings

#### Critical

- **[edge-case]** Querier is closed before the returned `ChunkSeriesSet` streams mmap-backed chunk bytes — use-after-free / SIGBUS — `storage/remote/read_handler.go:247` (defer Close) vs `:205-218` (lazy stream)
  - **What's wrong/missing:** `getChunkSeriesSet` returns the `ChunkSeriesSet` and its `defer querier.Close()` runs immediately (read_handler.go:247-251). `StreamChunkedReadResponses` then reads `chk.Chunk.Bytes()` *lazily during iteration* (codec.go:221; SYMBOL_CONTEXT), after Close. For persistent blocks with no tombstones, the chunk is used verbatim with no copy (`querier.go:730-735`; only the head's *active* in-memory chunk is copied via `ChunkWithCopy`, `querier.go:714-717` / `head_read.go:371-382`), so `Bytes()` points straight into the mmap'd segment file. Closing the querier releases the two mechanisms that keep that mmap alive:
    - Persistent blocks: `blockChunkReader.Close()` → `pb.pendingReaders.Done()` (block.go:567-569). `Block.Close()` does `pendingReaders.Wait()` *then* `pb.chunkr.Close()` which munmaps (block.go:378-390). Post-compaction block deletion can now munmap while streaming continues.
    - Head: `headChunkReader.Close()` → `h.isoState.Close()` (head_read.go:318-323). Head truncation calls `WaitForPendingReadersInTimeRange` which sleeps until no overlapping open read remains (head.go:1117, 1141-1158), then `truncateSeriesAndChunkDiskMapper` munmaps old head chunk files. Closing the querier removes the open read so truncation no longer waits. The db.go comment at 2022-2024 states this registration exists specifically to "not run into a race later" — this PR reintroduces that race.
  - **Why it matters:** Reading a munmap'd region is a fatal `SIGBUS` that Go's `recover()` cannot catch — the entire Prometheus process dies, taking down scraping, rule evaluation, and every concurrent request. The less-lucky outcome is no crash but silently corrupted bytes in the streamed response (the address space is reused). The merge/fanout path (`db.ChunkQuerier` → `storage.NewMergeChunkQuerier`, db.go:2067-2072) means every block and the head touched by the query are exposed, not just one. This fires only when streaming overlaps a routine truncation/compaction of the specific data being read — a race, so not every request — but compaction (~2h default) and head truncation are routine, and a slow client (the PR's own scenario) maximizes the overlap window.
  - **Fix:** Do not close the querier before the `ChunkSeriesSet` is fully consumed. Either revert to keeping the querier open for the streaming duration, or make early-close safe by materializing/deep-copying chunk bytes out of mmap before Close (the head already does this for its active chunk via `ChunkWithCopy`; it would have to be extended to mmap'd block/head chunks).
  - **Counter-argument (strongest, per GOVERNANCE):** If some higher layer serialized remote reads against compaction/truncation, or if `Select()` eagerly materialized chunks before returning, the window would not exist. I checked: `NewBlockChunkSeriesSet` is lazy (`querier.go:1154-1196`, chunks read in `populateWithDelChunkSeriesIterator` during `At()`), and truncation/deletion run on independent background goroutines gated *only* by the reader-registration this PR releases. The counter fails. Residual uncertainty is probability, not existence — hence 88, not 95.
  - **Rejected alternative:** "Copy chunk bytes before Close instead of reverting." Rejected as the primary rec because copying every mmap'd chunk out before streaming reintroduces exactly the memory pressure the PR is fighting and defeats the point of mmap; a straight revert (or gating close on a materialize step) is cleaner. Named here because it is the correct path if early-close is a hard requirement.
  - **Confidence:** 88/100

#### High

- **[test-gap]** No test exercises iteration-after-Close or the concurrent truncation/deletion race — `storage/remote/read_handler.go` (diff is 1 file, no test changed)
  - **What's wrong/missing:** The change alters a lifetime invariant with zero test coverage. There is no test that (a) reads the returned `ChunkSeriesSet` after the querier is closed, or (b) runs a chunked remote read concurrently with head truncation / block deletion. Existing remote-read tests almost certainly pass because they use small in-memory data with no concurrent compaction, so they never enter the unsafe window — passing tests here are false assurance.
  - **Why it matters:** A regression test that closed a chunk querier, triggered `head.Truncate` / block deletion, then iterated the set would surface the crash deterministically and prevent a re-introduction. Its absence means CI is blind to the exact failure the change creates.
  - **Fix:** Add a TSDB-level test that opens a chunk querier over head + a block, obtains the `ChunkSeriesSet`, closes the querier, forces truncation/deletion, then iterates — asserting it does not read freed memory (or asserting the querier stays open).
  - **Rejected alternative:** A unit test at the `read_handler` layer with a mock queryable — rejected because a mock won't reproduce mmap munmap; the test must run against real TSDB internals to be meaningful.
  - **Confidence:** 85/100

- **[docs]** `getChunkSeriesSet` docstring frames early-close as pure benefit and omits the load-bearing lifetime invariant it actually violates — `storage/remote/read_handler.go:239-241`
  - **What's wrong/missing:** The comment says the function encapsulates the query "to ensure timely release of the querier resources" — selling only the upside. It says nothing about the critical, now-violated constraint that the returned `ChunkSeriesSet` must not be iterated after the querier is closed when chunks are mmap-backed. The next developer has no warning; the comment actively misleads them into thinking returning a set whose querier is already closed is a safe, intentional pattern.
  - **Why it matters:** This is the kind of undocumented, non-obvious lifetime coupling that produces exactly this class of bug. Even if the crash risk were somehow mitigated elsewhere, the comment as written invites the pattern to be copied.
  - **Fix:** If the pattern is kept, document the invariant explicitly and why it is (believed) safe, citing the specific copy/pin that keeps bytes alive. If it is not safe, the comment should not exist because the code should not exist.
  - **Rejected alternative:** Leave the comment as-is and rely on reviewers — rejected because the comment is worse than none; it asserts safety it does not establish.
  - **Confidence:** 82/100

#### Medium

- **[observability]** No graceful degradation or signal for the new failure mode; it replaces an observable OOM with an unobservable crash-or-corruption — `storage/remote/read_handler.go:205-218`
  - **What's wrong/missing:** The OOM this PR targets is observable and semi-recoverable (memory metrics, `OOMKilled`, request-level failure). The failure it introduces is either a fatal `SIGBUS` (no metric, no log, no `recover()`, whole process down) or silent byte corruption in the response (no signal at all). There is no counter, no defensive check, and no degradation path for the mmap-freed case.
  - **Why it matters:** Operationally, an operator debugging a crashing Prometheus will see a bare SIGBUS with no breadcrumb tying it to remote read + compaction timing. The silent-corruption variant is worse: a remote-read consumer ingests wrong samples with nothing flagging it.
  - **Fix:** Tie this to the Critical remediation (don't read freed memory). Independently, this failure mode is not one that can be safely "degraded" — the only correct handling is to not create it.
  - **Rejected alternative:** Wrap the stream loop in `recover()` — rejected because SIGBUS from munmap is not a Go panic and is not recoverable; it would do nothing.
  - **Confidence:** 78/100

### Most Critical Gap
The PR closes the `ChunkQuerier` before its `ChunkSeriesSet` is streamed, releasing the head's `WaitForPendingReadersInTimeRange` protection and the block's `pendingReaders` guard while chunk bytes are still read lazily from mmap — a use-after-free that can SIGBUS the whole server (or silently corrupt the response) whenever slow streaming overlaps routine compaction/truncation. Fix before merge: keep the querier open for the streaming lifetime, or deep-copy chunk bytes out of mmap before Close.

### Positive Observations
- The error path is handled correctly: `ChunkQuerier()` failure returns `storage.ErrChunkSeriesSet(err)` and the caller checks `chunks.Err()` before streaming (read_handler.go:205-208, 243-245) — consistent with the `ErrChunkSeriesSet` contract.
- The hints-construction and Select logic were moved verbatim, not rewritten, keeping the diff reviewable.
- The stated motivation (queriers pinning the head against truncation → head growth → OOM under broken chunked reads) is a real problem; the diagnosis is sound even though the chosen remedy is unsafe.
