## Findings

### #1 🟡 Medium: Dead branch in `getCompletionData`'s "Fix location" switch — self-closing JSX location fixup silently dropped

| | |
|---|---|
| **File** | `src/services/completions.ts:3511` |
| **Category** | logic-error / dead-code |
| **Confidence** | 100 (unreachability); severity settled to Medium by validator |
| **Found by** | quick-reviewer (High), broad-reviewer (High), knowledge-reviewer (High), consistency-reviewer (High), typescript-reviewer (Medium) |
| **Validation** | confirmed — unreachability proven against `parser.ts`/`scanner.ts`; no observable regression found in a full downstream trace |

**Issue:** The "Fix location" `switch (currentToken.kind)` had its case label mechanically renamed from `SyntaxKind.SlashToken` to `SyntaxKind.LessThanSlashToken`, but the body was left unchanged:

```ts
case SyntaxKind.LessThanSlashToken:
    if (currentToken.parent.kind === SyntaxKind.JsxSelfClosingElement) {
        location = currentToken;
    }
    break;
```

`LessThanSlashToken` (`</`) is produced only for a `JsxClosingElement`/`JsxClosingFragment` (`parser.ts` `parseJsxClosingElement`/`parseJsxClosingFragment`), never for a `JsxSelfClosingElement`; a self-closing element `<div />` contains a plain `SlashToken`. So the guard `currentToken.parent.kind === SyntaxKind.JsxSelfClosingElement` can never be true after the rename — the branch is **dead**, and the original behavior (narrowing `location` to the self-closing element's `/`) no longer fires.

This is the only over-applied site: the closing-tag `</` really did merge into a single `LessThanSlashToken` under the fixed scanner, so the *other three* `completions.ts` renames (`getJsxClosingTagCompletion` walk-up, the `JsxClosingElement` branch at ~3521, `isValidTrigger`'s `"/"` case) and both `utilities.ts` changes are correct. This case, however, concerns a *different physical token* (`/`, not `</`) that the scanner fix does not affect, so it should have stayed `SyntaxKind.SlashToken`.

**Severity — why Medium, not High:** the dead-branch fact is airtight, but a downstream trace found no demonstrated user-visible regression: self-closing attribute completions are driven independently through `tryGetContainingJsxElement` (completions.ts:4833-4834, untouched, still lists both `SlashToken` and `LessThanSlashToken`); the only `location.kind === JsxSelfClosingElement` consumer (`isInJsxText`) runs *before* this switch; and no code switches on `location.kind === SlashToken`. So this is real dead code and latent risk (if `location` ever gains a new consumer), worth fixing for correctness/hygiene, but not a functional regression today.

**Fix:** Revert this one case label; its body is already correct for the self-closing slash.
```ts
case SyntaxKind.SlashToken:
    if (currentToken.parent.kind === SyntaxKind.JsxSelfClosingElement) {
        location = currentToken;
    }
    break;
```

### #2 🟡 Medium: Incomplete fix — `languageVariant` derived only from `sourceFile?`, so JSX is still mis-scanned via the text-change formatting path

| | |
|---|---|
| **File** | `src/services/services.ts:507` |
| **Category** | data-model / correctness (incomplete fix) |
| **Confidence** | 75 (reachable path confirmed by validator) |
| **Found by** | design-reviewer (Medium), typescript-reviewer (Medium), quick-reviewer (Medium — via `textChanges.ts:1339`) |
| **Validation** | confirmed — concrete reachable internal path traced |

**Issue:** In `createChildren`, the scan **text** falls back to `node.getSourceFile()` when `sourceFile` is undefined, but the language **variant** is derived only from `sourceFile?.languageVariant`:

```ts
const languageVariant = sourceFile?.languageVariant ?? LanguageVariant.Standard;
scanner.setText((sourceFile || node.getSourceFile()).text);
scanner.setLanguageVariant(languageVariant);
```

Because `languageVariant` was added as an **optional** field on the loosely-typed `SourceFileLike`, any caller that passes a lightweight object with `text` but no `languageVariant` gets JSX/TSX scanned as `Standard` — the exact `</div>` mis-tokenization this PR set out to fix.

The validator traced a **concrete, currently-reachable internal path** (which the initial reviews were split on): `textChanges.ts:1339` `getFormattedTextOfNode` builds `{ text, getLineAndCharacterOfPosition }` with no `languageVariant` → `formatNodeGivenIndentation` → `formatSpanWorker`'s trailing-edit branch → `findPrecedingToken(..., file, ...)` (`utilities.ts:1744`) → `n.getChildren(file)` → `createChildren` with a `languageVariant`-less `SourceFileLike`. The correct variant (`targetSourceFile.languageVariant`) is threaded only to the primary `FormattingScanner`, never to this object — so JSX content inserted/formatted via `ChangeTracker` (codefixes/refactors) is still re-scanned in `Standard` variant.

This is **not a regression** (pre-PR, `createChildren` was always `Standard` for everyone), but it is a real gap in what the PR intended to fix. Visible end-user impact was not demonstrated, hence Medium rather than High.

**Fix:** Derive the variant from the same resolved source used for the text, with the node's real source file as the fallback:
```ts
const sf = sourceFile ?? node.getSourceFile();
scanner.setText(sf.text);
scanner.setLanguageVariant((sourceFile?.languageVariant ?? node.getSourceFile().languageVariant) ?? LanguageVariant.Standard);
```

### #3 🟢 Low: Shared scanner's language variant is not reset on the exception path (no `try/finally`), and the reset invariant is undocumented

| | |
|---|---|
| **File** | `src/services/services.ts:507-530` |
| **Category** | shared-state / reliability / knowledge-preservation |
| **Confidence** | 75 (defect real); impact narrow |
| **Found by** | broad-reviewer (High), design-reviewer (High), typescript-reviewer (Low), knowledge-reviewer (undocumented-invariant angle) |
| **Validation** | confirmed defect; severity settled to Low — no observable impact through current consumers |

**Issue:** `createChildren` sets the language variant on the module-level **singleton** `scanner` (`utilities.ts:391`) and resets it to `LanguageVariant.Standard` afterward, but neither is in a `try/finally`:

```ts
scanner.setLanguageVariant(languageVariant);
... node.forEachChild(processNode, processNodes); addSyntheticNodes(children, pos, node.end, node);
scanner.setText(undefined);
scanner.setLanguageVariant(LanguageVariant.Standard);
```

If `node.forEachChild(...)` or `addSyntheticNodes` throws (the `Debug.fail` at `services.ts:544` is reachable, though it mainly guards malformed/synthetic trees), both resets are skipped and the shared scanner is left in `LanguageVariant.JSX`. Other consumers of the same singleton (`completions.ts:1898`, `preProcess.ts:338`) call `setText` but never `setLanguageVariant`, so they assume `Standard`. The validator confirmed `setText` does not reset the variant, and that `languageVariant === JSX` changes how `<`+`/` tokenizes.

**Severity — why Low:** the validator traced both current consumers and found neither actually branches on slash/less-than tokens (`preProcess.ts` inspects only braces/strings/identifiers/keywords; `completions.ts:1898` is a position-pinned rescan for `as Identifier` in an import clause), so a leaked JSX variant produces no observable wrong result *today*. It is nonetheless a genuine cross-cutting state hazard for any future consumer, and — unlike the pre-existing (self-healing) `setText(undefined)` reset — the variant leak is not self-healed by the consumers' own `setText` calls.

**Fix:** Wrap the scan body in `try/finally` so the resets always run, and add a one-line comment at the reset noting *why* it must restore `Standard` (other shared-scanner consumers assume that default and never set a variant):
```ts
scanner.setLanguageVariant(languageVariant);
try {
    // ... jsDoc, forEachChild, addSyntheticNodes ...
}
finally {
    scanner.setText(undefined);
    // Restore the shared scanner's default variant — preProcess.ts / completions.ts drive this
    // singleton without setting a variant and rely on it being Standard.
    scanner.setLanguageVariant(LanguageVariant.Standard);
}
```

### #4 🟢 Low: New `SourceFileLike.languageVariant` widens the public API surface without `@internal`, unlike its siblings

| | |
|---|---|
| **File** | `src/compiler/types.ts:4291` |
| **Category** | api-contract / knowledge-preservation |
| **Confidence** | 100 (deterministic API-surface fact) |
| **Found by** | broad-reviewer (Low), design-reviewer (Low) |
| **Validation** | not selected (Low, corroborated by 2 finders) |

**Issue:** `languageVariant?: LanguageVariant;` was added to `SourceFileLike` with no `/** @internal */` tag, unlike its two immediate siblings (`lineMap`, `getPositionOfLineAndCharacter`, both `@internal`). The `tests/baselines/reference/api/typescript.d.ts` baseline confirms this genuinely grows the **public** API surface (once public, it cannot be removed without a breaking change). Its only in-diff consumer, `createChildren`, is internal. Public exposure is plausibly intentional — `Node.getChildren(sourceFile?)` is public, so external callers passing a custom `SourceFileLike` need a way to supply the variant (and this is exactly the mechanism that finding #2 relies on for a correct fix) — but there is no comment recording that decision or why this field diverges from its `@internal` neighbors.

**Fix:** Either add `/** @internal */` to match the siblings if it is only for internal `createChildren` use, or keep it public and add a one-line comment stating that external `SourceFileLike` implementers must supply the variant so `getChildren` scans JSX correctly.
