## Findings

### #1 🟠 High: Crash paths use unbounded `klog.Flush()` before `os.Exit`, which can hang and defeat the restart it exists to force

| | |
|---|---|
| **File** | `pkg/proxy/node.go:154, 170, 178` |
| **Category** | error-handling / reliability |
| **Confidence** | 100 |
| **Found by** | go-reviewer (High), design-reviewer (Low) |

**Issue:** All three exit sites in `NodeManager` — PodCIDR change (154-155), NodeIP change (170-171), and `OnNodeDelete` (178-179) — replace the previous `klog.FlushAndExit(klog.ExitFlushTimeout, 1)` with a bare `klog.Flush()` followed by `n.exitFunc(1)` (`os.Exit` in production). `klog` ships `FlushAndExit` precisely because `Flush` is unbounded: its own docs note the flush hooks "may deadlock" and "might take too long." If the log sink stalls (full disk, blocked stderr/journal), `klog.Flush()` blocks indefinitely and `os.Exit(1)` is never reached — so kube-proxy neither restarts nor keeps serving correctly, silently defeating the entire purpose of `NodeManager` (force a clean restart when NodeIPs/PodCIDRs change). A post-merge report on this PR (nojnhuh) independently observed kube-proxy hanging after "Caches are synced" on real clusters and suspected exactly this flush-robustness regression.

**Fix:** Use `klog.FlushAndExit(klog.ExitFlushTimeout, 1)` at all three sites, or wrap `exitFunc` so the flush is bounded by a timeout before exiting.

### #2 🟡 Medium: `OnNodeChange` overwrites the node baseline before validating the new node's IPs, enabling a spurious crash

| | |
|---|---|
| **File** | `pkg/proxy/node.go:140-172` |
| **Category** | error-handling / correctness |
| **Confidence** | 50 (validated: confirmed) |
| **Found by** | broad-reviewer (Medium), adversarial-reviewer (Medium) |

**Issue:** `OnNodeChange` sets `n.node = node` at line 145 **before** checking whether the new node's IPs are resolvable at line 159. If an Update carries a node whose `Status.Addresses` transiently lack a parseable host IP, `GetNodeHostIPs(node)` errors and the function logs-and-returns at 160-163 *without crashing* — but `n.node` now holds the addressless node as the baseline. On the next Update that restores the node's real (unchanged) IP, `oldNodeIPs` is derived from the corrupted empty baseline, so `reflect.DeepEqual(nil, [IP])` is false and `n.exitFunc(1)` fires — an unwarranted crash even though the NodeIP never actually changed. A validator confirmed the mechanism against `utilnode.GetNodeHostIPs` (errors on zero usable addresses) and noted the trigger is uncommon via routine kubelet churn but plausible via external actors (manual edits, custom/cloud controllers, admission mutation).

**Fix:** Resolve and validate the incoming node's IPs before committing it as the baseline; on `GetNodeHostIPs(node)` error, log and return **without** overwriting `n.node`:
```go
nodeIPs, err := utilnode.GetNodeHostIPs(node)
if err != nil {
    klog.ErrorS(err, "Failed to retrieve NodeIPs")
    return // do not poison the baseline
}
n.mu.Lock()
oldNodeIPs, _ := utilnode.GetNodeHostIPs(n.node)
oldPodCIDRs := n.node.Spec.PodCIDRs
n.node = node
n.mu.Unlock()
// ...then the PodCIDR and NodeIP change checks as before
```

### #3 🟡 Medium: `NewNodeConfig` registers no `AddFunc`, so a node change in the startup window is detected late

| | |
|---|---|
| **File** | `pkg/proxy/config/config.go:288-294` |
| **Category** | async / informer wiring |
| **Confidence** | 50 (validated: confirmed at Medium — Critical/High overstated) |
| **Found by** | broad-reviewer (Critical), quick-reviewer (High), adversarial-reviewer (Medium) |

**Issue:** `NewNodeConfig` wires only `UpdateFunc` + `DeleteFunc`; `AddFunc` is absent, even though the `OnNodeChange` doc promises it fires on "creation or modification," and the sibling `NodeTopologyConfig` added in the same diff (config.go ~618) correctly wires *both* Add and Update. Because `NewNodeManager` starts and cache-syncs the node informer during `newProxyServer` construction (node.go:76-79), while `NodeConfig.RegisterEventHandler(s.NodeManager)` runs later in `Run()` (server.go:608-609), client-go replays the already-synced cache to the new handler as synthetic **Add** notifications — which are dropped (nil `AddFunc`).

Validation established this is **not** the permanent crash-safety failure broad-reviewer's Critical implied, nor the non-issue design-reviewer dismissed it as: `NodeManager`'s baseline comes from the startup poll (not an Add event), so the only lost signal is a Node change landing in the narrow window between that poll and the later handler registration. Such a change is re-delivered via `UpdateFunc` at the next informer resync (`ConfigSyncPeriod`, default 15 min), so it surfaces — and triggers the crash-restart — within one sync period rather than immediately. Real, bounded, self-healing; severity Medium.

**Fix:** Wire `AddFunc` to the same callback, matching `NodeTopologyConfig`:
```go
AddFunc:    func(obj interface{}) { result.handleChangeNode(obj) },
UpdateFunc: func(_, newObj interface{}) { result.handleChangeNode(newObj) },
DeleteFunc: result.handleDeleteNode,
```

### #4 🟡 Medium: `NodeEligible()` takes an exclusive `hs.lock` that guards nothing it touches, serializing the `/healthz` path

| | |
|---|---|
| **File** | `pkg/proxy/healthcheck/proxy_health.go:176-190` |
| **Category** | concurrency / performance |
| **Confidence** | 100 (validation waived — corroborated ×5, incl. two specialists at anchor 100) |
| **Found by** | consistency-reviewer (Medium), performance-reviewer (Medium), go-reviewer (Medium), broad-reviewer (Low), design-reviewer (Low) |

**Issue:** The old `SyncNode` needed `hs.lock.Lock()` to write the now-removed `nodeEligible` bool. The new `NodeEligible()` reads no `hs.lock`-guarded field — it only reads the fixed `hs.nodeManager` pointer and calls `nodeManager.Node()`, which is independently synchronized by `NodeManager.mu` — yet it still takes the **exclusive** write lock (downgraded from the previous `RLock`). `hs.lock` is the same mutex `Updated()`/`QueuedUpdate()` take on every proxier sync cycle and `Health()` takes (as `RLock`) on every probe, so `NodeEligible()` now needlessly serializes the health path against the proxier's hot path while holding the lock across a nested `NodeManager.mu` acquisition and a full `node.DeepCopy()`. No deadlock (lock order is globally consistent one-way), but pure contention plus unclear ownership of what `hs.lock` protects.

**Fix:** Drop the `hs.lock` acquisition from `NodeEligible()` entirely — `NodeManager` already synchronizes its own state. (See also #M7: the `Node()` deep-copy is itself avoidable for a two-field read.)

### #5 🟡 Medium: `OnNodeDelete` now hard-exits, replacing graceful health-drain with an immediate crash

| | |
|---|---|
| **File** | `pkg/proxy/node.go:175-180` |
| **Category** | reliability / lifecycle |
| **Confidence** | 50 |
| **Found by** | adversarial-reviewer (High), design-reviewer (Medium) |

**Issue:** `OnNodeDelete` unconditionally calls `exitFunc(1)` (`os.Exit`). Previously, node deletion flowed through `NodeEligibleHandler` → health server, which marked the node ineligible so `/healthz` returned 503 and load balancers drained it gracefully while kube-proxy kept serving existing rules; the old `NodePodCIDRHandler.OnNodeDelete` only logged. A transient delete (etcd restore, node re-registration churn, a brief watch delete) now terminates kube-proxy, and on restart `NewNodeManager` blocks up to 5 minutes polling for the node to reappear — a potential connectivity gap or crash loop under churn.

**Note (from prior-feedback):** exiting on delete was an **intentional** decision requested in review (danwinship: "by the end of the PR we should be exiting in this case too probably"). This is therefore a documented behavior change, not an accidental regression — but the residual reliability concern (lost graceful drain; crash-on-transient-delete) is real and worth an explicit design note.

**Fix:** Either confirm the single-node field-selected watch cannot deliver transient deletes and document why crash-on-delete is preferred over the health-based drain path, or gate the exit on a durable/confirmed deletion.

### #6 🟡 Medium: `ProxyHealthServer` depends on the concrete `*proxy.NodeManager`, flipping the package dependency direction

| | |
|---|---|
| **File** | `pkg/proxy/healthcheck/proxy_health.go:74` |
| **Category** | design / coupling |
| **Confidence** | 75 |
| **Found by** | design-reviewer (Medium) |

**Issue:** `ProxyHealthServer` now embeds `*proxy.NodeManager` for a single-method need (the current node). This inverts the previous dependency direction (proxy imported healthcheck) so the healthcheck package now pulls in the whole proxy package, and pins the health server to a heavyweight informer-backed type. The test fallout is observable: `healthcheck_test.go` must now spin up a real `NodeManager` with a fake clientset and informer just to exercise taint/deletion eligibility.

**Fix:** Depend on a narrow interface declared in the healthcheck package (e.g. `type nodeProvider interface { Node() *v1.Node }`) and accept that instead of `*proxy.NodeManager`. Restores the boundary, keeps the dependency direction inward, and lets the health server be tested with a trivial fake node.

### #7 🟡 Medium: The crash-on-change lifecycle model has no recorded rationale

| | |
|---|---|
| **File** | `pkg/proxy/node.go:41-43, 140-180` |
| **Category** | knowledge-preservation |
| **Confidence** | 75 |
| **Found by** | knowledge-reviewer (SHOULD) |

**Issue:** `NodeManager` self-terminates on NodeIP change, PodCIDR change, and node deletion — two of which are new behavior (crash-on-NodeIP-change and crash-on-delete did not previously exist). The doc comments and log lines say *what* happens but never *why* crashing the process is the chosen response instead of reconfiguring in place. The load-bearing constraint — NodeIPs/PodCIDRs are consumed once in `newProxyServer` and baked into the proxier, so runtime reconfiguration is unsupported and a restart is required — is invisible in the code. A future maintainer seeing kube-proxy self-terminate on a transient event could "fix" it into a graceful in-place update, silently reintroducing the stale-state behavior the crash exists to prevent (cf. https://issues.k8s.io/111321).

**Fix:** State the rationale on the `NodeManager` type doc, e.g. "NodeIPs and PodCIDRs are read once at startup and baked into the proxier; kube-proxy cannot reconfigure them at runtime, so any change (including node deletion, which invalidates them) triggers a process restart to re-read them cleanly."

### Testing Gaps

- `cmd/kube-proxy/app/server_test.go` — the new `newProxyServer` → `NodeManager` field wiring (`s.NodeManager`, `s.podCIDRs`, `s.NodeIPs`, `s.PrimaryIPFamily`) has no coverage; the deleted `Test_getNodeIPs`/`TestProxyServer_platformSetup` were the only tests exercising the old equivalent, and `NodeManager` is now tested only in isolation (test-reviewer).
- `pkg/proxy/node_test.go:205-218` — `TestNewNodeManager` coordinates a background update goroutine with `time.Sleep` against a fixed 1s poll timeout — a flaky-under-load pattern; a channel/callback sync (as used in the sibling `TestNewNodeTopologyConfig`) would be deterministic. The 10ms/15ms/100ms intervals were reviewer-tuned (danwinship) to reduce the risk, but the sleep-based approach remains (test-reviewer).

### Residual Risks

- `pkg/proxy/node.go:185-190` — `Node()` deep-copies the entire `*v1.Node` (labels, annotations, full status) on every call, though its only caller (`NodeEligible()`) reads just `DeletionTimestamp` and `Spec.Taints`; a narrow accessor would avoid the per-`/healthz` allocation (performance-reviewer, anchor 100). Coupled to #4.
- `pkg/proxy/node.go:129-132` — `PodCIDRs()` returns `n.node.Spec.PodCIDRs` directly, aliasing the informer-cached object, whereas `Node()` deep-copies — an inconsistent ownership contract. Currently safe (single call at startup), but exposing an internal slice of a shared cache object invites accidental mutation (design-reviewer).
