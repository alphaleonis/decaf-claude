### #1 🟠 High: Node informer handlers registered after the informer is already started & synced — data race on `eventHandlers` plus a droppable initial `OnTopologyChange`

| | |
|---|---|
| **File** | `cmd/kube-proxy/app/server.go:608-611`, `pkg/proxy/config/config.go:509-536`, `pkg/proxy/node.go:76-77` |
| **Category** | concurrency / async |
| **Confidence** | 100 (validated) |
| **Found by** | go-reviewer (Critical), quick-reviewer (High, ×2 anchors), adversarial-reviewer (Medium) |

**Issue:** `NewNodeManager` calls `thisNodeInformerFactory.Start(wait.NeverStop)` and `WaitForNamedCacheSync` (`node.go:76-77`), so the shared node informer returned by `NodeManager.NodeInformer()` is **already running and synced** when `NewNodeManager` returns. `NewNodeManager` runs inside `newProxyServer` (`server.go:211`), *before* `Run()`. Then in `Run()`, `NewNodeConfig`/`NewNodeTopologyConfig` register handlers on that already-synced informer and `nodeTopologyConfig.RegisterEventHandler(s.Proxier)` appends to `NodeTopologyConfig.eventHandlers` (`config.go:510`) with **no mutex**.

client-go replays the cached Node to a handler added on an already-started informer as a synthetic Add, delivered on a freshly-started listener goroutine. That delivery runs `handleNodeEvent`, which ranges over `n.eventHandlers` (`config.go:533`), concurrently with the main goroutine's unsynchronized `append` at line 611. Two consequences:

1. **Data race** on the `eventHandlers` slice (append vs. range-read) — undefined behavior; `go test -race` would flag it if the window reproduced.
2. **Logic race**: if the replayed Add runs before line 611's append, the loop iterates zero handlers and `s.Proxier` never receives the initial topology labels. Because `handleNodeEvent` short-circuits when labels are unchanged (`reflect.DeepEqual`, `config.go:528`), topology-aware endpoint routing can stay off until the next genuine label change or full resync (`ConfigSyncPeriod`, default 15m).

This is the exact hazard the file documents the opposite invariant for at `server.go:579-581` ("RegisterHandler() calls need to happen before creation of Sources ... the initial update ... may be lost if no handlers are registered yet"). The sibling service/endpointSlice configs get it right — they call `informerFactory.Start()` only *after* registration (`server.go:603-604`). The node informer is the one that was moved into `NewNodeManager` and started early.

**Note on severity:** the go-reviewer (language specialist) rated this **Critical**; consolidated to High because the append near-always wins the race in practice and the functional gap self-heals on the next update/resync — but it is a genuine data race and a real (if narrow) correctness gap. Dissent recorded.

**Fix:** Register `NodeManager` and `s.Proxier` before the node informer is started — i.e. don't `Start()` the informer factory inside `NewNodeManager`; defer it until after `NodeConfig`/`NodeTopologyConfig` registration in `Run()`, mirroring the service/endpointSlice pattern. Failing that, guard `NodeTopologyConfig.eventHandlers` (and `NodeConfig.eventHandlers`) with a mutex so `RegisterEventHandler` and `handleNodeEvent` cannot race.

### #2 🟡 Medium: `NewNodeConfig` registers no `AddFunc` — node-creation events are an unconditional no-op, contradicting the `OnNodeChange` contract

| | |
|---|---|
| **File** | `pkg/proxy/config/config.go:288-293` |
| **Category** | api-contract / async |
| **Confidence** | 100 (deterministic, 6 finders) |
| **Found by** | quick, broad, knowledge, consistency, design, go |

**Issue:** `NewNodeConfig`'s `cache.ResourceEventHandlerFuncs` wires only `UpdateFunc` and `DeleteFunc`; `AddFunc` was dropped in this PR's final commit (previously `AddFunc: result.handleAddNode`). client-go's `ResourceEventHandlerFuncs.OnAdd` invokes `AddFunc` only when non-nil, so this is an **unconditional, deterministic no-op** — every informer Add (including the initial replay of the existing Node to a late-registered handler) is silently swallowed. This directly contradicts the interface doc immediately above it (`config.go:263`): "OnNodeChange is called whenever creation or modification of node object is observed." Every sibling `*Config` in the same file (`EndpointSliceConfig`, `ServiceConfig`, `ServiceCIDRConfig`, and this PR's own new `NodeTopologyConfig`) registers `AddFunc`.

Currently masked because the sole registered handler, `NodeManager`, obtains its initial state independently via the `nodeLister` poll in `NewNodeManager` rather than via this event stream — so there is no observable functional regression today. It silently breaks the documented contract for any future `NodeHandler`, and reads as a bug to any maintainer (compounded by the dead tombstone branch in `handleChangeNode`, see Minor Findings).

**Fix:** Add `AddFunc: func(obj interface{}) { result.handleChangeNode(obj) }` to match the `OnNodeChange` contract and the sibling configs — or, if the omission is deliberate, add a one-line comment explaining that initial Node state is captured via the poll in `NewNodeManager` and only later changes need observing here.

### #3 🟡 Medium: `s.podCIDRs` is now populated unconditionally (was `LocalModeNodeCIDR`-only), activating pod-CIDR bad-config checks on every cluster

| | |
|---|---|
| **File** | `cmd/kube-proxy/app/server.go:218` |
| **Category** | logic / behavior-change |
| **Confidence** | verified against pre-PR code |
| **Found by** | broad |

**Issue:** `s.podCIDRs = s.NodeManager.PodCIDRs()` runs unconditionally, and `NodeManager.PodCIDRs()` (`node.go:131`) returns `n.node.Spec.PodCIDRs` unconditionally. In the pre-PR code (`server_linux.go`), `s.podCIDRs` was assigned **only** under `if s.Config.DetectLocalMode == LocalModeNodeCIDR` (and the field comment still reads `// only used for LocalModeNodeCIDR`, `server.go:175`). Verified via `git show 08727607^`.

Consequence: `checkBadIPConfig`'s `badCIDRs(s.podCIDRs, badFamily)` (`server.go:343`) and the dual-stack heuristic in `checkBadConfig` (`server.go:293`) previously saw an empty slice off-mode and no-op'd. They now evaluate `node.Spec.PodCIDRs` on **all** clusters (most nodes have PodCIDRs set), so a single-family node podCIDR against a dual-stack cluster can emit the "cluster is X but node.spec.podCIDRs contains only IPvY addresses" warning/error on clusters that never opted into NodeCIDR detection — where podCIDRs are functionally irrelevant. This widens a diagnostic to a population it was never meant to judge.

**Fix:** Gate the `podCIDRs`-based checks (or the `s.podCIDRs` assignment) on `DetectLocalMode == LocalModeNodeCIDR`, preserving the prior scope of these warnings.

### #4 🟡 Medium: Startup node-IP wait changed from ~63s non-fatal backoff to a fatal 5-minute poll, for all modes, undocumented

| | |
|---|---|
| **File** | `pkg/proxy/node.go:60`, `pkg/proxy/node.go:87-108`, `cmd/kube-proxy/app/server.go:211` |
| **Category** | reliability / behavior-change |
| **Confidence** | verified against pre-PR code |
| **Found by** | broad (adversarial noted in passing) |

**Issue:** `NewNodeManager` passes a flat `5*time.Minute` `pollTimeout` (`node.go:60`) that now gates the node-IP wait for **all** detect-local modes, and on timeout it returns an error → kube-proxy fails startup. The pre-PR `getNodeIPs` used `wait.ExponentialBackoff` (~63s) and was **non-fatal** — it returned whatever IPs it had; the 5-minute timeout previously applied only to the `LocalModeNodeCIDR` PodCIDR wait (`timeoutForNodePodCIDR`, old `server_linux.go:58`). Verified via `git show 08727607^`.

Net: a node that never acquires an IP now stalls kube-proxy startup for up to 5 minutes (was ~1 minute) and then crashes rather than proceeding. This is a new hard dependency on "kubelet sets a node IP within 5 minutes." The change is undocumented across all five commits, and it intersects two unresolved reviewer threads (adrianmoisey questioned the 5-minute value; danwinship asked for a warning when the IP wait yields nothing).

**Fix:** Document the new timeout/fatality semantics; consider preserving the shorter, non-fatal behavior for the plain node-IP path, or at minimum emit a warning (per the unresolved `server.go:219` thread) when the wait yields no node IP.

### #5 🟡 Medium: `NodeEligible()` on the `/healthz` hot path now takes an exclusive lock and deep-copies the whole `v1.Node` per request

| | |
|---|---|
| **File** | `pkg/proxy/healthcheck/proxy_health.go:176-177` |
| **Category** | performance |
| **Confidence** | 100 (verified) |
| **Found by** | broad, performance (×2 aspects) |

**Issue:** `NodeEligible()` is called on every `/healthz` / `/livez` request — a continuously-polled endpoint (cloud LB and kubelet health checks, every few seconds, per node, for the process lifetime). The change introduced two regressions there:

1. It calls `hs.nodeManager.Node()`, which `DeepCopy()`s the entire cached `v1.Node` on every request — replacing what was a cached-bool read — just to read `DeletionTimestamp` and `Spec.Taints`. `v1.Node` can carry a large `Status.Images` list plus Allocatable/Capacity/Conditions/Annotations.
2. It acquires `hs.lock.Lock()` (exclusive) where the prior code used `RLock()`. Since the `nodeEligible` field was removed, this function no longer writes any `hs`-owned state (`nodeManager.Node()` is guarded by NodeManager's own mutex), so the exclusive lock needlessly serializes every health probe against the proxier sync loop's `Updated()`/`QueuedUpdate()` calls.

**Fix:** Read only the fields needed under NodeManager's lock (add a narrow accessor like `NodeManager.eligibility()` returning `DeletionTimestamp`/taints, avoiding the full `DeepCopy`), and revert `NodeEligible()` to `RLock()` (or drop the `hs` lock entirely) now that it holds no `hs` state.

### #6 🟡 Medium: NodeManager exit paths use unbounded `klog.Flush()` + `os.Exit(1)` instead of `klog.FlushAndExit`; unresolved maintainer-reported regression

| | |
|---|---|
| **File** | `pkg/proxy/node.go:154-155, 170-171, 178-179` |
| **Category** | prior-feedback / reliability |
| **Confidence** | 75 (validated) |
| **Found by** | prior-feedback (High) |

**Issue:** All three exit sites (PodCIDR change, NodeIP change, node delete) do `klog.Flush()` then `n.exitFunc(1)` (`os.Exit` in production, wired at `node.go:60`). The pre-refactor `NodePodCIDRHandler` used `klog.FlushAndExit(klog.ExitFlushTimeout, ...)`, which bounds the flush with a timeout and is the idiomatic k8s exit; no `FlushAndExit`/`ExitFlushTimeout` remains anywhere in `pkg/proxy` or `cmd/kube-proxy`. An unresolved review thread (nojnhuh, on `node.go:155`) reports "this PR seems to have broken creating clusters for me" and questions whether the previous `FlushAndExit()` was more robust at getting logs written before exit.

Assessment: `klog.Flush()` is a synchronous flush, so the log-loss framing is weaker than the reviewer feared; the more likely substance of the "broke cluster creation" report is the **newly aggressive exit behavior** — `OnNodeDelete` now unconditionally crashes kube-proxy where the old handler did not, so transient node-object churn can crashloop the proxy. Either way the maintainer-reported regression is unresolved in the merged code.

**Fix:** Restore a bounded `klog.FlushAndExit(klog.ExitFlushTimeout, code)` for the production exit path, and re-examine whether unconditional `os.Exit(1)` on node delete/IP-change is the intended resilience posture (it is a deliberate design change; confirm it against the `nojnhuh` report before treating it as settled).

### #7 🟡 Medium: `TestNewNodeTopologyConfig` is a false-positive test — it cannot detect a broken "skip when unchanged" guard, the PR's headline behavior

| | |
|---|---|
| **File** | `pkg/proxy/config/config_test.go:492-599` |
| **Category** | test-quality (false-positive test) |
| **Confidence** | 100 (statically provable) |
| **Found by** | test-reviewer (Critical) |

**Issue:** This test is the one place validating "topology-label diffing fires only on a real change, not on unrelated label churn" (`handleNodeEvent`'s `reflect.DeepEqual` guard, `config.go:528`). Every "handler should receive no notification" sub-case asserts only the *final content* of `handler.topologyLabels` (`require.Empty` / `require.Len(..., 1)`), never whether `OnTopologyChange` was actually invoked. In each such case the newly-computed map is byte-identical to what the handler already holds (empty→empty, or `{zone: X}`→`{zone: X}`), so the assertions pass identically whether the skip-guard fires correctly *or is deleted entirely*. The mock (`nodeTopologyHandlerMock`) has no invocation counter, so it cannot distinguish "not called" from "called again with identical content." The regression guard this test purports to provide is inert.

Per consolidation policy a false-positive test is a defect in its own right (kept primary at Medium; the test-reviewer rated it Critical). The finder supplied a revert-probe (remove the `reflect.DeepEqual` guard → the test still passes); the probe was **not run** to avoid mutating the merged working tree, and it is unnecessary — the false-positive is provable from the test structure alone.

**Fix:** Add a `callCount` to `nodeTopologyHandlerMock`, and in each "no notification" sub-case assert the count is unchanged (`require.Equal(prevCallCount, handler.callCount)`); assert the specific expected map, not just its length, where a real change is expected.

- `cmd/kube-proxy/app/server_test.go` / `pkg/proxy/node_test.go:317-322` — dead re-assertion: `require.NoError(t, err)` on a never-reassigned `err` after the `void` call `OnNodeUpdate(...)`; verifies nothing about that call. (test-reviewer, anchor 100)

### Testing Gaps

- `pkg/proxy/node_test.go:200-260` — `TestNewNodeManager` drives node-state transitions from a background goroutine using fixed `time.Sleep` calls racing the poll loop's 1s timeout; a classic flake pattern under loaded CI. Replace with a deterministic signal (poll the fake lister / use the `waitForInvocation` callback pattern the config test already uses). (test-reviewer, anchor 50)
- `pkg/proxy/healthcheck/healthcheck_test.go` — `TestHealthzServer`/`TestLivezServer` construct their `NodeManager` via the exported `proxy.NewNodeManager`, which hard-wires `exitFunc: os.Exit`; they then call `nodeManager.OnNodeChange(...)`. Dormant today (the tweaks never change node IPs), but any future test case that alters the node's IPs would call `os.Exit(1)` inside the shared test binary, silently killing the whole package's test run. This package can't reach the unexported `newNodeManager` injection point the other tests use. Provide a test-only constructor / interface so `healthcheck` can inject a no-op exit. (test-reviewer, anchor 75)

### Residual Risks

- `pkg/proxy/healthcheck/proxy_health.go:74, 180` — `ProxyHealthServer` now depends on the concrete parent-package type `*proxy.NodeManager`, inverting the previous layering (the lower-level healthcheck utility reaches up into the proxy domain). Couples health tests to full NodeManager construction and creates latent import-cycle fragility; a narrow `NodeProvider{ Node() *v1.Node }` interface would decouple them. (design-reviewer)
- `cmd/kube-proxy/app/server.go:211-220` — NodeManager setup in `newProxyServer` extracts `rawNodeIPs`, calls `PodCIDRs()`, logs, then calls `detectNodeIPs` externally; danwinship (unresolved thread) argued this "knows too much about NodeManager internals" and asked whether the setup could move into NodeManager. Left as-is. (prior-feedback-reviewer)
