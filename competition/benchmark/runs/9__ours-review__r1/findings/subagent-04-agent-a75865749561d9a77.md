## Findings

### 🔴 Critical: `NodeConfig`'s merged `OnNodeChange` wiring silently drops all node-creation/replay events, undermining the crash-on-stale-detection guarantee

| | |
|---|---|
| **File** | `pkg/proxy/config/config.go:288-294` |
| **Category** | DATA_LOSS (silent failure of the new crash-safety mechanism) |
| **Confidence** | 100 |
| **Pre-existing** | no — introduced by this changeset |

**Issue:** `NewNodeConfig` now registers only an `UpdateFunc` and `DeleteFunc` on the node informer:

```go
handlerRegistration, _ := nodeInformer.Informer().AddEventHandlerWithResyncPeriod(
    cache.ResourceEventHandlerFuncs{
        UpdateFunc: func(_, newObj interface{}) { result.handleChangeNode(newObj) },
        DeleteFunc: result.handleDeleteNode,
    },
    resyncPeriod,
)
```

`AddFunc` is gone entirely, even though the `NodeHandler.OnNodeChange` doc comment explicitly promises: *"OnNodeChange is called whenever creation **or modification** of node object is observed."* `cache.ResourceEventHandlerFuncs.OnAdd` (`staging/src/k8s.io/client-go/tools/cache/controller.go:257-261`) is a no-op when `AddFunc == nil`, so "creation" events are silently dropped for every handler registered on this `NodeConfig` — currently just `NodeManager` (`cmd/kube-proxy/app/server.go:609`).

This matters because of how the informer is wired in `Run()`:
```go
s.NodeManager, err = proxy.NewNodeManager(...)   // starts + syncs its own informer factory, in newProxyServer()
...
nodeConfig := config.NewNodeConfig(ctx, s.NodeManager.NodeInformer(), ...)  // registered much later, in Run()
nodeConfig.RegisterEventHandler(s.NodeManager)
```
`NewNodeManager` (`pkg/proxy/node.go:76`, `thisNodeInformerFactory.Start(wait.NeverStop)`) starts and syncs the node informer *during `ProxyServer` construction*, long before `Run()` calls `NewNodeConfig`/`RegisterEventHandler`. Per `sharedIndexInformer.AddEventHandlerWithOptions` (`staging/src/k8s.io/client-go/tools/cache/shared_informer.go:697-721`), registering a handler on an *already-started* informer delivers the current cache contents as synthetic `Add` notifications, not `Update`. Since `AddFunc` is nil, this replay is a complete no-op for `NodeManager`.

The file itself documents the exact pitfall this hits, ~25 lines above the new code (unchanged by this PR):
```go
// Note: RegisterHandler() calls need to happen before creation of Sources because sources
// only notify on changes, and the initial update (on process start) may be lost if no handlers
// are registered yet.
```
(`cmd/kube-proxy/app/server.go:579-581`). `ServiceConfig`/`EndpointSliceConfig` correctly follow "register handler, then start informer factory." The new Node code does the opposite — the informer is started and synced (inside `NewNodeManager`) well before `NodeConfig.RegisterEventHandler` runs — precisely the ordering this comment warns against, and precisely why `AddFunc` needed to be wired.

Contrast with the sibling type added in the same commit, `NodeTopologyConfig` (`pkg/proxy/config/config.go:618-635`), which gets it right — it wires the equivalent merged handler to *both* `AddFunc` and `UpdateFunc`:
```go
AddFunc: func(obj interface{}) { result.handleNodeEvent(obj); ... },
UpdateFunc: func(_, newObj interface{}) { result.handleNodeEvent(newObj); ... },
```
This asymmetry between `NodeConfig` and `NodeTopologyConfig` (added in the very same diff) is strong evidence this is an oversight, not an intentional design choice.

**Why Critical:** Forward: a Node object change (NodeIP or PodCIDR) that lands between `NewNodeManager`'s internal poll succeeding and `NodeConfig`'s handler registration in `Run()` is invisible to `NodeManager` → `NodeManager.node` stays stale → the very next real API update is needed before `OnNodeChange` fires again with a comparable baseline. Since Kubernetes node heartbeats are carried via `coordination.k8s.io/v1 Lease` objects (not Node object churn) since ~1.17, actual Node object updates can be infrequent; the only guaranteed re-sync is the informer's periodic resync at `ConfigSyncPeriod` (default **15 minutes**, `pkg/proxy/apis/config/v1alpha1/defaults.go:122-123`). Backward: for the crash-safety net to fail silently, only a change occurring in the (non-trivial, since NodeManager's construction happens well before `Run()`'s informer wiring) startup-to-registration window is required — a narrow but real window, not a hypothetical one. Both paths hold. This is exactly the failure class (`https://issues.k8s.io/111321`) that motivated this whole redesign: kube-proxy silently continuing to route through stale/incorrect local-detection state instead of crash-restarting. No test exercises this: `pkg/proxy/config/config_test.go` has zero coverage of `NodeConfig`'s event wiring (before or after this PR), and `pkg/proxy/node_test.go`'s new tests call `NodeManager.OnNodeChange` directly, bypassing the real informer-registration path where the bug lives.

**Fix:**
```go
handlerRegistration, _ := nodeInformer.Informer().AddEventHandlerWithResyncPeriod(
    cache.ResourceEventHandlerFuncs{
        AddFunc:    func(obj interface{}) { result.handleChangeNode(obj) },
        UpdateFunc: func(_, newObj interface{}) { result.handleChangeNode(newObj) },
        DeleteFunc: result.handleDeleteNode,
    },
    resyncPeriod,
)
```

### 🟡 Medium: `NodeManager.OnNodeChange` caches a node whose IPs failed to resolve, corrupting the baseline for the next comparison

| | |
|---|---|
| **File** | `pkg/proxy/node.go:140-166` |
| **Category** | DATA_LOSS / false-positive crash |
| **Confidence** | 50 |
| **Pre-existing** | no — introduced by this changeset |

**Issue:**
```go
func (n *NodeManager) OnNodeChange(node *v1.Node) {
	n.mu.Lock()
	oldNodeIPs, _ := utilnode.GetNodeHostIPs(n.node)
	oldPodCIDRs := n.node.Spec.PodCIDRs
	n.node = node               // <-- overwritten unconditionally
	n.mu.Unlock()
	...
	nodeIPs, err := utilnode.GetNodeHostIPs(node)
	if err != nil {
		klog.ErrorS(err, "Failed to retrieve NodeIPs")
		return                   // <-- bails without exiting, but n.node is already the bad state
	}
	if !reflect.DeepEqual(oldNodeIPs, nodeIPs) {
		...
		n.exitFunc(1)
	}
}
```
`n.node` is replaced before it's known whether the new node's IPs are even resolvable. If a given `OnNodeChange` invocation carries a node with a transiently empty/invalid `Status.Addresses` (so `GetNodeHostIPs` errors), the function logs and returns without crashing — but `n.node` now holds this broken state as the new baseline.

**Why Medium:** On the *next* `OnNodeChange` call, `oldNodeIPs` is derived from this corrupted baseline (empty/nil), so when the node's real IP reappears with its original, unchanged value, `reflect.DeepEqual(oldNodeIPs, nodeIPs)` sees empty→real-IP as a "change" and triggers an unwarranted `exitFunc(1)` crash — even though the actual NodeIP never changed. This requires a specific transient condition (a live Update event carrying an addressless/unparseable node) to occur, which isn't certain in normal operation, hence confidence 50 rather than higher.

**Fix:** Don't commit `n.node = node` until after confirming `GetNodeHostIPs(node)` succeeds (or store the raw node but keep last-known-good IPs separately for comparison):
```go
nodeIPs, err := utilnode.GetNodeHostIPs(node)
if err != nil {
	klog.ErrorS(err, "Failed to retrieve NodeIPs")
	return // do not update n.node here
}
n.mu.Lock()
oldNodeIPs, _ := utilnode.GetNodeHostIPs(n.node)
oldPodCIDRs := n.node.Spec.PodCIDRs
n.node = node
n.mu.Unlock()
// ...then compare/exit as before
```

- [x] Fix specifies exact change
- [x] Fix requires no additional decisions

### 🟢 Low: `ProxyHealthServer.NodeEligible()` takes an unnecessary full write lock

| | |
|---|---|
| **File** | `pkg/proxy/healthcheck/proxy_health.go:176-190` |
| **Category** | COUPLING (leftover lock artifact) |
| **Confidence** | 75 |
| **Pre-existing** | no — introduced by this changeset |

**Issue:** The old `SyncNode` needed `hs.lock.Lock()` because it wrote the now-removed `hs.nodeEligible` field. The new `NodeEligible()` no longer writes anything guarded by `hs.lock` — it only reads `hs.nodeManager.Node()`, which has its own independent `NodeManager.mu` locking — yet it still does `hs.lock.Lock()` (full write lock) rather than the previous `RLock()` or no lock at all.

**Why Low:** Every `/healthz` request calls both `Health()` (which uses `hs.lock` for its own protected maps) and `NodeEligible()`; the latter now unnecessarily serializes with concurrent readers/writers of `lastUpdatedMap`/`oldestPendingQueuedMap` even though it touches none of that state. This is a performance/contention nit, not a correctness bug.

**Fix:** Drop the now-unneeded lock entirely (NodeManager already synchronizes its own state):
```go
func (hs *ProxyHealthServer) NodeEligible() bool {
	node := hs.nodeManager.Node()
	if !node.DeletionTimestamp.IsZero() {
		return false
	}
	for _, taint := range node.Spec.Taints {
		if taint.Key == ToBeDeletedTaint {
			return false
		}
	}
	return true
}
```

## Considered But Not Flagged

- **`NodeTopologyConfig` registration race** (`cmd/kube-proxy/app/server.go:610-611`): `NewNodeTopologyConfig` is created against the already-started/synced node informer, and `RegisterEventHandler(s.Proxier)` runs on the very next line — the same "start-before-register" pattern as the Critical finding above. In principle there's a TOCTOU window where the initial replay's `AddFunc` could fire (and record `n.topologyLabels`, permanently suppressing future no-op dedup) before `RegisterEventHandler` appends `s.Proxier` to `n.eventHandlers`, silently leaving the proxier's topology labels at zero-value until the label later changes. Unlike the Critical finding, `AddFunc` *is* wired here, and the register call is the immediate next line of synchronous code versus a goroutine-queued listener callback, making the loss window narrow and speculative rather than deterministic. (confidence 25 — not reported per gate, but worth a maintainer's second look given it shares the same root architectural cause as the Critical finding.)
- **Behavior change: startup now hard-fails after up to 5 minutes if NodeIPs can't be resolved**, vs. the old `getNodeIPs`'s ~63s exponential backoff that silently continued with a possibly-empty `NodeIPs` map. This looks like an intentional "fail fast" philosophy shift consistent with the PR's overall crash-on-bad-state design, and is plausibly reviewed/accepted upstream; not flagged as a defect.
- **Removal of `if node.Name != proxier.nodeName` guards** in the iptables/ipvs/nftables `OnTopologyChange` implementations: correct removal, since the input is now a pre-filtered `map[string]string` computed by `NodeTopologyConfig.handleNodeEvent` from a field-selector-scoped informer, not a raw `*v1.Node` — the check is meaningless on the new signature.
- **`NodeManager.PodCIDRs()` returns `n.node.Spec.PodCIDRs` without a copy** — a slice-aliasing possibility, but its only caller stores it once at startup (`s.podCIDRs = s.NodeManager.PodCIDRs()`) and isn't observed to be mutated afterward; too speculative to flag.

## Positive Observations

- Collapsing `OnNodeAdd`/`OnNodeUpdate` into a single `OnNodeChange` across five proxier implementations (iptables, ipvs, nftables, meta, winkernel) removes substantial duplicated boilerplate (each proxier previously repeated the same node-name check, `reflect.DeepEqual`, and label-copy logic twice).
- `NodeTopologyConfig` (`pkg/proxy/config/config.go`) is a clean, well-scoped abstraction — it correctly centralizes the "only the zone label matters, and only notify on actual change" logic that was previously duplicated per-proxier, and its `AddFunc`/`UpdateFunc` wiring is the *correct* reference pattern that `NodeConfig` should have matched.
- `pkg/proxy/node_test.go`'s new `TestNewNodeManager`/`TestNodeManagerOnNodeChange`/`TestNodeManagerOnNodeDelete` tests are thorough for the polling/constructor logic and correctly use table-driven cases with real fake-client interactions.
- `pkg/proxy/topology.go`'s new comment cross-referencing `NodeTopologyConfig.handleNodeEvent`'s filtering logic is a good knowledge-preservation addition — it flags the coupling between the two files for future maintainers who might add a new topology-aware field.
- Consolidating `getNodeIPs`/`waitForPodCIDR` (two independent polling/watch mechanisms in `cmd/kube-proxy/app/server*.go`) into one `NodeManager` constructor removes meaningfully duplicated wait-for-node-readiness logic.
