## Findings

### #1 🟠 High: `OnNodeChange` advances its comparison baseline before validating the new node's IPs → spurious `os.Exit(1)`

| | |
|---|---|
| **File** | `pkg/proxy/node.go:145` (within `OnNodeChange`, lines 140–172) |
| **Category** | correctness / lifecycle |
| **Confidence** | 100 (verified by code inspection; recurring — matches a validator-CONFIRMED finding in prior review `2026-07-17_13-26-42`) |
| **Found by** | orchestrator — surfaced via recurring-findings cross-check (Step 7) and independently re-verified against the current `node.go`. Not surfaced by this wave's reviewers (a gap for `bugs`/`models=low`). |

**Issue:** `OnNodeChange` assigns `n.node = node` (line 145) **before** the `GetNodeHostIPs(node)` error check (lines 159–163). Because the informer delivers events serially and `n.node` persists between calls, a single update whose `Status.Addresses` yields no parseable host IP poisons the stored baseline:

1. Baseline `n.node` = node with IP `A`.
2. An update arrives with **no parseable host IPs**: `oldNodeIPs, _ = GetNodeHostIPs(n.node)` → `[A]`; `n.node = node` overwrites the baseline with the IP-less node; then `GetNodeHostIPs(node)` returns an error → the function logs and `return`s **without exiting**. The stored baseline is now the IP-less node.
3. The next update restores the **same** IP `A`: `oldNodeIPs, _ = GetNodeHostIPs(n.node)` now derives from the IP-less baseline = `nil` (the error is discarded via `_`); `nodeIPs = [A]`; `reflect.DeepEqual(nil, [A]) == false` → `n.exitFunc(1)`.

The node's effective IP went `A → (none) → A` — unchanged across the two valid states — yet kube-proxy calls `os.Exit(1)`. Blast radius: any controller/cloud-provider update that transiently drops all node addresses makes the affected node's kube-proxy exit; the DaemonSet restarts and `NewNodeManager` can then block up to 5 minutes re-establishing state.

**Fix:** Only advance the baseline after confirming the incoming node yields valid IPs — move `n.node = node` below the `GetNodeHostIPs(node)` success check (and validate before overwriting), or keep a separate `lastGoodNodeIPs`/`lastGoodNode` field for the comparison. Then step 3 compares `[A]` vs `[A]` → no exit.

```go
nodeIPs, err := utilnode.GetNodeHostIPs(node)
if err != nil {
    klog.ErrorS(err, "Failed to retrieve NodeIPs")
    return // do NOT advance the baseline on an unparseable update
}

n.mu.Lock()
oldNodeIPs, _ := utilnode.GetNodeHostIPs(n.node)
oldPodCIDRs := n.node.Spec.PodCIDRs
n.node = node
n.mu.Unlock()
// ...then the PodCIDR and NodeIP change comparisons as before
```

### #2 🟠 High: `NodeTopologyConfig` handlers are registered on an already-started informer → data race on `eventHandlers` + potential permanent loss of the proxier's initial topology labels

| | |
|---|---|
| **File** | `cmd/kube-proxy/app/server.go:610-611`; `pkg/proxy/config/config.go:509-511` (unlocked append), `:533-536` (unlocked range), `:528` (DeepEqual suppression guard); `pkg/proxy/node.go:76-79` (informer started + synced in the constructor) |
| **Category** | concurrency / async |
| **Confidence** | 100 (data race verified by inspection; corroborated by 2 independent specialists this wave and by 3 prior reviews) |
| **Found by** | adversarial-reviewer (High), go-reviewer (High) |

**Issue:** `NewNodeManager` starts **and** cache-syncs its node informer inside the constructor (`node.go:76-79`), which runs early in `newProxyServer` (`server.go:211`). Later, in `Run()`, `NewNodeTopologyConfig(...)` attaches an event handler to that **already-started** informer, and the real downstream handler (`s.Proxier`) is appended via `RegisterEventHandler` **afterward** (`server.go:610-611`). client-go replays the current cache to a newly-added handler as a synthetic **Add**, delivered **asynchronously on the informer's listener goroutine**. Two defects follow from the same root cause:

1. **Data race on `NodeTopologyConfig.eventHandlers`.** The listener goroutine runs `handleNodeEvent` → `for i := range n.eventHandlers` (`config.go:533`) while the main goroutine runs `RegisterEventHandler` → `n.eventHandlers = append(...)` (`config.go:510`), with no mutex. Unsynchronized concurrent read/write of the slice header — a data race by definition (would be flagged by `-race`).
2. **Lost initial topology labels.** If the replayed Add runs before `RegisterEventHandler(s.Proxier)`, `handleNodeEvent` sets `n.topologyLabels` to the current zone with **zero** registered handlers, so the proxier is never called. The `reflect.DeepEqual` guard (`config.go:528`) then suppresses every subsequent unchanged event (including `ConfigSyncPeriod` resyncs, which arrive as `UpdateFunc`), so `proxier.topologyLabels` stays empty **until an actual zone-label change or a kube-proxy restart** — silently degrading topology-aware endpoint routing (topology hints / trafficDistribution).

The old code deliberately started the informer **after** registering all handlers (the removed comment: *"This has to start after the calls to NewNodeConfig because that must configure the shared informer event handler first"*), and every other informer in `Run()` still honors that register-before-start invariant.

**Fix:** Restore the register-before-deliver invariant for the node informer — e.g. pass the downstream handlers into `NewNodeTopologyConfig`/`NewNodeConfig` so they are present before `AddEventHandlerWithResyncPeriod` is called, or have `RegisterEventHandler` replay current state to the new handler under a lock. **A mutex on `eventHandlers` alone fixes only the data race, not the lost-update** — the structural ordering fix addresses both. (Note: `NodeConfig`'s omission of `AddFunc` — Minor finding below — is what keeps this same race from firing on the `NodeConfig` path; do not "fix" that by adding `AddFunc` without also fixing the ordering.)

## Minor Findings

### Consistency

- `pkg/proxy/config/config.go:288-294` — **`NewNodeConfig` wires only `UpdateFunc`+`DeleteFunc`, not `AddFunc`**, while the `NodeHandler.OnNodeChange` doc comment (`config.go:263-265`) says it is *"called whenever creation or modification of node object is observed"* and every sibling config (`NewServiceConfig`, `NewEndpointSliceConfig`, `newNodeTopologyConfig`) wires `AddFunc`. The omission appears **deliberate** (the baseline is captured by `NewNodeManager`'s poll; wiring `AddFunc` would replay the current node against that baseline and risk a spurious startup exit — and would re-introduce Finding #2's race on this path) but is **undocumented**, and the interface doc overstates the wired behavior. Narrow real-world gap: a NodeIP/PodCIDR change in the window between the startup poll and this registration is delivered only as the dropped Add, leaving `NodeManager`'s state stale until the next genuine Update/resync (self-correcting via kubelet heartbeats / `ConfigSyncPeriod`). *Recommend a clarifying comment rather than a behavior change.* (broad-reviewer; corroborated by prior reviews)

### Residual Risks

- `pkg/proxy/healthcheck/proxy_health.go:176-190` — **`NodeEligible()` takes an exclusive `hs.lock.Lock()`** (upgraded from the previous `RLock`) but no longer reads/writes any `hs`-owned field under it (node state now lives behind `NodeManager.mu`), and it calls `nodeManager.Node()`, which `DeepCopy()`s the entire `v1.Node` on every `/healthz` request to answer a two-field question (`DeletionTimestamp`, `Spec.Taints`). Not a correctness defect (lock ordering `hs.lock → NodeManager.mu` has no reverse path; probe cadence is single-digit req/s), but the write lock protects nothing it touches and the per-request deep copy is wasteful. (quick-, broad-, go-reviewer — all noted, none blocking)
- `pkg/proxy/node.go:131` — **`PodCIDRs()` returns `n.node.Spec.PodCIDRs` uncopied** (a reference into the cached node object) under lock. Does not manifest today (consumed once in `newProxyServer` before informer events), but the pattern is fragile — a later in-place mutation of the shared slice would race. Consider returning a copy. (go-reviewer)
