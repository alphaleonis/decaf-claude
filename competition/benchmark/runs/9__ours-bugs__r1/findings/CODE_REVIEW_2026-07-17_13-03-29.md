### #1 🔴 Critical: kube-proxy now `os.Exit(1)`s on ANY NodeIP change and on node deletion — new behavior, no debounce/settle/set-normalization

| | |
|---|---|
| **File** | `pkg/proxy/node.go:159-172` (NodeIP change), `pkg/proxy/node.go:176-180` (delete), default `exitFunc = os.Exit` at `pkg/proxy/node.go:60` |
| **Category** | correctness / production-reliability |
| **Confidence** | 75 (validator: confirmed) |
| **Found by** | adversarial-reviewer (Critical), broad-reviewer (High), prior-feedback-reviewer (High — reported regression) |

**Issue:** The removed `getNodeIPs()` (deleted from `cmd/kube-proxy/app/server.go`) fetched NodeIPs **once** at startup; nothing watched them afterward, and the old `NodePodCIDRHandler.OnNodeDelete` merely logged. This PR makes `NodeManager.OnNodeChange` compare `utilnode.GetNodeHostIPs(old)` vs `(new)` with `reflect.DeepEqual` and call `n.exitFunc(1)` on any difference, and `OnNodeDelete` call `n.exitFunc(1)` unconditionally. So exit-on-NodeIP-change and exit-on-delete are both new.

`GetNodeHostIPs` (`pkg/util/node/node.go:65-97`) returns an **order-dependent** slice built from `Status.Addresses`. `NewNodeManager` returns as soon as one usable IP exists. **[Inference — expected behavior from the code, not observed here]** during normal cluster bringup a Node's addresses commonly settle after registration (dual-stack: IPv4 first, IPv6 added later; or cloud-controller-manager assigning/overwriting the address), and a reordering of same-family InternalIPs flips the primary. Any such post-baseline change makes `DeepEqual` false → `os.Exit(1)` → DaemonSet pod restart, potentially repeatedly while addresses settle (CrashLoopBackOff), leaving kube-proxy down exactly when new Service/Endpoint rules must be programmed. A prior reviewer (nojnhuh) reported this PR broke cluster creation; the mechanism here is consistent with that report but is not independently confirmed to be its root cause.

There is no debounce/settle window and no order-insensitive (set-based) comparison mitigating this.

**Fix:** Compare NodeIPs as an order-insensitive set (or only the per-family primary identity), and/or add a settle window before exiting on a NodeIP change; consider guarding the node-deletion exit against transient tombstones. If a hard exit is the intended contract, document why in-place reconfiguration is rejected.

### #2 🟠 High: node informer is started before its event handlers are registered — data race + possible permanent miss of the proxier's initial topology

| | |
|---|---|
| **File** | `cmd/kube-proxy/app/server.go:608-611`; `pkg/proxy/config/config.go:528` (suppression guard), `:533` (unlocked range), `:509-511` (unlocked append — `NodeTopologyConfig` has no mutex); `pkg/proxy/node.go:76-79` (informer started+synced in constructor) |
| **Category** | concurrency / async |
| **Confidence** | 75 (validator: confirmed) |
| **Found by** | quick-reviewer (High), design-reviewer (Medium), adversarial-reviewer (Medium) |

**Issue:** `newNodeManager` starts the shared node informer and waits for cache sync inside the constructor. Later, in `Run()`, `NewNodeConfig`/`NewNodeTopologyConfig` call `AddEventHandlerWithResyncPeriod` on that already-started informer, and the real downstream handler (`s.NodeManager` / `s.Proxier`) is appended via `RegisterEventHandler` **after** the constructor returns. client-go replays the current cache to a newly-added handler as synthetic Add notifications delivered **asynchronously on the listener's own goroutine** (`vendor/.../shared_informer.go`). Consequences:

1. **Data race:** `NodeTopologyConfig` has no lock; `handleNodeEvent` does `for i := range n.eventHandlers` on the listener goroutine while `RegisterEventHandler(s.Proxier)` does `n.eventHandlers = append(...)` on the main goroutine (`server.go:611`) — unsynchronized concurrent read/write, flaggable by `-race`.
2. **Missed initial topology (timing-dependent):** if the replay wins, `handleNodeEvent` sets `n.topologyLabels` to the node's zone but iterates an empty handler list, so the proxier never receives the initial `OnTopologyChange`; the `reflect.DeepEqual` guard (`config.go:528`) then short-circuits subsequent resyncs, and `NodeTopologyConfig` has no `Run()`/resync recovery path — so the proxier can run without topology data until a real zone change (rare) or restart.

The pre-PR code carried an explicit comment requiring handlers be registered before starting the informer ("This has to start after the calls to NewNodeConfig because that must configure the shared informer event handler first."), removed here for the node path while still honored for the service path (`server.go` service wiring).

**Fix:** Register `NodeConfig`/`NodeTopologyConfig` handlers before the node informer starts, or add a mutex to `NodeTopologyConfig` and reconcile the initial cache state at registration time (e.g. an AddFunc that routes into the same change-detection path).

### #4 🟡 Medium: `OnNodeChange` overwrites the baseline `n.node` before the `GetNodeHostIPs` error check — transient IP-less update poisons the baseline

| | |
|---|---|
| **File** | `pkg/proxy/node.go:145` (assignment), `:159-163` (error check + early return), `:167-171` (exit) |
| **Category** | error-handling / logic-ordering |
| **Confidence** | 75 (validator: confirmed) |
| **Found by** | adversarial-reviewer |

**Issue:** `n.node = node` is assigned (under lock) **before** `nodeIPs, err := GetNodeHostIPs(node)`; on `err != nil` the function logs and returns without exiting, but `n.node` is already the IP-less node. A subsequent event that restores the original IP computes `oldNodeIPs` from the poisoned (IP-less) `n.node` = nil, `DeepEqual(nil, [restoredIPs])` is false → `exitFunc(1)` — even though the effective IP never changed from its true baseline. In the interim `NodeIPs()` (which discards the error) returns nil.

**Fix:** overwrite `n.node` only after a successful `GetNodeHostIPs`, or skip the baseline update and comparison when the new node yields no usable IPs.

### #5 🟡 Medium: `klog.Flush()` + `os.Exit` replaces `klog.FlushAndExit` — the log line explaining WHY kube-proxy exited can be dropped

| | |
|---|---|
| **File** | `pkg/proxy/node.go:154-155, 170-171, 178-179`; default `exitFunc` at `:60` |
| **Category** | error-handling / observability |
| **Confidence** | 50 |
| **Found by** | adversarial-reviewer (Medium), broad-reviewer (Low), prior-feedback-reviewer (High — reported regression) |

**Issue:** The old restart path used `klog.FlushAndExit(klog.ExitFlushTimeout, 1)` (bounded flush, then exit via the overridable `klog.OsExit`). The new path calls `klog.Flush()` then `n.exitFunc(1)` (=`os.Exit`). **[Inference — expected klog behavior, not guaranteed]** `klog.Flush()` is best-effort and drops the bounded-flush timeout guard; on the fatal path the very log line stating the exit reason (NodeIPs/PodCIDRs changed / node deleted) can be lost, matching the "restart with no logs" symptom in nojnhuh's report. This is the explicit, unaddressed change nojnhuh asked to revert.

**Fix:** default `exitFunc` to a `klog.FlushAndExit`-equivalent routed through the overridable `klog.OsExit` (preserving test injection), so the shutdown flush is bounded-wait rather than fire-and-forget — or reply on the thread declining, with rationale.

### #6 🟡 Medium: startup now blocks up to 5 min and hard-aborts the process for all modes when NodeIPs are absent; the cache-sync wait is unbounded

| | |
|---|---|
| **File** | `pkg/proxy/node.go:56-60` (5-min timeout, all modes), `:76-79` (unbounded `WaitForNamedCacheSync`); `cmd/kube-proxy/app/server.go:211-215` |
| **Category** | error-handling / startup-reliability |
| **Confidence** | 50 |
| **Found by** | broad-reviewer (Medium); quick-reviewer (unbounded-sync, considered @25) |

**Issue:** `NewNodeManager` always passes `pollTimeout = 5*time.Minute` regardless of `watchPodCIDRs`, and on timeout returns an error that aborts `newProxyServer` → the process exits. The removed `getNodeIPs` used ~1-minute exponential backoff and, for non-NodeCIDR modes, returned best-effort (possibly nil) IPs and let startup continue. Separately, `WaitForNamedCacheSync` uses the unbounded outer `ctx`, so if the informer never syncs (apiserver unreachable) startup can block indefinitely before the 5-minute poll even begins — whereas the old `waitForPodCIDR` bounded the whole wait. Failing fast is defensible, but the uniform 5-minute window + hard abort (and the now-unbounded sync wait) is a behavior change worth a deliberate decision, and it interacts with #1 during bootstrap.

**Fix:** bound the cache-sync wait too, and reconsider whether non-NodeCIDR modes should abort vs proceed (as before) when NodeIPs are slow.

### #7 🟡 Medium: `PodCIDRs()` returns the internal Node slice by reference while `Node()` deep-copies — inconsistent copy discipline / latent aliasing of shared informer cache

| | |
|---|---|
| **File** | `pkg/proxy/node.go:128-131` |
| **Category** | design / go-memory-model |
| **Confidence** | 75 |
| **Found by** | consistency-reviewer (Medium @100), go-reviewer (Medium @50) |

**Issue:** `PodCIDRs()` returns `n.node.Spec.PodCIDRs` directly — a slice aliasing the shared, informer-owned Node object — while `Node()` returns `n.node.DeepCopy()` and `NodeIPs()` builds a fresh slice. Any consumer that sorts/appends/mutates the returned slice would mutate the live informer cache (racing the informer goroutine and other readers). Current callers are read-only, so no live corruption today, but the exported API hands out a mutable window into shared cache state.

**Fix:** return `slices.Clone(n.node.Spec.PodCIDRs)` under the lock, matching `Node()`/`NodeIPs()`.

### #8 🟡 Medium: the AddFunc/DeleteFunc registration asymmetry silently encodes NodeManager's lifecycle invariant — undocumented, enabling a plausible nil-deref refactor

| | |
|---|---|
| **File** | `pkg/proxy/config/config.go:288-294` (NodeConfig: UpdateFunc+DeleteFunc only) vs `NodeTopologyConfig` (AddFunc+UpdateFunc, no-op DeleteFunc); invariant lives in `pkg/proxy/node.go` |
| **Category** | knowledge-preservation |
| **Confidence** | 75 |
| **Found by** | knowledge-reviewer |

**Issue:** `NewNodeConfig` deliberately omits `AddFunc`, safe only because `newNodeManager` polls and sets `n.node` before `Run()`, making the initial ADD redundant; `NodeTopologyConfig` keeps `AddFunc` (no constructor poll) and no-ops `DeleteFunc` (deletion is handled by `NodeManager.OnNodeDelete` → process exit). None of this reasoning is written down. A future maintainer who "fixes" the missing `AddFunc` by dropping the constructor poll and relying on informer events would leave `n.node` uninitialized — and `NodeIPs()`/`PodCIDRs()`/`Node()` unconditionally dereference `n.node`.

**Fix:** comment the intentional `AddFunc` omission (constructor captures the initial node; deletion is terminal) and the no-op `DeleteFunc`, and note the `n.node != nil` invariant.

### #10 🟡 Medium: `OnTopologyChange` hands the config's internal map to every proxier by reference, with no ownership/immutability contract

| | |
|---|---|
| **File** | `pkg/proxy/config/config.go:532-536` |

| **Found by** | design-reviewer |

**Issue:** `n.eventHandlers[i].OnTopologyChange(n.topologyLabels)` passes the same map reference to all handlers, and each proxier stores it (metaProxier forwards the identical map to both ipv4 and ipv6 proxiers).
