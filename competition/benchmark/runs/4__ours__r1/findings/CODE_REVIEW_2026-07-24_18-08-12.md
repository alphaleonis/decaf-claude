## Findings

### #1 🟡 Medium: "Fix location" switch case is dead — `LessThanSlashToken` guarded by `JsxSelfClosingElement` can never match

| | |
|---|---|
| **File** | `src/services/completions.ts:3511` |
| **Category** | correctness / logic |
| **Confidence** | 100 (deadness is a closed-form structural fact) |
| **Found by** | typescript (High/100), consistency (High/100), quick (High/75), broad (High/75), design (Medium/75), knowledge (comprehension/75) — **6 finders** |
| **Validation** | confirmed (validator independently re-derived the deadness from scanner.ts + parser.ts) |

**Issue:** In `getCompletionData`'s "Fix location" switch (guarded by `if (currentToken.parent === location)`), this PR changed `case SyntaxKind.SlashToken:` to `case SyntaxKind.LessThanSlashToken:` **but left the inner guard `if (currentToken.parent.kind === SyntaxKind.JsxSelfClosingElement)` unchanged.** `LessThanSlashToken` (`</`) is only ever the opening token of a `JsxClosingElement`/`JsxClosingFragment` (`scanner.ts:2204-2210, 3702-3710`; `parser.ts:6339, 6355`), never a `JsxSelfClosingElement`. The `/` in a self-closing `<div />` remains a standalone `SlashToken` (parent `JsxSelfClosingElement`) in **both** scanner variants. So this branch's body is now unreachable dead code. Because the edit was a **replace** (not an add — contrast `utilities.ts:1937`, where the author correctly *added* `LessThanSlashToken` while keeping `SlashToken`), the previously-live `location = currentToken` refinement for the self-closing-tag `/` scenario lost its matching case.

**Impact (calibrated down from the reviewers' initial High):** Validation found that the primary JSX attribute-completion machinery (`tryGetContainingJsxElement(contextToken)` at `completions.ts:4828-4854`) operates on `contextToken`, not `location`, and has its own working `case SlashToken:` for `JsxSelfClosingElement` — so the self-closing scenario is redundantly covered and the user-facing regression is likely minimal or nil. Residual risk: `location` still feeds `getOptionalReplacementSpan(location)` and `isJsxAttribute(location.parent)`; not every downstream use of `location` was exhaustively traced, so an edge-case replacement-span difference cannot be fully excluded. Held at **Medium**: a confirmed logic defect (mechanical over-application of the rename) with a trivial fix, but not a confirmed user-facing breakage.

**Fix:** Revert this one case label back to `SlashToken` (the closing-tag `</` scenario is already handled separately a few lines below at the `switch (parent.kind) { case JsxClosingElement: ... }` block):
```typescript
case SyntaxKind.SlashToken:
    if (currentToken.parent.kind === SyntaxKind.JsxSelfClosingElement) {
        location = currentToken;
    }
    break;
```
Add a fourslash completion test at the trailing `/` of a self-closing element (e.g. `<Some.Component /*pos*/ />`) asserting something sensitive to `location` (quick-info / replacement span), so a future regression here is caught (see Minor → Testing Gaps).

### #2 🟡 Medium: Shared global scanner's language variant is set/reset without `try/finally` — an exception mid-walk leaks the JSX variant into other features

| | |
|---|---|
| **File** | `src/services/services.ts:507-530` (`createChildren`) |
| **Category** | shared-mutable-state / reliability |
| **Confidence** | 75 |
| **Found by** | broad (High/50), design (Medium/50), typescript (Low/50), knowledge (comment angle/75) — **4 finders**; quick-reviewer **dismissed** it (see below) |
| **Validation** | confirmed — the "sticky, not self-healing" distinction was verified directly, refuting the dismissal |

**Issue:** `createChildren` sets the module-global singleton `scanner` (exported from `utilities.ts:391`) to the file's language variant (`scanner.setLanguageVariant(languageVariant)` after `scanner.setText(...)`), walks the node tree via `node.forEachChild(...)` / `addSyntheticNodes`, then resets to `LanguageVariant.Standard` at the end — with **no `try/finally`**. `addSyntheticNodes` (`services.ts:544`) can call `Debug.fail(...)`, which throws **unconditionally in all builds** (`debug.ts:196-204`). If it (or anything in the walk) throws, the shared scanner is left in the JSX variant.

**Why this is not the same as the pre-existing `setText` leak** (the crux quick-reviewer missed, confirmed by validation): grepping every `setLanguageVariant` call on this shared scanner shows **only** `createChildren`'s two calls exist. The other consumers of the same singleton — `preProcess.ts:338`, `completions.ts:1898`, `classifier.ts:123`, `organizeImports.ts:248` — all call `scanner.setText(...)` but **never** `setLanguageVariant(...)`; they rely on the variant being Standard. `git show 02672d281` confirms both `setLanguageVariant` calls are net-new in this PR (before it, the scanner's variant was permanently Standard). So the pre-existing `setText` leak is self-healing (every consumer must set text before scanning), but this new **variant** leak is not — a leaked JSX variant would silently mis-tokenize `</`-adjacent sequences in unrelated features until the next `createChildren` call resets it.

**Severity Medium (not broad's High):** the trigger is a `Debug.fail` on an already-malformed tree (rare), and the leak self-heals on the next `createChildren` call (invoked pervasively), so the blast radius is real but transient and narrow.

**Fix:** Bracket the shared-scanner mutation in `try/finally` so the reset always runs:
```typescript
const languageVariant = sourceFile?.languageVariant ?? LanguageVariant.Standard;
scanner.setText((sourceFile || node.getSourceFile()).text);
scanner.setLanguageVariant(languageVariant);
try {
    // ... existing pos/processNode/forEachChild/addSyntheticNodes body ...
}
finally {
    scanner.setText(undefined);
    scanner.setLanguageVariant(LanguageVariant.Standard);
}
return children;
```

### #3 🟢 Low: `SourceFileLike.languageVariant` — silent Standard default, asymmetric fallback, and an undocumented (public) contract

| | |
|---|---|
| **File** | `src/compiler/types.ts:4291` · `src/services/services.ts:507-508` |
| **Category** | design / evolution-readiness / knowledge |
| **Confidence** | 100 (the fallback asymmetry is a deterministic fact) |
| **Found by** | broad (Low/100 — asymmetry), knowledge (SHOULD/75 — contract doc), design (Low/50 — evolution) — 3 finders |
| **Validation** | not validated (Low, latent; asymmetry is self-evident) |

**Issue:** Two coupled observations on the new optional field:
1. **Asymmetric fallback:** `scanner.setText((sourceFile || node.getSourceFile()).text)` falls back to `node.getSourceFile()` for text, but `const languageVariant = sourceFile?.languageVariant ?? LanguageVariant.Standard` does **not** consult `node.getSourceFile().languageVariant` in that same branch — it silently defaults to Standard. Currently **latent/dead** (the sole caller, `NodeObject.getChildren`, defaults `sourceFile` to a non-optional `getSourceFileOfNode(this)`, so `sourceFile` cannot be `undefined` today), but it is a trap: a future caller passing an explicit `undefined` for a JSX node would silently rescan as Standard — reintroducing the exact bug this PR fixes.
2. **Undocumented, public contract:** `languageVariant?` is added to the deliberately-minimal `SourceFileLike` interface with no doc comment, and (unlike its `@internal` neighbors `lineMap?` / `getPositionOfLineAndCharacter?`) it is **not** marked `@internal`, so it ships in the public `typescript.d.ts` surface. Nothing tells an implementer that JSX/TSX-backing shims must populate it, or that omission silently means Standard.

**Fix:** Consult the underlying source file's variant instead of defaulting, and/or document the contract:
```typescript
const resolvedSourceFile = sourceFile || node.getSourceFile();
scanner.setText(resolvedSourceFile.text);
scanner.setLanguageVariant(resolvedSourceFile.languageVariant ?? LanguageVariant.Standard);
```
Add a doc comment on the field stating the "absent ⇒ Standard" contract, and confirm whether the public exposure is intended (else mark `@internal`).

### #4 🟢 Low: Undocumented non-local coupling between `createChildren`'s variant switch and the `LessThanSlashToken` consumer checks

| | |
|---|---|
| **File** | `src/services/services.ts:509` ⇄ `src/services/completions.ts:1598, 3521, 5808` · `src/services/utilities.ts:1892, 1937` |
| **Category** | knowledge-preservation / comprehension |
| **Confidence** | 75 |
| **Found by** | knowledge-reviewer only (single finder) |
| **Validation** | confirmed, but downgraded Medium → Low |

**Issue:** The consumer checks now match `LessThanSlashToken` only because `createChildren` scans JSX files with the JSX variant (making `</` a single token). None of the edited sites carries a comment tying the token kind to that variant switch, and `services.ts` has no forward pointer to the consumers that depend on it — an entirely non-local, bidirectionally-invisible contract. The codebase does document analogous scanner-state choices inline (`parser.ts:6207-6211`, `preProcess.ts:18`), so an anchoring comment is in-convention.

**Downgraded to Low:** the "silently break" framing is overstated — validation confirmed the coupling is guarded by ≥5 pre-existing fourslash tests (`tsxCompletionOnClosingTag1/2.ts`, `tsxCompletionOnClosingTagWithoutJSX1/2.ts`, `completionsTriggerCharacter.ts:59`, `jsxBraceCompletionPosition.ts` marker 4). A maintainer reverting the variant switch without updating consumers would fail CI loudly, not regress silently. This is a documentation/comprehension nit, not an undetected-regression risk.

**Fix:** Add a one-line comment near `services.ts:509` (JSX-variant scanning is what produces `LessThanSlashToken` for `</`, which downstream completion/utility checks depend on) and, optionally, at one representative consumer site.
