## Adversarial Review

### Summary
The fix is correct for the common path but introduces a new class of shared-global-state corruption and ships a genuine mis-migration. The biggest concern: the JSX-variant set/reset on the process-wide `scanner` singleton is not exception-safe, and one of the six token-kind rewrites (self-closing element) is provably wrong per the parser — and it shipped with zero completion tests to catch it.

### Findings

#### High

- **[composition-hazard]** JSX variant leak on the shared global scanner — no try/finally around set/reset — `src/services/services.ts:509,530`
  - **What's wrong/missing:** `createChildren` mutates the module-level singleton `scanner` (defined `src/services/utilities.ts:391`, created in `LanguageVariant.Standard`) to JSX at line 509 and only restores Standard at line 530. There is no `try/finally`. Between those lines, `node.forEachChild(processNode, processNodes)`, `createSyntaxList`, and `addSyntheticNodes` run — and `addSyntheticNodes` contains an unconditional `Debug.fail(...)` (the "Identifier in trivia" assert, `services.ts:544`) plus arbitrary `forEachChild` callback work, any of which can throw. If anything throws, the scanner is left in JSX mode.
  - **Why it matters:** That same singleton is consumed — with no variant reset of their own (confirmed: `grep setLanguageVariant` finds only `services.ts`) — by `classifier.ts` (lexical classification), `organizeImports.ts`, `preProcess.ts`, and `completions.ts:1898`. All of them `setText(...)` before scanning but none call `setLanguageVariant`, so a leaked JSX variant persists and mis-tokenizes `<`/`</` in non-JSX (`.ts`) files until the next `createChildren` runs to completion. The pre-existing `scanner.setText(undefined)` at line 529 is also outside a finally, but that leak is self-healing (every consumer re-sets text); the *variant* leak is not — this PR turns a benign non-restore into cross-module corruption.
  - **Fix:** Wrap the body in `try { ... } finally { scanner.setText(undefined); scanner.setLanguageVariant(LanguageVariant.Standard); }`. Rejected alternative: give `createChildren` its own local `createScanner(...)` per call (like `src/compiler/utilities.ts:2459`) — cleaner and removes the shared-state hazard entirely, but allocates a scanner per node-children computation on a hot path, so a `finally` is the lower-risk minimal fix. Counter-argument to weigh: reviewers may call the non-restore "consistent with the existing `setText` pattern," but the consequences differ (text self-heals, variant does not), so the pattern parity argument does not hold.
  - **Confidence:** 80/100

- **[incomplete-migration]** Self-closing element case rewritten to a token that never occurs there — `src/services/completions.ts:3511`
  - **What's wrong/missing:** The "Fix location" switch case for `currentToken.parent.kind === SyntaxKind.JsxSelfClosingElement` was changed from `SlashToken` to `LessThanSlashToken`. But a self-closing element's `/` is a `SlashToken`, not `</`: the parser does `parseExpected(SyntaxKind.SlashToken)` for self-closing (`src/compiler/parser.ts:6215`) and `parseExpected(SyntaxKind.LessThanSlashToken)` only for closing tags (`parser.ts:6339`); the scanner only emits `LessThanSlashToken` when `<` is immediately followed by `/` (`scanner.ts:2204-2210`). So `currentToken.kind === LessThanSlashToken && parent === JsxSelfClosingElement` is now unsatisfiable — the case is dead. The PR is internally inconsistent: `completions.ts:4834` and `:4843` correctly keep `SlashToken` for the self-closing/opening-element `/`. This looks like an over-eager find/replace: the *closing*-tag hunk at `:3521` (SlashToken→LessThanSlashToken) is correct, but the self-closing hunk at `:3511` should have stayed `SlashToken`.
  - **Why it matters:** The block exists specifically for self-closing completion (the comment above it reads `// <UI.Test /* completion position */ />`). It no longer fires, so `location` is not fixed up for completions at the `/` of a self-closing element — a silent completion-quality regression in exactly the scenario the code targets. Scope note: this is code-correctness (code-reviewer/edge-case lane); surfaced here per the incomplete-migration mandate and GOVERNANCE "adjacent harms."
  - **Fix:** Revert `completions.ts:3511` to `case SyntaxKind.SlashToken:`. Rejected alternative: keep both `SlashToken` and `LessThanSlashToken` cases — unnecessary, since a self-closing element never contains `</`.
  - **Confidence:** 82/100

#### Medium

- **[test-gap]** Behavioral completions changes ship with no completion tests — `src/services/completions.ts:3521`
  - **What's wrong/missing:** The diff changes five token-kind checks that drive JSX completion triggering/location (`completions.ts:1598,3511,3521,5808`) but adds/updates only two *syntactic-classification* baselines (`syntacticClassificationsJsx1/2.ts`). No fourslash completion test is added or changed (confirmed via `git diff --name-only`), even though the PR narrative names `tsxCompletionOnClosingTagWithoutJSX1` as the motivating failure.
  - **Why it matters:** This is precisely why the self-closing mis-migration (finding above) went undetected — nothing exercises the changed completion paths. Classification baselines don't cover completion trigger/location logic.
  - **Fix:** Add fourslash completion tests for `</` closing-tag completion and `<Foo /**/ />` self-closing completion in `.tsx`. Rejected alternative: rely on the downstream Corsa port to add coverage — leaves Strada regressions unguarded.
  - **Confidence:** 85/100

- **[edge-case]** `?? LanguageVariant.Standard` silently re-introduces the original bug for any `SourceFileLike` lacking `languageVariant` — `src/services/services.ts:507`
  - **What's wrong/missing:** `const languageVariant = sourceFile?.languageVariant ?? LanguageVariant.Standard;`. Because `languageVariant?` is *optional* on `SourceFileLike` (`types.ts:4291`), the correctness of the fix depends entirely on the caller supplying it. Real `SourceFile`s always do (`types.ts:4359` has it non-optional), and the default `getChildren()` arg resolves to a real `SourceFile`, so the common path is safe. But `getChildren`/`getFirstToken`/`getLastToken` accept any `SourceFileLike`; a JSX file passed as a `SourceFileLike` that omits `languageVariant` silently falls back to Standard — the exact original mis-tokenization — with no error or signal. The type system won't catch it because the field is optional.
  - **Why it matters:** Latent recurrence of the fixed bug through a non-obvious call path; fails silently. Reachability by current in-repo callers is unproven — flagging as latent, not confirmed-live.
  - **Fix:** Where a JSX node is expected, derive the variant from the node's own real source file rather than a possibly-partial `SourceFileLike`, or assert/require the field. Rejected alternative: make `languageVariant` required on `SourceFileLike` — clean but a breaking change to a public interface and forces every `SourceFileLike` constructor to supply it.
  - **Confidence:** 76/100

#### Low

- **[docs]** New `languageVariant?` leaks into the public API with no `@internal` and no doc — `src/compiler/types.ts:4291`
  - **What's wrong/missing:** Both sibling optional members added earlier to `SourceFileLike` (`lineMap?`, `getPositionOfLineAndCharacter?`) carry `/** @internal */`; the new `languageVariant?` does not, so it lands in the shipped public surface (confirmed in `tests/baselines/reference/api/typescript.d.ts:5910`, under the public `SourceFileLike` block, not the internal one), with no doc comment. It's only consumed internally by `getChildren`.
  - **Why it matters:** Unintended public-API commitment (now must be preserved) and undocumented. Non-breaking (optional), hence Low. High-impact-change note: this edits a public contract, so the counter-argument is that someone may have *intended* to let external `SourceFileLike` implementers pass a variant — if so, it needs a doc comment either way.
  - **Fix:** Add `/** @internal */` above the field (matching siblings) unless public exposure is intentional, in which case add a doc comment. Rejected alternative: leave as-is — locks in an undocumented public member by accident.
  - **Confidence:** 76/100

Additional low-confidence observation (not in json-findings, below threshold): `getPossibleTypeArgumentsInfo` (`utilities.ts:2049`) and the breakpoint switch (`breakpoints.ts:323`) have no `LessThanSlashToken` case, so a JSX closing bracket that previously surfaced as `LessThanToken` now falls through to their defaults. This appears benign (arguably more correct, since a JSX `</` isn't a generic-arg opener), but neither path is tested against the new tokenization. Confidence ~45.

### Most Critical Gap
The `createChildren` JSX-variant set/reset is not exception-safe (`services.ts:509`/`530`): a single throw between them leaves the process-wide shared scanner in JSX mode, silently corrupting classification, organize-imports, and preprocessing of ordinary `.ts` files until the next `createChildren`. Add a `try/finally`.

### Positive Observations
- The closing-tag migrations (`completions.ts:1598,3521,5808`; `utilities.ts:1892`) and the additive transparency-list entry (`utilities.ts:1937`) are consistent with the parser (`LessThanSlashToken` for `JsxClosingElement`).
- The `?? LanguageVariant.Standard` default is safe for the dominant path (real `SourceFile` always carries `languageVariant`), and the end-of-function reset restores the Standard invariant on the normal path.
- Classification baselines were correctly regenerated to reflect the new `</` single-token output.
