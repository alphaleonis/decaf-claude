### Invariants Identified

- Implicit: "a `SourceFileLike.languageVariant`, if present, correctly describes the syntax variant (JSX vs. Standard) of `.text`." Nothing enforces this — it's just data the caller may or may not populate correctly.
- Implicit: "omitted `languageVariant` means Standard." Encoded only at the single consumption site (`services.ts:507`) via `??`, not in the type itself — the type says "maybe a LanguageVariant," not "Standard if absent."
- Pre-existing invariant this PR partially duplicates: `SourceFile.languageVariant` is *always* populated correctly by the parser for real source files. Widening `SourceFileLike` to include an optional, unenforced version of the same concept creates two representations of "this file's variant" with different strength guarantees living in the same type hierarchy.

### Ratings

- **Encapsulation**: 4/10
  `SourceFileLike` is deliberately a narrow, mostly-`@internal` structural interface used by 15+ unrelated modules (scanner, formatting, importTracker, textChanges, sourcemaps, server layer, etc.). Adding a public, unguarded data field to satisfy one internal consumer (`services.ts:507`) breaks that interface's stated purpose ("subset of properties... used in multiple utility functions") and leaks a JSX-scanning implementation detail of `getChildren` into a type every ad hoc `{ text, getLineAndCharacterOfPosition }` object in the codebase structurally matches. This is a textbook Interface Segregation violation — the codebase's own precedent (`formatNodeGivenIndentation`'s explicit `languageVariant` parameter) shows the narrower alternative was known and available.

- **Invariant Expression**: 3/10
  The field being public-and-optional communicates "this may or may not be known" without saying what "unknown" means. The default (Standard) lives entirely in one `??` expression 200+ lines away in `services.ts`; nothing in `types.ts` documents it (no doc comment on the new member at all, unlike its `@internal` neighbor which at least signals "implementation detail"). A reader of the public `.d.ts` sees `languageVariant?: LanguageVariant` on a "subset of SourceFile" type with zero indication of what omission means or why `SourceFile` has the same field as required two members later.

- **Invariant Usefulness**: 5/10
  The underlying fix (scan `.tsx`-derived `SourceFileLike`s with the JSX variant so `<` / `</` tokenize correctly in `getChildren`) is a real, useful bug fix — confirmed by the `SlashToken` → `LessThanSlashToken` corrections throughout `completions.ts` and `utilities.ts` in this diff. But the *type-level* mechanism chosen (public interface field) is broader than the problem needs; a private/internal field or a parameter would have delivered the same behavioral fix without the public-API cost.

- **Invariant Enforcement**: 2/10
  Nothing prevents constructing a `SourceFileLike` with a `languageVariant` that disagrees with `.text`, and nothing prevents omitting it on a `.tsx`-backed object — which two existing call sites in this very codebase already do (`textChanges.ts:1339`, `sourcemaps.ts:231`). Because it's optional, the compiler gives zero signal to an author who forgets to wire it through when building a new `SourceFileLike`-shaped object; they'll silently get `Standard` scanning of what might be JSX text with no error, just subtly wrong node boundaries/children — precisely the failure category the "make illegal states unrepresentable" principle exists to close off.

### Strengths

- Correctly identifies and fixes a real bug: `createChildren`'s scanner previously always ran in `Standard` variant regardless of the source file's actual variant, corrupting JSX child-node boundaries (`<` `/` as two tokens instead of `LessThanSlashToken`) for anything invoked through a `SourceFileLike` rather than a full `SourceFile`.
- The `?? LanguageVariant.Standard` fallback matches the enum's own default ordinal (`Standard = 0`) and the pattern used elsewhere (`nodeFactory.ts:6056`), so the chosen default is at least consistent with the rest of the codebase.
- `SourceFile`'s own `languageVariant: LanguageVariant` remains required and correctly populated, so no regression for the common/default path (`getChildren()`'s default argument is `getSourceFileOfNode(this)`, a real `SourceFile`).

### Concerns

1. **Public API surface widened unintentionally.** `src/compiler/types.ts:4291` has no `@internal` tag, unlike its immediate neighbor at `4289-4290`, and consequently ships in `tests/baselines/reference/api/typescript.d.ts:5910`. Given the doc comment on the interface and the tagging pattern of every other non-`text` member, this reads as an oversight rather than a deliberate API decision — nothing in the PR discusses making it public, and its only consumer is internal (`services.ts`, not exported).
2. **Interface Segregation violation.** One consumer function's need is pushed onto a 15+-consumer shared interface instead of using the codebase's own established alternative (explicit parameter, as in `formatNodeGivenIndentation`, `src/services/formatting/formatting.ts:437`) or a narrower/`@internal` field.
3. **Silent-default footgun.** Optional + external default (`?? Standard`) means any current or future `SourceFileLike` literal that forgets the field degrades silently to `Standard`-variant scanning instead of failing loudly. Two such literals already exist in production code (`textChanges.ts:1339`, `sourcemaps.ts:231`); they happen not to reach `getChildren` today, but nothing in the type system pins that invariant — a future refactor routing either through `.getChildren()` would reintroduce exactly the bug this PR fixes, with no compiler warning.
4. **Conceptual duplication across the hierarchy.** `SourceFile.languageVariant` (required, parser-populated, trustworthy) and `SourceFileLike.languageVariant` (optional, caller-populated, unverified) now name the same concept with very different strength guarantees. Structurally this is safe (required satisfies optional, no LSP violation), but it invites confusion about which guarantee applies at a given call site, especially since no doc comment distinguishes them.

### Recommended Improvements

- Minimal, low-risk fix: mark the new field `/** @internal */`, matching its neighbor and removing it from the public `.d.ts` baseline. This alone resolves the API-surface concern without touching behavior, since the only reader (`services.ts:507`) is already internal code.
- Prefer following the codebase's existing convention over widening the interface at all: give `createChildren` (and `Node.getChildren`, if needed) an explicit `languageVariant` argument the way `formatNodeGivenIndentation` already does, rather than adding state to `SourceFileLike`. That keeps the "subset of properties used in multiple utility functions" contract narrow and avoids the silent-default problem entirely — a caller who doesn't pass a variant has to consciously choose the default at the call site, not rely on a struct field they might not know exists.
- If the field must stay on the interface (e.g. because multiple future consumers are anticipated), add a doc comment stating the default-on-omission behavior explicitly, and audit `textChanges.ts:1339` / `sourcemaps.ts:231` to either populate it or note in-line why omission is safe there — otherwise the "used in multiple utility functions" comment on `SourceFileLike` is now inaccurate for this member (it's used in exactly one).
