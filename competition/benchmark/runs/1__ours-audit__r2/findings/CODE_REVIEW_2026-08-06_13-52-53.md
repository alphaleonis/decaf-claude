## Findings

### #1 🟠 High: `Debug.Assert(rowIdForOrdinal != null)` now fires on a legitimate, handled no-rowid path

| | |
|---|---|
| **File** | `src/Microsoft.Data.Sqlite.Core/SqliteDataRecord.cs:393` |
| **Category** | correctness / error-handling (debug builds) |
| **Confidence** | 100 (corroborated ×7; validation waived — screened clear) |
| **Found by** | broad (High), dotnet (High), spec-compliance (High), quick (Medium), adversarial (Medium), design (Medium), knowledge (High) |

**Issue:** The old code seeded `_rowidOrdinal = -1` before the discovery loop, so `Debug.Assert(_rowidOrdinal.HasValue)` was *always* satisfied — the genuine "no rowid" case was carried by the sentinel `-1`. The rewrite drops the sentinel: `rowIdForOrdinal` stays `null` unless the loop breaks on a match, and `null` *is* the no-rowid case, handled two lines later by `if (rowIdForOrdinal == null) return new MemoryStream(GetCachedBlob(ordinal), false);`. But the assertion was mechanically translated to `Debug.Assert(rowIdForOrdinal != null)`, which now asserts the negation of a legitimate, explicitly-handled outcome.

The no-rowid outcome is reached on ordinary inputs — a literal/expression blob (`SELECT x'...'`), a column from a view/aggregate, a `WITHOUT ROWID` table, or a composite-PK table. The repository's **own existing test** `GetStream_works` (`SELECT x'427E5743';`) drives exactly this path: `FieldCount == 1`, the single column is skipped by `if (i == ordinal) continue`, the loop body never runs, and `rowIdForOrdinal` is `null` at line 393. In any build with assertions active (Debug — the default `dotnet test`/dev configuration) the assert trips on valid, supported input. (Release strips `Debug.Assert`, so shipped end users are unaffected; impact is on contributor/CI debug builds.)

**Fix:** Delete the assertion — `null` is a supported, immediately-handled result:
```csharp
// remove line 393; the following `if (rowIdForOrdinal == null)` already handles it
```
If a guard is still wanted, it must permit `null` (assert "the search ran", not "a rowid was found").

### #2 🟠 High: Negative "no rowid" result is no longer cached — repeated column scans + `pragma_table_info` queries per access

| | |
|---|---|
| **File** | `src/Microsoft.Data.Sqlite.Core/SqliteDataRecord.cs:329` (write sites 355/387; miss path 393–396) |
| **Category** | performance / scalability regression |
| **Confidence** | 100 (corroborated ×6; validation waived — screened clear) |
| **Found by** | performance (High), quick (Medium), broad (Medium), design (Medium), adversarial (Medium), knowledge (High) |

**Issue:** The old `int? _rowidOrdinal` cached *both* outcomes — a found ordinal, or the sentinel `-1` for "searched, none found" — so the expensive discovery ran at most once per reader. The new `RowIds` dictionary is written only inside the two success branches (`RowIds.Add` at lines 355 and 387); when the scan finds no rowid, nothing is inserted. Every subsequent `GetStream` for a blob column whose table has no discoverable rowid therefore re-enters the full `O(FieldCount)` scan — native interop (`sqlite3_column_database_name`/`table_name`/`origin_name` + UTF-8 string allocations) and `sqlite3_table_column_metadata` per column — and, for any INTEGER-PK candidate, re-executes `SELECT COUNT(*) FROM pragma_table_info($table)` against the open connection.

`GetBytes` and `GetChars` both route through `GetStream`, and consumers typically call them once per row. For a rowid-less blob column streamed across N rows, a previously O(1) resolution becomes N full scans plus up to N `COUNT` round-trips serialized on the reader's connection — a silent throughput regression on exactly the blob-heavy workloads this PR targets.

**Fix:** Memoize the negative result. Change the value type to nullable and store the outcome once after the loop instead of only inside the success branches:
```csharp
if (!RowIds.TryGetValue(rowidkey, out var rowIdForOrdinal))
{
    rowIdForOrdinal = null;
    // ... existing search; on success set rowIdForOrdinal and break WITHOUT calling RowIds.Add ...
    RowIds[rowidkey] = rowIdForOrdinal; // caches both hit and miss
}
```
This also resolves finding #1 cleanly (the assert becomes unnecessary).

### #3 🟠 High: Rowid cache key built by string concatenation can collide across distinct (database, table) pairs

| | |
|---|---|
| **File** | `src/Microsoft.Data.Sqlite.Core/SqliteDataRecord.cs:328` |
| **Category** | correctness / design / security (edge case) |
| **Confidence** | ~65 → **confirmed by validator** (real defect; low likelihood) |
| **Found by** | design (High), security (High), adversarial (High), quick (Medium), broad (Medium) |

**Issue:** The cache key is `string rowidkey = $"{blobDatabaseName}_{blobTableName}";`, stored in `Dictionary<string, RowIdInfo> RowIds`. Because `_` is a legal character in SQLite database and table identifiers, two distinct `(database, table)` pairs can produce the same key — e.g. database `main_foo` + table `bar` and database `main` + table `foo_bar` both yield `"main_foo_bar"` (reachable via `ATTACH DATABASE ... AS main_foo`). On a collision the second blob column's `GetStream` hits the *first* table's cached `RowIdInfo`, whose `.Ordinal` points at the first table's rowid column in the result set. `GetInt64(rowIdForOrdinal.Ordinal)` (line 402) then reads the wrong table's rowid, and `SqliteBlob` (line 404) is opened with the current column's correct db/table/column names but a **foreign rowid** — silently returning another row's blob, or throwing `no such rowid`. This is the exact class of cross-table rowid confusion the PR set out to fix (#32747), reintroduced via key aliasing.

**Likelihood / severity note:** Database/table names come from SQLite's own column metadata, not raw end-user input, and the collision needs a single-statement join across two tables/aliases whose names bracket the underscore differently (typically via `ATTACH`). The validator confirmed the mechanism is real but rated the trigger "narrow, deliberately-constructed rather than everyday." Kept at High on specialist (security + design) impact rating; treat likelihood as low.

**Fix:** Key the cache on a value that cannot alias:
```csharp
private readonly Dictionary<(string? database, string? table), RowIdInfo?> _rowIds = new();
// ...
var rowIdKey = (blobDatabaseName, blobTableName);
```
`RowIdInfo` already captures `TableName`; alternatively validate `rowIdForOrdinal.TableName == blobTableName` on a cache hit and re-scan on mismatch (see finding #4 — the disambiguating data is captured but never used).

### #4 🟢 Low: `RowIdInfo.TableName` is written but never read (dead field)

| | |
|---|---|
| **File** | `src/Microsoft.Data.Sqlite.Core/SqliteDataRecord.cs:23` (set at 354, 386) |
| **Category** | unused-code / dead state |
| **Confidence** | 100 (corroborated ×6) |
| **Found by** | quick, broad, knowledge, design, spec-compliance, dotnet |

**Issue:** `RowIdInfo.TableName` is populated at both construction sites but never read anywhere — resolution consumes only `.Ordinal` (line 402), and lookup is by dictionary key. The field adds a `string` per cache entry with no purpose, and its presence misleadingly implies the table name participates in cache-key identity/validation (it does not — key correctness rests entirely on the concatenated string, see finding #3). It also carries a non-nullable `string` annotation over a source (`sqlite3_column_table_name(...).utf8_to_string()`) the sibling code at lines 125–136 treats as possibly-null.

**Fix:** Remove `TableName` (and its constructor parameter), reducing `RowIdInfo` to just `Ordinal` — or, given finding #3, wire `TableName` into a cache-hit validation check so it earns its place. Do not carry unused state on a cache entry.

### Threat Model Notes (security-reviewer)

- **Trust boundary**: identifiers (`blobDatabaseName`, `blobTableName`, column names) come from SQLite column metadata reflecting the executed statement's schema — a second-order boundary, not direct user input. Exploitability of finding #3 hinges on whether an actor can influence schema/attached-DB naming (DDL rights, `ATTACH` aliases, or an app deriving table/schema names from user input).
- **No injection surface**: `pragma_table_info($table)` is parameterized; `sqlite3_table_column_metadata` and `sqlite3_blob_open` receive names as discrete C-API arguments, never concatenated into SQL.
- **Blast radius**: `RowIds` is a per-`SqliteDataRecord` instance field (per statement/reader), not static — a collision is scoped to one result set, not process-wide.

### Considered But Not Flagged (all agents)

- **Dictionary thread-safety** (`RowIds` mutated without locking) — `SqliteDataRecord`/`SqliteDataReader` is documented single-threaded and already carries several non-thread-safe per-instance caches (`_blobCache`, `_typeCache`, …); consistent with the existing model, no new hazard.
- **Stale cache across `NextResult`** — refuted: `NextResult` disposes and recreates `_record` (`SqliteDataReader.cs:142-145,180`), so `RowIds` never outlives the column layout it was built against; identical lifetime to the old `int?` field.
- **Two blob columns from the same table sharing one key** — correct, not a bug: `Ordinal` is the rowid column's position in the result set, identical for both blob columns of that table (this is the intended fix).
- **Expression/literal blobs producing key `"_"`** — harmless today because negative results are never cached; noted as a caveat for the finding #2 fix (a naive negative-cache would make all rowid-less columns share the `"_"` entry — fine only because they all resolve to `null`; the tuple-key fix in #3 removes the ambiguity).
- **`rowidkey` string allocation on every call (incl. cache hits)** — real per-row GC pressure but negligible against the `SqliteBlob`/`MemoryStream` + native-call cost; largely disappears once #2/#3 land.
- **`new Dictionary<string, RowIdInfo>()` vs target-typed `new()`** — checked and *not* flagged: the file uniformly uses explicit-type initializers (`new Dictionary<string,int>()`, `new string[FieldCount]`), so the explicit form is consistent, not drift.
