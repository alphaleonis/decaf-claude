### #1 🟠 High: NodeTopologyConfig registers handlers on an already-running informer — data race on `eventHandlers` and a startup window where the initial topology label can be silently dropped

| | |
|---|---|
| **File** | `cmd/kube-proxy/app/server.go:610-611`, `pkg/proxy/config/config.go:485-536` |
| **Category** | concurrency / async |
| **Confidence** | 100 (data race) / 50 (dropped-delivery consequence) |
| **Found by** | quick-reviewer (High), consistency-reviewer (High, "never Run()" angle); orchestrator-verified against source |

**Issue:** The node informer is started **eagerly inside `NewNodeManager`** (`pkg/proxy/node.go:76`, `thisNodeInformerFactory.Start(wait.NeverStop)`) during `newProxyServer`. Much later, in `Run()`, the code registers the node configs on that **already-started, already-synced** informer:

```go
nodeTopologyConfig := config.NewNodeTopologyConfig(...)   // server.go:610 — AddFunc registered on a running informer
nodeTopologyConfig.RegisterEventHandler(s.Proxier)        // server.go:611 — appends to eventHandlers (no lock)
```

Adding an `AddFunc` to a started shared informer schedules an **asynchronous synthetic Add** for the already-cached node, delivered on the informer's own listener goroutine. That goroutine runs `handleNodeEvent`, which ranges `n.eventHandlers` (`config.go:533`) — concurrently with the main goroutine's `RegisterEventHandler` appending to the same unguarded slice (`config.go:509-510`; `NodeTopologyConfig` has no mutex). This is a genuine **data race** on `eventHandlers` (a `go test -race` on the production wiring would flag it; the unit test avoids it by registering the handler *before* `Start`).

Second consequence: if the async replay wins the race, `handleNodeEvent` sets `n.topologyLabels` to the node's current zone but finds `eventHandlers` still empty, so `s.Proxier.OnTopologyChange` is **never called**. The dedup guard (`config.go:528`) then suppresses all future identical values, so the initial zone label is never redelivered — topology-aware / `PreferClose` routing silently fails to initialize for the process lifetime. On the major clouds nodes are pre-labeled with `topology.kubernetes.io/zone` before kube-proxy starts, so this is exactly the common case that would be affected.

This is a regression the codebase already warns about: the service/endpointslice path deliberately starts its informer **after** all `RegisterEventHandler` calls (`server.go:601-603`: *"This has to start after the calls to NewServiceConfig..."*). Moving informer ownership into `NodeManager` and starting it eagerly broke that invariant for the node informer only.

Consistency-reviewer's related observation — `nodeTopologyConfig` is never `Run()` (no `go nodeTopologyConfig.Run(...)`, and `NodeTopologyConfig` has no `Run` method, unlike every sibling `*Config`) — is the same wiring defect seen from the symmetry angle. Note its proposed fix (add a `Run()` that waits for cache sync) would **not** close the race, because the `AddFunc` replay still fires the moment the handler is registered on the running informer.

**Fix:** Register `NodeConfig`/`NodeTopologyConfig` handlers **before** the node informer is started (i.e. don't `Start()` inside `NewNodeManager`; start it after `Run()` wires the handlers, mirroring the service path), **or** guard `eventHandlers` (and `topologyLabels`) in both `NodeConfig` and `NodeTopologyConfig` with a mutex so registration is safe against the async replay.

### #2 🟠 High: kube-proxy now self-terminates (`os.Exit(1)`) on a much wider set of Node events, in all modes, with no debounce — and the `NodeManager` contract omits the delete trigger

| | |
|---|---|
| **File** | `pkg/proxy/node.go:41-43, 140-180`, `cmd/kube-proxy/app/server.go:607-609` |
| **Category** | design / availability / knowledge |
| **Confidence** | 75 |
| **Found by** | security-reviewer (High), knowledge-reviewer (High, doc angle), broad-reviewer (residual risk), adversarial-reviewer (scenarios) |

**Issue:** `NodeManager` is now registered unconditionally for every kube-proxy (`server.go:607-609`), and it terminates the process via `exitFunc(1)` = `os.Exit(1)` on:
- **any NodeIP change** (`node.go:167-172`) — for every `DetectLocalMode`;
- **any Node deletion** (`node.go:176-180`, `OnNodeDelete` unconditionally exits);
- **PodCIDR change** when `watchPodCIDRs` is set (`node.go:150-156`).

Per the diff and the corroborating reviewers, the prior behavior was narrower: only a PodCIDR change, only under `LocalModeNodeCIDR`, could crash; node **deletion was log-only**; and NodeIPs were fetched once at startup and never re-watched. The change is deliberate (carried from #125382 — crash-and-restart to re-derive dataplane state), but it has real operational weight:

- There is no debounce, backoff, rate-limit, or re-verification on the crash path. A single API write per node (flip `status.addresses`, or delete+recreate the Node) forces `os.Exit` + CrashLoopBackOff. A controller or etcd restore that rolls such a change across the fleet turns **O(1) API writes into O(nodes) simultaneous kube-proxy crashes** and dataplane sync gaps. A compromised kubelet can crash its own node's proxy via NodeRestriction-permitted self-status edits.
- The transient-deletion case (delete then recreate) now crashes where it previously only logged.

Separately, the authoritative type doc (`node.go:41-43`) states `NodeManager` "crashes kube-proxy if there are any changes in NodeIPs or PodCIDRs" and qualifies only the PodCIDR case — it **does not mention that node deletion also self-terminates**, so a maintainer reading the contract will not expect a transient delete event to exit the process.

**Fix:** Confirm this fail-closed trade is intended for all detect-local modes and document it (release note + the `NodeManager` doc comment, including the delete trigger). Consider debouncing / re-listing to confirm an observed change before exiting, so routine node churn cannot amplify into fleet-wide crash loops. At minimum, extend the `NodeManager` doc to enumerate deletion as an exit trigger.

### #3 🟡 Medium: `NodeConfig` registers no `AddFunc`; a NodeIP/PodCIDR change during the startup window is detected only at the next resync (up to `ConfigSyncPeriod`, default 15m), and the `OnNodeChange` contract is not honored

| | |
|---|---|
| **File** | `pkg/proxy/config/config.go:263-265, 288-294` |
| **Category** | design / async |
| **Confidence** | 75 |
| **Found by** | broad-reviewer (Medium), design-reviewer (Medium), adversarial-reviewer (Medium) — 3 independent finders |

**Issue:** `NewNodeConfig` wires only `UpdateFunc` and `DeleteFunc` (`config.go:290-291`) — no `AddFunc`. Because the node informer is already started (see #1), the synthetic replay-Add carrying the current node state is dropped (no `AddFunc`), and `NodeManager` keeps the baseline it captured by polling in `NewNodeManager`. Any NodeIP change (or PodCIDR change under `watchPodCIDRs`) that lands between that poll and handler registration in `Run()` is therefore not delivered promptly; it surfaces only when a genuine Update arrives or at the next informer resync (`ConfigSyncPeriod`, default 15m). During that window kube-proxy programs rules with stale NodeIPs and the prompt crash-and-restart that is `NodeManager`'s whole purpose is silently deferred.

This also breaks the interface contract: `NodeHandler.OnNodeChange` is documented as "called whenever creation **or modification** of node object is observed" (`config.go:263-265`), but creation events are never delivered. (The `NodeTopologyConfig` sibling *does* register an `AddFunc`, which is why it exhibits the different failure mode in #1 rather than this one.)

**Fix:** Register an `AddFunc` in `NewNodeConfig` routing to `handleChangeNode` (`OnNodeChange` is already idempotent — it compares old vs new — so a redundant initial Add is harmless), or re-seed `NodeManager`'s baseline from the lister at handler-registration time. Either closes the window and aligns behavior with the documented contract.

### #4 🟡 Medium: `/healthz` `NodeEligible()` regressed to an exclusive write-lock plus a full `Node` DeepCopy on every request

| | |
|---|---|
| **File** | `pkg/proxy/healthcheck/proxy_health.go:176-190` |
| **Category** | performance / concurrency |
| **Confidence** | 100 (lock + copy) / 75 (impact magnitude) |
| **Found by** | quick-reviewer (Medium), performance-reviewer (Medium), security-reviewer (Low), broad-reviewer (Low), design-reviewer (Low) — 5 finders |

**Issue:** `NodeEligible()` now takes `hs.lock.Lock()` — the **exclusive** write lock — then calls `hs.nodeManager.Node()`, which returns `n.node.DeepCopy()` (`node.go:189`), only to read `DeletionTimestamp` and `Spec.Taints` (verified at `proxy_health.go:177-188`). It mutates no `hs`-guarded field (the old cached `nodeEligible` bool was removed). This is a double regression versus the pre-PR pure `RLock`-over-a-bool reader:

1. The write lock needlessly serializes every `/healthz` request against every other `/healthz` request and against `Health()`/`Updated()`/`QueuedUpdate()` on the proxy sync hot path.
2. A full `Node` DeepCopy per request allocates and copies the entire object (`Status.Addresses/Conditions/Images` — often large) to read two small fields.

`/healthz` is unauthenticated and probed frequently by load balancers and monitoring, so the cost multiplies and adds a cheap availability-pressure surface.

**Fix:** Compute eligibility without `hs.lock` (node state is already synchronized inside `NodeManager`), and avoid the full DeepCopy — e.g. add a `NodeManager` method that returns just `(deleted bool, hasDeletionTaint bool)` under its own lock, reserving `Node()`'s defensive copy for callers that need the whole object.

### #5 🟡 Medium: `OnNodeChange` stores `n.node` before validating IPs — a transient IP-less update corrupts the baseline and causes a spurious `os.Exit` when the real IP is restored

| | |
|---|---|
| **File** | `pkg/proxy/node.go:142-163` |
| **Category** | error-handling |
| **Confidence** | 50 |
| **Found by** | adversarial-reviewer (Medium), knowledge-reviewer (invariant angle), go-reviewer + security-reviewer (noted) |

**Issue:** `OnNodeChange` computes `oldNodeIPs`/`oldPodCIDRs` and immediately assigns `n.node = node` under the lock (`node.go:143-145`) **before** validating IPs. If a node update transiently drops all parseable addresses, `GetNodeHostIPs(node)` errors and the function logs and returns (`node.go:159-163`) — but `n.node` has already been replaced with the IP-less object. On the **next** event, `oldNodeIPs` is derived from that degraded baseline (nil), so restoring the original IP compares `nil` vs `[IP]` → `reflect.DeepEqual` false → `os.Exit(1)`, even though the effective NodeIP never actually changed.

**Fix:** Compute `nodeIPs` first and only advance `n.node` after successful validation; on the `GetNodeHostIPs` error path, leave the previous baseline intact.

### #6 🟡 Medium: NodeIP change detection uses order-sensitive `reflect.DeepEqual`; a benign reordering of `Status.Addresses` triggers a spurious `os.Exit`

| | |
|---|---|
| **File** | `pkg/proxy/node.go:159-172` |
| **Category** | correctness |
| **Confidence** | 50 |
| **Found by** | adversarial-reviewer (High, conf 50) |

**Issue:** The exit decision is `!reflect.DeepEqual(oldNodeIPs, nodeIPs)` over the **slice** returned by `GetNodeHostIPs`, whose ordering follows `Node.Status.Addresses` ordering. A same-set reorder of addresses (same IPs, different order) produces a differently-ordered slice → `DeepEqual` false → `os.Exit(1)`, despite no real IP change. Combined with #2's fleet-wide blast radius, a controller that rewrites `Status.Addresses` ordering across nodes could trip every kube-proxy at once. The trigger (address reordering) is uncommon, hence the confidence, but the cost of a false positive here is a process crash.

**Fix:** Compare NodeIPs as an order-independent set (sort, or `sets.New`) before deciding to exit.

### #7 🟡 Medium: Startup now hard-fails (blocks up to 5 minutes, then fatal) when the node lacks NodeIPs, in all modes — and the superseded loopback-fallback path is left in place and reads as still-live

| | |
|---|---|
| **File** | `pkg/proxy/node.go:56-109`, `cmd/kube-proxy/app/server.go:210-220`, `detectNodeIPs` |
| **Category** | error-handling / knowledge |
| **Confidence** | 75 |
| **Found by** | adversarial-reviewer (Medium), knowledge-reviewer (High, comprehension angle) |

**Issue:** `newNodeManager` polls up to `pollTimeout` (5 minutes) requiring `GetNodeHostIPs` to succeed (`node.go:87-104`); on failure it returns an error, which `newProxyServer` propagates (`server.go:213-215`), so kube-proxy **fails to start** (CrashLoopBackOff). The replaced `getNodeIPs` retried for ~63s and, on failure, returned `nil`, letting `detectNodeIPs` fall back to loopback so kube-proxy still came up degraded. This fail-fast switch (a) is a behavior change for slow-bring-up nodes where the InternalIP is published late, and (b) is undocumented — and the `detectNodeIPs` loopback-fallback comment/log ("Can't determine this node's IP, assuming loopback…") is retained unchanged, so a reader concludes the no-IP path still degrades gracefully when it now blocks-then-crashes.

**Fix:** Confirm the stricter contract is intended for all detect-local modes and document it (comment at the `NewNodeManager` call site + release note). If degraded loopback start should be preserved outside `watchPodCIDRs`, don't treat missing NodeIPs as a fatal constructor error there. Note in `detectNodeIPs` that for the kube-proxy path `rawNodeIPs` is now guaranteed non-empty.

### #10 🟢 Low: `PodCIDRs()` returns the internal, informer-owned slice without copying — inconsistent with `Node()` (DeepCopy) and `NodeIPs()` (fresh slice)

| | |
|---|---|
| **File** | `pkg/proxy/node.go:128-132` |
| **Category** | data-model / resource-management |
| **Confidence** | 50 |
| **Found by** | design-reviewer (Low), go-reviewer (Low) |

**Issue:** `PodCIDRs()` returns `n.node.Spec.PodCIDRs` directly — a slice aliasing the shared, informer-cache-owned Node object. `Node()` returns a DeepCopy and `NodeIPs()` allocates a fresh slice, so the ownership contract is inconsistent. A caller that sorts or appends-within-cap to the returned slice would corrupt shared informer state observed by other handlers. Current callers only read it, so it is latent, not an active bug.

**Fix:** Return `slices.Clone(n.node.Spec.PodCIDRs)` under the lock, or document `PodCIDRs()` as read-only, matching the copy-on-return discipline of the sibling accessors.

### #11 🟢 Low: The node informer is started with `wait.NeverStop`, not bound to `ctx` — informer goroutines outlive context cancellation (per-call leak in tests)

| | |
|---|---|
| **File** | `pkg/proxy/node.go:76` |
| **Category** | goroutine-lifecycle |
| **Confidence** | 75 |
| **Found by** | go-reviewer (Low) |

**Issue:** `newNodeManager` starts its informer factory with `wait.NeverStop` even though a cancellable `ctx` is in scope. In production the process lifetime absorbs this, but every `newNodeManager` call in tests (`TestHealthzServer`, `TestLivezServer`, `TestNewNodeManager`, …) spins up an informer whose watch goroutines outlive the test, and the constructor's own `ctx` cancellation cannot stop the watch it created.

**Fix:** Start the factory with `ctx.Done()` so the informer's goroutines terminate on context cancellation.

## Specialist Notes

### Threat Model Notes (security-reviewer)

- **Trust boundary:** kube-proxy consumes Node objects from the API server. The Node's `status.addresses`, `spec.podCIDRs`, topology labels, and now its **existence** drive not only dataplane programming but the process lifecycle. RBAC/NodeRestriction limit who can write which nodes, but node update/delete is held by many controllers.
- **Dominant attack-surface change:** Node-object events are now a process-termination trigger for *every* kube-proxy (finding #2). The fail-closed choice (crash to re-init on IP/CIDR change) is defensible for rule correctness, but the crash path has no source-side mitigation, so it doubles as an availability amplifier: O(1) API writes → O(nodes) crash loops.
- **Fail-open vs fail-closed:** startup and IP/CIDR-change paths are fail-closed (appropriate for a dataplane). The one fail-open seam is the `GetNodeHostIPs` error branch in `OnNodeChange`, which caches a malformed update without crashing (finding #5).
- **No new crypto/secrets/injection/network surface.** `/healthz` and `/livez` remain unauthenticated (unchanged); only per-request cost regressed (finding #4).

### Considered But Not Flagged (all agents)

- **Nil-`nodeManager` deref in `NodeEligible()`** — examined by quick, broad, design, security, adversarial, go; all agree it is unreachable in production (constructor ordering guarantees non-nil; hollow-proxy builds no health server). Recorded as a residual risk (above), not a live finding.
- **`healthcheck → proxy` import-direction flip** — verified no import cycle (no `pkg/proxy/*.go` imports `proxy/healthcheck`). Clean layering.
- **Dropped per-proxier `node.Name != proxier.nodeName` guards** in the `OnTopologyChange` handlers — correctly removed; the `NodeManager` informer is field-selector-scoped to `metadata.name == nodeName`, so only this node's events are delivered.
- **Topology-label narrowing to `LabelTopologyZone`** — verified `CategorizeEndpoints` reads only the zone label; the narrowing is safe and documented via a cross-reference note in `topology.go`. Good knowledge preservation.
- **Sharing one `topologyLabels` map reference across IPv4/IPv6 sub-proxiers** — safe: `handleNodeEvent` always builds a fresh map and replaces the field wholesale, never mutating a published map (immutable-snapshot pattern; confirmed by quick, go, performance).
