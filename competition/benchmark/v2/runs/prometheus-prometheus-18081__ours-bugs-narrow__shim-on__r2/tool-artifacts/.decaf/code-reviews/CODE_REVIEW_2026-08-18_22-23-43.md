### #1 🟠 High: `totalQueryableSamples` and `prometheus_engine_query_samples_total` silently change for `@`-modified range selectors

| | |
|---|---|
| **File** | `promql/engine.go:2145`, `promql/engine.go:2183` |
| **Category** | correctness |
| **Confidence** | 100 |
| **Verified** | executed |
| **Pre-existing** | no |
| **Found by** | solo-reviewer (High) |

**Issue:** The old code computed the increment inline and unconditionally at every step:

```go
ev.samplesStats.IncrementSamplesAtStep(step, int64(len(floats)+totalHPointSize(histograms)))
```

`floats`/`histograms` persist across steps, so when an `@` modifier suppresses re-evaluation (`ts != ev.startTimestamp && selVS.Timestamp != nil`), the retained window was still counted at every step. The new code hoists the value into `fullWindowCount`, declared at `:2145` and assigned **only inside** the `if ts == ev.startTimestamp || selVS.Timestamp == nil` block, so those steps now contribute `0`.

This is a change to the *existing* statistic, not the new one. It alters `totalQueryableSamples`, `totalQueryableSamplesPerStep`, and the counter `prometheus_engine_query_samples_total` — the metric operators use for query-cost accounting. The change's own stated intent says `totalQueryableSamples` semantics are unchanged, and the diff *adds* a comment at `util/stats/query_stats.go:276` reading "For range-vector functions, each step counts the full window at that step", which the code now contradicts. The pre-existing doc comment retained at `:271-275` ("we intentionally do not account for optimizations that happen inside the range query engine that reduce the actual work") states the opposite policy explicitly.

The `@`-reuse branch is reachable: `preprocessExprHelper` returns `shouldWrap = false` for `*parser.MatrixSelector` (`promql/engine.go:4364-4367`), so a range selector carrying `@` is **not** wrapped in a `StepInvariantExpr` when a sibling argument of the call is not step-invariant.

**Evidence:** Executed. Same probe run against base (`efbdc3f88`, via a temporary worktree) and head (`ec7157593`), query `quantile_over_time(scalar(m), m[60s] @ 30)` as a range query `201s..216s` step `5s`, series `m 1+1x100` at 10s resolution:

```
base: TotalSamples=20  perStep={201000:5, 206000:5, 211000:5, 216000:5}
head: TotalSamples=8   perStep={201000:5, 206000:1, 211000:1, 216000:1}
```

A 60% drop in a user-facing statistic and in the engine counter. `TestQueryStatistics` contains no case on this path, so the suite stays green.

**Fix:** Keep `TotalSamples` accounting unconditional; only gate the new `SamplesRead` value. For example, restore the full-window value outside the branch:

```go
fullWindowCount := int64(len(floats) + totalHPointSize(histograms))
ev.samplesStats.IncrementSamplesAtStep(step, fullWindowCount)
ev.samplesStats.IncrementSamplesReadAtStep(step, samplesReadCount) // 0 when data was reused
```

placing it after the `matrixIterSlice` block but outside the `if`, and add a `TestQueryStatistics` case for a non-step-invariant call with an `@`-modified range argument.

### #2 🟠 High: subquery step count now drives an unbounded allocation that bypasses `query.max-samples`

| | |
|---|---|
| **File** | `promql/engine.go:2397` |
| **Category** | production |
| **Confidence** | 100 |
| **Verified** | executed |
| **Pre-existing** | no |
| **Found by** | solo-reviewer (High) |

**Issue:** `subqSamplesStats := stats.NewChildWithStepTracking(ev.samplesStats.StepTrackingEnabled(), subqStart, subqEnd, subqInterval)` calls `InitStepTracking` (`util/stats/query_stats.go:298-309`), which allocates **two** `[]int64` of `numSteps = int((subqEnd-subqStart)/subqInterval) + 1` — sized by the *subquery's* step count, which is `range / step` and is subject to no limit anywhere in Prometheus. The previous code used `ev.samplesStats.NewChild()`, which returns `NewQuerySamples(false)` and allocates nothing.

The allocation happens before any sample is read, so `query.max-samples` cannot protect against it. The outer range-query step count is bounded (11000 points at the API layer); the subquery step count is not.

**Evidence:** Executed. Engine with `maxSamples = 50`, per-step stats enabled, instant query `sum_over_time(m[10000s:1ms])` (10,000,000 subquery steps), `runtime.MemStats.TotalAlloc` delta around `qry.Exec`:

```
base: err="query processing would load too many samples into memory"  totalAllocDelta=  0.1 MB
head: err="query processing would load too many samples into memory"  totalAllocDelta=152.7 MB
```

152.7 MB matches 2 × 10^7 × 8 bytes. The query is rejected on the sample limit in both cases — the memory is spent before the limit is reached, and it scales linearly: `m[1000000s:1ms]` would request ~16 GB. Reachable by any client that can issue a query with `stats=all` on a server started with `--enable-feature=promql-per-step-stats`.

**Fix:** Do not size the child's per-step arrays by the subquery layout. The merge at `:2426-2444` maps subquery timestamps onto *outer* steps anyway, so the child only needs `SamplesRead` plus an outer-sized array — or, simpler, drop the child array entirely and have the subquery accumulate a total that the attribution loop distributes. If the subquery-sized array is genuinely needed, cap `numSteps` (and return an error above the cap) rather than allocating unconditionally.

### #3 🟠 High: `samplesRead` double-counts subquery samples when a subquery is a range-vector function argument

| | |
|---|---|
| **File** | `promql/engine.go:1874` (with `promql/engine.go:2184`) |
| **Category** | correctness |
| **Confidence** | 100 |
| **Verified** | executed |
| **Pre-existing** | no |
| **Found by** | solo-reviewer (High) |

**Issue:** `evalSubquery` now merges the subquery's `SamplesRead` into the parent (`parentSamplesStats.MergeSamplesReadFromSubquery(ev.samplesStats)`), and then returns a synthetic `*parser.MatrixSelector` holding the *materialized* subquery output. The caller (`promql/engine.go:2008`) substitutes that into `e.Args[i]`, and the range-vector loop then runs `ev.samplesStats.IncrementSamplesReadAtStep(step, samplesReadCount)` at `:2184` over those materialized points.

The materialized points are not I/O — they are already-computed values in memory. Counting both the subquery's real reads *and* the materialized points inflates `samplesRead` and the new counter `prometheus_engine_query_samples_read_total`. Note that `TotalSamples` deliberately avoids this: `MergeSamplesReadFromSubquery` (`util/stats/query_stats.go:423-434`) explicitly does not merge `TotalSamples`, leaving the outer loop as the sole counter. `SamplesRead` gets both.

This directly falsifies the invariant this change documents in three places — `docs/feature_flags.md:47`, `docs/querying/api.md:246`, and `util/stats/query_stats.go:280-283`: "For other query types, this equals totalQueryableSamples." For instant queries it does not.

**Evidence:** Executed. Instant queries at `t=600s`, per-step stats enabled, series `m 1+1x1000` at 10s resolution:

```
m[60s:10s]                                        TotalSamples=  6  SamplesRead=  6   (bare subquery — correct)
max_over_time(m[60s])                             TotalSamples=  6  SamplesRead=  6   (control — correct)
max_over_time(m[60s:10s])                         TotalSamples=  6  SamplesRead= 12   (2x)
sum_over_time(max_over_time(m[60s:10s])[5m:1m])   TotalSamples=  5  SamplesRead= 65   (13x — compounds when nested)
```

The bare-subquery and plain-matrix-selector controls confirm the inflation is specific to the `evalSubquery` path, and the nesting case shows it compounds. The new tests encode the inflated values rather than catching them: `promql/engine_test.go:1177-1187` asserts `TotalSamples: 36, SamplesRead: 72` for the instant query `max_over_time(metricWith3SampleEvery10Seconds[60s:5s])`, and `promql/engine_test.go:1548` asserts `SamplesRead: 2, // subquery + outer` against `TotalSamples: 1`.

**Fix:** Count each sample once. Either (a) drop the `MergeSamplesReadFromSubquery` call at `:1874` so the outer loop remains the single counter (matching how `TotalSamples` is handled), or — closer to the stated I/O semantics — (b) keep the merge and suppress the `IncrementSamplesReadAtStep` at `:2184` when the matrix argument was produced by `evalSubquery` (the `Call` case already knows this at `:2004-2016` and can pass a flag down). Then correct the affected test expectations at `engine_test.go:1184`, `:1195`, `:1424`, `:1445`, `:1466`, `:1487`, `:1508`, and the new subquery block from `:1517` onward.
