### #1 🔴 Critical: `groups` defaults to the string `"{}"`, so every request that omits it fails with HTTP 500

| | |
|---|---|
| **File** | `posthog/api/feature_flag.py:3403` (field at `:1943`, `GroupsJSONField` at `:1834`) |
| **Category** | correctness |
| **Confidence** | 100 — reproduced with pinned DRF 3.16.1 |
| **Found by** | design-reviewer (Critical) |
| **Validation** | confirmed |

**Issue:** `FeatureFlagTestEvaluationRequestSerializer.groups = GroupsJSONField(required=False)`, and
`GroupsJSONField.__init__` does `kwargs.setdefault("default", "{}")` (`:1842`). DRF returns a field
default straight from `get_default()` without running `to_internal_value`, so when the caller omits
`groups`, `validated_data["groups"]` is the **string** `"{}"`, not a dict. The action's
`groups = request.validated_data.get("groups") or {}` does not catch it — `"{}"` is truthy.

`get_flags_from_service` then does `if groups: payload["groups"] = groups`
(`posthog/api/services/flags_service.py:71-72`), putting the string into the JSON body. On the Rust
side `FlagRequest.groups` is `Option<HashMap<String, Value>>`
(`rust/feature-flags/src/flags/flag_request.rs:62`); `serde_json::from_value::<FlagRequest>`
(`flag_request.rs:115`) fails, returning `FlagError::RequestDecodingError` → HTTP 400. Django's
`response.raise_for_status()` raises `HTTPError`, caught by the blanket `except Exception` at
`:3612` → **HTTP 500 "Failed to evaluate flag"**.

Reproduced against the real field code:

```
groups value: '{}' type: str
truthy (so `or {}` will NOT replace it): True
payload sent to Rust: {"groups": "{}"}
```

This is not conditional on `timestamp` — it breaks the default call path entirely. The sibling
`my_flags` action in the **same file** already carries the exact guard this omits:

```python
# posthog/api/feature_flag.py:2510-2513
groups = request.validated_query_data.get("groups", {})
# Ensure groups is always a dict, not a string
if isinstance(groups, str):
    groups = json.loads(groups) if groups else {}
```

**Fix:** Declare the body field as a real object field rather than reusing the query-string
`CharField` subclass:

```python
groups = serializers.DictField(required=False, default=dict, help_text="Groups for group-based flags")
```

Reusing `GroupsJSONField` also makes drf-spectacular emit `type: string` for a field that accepts an
object, which per `AGENTS.md` propagates into the generated TypeScript types and MCP tool schemas.

### #2 🔴 Critical: `model_to_dict` emits non-JSON-serializable values, so historical evaluation 500s for any flag with traffic

| | |
|---|---|
| **File** | `posthog/api/feature_flag.py:3519-3533`, failing at the call on `:3539` |
| **Category** | correctness / error-handling |
| **Confidence** | 100 — reproduced with pinned Django 4.2.29 |
| **Found by** | design-reviewer (Critical), adversarial-reviewer (High) |
| **Validation** | confirmed (one sub-claim refuted — see below) |

**Issue:** The override payload is built by reflecting over the Django model:

```python
flag_dict = model_to_dict(evaluation_flag, exclude=["created_by", "last_modified_by", "team", "usage_dashboard"])
if flag_dict.get("created_at"): flag_dict["created_at"] = flag_dict["created_at"].isoformat()
if flag_dict.get("updated_at"): flag_dict["updated_at"] = flag_dict["updated_at"].isoformat()
```

Only those two datetimes are converted. `model_to_dict` also returns:

- **`last_called_at`** — `models.DateTimeField(null=True, blank=True)`
  (`posthog/models/feature_flag/feature_flag.py:116`), editable, so included as a raw `datetime`; and
- **`analytics_dashboards`** — a `ManyToManyField` (`feature_flag.py:74`) **not** in the `exclude`
  list, returned as a list of `Dashboard` instances.

Reproduced against the real field definitions:

```
keys: ['dashboards', 'id', 'key', 'last_called_at']
last_called_at in dict: True -> datetime.datetime(2026, 1, 1, 0, 0, tzinfo=...)
m2m value with attachment: [<Dash: Dash object (1)>]
json.dumps FAILED: Object of type datetime is not JSON serializable
```

The `TypeError` is raised by `requests`' `json=payload` inside `get_flags_from_service`, called at
`:3539` — **outside** the local `try` (which closes at `override_definitions = {...}` on `:3533`) but
inside the outer `try`, so it lands in the blanket handler at `:3612` → **HTTP 500**.

`last_called_at` alone is sufficient, and it is populated by a scheduled task every 30 minutes
(`posthog/tasks/scheduled.py:335`, "sync feature flag last_called_at timestamps"). So every
timestamped `test_evaluation` on any flag that has actually been used fails.

Note the codebase already has the correct exclusion list: `RECONSTRUCTABLE_FIELDS` derives from
`field_exclusions["FeatureFlag"]`, which excludes exactly `analytics_dashboards` and
`usage_dashboard` (`posthog/models/activity_logging/activity_log.py:367-373`). The new `exclude`
list diverged from it.

Two incidental facts: because `evaluation_flag` carries `id=feature_flag.id`, the m2m access issues a
real DB query for an unsaved instance; and `updated_at` is `auto_now=True` ⇒ `editable=False`, so it
is never in the dict and that isoformat branch is dead code.

**Refuted sub-claim:** design-reviewer also asserted `model_to_dict` **drops** `id` (making the Rust
`FeatureFlag` deserialization fail on a missing required field). Reproduction shows `id` **is**
present — `AutoField` is editable here. Disregard that half.

**Fix:** Build the payload explicitly from the fields the Rust struct declares rather than reflecting
over the model, and add a contract test round-tripping it through `serde_json::from_value::<FeatureFlag>`:

```python
flag_dict = {
    "id": evaluation_flag.id, "team_id": evaluation_flag.team_id,
    "key": evaluation_flag.key, "name": evaluation_flag.name,
    "filters": evaluation_flag.filters, "active": evaluation_flag.active,
    "deleted": evaluation_flag.deleted, "version": evaluation_flag.version,
    "ensure_experience_continuity": evaluation_flag.ensure_experience_continuity,
    "evaluation_runtime": evaluation_flag.evaluation_runtime,
    "bucketing_identifier": evaluation_flag.bucketing_identifier,
}
```

This also fixes finding #6.

### #3 🔴 Critical: `override_flags_definitions` and `only_use_override_person_properties` are ungated on the public `/flags` endpoint

| | |
|---|---|
| **File** | `rust/feature-flags/src/handler/mod.rs:196` and `:223`; applied at `rust/feature-flags/src/handler/flags.rs:152-188` |
| **Category** | security / authorization |
| **Confidence** | 100 |
| **Found by** | quick-reviewer (Critical), broad-reviewer (Critical), design-reviewer (High), security-reviewer (High ×2), adversarial-reviewer (Medium), knowledge-reviewer (SHOULD) |
| **Validation** | confirmed |

**Issue:** This change adds three caller-controlled inputs to the Rust `/flags` endpoint. Only one is
gated:

```rust
// handler/mod.rs:218-223
if context.meta.detailed_analysis.unwrap_or(false) && authentication::is_internal_request(&context) {
    Some(true)
} else {
    Some(false)
},
context.meta.only_use_override_person_properties,   // <-- ungated
```

and `request.override_flags_definitions.as_ref()` is passed unconditionally into `fetch_and_filter`
(`mod.rs:196`), which replaces the DB definition wholesale:

```rust
// handler/flags.rs:172
*flag = override_flag;
```

`/flags` authenticates with the team's **public, client-embeddable** project API token
(`parse_and_authenticate`, `handler/authentication.rs:9-23`); there is no secret- or personal-key
requirement and no separate internal listener (`router.rs`).

Verified consequences:

- **Property-inference oracle.** The caller chooses `distinct_id` freely, and when
  `only_use_override_person_properties` is *not* set, the real DB person properties are still loaded
  (`prepare_evaluation_state_if_needed`, `flag_matching.rs:813-829`) and merged
  (`get_person_properties`, `flag_matching.rs:1692-1710`). So a crafted condition plus a chosen
  `distinct_id` returns a boolean that reveals whether that person's real property satisfies the
  predicate — a search primitive over arbitrary persons' properties (email, plan, any custom PII).
- **Forced flag results.** Supplying `{"<known-key>": {"active": true, "deleted": false, "filters": {"groups": [{"rollout_percentage": 100}]}}}` returns `enabled: true` plus an attacker-chosen
  variant/payload for a flag the caller is not targeted by, and can force evaluation of flags the
  team has disabled or soft-deleted (`filtered_out_flag_ids` is computed *after* substitution,
  `flags.rs:191`).
- **Property suppression flips negated operators.** With DB properties erased, absent properties make
  `is_not`, `not_icontains`, `not_icontains_multi`, `not_regex` and `is_not_set` return **true**
  (`properties/property_matching.rs:76-83, 131-133, 154-157, 187-188, 195-196`).

**Scoped correctly:** the effect is confined to the caller's own response — flags are deserialized
fresh per request via `HyperCacheReader` (`T: DeserializeOwned`), so the in-place mutation cannot
poison a shared cache or affect other tenants. `not_in` was named by one reviewer but is not
evaluated in `match_property` (it errors there, `property_matching.rs:425-430`); the other five
operators are confirmed.

**Fix:** Resolve all three inputs through one gate so a future knob cannot be added ungated:

```rust
let internal = authentication::is_internal_request(&context);
let override_defs = internal.then(|| request.override_flags_definitions.as_ref()).flatten();
let only_use_override = internal && context.meta.only_use_override_person_properties.unwrap_or(false);
```

Additionally, do not accept `id`/`team_id`/`key` from the caller — merge only the evaluable subset
onto the DB-loaded flag so identity fields cannot be reassigned.

### #4 🟠 High: `only_use_override_person_properties` skips *all* DB preparation, so cohort and group conditions silently evaluate as false

| | |
|---|---|
| **File** | `rust/feature-flags/src/flags/flag_matching.rs:827` |
| **Category** | correctness |
| **Confidence** | 100 |
| **Found by** | adversarial-reviewer (High), design-reviewer (Medium) |
| **Validation** | waived — corroborated, mechanism traced directly |

**Issue:** The new flag was added to an early return that was scoped to person properties only:

```rust
if flags_requiring_db_preparation.is_empty() || self.only_use_override_person_properties {
    self.flag_evaluation_state.skip_person_properties();
    return false;
}
```

But `prepare_flag_evaluation_state` is the **sole** caller of `set_cohorts`
(`flag_matching.rs:214`), and it also does group-type mapping and group-property preparation. Since
`flags_require_db_preparation` includes `requires_cohort_filters()`
(`flags/flag_operations.rs:40`), short-circuiting it means `flag_evaluation_state.cohorts` stays
`None`. `evaluate_cohort_filters` then falls back to an empty map:

```rust
// flag_matching.rs:705-708
let cached_matches = match self.flag_evaluation_state.get_cohort_matches() {
    Some(matches) => matches.clone(),
    None => HashMap::new(), // Happens when targeting an anonymous user with no person record
};
```

Because Django sends `only_use_override_person_properties=True` for **every** timestamped
evaluation, static cohort membership is always unavailable there. A cohort- or group-targeted flag
that was genuinely ON at the requested timestamp is reported OFF with
`reason: no_condition_match, failed: false` — a confidently wrong answer for the exact question the
endpoint exists to answer, and no error is surfaced.

**Fix:** Separate the two concerns. Keep calling `prepare_flag_evaluation_state` and apply
`only_use_override_person_properties` solely inside `get_person_properties` (which already handles
it at `:1696`). If static cohort membership genuinely cannot be reconstructed at a past timestamp,
surface that as an explicit per-condition "not reconstructable" state rather than `false`.

### #6 🟠 High: Historical reconstruction discards most reconstructed fields, so bucketing reverts to model defaults

### #7 🟠 High: The condition analysis is a second matching implementation and contradicts the real evaluator

| | |
|---|---|
| **File** | `rust/feature-flags/src/api/types.rs:602-607` |
| **Category** | correctness / duplicated domain logic |
| **Confidence** | 100 |
| **Found by** | broad-reviewer (High), design-reviewer (High), knowledge-reviewer (SHOULD) |
| **Validation** | waived — corroborated, mechanism traced directly |

**Issue:** `build_condition_analysis` evaluates every filter one way:

```rust
let matched = match_property(property, props, false).unwrap_or(false);
```

against merged **person** properties only. The canonical evaluator `is_condition_match`
(`flag_matching.rs:1572-1587`) dispatches three ways:

```rust
if filter.depends_on_feature_flag() { ... match_flag_value_to_flag_filter(...) }
else if filter.is_cohort() { cohort_filters.push(filter); }        // batch-evaluated after the loop
else { let props = property_context.resolve_for_filter(filter);    // person OR group properties
       if !match_property(filter, props, false).unwrap_or(false) { ... } }
```

The analysis path handles none of these. It even classifies `PropertyType::Cohort` and
`PropertyType::Flag` in `type_str` (`types.rs:577-583`) and then matches them as plain person
properties — and `props` has no entry keyed by a cohort id, so those filters come back
`matched: false` with an explanation like `"Property 'id' does not equal 5"`, while `enabled` on the
same object says the flag matched. Group-property filters fail the same way.

Two matching implementations for one semantics will also drift on every future operator or
property-source change, with no visible link between them.

**Fix:** Have the matcher record per-condition/per-property outcomes as it evaluates and surface
those, rather than re-deriving them afterwards from a partial property bag. At minimum, skip filters
where `depends_on_feature_flag() || is_cohort() || group_type_index.is_some()`, mark them
"not evaluated here", and add a comment naming `is_condition_match` as the source of truth.

### #8 🟠 High: `rollout_excluded` requires a zero rollout, so the ordinary partial-rollout exclusion is mislabeled

| | |
|---|---|
| **File** | `rust/feature-flags/src/api/types.rs:652-696`; contract at `posthog/api/feature_flag.py:1970-1977` |
| **Category** | correctness / API contract |
| **Confidence** | 100 |
| **Found by** | broad-reviewer (High), design-reviewer (High), knowledge-reviewer (SHOULD) |
| **Validation** | waived — corroborated, mechanism traced directly |

**Issue, two halves.**

`is_zero_rollout = rollout_percentage == 0.0` is required on **every** branch that can set
`this_condition_rollout_excluded`, including the branch where `flag_match.condition_index` already
identifies the excluded condition unambiguously:

```rust
if let Some(match_condition_index) = flag_match.condition_index {
    index == match_condition_index && is_zero_rollout    // <- the && is wrong
}
```

But `check_rollout` returns `OutOfRolloutBound` for **any** percentage below 100 whose hash falls
outside the bucket:

```rust
// flag_matching.rs:1931-1945
if rollout_percentage == 100.0 { return Ok((true, ConditionMatch)); }
let hash = self.get_hash(...)?;
if hash <= (rollout_percentage / 100.0) { Ok((true, ConditionMatch)) }
else { Ok((false, OutOfRolloutBound)) }
```

So for a 50% rollout — the common case, and precisely the case this feature exists to explain —
`rollout_excluded` is reported `false` and the explanation falls through to the wrong branch:
`"Condition N matched properties but was not evaluated due to an earlier condition matching"`.

Second half: `matched: all_properties_matched` (`types.rs:713`) means "all property filters in this
condition matched", but the DRF field it feeds documents it as *"Whether this condition was the one
that matched"* (`feature_flag.py:1970`). The locally computed `condition_matched`, which does carry
that meaning, is used only inside the explanation string. Per `AGENTS.md` these `help_text` strings
are the source of truth flowing into generated TypeScript types and MCP tool schemas, so consumers
will code against a contract the producer does not honor.

**Fix:**

```rust
let this_condition_rollout_excluded = if properties_matched_but_rollout_failed {
    match flag_match.condition_index {
        Some(i) => index == i,
        None => is_zero_rollout && all_properties_matched,
    }
} else { is_zero_rollout && all_properties_matched };
```

and split the two booleans into separately documented fields (`properties_matched` vs
`is_matching_condition`) so the Rust producer and the DRF schema agree.

### #9 🟠 High: A dropped override silently reports a present-day evaluation as historical

| | |
|---|---|
| **File** | `posthog/api/feature_flag.py:3534-3537`; `rust/feature-flags/src/handler/flags.rs:177-186` |
| **Category** | error-handling / silent failure |
| **Confidence** | 100 |
| **Found by** | broad-reviewer (Medium), design-reviewer (Medium), knowledge-reviewer (MUST) — **dissent noted** |
| **Validation** | confirmed; one sub-path corrected |

**Issue:** Two silent paths discard the reconstructed definition while the response still presents a
historical answer:

- Python: `except Exception as e: logging.exception(...); override_definitions = None` — evaluation
  proceeds against the current flag. Low reachability (a `model_to_dict`/isoformat failure); note the
  `json.dumps` `TypeError` of finding #2 happens *later* and does **not** land here.
- Rust: `Err(e) => tracing::warn!("Failed to parse override definition for flag {}: {}", ...)` — the
  DB flag is kept. Reachable: `FlagFilters` is largely `#[serde(default)]`, but historical filter
  shapes from an older schema can still fail strict parsing of required or enum fields.

In both cases the caller gets HTTP 200 carrying `person_properties` reconstructed at the timestamp
and a `result` computed from **today's** conditions. `FeatureFlagTestEvaluationResponseSerializer`
has exactly seven fields (`flag_key`, `result`, `reason`, `condition_index`, `payload`,
`person_properties`, `conditions`) — none distinguishes the two cases. And `is_historical`, which
`reconstruct_flag_at_version` does return and which the changeset's own tests assert on, is read into
`reconstructed_flag_data` and then **never copied into the response**.

**Corrected sub-claim:** the third path, `tracing::warn!("Flag not found for override")`, does *not*
produce this failure mode. Its realistic trigger is a soft-deleted flag, and in that case the flag is
also absent from the evaluation set, so Django reports an explicit `reason: "flag_not_found"` — a
visible failure, not a silent blend. That path was much of what drove the MUST rating; hence High
rather than Critical.

**Fix:** Make override application a hard contract. Return the applied override keys in the response
(the Rust canonical log already tracks `flags_overridden`), fail the request when a requested override
cannot be applied, and surface `is_historical` / `used_historical_definition` so a caller can assert
on it.

### #10 🟠 High: `feature_flag:read` is enough to read any person's properties

| | |
|---|---|
| **File** | `posthog/api/feature_flag.py:3388` (response built at `:3604`) |
| **Category** | security / authorization |
| **Confidence** | 100 |
| **Found by** | security-reviewer (High), design-reviewer (Medium) |
| **Validation** | waived — quotable, verified directly |

**Issue:** The action is declared `@action(methods=["POST"], detail=True, required_scopes=["feature_flag:read"])`,
but its response always includes the target person's full property dictionary — `person.properties`
on the no-timestamp path (`:3464`) and the reconstructed ClickHouse map otherwise, both returned as
`person_properties`. The per-property `actual_value` echo in the condition analysis carries the same
data.

Because `distinct_id` is caller-supplied, an API key scoped **only** to feature flags can enumerate
arbitrary persons' properties (email, name, any custom PII) across the whole team. The precedent in
this codebase is explicit — the sibling endpoint that returns exactly this data requires the person
scope:

```python
# posthog/api/person.py:1358
@action(methods=["GET"], detail=False, required_scopes=["person:read"])
def properties_at_time(self, request: request.Request) -> response.Response:
```

A `person` scope exists (`posthog/scopes.py`) and is being bypassed.

**Fix:** Require both scopes (`["feature_flag:read", "person:read"]`), or drop `person_properties`
and `actual_value` from the response so the endpoint stays inside the feature-flag trust boundary.

**Issue:** `auth_token == *internal_token` uses `String`/`str` `PartialEq` — a length check plus
early-exit `memcmp` — rather than a constant-time primitive, which in principle leaks a byte-position
oracle to a caller who can issue repeated requests.

**Assessed honestly:** `is_internal_request` runs inside a pipeline dominated by JSON decoding,
Postgres/Redis team verification, and flag/cohort evaluation, so the sub-microsecond signal from an
early-exit `memcmp` is buried under network jitter and multi-millisecond I/O. This is theoretical
rather than practically actionable — hence Low, not the finder's High. The substantive half of that
finding (unscoped global credential) is reported separately as #21.

**Fix:** Use `subtle::ConstantTimeEq` or `ring::constant_time::verify_slices_are_equal`. Cheap, and
it removes the class of concern entirely.

## Specialist Notes

### Threat Model Notes (security-reviewer)

- **Two trust boundaries touched.** (a) `POST /api/projects/{id}/feature_flags/{id}/test_evaluation` — authenticated staff/API-key surface, team-scoped via `TeamAndOrgViewSetMixin` + `get_object()`. (b) `POST /flags` on the Rust service — reachable by anyone, since the credential is the *public, client-side* project API token. The change adds three new inputs on side (b) and gates exactly one.
- **Data sensitivity.** Person property dictionaries (email, name, arbitrary customer PII) now flow through a Django response body and, via `PropertyAnalysis.actual_value`, the Rust response. Flag targeting configuration (cohort ids, property allowlists) newly flows into INFO-level logs.
- **Attack surface change.** The evaluation engine gained a caller-controlled flag-definition substitution path and a caller-controlled "ignore the database" property mode. Both were plainly designed as internal-only; only the response-shape knob received the trust check.
- **Tenant isolation holds.** Every downstream read and write uses `self.team_id` from the authenticated matcher context, not the override's `team_id` — verified for `set_feature_flag_hash_key_overrides` (`flag_matching.rs:634`), cohort resolution (`:2019`), and realtime membership (`:2111`). A forged `id` collides only within the caller's own team and only in their own response.
- **Correctly ruled out:** ReDoS via caller-supplied `regex` operators (`fancy_regex::RegexBuilder` has an explicit backtrack limit and fails closed); injection in the new `person_existed_at_timestamp` query (fully parameterized, `team_id` filtered); cross-request cache poisoning from `*flag = override_flag` (HyperCache returns owned `DeserializeOwned` values per request).
