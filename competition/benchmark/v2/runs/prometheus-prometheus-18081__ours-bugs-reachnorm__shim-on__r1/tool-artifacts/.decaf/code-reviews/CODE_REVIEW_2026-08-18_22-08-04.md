### #1 🟠 High: `totalQueryableSamples` / `prometheus_engine_query_samples_total` silently changes value for `@`-modified matrix selectors

| | |
|---|---|
| **File** | `promql/engine.go:2145` (and `:2160`, `:2183`) |

| **Confidence** | 100 |
| **Verified** | executed |
| **Pre-existing** | no |
| **Found by** | solo-reviewer (High) |

**Issue:** `fullWindowCount` is declared *inside* the per-step loop and only assigned inside the `if ts == ev.startTimestamp || selVS.Timestamp == nil` block. When a range-vector selector carries an `@` modifier and the data is reused across steps, `fullWindowCount` stays `0`, so `IncrementSamplesAtStep(step, fullWindowCount)` at line 2183 adds nothing. Previously the same call passed `int64(len(floats)+totalHPointSize(histograms))` unconditionally, counting the reused window at every step. The inline comment on line 2143 claims "Full window count for TotalSamples (unchanged semantics)" — that claim is false. This changes a stable, documented metric (`prometheus_engine_query_samples_total`) and the `totalQueryableSamples` API field, and it contradicts the documentation this same PR adds (`docs/feature_flags.md:47`: "each step counts the full window").

The reachable shape is a matrix argument to an `@`-modifier-*unsafe* function, i.e. `predict_linear` (`promql/functions.go:2244-2252`) — those Calls are not wrapped in `StepInvariantExpr`, so the multi-step reuse path really executes.

**Evidence:** executed. Range query `predict_linear(metricWith1SampleEvery10Seconds[60s] @ 30, 3600)`, start 201s, end 220s, step 5s, per-step stats on:

| | base `efbdc3f88` | head `ec7157593` |
|---|---|---|
| `TotalSamples` | 16 | **4** |
| `TotalSamplesPerStep` | `{201000:4, 206000:4, 211000:4, 216000:4}` | **`{201000:4, 206000:0, 211000:0, 216000:0}`** |

(Base measured in a throwaway `git worktree` at `efbdc3f88`, since removed.) The control case `max_over_time(metricWith1SampleEvery10Seconds[60s] @ 30)` is unaffected (16 both sides) because it *is* wrapped in `StepInvariantExpr`. No existing or new test covers the `predict_linear` shape, so the full `./promql/...` suite passes.

**Fix:** keep `TotalSamples` accounting byte-identical to before by computing it outside the reuse guard, e.g. move `fullWindowCount = int64(len(floats) + totalHPointSize(histograms))` to just before line 2183 (after the `len == 0` continue), and only gate `samplesReadCount` on the reuse branch. Then add a regression case for `predict_linear(x[60s] @ T, …)` over a multi-step range query.

### #2 🟠 High: subquery samples are counted twice in `SamplesRead`, so `samplesRead` exceeds `totalQueryableSamples`

| | |
|---|---|
| **File** | `promql/engine.go:1874` |
| **Category** | correctness |
| **Confidence** | 100 |
| **Verified** | executed |
| **Pre-existing** | no |
| **Found by** | solo-reviewer (High) |

**Issue:** `evalSubquery` now calls `parentSamplesStats.MergeSamplesReadFromSubquery(...)`, folding the subquery's storage reads into the parent. But the caller (`eval`'s `*parser.Call` case) then materializes the subquery result as a `MatrixSelector` and walks it with the same per-step loop, which calls `IncrementSamplesReadAtStep(step, samplesReadCount)` at line 2184 over the *in-memory* subquery matrix. The same underlying samples are therefore charged to `SamplesRead` twice: once as real I/O, once as synthetic window reads.

This is precisely the double counting the old code deliberately avoided for `TotalSamples` (`NewChild()` plus the comment "Avoid double counting samples when running a subquery, those samples will be counted in later stage"), which the rewrite dropped for the samples-read path. The consequence is that the headline number the PR exists to add — `prometheus_engine_query_samples_read_total`, help text "The total number of samples read by all queries" — reports roughly 2× the loaded-sample count for any range-vector function over a subquery, which is nonsense for an I/O metric.

**Evidence:** executed, instant query at t=201s over three series `m3{a="1|2|3"}` at 10s resolution:

```
QUERY max_over_time(m3[60s:5s])   TotalSamples= 36  SamplesRead= 72
```

The pattern is systematic and is baked into the new expectations throughout the diff: `promql/engine_test.go:1184` (`36` vs `72`), `:1197` (`72` vs `144`), `:1521` (`2` vs `4`), `:1560` (`6` vs `12`), `:1988`–`:2012` (histogram cases `26` vs `52`, `52` vs `104`). Compare `metricWith1SampleEvery10Seconds[60s:5s]` (a bare subquery, not wrapped in a range-vector function) at `:1158`, where `SamplesRead == TotalSamples == 12` — i.e. the inflation appears exactly when both accounting paths fire.

**Fix:** pick one attribution point. Either keep the merge in `evalSubquery` and suppress the per-step `IncrementSamplesReadAtStep` for selectors produced by `evalSubquery` (the `*parser.VectorSelector` it synthesizes is identifiable), or drop the merge and count only the materialized matrix. Then add an assertion to the stats harness that `SamplesRead <= TotalSamples` holds for every case, which would have caught this.

### #3 🟠 High: subquery step-tracking arrays are allocated proportional to subquery step count, before and regardless of `query.max-samples`

| | |
|---|---|
| **File** | `promql/engine.go:2397` |
| **Category** | production |
| **Confidence** | 100 |
| **Verified** | executed |
| **Pre-existing** | no |
| **Found by** | solo-reviewer (High) |

**Issue:** `stats.NewChildWithStepTracking(..., subqStart, subqEnd, subqInterval)` calls `InitStepTracking`, which allocates **two** `[]int64` of `int((end-start)/interval)+1` entries (`util/stats/query_stats.go:305-307`). Previously subqueries used `NewChild()`, which disabled per-step tracking entirely, so nothing was allocated. The subquery window spans the whole outer query range plus the subquery range, at the *subquery* resolution — a resolution the user controls and which nothing bounds. The allocation happens **before** evaluation, so `query.max-samples` cannot protect against it: a query that is rejected after loading 10 samples still allocates the full arrays first. The subquery's `TotalSamplesPerStep` array is pure waste on top, since `MergeSamplesReadFromSubquery` never reads it and the `*parser.SubqueryExpr` case reads only the scalar `newEv.samplesStats.TotalSamples`.

**Evidence:** executed. Instant query `max_over_time(foo[10m:1ms])` with `MaxSamples=10` (query aborts with `ErrTooManySamples`), measuring `runtime.MemStats.TotalAlloc` across `qry.Exec`:

| | base `efbdc3f88` | head `ec7157593` |
|---|---|---|
| `foo[10m:1ms]` | 95,920 B | **9,697,032 B** |
| `foo[10m:1s]` | 22,656 B | 32,464 B |

9.6 MB is exactly 600,001 steps × 8 B × 2 arrays. Scaling is linear: `[1h:1ms]` is ~57 MB per subquery occurrence in an instant query, and for a 30-day range query the span becomes (30d + 1h)/1ms ≈ 2.6e9 entries ≈ 41 GB. Gated behind `--enable-feature=promql-per-step-stats` **and** a caller-supplied `stats=all`, so on a server with that flag any query author can trigger it.

**Fix:** do not initialize per-step tracking on the subquery child at the subquery's own resolution. The attribution loop only needs, per outer step, the sum of subquery reads falling in that outer step — accumulate directly into an array sized by `numOuterSteps` (map subquery step → outer step at increment time), or cap the child array and fall back to scalar-only attribution above a threshold.

### #4 🟠 High: `countSamplesAfter` adds an O(window) linear scan per step to the hottest PromQL loop, paid even when stats are disabled

| | |
|---|---|
| **File** | `promql/engine.go:2164`, `promql/value.go:195-207` |
| **Category** | efficiency |
| **Confidence** | 100 |
| **Verified** | executed |
| **Pre-existing** | no |
| **Found by** | solo-reviewer (High) |

**Issue:** For every series × every step of every range-vector function, `countSamplesAfter` walks the entire `floats` slice (and `histograms`) comparing timestamps. `floats`/`histograms` are already sorted ascending by `T`, so this is an O(log n) problem solved in O(n). The cost is unconditional: `SamplesRead` is accumulated even when per-step stats and `stats=` are off, because the engine always feeds `prometheus_engine_query_samples_read_total`.

**Evidence:** executed, repository's own `BenchmarkRangeQuery`, `-benchtime 5x -count 6`, same machine, head vs. a `git worktree` at `efbdc3f88`:

```
expr=rate(a_one[1d]),steps=1000
  base: 5902168 6020858 5719385 5870519 5674922 5615062  ns/op   (~5.80 ms)
  head: 8935670 9097434 8940164 9284903 8975939 9302178  ns/op   (~9.09 ms)   +57%

expr=rate(a_hundred[1m]),steps=10000
  base: ~6.29 ms   head: ~6.65 ms   +5%
```

Non-overlapping ranges, and the magnitude tracks window width exactly as an O(window) per-step scan predicts (8,640 points/window × 1,000 steps ≈ 8.6M extra comparisons). Allocations are unchanged, confirming it is CPU in the scan and not the stats allocation of #3 (per-step stats are off in this benchmark).

**Fix:** replace the linear scan with `sort.Search` / `slices.BinarySearchFunc` on `T > cutoff` for the float slice; for histograms, binary-search the index then sum `size()` only over the tail (or track a running total). Alternatively, remember the previous step's window end index and count forward from there, which is O(new points).

### #9 🟢 Low: `MergeSamplesReadFromSubquery` merges per-step arrays by index with no check that the layouts match

| | |
|---|---|
| **File** | `util/stats/query_stats.go:423-434` |
| **Category** | api-design |
| **Confidence** | 75 |
| **Verified** | traced |
| **Pre-existing** | no |
| **Found by** | solo-reviewer (Low) |

**Issue:** The merge adds `child.SamplesReadPerStep[i]` into `qs.SamplesReadPerStep[i]` positionally, and iterates `min(len(qs), len(child))`. Correctness depends entirely on the caller having constructed the child with the parent's `StartTimestamp` and `Interval` — an invariant enforced nowhere and documented only in prose. If the lengths differ, the tail of the child is silently dropped from the per-step array while `qs.SamplesRead` (line 429) has already absorbed the full scalar, so the API would emit a `samplesReadPerStep` whose entries do not sum to `samplesRead`, with no error.

Today the only caller (`promql/engine.go:1869`/`:1874`) does pass a matching layout, so this is latent rather than active — but the function is exported from `util/stats` and the guard costs two comparisons.

**Evidence:** traced. `NewChildWithStepTracking` at `query_stats.go:411` takes `start, end, interval` from the caller with no relation to the receiver; `MergeSamplesReadFromSubquery` never reads `child.StartTimestamp` or `child.Interval`.

**Fix:** either compare `qs.StartTimestamp == child.StartTimestamp && qs.Interval == child.Interval` and fall back to scalar-only merge otherwise, or make it a method that derives the child's layout from the receiver so a mismatch is unconstructible.
