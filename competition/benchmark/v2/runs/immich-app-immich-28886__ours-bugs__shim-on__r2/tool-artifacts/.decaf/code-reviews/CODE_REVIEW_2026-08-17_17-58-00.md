### #1 🟠 High: Write path re-permits `rating: -1` but the search filter still rejects it

| | |
|---|---|
| **File** | `server/src/dtos/search.dto.ts:36-49` (interacting with the changed `server/src/dtos/asset.dto.ts:16-23`) |
| **Category** | api-contract / composition |
| **Confidence** | 100 (promoted on agreement) |
| **Screen** | 90 |
| **Validation** | confirmed |
| **Found by** | broad-reviewer (High), adversarial-reviewer (High) |

**Issue:** `server/src/dtos/asset.dto.ts:19` now accepts `rating: -1`. `BaseSearchSchema.rating` at `server/src/dtos/search.dto.ts:36-49` was not restored and still carries `.min(1).max(5)` from `99281de`. `BaseSearchSchema` backs `MetadataSearchDto`, `SmartSearchDto`, `RandomSearchDto` and `StatisticsSearchDto` — i.e. `/search/metadata`, `/search/smart`, `/search/random`, `/search/statistics` — so a client can mark an asset "rejected" with `rating: -1` and then gets a 400 trying to filter for it. The validator searched for an alternative route (an `isRejected` flag, a separate query parameter, a saved-search mechanism) and found none: this rating filter is the only surface. Marking assets rejected so they can later be found is the entire reason `-1` exists.

Verified empirically by parsing candidate values through the real schemas:

```
UPDATE rating=-1 => ACCEPTED
SEARCH rating=-1 => REJECTED: ["Too small: expected number to be >=1"]
```

Before this diff both sides rejected `-1`, so the asymmetry is introduced here, not inherited.

**Fix:** restore the lower bound on the search filter and correct its now-false history entry:

```ts
// server/src/dtos/search.dto.ts:36
rating: z
  .int()
  .min(-1)
  .max(5)
  .nullish()
  .describe('Filter by rating [1-5], -1 (rejected) or null (unrated)')
```

The `x-immich-history` entry at `search.dto.ts:47` — `.updated('v3', 'Using -1 as a rating is no longer valid.')` — becomes false once the write path permits `-1`; it needs the same treatment the asset DTO's entry received. Regenerate the OpenAPI spec and clients afterwards.

### #2 🟠 High: The `.refine()` rewrite drops the rating range constraint from the generated OpenAPI contract

| | |
|---|---|
| **File** | `server/src/dtos/asset.dto.ts:16-23`; generated output in `open-api/immich-openapi-specs.json` (the `rating` property of `UpdateAssetDto` and `AssetBulkUpdateDto`) |
| **Category** | api-contract |
| **Confidence** | 100 (promoted on agreement) |
| **Screen** | 90 |
| **Validation** | confirmed |
| **Found by** | broad-reviewer (High), adversarial-reviewer (Medium — dissent recorded, highest severity kept) |

**Issue:** the old schema used `.min(1).max(5)`, which the zod→OpenAPI generator translated into `"minimum": 1, "maximum": 5`. A zod refinement emits no JSON Schema keywords, so the generator falls back to JS safe-integer bounds. The regenerated spec in this very diff publishes, for both DTOs:

```json
"description": "Rating in range [1-5], -1 (rejected) or null (unrated)",
"maximum": 9007199254740991,
"minimum": -9007199254740991,
```

The contract now contradicts its own description in the same object. Any consumer validating against the published spec — third-party clients, generated strict SDKs, form/UI generators, request validators — accepts `0`, `6`, `-50`, `1000000` as contract-valid and discovers the rejection only as a server 400.

`quick-reviewer` examined this and declined to flag it, arguing that unbounded `9007199254740991` fields already appear throughout the spec, making this a codebase-wide framework tradeoff. The validator settled that counter-argument by counting: the literal `9007199254740991` occurs **228 times in the base spec and 232 times after this diff** — a delta of exactly 4, i.e. the two new min/max pairs on precisely the two `rating` properties this diff touches. The pre-existing occurrences elsewhere are a separate pattern; they do not excuse a real, generator-honored bound being lost on this field.

**Fix:** express the constraint in a form the generator can carry:

```ts
rating: z
  .union([z.literal(-1), z.int().min(1).max(5)])
  .nullable()
  .optional()
  .describe('Rating in range [1-5], -1 (rejected) or null (unrated)')
  .meta({ ... })
```

`z.union` emits `anyOf` through `toJSONSchema`, which survives the project's OpenAPI 3.0 cleanup step. Note the alternative sometimes suggested — attaching `.meta({ minimum: -1, maximum: 5 })` alongside the refine — is *not* equivalent: it would advertise `0` as valid.

### #3 🟠 High: A user-set `rating: -1` is silently erased by the next metadata extraction

| | |
|---|---|
| **File** | `server/src/services/metadata.service.ts:308` |
| **Category** | data-loss / composition |
| **Confidence** | 75 |
| **Screen** | 82 |
| **Validation** | confirmed |
| **Found by** | adversarial-reviewer (High) |

**Issue:** the change restores `-1` on the write path only. `metadata.service.ts:308` still reads:

```ts
rating: exifTags.Rating === 0 ? null : validateRange(exifTags.Rating, 1, 5),
```

`git show 99281de -- server/src/services/metadata.service.ts` shows this line was `validateRange(exifTags.Rating, -1, 5)` before the commit being reverted, and that the same commit deleted the spec case `should handle valid negative rating value`. Neither is restored here.

The full round trip, every link independently re-derived from source by both a screener and the validator:

1. `server/src/services/asset.service.ts:498-527` — the API write calls `upsertExif({ …, lockedPropertiesBehavior: 'append' })`; `updateLockedColumns` (`server/src/utils/database.ts:520-524`) locks each written key present in `lockableProperties` (`server/src/database.ts:506-514`, which includes `'rating'`), then unconditionally queues `JobName.SidecarWrite`.
2. `metadata.service.ts:490-541` (`handleSidecarWrite`) writes `Rating: -1` into the XMP sidecar via `metadataRepository.writeTags` (`server/src/repositories/metadata.repository.ts:121`), then at line 539 calls `unlockProperties(asset.id, lockedProperties)`. `unlockProperties` (`server/src/repositories/asset.repository.ts:342-350`) is a durable SQL update removing `'rating'` from `asset_exif.lockedProperties` — not a transient marker.
3. `getExifTags` (`metadata.service.ts:580-621`) spreads sidecar tags last, so a later extraction reads `Rating: -1` back.
4. `metadata.service.ts:308` clamps it: `validateRange` (lines 106-116) returns `null` when `val < min`, so `-1` → `null`.
5. `metadata.service.ts:384-389` upserts with `lockedPropertiesBehavior: 'skip'`, but `rating` was unlocked in step 2, so the `skipLocked` case-expression falls through to `excluded.rating` and the `null` overwrites the stored `-1`.

The re-extraction trigger is ordinary, not contrived: the `REFRESH_METADATA` job (`server/src/dtos/asset.dto.ts:67`, `server/src/services/asset.service.ts:470`) is a user- and admin-exposed per-asset action, and external-library rescans hit the same path. The validator specifically looked for a config gate, an alternate lock source, or conditional sidecar writing that would break the chain, and found none.

Net effect: the user's "rejected" mark disappears from the database on the next metadata refresh, while the XMP sidecar still says `-1`.

**Fix:** restore the pre-`99281de` bound so the read path admits what the write path now accepts:

```ts
// server/src/services/metadata.service.ts:308
rating: exifTags.Rating === 0 ? null : validateRange(exifTags.Rating, -1, 5),
```

and restore the deleted `should handle valid negative rating value` case in `server/src/services/metadata.service.spec.ts`.

### Consistency

- **M1** — `server/src/dtos/exif.dto.ts:32` — **response schema still forbids the value the request schema now accepts.** `rating: z.int().min(1).max(5).nullish().default(null)` was tightened by `99281de` and not restored. `mapExif` (`exif.dto.ts:39-64`) passes `entity.rating` straight through and no controller applies `@ZodSerializerDto` (verified: only TODO comments reference it, and `ZodSerializerInterceptor` returns early when no response schema is registered), so there is **no runtime 500** — the defect is contract-level. After `PUT /assets/:id {rating:-1}` succeeds, `GET /assets/:id` returns `exifInfo.rating: -1`, which the published `ExifResponseDto` schema declares invalid (`minimum: 1`). Verified empirically: `ExifResponseSchema.safeParse({ rating: -1 })` fails with `Too small: expected number to be >=1`. Fix: `z.int().min(-1).max(5).nullish().default(null)` and regenerate. *(adversarial-reviewer, Medium; screen 78 — two points under the bar with a single finder)*

- **M2** — `server/src/schema/migrations/1780592070031-ConvertNegativeRatingToNull.ts` (deleted) — **deleting an already-applied migration will hard-fail server startup for any database that ran it.** The mechanism is certain and was verified directly, not inferred: Immich runs migrations through Kysely's `Migrator` + `FileMigrationProvider` (`server/src/repositories/database.repository.ts:509-522`); `Migrator.#getState` calls `#ensureNoMissingMigrations` **unconditionally** (`kysely@0.28.17/dist/cjs/migration/migrator.js:444-458`), which throws `corrupted migrations: previously executed migration <name> is missing` (line 491-498) when a `kysely_migrations` row has no matching file; `runMigrations()` rethrows it (`database.repository.ts:371-393`). There is no allowlist, baseline, or squash step in `createMigrator()` that would bypass this. The migration was added by `99281de` on 2026-06-04 and the base commit here is 2026-06-07, so it sat on mainline for ~3 days — every developer database and any main-tracking deployment migrated in that window carries the row and would fail to boot permanently. *(adversarial-reviewer, Critical; screen 40)*

  **Why this was tiered down rather than reported as Critical, stated plainly so you can overrule it.** The screen scored the *mechanism* certain but the *affected population* unverified, and it cited an in-repo precedent. I checked that precedent independently and it holds up: commit `0975b15` (`fix: remove stray migration (#28565)`) deleted `1773175313374-Test.ts`, which was a real schema change (`ALTER TABLE "workflow" ADD "updateId"`), added on 2026-05-18 and deleted on 2026-05-22 — four days on mainline, one day longer than this one. So the project has done exactly this before. What neither I nor any agent could establish is whether `99281de` reached a released or nightly build: **this clone has no git tags**, and no version bump appears between `99281de` and the base commit. If you know that a nightly or RC shipped in that window, this is a Critical and the fix is to keep the file with a no-op `up()` rather than delete it. `data-migration-reviewer` was dropped by the roster cap and is the agent that would normally settle this.
