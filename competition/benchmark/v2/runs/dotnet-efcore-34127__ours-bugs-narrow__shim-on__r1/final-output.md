**#1 — `SqlNullabilityProcessor.cs:626`**: `NullPropagatedOperands` recurses into every `SqlBinaryExpression` operator, including `AndAlso`/`OrElse`, which are three-valued in SQL and do not propagate NULL (`NULL AND FALSE` is `FALSE`). The guard is therefore dropped when its falsity is not implied, and the query yields `true`/`false` where it previously yielded NULL. Four probe queries over 18 rows mismatched at HEAD and matched at `051c33a79`. Notably, one unsafe `AndAlso` is generated by EF itself when expanding `a == b` on two nullable columns, so the shape does not require the user to write `&&`. `Coalesce` is reachable via `ISqlExpressionFactory.MakeBinary` with the same defect. Fix: an allow-list of genuinely null-propagating operators.

**#2 — `SqlNullabilityProcessor.cs:587`**: when `clause.Result` is a search condition, the removed `ELSE NULL` was what carried UNKNOWN into `bool?`. On SQL Server, `SearchConditionConvertingExpressionVisitor` later rewrites the collapsed predicate to `CASE WHEN <pred> THEN 1 ELSE 0 END`, which cannot produce NULL, so UNKNOWN becomes `false` — and in a predicate context the row set changes. Confirmed through generated SQL at both commits. SQLite happens to survive this shape, so a SQLite-only check would miss it.
