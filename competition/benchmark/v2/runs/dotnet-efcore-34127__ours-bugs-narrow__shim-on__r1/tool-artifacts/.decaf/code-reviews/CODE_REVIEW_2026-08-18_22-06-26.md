## Findings

### #1 🔴 Critical: `NullPropagatedOperands` treats `AndAlso`/`OrElse` as null-propagating, so a load-bearing `IS NOT NULL` guard is dropped

| | |
|---|---|
| **File** | `src/EFCore.Relational/Query/SqlNullabilityProcessor.cs:626` |
| **Category** | correctness |
| **Confidence** | 100 |
| **Verified** | executed |
| **Pre-existing** | no |
| **Found by** | solo-reviewer (Critical) |

**Issue:** The `else if (expression is SqlBinaryExpression binary)` arm recurses into `Left` and `Right` for *every* operator `SqlBinaryExpression.IsValidOperator` admits (`SqlBinaryExpression.cs:83-105`). That includes `AndAlso` and `OrElse`, which are three-valued in SQL and do **not** propagate NULL: `NULL AND FALSE` is `FALSE`, `NULL OR TRUE` is `TRUE`. Adding their operands to `nullPropagatedOperands` makes `DropNotNullChecks` delete a guard whose falsity is not implied by the result being non-NULL, so the query returns `true`/`false` where it previously returned NULL — in both projections and `WHERE` row sets, with no error.

**Evidence:** A standalone probe was built against `src/EFCore.Sqlite.Core` at HEAD and at the parent commit `051c33a79` (scratch `git worktree`, since removed), 18 rows over the cross-product of `NullableBoolA ∈ {true,false,null} × BoolA ∈ {true,false} × NullableIntA ∈ {10,1,null}`, comparing SQLite results against the same expression evaluated in memory.

| query | base SQL | HEAD SQL | HEAD result |
|---|---|---|---|
| `x.NullableBoolA != null ? (bool?)(x.NullableBoolA.Value \|\| x.BoolA) : null` | `CASE WHEN "NullableBoolA" IS NOT NULL THEN "NullableBoolA" OR "BoolA" ELSE NULL END` | `"NullableBoolA" OR "BoolA"` | **MISMATCH 3/18** — `db=True clr=NULL` |
| `... (x.NullableBoolA.Value && x.BoolA) ...` | `CASE WHEN ... THEN "NullableBoolA" AND "BoolA" ELSE NULL END` | `"NullableBoolA" AND "BoolA"` | **MISMATCH 3/18** — `db=False clr=NULL` |
| `... (bool?)!(x.NullableBoolA.Value \|\| x.BoolA) ...` | `CASE WHEN ... ELSE NULL END` | `NOT("NullableBoolA") AND NOT("BoolA")` | **MISMATCH 3/18** — `db=False clr=NULL` |
| `x.NullableIntA != null ? (bool?)(x.NullableIntA == x.NullableIntB) : null` | `CASE WHEN ... ELSE NULL END` | `"NullableIntA" = "NullableIntB" AND "NullableIntB" IS NOT NULL` | **MISMATCH 6/18** — `db=False clr=NULL` |

All four returned `MATCH (18 rows)` at the parent commit, so these are regressions introduced by this hunk. Raw SQL confirms the mechanism: `SELECT (NULL OR 1), (NULL AND 0)` returns `1 | 0`, not NULL.

Note the fourth row: the `AndAlso` there is **generated by EF itself** — it is the null-semantics expansion of `a == b` performed under the guard's `_nonNullableColumns` assumption. So the unsafe shape does not require the user to write `&&`; ordinary `==` on two nullable columns inside a null-propagating ternary produces it.

Latent, same root cause: `MakeBinary` (`SqlExpressionFactory.cs:394-421`) accepts `ExpressionType.Coalesce` and will build a `SqlBinaryExpression{Coalesce}`, which this arm would also traverse — unsound, since `COALESCE(a, b)` is non-NULL whenever `b` is. EF's own translator routes `??` to the `COALESCE` *function* (`RelationalSqlTranslatingExpressionVisitor.cs:450`), so no repro was constructible without a custom provider; the public `ISqlExpressionFactory.MakeBinary` surface makes it reachable for third parties. `And`/`Or`/`ExclusiveOr` are safe — `QuerySqlGenerator.cs:1097-1099` renders them as bitwise `&`/`|`/`^`, which do propagate NULL (confirmed: `!x.NullableBoolA.Value` becomes `[NullableBoolA] ^ CAST(1 AS bit)` and stays correct).

**Fix:** Restrict the binary recursion to operators that actually propagate NULL — e.g.

```csharp
else if (expression is SqlBinaryExpression
    {
        OperatorType: ExpressionType.Add or ExpressionType.Subtract or ExpressionType.Multiply
            or ExpressionType.Divide or ExpressionType.Modulo
            or ExpressionType.And or ExpressionType.Or or ExpressionType.ExclusiveOr
            or ExpressionType.Equal or ExpressionType.NotEqual
            or ExpressionType.LessThan or ExpressionType.LessThanOrEqual
            or ExpressionType.GreaterThan or ExpressionType.GreaterThanOrEqual
    } binary)
```

(an allow-list, so a future operator addition fails closed). The comparison operators in that list are only safe once finding #2 is also addressed.

### #2 🔴 Critical: collapsing the `CASE` when the result is a search condition turns UNKNOWN into `false`

| | |
|---|---|
| **File** | `src/EFCore.Relational/Query/SqlNullabilityProcessor.cs:587` |
| **Category** | correctness |
| **Confidence** | 100 |
| **Verified** | executed (SQL semantics + SQL generation; no SQL Server engine available) |
| **Pre-existing** | no |
| **Found by** | solo-reviewer (Critical) |

**Issue:** When `clause.Result` is a boolean-valued *predicate* rather than a value, the `ELSE NULL` arm of the `CASE` is what carries "unknown → NULL" into the projected `bool?`. Comparison operators (`=`, `<>`, `<`, `>`, …) do propagate three-valued UNKNOWN, so finding #1's fix does not cover them — but on providers that convert a search condition back to a bit value (SQL Server's `SearchConditionConvertingExpressionVisitor`, which runs *after* this processor), the collapsed expression becomes `CASE WHEN <pred> THEN CAST(1 AS bit) ELSE CAST(0 AS bit) END`, which **cannot produce NULL**. UNKNOWN silently becomes `false`. The same applies in a predicate context, where it changes the returned row set.

**Evidence:** SQL Server SQL generated via `ToQueryString()` (no connection needed) at HEAD vs. the parent commit `051c33a79`:

`x.NullableIntA != null ? (bool?)(x.NullableIntA > 5) : null`
- base: `CASE WHEN [e].[NullableIntA] IS NOT NULL THEN CASE WHEN [e].[NullableIntA] > 5 THEN CAST(1 AS bit) ELSE CAST(0 AS bit) END ELSE NULL END`
- HEAD: `CASE WHEN [e].[NullableIntA] > 5 THEN CAST(1 AS bit) ELSE CAST(0 AS bit) END`

For a row with `NullableIntA IS NULL`, `NULL > 5` is UNKNOWN, the `WHEN` is not satisfied, and the projection yields `0` (`false`) where the LINQ expression specifies `null`. CASE semantics were executed directly to confirm UNKNOWN falls to `ELSE`: `SELECT CASE WHEN (NULL = 1) THEN 1 ELSE 0 END, CASE WHEN (NULL > 5) THEN 1 ELSE 0 END` returns `0 | 0`. The same collapse was observed for `x.NullableBoolA != null ? (bool?)(x.NullableBoolA.Value == x.BoolA) : null`.

This also bites in a predicate context — `Where(x => (x.NullableBoolA != null ? (bool?)(x.NullableBoolA.Value || x.BoolA) : null) == true)` goes from a `CASE … ELSE NULL END = CAST(1 AS bit)` (which excludes the NULL rows) to a bare `[NullableBoolA] = CAST(1 AS bit) OR [BoolA] = CAST(1 AS bit)`, which admits rows where `NullableBoolA IS NULL AND BoolA = 1`.

This case is provider-dependent: on SQLite the same shape happens to survive (`SELECT "NullableIntA" > 5` yields NULL), which is why a SQLite-only check would miss it. SQL Server is the provider whose baselines this change updates.

**Fix:** Refuse the optimization when the result is a search condition. The cheapest reliable guard is to require the result to be a non-boolean value expression before entering the block, e.g. add `&& clause.Result.Type != typeof(bool) && clause.Result.Type != typeof(bool?)` to the condition at line 578 — or, more precisely, skip when `clause.Result` is a `SqlBinaryExpression` with a comparison/logical operator, a `SqlUnaryExpression { OperatorType: Not }`, `LikeExpression`, `InExpression`, or `ExistsExpression`. Whichever form is chosen, a test with a boolean-valued result is needed; none of the five new tests exercises one.
