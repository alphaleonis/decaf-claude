## Findings

### #1 🟠 High: subquery samples are counted twice in `SamplesRead`

| | |
|---|---|
| **File** | `promql/engine.go:1874` (with `promql/engine.go:2184`) |
| **Category** | correctness |
| **Confidence** | 100 |
| **Verified** | executed |
| **Found by** | solo-reviewer (High) |
| **Pre-existing** | no |

**Issue:** `evalSubquery` now merges the subquery's `SamplesRead` into the parent, but the subquery's
result is then re-read by the matrix-selector range-eval path, which increments `SamplesRead` again
for the same points. The pre-change code used `NewChild()` precisely to avoid this — its comment said
"Avoid double counting samples when running a subquery, those samples will be counted in later stage"
(`promql/engine.go:1867-1869` before the change). That later stage still runs, so every subquery's
I/O is counted twice.

Consequences: `prometheus_engine_query_samples_read_total` and the `samplesRead` API field are roughly
2× the true read count for every subquery; `SamplesRead` can exceed `TotalSamples`, inverting the
relationship the change is built on; and for instant queries `SamplesRead != TotalSamples`,
contradicting the change's own documented rule.

**Evidence:** executed against the change (probe using `promqltest.LoadedStorage` with `m 1+1x100` at
10 s resolution, per-step stats on):

```
count_over_time(m[1m:10s])   @201s instant  total=6   read=12
max_over_time(m[20s:10s])    @201s instant  total=2   read=4
sum_over_time(m[30s:30s])    @90s  instant  total=1   read=2
sum_over_time(m[10s:10s])    201–400s/5s    total=40  read=41   <-- read > total
sum_over_time(sum_over_time(m[1m:10s])[2m:30s]) @201s  total=4  read=36
```

Traced arithmetic for `count_over_time(m[1m:10s])` @201 s: the subquery evaluates 6 steps
(150 s…200 s), reading 1 sample each → child `SamplesRead=6`, merged at `engine.go:1874`. The 6
in-memory points are then walked by the range-eval path, which adds 6 more at `engine.go:2184` → 12.
True storage reads: 6. `TotalSamples=6` — i.e. the *old* counter is exact here and the new one is 2×
wrong.

Counter-argument considered: `promql/engine_test.go:1548` documents the value as intended
(`SamplesRead: 2, // subquery + outer`), and `promql/engine.go:1863-1864` documents the merge. But the
merge is what makes `read (41) > total (40)` for `sum_over_time(m[10s:10s])` and breaks the rule stated
at `docs/feature_flags.md:48`; the author's intent is not self-consistent, so the decision needs to be
revisited rather than parked.

**Fix:** pick one owner of the subquery's reads. Either drop
`parentSamplesStats.MergeSamplesReadFromSubquery(ev.samplesStats)` at `engine.go:1874` (letting the
range-eval path at `engine.go:2184` count the materialized points, which already applies the correct
per-step delta), or keep the merge and suppress the `IncrementSamplesReadAtStep` for a selector whose
`Series` came from `evalSubquery`. The first is the smaller change and preserves the delta semantics
for the outer window. Note that the direct `*parser.SubqueryExpr` case (`engine.go:2426-2447`) is *not*
double-counting — `m[20s:10s]` correctly reports `total=2 read=2` — so only the `evalSubquery` merge
needs to go.

### #2 🟠 High: every subquery now eagerly allocates 16 bytes per subquery step, before any sample limit applies

| | |
|---|---|
| **File** | `promql/engine.go:2397` (with `util/stats/query_stats.go:306-308`) |
| **Category** | production |
| **Confidence** | 100 |
| **Verified** | executed |
| **Found by** | solo-reviewer (High) |
| **Pre-existing** | no |

**Issue:** `stats.NewChildWithStepTracking(..., subqStart, subqEnd, subqInterval)` calls
`InitStepTracking`, which allocates **two** `[]int64` of `numSteps` where
`numSteps ≈ (queryRange + subqueryRange) / subqueryStep`. Previously the subquery child was
`NewChild()` → `NewQuerySamples(false)`, which allocated nothing. The allocation happens before the
subquery is evaluated, so `query.max-samples` cannot stop it, and `TotalSamplesPerStep` is allocated
too even though a subquery child's total-samples stats are never read
(`MergeSamplesReadFromSubquery` merges only the read fields).

`subqueryStep` is fully attacker-controlled in the expression (`[<range>:<step>]`) and has no lower
bound beyond 1 ms, so the allocation is unbounded and scales linearly with the requested subquery
range.

**Evidence:** executed. Probe with `MaxSamples=10`, so the query is rejected almost immediately in
both revisions. `totalAlloc` delta across `qry.Exec`:

| query | this change, per-step on | base `efbdc3f8`, per-step on |
|---|---|---|
| `count_over_time(m[10m:1ms])` | 9.2 MiB | 0.1 MiB |
| `count_over_time(m[1h:1ms])` | 55.0 MiB | 0.1 MiB |
| `count_over_time(m[6h:1ms])` | 329.7 MiB | (not run) |

(Base measured in a throwaway `git worktree` at `efbdc3f8`, since removed; HEAD never moved on this
checkout.) Linear at ~16 B/step: `[24h:1ms]` ⇒ ≈1.3 GiB, `[30d:1ms]` ⇒ ≈40 GiB, all allocated before
the sample limit is consulted. Gated behind `--enable-feature=promql-per-step-stats` **and**
`stats=all`, but once an operator enables the flag any query author can trigger it.

**Fix:** bound or avoid the allocation. Options: (a) do not allocate `TotalSamplesPerStep` for
subquery children (split `InitStepTracking` so read-only children get one slice); (b) cap `numSteps`
for the subquery child and fall back to the scalar-only `IncrementSamplesReadAtTimestamp` path at
`engine.go:2446` above the cap; (c) attribute subquery reads without a per-step child at all — the
loop at `engine.go:2429-2443` only needs, per subquery step, the outer step index, which can be
accumulated into the parent's slice directly as the subquery is evaluated.

### #3 🟡 Medium: the new test cases encode the double-counted values, so they cannot fail for the defect

| | |
|---|---|
| **File** | `promql/engine_test.go:1548` (also `1544`, `1432`, `1453`, `1474`, `1495`, `1516`, `2163`) |

**Issue:** The ~1100 new lines of table entries were populated from observed output rather than derived
from the intended semantics, and the comments say so:
`TotalSamples: 1, // Actual behavior: single step shows 1 effective sample`,
`SamplesRead: 2, // subquery + outer`, `// Single inner step (step = range) - corrected values`, and
five instances of `// steps after last outer → last step`. Because the expected value *is* the double

if the defect were fixed. A characterization test is not worthless, but this one is presented as a

**Evidence:** executed — `go test ./promql/ -run TestQueryStatistics` is green with the double count in

### #4 🟡 Medium: both docs pages state two properties of `samplesRead` that the implementation does not have

| | |
|---|---|
| **File** | `docs/feature_flags.md:48` (also `docs/querying/api.md:247`) |
| **Category** | production |
| **Confidence** | 100 |
| **Verified** | executed |
| **Found by** | solo-reviewer (Medium) |
| **Pre-existing** | no |

**Issue:** Two claims are false as written:

1. *"For other query types, this equals totalQueryableSamples."* Executed: instant query
   `max_over_time(m[20s:10s])` → `totalQueryableSamples=2`, `samplesRead=4`; `count_over_time(m[1m:10s])`
   → 6 vs 12. (Consequence of #1.)
2. *"Total number of samples **read** (I/O)."* For instant vector selectors the counter is incremented
   once per step with no de-duplication (`promql/engine.go:1818`, `promql/engine.go:1841`,
   `promql/engine.go:2578`), so lookback-overlapped re-reads are counted repeatedly. Executed: `m` as a
   range query 201–220 s at 5 s steps reports `samplesRead=4`, while the engine reads two distinct
   samples (t=200 s serves steps 201 s and 206 s; t=210 s serves 211 s and 216 s). An operator comparing
   `prometheus_engine_query_samples_total` against `prometheus_engine_query_samples_read_total` will read
   the gap as "I/O avoided", which is only true for range-vector windows.

**Evidence:** as above, from the executed probe table. The metric help string at `promql/engine.go:428`
is more careful ("only new points per step for range-vector") than the prose docs, which is the
inconsistency.

**Fix:** fix #1, then reword both bullets to scope the guarantee precisely: `samplesRead` de-duplicates
only the per-step window overlap of range-vector selectors and is otherwise identical to
`totalQueryableSamples`; it is not a storage-read count. Consider whether the metric name
`query_samples_read_total` should instead say something like "window-deduplicated" to avoid the I/O
reading.

### #5 🟢 Low: the new increment helpers silently drop out-of-range steps where their siblings panic

| | |
|---|---|
| **File** | `util/stats/query_stats.go:352` (also `:365`) |
| **Category** | correctness |
| **Confidence** | 75 |
| **Verified** | traced |
| **Found by** | solo-reviewer (Low) |
| **Pre-existing** | no |

**Issue:** `IncrementSamplesReadAtStep` guards with `i < len(qs.SamplesReadPerStep)` and
`IncrementSamplesReadAtTimestamp` with `i >= 0 && i < len(...)`, while the pre-existing
`IncrementSamplesAtStep` (`:320`) and `IncrementSamplesAtTimestamp` (`:339`) index unchecked and panic.
The scalar `SamplesRead` is incremented *before* the guard, so any out-of-range index yields
`SamplesRead != sum(SamplesReadPerStep)` — a silent, unattributable divergence between the two
representations the API exposes side by side, rather than a detectable failure.
`IncrementSamplesReadAtStep` is also missing the `i >= 0` check its timestamp sibling has, so a negative
index writes out of bounds instead of being skipped.

**Evidence:** traced. Not reachable today: the two call sites that could produce a bad index are
`engine.go:2184` (`step` bounded by the range-eval loop) and `engine.go:2472` (literal `0`), and
`InitStepTracking` cannot produce `numSteps <= 0` (see Considered But Not Flagged). The defect is that
the guard converts a future indexing mistake — for example a change to the clamp at
`engine.go:2440-2442` — into inconsistent published statistics with no signal.

**Fix:** either match the siblings and let a bad index panic, or increment the scalar only on the path
that also updates the slice so the two can never diverge. Add the missing `i >= 0` to
`IncrementSamplesReadAtStep`.

## Minor Findings

### Consistency

- `promql/engine.go:2437` — the outer-step index mixes sources: the base comes from the evaluator
  (`ev.startTimestamp`) while the stride comes from the stats object (`ev.samplesStats.Interval`).
  Traced equal on every reachable path (query-level `InitStepTracking` at `engine.go:815`/`875`,
  `NewChildWithStepTracking` in `evalSubquery`, and the subquery evaluator's own child), but the pairing
  is fragile and the correct partner for `ev.startTimestamp` is `ev.interval`. Use one source
  consistently, or assert `ev.samplesStats.StartTimestamp == ev.startTimestamp`. (solo-reviewer)
- `promql/value.go:195-206` — `countSamplesAfter` scans both slices front-to-back, but
  `floats`/`histograms` are time-ordered and the new points are always at the tail, so a reverse scan
  with an early `break` is O(new) instead of O(window). The per-step `call()` is already O(window), so
  this is a constant-factor cost, not an order change — but it is free to avoid. (solo-reviewer)
- `util/stats/query_stats.go:412` — `NewChildWithStepTracking` is a package function while `NewChild`
  (`:400`) is a method; that asymmetry is the only reason the `StepTrackingEnabled()` accessor at `:313`
  had to be added. A method
  `func (qs *QuerySamples) NewChildWithStepTracking(start, end, interval int64)` with the existing
  nil-receiver guard would need neither. (solo-reviewer)

### Testing Gaps

- `util/stats/stats_test.go:53-69` — `MergeSamplesReadFromSubquery`, `NewChildWithStepTracking`,
  `SamplesReadPerStepMap`, and `StepTrackingEnabled` have no direct unit tests; the only addition is two
  `IncrementSamplesReadAtTimestamp` calls. `MergeSamplesReadFromSubquery`'s length-mismatch branch
  (`min(len(parent), len(child))`, which drops the child's tail while adding its scalar in full) is
  untested and would silently break the scalar/per-step invariant if the layouts ever diverge.
  (solo-reviewer)
- `promql/value.go:195` — `countSamplesAfter` has no unit test; in particular the strict-`>` boundary
  (a point at exactly `cutoff`) is only exercised indirectly. (solo-reviewer)
- `promql/engine.go:2151-2157` — the `selVS.Anchored` / `selVS.Smoothed` branches shift `mint`/`maxt`,
  and the new `maxt - ev.interval` cutoff depends on that shift being applied identically at every step.
  Traced correct for both modifiers, but no new test case covers a `smoothed`/`anchored` selector's
  `SamplesRead`. (solo-reviewer)
