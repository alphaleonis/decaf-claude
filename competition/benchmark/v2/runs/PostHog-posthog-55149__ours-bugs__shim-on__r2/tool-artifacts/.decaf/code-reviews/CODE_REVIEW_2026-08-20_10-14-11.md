### #1 🔴 Critical: `override_flags_definitions` is accepted on the public `/flags` endpoint with no internal-request gate

| | |
|---|---|
| **File** | `rust/feature-flags/src/handler/mod.rs:196` |
| **Category** | security |
| **Confidence** | 100 |
| **Verified** | traced |
| **Pre-existing** | no |

**Issue:** `request.override_flags_definitions` is passed straight into `fetch_and_filter` with no authorization check, on the endpoint whose only credential is the project's *public* `phc_` token (embedded in every PostHog-instrumented web page). `flags.rs:151-186` then replaces the entire server-side `FeatureFlag` — `id`, `team_id`, `key`, `filters`, `active`, `deleted`, `ensure_experience_continuity`, `bucketing_identifier` — with caller-supplied JSON. Note the contrast four lines below: `detailed_analysis`, which only *adds explanatory output*, **is** gated behind `authentication::is_internal_request(&context)` at `mod.rs:218`. The far more powerful capability is the ungated one.

**Evidence:** Three concrete consequences were traced:

1. **Attacker-controlled regexes compiled and executed server-side.** `fetch_and_filter` calls `flag_list.prepare_regexes()` (`flags.rs:234`) *after* applying overrides, feeding arbitrary patterns into `fancy_regex::RegexBuilder` (`flags/property_filter.rs:70`) — a backtracking engine. `REGEX_BACKTRACK_LIMIT` bounds each match, but compilation and matching cost is now caller-chosen on PostHog's highest-QPS public endpoint.
2. **Induced Postgres writes on the persons writer.** `has_experience_continuity()` (`flag_operations.rs:47`) reads `ensure_experience_continuity` from the now attacker-supplied definition; `flag_matching.rs:486-513` uses it to decide `do_hash_key_lookup`, and `process_hash_key_override` (`flag_matching.rs:634-651`) calls `set_feature_flag_hash_key_overrides` against `router.get_persons_writer()`. `skip_writes` is only forced true when `detailed_analysis` (gated → always `Some(false)` externally) or `only_use_override_person_properties` is set (`flags.rs:336-338`), so an override sent *without* that query param leaves writes enabled. A caller can therefore drive inserts into `posthog_featureflaghashkeyoverride` for a team that owns no experience-continuity flag at all, varying `distinct_id`/`$anon_distinct_id` per request.
3. **Evaluation-metadata desync.** `evaluation_metadata.dependency_stages` and `transitive_deps` were computed by Django for the original flag IDs; `*flag = override_flag` (`flags.rs:172`) can change `flag.id` and `flag.team_id`, after which `filtered_out_flag_ids` (`flags.rs:198`) and the stage graph disagree about which flag is which.

**Fix:** Gate the override the same way its sibling is gated — refuse `override_flags_definitions` unless `authentication::is_internal_request(&context)`, e.g. pass `request.override_flags_definitions.as_ref().filter(|_| authentication::is_internal_request(&context))`, and reject (rather than silently ignore) an override on a non-internal request so the Python caller sees a hard failure. Additionally, preserve the original `id`/`team_id` when applying an override instead of replacing the whole struct, and cap the override map size.

### #2 🟠 High: `only_use_override_person_properties` skips all DB preparation, silently breaking cohort- and group-based conditions

| | |
|---|---|
| **File** | `rust/feature-flags/src/flags/flag_matching.rs:827` |
| **Category** | correctness |
| **Confidence** | 100 |
| **Verified** | traced |
| **Pre-existing** | no |

**Issue:** The new `|| self.only_use_override_person_properties` disjunct short-circuits `prepare_evaluation_state_if_needed` entirely. The pre-existing `flags_requiring_db_preparation.is_empty()` arm was safe because `requires_db_preparation` (`flag_operations.rs:37-40`) returns true for *cohort filters and group-typed flags*, not just person properties. Bypassing it unconditionally skips `prepare_flag_evaluation_state`, which is the only place `set_cohorts`, `initialize_group_type_mappings_if_needed`, and `prepare_group_data` are called (`flag_matching.rs:2004-2051`).

**Failure scenario:** A flag whose condition is `{"type": "cohort", "key": "id", "value": 42}` is evaluated through the new `test_evaluation` endpoint with a `timestamp` (which sets `only_use_override_person_properties=true`, `feature_flag.py:3545`). `flag_evaluation_state.cohorts` is never populated, so `flag_matching.rs:1591-1594` hits `None => return Ok((false, FeatureFlagMatchReason::NoConditionMatch))`. The endpoint reports the flag as **off with reason `no_condition_match`**, with no error flag set — indistinguishable from a genuine non-match. Group-aggregated flags degrade the same way: `group_type_mapping` stays `None` and `group_properties` stays empty.

**Evidence:** All three call sites traced. The stated goal of the flag ("ignore DB person properties") is already fully achieved by the separate change at `flag_matching.rs:1696-1704`, which starts `merged_properties` from an empty map. The `827` short-circuit is not needed for that goal and is what causes the loss.

**Fix:** Drop `|| self.only_use_override_person_properties` at line 827. `get_person_properties` already ignores DB person properties when the flag is set; keeping DB preparation only costs one avoidable person-property fetch while preserving cohort and group data. If that fetch must be avoided, pass a "skip person properties only" signal into `prepare_flag_evaluation_state` instead of skipping it wholesale.

### #3 🟠 High: Response serializer rejects `value: null`, returning HTTP 500 for any flag with an `is_set`/`is_not_set` condition

| | |
|---|---|
| **File** | `posthog/api/feature_flag.py:1961` |
| **Category** | correctness |
| **Confidence** | 100 |
| **Verified** | executed |
| **Pre-existing** | no |

**Issue:** `FeatureFlagConditionPropertyAnalysisSerializer.value` is `serializers.JSONField(...)` without `allow_null=True`. The Rust side emits `value: null` whenever a property filter has no value — `api/types.rs:709` does `property.value.clone().unwrap_or(serde_json::Value::Null)`, and `properties/property_models.rs:76-77` documents exactly when that happens: *"if a property filter is of type is_set or is_not_set, the value isn't used, and if it's a filter made by the API, the value is None."* DRF's `Field.validate_empty_values` fails on `None` when `allow_null` is False, so `is_valid(raise_exception=True)` at `feature_flag.py:3600` raises, and the blanket `except Exception` at `3603` converts it into `500 {"error": "Failed to evaluate flag"}`.

**Failure scenario:** POST `/api/projects/<id>/feature_flags/<id>/test_evaluation/` for a flag whose only condition is `email is_set`. Detailed analysis succeeds in Rust, then the Python response serializer rejects its own payload → 500. The bug manifests *only when the feature is correctly configured* (see #6), so it is invisible until `INTERNAL_REQUEST_TOKEN` is deployed.

**Evidence:** Reproduced against the pinned `djangorestframework==3.16.1` with the exact serializer definitions from lines 1955-1995 and a representative Rust payload:

```
DRF 3.16.1
is_valid: False
errors: {'conditions': [{'properties': [{'value': [ErrorDetail(string='This field may not be null.', code='null')]}]}]}
```

Changing only `value` to `allow_null=True` makes the same payload validate.

**Fix:** `value = serializers.JSONField(allow_null=True, help_text="Expected property value")`. Also consider narrowing the `except Exception` at `3603` so a response-shape bug does not present as a generic evaluation failure.

### #4 🟠 High: `rollout_excluded` only detects 0% rollout, so partial-rollout exclusions get a flatly wrong explanation

| | |
|---|---|
| **File** | `rust/feature-flags/src/api/types.rs:652` |
| **Category** | correctness |
| **Confidence** | 100 |
| **Verified** | traced |
| **Pre-existing** | no |

**Issue:** `is_zero_rollout = rollout_percentage == 0.0` gates every branch that can set `this_condition_rollout_excluded` (`types.rs:675-686`). A user excluded by a 30% rollout therefore gets `rollout_excluded: false`, and falls through to the wrong explanation string.

**Failure scenario:** Flag with a single condition: `email icontains "@acme.com"`, rollout 30%. A user matching the property but hashing outside the bucket produces `FeatureFlagMatch { matches: false, reason: OutOfRolloutBound, condition_index: Some(0) }`. Tracing `build_condition_analysis`:

- `properties_matched_but_rollout_failed = true`, `condition_index = Some(0)` → `index == 0 && is_zero_rollout` → `is_zero_rollout` is `false` (0.30 ≠ 0.0) → `this_condition_rollout_excluded = false`.
- `condition_matched = false` (because `flag_match.matches` is false, `types.rs:557`), `all_properties_matched = true`.
- Explanation branch order (`types.rs:688-706`) lands on: **"Condition 0 matched properties but was not evaluated due to an earlier condition matching"** — there is no earlier condition, and the real cause is the rollout.

The emitted `rollout_excluded: false` also directly contradicts the top-level `reason: "out_of_rollout_bound"` returned in the same response. Explaining exactly this case is the feature's raison d'être.

**Evidence:** Traced against `FeatureFlagMatchReason::OutOfRolloutBound` (`flag_match_reason.rs:12-13`) and `FeatureFlagMatch.condition_index: Option<usize>` (`flag_matching.rs:106`).

**Fix:** Drive rollout exclusion from the match reason and index rather than a zero-percent test: when `flag_match.reason == OutOfRolloutBound` and `flag_match.condition_index == Some(index)`, set `rollout_excluded = true` regardless of percentage. Keep the `is_zero_rollout` path only as the fallback when `condition_index` is `None`. Also add an explanation arm for "no earlier condition matched" so the "earlier condition" string is only produced when an earlier condition actually matched.

### #5 🟠 High: `feature_flag:read` scope now returns arbitrary persons' full property blobs

| | |
|---|---|

| **Category** | security |

**Issue:** `test_evaluation` is declared `required_scopes=["feature_flag:read"]`, and its response includes `person_properties` (`feature_flag.py:3595`), which on the non-timestamp path is `person.properties or {}` (`feature_flag.py:3462`) — the complete person property document, typically containing `email`, `name`, and arbitrary customer-set PII. **Failure scenario:** A personal API key scoped to `feature_flag:read` only (a natural grant for a flag-management integration or a third-party tool) can POST `{"distinct_id": "<any id>"}` to this endpoint for any flag in the project and read that person's full property blob, one distinct_id at a time. **Evidence:** Traced the decorator's `required_scopes` against `posthog/scopes.py`'s separate `person` scope object. A scoped-key request was not executed, hence anchor 75 rather than 100.

**Fix:** Require both scopes (`required_scopes=["feature_flag:read", "person:read"]`), or omit `person_properties` from the response unless `person:read` is held. If the properties are needed for the debugging UI, returning only the keys referenced by the flag's own conditions would satisfy the use case without a blanket PII read.
