### #1 🔴 Critical: A `-1` rating set through the widened API is silently reset to `null` by the sidecar-write → re-extract chain

| | |
|---|---|
| **File** | `server/src/services/metadata.service.ts:308` |
| **Category** | data-model / error-handling |
| **Confidence** | 100 |
| **Screen** | 90 |
| **Validation** | confirmed (validator corrected `pre_existing` → `false`) |
| **Found by** | adversarial-reviewer (Critical), design-reviewer (High), quick-reviewer (High), broad-reviewer (Medium, as pre-existing) |

**Issue:** `asset.dto.ts` now accepts `rating: -1`, but the metadata-extraction path still clamps to
`[1,5]`, and the write path automatically routes every manual rating edit back through that path.
The full chain, verified line by line:

1. `PATCH/PUT /assets/:id {rating:-1}` → `AssetService.updateExif` (`server/src/services/asset.service.ts:520-527`)
   upserts with `lockedPropertiesBehavior: 'append'`, which locks `rating`, then queues `JobName.SidecarWrite`.
2. `MetadataService.handleSidecarWrite` (`server/src/services/metadata.service.ts:491-541`) writes
   `Rating: -1` into the XMP sidecar (`:509`), registers a Sidecar file record if none exists, then
   calls `unlockProperties(asset.id, lockedProperties)` at `:539` — **releasing the `rating` lock**.
3. `JobService` `onDone` for `SidecarWrite` (`server/src/services/job.service.ts:75-81`) queues
   `JobName.AssetExtractMetadata`.
4. `handleMetadataExtraction` re-fetches the asset, `getExifTags` (`:580-588`) merges sidecar tags
   over media tags so `exifTags.Rating === -1`, and line 308 computes
   `validateRange(exifTags.Rating, 1, 5)` → `null` (`validateRange` returns `null` when `val < min`,
   `:107-118`). Its `upsertExif` uses `lockedPropertiesBehavior: 'skip'` (`:389`) — which no longer
   protects `rating`, because step 2 unlocked it.

Net effect: `asset_exif.rating` becomes `NULL`. Ratings `1..5` survive the identical loop; only `-1`
does not. Empirically confirmed that the sidecar write does not fail and the value round-trips: a
probe run with the installed `exiftool-vendored` wrote `Rating: -1` to an XMP file and read it back
as the number `-1`, so step 4 really does see `-1`.

The same line also drops a `-1` `xmp:Rating` authored by other tools (the standard "rejected" value)
on import. And the bulk path (`asset.service.ts:180`) multiplies the cost: `rating:-1` over N assets
produces N sidecar writes plus N extractions for zero net effect.

**On `pre_existing`:** the validator settled the dissent. `git show 99281de` shows this bound was
tightened from `-1` to `1` *in lockstep with* the DTO rejecting `-1`, so the cascade was unreachable
and harmless before. This change reopens the DTO without reopening the extraction bound, making the
regression newly reachable — the line is textually unchanged, but the invariant its correctness
rested on is what this change deliberately breaks.

**Fix:** Restore the pre-`99281de` bound as part of this change.

```ts
// server/src/services/metadata.service.ts:308
rating: exifTags.Rating === 0 ? null : validateRange(exifTags.Rating, -1, 5),
```

Better still, derive both this bound and the DTO's from one shared definition (see P1) so the write
and ingest boundaries cannot drift apart again.

### #2 🔴 Critical: Deleting the already-shipped `ConvertNegativeRatingToNull` migration makes the server fail to boot on any instance that ran it

| | |
|---|---|
| **File** | `server/src/schema/migrations/1780592070031-ConvertNegativeRatingToNull.ts` (deleted in `6c9a6e7`) |
| **Category** | data-migration |
| **Confidence** | 100 |
| **Screen** | 85 |
| **Validation** | confirmed |
| **Found by** | broad-reviewer (Critical), data-migration-reviewer (Critical), adversarial-reviewer (Critical), design-reviewer (Medium) |

**Issue:** Kysely's `Migrator.#ensureNoMissingMigrations`
(`node_modules/.pnpm/kysely@0.28.17/.../migration/migrator.js:491-498`) throws
`corrupted migrations: previously executed migration <name> is missing` for any name recorded in
`kysely_migrations` whose file is gone. It is called from `#getState` at `:447`, **before** the
`allowUnorderedMigrations` gate at `:448`, so immich's dev-only `allowUnorderedMigrations`
(`server/src/repositories/database.repository.ts:514`) cannot suppress it.
`runMigrations()` rethrows the captured error (`database.repository.ts:388-391`), and
`DatabaseService.onBootstrap` awaits it unguarded (`server/src/services/database.service.ts:114-117`)
from Nest's `onModuleInit` (`server/src/app.module.ts:95`), so the process fails to start —
repeatedly, on every restart, until someone hand-edits the database.

Because the throw happens before `pendingMigrations` is computed, **every** later migration is
blocked too, including the already-present `1780592071031-AssetOcrSync.ts` and anything shipped
after it.

Exposure: the migration landed on `main` in `99281de` (2026-06-04) and is deleted here (2026-06-07),
and `.github/workflows/docker.yml` publishes a `main`-tagged server image on every push to `main` —
so instances tracking `main`, plus every contributor database, executed it inside that window.
`database.skipMigrations` defaults to `false` (`server/src/repositories/config.repository.ts:310`),
and the validator found no documentation scoping `main`-channel instances out of support.

**Counter-evidence, and why it does not clear this.** `0975b15` ("fix: remove stray migration",
#28565) deleted `1773175313374-Test.ts` after a 4-day window on `main`, so the project has done this
before. The validator read that diff: it removed a scratch file literally named `Test` that added a
column to the brand-new `workflow` table introduced four days earlier — not a data migration that
had already mutated user data. It establishes that the practice has happened, not that the
boot-crash mechanism was considered.

**Fix:** Keep the file. Its `up()` is a one-shot `UPDATE` that will never run again on an instance
that recorded it, so leaving it in place costs nothing and keeps the name resolvable:

```ts
// server/src/schema/migrations/1780592070031-ConvertNegativeRatingToNull.ts
import { Kysely, sql } from 'kysely';

export async function up(db: Kysely<any>): Promise<void> {
  await sql`UPDATE "asset_exif" SET "rating" = NULL WHERE "rating" = -1;`.execute(db);
}

export async function down(): Promise<void> {
  // not supported
}
```

An empty `up()` also works if the statement must be neutralized for fresh installs. If deletion is
genuinely intended, it needs a release note carrying the manual step
`DELETE FROM kysely_migrations WHERE name = '1780592070031-ConvertNegativeRatingToNull';`.

**Issue:** `BaseSearchSchema.rating` remains `z.int().min(1).max(5).nullish()`, and it feeds

### #6 🟡 Medium: `.refine()` erases the valid range from the machine-readable contract

| | |
|---|---|
| **File** | `server/src/dtos/asset.dto.ts:16` |
| **Category** | api-contract / type-safety |
| **Confidence** | 100 |
| **Screen** | 100 |
| **Validation** | waived — corroborated ×5, all at anchor 100 |
| **Found by** | quick-reviewer, broad-reviewer, adversarial-reviewer, design-reviewer, typescript-reviewer (all Medium) |

**Issue:** `z.toJSONSchema` cannot see refinements, so moving the constraint out of `.min()/.max()`
and into `.refine()` degrades the emitted contract from `minimum: 1, maximum: 5` to
`minimum: -9007199254740991, maximum: 9007199254740991`. Verified directly against the installed
`zod@4.3.6`, and visible in every committed artifact — `open-api/immich-openapi-specs.json` for both
`UpdateAssetDto` and `AssetBulkUpdateDto`, and `mobile/openapi/lib/model/update_asset_dto.dart`,
whose doc comment now reads `Minimum value: -9007199254740991`.

The real domain now lives only in the `describe()` string and the refine's error message. A
spec-driven consumer sees `0` as in range and sends it — and `0` is exactly the value a tool
round-tripping XMP will naturally send back, since immich's own sidecar writer emits `Rating: 0` for
unrated (`metadata.service.ts:509`) — and gets a 400 the machine-readable contract gave it no way to
anticipate.

**Fix:** Either of these preserves behavior *and* the emitted bounds (both checked against
`zod@4.3.6`):

```ts
// minimal change — keeps the numeric keywords, refine only excludes 0
rating: z.int().min(-1).max(5).nullable()
  .refine((v) => v !== 0, { error: 'Must be -1, a number from 1 to 5, or null' })
  .optional()

// or state the domain exactly — emits enum: [-1,1,2,3,4,5]
rating: z.literal([-1, 1, 2, 3, 4, 5]).nullable().optional()
```

The first emits `minimum: -1, maximum: 5`; the second an explicit enum. Both accept
`{undefined, null, -1, 1..5}` and reject `0`, `7`, `-2`, `3.5` — the same set as the shipped refine.

### #7 🟡 Medium: One published spec now contradicts itself about `-1` in four places

| | |
|---|---|
| **File** | `server/src/dtos/asset.dto.ts:28` (emitted into `open-api/immich-openapi-specs.json`) |
| **Category** | api-contract / documentation |
| **Confidence** | 100 |
| **Screen** | 80 |
| **Validation** | waived — quotable fact, verified directly against the committed spec |
| **Found by** | design-reviewer (Medium) — unique |

**Issue:** Extracting every `rating` property from the committed spec shows a single document making
mutually exclusive claims about one domain field:

| schema | min / max | `x-immich-history` says |
|---|---|---|
| `UpdateAssetDto`, `AssetBulkUpdateDto` | ±9007199254740991 | "Using **0** as a rating is no longer valid." |
| `MetadataSearchDto`, `RandomSearchDto`, `SmartSearchDto`, `StatisticsSearchDto` | 1 / 5 | "Using **-1** as a rating is deprecated…" and "Using **-1** as a rating is no longer valid." |
| `ExifResponseDto` | 1 / 5 | — |

A client reading this spec is told simultaneously that `-1` is valid (update) and no longer valid
(search). That is the visible surface of #3 and #4, but it is a distinct artifact: the history
metadata is the API changelog consumers migrate against, and it is now wrong in the spec as shipped.

Separately, and more weakly: the `v2.6.0` entry ("Using -1 as a rating is deprecated and will be
removed in the next major version") was published in a released spec and is **deleted** here rather
than superseded, so a client that migrated off `-1` on the strength of that notice has no trail
explaining the reversal. [Inference] `x-immich-history` looks append-only by purpose, but the repo
documents no such rule, so treat this half as a question for a maintainer rather than a defect.

**Fix:** Apply one consistent history to every schema exposing the field, and append the reversal
rather than rewriting the published entry — e.g.
`.updated('v3', 'Using -1 as a rating (rejected) is valid again; using 0 is no longer valid.')`.

### #8 🟡 Medium: Web renders a rejected asset as unrated, and a cast hides `-1` from the type system

| | |
|---|---|
| **File** | `web/src/lib/components/asset-viewer/DetailPanelStarRating.svelte:16` |
| **Category** | type-safety / correctness |
| **Confidence** | 100 |
| **Screen** | 80 |
| **Validation** | waived — orchestrator verified both files directly |
| **Found by** | adversarial-reviewer (Medium) — unique |

**Issue:** `StarRating.svelte:9` declares `export type Rating = 1 | 2 | 3 | 4 | 5 | null`, and
`DetailPanelStarRating.svelte:16` launders `-1` straight through it:

```ts
let rating = $derived(asset.exifInfo?.rating || null) as Rating;
```

`|| null` is truthy-based, so only `0` becomes `null` — `-1` passes through, and the `as Rating` cast
tells the compiler otherwise. Downstream (verified in `StarRating.svelte`):

- `filled = (ratingSelection || 0) >= value` → false for all five stars, so a rejected asset renders
  identically to an unrated one.
- `{#if ratingSelection !== null && !readOnly}` → the "Clear rating" button *does* show, so the UI
  presents a state it has no vocabulary for: zero stars plus a clear affordance.
- `handleSelect`'s `if (newRating === rating) return` guard never matches `-1`, so the first star a
  user clicks on what looks like an unrated asset silently overwrites the reject mark, with no undo.

**Fix:** Either widen `Rating` to include `-1` and render an explicit rejected state, or normalize
`-1` to `null` at the read boundary and hide the editor for rejected assets. Replace the `as Rating`
cast with a narrowing check so the next domain change fails at compile time instead of silently.

### P2 🟢 Low: Duplicate resolution treats `-1` as absent and silently un-rejects

| | |
|---|---|
| **File** | `server/src/services/duplicate.service.ts:258` |
| **Category** | data-model |
| **Confidence** | 50 |
| **Found by** | adversarial-reviewer (Low), design-reviewer (Medium) |

**Issue:** Rating propagation on merge does `const assetRating = asset.exifInfo?.rating ?? 0;` then
`if (assetRating > rating)` and `if (rating > 0)`. A group holding one asset rated 3 and one
deliberately rejected resolves to `rating: 3`, so merging duplicates silently un-rejects the asset;

**Fix:** Make the reducer sentinel-aware once `-1` is supported — skip propagation when the kept
asset is rejected, or define and document a precedence rule for rejected vs. starred. The deeper
question is whether "rejected" belongs in an ordinal magnitude field at all.

### Migration Safety Notes (data-migration-reviewer)

Affected table: `asset_exif` (the deleted migration's `UPDATE`), plus the meta-tables
`kysely_migrations` / `kysely_migrations_lock`. Migrations run automatically and synchronously at
startup (`DatabaseService.onBootstrap`), gated only by `database.skipMigrations`, which defaults to
`false`.

The project's own developer doc (`docs/docs/developer/database-migrations.md`) describes the
sanctioned way to undo a migration as `mise //server:migrations revert`, which calls `down()` — and
this migration's `down()` was explicitly `// not supported`, so the sanctioned revert path was never
available and file deletion was the only mechanism reached for.

Diagnostic worth running against any instance that tracked `main` in the 2026-06-04 → 2026-06-07 window:

```sql
SELECT * FROM kysely_migrations WHERE name = '1780592070031-ConvertNegativeRatingToNull';
```

A row means that instance will crash-loop at startup on this build. Recovery is
`DELETE FROM kysely_migrations WHERE name = '1780592070031-ConvertNegativeRatingToNull';` — safe
here, since the migration was pure data cleanup with no DDL — then redeploy.

Also note, unrecoverably: the `-1` ratings the migration already nulled are gone. `NULL` is
indistinguishable from "unrated", the `down()` was unsupported, and no migration can restore
overwritten values. Re-permitting `-1` does not bring them back. Worth a release note for users who
had set rejects before `99281de` reached them.

### Considered But Not Flagged (all agents)

**Refuted or dismissed on evidence:**

- **A runtime 500 on `GET` for a `-1` asset.** Traced and dropped: `ZodSerializerInterceptor`
  early-returns when no `ZodSerializerDto` metadata is present, and immich sets none (six DTO files
  carry `// TODO: use ZodSerializerDto`). Carried as the *latent* half of #4, not a present-tense
  failure. (adversarial-reviewer)
- **A self-amplifying job storm.** Checked whether the nulling extraction re-queues another
  `SidecarWrite`, which would oscillate: `handleMetadataExtraction` does not queue one, and
  `job.service.ts` has no `AssetExtractMetadata → SidecarWrite` edge. The chain terminates after one
  round trip, so #1 is destructive rather than oscillating. (adversarial-reviewer)
- **`.refine()` surviving `.extend()` into the derived DTOs.** Replicated the exact composition
  against `zod@4.3.6`: both `AssetBulkUpdateDto` and `UpdateAssetDto` reject `0`/`7`/`-2` with the new
  message, accept `-1` and `3`, and the top-level lat/long refinement still fires. Sound.
  (design-reviewer)
- **`.nullable().refine().optional()` ordering.** `z.infer` resolves to `number | null | undefined`,
  matching `rating?: number | null` in `packages/sdk/src/fetch-client.ts`. No optionality or
  narrowing defect. (typescript-reviewer)
- **The updated error-message assertions in `asset.controller.spec.ts`.** Verified against
  `zod@4.3.6`: `7`, `-2`, and `0` produce exactly `Must be -1, a number from 1 to 5, or null`, and
  `3.5` produces `Invalid input: expected int, received number`. The assertions are factually correct.
- **A DB-level constraint on `asset_exif.rating`.** None exists (`integer`, nullable, no `CHECK`) —
  confirmed from `schema/tables/asset-exif.table.ts` and the initial migration. The restriction was
  always purely application-level, so no schema work is implied. (broad-reviewer)
- **Schema/ModelSnapshot drift from the deleted migration.** It ran a data `UPDATE` only, no DDL, so
  its removal does not desynchronize the code-first schema. (data-migration-reviewer)
- **Locked-properties protection as a mitigation for #1.** Initially looked like it would save the
  `-1` value, and does for a manual edit taken in isolation — but `handleSidecarWrite` unlocks
  `rating` before the extraction runs, which is precisely the step that opens the cascade. Recorded
  because it is the most likely reason to think #1 is not real. (broad-reviewer, then resolved by the
  validator)
- **`0` returning 400 where it used to coerce to `null`.** The break landed in `99281de`, not here;
  at `9e45344` the 400 already occurred. This change is the one that finally documents it, and immich's
  own web and mobile clients send `null` rather than `0` to clear, so no first-party path breaks. Its
  *undocumented-in-spec* form is #6. (adversarial-reviewer, design-reviewer)
- **The `v2.6.0` deprecation entry being removed.** Keeping "deprecated, will be removed" language
  while re-permitting the value would be actively misleading, so removing *something* was right; only
  rewriting rather than superseding is questioned, in #7. (broad-reviewer)
- **Web search-filter index confusion** (`options[rating === null ? 0 : rating]` in
  `SearchRatingsSection.svelte:29` → `options[-1]` is `undefined`). Unreachable today: the search DTO
  rejects `-1` before it can be persisted into a saved filter. Becomes live the moment #3 is fixed —
  worth carrying as a note attached to that fix. (adversarial-reviewer)
- **`error:` vs `message:` in `refine` options.** The new field-level refine uses `error:` while the
  unchanged object-level lat/long refine two blocks below uses `message:`. `zod@4.3.6` supports both,
  `error:` matches `src/validation.ts` and sibling DTOs, and the inconsistency predates the diff.
  Anchor 25 — not reported. (typescript-reviewer)
- **`SyncAssetExifV1.rating` being unconstrained** (`z.int().nullable()`). Intentional — it mirrors
  the DB column for delta sync. Not drift. (design-reviewer)
- **Orphaned references to the deleted migration.** None: no manifest, index, seed, or doc names it,
  so the deletion leaves no dangling pointer in the repo. The problem is the row in the *database*,
  not in the tree. (quick-reviewer, data-migration-reviewer)
