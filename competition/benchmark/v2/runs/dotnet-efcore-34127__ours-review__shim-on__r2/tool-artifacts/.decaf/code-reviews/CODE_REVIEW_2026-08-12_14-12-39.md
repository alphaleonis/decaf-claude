### #1 🔴 Critical: `NullPropagatedOperands` treats `AndAlso`/`OrElse` as NULL-propagating, so the rewrite silently returns wrong query results

| | |
|---|---|
| **File** | `src/EFCore.Relational/Query/SqlNullabilityProcessor.cs:626` |
| **Category** | correctness / null-safety |
| **Confidence** | 100 |
| **Found by** | quick-reviewer (Critical), broad-reviewer (Critical), adversarial-reviewer (Critical ×2 — projection and predicate/ordering), dotnet-reviewer (Critical), knowledge-reviewer (corroborating) |
| **Validation** | confirmed |

**Issue:** The new `NullPropagatedOperands` local function recurses into `Left` and `Right` of
**every** `SqlBinaryExpression`, with no `OperatorType` discrimination:

```csharp
else if (expression is SqlBinaryExpression binary)
{
    NullPropagatedOperands(binary.Left, operands);
    NullPropagatedOperands(binary.Right, operands);
}
```

The set it builds is consumed by `DropNotNullChecks` (`:595`), which deletes an `<e> IS NOT NULL`
conjunct from the CASE test whenever `e` is in the set — and when the test collapses entirely,
`VisitCase` returns `clause.Result` outright (`:587`), erasing the guard.

That is sound only for operators where SQL guarantees NULL if *either* operand is NULL. It is **not**
sound for `AndAlso`/`OrElse`, because SQL's three-valued logic has absorbing values:
`NULL AND FALSE = FALSE`, `NULL OR TRUE = TRUE`. So
`CASE WHEN e IS NOT NULL THEN (e AND b) ELSE NULL END` is **not** equivalent to `(e AND b)`.

**This codebase already knows the rule.** 1,690 lines below, `ProcessNullNotNull` implements the
identical inference *with* the guard, and says why (`:2313-2320`):

```csharp
case SqlBinaryExpression sqlBinaryOperand
    when sqlBinaryOperand.OperatorType != ExpressionType.AndAlso
    && sqlBinaryOperand.OperatorType != ExpressionType.OrElse:
{
    // binaryOp(a, b) == null -> a == null || b == null
    // binaryOp(a, b) != null -> a != null && b != null
    // for AndAlso, OrElse we can't do this optimization
```

The new code re-derives that inference and drops the exclusion.

**Measured impact.** Two reviewers independently built out-of-tree SQLite probes and observed
row-level divergence from the LINQ-to-Objects oracle (4-row table:
`1:(A=null,B=null,NBoolA=null,BoolB=true)`, `2:(A=null,B="x",NBoolA=null,BoolB=false)`,
`3:(A="x",B="x",NBoolA=true,BoolB=true)`, `4:(A="x",B=null,NBoolA=false,BoolB=false)`):

| LINQ projection | SQL emitted after this change | DB result | Correct |
|---|---|---|---|
| `NBoolA != null ? (bool?)(NBoolA.Value && BoolB) : null` | `"NBoolA" AND "BoolB"` | null, **False**, True, False | null, null, True, False |
| `NBoolA != null ? (bool?)(NBoolA.Value \|\| BoolB) : null` | `"NBoolA" OR "BoolB"` | **True**, null, True, False | null, null, True, False |
| `A != null ? (bool?)(A == B) : null` | `"A" = "B" AND "B" IS NOT NULL` | **False**, null, True, False | null, null, True, False |
| `A != null ? (bool?)(A != B) : null` | `"A" <> "B" OR "B" IS NULL` | **True**, null, False, True | null, null, False, True |

The third and fourth rows are the worst case: the user never wrote `&&` or `||` — the `AndAlso` was
manufactured by EF's *own* null-semantics expansion of `A == B`. So the defect is reachable from an
ordinary equality comparison inside a null-guarded conditional, not only from hand-written boolean
composition.

The same rewrite in a predicate or `ORDER BY` changes the **row set** and **row order**, not just a
projected value: `Where(e => (e.A != null ? (bool?)(e.A != e.B) : null) != true)` returned ids
`{2,3}` where the oracle returns `{1,2,3}`; `OrderBy(e => e.A != null ? (bool?)(e.A == e.B) : null)`
ordered `2,1,4,3` instead of `1,2,4,3` because NULL now sorts as FALSE.

**Reachability was the strongest available refutation, and it was checked and refuted.** The
plausible defense is that boolean-valued expressions are converted into nested
`CASE WHEN pred THEN CAST(1 AS bit) ELSE CAST(0 AS bit) END` before this code runs, which would make
raw `AndAlso`/`OrElse` unreachable in the result position — and
`Select_null_propagation_negative1`'s baseline does show exactly that nested-CASE shape. But that
conversion is `SearchConditionConvertingExpressionVisitor`, invoked from
`SqlServerParameterBasedSqlProcessor.Optimize:45`, **after** `base.Optimize(...)` at `:41` — and
`base.Optimize` is what runs `ProcessSqlNullability` → `VisitCase`. The nested CASE exists only in
the final emitted SQL, produced by a later pass. At the moment `NullPropagatedOperands` walks the
tree, `AndAlso`/`OrElse` are still raw. This affects every relational provider, not just SQLite —
neither `SqliteSqlNullabilityProcessor` nor `SqlServerSqlNullabilityProcessor` overrides `VisitCase`.

A structural-equality escape was also checked and does not save it: the SQL Server baseline
`SELECT [e].[NullableIntA] + [e].[NullableIntB]` proves the `Contains` lookup does match for exactly
this column-reference shape, so the incidental `ColumnExpression.IsNullable` mismatch that blocked a
`Coalesce` probe does not generalize to the `AndAlso`/`OrElse` cases.

**Fix:** Restrict the `SqlBinaryExpression` arm to operators that unconditionally propagate NULL,
mirroring the guard already at `:2314`:

```csharp
else if (expression is SqlBinaryExpression binary
    && binary.OperatorType is not (ExpressionType.AndAlso or ExpressionType.OrElse))
{
    NullPropagatedOperands(binary.Left, operands);
    NullPropagatedOperands(binary.Right, operands);
}
```

Consider also excluding `ExpressionType.Coalesce`. `SqlBinaryExpression.IsValidOperator`
(`src/EFCore.Relational/Query/SqlExpressions/SqlBinaryExpression.cs:83`) permits it, and
`COALESCE(NULL, y) = y` does not propagate NULL. In practice `??` translates via
`SqlExpressionFactory.Coalesce` into a `SqlFunctionExpression` with
`argumentsPropagateNullability: [false, false]` — which the function arm handles correctly, and a
targeted probe confirmed the CASE wrapper is retained there. But nothing in `NullPropagatedOperands`
*enforces* that `Coalesce` never arrives as a `SqlBinaryExpression`, and this same file manufactures
`SqlBinaryExpression` nodes at `:1441`. Excluding it costs nothing and removes the latent hazard.

Boolean-typed `And`/`Or` are normalized to `AndAlso`/`OrElse` by
`RelationalSqlTranslatingExpressionVisitor.cs:441-442`, so the exclusion above covers them; integer
bitwise `And`/`Or`/`ExclusiveOr` genuinely do propagate NULL and can stay.

### #2 🟠 High: No test puts a boolean/logical expression in the CASE *result* — the exact shape that breaks

| | |
|---|---|

| **Validation** | waived — corroborated ×2, and directly entailed by confirmed finding #1 |

**Issue:** All five new tests use `~` (unary `Not`), integer `+`, or string `+` in the **result**
position. `Is_not_null_optimizes_binary_op_with_mixed_checks` does use `&&`, but only in the **test**

`DropNotNullChecks` explicitly supports. Nothing exercises `&&`, `||`, or a `bool?`-typed result
*inside* `clause.Result`, which is precisely where finding #1 lives.

This is the gap that let a data-correctness defect through a changeset that otherwise updated 6
baseline files. Two other properties of the suite were checked and are sound — so the gap is one of
missing an operator category, not of weak assertions:

- `AssertQuery` is a genuine oracle. It runs the same lambda against the real DB and against
  in-memory `NullSemanticsData`, comparing element-by-element
  (`test/EFCore.Specification.Tests/TestUtilities/TestHelpers.cs:281-318`), and
  `QueryAsserter.AssertResultCount:123-141` throws on an empty result set when `assertEmpty` was not
  passed — which it was not, in any of the five. A wrong-results regression *would* fail.
- The seed data exercises both branches:
  `test/EFCore.Specification.Tests/TestModels/NullSemanticsModel/NullSemanticsData.cs:41-89` produces
  27 rows via a 3×3×3 cross, giving 18 non-null / 9 null for each nullable column.

**Fix:** Add result-position coverage for the logical operators, asserting query results (not just
SQL shape) so the oracle catches the divergence:

```csharp
[ConditionalTheory]
[MemberData(nameof(IsAsyncData))]
public virtual Task Is_not_null_does_not_optimize_AndAlso_in_result(bool async)
    => AssertQuery(
        async,
        ss => ss.Set<NullSemanticsEntity1>().Select(
            x => x.NullableBoolA != null ? x.NullableBoolA.Value && x.BoolB : (bool?)null));
```

plus an `||` variant, and — covering the manufactured-`AndAlso` path from #1 — a comparison variant:
`x.NullableStringA != null ? (bool?)(x.NullableStringA == x.NullableStringB) : null`.
Add predicate-position and `OrderBy`-position cases too; a projection-only suite passes while `WHERE`
returns the wrong rows.

### #3 🟡 Medium: The rewrite's soundness invariant is stated nowhere, and the two recursion arms give contradictory signals

| | |
|---|---|
| **File** | `src/EFCore.Relational/Query/SqlNullabilityProcessor.cs:617` |
| **Category** | knowledge-preservation |
| **Confidence** | 100 |
| **Found by** | knowledge-reviewer (MUST) |
| **Validation** | waived — deterministic, quotable from the diff |

**Issue:** The rewrite is correct only if `NullPropagatedOperands(result)` yields exactly the
sub-expressions `e` for which `e IS NULL ⇒ result IS NULL`. That invariant is the entire
justification for `DropNotNullChecks` deleting a guard, and it appears in no comment, no XML doc,
and no repo doc. The only comments added are `// optimize expressions such as expr != null ? expr : null`,
a `// TODO`, and a two-word `// true`.

The code then gives two contradictory signals and explains neither: the unary arm (`:621-622`) is
*deliberately narrow* — `Not`, `Negate`, `Convert` only, silently excluding the `Equal`/`NotEqual`
(IS NULL / IS NOT NULL) operators `SqlUnaryExpression` also permits — while the binary arm
(`:626-630`) recurses with *no discrimination at all*. A reader cannot tell whether the blanket
binary recursion is considered or an oversight. Finding #1 establishes it was an oversight; a stated
rule would have made it visible at authoring time, and will prevent the next operator from being
added to either arm without checking it.

This is separately actionable from #1: gating the operators fixes today's bug, but without the stated
contract the next maintainer has nothing to check an addition against.

**Fix:** Add above `NullPropagatedOperands` at `:617`:

```csharp
// Collects the sub-expressions e of 'expression' for which 'e IS NULL' implies
// 'expression IS NULL'. Only recurse through operators that propagate NULL: adding one that
// does not (AndAlso/OrElse/Coalesce, whose three-valued semantics can yield a non-NULL result
// from a NULL operand) makes DropNotNullChecks unsound and silently changes query results.
```

Also widen the block comment at `:576` — "optimize expressions such as `expr != null ? expr : null`"
describes only the degenerate total-collapse case and does not prepare a reader for the partial
rewrite at `:590`, where some not-null checks are dropped and others retained.

### #4 🟢 Low: `DropNotNullChecks` uses `SqlExpression?` as a tri-state sentinel meaning "unconditionally true", with no declared contract

| | |
|---|---|
| **File** | `src/EFCore.Relational/Query/SqlNullabilityProcessor.cs:595` |
| **Category** | knowledge-preservation |
| **Confidence** | 75 |
| **Found by** | knowledge-reviewer (MUST) |
| **Validation** | waived — deterministic, quotable from the diff |

**Issue:** `DropNotNullChecks` returns `SqlExpression?` where `null` does **not** mean "absent" or
"could not optimize" — the ambient C# reading — but "the test is now vacuously true, so drop it
entirely". The only statement of this is the trailing `// true` at `:600`. The declaration carries no
comment, unlike sibling helpers in this file (`OptimizeNonNullableNotExpression` at `:1961` has a
`<summary>`; `IsNull` at `:1632` carries an explanatory `// Note that …`).

The `AndAlso` arm at `:604-609` silently depends on the sentinel reading:
`left is null ? right : right is null ? left : binary.Update(left, right)` means "a vacuously-true
conjunct is absorbed". A maintainer reading `null` as the conventional "bail out" would write
`return left is null || right is null ? null : binary.Update(left, right)` — which reads as obviously
correct under the wrong contract, discards a surviving and still-required not-null check, and makes
`:585-588` return `clause.Result` unconditionally. Nothing in the signature or a test name stops that
edit.

**Fix:** Document the contract at the declaration:

```csharp
// Removes from 'expression' every 'e IS NOT NULL' conjunct whose operand is in
// nullPropagatedOperands (such a check is implied by the result being non-NULL). Returns null
// when the test is thereby reduced to constant TRUE — callers must read null as "no test
// needed", not as "no result".
```

### #5 🟢 Low: `func.Instance!` asserts non-null where the sibling code one method away pattern-matches defensively

| | |
|---|---|

**Issue:** The new code asserts `func.Instance` non-null purely from `InstancePropagatesNullability == true`:

```csharp
if (func.InstancePropagatesNullability == true)
{
    NullPropagatedOperands(func.Instance!, operands);
}
```

The validator verified the two supporting facts:
- The `[EntityFrameworkInternal]` constructor at
  `src/EFCore.Relational/Query/SqlExpressions/SqlFunctionExpression.cs:193` assigns `Instance` (line 207)
  and `InstancePropagatesNullability` (line 214) independently, validating only the
  `Arguments`/`ArgumentsPropagateNullability` count. There is no `[MemberNotNullWhen]` on
  `InstancePropagatesNullability` (only `IsNiladic` carries one, at line 242, for a different member).
  The safe factory overload `SqlExpressionFactory.Function` (`SqlExpressionFactory.cs:632`) takes a
  non-nullable `SqlExpression instance`, so ordinary use is compiler-safe — but the internal
  constructor bypasses it and is documented as usable by providers.
- The same file already has the defensive idiom for exactly this combination, at `:2394`:
  `if (sqlFunctionExpression is { Instance: not null, InstancePropagatesNullability: true })`.

Practical risk is low (an `NRE` during query compilation, only from a provider using the internal
constructor). The finding is kept because the house pattern is one method away and the fix is free.

**Fix:** `if (func is { Instance: not null, InstancePropagatesNullability: true })`.

### #6 🟢 Low: `IsNull(elseResult)` does not match the no-`ELSE` shape, skipping the optimization on a reachable, semantically identical CASE

| | |
|---|---|
| **File** | `src/EFCore.Relational/Query/SqlNullabilityProcessor.cs:578` |
| **Category** | missed optimization |
| **Confidence** | 100 |
| **Found by** | broad-reviewer (Low) |
| **Validation** | confirmed |

**Issue:** `IsNull` (`:1633`) matches only `SqlConstantExpression { Value: null }` or a null-valued
parameter. When the source `CaseExpression` has no `ELSE` at all, `elseResult` is C# `null`, so
`IsNull(null)` is `false` and the optimization is skipped — even though SQL's
`CASE WHEN x IS NOT NULL THEN y END` is identical to `CASE WHEN x IS NOT NULL THEN y ELSE NULL END`.

The validator confirmed this shape is genuinely reachable rather than vacuous:
`RelationalSqlTranslatingExpressionVisitor.cs:1407` constructs a single-when-clause searched CASE with
`elseResult: null` (shared-table / owned-entity property access); `SqlExpressionFactory.Case`
(`:573-590`) and `ApplyTypeMapping` (`:48`) pass the null through unchanged, and `CaseExpression`
stores it verbatim (`CaseExpression.cs:37/51`). The pre-existing `nullable |= elseResult == null;` at
`:562` corroborates that the shape is expected here.

The proposed fix is also semantically correct, not merely an optimization: `:573` in this same method
already treats a missing `ELSE` as `NULL` (`elseResult ?? _sqlExpressionFactory.Constant(null, ...)`).

**Fix:** `if (testIsCondition && whenClauses is [var clause] && (elseResult is null || IsNull(elseResult)))`

### Residual Risks

*(Included despite `reach=norm` — both are verified and actionable, screened below the primary bar
rather than dismissed. See Process deviations.)*

- `src/EFCore.Relational/Query/SqlNullabilityProcessor.cs:617` — building the operand set is
  **O(n²) in subtree size** (performance-reviewer). `SqlExpression.GetHashCode` is structural and
  uncached — `SqlBinaryExpression.cs:173` is `HashCode.Combine(base.GetHashCode(), OperatorType, Left, Right)`,
  which recurses into children; `SqlFunctionExpression.cs:422-440` hashes `Instance` and every
  argument. Since every node of `clause.Result` is `Add`ed, and each `Add` costs O(that node's
  subtree), a chain-shaped result (a long `a + b + c + …` concat) costs O(n²). Screened marginal:
  this is compile-time only, cached per query shape × parameter-nullability by
  `RelationalCommandCache`, and real trees are small — 50 operands is ~2,500 hash steps. Worth
  knowing before someone applies this pattern to a larger tree.
- `src/EFCore.Relational/Query/SqlNullabilityProcessor.cs:578` — no cheap early-out
  (performance-reviewer). The `HashSet` allocation and the full `clause.Result` walk run for every
  single-WHEN, null-`ELSE`, operand-less CASE, even when `clause.Test` contains no `IS NOT NULL` node
  at all and the walk cannot possibly help. `Is_not_null_optimizes_binary_op_with_mixed_checks`
  demonstrates it directly: its surviving test is `[e].[BoolA] = CAST(1 AS bit)`, yet the full walk
  ran. A shallow scan of `clause.Test` (typically far smaller than the result) for at least one
  `SqlUnaryExpression { OperatorType: NotEqual }` would skip the work.

## Specialist Notes

### Considered But Not Flagged (all agents)

**Refuted or dismissed after investigation:**

- **`Coalesce` as an independently confirmed instance of #1** (quick, broad, knowledge). `??`
  translates via `SqlExpressionFactory.Coalesce` (`SqlExpressionFactory.cs:485-511`) to a
  `SqlFunctionExpression` with `argumentsPropagateNullability: [false, false]`, which the function arm
  handles correctly. Two independent probes confirmed the CASE wrapper is *retained* for
  `IntA != null ? (IntA ?? IntB) : null`. Folded into #1's fix as a latent-hazard note rather than
  reported as a second Critical.
- **`caseExpression.Update` ignoring the reassigned `whenClauses`** (adversarial, dotnet).
  `CaseWhenClause` overrides `Equals` structurally (`CaseWhenClause.cs:38-47`), so `Update`'s
  `SequenceEqual` correctly detects the rewrite; the collection expression target-types to
  `List<CaseWhenClause>`. The `Is_not_null_optimizes_binary_op_with_mixed_checks` baseline confirms the
  partial-drop path works. Not a defect.
- **Newly exposed runtime errors from removing the guard** (adversarial). No counterexample
  constructible: dropping `A IS NOT NULL` only admits rows where `A` is NULL, and `x / NULL`,
  `CAST(NULL AS int)`, `LEN(NULL)` all yield NULL rather than erroring. The set of non-NULL values
  reaching the expression is unchanged.
- **Partially-dropped `AndAlso` tests leaving conjuncts simplified under the non-null assumption**
  (adversarial). Traced both branches of e.g. `A != null && A != B ? A : null`; the surviving test can
  be TRUE for a NULL `A`, but the result is then NULL anyway. No observable divergence.
- **`HashSet<SqlExpression>` matching the wrong operand, or failing to match** (dotnet). All concrete
  subtypes implement full structural `Equals`/`GetHashCode` including `TypeMapping`. A `TypeMapping`
  difference would forgo the optimization (missed optimization, not a correctness bug); collisions
  between distinct columns are not possible.
- **`ExclusiveOr` recursion** (adversarial). Bit/int XOR propagates NULL on both SQL Server and
  SQLite. No scenario.
- **Non-boolean bitwise `And`/`Or`** (quick). `NULL & x` is always NULL, so total propagation holds;
  boolean `&`/`|` are normalized to `AndAlso`/`OrElse` at
  `RelationalSqlTranslatingExpressionVisitor.cs:441-442` and so are covered by #1.
- **`InExpression` / `LikeExpression` / `ScalarSubqueryExpression` / `CaseExpression` results**
  (adversarial). These hit none of the three recursion arms, so only the node itself is added and the
  guard survives. Verified by construction — and visible in the retained baseline for
  `Select_null_propagation_negative1` and `Null_propagation_optimization3`, both of which have a
  nested `CaseExpression` result and are correctly left unoptimized.
- **Unary arm restricted to `Not`/`Negate`/`Convert`** (quick, knowledge). Matches
  `ProcessNullNotNull`'s own unary handling at `:2288-2298`. Correct; the exclusion of
  `Equal`/`NotEqual` (IS NULL / IS NOT NULL) is right, just undocumented — see #3.
- **`func.ArgumentsPropagateNullability.Count` index mismatch / NRE** (adversarial). The
  `SqlFunctionExpression` constructor validates the count (`:217`) and `IsNiladic` is
  `[MemberNotNullWhen(false, …)]`, so `!func.IsNiladic` makes the access safe.
- **`VisitCase` XML doc not updated** (knowledge). The method already returned non-`CaseExpression`
  values before this change (pre-existing `:547`, `:573`); "An optimized sql expression" remains
  accurate. No provider-facing contract changed.
- **`nullable` out-parameter fidelity when returning `clause.Result`** (broad). `nullable` is already
  forced true whenever an explicit `ELSE NULL` is present, independent of the new branch. No
  discrepancy.
- **`Type`/`TypeMapping` fidelity when substituting `clause.Result` for the `CaseExpression`** (broad).
  Construction invariants require the when-results and else-result to share the case's type and
  mapping. No counterexample; the six updated baseline files show no widening/narrowing artifacts.
- **Missing SQLite baseline overrides for the five new tests** (test-reviewer). Matches the existing
  convention for the adjacent, unmodified `Is_null_on_column_followed_by_OrElse_*` tests — SQL Server
  gets explicit `AssertSql` overrides, other providers inherit the result-correctness check. Not a gap
  this diff introduces.
- **Unlinked `// TODO: optimize expr == null ? null : expr`** (`:577`, knowledge). Of 30 TODOs in
  `src/EFCore.Relational/Query/`, the large majority carry no issue number. House style; no standard
  violated.
- **Unbounded recursion depth in the two new helpers** (dotnet, performance). Matches the pervasive
  recursive-visitor style of the whole file; `VisitCase`'s existing `Visit()` calls already recurse
  over the same depth. No new order of risk.
- **Sargability loss from removing the `IS NOT NULL` guard** (performance). The original predicate was
  already non-sargable (column wrapped in `CASE` plus a function call), so nothing index-usable is
  lost. Neutral to positive.
- **Bare `HashSet` allocation per CASE node** (performance, anchor 50). Typical of compiler hot paths;
  below the reporting bar on its own, separate from the O(n²) item above.

**Suppressed by the confidence gate:** none. Two performance findings were screened below the primary
bar and tiered down to Minor / Residual Risks rather than suppressed.
