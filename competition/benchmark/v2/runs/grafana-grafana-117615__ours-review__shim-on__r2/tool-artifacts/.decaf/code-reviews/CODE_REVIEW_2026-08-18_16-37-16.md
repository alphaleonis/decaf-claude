### #1 🟠 High: `quoteIdentifierIfNecessary(vars[0])` throws and takes down the SQL expression editor when there are no sibling queries

| | |
|---|---|
| **File** | `public/app/features/expressions/components/SqlExpressions/SqlExpr.tsx:81` |
| **Category** | null-safety / regression |
| **Confidence** | 100 (mechanism and regression both probe-verified — see Probe Results) |
| **Found by** | quick-reviewer (High), adversarial-reviewer (High), typescript-reviewer (High), security-reviewer (Medium), broad-reviewer (dismissed as pre-existing — refuted by probe) |

**Issue:** `vars` is `refIds.map((v) => v.value!)` (`SqlExpr.tsx:61`); the `!` makes `vars[0]` *type* as `string` while it is `undefined` at runtime whenever `refIds` is empty. Both call sites build `refIds` by filtering the expression's own RefID out of the query list (`ExpressionQueryEditor.tsx:118`, `alerting/unified/components/expressions/Expression.tsx:101`), so `refIds` is empty whenever the SQL expression is the only query in the panel or rule.

`quoteIdentifierIfNecessary` reaches `identifier.toUpperCase()` in `isValidIdentifier` (`public/app/plugins/datasource/mysql/sqlUtil.ts:54`) without a guard, so the call throws `TypeError: Cannot read properties of undefined (reading 'toUpperCase')`. `initialQuery` is computed **in the render body**, not in an effect or a `useMemo`, so the throw happens on every render and React unmounts the subtree ("Consider adding an error boundary…"). Before this change the same expression was a bare template interpolation, which degraded harmlessly to the literal text `FROM undefined`.

Probe-verified both ways: with line 81 as written, rendering `<SqlExpr refIds={[]} …/>` throws the `TypeError`; with only that line reverted to `${vars[0]}`, no throw occurs (the run then fails on an unrelated `act()` warning from the lazy `SQLEditor`, not on an error). This is a change-introduced regression, not a pre-existing condition.

**Fix:**
```ts
const table = vars[0] ? quoteIdentifierIfNecessary(vars[0]) : '';
const initialQuery = `SELECT
  *
FROM
  ${table}
LIMIT
  10`;
```
Add a regression test rendering `SqlExpr` with `refIds={[]}`. Hardening `isValidIdentifier` against non-string input would also work, but it lives in a datasource plugin and has other callers, so guarding at this call site is the smaller change.

### #2 🟡 Medium: Three quoting call sites, two different quoting implementations — `metaSqlExpr.ts` keeps the weaker local copy

| | |
|---|---|
| **File** | `public/app/features/expressions/utils/metaSqlExpr.ts:15` (helper at `:114`) |
| **Category** | correctness / duplicated logic |
| **Confidence** | 100 (quotable fact: the two implementations are in the tree and differ) |
| **Found by** | quick-reviewer (High), broad-reviewer (High + Medium), adversarial-reviewer (Medium), typescript-reviewer (Medium), security-reviewer (Medium), test-reviewer (Medium, as a test gap) |

**Issue:** The change adds `import { quoteIdentifierIfNecessary } from 'app/plugins/datasource/mysql/sqlUtil'` to `SqlExpr.tsx:13` and `sqlCompletionProvider.ts:9`, but **not** to `metaSqlExpr.ts` — so the new call at `metaSqlExpr.ts:15` resolves to that file's own private helper (`metaSqlExpr.ts:114`), which is regex-only:

```ts
function quoteIdentifierIfNecessary(value: string) {
  return /^[a-zA-Z_][a-zA-Z0-9_$]*$/g.test(value) ? value : `\`${value}\``;
}
```

The imported version additionally quotes MySQL reserved words via `isValidIdentifier`'s `RESERVED_WORDS` check. The result: for a RefID that is identifier-shaped but reserved (`Order`, `Group`, `select` — all accepted by the RefID rename input), the editor's initial query and the table completion are correctly backtick-quoted, while the metadata query emitted by `fetchSQLFields` is not, producing `SELECT * FROM Order LIMIT 1` — a syntax error at the backend parser (`pkg/expr/sql/parser_allow.go` uses the vitess MySQL parser).

Two same-named functions with silently different behavior in one feature is also a standing drift hazard: a future fix to the shared helper will not reach this path, and nothing in the code says so.

**Fix:** Import the shared helper in `metaSqlExpr.ts` and delete the private duplicate at `:114`. If the divergence is deliberate, say why in a comment — but nothing in the diff suggests it is.

**Impact bound (why Medium, not High):** the only caller of `fetchSQLFields` is `columns.resolve` in `sqlCompletionProvider.ts:36`, gated by `config.featureToggles.sqlExpressionsColumnAutoComplete`, which is `Expression: "false"` and Experimental (`pkg/services/featuremgmt/registry.go:878-884`). The functional half of this finding is therefore off by default today; the drift half is not gated.

### #3 🟡 Medium: Completions now insert backtick-quoted table names, but the read path never unquotes them — column autocomplete silently returns nothing for exactly the names this change targets

| | |
|---|---|
| **File** | `public/app/features/expressions/components/SqlExpressions/CompletionProvider/sqlCompletionProvider.ts:27` (consumed at `public/app/features/expressions/utils/metaSqlExpr.ts:15,20`) |
| **Category** | composition / correctness |
| **Confidence** | 100 (validator-confirmed, full chain traced through `@grafana/plugin-ui` and monaco) |
| **Found by** | adversarial-reviewer (High), broad-reviewer (Medium), security-reviewer (Medium) · validator: **confirmed** |

**Issue:** Accepting the new quoted table completion puts `` FROM `gdp per capita` `` in the editor. The chain back to column autocomplete does not handle those backticks:

1. The expressions provider supplies no `parseName` on its `tables` config, and plugin-ui falls back to `defaultTableNameParser` (`SQLEditor.js`: `customProvider.tables?.parseName ?? defaultTableNameParser`).
2. `getTableToken` returns the first *non-whitespace* token after `FROM` (`tokenUtils.js:13`), and monaco's mysql tokenizer emits the backtick as its own `identifier.quote` token separate from the identifier body (`monaco-editor/esm/vs/basic-languages/mysql/mysql.js:866-871`). plugin-ui's `linkedTokenBuilder` does no merging, so the token handed over is the lone backtick.
3. `defaultTableNameParser` splits that token's value on `.` and returns `` { table: '`' } `` (`tokenUtils.js:25`).
4. That reaches `fetchSQLFields` via `SqlExpr.tsx:357`, where `metaSqlExpr.ts:15` re-quotes it and `metaSqlExpr.ts:20`'s `queries.filter((q) => q.refId === query.table)` matches no frame.
5. The failure is swallowed by `catch { return []; }` at `sqlCompletionProvider.ts:38-40`, so the user sees an empty column list with no error.

The sibling providers show the expected pattern: `mssql/sqlCompletionProvider.ts:25` and `grafana-postgresql-datasource/sqlCompletionProvider.ts:26` both supply a custom `parseName`, and the MySQL datasource unquotes identifiers before metadata queries (`mysql/mySqlMetaQuery.ts:39`, `quoteIdentAsLiteral`).

**Fix:** Supply a `parseName` on the `tables` completion config that walks the `IdentifierQuote`/`Identifier` tokens into a single name, and/or normalize with `unquoteIdentifier` at the start of `fetchSQLFields` so both the quoting and the `q.refId === query.table` comparison work on the bare name. Also consider not swallowing the error at `sqlCompletionProvider.ts:38-40` — this defect is invisible precisely because of that bare `catch`.

**Impact bound (why Medium):** same feature toggle as #2 — `sqlExpressionsColumnAutoComplete` is Experimental and defaults to false.

### #5 🟡 Medium: Assertions hidden inside an unguarded `if` — the second completion-provider test can pass having asserted nothing

| | |
|---|---|
| **File** | `public/app/features/expressions/components/SqlExpressions/CompletionProvider/sqlCompletionProvider.test.ts:42` |
| **Category** | false-positive test |
| **Confidence** | 100 (quotable fact) |
| **Found by** | test-reviewer (High) |

**Issue:** In `'should use label if provided, otherwise value for table name'`, `resolveFunc` comes from `provider.tables?.resolve` and every assertion sits inside `if (resolveFunc) { … }` — with no `expect(resolveFunc).toBeDefined()` first. If `tables.resolve` ever stops being defined (a rename, a refactor of the provider shape, a regression in `getSqlCompletionProvider`), the `if` body is skipped and the test reports green having run zero assertions. The test immediately above it gets this right: it asserts `expect(resolveFunc).toBeDefined()` at line 15 before the same `if` at line 17. The regression this test exists to catch is exactly the kind that would remove the resolver.

**Fix:**
```ts
const resolveFunc = provider.tables?.resolve;
expect(resolveFunc).toBeDefined();

const tables = await resolveFunc!();
expect(tables[0].name).toBe('value_only');
expect(tables[1].name).toBe('Label A');
```
Better still, drop the `if` in the first test too and rely on the assertion plus `!`.

### #6 🟢 Low: `quoteIdentifierIfNecessary` quotes but does not escape — an embedded backtick breaks out of its own quoting

| | |
|---|---|
| **File** | `public/app/features/expressions/components/SqlExpressions/SqlExpr.tsx:81` (helper at `public/app/plugins/datasource/mysql/sqlUtil.ts:44`; local copy at `public/app/features/expressions/utils/metaSqlExpr.ts:114`) |
| **Category** | correctness / input handling |
| **Confidence** | 100 (reading the helper: `` `\`${value}\`` `` with no doubling) |
| **Found by** | security-reviewer (High — dissent recorded below), adversarial-reviewer (Medium) |

**Issue:** Neither implementation doubles backticks contained in the value, which is what MySQL identifier quoting requires. A RefID such as `` A`,`B `` yields `` FROM `A`,`B` `` — the identifier terminates its own quoting and the rest is parsed as query structure. The change makes this helper the sole sanitization step on three generated-SQL paths, one of which (`metaSqlExpr.ts:15`) builds SQL the user never sees.

**Fix:** Double embedded backticks (`value.replace(/`/g, '``')`) inside whichever helper becomes canonical after #2, and normalize already-quoted input before re-quoting (the unquote-then-quote convention the MySQL datasource follows at `mySqlMetaQuery.ts:39`). Validating the identifier against the known RefID set would be stronger still, since that set is enumerable here.

**Dissent — why Low and not High:** `security-reviewer` rated this High as an injection surface. I could not substantiate a crossed trust boundary, so I lowered it to a correctness finding: the identifier originates from a RefID set by the same user who can type arbitrary SQL directly into the same editor; the meta query executes only over that request's own frames; `AllowQuery` restricts the permitted node and function set (`pkg/expr/sql/parser_allow.go`); and `db.go` disables file writes and applies cell/time limits. The realistic outcome is a malformed query, not escalation or exfiltration. The escaping gap is still a real defect — just not a security one on the evidence available.

## Specialist Notes

### Threat Model Notes (security-reviewer)

- **Boundaries crossed.** (1) Dashboard/alert-rule JSON → frontend: RefIDs are shapeable by anyone who can save or provision a dashboard, and are not restricted to `A`/`B`-style tokens (`QueryEditorRowHeader.tsx` trims and de-duplicates only). (2) Frontend → backend: `runMetaSQLExprQuery` sends SQL the user never reviews. (3) Upstream datasource frames → SQL: column names are quoted with the same incomplete helper at `metaSqlExpr.ts:29` (pre-existing line, same defect class).
- **Blast radius is bounded**, which is why nothing here was rated Critical: injected structure is still filtered by `AllowQuery`'s node and function allowlist, executes only over the frames of the same request, has file writes disabled, and is cell- and time-limited (`pkg/expr/sql/db.go`, `pkg/expr/sql_command.go`).
- **Systemic observation.** The change promotes a display-oriented quoting helper into a load-bearing sanitizer for a server-executed string, with no normalize step, no rejection path, and no allow-list check against the enumerable RefID set. Validating against that set, with escaping as defense in depth, is the stronger control.

### Considered But Not Flagged (all agents)

**Refuted by evidence gathered during consolidation:**
- `broad-reviewer` dismissed #1 as pre-existing behavior at anchor 25 ("previously `${vars[0]}` had the same 'undefined' stringification issue"). Refuted by the revert probe: the old code produced the harmless literal `FROM undefined`, the new code throws. Promoted to finding #1 (Step 5.5).

**Correctly not flagged (checked and agreed):**
- The `/g` flag on the regex literals in both quoting helpers looks like a `lastIndex` footgun, but the literals are re-created on every call, so no state carries across invocations. Confirmed independently by four reviewers.
- `sqlCompletionProvider.ts:27`'s `|| ''` fallback means the empty-RefID case yields two backticks rather than a crash — the `|| ''` is what saves this call site from #1's fate. Both current callers set `label === value === q.refId` from a non-empty RefID, so the branch is unreachable today.
- `refId.label || refId.value` precedence (completion uses the label, `SqlExpr`'s initial query uses the value) is a pre-existing asymmetry; both call sites currently set the two to the same string, so no divergent state exists to exploit.
- Resource amplification through an injected join is bounded by `SQLExpressionCellLimit` / `SQLExpressionOutputCellLimit` / `SQLExpressionTimeout` and `WithDisableFileWrites(true)`.
- Already-saved expressions are not migrated — `query.expression || initialQuery` means the fix only affects newly created expressions. A behavior gap by design, not a defect; out of reach at `reach=norm`.
- `metaSqlExpr.ts:29` (`value: quoteIdentifierIfNecessary(name)` for column names) carries the same escaping gap as #6 but is a pre-existing line the diff does not touch.
