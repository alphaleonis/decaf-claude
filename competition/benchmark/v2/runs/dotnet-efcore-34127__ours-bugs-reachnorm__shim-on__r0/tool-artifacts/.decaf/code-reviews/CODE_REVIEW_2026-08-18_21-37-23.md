## Findings

### #1 🔴 Critical: `NullPropagatedOperands` treats *every* `SqlBinaryExpression` as null-propagating, including `AndAlso`/`OrElse` — silently wrong query results

| | |
|---|---|
| **File** | `src/EFCore.Relational/Query/SqlNullabilityProcessor.cs:626` |
| **Category** | correctness |
| **Confidence** | 100 |
| **Verified** | executed |
| **Pre-existing** | no |
| **Found by** | solo-reviewer (Critical) |

**Issue:** The `else if (expression is SqlBinaryExpression binary)` arm descends into both operands of any binary operator with no check on `OperatorType`. SQL's `AND`/`OR` are *not* null-propagating: `NULL AND FALSE` is `FALSE` and `NULL OR TRUE` is `TRUE`. When the when-clause result is (or contains) a logical conjunction/disjunction, the operand of the `IS NOT NULL` test gets added to `nullPropagatedOperands`, `DropNotNullChecks` deletes the test, and the `CASE` collapses to an expression that returns `FALSE`/`TRUE` where the original returned `NULL`.

`SqlNullabilityProcessor` runs *before* SQL Server's `SearchConditionConvertingExpressionVisitor` (`src/EFCore.SqlServer/Query/Internal/SqlServerParameterBasedSqlProcessor.cs:45`), so at this point boolean search conditions legitimately sit in `CASE ... THEN` result position on every provider — see the pre-existing baseline `test/EFCore.Sqlite.FunctionalTests/Query/NullSemanticsQuerySqliteTest.cs:964` (`WHEN "e"."BoolA" THEN (...) AND (...)`). This is not a theoretical shape.

Note this is not limited to a literal `&&` in the user's LINQ: EF's own null-semantics expansion of `a == b` produces an `AndAlso`/`OrElse`, so a plain equality in the result triggers it too (last row below).

**Evidence:** Executed against SQLite, HEAD vs. parent commit `051c33a79`, over rows `{A=null,BoolB=false}`, `{A=null,BoolB=true}`, `{A=10,BoolB=true}`:

| LINQ result expression | SQL at HEAD | HEAD result | Parent-commit result | LINQ-to-Objects expectation |
|---|---|---|---|---|
| `A != null ? (bool?)(A > 5 && BoolB) : null` | `SELECT "NullableIntA" > 5 AND "BoolB"` | `False,NULL,True` | `NULL,NULL,True` | `NULL,NULL,True` |
| `A != null ? (bool?)(A > 5 \|\| BoolB) : null` | `SELECT "NullableIntA" > 5 OR "BoolB"` | `NULL,True,True` | `NULL,NULL,True` | `NULL,NULL,True` |
| `NullableBoolA != null ? (bool?)(NullableBoolA.Value && BoolB) : null` | `SELECT "NullableBoolA" AND "BoolB"` | `False,NULL,True` | `NULL,NULL,True` | `NULL,NULL,True` |
| `A != null ? (bool?)(A == B) : null` | `SELECT "NullableIntA" = "NullableIntB" AND "NullableIntB" IS NOT NULL` | `False,False,False` | `NULL,NULL,False` | `NULL,NULL,False` |

The parent-commit SQL in every row is the un-collapsed `CASE WHEN "NullableIntA" IS NOT NULL THEN ... ELSE NULL END`, and every parent-commit result matches the LINQ-to-Objects expectation. Every HEAD result that differs is a wrong answer returned without any error.

**Fix:** Gate the binary arm on an allowlist of genuinely strict operators, e.g.

```csharp
else if (expression is SqlBinaryExpression
         {
             OperatorType: ExpressionType.Add or ExpressionType.Subtract or ExpressionType.Multiply
                 or ExpressionType.Divide or ExpressionType.Modulo
                 or ExpressionType.And or ExpressionType.Or or ExpressionType.ExclusiveOr
         } binary)
```

Comparison operators (`Equal`, `NotEqual`, `LessThan`, …) are strict *as SQL conditions* but must still be excluded because of finding #2; `AndAlso`/`OrElse` must be excluded because they are not strict at all; `Coalesce` must be excluded (see #4).

### #2 🔴 Critical: Condition-valued results lose their `NULL` on SQL Server — `UNKNOWN` collapses to `CAST(0 AS bit)`

| | |
|---|---|
| **File** | `src/EFCore.Relational/Query/SqlNullabilityProcessor.cs:576` |
| **Category** | correctness |
| **Confidence** | 100 |
| **Verified** | traced (SQL generation executed; T-SQL evaluation traced) |
| **Pre-existing** | no |
| **Found by** | solo-reviewer (Critical) |

**Issue:** Even for a result that *is* strictly null-propagating in three-valued logic — a bare comparison such as `A > 5` — removing the enclosing `CASE ... ELSE NULL END` is unsound on providers that materialize a search condition as a value. SQL Server's `SearchConditionConvertingExpressionVisitor` runs after this processor and wraps a condition in a value position as `CASE WHEN <cond> THEN CAST(1 AS bit) ELSE CAST(0 AS bit) END`. That mapping sends `UNKNOWN` to `0`, not to `NULL`. The outer `CASE` that this optimization deletes was the only thing preserving the `NULL`.

This is a distinct root cause from #1: it fires with no `AndAlso`/`OrElse` anywhere, on the plainest possible boolean result.

**Evidence:** SQL generated for `ctx.Entities1.Select(x => x.NullableIntA != null ? (bool?)(x.NullableIntA > 5) : null)`:

Parent commit `051c33a79`:
```sql
SELECT CASE
    WHEN [e].[NullableIntA] IS NOT NULL THEN CASE
        WHEN [e].[NullableIntA] > 5 THEN CAST(1 AS bit)
        ELSE CAST(0 AS bit)
    END
    ELSE NULL
END
FROM [Entities1] AS [e]
```

HEAD:
```sql
SELECT CASE
    WHEN [e].[NullableIntA] > 5 THEN CAST(1 AS bit)
    ELSE CAST(0 AS bit)
END
FROM [Entities1] AS [e]
```

With `NullableIntA IS NULL`, `[e].[NullableIntA] > 5` is `UNKNOWN`, the `WHEN` is not satisfied, and the `ELSE` yields `0` — the projection returns `false` where the parent commit (and LINQ-to-Objects) returns `null`. The same collapse applies to the `AndAlso`/`OrElse` shapes of #1 on SQL Server (both were generated; both lose the outer `CASE` identically). This could not be executed against a live SQL Server, but the `CASE`/`UNKNOWN` evaluation is unambiguous SQL semantics, and the generated-SQL difference is executed evidence.

**Fix:** Additionally require that the when-clause result is not a condition before collapsing — e.g. skip the whole rewrite when `clause.Result.Type.UnwrapNullableType() == typeof(bool)`, or narrow `NullPropagatedOperands`' binary arm to arithmetic/bitwise/concat operators only (which excludes comparisons and therefore all condition-shaped results). If a boolean-result optimization is wanted later, it has to be done after search-condition conversion, or guarded per-provider.

**Issue:** All five new tests project non-boolean results (`int?` via `~` and `+`, `string` via concat). The optimization's admitted shape is much wider — the `SqlBinaryExpression` arm accepts every operator and the collapse applies to any result type — and the entire dangerous region (boolean results, `AndAlso`/`OrElse`, comparisons) has no test. This is why #1 and #2 are green in CI: only the safe corner of the new behavior is exercised.

The existing test data is sufficient to catch it — `NullSemanticsData` seeds `null` into every nullable column — so the gap is purely in the queries chosen, not in the fixture.

**Evidence:** Every `clause.Result` in the new tests is `~x.NullableIntA`, `x.NullableIntA + x.NullableIntB`, or a string concat. Adding `x => x.NullableIntA != null ? (bool?)(x.NullableIntA == x.NullableIntB) : null` to this class fails on SQLite today (returns `False` for the `NullableIntA IS NULL` rows; expected `null`) — that exact query was run through the built SQLite provider, see #1's table.

**Fix:** Add specification tests for at least: comparison result (`(bool?)(A == B)`), `AndAlso` result, `OrElse` result, and a nullable-bool logical result. They should be added before the fixes for #1/#2 so they demonstrably fail first.

### #4 🟢 Low: `ExpressionType.Coalesce` is a legal `SqlBinaryExpression` operator and would be walked as strict

| | |
|---|---|
| **File** | `src/EFCore.Relational/Query/SqlNullabilityProcessor.cs:626` |
| **Category** | correctness |
| **Confidence** | 50 |
| **Verified** | read |
| **Pre-existing** | no |
| **Found by** | solo-reviewer (Low) |

**Issue:** `SqlBinaryExpression.IsValidOperator` (`src/EFCore.Relational/Query/SqlExpressions/SqlBinaryExpression.cs:102`) admits `ExpressionType.Coalesce`. The unconditional binary arm would therefore treat `COALESCE(a, b)`-as-binary as strict in `a`, and `A != null ? coalesce(A, 0) + 1 : null` would collapse to `coalesce(A, 0) + 1`, returning `1` instead of `NULL`. This matters because the optimization lives in shared relational code that third-party providers inherit.

**Evidence:** The in-box `SqlExpressionFactory.Coalesce` (`src/EFCore.Relational/Query/SqlExpressionFactory.cs:495`) builds a `SqlFunctionExpression` with `argumentsPropagateNullability: [false, false]`, not a binary, and `QuerySqlGenerator`'s binary operator switch (`src/EFCore.Relational/Query/QuerySqlGenerator.cs:1082`) has no `Coalesce` case and throws `UnreachableException` for it — so no in-box path constructs it and no repro could be built. That is the counter-argument, and it is exactly why this is Low/50 rather than higher; but the operator is public API surface that a provider overriding `QuerySqlGenerator` may legitimately use, and the operator allowlist in #1's fix closes it for free.

**Fix:** Covered by the operator allowlist proposed in #1 — do not rely on `Coalesce` being unconstructible.
