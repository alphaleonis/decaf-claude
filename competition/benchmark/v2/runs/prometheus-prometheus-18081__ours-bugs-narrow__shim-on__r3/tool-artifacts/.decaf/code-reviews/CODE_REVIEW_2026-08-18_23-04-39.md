### #1 🔴 Critical: unbounded eager per-step allocation for subqueries kills the process with a fatal OOM

| | |
|---|---|
| **File** | `promql/engine.go:2397` (allocation site `util/stats/query_stats.go:306-308`) |
| **Category** | production |
| **Confidence** | 100 |
| **Verified** | executed |
| **Pre-existing** | no |
| **Found by** | solo-reviewer (Critical) |

**Issue:** The `*parser.SubqueryExpr` branch now calls `stats.NewChildWithStepTracking(..., subqStart, subqEnd, subqInterval)`, which runs `InitStepTracking` and eagerly allocates **two** `[]int64` sized by the *subquery's own* step count — before any evaluation, and therefore before `-query.max-samples`, the query timeout, or context cancellation can intervene. Subquery step counts are bounded by nothing in Prometheus (only the produced samples are). At 16 bytes per subquery step, a modest query string requests an arbitrarily large slab. When the request exceeds available memory the Go runtime calls `runtime.throw`, which `evaluator.recover` (`promql/engine.go:1180-1187`, `case runtime.Error`) cannot catch — the whole Prometheus process dies. Pre-change the child was `NewChild()`, which forces per-step off and allocates nothing.

**Evidence:** Executed. Range query `count_over_time(metric[300d:1ms])` (start 201s, end 220s, step 5s) with the engine and query opts having per-step stats enabled:

- At `ec7157593`: `fatal error: runtime: out of memory`, stack `runtime.makeslice → util/stats.InitStepTracking (query_stats.go:307) → util/stats.NewChildWithStepTracking (query_stats.go:414) → promql.(*evaluator).eval (engine.go:2397) → evalSubquery (engine.go:1871)`. Process terminated.
- At `efbdc3f88`, identical query: returns `query processing would load too many samples into memory`, `TotalAlloc` delta 0.5 MiB, 88 s.

The scaling is linear and measurable at safe sizes (`TotalAlloc` delta, same query shape, HEAD vs base): `[10m:1ms]` 10.0 MiB vs 0.5 MiB; `[2h:1ms]` 110.7 MiB vs 0.5 MiB. Both of those queries *fail* with `ErrTooManySamples`, yet the memory is charged anyway. Extrapolating, `[1d:1ms]` requests ≈1.4 GiB and `[300d:1ms]` ≈414 GiB.

Gated behind `--enable-feature=promql-per-step-stats` plus `stats=all` on the request — but within that configuration it is reachable from any unauthenticated query the HTTP API accepts.

**Fix:** Do not size a stats array from an unvalidated subquery step count. Either (a) drop the per-step child for subqueries entirely and attribute the subquery's `SamplesRead` scalar to the outer step (the `else` branch at `engine.go:2447` already does exactly this correctly), or (b) cap `numSteps` in `InitStepTracking` and fall back to total-only accounting above the cap. Option (a) also removes finding #2's mechanism.

### #2 🟠 High: `samplesRead` double counts every subquery sample, and can exceed `totalQueryableSamples` by up to 7×

| | |
|---|---|
| **File** | `promql/engine.go:1874` (helper at `util/stats/query_stats.go:423`) |
| **Category** | correctness |
| **Confidence** | 100 |
| **Verified** | executed |
| **Pre-existing** | no |
| **Found by** | solo-reviewer (High) |

**Issue:** `evalSubquery` now merges the subquery's `SamplesRead` into the parent (`parentSamplesStats.MergeSamplesReadFromSubquery`). But the subquery result is then materialized as a `MatrixSelector` and the enclosing range-vector step loop counts those same points *again* at `engine.go:2184`. The deleted comment on the line this replaces stated the reason precisely: *"Avoid double counting samples when running a subquery, those samples will be counted in later stage."* That is exactly the double count reintroduced. The result is not an approximation of I/O in either direction: it is strictly larger than the number of samples the storage layer produced, and larger than `totalQueryableSamples` itself, which is meant to be the *over*-counting metric.

**Evidence:** Executed, per-step stats enabled, `m3` = 2 series at 10 s resolution:

| query | kind | `totalQueryableSamples` | `samplesRead` |
|---|---|---|---|
| `max_over_time(m1[60s:5s])` | instant | 12 | **24** |
| `count_over_time(m1[60s:1s])` | instant | 60 | **120** |
| `max_over_time(m3[60s:5s])` | instant | 36 | **72** |
| `sum_over_time(max_over_time(m3[60s])[5m:1m])` | instant | 10 | **70** |
| `avg_over_time(rate(m3[1m])[5m:30s])` | instant | 20 | **86** |
| `histogram_count(max_over_time(mh[20s:10s]))` | range (4 steps) | 182 | **208** |

For every instant subquery the ratio is exactly 2.0 — each sample counted once by the inner selector and once by the outer window. The new tests bake this in and label it as intended (`promql/engine_test.go:1548` `SamplesRead: 2, // subquery + outer`; `:1789-1797` `TotalSamples: 26` / `SamplesRead: 52`; `:1817-1825` `9` / `18`). That is a counter-argument, not a defense: the same PR documents the opposite contract at `docs/feature_flags.md:48` ("Total number of samples *read* (I/O) … For other query types, this equals totalQueryableSamples").

**Fix:** Pick one attribution point. Either merge the subquery's `SamplesRead` and suppress the outer loop's re-count of a materialized subquery matrix, or drop `MergeSamplesReadFromSubquery` and keep only the outer count (mirroring how `TotalSamples` already avoids this).

### #3 🟠 High: silent regression of `totalQueryableSamples` and `prometheus_engine_query_samples_total` for `@`-modified range selectors

| | |
|---|---|
| **File** | `promql/engine.go:2156-2166`, increment at `:2183` |
| **Category** | api-design |
| **Confidence** | 100 |
| **Verified** | executed |
| **Pre-existing** | no |
| **Found by** | solo-reviewer (High) |

**Issue:** `fullWindowCount` is declared at `:2158` and assigned only inside the `if ts == ev.startTimestamp || selVS.Timestamp == nil` block. On a reuse step (`selVS.Timestamp != nil`, `ts != ev.startTimestamp`) it stays 0, so `IncrementSamplesAtStep(step, fullWindowCount)` at `:2183` adds nothing. The previous code passed `int64(len(floats)+totalHPointSize(histograms))` — the *retained* slices from step 0 — so every step counted the full window. This changes the existing, stable `totalQueryableSamples` / `totalQueryableSamplesPerStep` statistic and the `prometheus_engine_query_samples_total` counter, regardless of the feature flag, contrary to the change's stated intent that those semantics are unchanged. The inline comment at `:2156-2157` shows the change was deliberate, but the stated intent says the opposite.

The reuse path is reachable in a multi-step range evaluation whenever a range-vector function has an `@`-anchored matrix selector *and* a non-step-invariant argument: `preprocessExprHelper` never wraps a `MatrixSelector` in a `StepInvariantExpr` (`promql/engine.go:4364-4367`, `:4357-4361`), so the `Call` is evaluated step by step with `selVS.Timestamp != nil`.

**Evidence:** Executed, same storage and range (start 201 s, end 220 s, step 5 s) on both commits:

| query | base `TotalSamples` / perStep | HEAD `TotalSamples` / perStep |
|---|---|---|
| `quantile_over_time(scalar(m1), m3[60s] @ 30)` | 52 / `{13,13,13,13}` | **16** / `{13,1,1,1}` |
| `predict_linear(m3[60s] @ 30, scalar(m1))` | 52 / `{13,13,13,13}` | **16** / `{13,1,1,1}` |

All 12 other shapes compared were identical, and `PeakSamples` was unchanged everywhere — so this is an isolated, silent change, and no existing expected value in `TestQueryStatistics` was updated to reflect it (the diff removes no expectation lines), which is why the suite still passes.

**Fix:** If `totalQueryableSamples` is to keep its meaning, restore the full-window count on reuse steps: assign `fullWindowCount = int64(len(floats) + totalHPointSize(histograms))` unconditionally after the `if`, and leave only `samplesReadCount` at 0 for reuse steps. If the change is intentional, it is a breaking change to a documented statistic and a server metric and needs to be called out and covered by a test.

### #4 🟠 High: `countSamplesAfter` adds an O(window) scan per step per series to the range-vector hot loop — ~25% slower `rate()`

| | |
|---|---|
| **File** | `promql/value.go:195-208`, call site `promql/engine.go:2164` |
| **Category** | efficiency |
| **Confidence** | 100 |
| **Verified** | executed |
| **Pre-existing** | no |
| **Found by** | solo-reviewer (High) |

**Issue:** `countSamplesAfter` scans the entire retained window from the front on every step of every series, to count the handful of points newer than `maxt-ev.interval`. Total cost is O(window_points × steps × series) where the answer is obtainable in O(new points): both slices are sorted ascending by `T`, so a reverse scan from the tail (or `sort.Search`) stops as soon as `T <= cutoff`. This runs unconditionally — `SamplesRead` is tracked even when the caller requested no statistics at all — so it taxes every range-vector range query in the server.

**Evidence:** Executed. `rate(m1[1h])`, 1 s-resolution series, range 3600 s→7200 s at 15 s steps (240 steps × 3600-point window), `-cpu 1 -benchtime 30x -count 6`:

- base `efbdc3f88`: 1.303, 1.346, 1.391, 1.301, 1.341, 1.330 ms/op (median ≈1.34)
- HEAD `ec7157593`: 1.673, 1.669, 1.711, 1.628, 1.703, 1.646 ms/op (median ≈1.67) — **+25%**, non-overlapping distributions

Mutation probe under the snapshot protocol (`promql/engine.go:2164` replaced with `samplesReadCount = 0`, then restored, verified byte-identical with `cmp`, tests re-run green): 1.288, 1.435, 1.346, 1.311, 1.299, 1.345 ms/op — median ≈1.32, back at base. The entire regression is attributable to this one call.

**Fix:** Iterate both slices backwards from the tail and break on the first `T <= cutoff`. Equivalently, since the newly buffered points are exactly those with `T > maxt-ev.interval`, the count can be derived from the growth of the slices across steps without any scan.

### #5 🟡 Medium: the documented and schema-published contract for `samplesRead` is not the implemented behavior

| | |
|---|---|
| **File** | `docs/feature_flags.md:48`, `docs/querying/api.md:247`, `web/api/v1/openapi_schemas.go:593-595` |
| **Category** | production |
| **Confidence** | 100 |
| **Verified** | executed |
| **Pre-existing** | no |
| **Found by** | solo-reviewer (Medium) |

**Issue:** All three places state that for anything other than range-vector functions in range queries, `samplesRead` equals `totalQueryableSamples`. It does not, in two distinct directions:

- **Lower**, for `@`-modified / step-invariant expressions, which are not range-vector functions: `metricWith3SampleEvery10Seconds @ 15` over 4 steps gives `totalQueryableSamples=12`, `samplesRead=3`; `sum(metricWith3SampleEvery10Seconds @ 15)` likewise 12 vs 3; `topk(1, sum_over_time(m3[50s] @ 100))` 70 vs 10. The `StepInvariantExpr` branch (`promql/engine.go:2471`) deliberately adds `SamplesRead` once at step 0 — correct behavior, undocumented.
- **Higher**, for subqueries (finding #2): 12 vs 24, 60 vs 120, 10 vs 70.

The OpenAPI description is shipped to clients in both golden schemas, so the wrong contract propagates to generated SDKs.

**Evidence:** Executed; the numbers above come from the probe table in findings #2 and from a range-query run over 12 shapes at HEAD with per-step stats enabled.

**Fix:** Rewrite the three descriptions to state the actual rule — full-window count at step 0 and per-step deltas for range-vector functions in range queries; once per query (attributed to step 0) for step-invariant subexpressions; equal to `totalQueryableSamples` for plain selectors — and correct the subquery statement once finding #2 is resolved.
