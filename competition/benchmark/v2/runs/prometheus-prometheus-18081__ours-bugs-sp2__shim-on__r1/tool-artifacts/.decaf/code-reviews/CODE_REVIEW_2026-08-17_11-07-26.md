## Findings

### #1 🟠 High: `@`-modifier range-vector queries silently stop counting `TotalSamples` per step

| | |
|---|---|
| **File** | `promql/engine.go:2145` (also `2160`, `2183`) |
| **Category** | correctness |
| **Confidence** | 100 |
| **Verified** | executed |
| **Pre-existing** | no |
| **Found by** | solo-reviewer (High) |

**Issue:** `fullWindowCount` is declared inside the per-step loop and only assigned inside the `if ts == ev.startTimestamp || selVS.Timestamp == nil` block. When the `@`-modifier data-reuse path skips re-evaluation, `fullWindowCount` stays `0`, so line 2183 calls `IncrementSamplesAtStep(step, 0)`. The old code computed the count at the increment site from the *retained* `floats`/`histograms`, so it counted the full window at every step. This silently changes the existing, user-visible `totalQueryableSamples` / `totalQueryableSamplesPerStep` API fields and the existing `prometheus_engine_query_samples_total` counter — the comment on line 2143 claims "unchanged semantics", and `docs/feature_flags.md:47` (added by this same change) states that for range-vector functions "each step counts the full window", which this makes false.

**Evidence:** executed. Built an out-of-tree harness against both `ec7157593` and the base `efbdc3f88` (extracted via `git archive`, no worktree mutation), query `predict_linear(metricWith1SampleEvery10Seconds[60s] @ 30, 60)`, range `201s→291s` step `30s`:

```
base (efbdc3f88):  TotalSamples=16  perStep={201000:4 231000:4 261000:4 291000:4}
new  (ec7157593):  TotalSamples=4   perStep={201000:4 231000:0 261000:0 291000:0}
```

The reuse path is reachable because `predict_linear` is in `AtModifierUnsafeFunctions` (`promql/functions.go:2248`), so the `Call` is never wrapped in a `StepInvariantExpr`, while `selVS.Timestamp != nil` from the `@`. Any range function with a non-step-invariant scalar argument (e.g. `quantile_over_time(scalar(x), m[5m] @ 100)`) hits the same path. `go test ./promql/ -run TestQueryStatistics` passes — no test covers this shape, so the regression ships silently.

**Fix:** compute `fullWindowCount` unconditionally at the increment site as before, and only make `samplesReadCount` conditional:

```go
fullWindowCount := int64(len(floats) + totalHPointSize(histograms))
ev.samplesStats.IncrementSamplesAtStep(step, fullWindowCount)
ev.samplesStats.IncrementSamplesReadAtStep(step, samplesReadCount)
```

with `samplesReadCount` left at 0 on the reuse path (which is correct — no I/O happens there).

### #2 🟠 High: `SamplesRead` double-counts subqueries, compounding with nesting depth

| | |
|---|---|
| **File** | `promql/engine.go:1874` (with `2184`) |
| **Category** | correctness |
| **Confidence** | 100 |
| **Verified** | executed |
| **Pre-existing** | no |
| **Found by** | solo-reviewer (High) |

**Issue:** `evalSubquery` replaces the `SubqueryExpr` with an **in-memory** `MatrixSelector` whose `VectorSelector.Series` is the subquery's result matrix (`engine.go:2004-2016`), and merges the subquery's storage reads into the parent (`MergeSamplesReadFromSubquery`, line 1874). The range-vector loop then iterates that synthetic matrix and calls `IncrementSamplesReadAtStep` on it again at line 2184. So every derived point is counted as a "sample read" on top of the raw reads that produced it. Nothing in this path touches storage, so those counts are not I/O at all. The pre-existing design deliberately avoided this for `TotalSamples` (the old `NewChild()` discarded the inner counts — "Avoid double counting samples when running a subquery"); the new code re-introduces exactly that double count for `SamplesRead`.

Consequences: `samplesRead` exceeds `totalQueryableSamples` (inverting the documented "reads are a subset of loads" framing), and the claim at `docs/feature_flags.md:48` / `docs/querying/api.md:247` — "For other query types, this equals totalQueryableSamples" — is false for any function over a subquery.

**Evidence:** executed, instant query at t=600s over `m 1+1x1000` (10s scrape):

```
m[1m:20s]                                                 Total= 3  Read= 3
max_over_time(m[1m:20s])                                  Total= 3  Read= 6   <- 2x
sum_over_time(max_over_time(m[1m:20s])[5m:1m])            Total= 5  Read=35
sum_over_time(sum_over_time(max_over_time(m[1m:20s])[5m:1m])[20m:5m])
                                                          Total= 3  Read=76
```

The same underlying I/O reports `3` as a bare subquery and `6` once a function wraps it. The added tests encode this: `engine_test.go:1168-1187` asserts `TotalSamples: 36 / SamplesRead: 72` for `max_over_time(metricWith3SampleEvery10Seconds[60s:5s])` — exactly 36 inner reads plus 36 re-reads of the subquery's own output — and `engine_test.go:1548` labels it `// subquery + outer`. Per the fail-closed rule this is reported rather than parked: a test comment asserting the doubling is intended is not evidence that the metric is correct, and the docs added by this same change state the opposite.

**Fix:** either skip `IncrementSamplesReadAtStep` when the matrix argument came from `evalSubquery` (thread a flag out of `evalSubquery`, mirroring how `TotalSamples` already avoids the inner counts), or drop `MergeSamplesReadFromSubquery` and count only the outer layer. Whichever is chosen, the docs' "equals totalQueryableSamples for other query types" claim needs to be corrected or made true.

### #3 🟠 High: `countSamplesAfter` adds a full-window scan per step — ~10% slowdown on large-window range queries

| | |
|---|---|
| **File** | `promql/value.go:195` (called at `promql/engine.go:2164`) |
| **Category** | production |
| **Confidence** | 100 |
| **Verified** | executed |
| **Pre-existing** | no |
| **Found by** | solo-reviewer (High) |

**Issue:** `countSamplesAfter` scans **every** point in the window at **every** step, purely to count the tail. The old code needed only `len(floats)` (O(1)) plus `totalHPointSize(histograms)`. Because `floats`/`histograms` are ascending in `T`, the same answer is obtainable in O(new points) by scanning backwards from the end (or by capturing the retained length before `matrixIterSlice`). This runs unconditionally — `ev.samplesStats` is always live, regardless of whether the caller requested `stats`.

**Evidence:** executed. `go test ./promql/ -run XXX -bench 'BenchmarkRangeQuery/expr=changes\(a_one\[1d\]\),steps=1000' -benchtime 5x -count=6`, new tree vs. the base tree extracted to a temp dir:

```
base (efbdc3f88): 47.99  48.21  48.66  48.68  48.79  48.96  ms/op
new  (ec7157593): 53.47  53.48  53.67  53.96  54.31  54.65  ms/op
```

Ranges do not overlap; ~+10.5%. The workload is a 1d window (8640 points) over 1000 steps = 8.64M extra comparisons, and the measured delta (~5.2 ms) matches at ~0.6 ns/iteration. Allocation counts are unchanged, and the only added per-step work in that loop is this scan. A second case, `rate(a_hundred[1m]),steps=10000` (6M extra comparisons), shows ~+7% with slightly overlapping ranges — directionally consistent but not sufficient on its own.

**Fix:**

```go
func countSamplesAfter(floats []FPoint, histograms []HPoint, cutoff int64) int64 {
	var n int64
	for i := len(floats) - 1; i >= 0 && floats[i].T > cutoff; i-- {
		n++
	}
	for i := len(histograms) - 1; i >= 0 && histograms[i].T > cutoff; i-- {
		n += int64(histograms[i].size())
	}
	return n
}
```

A comment should record that this relies on both slices being ascending in `T`, which `matrixIterSlice` guarantees.

### #4 🟢 Low: subquery children now allocate two per-step arrays that are largely discarded

| | |
|---|---|
| **File** | `promql/engine.go:1869` (also `2397`, `util/stats/query_stats.go:411`) |
| **Category** | production |
| **Confidence** | 75 |
| **Verified** | traced |
| **Pre-existing** | no |
| **Found by** | solo-reviewer (Low) |

**Issue:** the old `NewChild()` returned `NewQuerySamples(false)`, so subquery children never allocated per-step arrays. `NewChildWithStepTracking` now calls `InitStepTracking`, which allocates **both** `TotalSamplesPerStep` and `SamplesReadPerStep` (`query_stats.go:305-306`) for every subquery evaluation whenever the `promql-per-step-stats` flag and `stats=all` are in play. The `TotalSamplesPerStep` array is pure waste — `MergeSamplesReadFromSubquery` deliberately never merges it (`query_stats.go:419-431`), and nothing else reads it.

**Evidence:** traced. `stats.NewChildWithStepTracking(..., subqStart, subqEnd, subqInterval)` at `engine.go:2397` sizes the arrays to the *subquery's* step count. For `sum_over_time(m[1d:1s])` that is 86400 steps → 2 × 86400 × 8 B ≈ 1.4 MB per evaluation, half of it never read. `engine.go:1869` additionally allocates two arrays sized to the outer query's step count per subquery argument.

**Fix:** have `InitStepTracking` (or a variant used here) allocate only `SamplesReadPerStep` for subquery children, since `TotalSamplesPerStep` is by design not propagated out of a subquery.

### Considered But Not Flagged (solo-reviewer)

- **Index-out-of-range at `engine.go:2441` (`outerStep = numOuterSteps - 1`) when `numOuterSteps == 0`** — anchor 0, traced and found unreachable. `InitStepTracking` computes `int((end-start)/interval)+1`; for the subquery child, `subqStart ∈ (start-offset-range, start-offset-range+interval]` (lines 2391-2394), so `subqEnd - subqStart > (end-start) + range - interval > -interval`, and Go's truncating division yields `0`, never `-1`. Length is therefore always ≥ 1 and `make` is never called with a negative length. Probed with degenerate shapes (`sum_over_time(sum_over_time(m[5m:1m])[1s:1h])`, `sum_over_time(sum_over_time(m[1s:1h])[1s:1h])`, negative offsets, instant and range) — no panic, all returned `readPerStep` maps of length ≥ 1.
- **Division by zero on `ev.samplesStats.Interval` at `engine.go:2437`** — anchor 0. `Interval` is only non-zero-initialized together with the slice being allocated (`query_stats.go:304-308`), and the guard at line 2425 requires the slice to be non-nil. Instant queries use `InitStepTracking(start, start, 1)` (`engine.go:815`).
- **`countSamplesAfter` mis-identifying "new points" for `Anchored`/`Smoothed` selectors** — anchor 0, traced. The cutoff `maxt - ev.interval` uses the already-extended `maxt`, and the previous step's extended `maxt` is exactly `maxt - ev.interval`, so the delta is correct. Likewise the `continue` at line 2166 cannot lose a non-zero count: if step *n*'s window is empty, any point in step *n+1*'s window at or below `maxt_n` would necessarily have been in window *n*.
- **`SamplesRead` counting the same raw sample once per step for plain instant-vector selectors** (`engine.go:1818`, `1841`) — anchor 25 as a defect. It over-states I/O for step < scrape-interval queries, but the docs explicitly scope the delta optimization to range-vector functions, so this could not be distinguished from the stated design.

- **`docs/feature_flags.md:44-50` documents `samplesRead` and `prometheus_engine_query_samples_read_total` under the `promql-per-step-stats` flag, though neither is gated by it** — minor, out of reach; the section already had this shape for `totalQueryableSamples`.
