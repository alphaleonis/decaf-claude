**Verdict**: ❌ NEEDS_CHANGES

The change's stated goal — reject malformed slash-command responses — is sound, and the three new tests are real guards (probe-confirmed, not false positives). ## Findings

### #1 🟠 High: The new validation is bypassable by a single response header — the plain-text branch is never validated

| | |
|---|---|
| **File** | `server/public/model/command_response.go:35-49` (bypass), `:72` (gate) |
| **Category** | api-design / input-validation |
| **Confidence** | 100 (probe-verified) |
| **Found by** | broad-reviewer (High), adversarial-reviewer (High), security-reviewer (Medium), quick-reviewer (Low) |

**Issue:** `CommandResponseFromHTTPBody` routes to `CommandResponseFromJSON` — and therefore to `IsValid` — only when the `Content-Type` is exactly `application/json`. Every other content type, including an absent one, falls to `CommandResponseFromPlainText` (`:45-49`), which constructs a `CommandResponse` and never validates it. The party the gate is meant to constrain picks which branch runs.

Verified by execution:

```
text/plain,       100000 bytes: err=<nil>, textLen=100000   ← accepted
application/json, same text:    err=model.command_response.is_valid.text.app_error  ← rejected
empty Content-Type, same text:  err=<nil>, textLen=100000   ← accepted
```

Both untrusted callers control that header: the admin-configured slash-command server whose response is parsed at `server/channels/app/command.go:595`, and any client of `POST /hooks/commands/{id}` at `server/channels/web/webhook.go:114` (registered `APIHandlerTrustRequester` — no session; the hook ID is the only credential). The effective ceiling on the plain-text branch is `MaxIntegrationResponseSize` (1 MB) on the command path and `ServiceSettings.MaximumPayloadSizeBytes` (default 300000) on the webhook path.

Because the invariant is header-selectable, no downstream code can rely on it — which undercuts the premise of adding it.

**Fix:** Make validation a property of construction rather than of one decoder — call `IsValid()` in `CommandResponseFromHTTPBody` after both branches:

```go
func CommandResponseFromHTTPBody(contentType string, body io.Reader) (*CommandResponse, error) {
	if strings.TrimSpace(strings.Split(contentType, ";")[0]) == "application/json" {
		return CommandResponseFromJSON(body)
	}
	if b, err := io.ReadAll(body); err == nil {
		resp := CommandResponseFromPlainText(string(b))
		if err := resp.IsValid(); err != nil {
			return nil, err
		}
		return resp, nil
	}
	return nil, nil
}
```

### #2 🟠 High: One invalid nested `extra_responses` entry now fails the whole response — a partial success becomes a total failure with no posts and an HTTP 500

| | |
|---|---|
| **File** | `server/public/model/command_response.go:72`, `:90-98` |
| **Category** | error-handling / behavior-regression |
| **Confidence** | 100 (validator confirmed) |
| **Found by** | adversarial-reviewer (High) |

**Issue:** `IsValid` recurses into `ExtraResponses` and returns on the first failure, so the whole payload is rejected at parse time. Consider an integration returning:

```json
{"response_type":"in_channel","text":"deploy done",
 "extra_responses":[{"response_type":"comment","text":"logs"}]}
```

- **Before:** `CreateCommandPost` (`server/channels/app/command.go:73-84`) branches only on `in_channel` and on `"" || ephemeral`. A `response_type` of `comment` matches neither and falls through to `return post, nil` — **no error, no post, silent no-op**. `HandleCommandResponse`'s `lastError` accumulator is never set. The main post is created; the bad extra silently vanishes.
- **After:** parsing fails before `HandleCommandResponse` is ever reached. At `command.go:595-597` the error is wrapped into `api.command.execute_command.failed.app_error` with HTTP 500. **Neither the main post nor any extra is created.**

The commit's own new test case (`command_response_test.go:171-182`) asserts exactly this shape — valid main, invalid nested — errors, so the all-or-nothing behavior is deliberate rather than an oversight. It is still a regression in blast radius: a field the server previously ignored now destroys a response that would otherwise have posted correctly.

Note `response_type: "comment"` is not a strawman — `OutgoingHookResponseTypeComment` is a real constant in this codebase, and integration authors routinely reuse outgoing-webhook vocabulary against slash commands.

**Fix:** Validate per-response at the consumption site (`HandleCommandResponse`), skipping and logging invalid extras, rather than making one nested field fatal to the whole payload at parse time. If the parse-time gate is kept, at minimum restrict it to the top-level response so a bad extra degrades as it did before.

### #3 🟠 High: Validation is applied on the read side only — the server can emit responses that its own `Client4` now rejects

| | |
|---|---|
| **File** | `server/public/model/command_response.go:72` |
| **Category** | api-design |
| **Confidence** | 100 (validator confirmed both routes) |
| **Found by** | adversarial-reviewer (High), security-reviewer (Medium) |

**Issue:** `server/channels/api4/command.go` serializes the `*model.CommandResponse` returned by `App.ExecuteCommand` with `json.NewEncoder(w).Encode(response)` and never calls `IsValid`, while `Client4.ExecuteCommand` / `ExecuteCommandWithTeam` (`server/public/model/client4.go:5961`, `:5982`) parse the server's own reply through `CommandResponseFromJSON`, which now hard-fails. Two confirmed routes:

- **(b) No plugin required.** An outgoing slash-command server replies `text/plain` with a body over 65535 bytes. Per finding #1 that passes unvalidated, `HandleCommandResponsePost` creates the post (the side effect happens), `api4` encodes the object verbatim, and `Client4` then rejects the server's own response with `text is too long`. The caller sees the command as failed while the post exists.
- **(a)** `tryExecutePluginCommand` (`server/channels/app/plugin_commands.go:165`) takes the plugin hook's return value verbatim — `ResponseType` is a free-form string — into the same unchecked `api4` encode.

The validator noted this is not confined to external consumers: `Client4.ExecuteCommand` is exercised by 25+ call sites in the server's own `server/channels/api4/commands_test.go` integration suite.

**Fix:** Enforce the contract where the value is produced — validate in the `api4` execute handler (and when accepting a plugin command response) so the server cannot emit what its clients reject — or keep `Client4` lenient and confine the gate to the inbound third-party direction. Applying it to both directions with validation on only one is the one combination that cannot hold.

### #4 🟠 High: Hardcoded 65535-**byte** cap contradicts the deployment-configurable, rune-based post size limit

| | |
|---|---|
| **File** | `server/public/model/command_response.go:85-88` |
| **Category** | api-design |
| **Confidence** | 100 (validator confirmed; scope narrowed) |
| **Found by** | broad-reviewer (High), adversarial-reviewer (High) |

**Issue:** The authoritative limit on this text is decided at runtime by `determineMaxPostSize` (`server/channels/store/sqlstore/post_store.go:2640-2663`), whose own comment states the `posts.message` column "may be manually enlarged to support longer posts", yielding `max(column_bytes/4, PostMessageMaxRunesV2)` **runes**. `Post.IsValid` (`server/public/model/post.go:508`) measures with `utf8.RuneCountInString` against that runtime value. The new check measures bytes against a constant inside a released module that no deployment configuration can raise.

Validator scoping, which the finding should be read with: under the **default** Postgres schema (`posts.message` VARCHAR(65535)) the runtime cap is `max(65535/4, 16383) = 16383` runes, so for worst-case 4-byte runes the two gates roughly coincide and there is no default-config regression. The break is on enlarged-column deployments — a documented, supported operation — where `GetMaxPostSize()` can exceed 65535 runes and an ASCII payload of, say, 200 KB that `Post.IsValid` would accept is now rejected earlier by the fixed byte cap, surfacing as a 500 (per finding #10).

**Fix:** Measure runes against the package's own derived constant, so the two limits cannot disagree:

```go
if utf8.RuneCountInString(o.Text) > PostMessageMaxRunesV2 {
	return NewAppError("CommandResponse.IsValid", "model.command_response.is_valid.text.app_error",
		map[string]any{"MaxLength": PostMessageMaxRunesV2}, "text is too long", http.StatusBadRequest)
}
```

Do **not** take the "drop the check entirely" alternative without care: the validator found that `SendEphemeralPost` (`server/channels/app/post.go:692`) never calls `Post.IsValid`, so for ephemeral command responses this new check is currently the only size gate on that path.

### #7 🟡 Medium: `IsValid` recurses to unlimited depth, but the consumer only ever processes one level of `extra_responses`

| | |
|---|---|
| **File** | `server/public/model/command_response.go:90-98` |
| **Category** | api-design |
| **Confidence** | 100 |
| **Found by** | adversarial-reviewer (Medium), broad-reviewer (Medium) |

**Issue:** Both consumers are single-level. `HandleCommandResponse` (`server/channels/app/command.go:620-635`) iterates `response.ExtraResponses` exactly once; a nested response's own `ExtraResponses` is never posted. The pre-existing attachment-stringification loop in this same file (`:65-70`) is likewise one level deep. Only the new validation recurses.

Consequence: a payload whose **second-level** nested response carries a bogus `response_type` — content the server would discard without ever reading — now fails the entire command, including the top-level text and the first-level extras that would have posted fine. The validator is strictly stricter than the code it protects.

**Fix:** Bound the validation to the depth the consumer actually processes (one level), matching the attachment loop, or explicitly reject payloads containing nested `extra_responses` so validation and consumption agree on the accepted shape.

### #8 🟡 Medium: The new validation's tests leave the accepting boundary and the error identity unpinned

| | |
|---|---|
| **File** | `server/public/model/command_response_test.go:159-182`, `:235-237` |
| **Category** | test-coverage |
| **Confidence** | 100 (boundary gap probe-proven) |
| **Found by** | test-reviewer (Medium ×3, Low ×1), broad-reviewer (Medium), security-reviewer (Low) |

**Issue:** The three new cases are genuine guards — each probe that neutralized its production branch made the corresponding test fail. The gaps are in what is *not* covered:

1. **The accepting boundary is unguarded.** Only `strings.Repeat("a", 65536)` is tested. Mutating `>` to `>=` at `command_response.go:86` was run and **no test failed** — an off-by-one tightening ships silently. A case at exactly 65535 asserting success is missing.

5. **`CommandResponseFromHTTPBody` is untested for the bypass in finding #1** — a regression there would be invisible to the suite.

### P2 🟡 Medium: `ExtraResponses` has no count bound, and the new recursive validator is the natural place for one

| | |
|---|---|
| **File** | `server/public/model/command_response.go:90` |
| **Category** | resource-bounds |
| **Confidence** | 75 |
| **Found by** | security-reviewer (Medium, self-marked pre-existing) |

## Specialist Notes

### Threat Model Notes (security-reviewer)

- **Trust boundaries crossed by this function** — three, with different adversaries: (a) HTTP responses from admin-configured but third-party-operated slash-command servers (`server/channels/app/command.go:595`); (b) `POST /hooks/commands/{id}`, registered `APIHandlerTrustRequester` (`server/channels/web/webhook.go:21`) — no session, the hook ID is the only credential, and `CommandWebhook().TryUse(hook.Id, 5)` caps reuse at five; (c) the Mattermost server's own reply parsed by `Client4`, where the "untrusted" party is the peer server.
- **Attack surface change** — no new endpoint. The change converts previously-tolerated inputs into hard failures, shifting risk from silent-acceptance toward availability: on the command path a rejection becomes a 500 with the whole response discarded.
- **Data sensitivity** — command response text becomes post content; no credentials or PII flow through the validated fields.
- **Not verified empirically** — the `ExtraResponses` fan-out volume (P2) was read off the call graph, not measured.

### Considered But Not Flagged (all agents, plus orchestrator probe results)

**Refuted by probe or by code reading:**

- **Stack exhaustion via deeply nested `extra_responses`** — dismissed by three reviewers and refuted by probe: nesting at 1000 and 4000 levels validates cleanly; 6000 is rejected by `encoding/json`'s `maxNestingDepth = 10000` scanner limit before `IsValid` runs. Go's growable stacks handle the reachable depth trivially. Only the *explicitness* of the bound is at issue (go-reviewer, Low, anchor 50) — not flagged, since the behavior is correct today.
- **Typed-nil `*AppError` boxed as a non-nil `error`** — the classic Go trap does not apply. At both assignment points (`command_response.go:72` and `:95`) `err` is declared as the concrete `*AppError` via `:=` and the nil check happens before any interface conversion. Verified independently by go-reviewer and broad-reviewer. Anchor 0.
- **Empty `response_type` wrongly rejected** — probe: `{"text":"hi"}` is accepted. The `!= ""` clause is correct.
- **`nil` entries in `extra_responses` causing a panic** — probe: `{"text":"hi","extra_responses":[null]}` is accepted; the `resp == nil` guard at `:91` works (though it is untested — see #8).
- **"Wrong unit" half of the byte-vs-rune claim** — weak. `PostMessageMaxBytesV2 = 65535` is the byte-based storage ground truth and `PostMessageMaxRunesV2` is derived from it as a conservative approximation, so a byte check is defensible in isolation. The strong half — that the constant is unconfigurable while the real limit is not — survives as finding #4.
- **`t.Parallel()` with the `testCase` loop variable** — `server/public/go.mod` declares Go 1.26.3; per-iteration loop variables apply. Anchor 0.

**Examined and dismissed on downstream guards:**

- **`GotoLocation` left unvalidated by the new `IsValid`** — a malicious slash-command server can set an arbitrary `goto_location`, but the consumer guards it: `webapp/channels/src/actions/command.ts:203` gates on `isUrlSafe` before navigating.
- **`DetailedError` leaking to the end user** — `NewAppError` carries "invalid response type" / "text is too long" as details, but `server/channels/web/handlers.go:427` calls `WipeDetailed()` whenever `EnableDeveloper` is false.
- **Unbounded `Attachments` text as an alternate channel around the `Text` bound** — real, but bounded downstream at `PostPropsMaxRunes = 800000` (`post.go:566`). Not a new gap.
- **Retry storm against the delayed-response endpoint** — parse failure returns 400 *before* `CommandWebhook.TryUse(hook.Id, 5)`, so a retrying integration never burns its five uses and can re-fail indefinitely. The amplification lives entirely in third-party retry logic that could not be inspected; a required step is unconfirmed. Anchor 25.
- **Non-recursive `Attachments` stringify loop (`:65-70`) vs. the recursive new `IsValid` loop** — a real asymmetry, but `IsValid` never inspects `Attachments`, so the two do not interact. Pre-existing; folded into finding #7's framing.
- **Top-level `response_type: "comment"` becoming fatal** — not a regression on its own: `CreateCommandPost` already fell through both branches for unknown types, so nothing was posted before either. Only the `extra_responses` variant (finding #2) turns a partial success into a total failure.

**Positive observations worth keeping:**

- The three new test cases are genuine guards, not tautologies — each probe that neutralized its production branch made exactly the expected test fail.
- Adding `assert.Error(t, err)` at `:236` closes a real pre-existing gap: the "empty response", "malformed response", and "invalid response" cases previously asserted only `assert.Nil(t, response)`, which an unexpected `(nil, nil)` return would have satisfied.
- The `resp == nil` guard at `:91` correctly mirrors the existing guard in the attachment loop at `:66`.
- Validation is correctly placed *after* attachment stringification, so it observes the same object the caller receives.
- The error-ID naming follows the established `model.<type>.is_valid.<field>.app_error` shape.
