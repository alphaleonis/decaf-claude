## Findings

### #1 🔴 Critical: Deleting the already-merged `ConvertNegativeRatingToNull` migration makes any database that ran it fail to boot

| | |
|---|---|
| **File** | `server/src/schema/migrations/1780592070031-ConvertNegativeRatingToNull.ts` (deleted); mechanism at `server/src/repositories/database.repository.ts:371-394` and `:510-523` |
| **Category** | data-migration / production-reliability |
| **Confidence** | 100 (validator-confirmed; finders 75–100) |
| **Found by** | broad-reviewer (Critical), data-migration-reviewer (Critical ×2), adversarial-reviewer (High) |

**Issue:** The diff deletes `1780592070031-ConvertNegativeRatingToNull.ts`, which was merged to `main`
in commit `99281de` on **2026-06-04** and deleted three days later in `6c9a6e7` (2026-06-07). Kysely
matches migrations by exact filename, and its missing-migration check is unconditional:

- `DatabaseRepository.createMigrator()` (`database.repository.ts:510-523`) uses a stock
  `FileMigrationProvider` over `schema/migrations` with `migrationTableName: 'kysely_migrations'`.
- Installed kysely 0.28.17 `migrator.js` calls `#ensureNoMissingMigrations(...)` at line 447,
  **before** the `allowUnorderedMigrations` gate at line 448 — that flag (`isDev()`) only relaxes the
  separate ordering check. `#ensureNoMissingMigrations` (lines 491-498) throws
  `corrupted migrations: previously executed migration 1780592070031-ConvertNegativeRatingToNull is missing`
  for any recorded name with no file on disk.
- `runMigrations()` (`database.repository.ts:390-393`) rethrows: `if (error) { … throw error; }`.
- `DatabaseService.onBootstrap()` (`database.service.ts:114-116`) calls it unconditionally unless
  `DB_SKIP_MIGRATIONS` is set. The validator traced the error upward through
  `event.repository.ts:227-237` (a plain `for` loop awaiting each `AppBootstrap` handler, no
  `try/catch`) and `app.module.ts`'s `onModuleInit` — **the throw is unguarded all the way up**. There
  is no degraded-start path, no `NO_MIGRATIONS` tolerance, and no automatic `kysely_migrations`
  reconciliation anywhere in the codebase. `immich-admin schema-check` *does* detect this exact
  condition (`status: 'deleted'`), but it is a manual CLI diagnostic and boot crashes first.

Affected instances restart-loop until an operator manually runs
`DELETE FROM kysely_migrations WHERE name = '1780592070031-ConvertNegativeRatingToNull'`.

**Is the affected population real?** Yes, likely rather than speculative:
- `.github/workflows/docker.yml` pushes `ghcr.io` images on **every push to `main`**, so the
  migration was live on a published track for 3 days.
- The migration immediately following it, `1780592071031-AssetOcrSync.ts`, is **retained** — any
  instance that ran it necessarily ran the deleted one first (kysely applies in order).
- This has already happened once in this repo: `0975b15 fix: remove stray migration (#28565)` deleted
  `1773175313374-Test.ts` four days after `3d075f2` added it — same pattern, same unreconciled
  bookkeeping row.

**Second consequence, same root cause — irreversible data loss.** Every instance that ran the
migration executed `UPDATE "asset_exif" SET "rating" = NULL WHERE "rating" = -1;` **in place**, and
`down()` is an explicit no-op (`// not supported`). Those `-1` values are unrecoverable, and a
formerly-`-1` row is now indistinguishable from a genuinely unrated one. This change re-permits `-1`
going forward while shipping nothing to reconcile — or even acknowledge — the destroyed data.

**Fix:** Do not delete an already-merged migration. Either keep the file as a no-op tombstone so the
recorded name still resolves:

```ts
// server/src/schema/migrations/1780592070031-ConvertNegativeRatingToNull.ts
// Retained as a tombstone: the -1 -> NULL conversion was reverted in the application layer,
// but the name must stay resolvable for databases that already recorded it.
export async function up(): Promise<void> {}
export async function down(): Promise<void> {}
```

…or, if the file must go, ship a *preceding* migration that removes the bookkeeping row before the
file disappears. Separately, state the irreversible loss of previously-converted `-1` ratings in the
release notes.

### #2 🔴 Critical: A `-1` rating accepted by the API is silently reset to NULL by the server's own job pipeline

| | |
|---|---|
| **File** | `server/src/services/metadata.service.ts:308` |
| **Category** | async / composition |
| **Confidence** | 100 (validator-confirmed; finders 75–100) |
| **Found by** | adversarial-reviewer (Critical), broad-reviewer (High — bundled with two sibling sites) |

**Issue:** Commit `99281de` changed **four** server files; this change reverts only `asset.dto.ts`. It
leaves `metadata.service.ts:308` at the restricted bound:

```ts
rating: exifTags.Rating === 0 ? null : validateRange(exifTags.Rating, 1, 5),
```

(`git show 99281de -- server/src/services/metadata.service.ts` shows exactly `- validateRange(exifTags.Rating, -1, 5)` / `+ validateRange(exifTags.Rating, 1, 5)`.)

The full chain, traced link by link and independently re-verified:

1. `PUT /assets/:id {rating:-1}` → `AssetService.updateExif()` (`asset.service.ts:498-529`): `-1`
   survives `_.omitBy(…, _.isUndefined)`, `updateLockedColumns` (`utils/database.ts:520-525`) adds
   `'rating'` to `lockedProperties`, `upsertExif({…, lockedPropertiesBehavior: 'append'})` persists
   `-1`, then `JobName.SidecarWrite` is queued. The bulk path (`asset.service.ts:130-181`) queues the
   same job per id.
2. `MetadataService.handleSidecarWrite()` (`metadata.service.ts:491-541`): `rating: asset.exifInfo.rating ?? 0`
   leaves `-1` intact (`??` does not fire on `-1`), writes `Rating: -1` into the XMP, then calls
   `assetRepository.unlockProperties(asset.id, lockedProperties)` at line 539 —
   `asset.repository.ts:343-351` confirms this removes `'rating'` from the locked array. **`rating`
   is now unprotected.**
3. `JobService.onDone` (`job.service.ts:75-81`): `SidecarWrite` unconditionally queues
   `AssetExtractMetadata` with `{ id, source: 'sidecar-write' }`.
4. `handleMetadataExtraction()` (`metadata.service.ts:236-416`) has **no branch on `data.source`** —
   it runs in full. `getExifTags` (lines 580-626) spreads sidecar tags **last**, so the just-written
   `Rating: -1` wins. At line 308, `validateRange(-1, 1, 5)` hits `val < min` (lines 107-117) and
   returns `null`.
5. `upsertExif({ exif: exifData, …, lockedPropertiesBehavior: 'skip' })` (lines 384-390): the
   `skipLocked` SQL `CASE` (`asset.repository.ts:251-307`) keeps the old value only when the property
   is still in `lockedProperties`. Step 2 unlocked it, so the `ELSE` branch fires and **`NULL`
   overwrites the `-1`.**

Ratings `1`–`5` round-trip correctly through the same path, so this destroys **only** the value this
change exists to re-enable. The API returns 200 and the user's "rejected" mark disappears seconds
later, with no error surfaced anywhere.

No test would catch this: `99281de` deleted both the unit case for a negative rating from
`metadata.service.spec.ts` and the e2e case `should set the negative rating` from
`e2e/src/specs/server/api/asset.e2e-spec.ts`, and this change restores neither.

**Fix:** Revert the companion line too, and restore the deleted tests:

```ts
// server/src/services/metadata.service.ts:308
rating: exifTags.Rating === 0 ? null : validateRange(exifTags.Rating, -1, 5),
```

### #3 🟠 High: Moving the bound into `.refine()` erases it from the published OpenAPI contract

| | |
|---|---|
| **File** | `server/src/dtos/asset.dto.ts:16-23` |
| **Category** | api-contract |
| **Confidence** | 100 (validation waived — corroborated ×3, all at anchor 100) |
| **Found by** | quick-reviewer (High), broad-reviewer (Medium), adversarial-reviewer (Medium) — *severity dissent: 2 of 3 rated this Medium* |

**Issue:** Zod v4 cannot express a custom `.refine()` predicate in JSON Schema, so replacing
`.min(1).max(5)` with a refinement drops the bound from the generated spec entirely. Visible directly
in the diff — for both `UpdateAssetDto.rating` and `AssetBulkUpdateDto.rating`:

```diff
-            "maximum": 5,
-            "minimum": 1,
+            "maximum": 9007199254740991,
+            "minimum": -9007199254740991,
```

The published contract now says "any safe integer" while the server enforces `{-1} ∪ [1,5]`. The real
constraint survives only as free-text `description`. Concrete consumers:
`mobile/openapi/lib/model/update_asset_dto.dart` now documents `Minimum value: -9007199254740991`;
generators that emit request-side validation (Java/Kotlin/C#/pydantic clients) stop rejecting
`rating: 42` client-side; spec-driven contract tests and fuzzers will now generate 2^53-scale values.
This is a regression even against the pre-`99281de` state, where `[1,5]` was at least a correct subset.

The runtime validation itself is correct — the `.int().nullable().refine(…).optional()` chain was
probed against the repo's own Zod and behaves as intended for `undefined`, `null`, `-1`, `0`, `1`,
`5`, `6`, `-2`, and `3.5`, matching the updated `asset.controller.spec.ts` expectations (42 tests
pass). The defect is contract fidelity only.

**Fix:** Express the domain in a form the JSON-Schema exporter can render:

```ts
rating: z
  .union([z.literal(-1), z.int().min(1).max(5)])
  .nullable()
  .optional()
  .describe('Rating in range [1-5], -1 (rejected) or null (unrated)')
```

Alternatively, attach explicit bounds via `.meta({ minimum: -1, maximum: 5 })` so the published spec
still constrains the field.

### #4 🟠 High: Search DTOs still reject `-1`, so rejected assets can be set but never found — and the spec now contradicts itself

| | |
|---|---|
| **File** | `server/src/dtos/search.dto.ts:36-49` |
| **Category** | api-contract / composition |
| **Confidence** | 100 (validator-confirmed) |
| **Found by** | quick-reviewer (Medium), broad-reviewer (High), adversarial-reviewer (High) |

**Issue:** `99281de` changed `BaseSearchSchema.rating` from `.min(-1)` to `.min(1)`. This change does
not revert it:

```ts
rating: z.int().min(1).max(5).nullish()
  .describe('Filter by rating [1-5], or null for unrated')
  .meta({ ...new HistoryBuilder()
    .added('v1').stable('v2')
    .updated('v2.6.0', 'Using -1 as a rating is deprecated and will be removed in the next major version.')
    .updated('v3', 'Using -1 as a rating is no longer valid.')      // ← now false
    .getExtensions() }),
```

**Functional asymmetry.** `POST /search/metadata`, `/search/random`, `/search/smart`, and the
statistics search (`search.controller.ts:38/50/62/86`, all built on `BaseSearchSchema`) reject
`rating: -1` with `400 Too small: expected number to be >=1`. `rating: null` is not a workaround —
`utils/database.ts:429` uses `is` for null and `=` otherwise, so null matches genuinely-unrated
assets. The validator found no other mechanism to isolate rejected assets. Users can mark assets
rejected but have no way to list them, which defeats the purpose of restoring the state.

**Self-contradicting published contract.** Dumping the regenerated
`open-api/immich-openapi-specs.json` confirms the same document now makes opposite claims about the
same concept in the same API version:

| Schema | `minimum` | `x-immich-history` v3 entry |
|---|---|---|
| `UpdateAssetDto.rating` | `-9007199254740991` | "Using **0** as a rating is no longer valid." |
| `AssetBulkUpdateDto.rating` | `-9007199254740991` | "Using **0** as a rating is no longer valid." |
| `MetadataSearchDto.rating` | `1` | "Using **-1** as a rating is no longer valid." |
| `RandomSearchDto.rating` | `1` | "Using **-1** as a rating is no longer valid." |
| `SmartSearchDto.rating` | `1` | "Using **-1** as a rating is no longer valid." |
| `StatisticsSearchDto.rating` | `1` | "Using **-1** as a rating is no longer valid." |

Before this change both schemas carried an identical `.min(1)`, so the asymmetry is
change-introduced, not pre-existing.

**Fix:** Extract the rating schema to one shared definition and use it on both sides, so they cannot
drift again:

```ts
// e.g. src/validation.ts
export const ratingSchema = z
  .union([z.literal(-1), z.int().min(1).max(5)])
  .nullable();
```

…then apply it in `asset.dto.ts` and `search.dto.ts`, updating `search.dto.ts`'s `describe()` text
and reconciling its `HistoryBuilder` entries with `asset.dto.ts`'s.

### #5 🟡 Medium: The EXIF response contract still declares `[1-5]`, so the server can return a `-1` that violates its own published schema

| | |
|---|---|
| **File** | `server/src/dtos/exif.dto.ts:32` |
| **Category** | api-contract |
| **Confidence** | 100 (validator-confirmed) |
| **Found by** | broad-reviewer (High — bundled), adversarial-reviewer (Medium) — *severity dissent; validator endorsed Medium* |

**Issue:** `99281de` tightened `ExifResponseSchema.rating` from `z.int().nullish().default(null)` to
`z.int().min(1).max(5).nullish().default(null)`; this change does not revert it. `mapExif()`
(`exif.dto.ts:62`) passes `entity.rating` through with no clamping, and the generated spec still has
`ExifResponseDto.properties.rating = {"minimum":1,"maximum":5,…}`. So `GET /assets/:id` for an asset
rated `-1` returns `exifInfo.rating: -1` in violation of the documented response schema.

No runtime failure today: `grep -rn "ZodSerializerDto" server/src` returns nothing, so the globally
registered `ZodSerializerInterceptor` (`app.module.ts:48`) is inert, and the generated Dart client
(`mobile/openapi/lib/model/exif_response_dto.dart:296`) does a bare `int.parse` with no range check.
The impact is on spec-driven consumers and contract tests — hence Medium rather than High. Note the
severity would rise the day a `@ZodSerializerDto` is added, since every rejected asset would then
fail or be silently coerced.

**Relationship to #2:** these are independent. #2 destroys the `-1` on the *next* metadata-extraction
cycle; there is a real window between the API write and job completion in which `-1` is stored and
returned. Fixing #2 makes #5 permanently reachable rather than transient.

**Fix:**

```ts
// server/src/dtos/exif.dto.ts:32
rating: ratingSchema.default(null).describe('Rating'),   // using the shared schema from #4
```

### Migration Safety Notes (data-migration-reviewer)

- **Runner semantics verified mechanically**, not inferred: migrations are keyed by exact
  filename-minus-extension (`FileMigrationProvider`), stored in `kysely_migrations.name`.
  `#ensureNoMissingMigrations` runs before and independently of `allowUnorderedMigrations`.
- **Ordering**: the deleted migration (`1780592070031`) sorts strictly before the retained
  `1780592071031-AssetOcrSync.ts`. This creates no *separate* ordering hazard — but it does prove the
  affected population is non-empty in practice, since any instance that ran `AssetOcrSync` ran the
  deleted migration first.
- **Fresh installs are safe**: a database that never recorded the migration simply never sees it in
  the directory listing.
- **No DB-level constraint on `rating`**: `server/src/schema/tables/asset-exif.table.ts:108` declares
  `@Column({ type: 'integer', nullable: true })`, and the original `CREATE TABLE` in
  `1744910873969-InitialMigration.ts` has no `CHECK`. Re-permitting `-1` at the DTO layer needs no
  DDL change, and `getSchemaDrift()` is unaffected by this diff.

  `SELECT name FROM kysely_migrations WHERE name = '1780592070031-ConvertNegativeRatingToNull';` — a
  hit means that instance will fail to boot (finding #1).

### Considered But Not Flagged (all agents)

**Tiered down by the `evidence=strong` bar** (`bugs` preset requires screen score ≥80, or ≥60 with
2+ independent finders):

- **`server/src/services/duplicate.service.ts:258-267` — duplicate-merge silently discards a `-1`

**Dismissed with sound reasoning:**

- **`1771535611395-ConvertRating0ToNull.ts`** (earlier migration converting `rating = 0` to NULL) —
