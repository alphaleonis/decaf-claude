### #1 🟠 High: `@`-modifier reuse path silently stops incrementing `TotalSamples` — an existing metric and API field regress

| | |
|---|---|
| **File** | `promql/engine.go:2145` (and `:2160`, `:2183`) |
| **Category** | correctness |
| **Confidence** | 100 |
| **Verified** | executed |
| **Pre-existing** | no |
| **Found by** | solo-reviewer (High) |

**Issue:** `fullWindowCount` is declared inside the per-step loop and assigned **only** inside
`if ts == ev.startTimestamp || selVS.Timestamp == nil`. When a range-vector argument carries an `@`
modifier and the selector data is reused across steps, that block is skipped and `fullWindowCount`
stays `0`, so `IncrementSamplesAtStep(step, fullWindowCount)` adds nothing. The pre-change line added
`int64(len(floats)+totalHPointSize(histograms))` unconditionally, using the *retained* buffer — i.e.
the full window was counted at every step.

This changes `prometheus_engine_query_samples_total`, `stats.samples.totalQueryableSamples` and
`totalQueryableSamplesPerStep` — the exact fields the change's own comment ("Full window count for
TotalSamples (unchanged semantics)", line 2143) and the amended doc comment at
`util/stats/query_stats.go:271-275` claim are unchanged. It also breaks the documented invariant on
`TotalSamplesPerStep` ("Each step should be identical to the TotalSamples when a step is run as an
instant query").

The reachable query class is a range-vector call that is *not* wrapped in `StepInvariantExpr`: either
an `AtModifierUnsafeFunctions` member taking a range vector (`predict_linear`), or a call with a
second non-step-invariant argument, since `preprocessExprHelper` returns `shouldWrap=false` for
`*parser.MatrixSelector` (`promql/engine.go:4364-4367`) and so never wraps the `@`-bearing range
argument on its own.

**Evidence:** Ran the identical probe query at base (`efbdc3f88`, in a throwaway `git worktree`) and
at head. Query `predict_linear(metricWith1SampleEvery10Seconds[60s] @ 30, 3600)`, range 201s→216s
step 5s:

```
base: TotalSamples=16  TotalPerStep={201000:4, 206000:4, 211000:4, 216000:4}
head: TotalSamples=4   TotalPerStep={201000:4, 206000:0, 211000:0, 216000:0}
```

With 3 series (`metricWith3SampleEvery10Seconds`): base `48` / `[12,12,12,12]` → head `12` /
`[12,0,0,0]`. Running the *same expression* as three separate instant queries at 206s, 211s, 216s
gives `TotalSamples=4` each at head — confirming the per-step invariant is violated (range-query step
206000 reports `0`, instant query at 206s reports `4`).

No test in the change covers this path: the only `@` cases in the table
(`max_over_time(...[60s] @ 30)`) go through `StepInvariantExpr`, which is untouched.

**Fix:** Compute the full-window count from whatever `floats`/`histograms` currently hold, outside the
re-evaluation guard, and gate only the read-delta:

```go
var samplesReadCount int64
if ts == ev.startTimestamp || selVS.Timestamp == nil {
    ...
    floats, histograms = ev.matrixIterSlice(it, mint, maxt, floats, histograms)
    if step == 0 {
        samplesReadCount = int64(len(floats) + totalHPointSize(histograms))
    } else {
        samplesReadCount = countSamplesAfter(floats, histograms, maxt-ev.interval)
    }
}
...
ev.samplesStats.IncrementSamplesAtStep(step, int64(len(floats)+totalHPointSize(histograms)))
ev.samplesStats.IncrementSamplesReadAtStep(step, samplesReadCount)
```

### #2 🟠 High: `SamplesRead` double counts every subquery used as a range-vector function argument, contradicting its own documentation

| | |
|---|---|
| **File** | `promql/engine.go:1874` (with `promql/engine.go:2184`) |
| **Category** | correctness |
| **Confidence** | 100 |
| **Verified** | executed |
| **Pre-existing** | no |
| **Found by** | solo-reviewer (High) |

**Issue:** `evalSubquery` now merges the child's `SamplesRead` into the parent
(`MergeSamplesReadFromSubquery`, line 1874). But the pre-existing design is that the subquery's
*output* is then re-consumed by the same `matrixIterSlice` step loop (that is what the deleted comment
"those samples will be counted in later stage" referred to), and that loop now also calls
`IncrementSamplesReadAtStep` at line 2184. The same subquery therefore contributes twice: once as real
storage I/O, once as an in-memory re-read of its own result — which by the stated definition
("samples read (I/O)") is not I/O at all.

This directly falsifies three places the change itself wrote:

- `docs/querying/api.md:247` — "for other queries this equals `totalQueryableSamples`"
- `docs/feature_flags.md:48` — "For other query types, this equals totalQueryableSamples"
- `util/stats/query_stats.go:279-281` — "elsewhere it equals TotalSamples"

It also inflates the new `prometheus_engine_query_samples_read_total` counter, which is the headline
deliverable of the change.

Note the inconsistency between the two subquery code paths: the bare-subquery path
(`case *parser.SubqueryExpr`, lines 2440-2446) is *not* double counted, only the function-argument
path is.

**Evidence:** Executed at head against the change's own fixture data:

```
max_over_time(metricWith3SampleEvery10Seconds[60s:5s])  instant @201s
    TotalSamples=36   SamplesRead=72     <- exactly 2x

metricWith1SampleEvery10Seconds[60s:5s]                 instant @201s
    TotalSamples=12   SamplesRead=12     <- bare subquery, not doubled
```

The change's own test table encodes the doubling as expected (`promql/engine_test.go:1184`
`SamplesRead: 72` against `TotalSamples: 36`; `:1197` `144` vs `72`; `:1554` `12` vs `6`), so the
tests lock in the behavior rather than catch it.

**Fix:** Pick one accounting point and document it. Either (a) do not merge the child's `SamplesRead`
in `evalSubquery` and let the later stage count the subquery output (matches `TotalSamples`, satisfies
the docs, but then `SamplesRead` is not I/O); or (b) keep the merge and suppress the outer
`IncrementSamplesReadAtStep` when the matrix selector is a materialized subquery result (matches the
"I/O" definition). Whichever is chosen, the three doc/comment sites above must be corrected — as
written they are false for every instant query containing `f(subquery)`.

### #3 🟠 High: `countSamplesAfter` adds an O(window) scan per step per series to the hottest engine loop — ~38% slowdown measured on wide-window range queries

| | |
|---|---|
| **File** | `promql/value.go:195` (called from `promql/engine.go:2164`) |
| **Category** | production |
| **Confidence** | 100 |
| **Verified** | executed |
| **Pre-existing** | no |
| **Found by** | solo-reviewer (High) |

**Issue:** `countSamplesAfter` linearly scans the entire retained window (`floats` and `histograms`) at
every step of every series. Before the change the equivalent bookkeeping for floats was `len(floats)`
— O(1). `matrixIterSlice` deliberately reuses the buffer and only drops/appends the delta
(`promql/engine.go:2774-2793`), so this new scan is the only O(window) *per-step* float work in the
loop. It runs unconditionally: `sampleStats` is always accumulated because
`prometheus_engine_query_samples_total` / `_read_total` are always exported, so clients that never
request `stats` pay the cost too.

`floats` is sorted ascending by timestamp, so the count of points after a cutoff is obtainable by
scanning backwards from the end (O(new points)) or by binary search (O(log n)) — the linear forward
scan discards that ordering.

**Evidence:** `BenchmarkRangeQuery`, same machine, base (`efbdc3f88`, temp worktree) vs head,
`-benchtime` fixed, 3 runs each:

| case | base ns/op | head ns/op | delta |
|---|---|---|---|
| `rate(a_one[1d]),steps=1000` | 7,172,620 / 7,164,494 / 7,212,581 | 11,010,173 / 9,814,081 / 9,894,738 | **+38%** |
| `changes(a_one[1d]),steps=1000` | 41,607,676 / 41,918,508 / 42,029,396 | 48,082,572 / 47,895,334 / 47,695,114 | **+14%** |
| `rate(a_one[1m]),steps=1000` | ~94,000 | ~93,000 | no change |

The arithmetic corroborates attribution: at a 10s interval a `[1d]` window holds 8,640 points;
8,640 × 1,000 steps ≈ 8.64M extra iterations, and the measured delta is ≈2.7 ms ≈ 3.1 ns/iteration —
consistent with a strided scan over 16-byte `FPoint`s. Allocation counts are unchanged, and no other
diff hunk is on the `rate(a_one[1d])` path (no subquery, no `@`), so `countSamplesAfter` is the only
candidate.

**Fix:** Exploit the ascending sort:

```go
func countSamplesAfter(floats []FPoint, histograms []HPoint, cutoff int64) int64 {
	var n int64
	for i := len(floats) - 1; i >= 0 && floats[i].T > cutoff; i-- {
		n++
	}
	for i := len(histograms) - 1; i >= 0 && histograms[i].T > cutoff; i-- {
		n += int64(histograms[i].size())
	}
	return n
}
```

Cleaner still: have `matrixIterSlice` return the number of points it newly appended, which it already
knows, making the count free.

**Issue:** `require.GreaterOrEqual(t, qs.Samples.SamplesRead, int64(0))` asserts that a

`SamplesRead` is never incremented at all. Both the `stats=true` and `stats=all` cases would still

**Evidence:** `SamplesRead int64` (`util/stats/query_stats.go:282`) is only ever incremented by `+= n`

for a query known to read samples, or

instant query used by this test, which would also pin the documented equality from finding #2.

### #6 🟢 Low: the max-samples check now uses `PeakSamples` from the per-step-*disabled* run

| | |
|---|---|
| **File** | `promql/engine_test.go:2436` |
| **Category** | tests |
| **Confidence** | 75 |
| **Verified** | read |
| **Pre-existing** | no |
| **Found by** | solo-reviewer (Low) |

**Issue:** `stats` is asserted against `c.PeakSamples` after the first (per-step-enabled) run, then
**reassigned** by the newly inserted per-step-disabled run at line 2436. The subsequent bound
`promqltest.NewTestEngine(t, true, 0, stats.Samples.PeakSamples-1)` (line 2447) therefore uses the
peak from the disabled engine, which is never asserted against `c.PeakSamples`. If the two engines'
peaks ever diverge, the `ErrTooManySamples` check silently runs against the wrong threshold — and
would then fail confusingly rather than pointing at the divergence. The change is meaningful here
because the new `NewChildWithStepTracking` path makes the enabled and disabled configurations
structurally different for subqueries (the enabled path allocates and writes per-step arrays the
disabled path does not).

**Evidence:** Read `promql/engine_test.go:2424-2448`. Peaks happen to match today, so the suite
passes.

**Fix:** Capture the enabled-run peak in a separate variable before the disabled run, or add
`require.Equal(t, c.PeakSamples, stats.Samples.PeakSamples)` to the disabled block as well.

  `TotalSamplesPerStep` on subquery children is written to (`:2424`) and then discarded —
  `MergeSamplesReadFromSubquery` merges only `SamplesRead`. That is one wasted `[]int64` of `numSteps`

  neither existed. (solo-reviewer)
