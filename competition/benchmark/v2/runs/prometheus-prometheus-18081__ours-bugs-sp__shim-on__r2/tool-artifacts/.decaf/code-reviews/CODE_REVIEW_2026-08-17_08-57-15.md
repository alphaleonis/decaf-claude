## Findings

### #1 🟠 High: `totalQueryableSamples` silently drops range-vector windows on `@`-modifier steps

| | |
|---|---|
| **File** | `promql/engine.go:2145` (and `:2160`, `:2183`) |
| **Category** | correctness |
| **Confidence** | 100 |
| **Verified** | executed |
| **Pre-existing** | no |
| **Found by** | solo-reviewer (High) |

**Issue:** `fullWindowCount` is declared inside the per-step loop and only assigned inside the
`if ts == ev.startTimestamp || selVS.Timestamp == nil` block. When a range-vector selector carries an
`@` modifier and the enclosing expression is *not* step-invariant, that block is skipped for every
step after the first, so `IncrementSamplesAtStep(step, fullWindowCount)` now adds **0** instead of
the retained window size. Before this change the line was
`IncrementSamplesAtStep(step, int64(len(floats)+totalHPointSize(histograms)))`, evaluated against the
slices retained from step 0 — i.e. the full window at every step.

This changes an existing, publicly exposed statistic (`totalQueryableSamples` /
`totalQueryableSamplesPerStep`) and the existing `prometheus_engine_query_samples_total` counter,
directly contradicting the change's own stated invariant that "`totalQueryableSamples` keeps existing
semantics". The added comment ("When we reuse data (@ modifier), we don't increment either")
documents the new behavior but not that it is a break.

The path is reachable whenever a multi-arg range function pairs an `@`-anchored matrix selector with
a step-variant scalar argument — `predict_linear`, `quantile_over_time`,
`double_exponential_smoothing`. `preprocessExprHelper` (`promql/engine.go:4363-4368`) returns
`shouldWrap=false` for `*parser.MatrixSelector`, so such a selector is never individually wrapped in
`StepInvariantExpr`, and the range-vector loop really does run over all steps with
`selVS.Timestamp != nil`.

**Evidence:** Probe test (untracked, since removed) on
`predict_linear(metricWith1SampleEvery10Seconds[60s] @ 30, scalar(metricWith1SampleEvery10Seconds))`,
range 201s→220s step 5s, per-step stats on:

- at `efbdc3f88` (before): `TotalSamples=20 TotalSamplesPerStep=[5 5 5 5]`
- at `ec7157593` (this change): `TotalSamples=8 TotalSamplesPerStep=[5 1 1 1]`

The matrix contribution of 4 samples/step collapsed to 4 at step 0 only (the residual `1` per step is
the `scalar(...)` argument). No test in the change covers this shape, which is why
`go test ./promql/... ./util/stats/...` is green.

**Fix:** Keep `fullWindowCount` on the previous semantics by computing it from the (possibly
retained) slices *after* the `if` block, and only gate `samplesReadCount`:

```go
if ts == ev.startTimestamp || selVS.Timestamp == nil {
    ...
    floats, histograms = ev.matrixIterSlice(it, mint, maxt, floats, histograms)
    if step == 0 {
        samplesReadCount = int64(len(floats) + totalHPointSize(histograms))
    } else {
        samplesReadCount = countSamplesAfter(floats, histograms, maxt-ev.interval)
    }
}
fullWindowCount := int64(len(floats) + totalHPointSize(histograms))
```

and add a test case with an `@`-anchored matrix selector under a non-step-invariant call.

### #2 🟠 High: subquery samples are counted twice in `samplesRead`

| | |
|---|---|
| **File** | `promql/engine.go:1874` (`evalSubquery`), with `util/stats/query_stats.go:423` |
| **Category** | correctness |
| **Confidence** | 100 |
| **Verified** | executed |
| **Pre-existing** | no |
| **Found by** | solo-reviewer (High) |

**Issue:** When a subquery is used as a range-vector function argument, `evalSubquery` now merges the
child's `SamplesRead` into the parent (`MergeSamplesReadFromSubquery`). But the subquery result is
then materialized into `ms.VectorSelector.Series` and handed to the range-vector loop, which counts
those very same points *again* via `IncrementSamplesReadAtStep(step, samplesReadCount)` at
`promql/engine.go:2184`.

The original code deliberately discarded the child's totals — "Avoid double counting samples when
running a subquery, those samples will be counted in later stage" (`promql/engine.go:1866-1870`,
pre-change). The new merge re-introduces exactly the double count that comment guarded against, for
the new counter only.

Consequences:

- `samplesRead` (and `prometheus_engine_query_samples_read_total`) is inflated ~2× for the extremely
  common `f_over_time(<subquery>)` shape.
- `samplesRead > totalQueryableSamples` for instant subquery queries, which contradicts
  `docs/feature_flags.md:48` ("For other query types, this equals totalQueryableSamples") and the
  "samples *read* (I/O)" framing — the second count is a re-read of an in-memory matrix, not I/O at
  all.
- The inflation is baked into the new tests, so it will not be caught later.

**Evidence:** Mutation probe in an isolated worktree at `ec7157593` (`/tmp/promwt2`, since removed),
with only line 1874 commented out:

```
--- FAIL: TestQueryStatistics/max_over_time(metricWith3SampleEvery10Seconds[60s:5s])
    expected: 72
    actual  : 36        (Samples read mismatch)
```

36 is exactly `TotalSamples` for that instant query (`promql/engine_test.go:1129-1141` asserts
`TotalSamples: 36, SamplesRead: 72`) — i.e. the merged 36 are a byte-for-byte duplicate of what the
outer loop already counted. Hand-traced for the range-query variant at
`promql/engine_test.go:1414-1433` (`SamplesRead: 93`, per-step `{72, 6, 6, 9}`): 48 from the child's
16 subquery steps × 3 series, plus 45 from the outer loop (36 + 3 + 3 + 3), with 36 of each landing
on step 0 → 72. The whole test suite is green with the double count in place.

**Fix:** Pick one accounting point, not both. Either drop the `MergeSamplesReadFromSubquery` call at
`promql/engine.go:1874` (subquery points get counted once, when the materialized matrix is scanned —
consistent with `TotalSamples`), or keep the merge and suppress the outer loop's `SamplesRead`
increment for subquery-derived selectors. If the intent is that the child's count is the "real" I/O
and the outer count is not, that reasoning belongs in a comment and the outer increment must be
suppressed. Either way the test expectations at `promql/engine_test.go:1129`, `:1141`, `:1414-1433`
and the sibling subquery cases need to be recomputed.

### #3 🟢 Low: per-step arrays now allocated for every subquery evaluation

| | |
|---|---|
| **File** | `promql/engine.go:2396` and `promql/engine.go:1869` |
| **Category** | production |
| **Confidence** | 75 |
| **Verified** | traced |
| **Pre-existing** | no |
| **Found by** | solo-reviewer (Low) |

**Issue:** `stats.NewChild()` previously returned a `QuerySamples` with per-step stats *off*,
allocating nothing. Both new call sites use `NewChildWithStepTracking(...)`, which calls
`InitStepTracking` and allocates **two** `[]int64` sized by the step count — the *subquery's* step
count at `:2396`. For `foo[1d:1s]` that is 86 401 entries × 2 × 8 B ≈ 1.4 MB per subquery node
evaluation, none of it charged against `query.max-samples`. `TotalSamplesPerStep` is allocated too
even though the child's totals are discarded.

Scope is limited: only under `--enable-feature=promql-per-step-stats` with `stats=all`. Still,
per-step stats is precisely the mode an operator turns on to diagnose expensive queries — the ones
with the widest subqueries.

**Fix:** Allocate only `SamplesReadPerStep` for these children, or cap/skip step tracking when the
subquery step count greatly exceeds the outer step count (the array is only ever redistributed into
the outer array and then dropped).

### #4 🟢 Low: new API assertions cannot fail

| | |
|---|---|
| **File** | `web/api/v1/api_test.go:983` (and `:999`) |
| **Category** | tests |
| **Confidence** | 100 |
| **Verified** | read |
| **Pre-existing** | no |
| **Found by** | solo-reviewer (Low) |

**Issue:** `require.GreaterOrEqual(t, qs.Samples.SamplesRead, int64(0))` is tautological —
`SamplesRead` is an `int64` that is only ever incremented by non-negative counts, so the assertion
holds even if the entire feature is wired to nothing and `samplesRead` is always 0. It guards nothing
about the API surface it appears to cover. (`require.NotNil(t, qs.Samples.SamplesReadPerStep)` at
`:1000` is a real check; the `GreaterOrEqual` pair is not.)

**Fix:** Assert a concrete expected value for the fixture query (the `TestStats` fixture is
deterministic), or at minimum `require.Positive(t, qs.Samples.SamplesRead)` so a silently-zero
counter fails.

## Minor Findings

### Consistency

- `util/stats/query_stats.go:352` — `IncrementSamplesReadAtStep` adds to `SamplesRead`
  unconditionally but guards the per-step write with `i < len(...)`, while the sibling
  `IncrementSamplesAtStep` (`:322-330`) indexes unguarded. An out-of-range step would panic loudly on
  the totals path but silently desynchronize `SamplesRead` from `sum(SamplesReadPerStep)` on the read
  path. No currently reachable out-of-range index was found, but the asymmetry converts a future
  indexing bug from a crash into wrong numbers. Note also the missing `i >= 0` check here, which
  `IncrementSamplesReadAtTimestamp` at `:369` does have. (solo-reviewer)
- `promql/engine.go:2440` — the subquery step-mapping loop divides by `ev.samplesStats.Interval`
  while offsetting by `ev.startTimestamp` (the *evaluator's* field). The two are equal on every path
  today, but mixing the stats object's copy of the layout with the evaluator's is fragile;
  `ev.interval` would be the consistent choice, matching `ev.startTimestamp`. (solo-reviewer)

## Specialist Notes

### Considered But Not Flagged (solo-reviewer)

- **`samplesRead` does not dedupe under instant-vector lookback.** `evalSeries`
  (`promql/engine.go:1773`, `:1796`) increments read-count once per step, so a 10s-spaced series
  queried at 5s steps counts the same stored sample twice. Inconsistent with the delta treatment
  given to range-vector selectors, but explicitly documented as intended at `docs/feature_flags.md:48`
  ("For other query types, this equals totalQueryableSamples") — a design choice, not a defect.
- **Subquery steps beyond the last outer step clamped to `numOuterSteps-1`**
  (`promql/engine.go:2445-2447`). The subquery evaluator produces points past the last outer window
  (e.g. `t=220000` in the `[60s:5s]` test), which no outer step consumes. Attributing them to the
  last step is deliberate and documented in the code comment; the wasted evaluation itself is
  pre-existing.
- **`NewChildWithStepTracking` with `subqStart > subqEnd`** (possible for `foo[1m:5m]`-style
  step > range). Arithmetic traced: `subqEnd - subqStart > -subqInterval` always, so Go's truncating
  division yields `numSteps >= 1` and `make([]int64, numSteps)` cannot panic or produce a negative
  index. No defect.
- **Newly non-nil `TotalSamplesPerStep` on `evalSubquery`'s child** now makes
  `IncrementSamplesAtStep`'s unguarded index live where it was previously a no-op. Every write
  reachable through `ev.eval(ctx, subq)` from `evalSubquery` was walked — only
  `IncrementSamplesAtTimestamp(ev.endTimestamp, …)` reaches that array, landing on `numSteps-1`. No
  reachable out-of-range index.
- **`docs/querying/api.md:249` anchor `../feature_flags.md#per-step-stats`** — the `## Per-step stats`
  heading exists at `docs/feature_flags.md:40`. Valid.
- **Mutation probe on finding #1** — decided against; the before/after worktree comparison gave
  direct executed evidence without touching tracked source, so no snapshot protocol was needed.
