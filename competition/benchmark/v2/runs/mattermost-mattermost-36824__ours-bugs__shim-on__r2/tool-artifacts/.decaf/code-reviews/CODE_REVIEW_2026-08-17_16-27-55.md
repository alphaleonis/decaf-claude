#### M1 — `CommandResponseFromHTTPBody` enforces the new limits on only one of its two branches (screen 78)

| | |
|---|---|
| **File** | `server/public/model/command_response.go:36-41` (gate added at `:72`) |
| **Category** | half-enforced contract |
| **Found by** | adversarial-reviewer (Medium, anchor 100) |
| **Screen** | 78 — *"verified, and it will be hit in practice"* |

**Issue.** The commit adds the `Text`-length and `response_type` gates inside
`CommandResponseFromJSON`, which is only the `application/json` branch of the shared ingest
function. The other branch returns `CommandResponseFromPlainText(...)` (`:40`), which never calls
`IsValid`. Both branches serve the same two callers — the outgoing slash-command response path
(`server/channels/app/command.go:595`) and the public, session-less `commandWebhook` endpoint
(`server/channels/web/webhook.go:114`, registered with `RequireSession: false`), where
`Content-Type` is fully caller-controlled.

The result is that the *same payload* is accepted or rejected purely on Content-Type. Probe run
against this commit:

```
CommandResponseFromHTTPBody("text/plain",       <65536 'a'>)  → resp ok, len(Text)==65536, err=nil
CommandResponseFromHTTPBody("",                 <65536 'a'>)  → resp ok,                   err=nil
CommandResponseFromHTTPBody("application/json", {"text": <same>}) → err: "text is too long"
```

The screener additionally traced why the bypass is not caught downstream: a plain-text response has
`ResponseType == ""`, which routes to the ephemeral branch of `CreateCommandPost`
(`server/channels/app/command.go:82-84`) → `SendEphemeralPost`, which is broadcast over websocket
and never persisted, so the store-layer `Post.IsValid` size check never runs on it. On the
outgoing-command path the plain-text branch admits up to `MaxIntegrationResponseSize` = 1 MiB
(`server/channels/app/webhook.go:31`).

This is change-introduced, not pre-existing: before this commit neither branch validated anything,
so there was no asymmetry to exploit.

**Fix.** Call `IsValid` from `CommandResponseFromHTTPBody` (or from `CommandResponseFromPlainText`)
so both branches enforce the same contract, and return the validation error rather than the current
`nil, nil`.

#### M2 — Strict validation converts a tolerated third-party response into a total command failure (screen 72, validator: **confirmed**)

| | |
|---|---|
| **File** | `server/public/model/command_response.go:81-88` (call site `:72-74`) |
| **Category** | backward compatibility / production reliability |
| **Found by** | broad-reviewer (High, anchor 75) — **dismissed** by quick-reviewer and adversarial-reviewer (see below) |
| **Screen** | 72 — *"verified, and it will be hit in practice"* |
| **Validation** | confirmed |

**Issue.** `IsValid` rejects any `ResponseType` outside `{"", "in_channel", "ephemeral"}` and any
`Text` over 65535 bytes, and `CommandResponseFromJSON` now calls it unconditionally. On the
outgoing slash-command path this parses the HTTP response body of a **third-party integration
Mattermost does not control**.

The validator traced the concrete before/after for
`{"response_type":"IN_CHANNEL","text":"hi","goto_location":"https://x","extra_responses":[{"text":"ok","response_type":"ephemeral"}]}`:

- **Parent commit** — parses fine. In `CreateCommandPost` (`server/channels/app/command.go:73,82`)
  `"IN_CHANNEL"` matches neither branch, so *that one post* is silently skipped. The loop in
  `HandleCommandResponse` still posts the valid ephemeral sibling, and the full response —
  `GotoLocation`, `TriggerId` — is encoded back to the client with **HTTP 200**.
- **This commit** — `IsValid` rejects it, the error is wrapped at `command.go:596-597` into
  `api.command.execute_command.failed.app_error` (**HTTP 500**), `response` is `nil` so
  `HandleCommandResponse` is never reached, and the sibling `extra_responses`, `goto_location` and
  `trigger_id` are **all lost**. The user's slash command visibly fails.

**The comparison is case-sensitive** (`o.ResponseType != CommandResponseTypeInChannel`, no
normalization), so ordinary capitalization drift — `"IN_CHANNEL"`, `"Ephemeral"` — trips it. That
widens this from an edge case to a broad compatibility break.

**Recorded dissent.** Two reviewers dismissed this, both on the same ground: an unrecognized
`response_type` was *already* silently dropped, so erroring is "a behavior tightening consistent
with existing downstream semantics." The screener and the validator both examined that argument and
found it incomplete — it accounts for the dropped response but not for the **collateral loss** of
the sibling responses, `goto_location`, and overall command success. The counter-argument that a
loud 500 usefully tells an admin their integration is misconfigured has real merit, but the failure
surfaces to the *end user* as a wholly failed command with no indication which sub-response was at
fault.

**Fix.** A compatibility-policy decision the author must make, not a mechanical edit: either treat
an unrecognized `response_type` as the existing permissive fallback, or scope the strict validation
to the ingest points that actually want it rather than applying it inside an exported decoder shared
by every caller. At minimum, make the comparison case-insensitive.

#### M3 — `Client4` now validates data the server produced, after the command already ran (screen 45)

| | |
|---|---|
| **File** | `server/public/model/client4.go:5961`, `:5982` |
| **Category** | validation on the wrong side of the wire |
| **Found by** | adversarial-reviewer (High, anchor 75) |
| **Screen** | 45 — real but narrow |

**Issue.** `Client4.ExecuteCommand` / `ExecuteCommandWithTeam` use `CommandResponseFromJSON` to
decode a response the **Mattermost server itself produced**, and nothing server-side enforces
`IsValid` before sending: `server/channels/api4/command.go:428` encodes `App.ExecuteCommand`'s
result directly, and `server/channels/app/plugin_commands.go:172-176` only clamps an out-of-range
HTTP status, never touching `ResponseType`/`Text`.

The screener confirmed the premise and narrowed the concrete case: every *in-tree* command uses only
the two allowed constants, so the trigger is limited to third-party plugin commands. The one
verified regression is **oversized ephemeral text** — `SendEphemeralPost` runs synchronously before
the HTTP response is written and bypasses `Post.IsValid` entirely, so a >65535-byte ephemeral
message is already delivered over websocket by the time the client-side decoder rejects the same
payload. mmctl or a bot then sees a failure for a succeeded, non-idempotent operation; a retry
re-executes it.

**Fix.** Do not run producer-side validation inside the client decoder — either invoke `IsValid`
explicitly at the two ingest points that want it (`app/command.go:595`, `web/webhook.go:114`), or
add a non-validating decode variant for `client4.go`.

#### M4 — Both new `AppError` translation IDs are absent from the i18n catalog (screen 45, 2 finders)

| | |
|---|---|
| **File** | `server/public/model/command_response.go:82`, `:87` |
| **Category** | convention violation |
| **Found by** | quick-reviewer (High, anchor 100), broad-reviewer (Medium, anchor 100) |
| **Screen** | 45 — verified, but consequence is developer-facing |

**Issue.** `model.command_response.is_valid.response_type.app_error` and
`model.command_response.is_valid.text.app_error` have no entry in `server/i18n/en.json`
(`grep -c 'model.command_response' server/i18n/en.json` → `0`), while all eleven sibling
`model.command.is_valid.*` IDs are present at `server/i18n/en.json:11218-11270`. `NewAppError`
calls `Translate`, and `server/public/shared/i18n/i18n.go:210-213` returns the raw ID unchanged when
no catalog match exists — so `Message` becomes the literal dotted key. Probe output confirms it:

```
Id="model.command_response.is_valid.response_type.app_error"
Message="model.command_response.is_valid.response_type.app_error"
```

**Why this is Minor rather than higher.** The screener traced the user-visible path and found the
blast radius small: both server call sites `.Wrap()` the inner error inside an outer `AppError`
whose ID *is* registered, `wrappedToDetailed()` folds the inner text into `DetailedError` (not
`Message`), and `server/channels/web/handlers.go:426-428` strips `DetailedError` from API responses
unless `EnableDeveloper` is on. It also verified that **no CI job enforces this** — the i18n
workflow triggers only on `server/i18n/**` paths, which this diff does not touch. So the raw ID
reaches server debug logs and developer-mode responses, not ordinary end users.

**Fix.**
```json
{ "id": "model.command_response.is_valid.response_type.app_error", "translation": "Invalid response type." },
{ "id": "model.command_response.is_valid.text.app_error",          "translation": "Text is too long." }
```

#### M5 — `IsValid` recurses to unlimited `ExtraResponses` depth; every consumer walks one level (screen 30)

| | |
|---|---|
| **File** | `server/public/model/command_response.go:90-98` |
| **Category** | self-contradicting contract |
| **Found by** | adversarial-reviewer (High, anchor 100) |
| **Screen** | 30 — correct and reproducible, but the data is inert |

**Issue.** `IsValid` recurses through `ExtraResponses` without depth limit, but
`HandleCommandResponse` (`server/channels/app/command.go:621-630`) loops the direct children exactly
once and never recurses; `CommandResponseFromJSON` itself stringifies attachments only one level
deep (`:65-70`). A malformed entry at depth ≥2 therefore rejects the entire response even though no
consumer has ever read it. Probe-confirmed:

```
{"text":"main ok","response_type":"in_channel","extra_responses":[{"text":"level1",
 "extra_responses":[{"text":"level2","response_type":"bogus"}]}]}
  → err: invalid response type   (whole response rejected)
```

The screener verified the depth mismatch but scored it low: `grep` over `webapp/` shows zero
client-side consumption of `extra_responses` at any depth, so reaching this requires an integration
to populate a field nobody renders with malformed content specifically at the unused third level.
No stack-exhaustion angle — `encoding/json` bounds nesting long before recursion matters.

**Fix.** Make validation reach exactly as far as processing — validate the top level plus one level
of `ExtraResponses` — or make `HandleCommandResponse` recurse so the two agree.

#### M6 — Hardcoded `65535` duplicates `PostMessageMaxBytesV2`; byte check against rune-based semantics

| | |
|---|---|
| **File** | `server/public/model/command_response.go:85` |
| **Category** | duplicated literal / unit mismatch |
| **Found by** | quick-reviewer (Low, anchor 75) |

**Issue.** `maxLength := 65535` re-states a value that already has a name in the same package:
`PostMessageMaxBytesV2 = 65535` (`server/public/model/post.go:72`). Separately, the check counts
**bytes** while the package's post-length semantics are **runes** — `post.go:73` defines
`PostMessageMaxRunesV2 = PostMessageMaxBytesV2 / 4 // Assume a worst-case representation` (= 16383),
and `Post.IsValid` uses `utf8.RuneCountInString` (`post.go:508`). Probe: 30000 CJK runes = 90000
bytes trips the new check, while 16383 CJK runes = ~49 KB does not — the two limits do not line up.
Consequence-free for persisted posts (the downstream rune limit binds first in every direction
tested), so this is a clarity issue rather than a defect.

**Fix.** Use `PostMessageMaxBytesV2` instead of the literal, or add a comment stating why a distinct
byte-based limit is intentional here.
