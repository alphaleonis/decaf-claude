### #1 🔴 Critical: `NullPropagatedOperands` treats every `SqlBinaryExpression` operator as null-propagating, so the optimization drops load-bearing `IS NOT NULL` guards

| | |
|---|---|
| **File** | `src/EFCore.Relational/Query/SqlNullabilityProcessor.cs:626` |
| **Category** | correctness / data-integrity |
| **Confidence** | 100 — reproduced by the orchestrator and independently by three reviewers |
| **Found by** | quick (Critical), broad (Critical), adversarial (Critical), design (Critical), dotnet (High), security (High), knowledge (MUST) |

**Issue:** The whole rewrite rests on one obligation: for every operand `e` collected from the CASE result `R`, `e IS NULL ⟹ R IS NULL`. The binary arm of the collector honors no such restriction:

```csharp
else if (expression is SqlBinaryExpression binary)
{
    NullPropagatedOperands(binary.Left, operands);
    NullPropagatedOperands(binary.Right, operands);
}
```

`SqlBinaryExpression.IsValidOperator` (`src/EFCore.Relational/Query/SqlExpressions/SqlBinaryExpression.cs:82-105`) admits `AndAlso`, `OrElse` and `Coalesce` alongside the arithmetic and comparison operators. None of those three propagates NULL under SQL's three-valued logic — `NULL OR TRUE = TRUE`, `NULL AND FALSE = FALSE`, `COALESCE(NULL, y) = y`. So an operand reachable only through one of them is wrongly admitted to `nullPropagatedOperands`, `DropNotNullChecks` deletes the guard that was protecting it, and the CASE collapses to an expression with different semantics.

The same file already states the rule this violates, at line 2321: `// for AndAlso, OrElse we can't do this optimization`.

**Note the unary arm and the function arm are both correct.** The unary arm is a whitelist (`Not`, `Negate`, `Convert` — all strict), and the function arm consults `IsNullable` / `ArgumentsPropagateNullability` / `InstancePropagatesNullability`, which is why `COALESCE` built through `SqlExpressionFactory.Coalesce` (a `SqlFunctionExpression` with `argumentsPropagateNullability: [false, false]`) is handled safely. Only the binary arm is blanket.

**Failure scenario — executed**, SQLite, provider built from this tree. Rows: `Id=1 {NullableIntA=null, NullableIntB=null, IntB=5}`, `Id=2 {NullableIntA=3, NullableIntB=4, IntB=0}`, `Id=3 {all null, IntB=0}`.

```
MISMATCH  x.NullableIntA != null ? (bool?)(x.NullableIntA > 0 || x.IntB > 0) : null
          sql    = SELECT "e"."NullableIntA" > 0 OR "e"."IntB" > 0 FROM "Es" AS "e"
          server = True, True, NULL
          correct= NULL, True, NULL          <-- row 1 wrong

MISMATCH  x.NullableIntA != null ? (bool?)(x.NullableIntA > 0 && x.IntB > 0) : null
          sql    = SELECT "e"."NullableIntA" > 0 AND "e"."IntB" > 0 FROM "Es" AS "e"
          server = NULL, False, False
          correct= NULL, False, NULL         <-- row 3 wrong

MISMATCH  x.NullableIntA != null ? (bool?)(x.NullableIntA == x.NullableIntB) : null
          sql    = SELECT "e"."NullableIntA" = "e"."NullableIntB" AND "e"."NullableIntB" IS NOT NULL
          server = False, False, False
          correct= NULL,  False, NULL        <-- rows 1 and 3 wrong

  ok      x.NullableIntA != null ? x.NullableIntA + 1 : null      (control — genuinely strict)
          sql    = SELECT "e"."NullableIntA" + 1 FROM "Es" AS "e"
```

**It is not confined to projections.** The same shape in a predicate changes which rows are returned:

```
MISMATCH  .Where(x => (x.NullableIntA != null ? (bool?)(x.NullableIntA > 0 || x.IntB > 0) : null) == true)
          sql    = SELECT "e"."Id" FROM "Es" AS "e" WHERE "e"."NullableIntA" > 0 OR "e"."IntB" > 0
          server = [1, 2]
          correct= [2]                       <-- row 1 leaks in
```

Row-level authorization in EF Core applications is routinely expressed as exactly this kind of predicate (`HasQueryFilter`, `Where`), so a `NULL → TRUE` flip is a fail-open row-visibility change, not merely a value bug. `OrElse` and `Coalesce` fail open; `AndAlso` fails closed.

The `Equal`/`NotEqual` case is worth calling out separately because it needs no exotic operator: EF's own null-semantics expansion turns `A == B` into `A = B AND B IS NOT NULL` (the `A IS NULL AND B IS NULL` arm having been elided because `A` was assumed non-null while the result was visited). The top node is an `AndAlso`, so the blanket recursion walks straight through it to `A`.

There is no opt-out — no flag, no `AppContext` switch — and `SqlNullabilityProcessor` is shared by every relational provider.

**Fix:** make the binary arm operator-allowlisted rather than shape-based, mirroring the exclusion already stated at line 2321. Prefer an explicit `switch` with a `default` that does *not* recurse, so a future addition to `IsValidOperator` is opted out until someone proves strictness — the preceding commit (`051c33a79`) added exactly such an operator (`ExclusiveOr`).

```csharp
else if (expression is SqlBinaryExpression
         {
             OperatorType: ExpressionType.Add or ExpressionType.Subtract
                 or ExpressionType.Multiply or ExpressionType.Divide or ExpressionType.Modulo
                 or ExpressionType.And or ExpressionType.Or or ExpressionType.ExclusiveOr
                 or ExpressionType.Equal or ExpressionType.NotEqual
                 or ExpressionType.LessThan or ExpressionType.LessThanOrEqual
                 or ExpressionType.GreaterThan or ExpressionType.GreaterThanOrEqual
         } binary)
{
    NullPropagatedOperands(binary.Left, operands);
    NullPropagatedOperands(binary.Right, operands);
}
```

Two caveats on that list, both worth deciding explicitly rather than inheriting:
- **`And`/`Or` on `bool`.** SQL Server renders bitwise `&`/`|` distinctly from `AND`/`OR` (`QuerySqlGenerator` emits ` & `/` | ` for `And`/`Or` and ` AND `/` OR ` for `AndAlso`/`OrElse`), so C# `&`/`|` on bools is not an allowlist escape on the providers in this repo — but gating on `binary.Type != typeof(bool)` costs nothing and removes the question.
- **Comparisons** are strict as *values*, but on SQL Server `SearchConditionConvertingExpressionVisitor` runs after this pass and materializes a projected search condition as `CASE WHEN cond THEN CAST(1 AS bit) ELSE CAST(0 AS bit) END`, so `UNKNOWN` lands as `0` rather than `NULL`. Worth confirming against SQL Server before keeping them in the allowlist. *(Derived from reading `SqlServerParameterBasedSqlProcessor.Optimize` and `SearchConditionConvertingExpressionVisitor.ConvertToValue`; not executed — no SQL Server available.)*

### #2 🟠 High: The added tests cover only the shapes on which the optimization is already sound

| | |

**Issue:** All five new tests project results that genuinely propagate NULL — `~` on `int?`, `int? + int?`, and string concatenation. The five rebaselined GearsOfWar tests are likewise all `LEN`/`CAST`/string-concat/identity. Nothing in the changeset projects a `bool?`, exercises `&&`/`||`/`??` in the result, or puts the optimization in a `WHERE` predicate — even though the diff's own baselines (`Null_propagation_optimization5/6`) show it rewriting WHERE clauses.

This is why finding #1 ships green: the suite is structurally incapable of failing on it. Mapping the accepted shapes against coverage:

| Shape accepted by `NullPropagatedOperands` | Covered by |
|---|---|
| unary `Not` | `_unary_op` (`~` on `int?`; logical `NOT` on bool untested) |

| unary `Negate` | none |
| binary `Add` | the four remaining new tests |
| binary `Subtract`/`Multiply`/`Divide`/`Modulo` | none (sound — low risk) |
| binary `And`/`Or`/`ExclusiveOr` | none |
| binary `AndAlso`/`OrElse` | **none — and unsound** |
| binary `Coalesce` | **none — and unsound** |
| binary comparisons as a result | none |
| `SqlFunctionExpression` arguments | GoW `LEN` only |
| `SqlFunctionExpression` instance | none |

There is also no *negative* test anywhere in the new set — nothing pins the boundary by asserting the `CASE` is **retained**. That matters beyond finding #1: `Is_not_null_optimizes_binary_op_with_partial_checks` silently depends on `SqlExpressionFactory.Coalesce` setting `argumentsPropagateNullability: [false, false]` (`src/EFCore.Relational/Query/SqlExpressionFactory.cs:502-509`), an invariant no test asserts. If someone later relaxed it, all five new tests would still pass.

**Fix:** add result-asserting tests for the unsound shapes, at least one in `Where(...)` position, and at least one negative test whose baseline still shows the `CASE`:

```csharp
public virtual Task Is_not_null_does_not_optimize_orelse(bool async)
    => AssertQuery(async, ss => ss.Set<NullSemanticsEntity1>().Select(
        x => x.NullableIntA != null ? (bool?)(x.NullableIntA > 0 || x.IntB > 0) : null));

public virtual Task Is_not_null_does_not_optimize_andalso(bool async)
    => AssertQuery(async, ss => ss.Set<NullSemanticsEntity1>().Select(
        x => x.NullableIntA != null ? (bool?)(x.NullableIntA > 0 && x.IntB > 0) : null));

public virtual Task Is_not_null_does_not_optimize_comparison(bool async)
    => AssertQuery(async, ss => ss.Set<NullSemanticsEntity1>().Select(
        x => x.NullableIntA != null ? (bool?)(x.NullableIntA == x.NullableIntB) : null));
```

The `NullSemanticsData` fixture seeds the full 3×3×3 cross product (27 rows, each nullable column NULL in 9 of them), so the discriminating rows already exist — these will fail on the current change and pass once #1 is fixed. Add a Sqlite `AssertSql` override too: Sqlite emits raw booleans where SQL Server wraps them, so it is the provider whose codegen exposes this arm, and it currently has no SQL-shape coverage for the optimization at all.

### #3 🟠 High `pre-existing`: `RestoreNullValueColumnsList` is passed the non-nullable-columns counter

| | |
|---|---|
| **File** | `src/EFCore.Relational/Query/SqlNullabilityProcessor.cs:539` |
| **Category** | correctness (copy-paste) |
| **Confidence** | 100 — verified directly by the orchestrator |
| **Found by** | broad (High) |

**Issue:** In the when-clause loop:

```csharp
RestoreNonNullableColumnsList(currentNonNullableColumnsCount);
RestoreNullValueColumnsList(currentNonNullableColumnsCount);   // should be currentNullValueColumnsCount
```

Every other pairing in the method uses the matching counter — line 528-529 in the `IsFalse` branch immediately above, and lines 565-566 after the loop. `git blame` puts this on `17a9035ad`, so it predates the change under review; it is reported here because `reach=wide` and because the new optimization block consumes exactly this state.

**Failure scenario:** when `_nullValueColumns.Count > _nonNullableColumns.Count` on entry, the call truncates entries belonging to the *enclosing* scope — lost information, hence missed optimizations. In the other direction (`_nullValueColumns.Count < _nonNullableColumns.Count`) `RestoreNullValueColumnsList`'s `counter < Count` guard makes the call a no-op, so "this column is known NULL" facts learned in when-clause *N*'s test leak into when-clause *N+1*, where they do not hold — a premise applied out of scope, which can produce wrong SQL.

**Fix:** `RestoreNullValueColumnsList(currentNullValueColumnsCount);`

### #4 🟡 Medium: The soundness invariant the whole optimization rests on is nowhere written down

| | |
|---|---|
| **File** | `src/EFCore.Relational/Query/SqlNullabilityProcessor.cs:576`, `:617` |
| **Category** | knowledge-preservation |
| **Confidence** | 100 |
| **Found by** | broad (Medium), knowledge (MUST) |

**Issue:** The only comment is `// optimize expressions such as expr != null ? expr : null`, which describes the degenerate case. The rule a maintainer actually needs — *an expression may only be added to `nullPropagatedOperands` if its being NULL forces the whole result to be NULL, as a value, under three-valued logic* — appears nowhere, and neither function carries a doc comment.

The cost is already visible in the diff: the unary arm is a careful whitelist and the function arm consults per-argument metadata, but the binary arm is blanket — and nothing in the code tells you which of the three is the intended pattern. **Fix:** state the invariant above `NullPropagatedOperands`, name the excluded operator classes and why (3VL for `AndAlso`/`OrElse`; `COALESCE` by construction), and cross-reference `ProcessNullNotNull`, which states the same rules at line 2321.

### #6 🟡 Medium: The propagation taxonomy lives in `static` local functions, so it is neither overridable nor exhaustiveness-checked

| | |
|---|---|
| **File** | `src/EFCore.Relational/Query/SqlNullabilityProcessor.cs:595`, `:617` |
| **Category** | evolution-readiness |
| **Confidence** | 75 |
| **Found by** | adversarial (Medium), design (Medium) |

**Issue:** `SqlNullabilityProcessor` otherwise exposes a per-node-type virtual surface (`VisitSqlBinary`, `VisitSqlFunction`, `VisitCustomSqlExpression`, …) precisely so providers can control nullability. This new knowledge has no such hook: a provider needing different semantics must override the entire ~100-line `VisitCase` and keep it in sync forever.

The failure asymmetry is the real risk. An unrecognized *node type* falls to the `else` and is added without recursion — fail-safe, since `CASE WHEN e IS NOT NULL THEN e ELSE NULL END ≡ e` holds for any `e`. But a new *operator* added to `SqlBinaryExpression.IsValidOperator` is silently opted **in** to "propagates null from both operands", with no exhaustiveness check and no test. The immediately preceding commit added `ExclusiveOr`; the next one may not be strict.

**Fix:** promote both helpers to `protected virtual` members (mirroring `PreferExistsToInWithCoalesce` at line 1629), and structure the operator decision as a `switch` with no default-true arm so future additions are a visible decision.

*(No provider in this repo overrides `VisitCase` today — `SqlServerSqlNullabilityProcessor` and `SqliteSqlNullabilityProcessor` override `VisitCustomSqlExpression`, `VisitSqlFunction`, `IsCollectionTable`, `UpdateParameterCollection`, `PreferExistsToInWithCoalesce` — so nothing is bypassed at present. This is about the extension point that is missing, not one that is broken.)*

### #7 🟡 Medium: `func.Instance!` replaces the canonical `Instance: not null` guard with a null-forgiving operator

| | |
|---|---|
| **File** | `src/EFCore.Relational/Query/SqlNullabilityProcessor.cs:633` |
| **Category** | null-safety |
| **Confidence** | 75 — sibling convention verified directly by the orchestrator |
| **Found by** | dotnet (Medium) |

**Issue:** The new code writes `if (func.InstancePropagatesNullability == true) { NullPropagatedOperands(func.Instance!, operands); }`. The canonical guard for the identical question, in this same file at line 2394, is:

```csharp
if (sqlFunctionExpression is { Instance: not null, InstancePropagatesNullability: true })
```

The new code drops the `Instance: not null` half and substitutes `!`, asserting an invariant the type does not enforce: `SqlFunctionExpression`'s `[EntityFrameworkInternal]` constructor accepts `SqlExpression? instance` alongside `bool? instancePropagatesNullability` and validates only argument/flag *counts*, and `Update(instance, arguments)` preserves `InstancePropagatesNullability` verbatim while accepting a null instance.

In practice the public factories do appear to keep `instancePropagatesNullability: true` and a non-null `instance` together, so this is very likely unreachable today — which is exactly why it should be a pattern match rather than a `!`: the compiler then keeps it unreachable for free.

**Fix:** `if (func is { Instance: not null, InstancePropagatesNullability: true })` — removes the null-forgiving operator and matches the sibling.

### #8 🟡 Medium: `DropNotNullChecks` returns `null` to mean the constant TRUE, leaving no sentinel for "cannot simplify"

| | |
|---|---|
| **File** | `src/EFCore.Relational/Query/SqlNullabilityProcessor.cs:595`, `:600`, `:585` |
| **Category** | comprehension-risk |
| **Confidence** | 75 |
| **Found by** | knowledge (SHOULD) |

**Issue:** The encoding is documented only by a trailing `// true` on the return. The signature says nothing, and the call site reads `if (test is null) { return clause.Result; }`, which scans as a defensive null check rather than "the guard is now vacuous, so emit the result unconditionally".

The sentinel has no spare value. A maintainer extending `DropNotNullChecks` to handle a case it *cannot* simplify — an `OrElse` test, an unrecognized provider node — has one obvious-looking bail-out, `return null`, and that bail-out does not mean "leave the CASE alone", it means "delete the guard entirely". The failure is silent: no exception, no assertion, just a query that has lost its null guard.

**Fix:** document the contract on the local function and rule the third outcome out explicitly:

```csharp
// Returns the test with redundant "X IS NOT NULL" conjuncts removed, or null if every
// conjunct was removed (the test is now constant TRUE, so the result can be emitted
// unconditionally). Never return null to signal "cannot simplify" — return the
// original expression instead.
```

### #9 🟢 Low: The analysis is done eagerly and unconditionally, with superlinear structural hashing

| | |
|---|---|
| **File** | `src/EFCore.Relational/Query/SqlNullabilityProcessor.cs:580-582`, `:619` |
| **Category** | efficiency |
| **Confidence** | 100 |
| **Found by** | performance (Low ×2), broad (Low), security (Low) |

**Issue:** Two compounding costs on the query-compilation path, paid for every single-when-clause CASE with a NULL else — a very common shape (optional-navigation and null-conditional projections):

1. **Order.** A `HashSet<SqlExpression>` is allocated and the *entire* null-propagating result subtree walked (line 582) *before* line 583 ever looks at the test. When the test contains no `IS NOT NULL` — `x > 5 ? bigExpr : null` — all of that work is discarded.
2. **Hashing.** `SqlBinaryExpression.GetHashCode` is `HashCode.Combine(base, OperatorType, Left, Right)` and is never memoized, so hashing one node is O(subtree). Since every node on the spine is `Add`ed, the total is O(R log R) for a balanced result and **O(R²)** for a deep left-leaning one — precisely what long concatenation and `OR`/`AND` chains produce.

Bounded in practice by plan caching and ordinary expression sizes, which is why this is Low rather than higher; but it is on the cold-compile path that dominates application startup.

**Fix:** drop the set entirely. Collect the one-to-three operands of the `IS NOT NULL` checks actually present in the test first (cheap, O(T), and bails out immediately when there are none), then run a targeted `PropagatesNullFrom(result, operand)` predicate with a `ReferenceEquals` fast path and early exit on first match. That removes the allocation, all structural hashing, and the wasted walk in one change. Also skip the `whenClauses = [new(test, clause.Result)]` allocation at line 590 when `ReferenceEquals(test, clause.Test)`.

### #10 🟢 Low: `IsNull(elseResult)` is false for an absent `ELSE`, so two equivalent trees optimize differently

| | |
|---|---|
| **File** | `src/EFCore.Relational/Query/SqlNullabilityProcessor.cs:578` (with `IsNull` at `:1633`) |
| **Category** | consistency (missed optimization) |
| **Confidence** | 100 |
| **Found by** | broad (Low), design (Low) |

**Issue:** `IsNull` matches only a null `SqlConstantExpression` or a parameter bound to null. A `CaseExpression` with `ElseResult == null` means `ELSE NULL` in SQL — `VisitCase` itself records that equivalence a few lines above, materializing a null constant on the `whenClauses.Count == 0` path — but it does not satisfy the guard. So `CASE WHEN x IS NOT NULL THEN f(x) END` is never optimized while the identical `... ELSE NULL END` is. A live example sits in the new baselines: `CASE WHEN [e].[NullableStringA] IS NOT NULL THEN 0 END`.

Conservative, so no wrong results — but the asymmetry is invisible and will read as a bug to the next maintainer.

**Fix:** `elseResult is null || IsNull(elseResult)`, matching how the `whenClauses.Count == 0` branch already normalizes the two forms.

## Specialist Notes

### Threat Model Notes (security-reviewer)

- No trust boundary is crossed inside the changed code — it is a compile-time expression rewriter with no string interpolation, no external input parsing, and no I/O. No SQL-injection, secrets, or authn/authz surface. Manufacturing an OWASP finding here would be noise.
- The security-relevant property is **semantic**: a query-plan optimizer's contract is that the rewritten predicate admits exactly the rows the original admitted. Because EF Core applications overwhelmingly express row-level authorization as LINQ predicates (`HasQueryFilter`, `Where`), the WHERE-clause semantics change in finding #1 is an access-control change in those applications. `NULL` in a filter means "excluded"; turning it into `TRUE` is a fail-open. `OrElse` and `Coalesce` fail open, `AndAlso` fails closed — weight the former higher.
- **Blast radius**: `SqlNullabilityProcessor` is shared by every relational provider, with no opt-out flag and no `UseRelationalNulls`-style escape hatch for this rewrite.
- **Resource bounds**: for a front end that builds LINQ predicates from client input (OData/GraphQL/dynamic filter builders), each distinct hostile tree is a fresh compilation that the plan cache does not absorb, so finding #9's superlinear hashing is reachable per-request. The fix for #9 also caps this.
- **Stack overflow via unbounded recursion: not a new risk.** `SqlNullabilityProcessor.Visit`, `ExpressionVisitor`, and the Roslyn-produced tree all already recurse to the same depth; a tree deep enough to overflow in `NullPropagatedOperands` overflows several phases earlier. Three reviewers examined this independently and reached the same conclusion.

### Considered But Not Flagged (all agents)

**Refuted by validation:**

- **"Dropping the test invalidates the non-null premise the result was simplified under"** (line 578) — raised by broad (High), adversarial (High), and design (Critical); the strongest non-#1 claim in the wave. **Refuted.** The new block runs *after* `RestoreNonNullableColumnsList`/`RestoreNullValueColumnsList` at line 565, so `NullPropagatedOperands` analyzes the already-emitted result rather than re-deriving it under the premise; soundness therefore reduces entirely to whether the collector classifies the emitted expression's strictness correctly, which is finding #1. Moreover every premise-driven elision (the `COALESCE(x, N'')` concat protection at 1341-1349, the `CASE WHEN cond THEN TRUE ELSE FALSE` wrap at 1411-1431, the null-semantics `AND`/`OR` expansion at 1389-1403) *removes* non-strictness, making the emitted expression more null-propagating, not less — the direction that makes dropping the guard safe. A 30-query probe battery produced exactly three mismatches, all with `AndAlso`/`OrElse` at the top of the result and therefore all subsumed by #1's allowlist fix. The specific string-concat case was checked directly: `x.StrA != null ? x.StrA + "foo" : null` emits `SELECT "StrA" || 'foo'` with no `COALESCE` and correctly returns NULL.

**Examined and found sound:**

- **The `SqlFunctionExpression` arm.** The `{ IsNullable: true }` pattern correctly skips non-nullable functions; `[MemberNotNullWhen(false, nameof(Arguments), nameof(ArgumentsPropagateNullability))]` on `IsNiladic` covers the niladic guard; and the constructor enforces `Arguments.Count == ArgumentsPropagateNullability.Count` (`SqlFunctionExpression.cs:217-223`), so no `IndexOutOfRangeException` is reachable. This arm is the model the binary arm should have followed.
- **`COALESCE` via the factory.** `SqlExpressionFactory.Coalesce` (`SqlExpressionFactory.cs:502-509`) emits a `SqlFunctionExpression` with `argumentsPropagateNullability: [false, false]`, so `??` is handled correctly today. The binary-`Coalesce` hazard in #1 is about what a provider or custom factory could construct, not about the in-box path.
- **The `SqlUnaryExpression` arm** (`Not`, `Negate`, `Convert`) — all three are strict in SQL. `Not` correctly does not recurse past a nested `IS NULL` (unary `Equal`), since that operator is absent from the list.
- **`HashSet<SqlExpression>` without an explicit comparer.** Every `SqlExpression` subclass overrides `Equals`/`GetHashCode` structurally, so `Contains` matches structurally, which is what the optimization needs. `ExpressionEqualityComparer` is EF's comparer for raw LINQ trees, which lack structural `Equals` — not applicable here, and sibling code in this file already relies on built-in structural equality (`_nonNullableColumns.Contains(columnOperand)`, line 2280). The one sibling that supplies `ReferenceEqualityComparer` (`SelectExpression.Helper.cs:158`) needs identity, a different requirement. Any mismatch would cause a *missed* optimization, never a wrong one — fails safe.
- **The `out bool nullable` contract** on both new exits. On `return clause.Result`, the `IsNull(elseResult)` guard means `elseResultNullable` was already set, so `nullable` is `true` — conservative and correct. On the `whenClauses` rewrite, neither result nor else changed.
- **Type/type-mapping loss on `return clause.Result`.** `CaseExpression`'s constructors take `Type`/`TypeMapping` from `whenClauses[0].Result`, so returning the sole when-clause result preserves both. This also matches the pre-existing early return at line 547.
- **`DropNotNullChecks` only unwrapping `AndAlso`.** Correct and conservative — a check inside an `OrElse` must not be dropped, and probes confirm the CASE is retained in that shape.
- **Provider custom `SqlExpression` subtypes** (spatial, JSON, vector). Traced both directions: in the *test* position an unrecognized shape falls through `DropNotNullChecks`'s `else` unchanged; in the *result* position it is added without recursion. Both fail-safe. The unsoundness is entirely in the recursion arms.
- **Local `static` functions declared after a `return`.** Established in this exact file — `TryNegate` (line 2095) sits after `return sqlUnaryExpression;` in the same style. Also `static` correctly prevents capturing `this`/`_sqlExpressionFactory`.
- **Collection expressions `[]` / `[new(test, clause.Result)]`.** Target-type to `List<CaseWhenClause>`; `CaseExpression.Update` takes `IReadOnlyList<CaseWhenClause>`. No behavior change from the reassignment.
- **Bare `// TODO: optimize expr == null ? null : expr` without an issue reference.** Checked against repo practice: `src/` holds 226 TODOs of which only 65 (~29%) carry a `#NNNNN`, with many bare ones in `src/EFCore.Relational/Query/` itself; no CONTRIBUTING.md or CLAUDE.md states a standard. The TODO names the exact unimplemented case, so no knowledge is lost.
- **`VisitCase`'s XML doc not updated.** It already promises "An optimized sql expression", and `VisitCase` could already return a non-`CaseExpression` before this change (line 546). No contract change for overriders.
- **Sqlite not overriding the five new tests.** `NullSemanticsQuerySqliteTest` selectively overrides only ~24 base tests and does not override the pre-existing sibling family `Is_null_on_column_followed_by_OrElse_optimizes_*` either — consistent with existing practice, not a symmetry gap. (Finding #2 still recommends adding a Sqlite override, for coverage reasons rather than convention.)
- **Baseline completeness.** The only other same-shape baseline in the test tree, `Null_propagation_optimization3` (`GearsOfWarQuerySqliteTest.cs:1561`, `THEN "g"."LeaderNickname" LIKE '%us'`), correctly did *not* change — `LikeExpression` is not a node type the collector recurses into. All five GearsOfWar files updated the identical set of five tests; `TPCGearsOfWarQuerySqliteTest` / `TPTGearsOfWarQuerySqliteTest` override none of them.
- **GearsOfWar baseline-only changes hiding a behavior change.** All five rewritten baselines belong to `AssertQuery`-based tests in `GearsOfWarQueryTestBase.cs`, so each shape change is backed by a result assertion against the in-memory model on both SqlServer and Sqlite.
- **Whether this optimization belongs in a different pass.** No — `SqlExpressionOptimizingExpressionVisitor` and `SearchConditionConvertingExpressionVisitor` run before and after nullability expansion respectively, and the `IS NOT NULL` tests being targeted are largely *produced* by `SqlNullabilityProcessor` itself. The placement objection is about granularity within the class, which is finding #6.
