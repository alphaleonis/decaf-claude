## Findings

### #1 🔴 Critical: `NullPropagatedOperands` treats `AND`/`OR` as null-propagating, so the guard is dropped from `CASE WHEN x IS NOT NULL THEN <boolean expr over x> ELSE NULL END` and the query returns `true`/`false` where it must return `null`

| | |
|---|---|
| **File** | `src/EFCore.Relational/Query/SqlNullabilityProcessor.cs:626` |
| **Category** | correctness |
| **Confidence** | 100 |
| **Verified** | executed |
| **Pre-existing** | no |
| **Found by** | solo-reviewer (Critical) |

**Issue:** The `else if (expression is SqlBinaryExpression binary)` arm recurses into `Left` and `Right` for *every* `SqlBinaryExpression` operator type. `SqlBinaryExpression.IsValidOperator` (`SqlBinaryExpression.cs:83-108`) admits `AndAlso` and `OrElse`, and under SQL's three-valued logic those do **not** propagate NULL: `NULL OR TRUE = TRUE`, `NULL AND FALSE = FALSE`. So any operand that appears anywhere inside a boolean expression gets marked "null-propagated", `DropNotNullChecks` deletes its `IS NOT NULL` test, and the whole `CASE` collapses to the bare boolean expression — which yields `TRUE`/`FALSE` for exactly the rows the guard existed to map to `NULL`.

This is not an exotic shape. EF's own null-semantics expansion of `==`/`!=` between two nullable operands *produces* `AndAlso`/`OrElse` nodes, so the most ordinary conditional-comparison projection hits it. It also composes with the `Not` unary arm at `:621-625`, which descends into a boolean operand and then lands in this same arm.

**Evidence:** Executed. A scratch console app (built in `/tmp`, since `test/EFCore.Specification.Tests` does not compile under the installed SDK for reasons unrelated to this change) was run against `src/EFCore.Sqlite.Core` at `HEAD` (`afcfba2e9`) and against a `git worktree` at the pre-change commit `051c33a79`, over three rows, comparing each query's database result to the same lambda run with LINQ-to-Objects. Five independent shapes regress; the pre-change build is correct on all of them.

| Query (`x` = entity) | SQL at `afcfba2e9` | Row data | DB (after) | DB (before) / LINQ |
|---|---|---|---|---|
| `x.NullableIntA != null ? (bool?)(x.NullableIntA == x.NullableIntB) : null` | `"NullableIntA" = "NullableIntB" AND "NullableIntB" IS NOT NULL` | A=null, B=null | **`False`** | `null` |
| `x.NullableIntA != null ? (bool?)(x.NullableIntA != x.NullableIntB) : null` | `"NullableIntA" <> "NullableIntB" OR "NullableIntB" IS NULL` | A=null, B=null | **`True`** | `null` |
| `x.NullableStringA != null ? (bool?)(x.NullableStringA == x.NullableStringB) : null` | `"NullableStringA" = "NullableStringB" AND "NullableStringB" IS NOT NULL` | A=null, B=null | **`False`** | `null` |
| `x.NullableIntB != null ? (bool?)(x.NullableIntB > 0 \|\| x.BoolA) : null` | `"NullableIntB" > 0 OR "BoolA"` | B=null, BoolA=true | **`True`** | `null` |
| `x.NullableIntB != null ? (bool?)(x.NullableIntB > 0 && x.BoolA) : null` | `"NullableIntB" > 0 AND "BoolA"` | B=null, BoolA=false | **`False`** | `null` |
| `x.NullableIntB != null ? (bool?)!(x.NullableIntB > 0 \|\| x.BoolA) : null` | `"NullableIntB" <= 0 AND NOT ("BoolA")` | B=null, BoolA=true | **`False`** | `null` |

The pre-change SQL in every case is `CASE WHEN <col> IS NOT NULL THEN <expr> ELSE NULL END`, which returns `NULL` correctly.

Note the mechanism has a second, compounding half worth stating in the fix: the WHEN-result is visited at `:534` while `_nonNullableColumns` still carries the knowledge established by the test (`preserveColumnNullabilityInformation: true` at `:513-514`). That is why `A == B` is emitted as `A = B AND B IS NOT NULL` rather than the full `(A = B) OR (A IS NULL AND B IS NULL)` — the `A IS NULL` disjunct was already folded away *because the guard proved `A` non-null*. Removing the guard therefore invalidates simplifications baked into the result, not just the guard itself. In every shape constructed, that invalidation surfaces through an `AndAlso`/`OrElse` node, so the operator whitelist below is sufficient for the demonstrated cases — but the premise "the result propagates null from the operand" must be evaluated against the *unsimplified* result, and it would be worth a comment saying so.

**Fix:** Restrict the binary arm to operators that genuinely propagate NULL in emitted SQL, instead of accepting every valid operator:

```csharp
else if (expression is SqlBinaryExpression
    {
        OperatorType: ExpressionType.Add or ExpressionType.Subtract or ExpressionType.Multiply
            or ExpressionType.Divide or ExpressionType.Modulo
            or ExpressionType.And or ExpressionType.Or or ExpressionType.ExclusiveOr
            or ExpressionType.Equal or ExpressionType.NotEqual
            or ExpressionType.LessThan or ExpressionType.LessThanOrEqual
            or ExpressionType.GreaterThan or ExpressionType.GreaterThanOrEqual
    } binary)
```

i.e. exclude `AndAlso`, `OrElse` (three-valued logic) and `Coalesce` (see #2). An allow-list rather than a deny-list is the right shape here, so a future operator added to `SqlBinaryExpression.IsValidOperator` fails closed. Also add spec tests with `bool?`-typed results — all five new tests project non-boolean results (`int?`/`string`), which is precisely why the suite is green on a change that miscompiles the boolean case.

### #2 🟡 Medium: `Coalesce` is also traversed as null-propagating

| | |
|---|---|
| **File** | `src/EFCore.Relational/Query/SqlNullabilityProcessor.cs:626` |
| **Category** | correctness |
| **Confidence** | 50 |
| **Verified** | traced |
| **Pre-existing** | no |
| **Found by** | solo-reviewer (Medium) |

**Issue:** Same arm, distinct operator. `ExpressionType.Coalesce` is admitted by `SqlBinaryExpression.IsValidOperator` (`SqlBinaryExpression.cs:102`) and is constructible through the public `ISqlExpressionFactory.MakeBinary` (`SqlExpressionFactory.cs:394-421`, which only rejects operators failing `IsValidOperator`). `COALESCE(a, b)` does not propagate null from `a`, so marking `a` null-propagated and dropping `a IS NOT NULL` from `CASE WHEN a IS NOT NULL THEN COALESCE(a, b) ELSE NULL END` yields `b` instead of `NULL` when `a` is null.

**Evidence:** Traced. The counter-argument, stated plainly: this arm is not reachable through the stock pipeline today. `RelationalSqlTranslatingExpressionVisitor.cs:450-451` routes `??` to `SqlExpressionFactory.Coalesce`, which builds a `SqlFunctionExpression("COALESCE", …, argumentsPropagateNullability: [false, false])` (`SqlExpressionFactory.cs:502-508`) — handled correctly by the function arm, and it was confirmed empirically that `x.NullableIntB != null ? (x.NullableIntB ?? 100) + 1 : null` keeps its `CASE` intact at `HEAD`. Further, `QuerySqlGenerator.GetOperator` (`QuerySqlGenerator.cs:1081-1102`) has no `Coalesce` case and throws `UnreachableException`, so a binary-`Coalesce` tree cannot currently reach SQL at all. The exposure is therefore limited to a provider that overrides the `protected virtual GetOperator` to render it, or any future change that starts emitting the binary form — at which point the wrong results are silent rather than an exception. Reported rather than parked because the operator is legal per `IsValidOperator`, the public factory builds it, and the fix is free.

**Fix:** Covered by the allow-list in #1 — `Coalesce` simply is not in it.
