## Findings

### #1 🟠 High: `TotalSamples` silently stops counting per-step for `@`-anchored range selectors

| | |
|---|---|
| **File** | `promql/engine.go:2145` (also `:2160`, `:2183`) |
| **Category** | correctness |
| **Confidence** | 100 |
| **Verified** | executed |
| **Pre-existing** | no |
| **Found by** | solo-reviewer (High) |

**Issue:** `fullWindowCount` is declared inside the step loop and assigned *only* inside the
`if ts == ev.startTimestamp || selVS.Timestamp == nil` block. Before this change,
`IncrementSamplesAtStep` was called outside that block with the live
`len(floats)+totalHPointSize(histograms)`, which stayed populated across steps when the `@`
modifier let the data be reused. Now every step after the first contributes `0`. That changes
the value of the existing `totalQueryableSamples`, `totalQueryableSamplesPerStep` and the
`prometheus_engine_query_samples_total` counter — the exact things the inline comment claims are
"unchanged semantics".

The path is reachable whenever the range-vector selector carries `@` but the enclosing call is
*not* step-invariant, i.e. multi-argument range functions: `quantile_over_time`,
`predict_linear`, `double_exponential_smoothing`. (For single-argument calls the whole expression
is wrapped in `StepInvariantExpr`, which masks the bug — which is why the existing `@` cases in
`TestQueryStatistics` still pass.)

**Evidence:** Executed. The same probe file was run in this tree and in a `git worktree` at the
base commit `efbdc3f88`; range query `start=201s end=220s step=5s` over
`metricWith1SampleEvery10Seconds 1+1x100`:

```
q = quantile_over_time(scalar(metricWith1SampleEvery10Seconds), metricWith1SampleEvery10Seconds[60s] @ 30)
base (efbdc3f88): TotalSamples=20  perStep=[5 5 5 5]
head (ec7157593): TotalSamples=8   perStep=[5 1 1 1]
```

The residual `1` per step is the unrelated `scalar(...)` selector; the range-vector's
contribution went from 4 per step to 4 only at step 0. The control query without `@` is unchanged
(28 / `[7 7 7 7]` in both). No test in the change covers this shape.

**Fix:** Keep `TotalSamples` accounting where it was — compute the full-window count
unconditionally from the (possibly reused) `floats`/`histograms` slices after the `if`, and only
gate the new `samplesReadCount` on whether data was actually re-read:

```go
fullWindowCount := int64(len(floats) + totalHPointSize(histograms))
ev.samplesStats.IncrementSamplesAtStep(step, fullWindowCount)
ev.samplesStats.IncrementSamplesReadAtStep(step, samplesReadCount) // 0 when @ reused
```

### #2 🟠 High: `SamplesRead` double-counts every subquery, and the documented invariant it advertises is false

| | |
|---|---|
| **File** | `promql/engine.go:1874` (with `util/stats/query_stats.go:423`) |
| **Category** | correctness |
| **Confidence** | 100 |
| **Verified** | executed |
| **Pre-existing** | no |
| **Found by** | solo-reviewer (High) |

**Issue:** `evalSubquery` now merges the subquery's `SamplesRead` into the parent
(`MergeSamplesReadFromSubquery`), *and* the resulting synthetic matrix is then walked again by
the range-vector branch at `engine.go:2184`, which adds the same points a second time via
`IncrementSamplesReadAtStep`. The pre-existing comment that this change replaced said exactly why
the child was discarded: "Avoid double counting samples when running a subquery, those samples
will be counted in later stage." That rationale applies to `SamplesRead` too — the subquery's
output points *are* the samples the subquery read.

Consequences:

1. `prometheus_engine_query_samples_read_total` and `samplesRead` report ≈2× the real I/O for any
   query containing a subquery — the headline number of the feature.
2. `samplesRead` can exceed `totalQueryableSamples`, directly contradicting the text this change
   adds at `docs/querying/api.md:246` and `docs/feature_flags.md:47`: *"For other query types,
   this equals totalQueryableSamples."*

**Evidence:** Executed, and also visible in the change's own committed expectations.

Probe (instant queries, per-step stats on, `m 1+1x1000` at 10s):

```
rate(m[5m:1m])          TotalSamples=5   SamplesRead=10
max_over_time(m[1m:1m]) TotalSamples=1   SamplesRead=2
```

Exactly 2× in both. The change's own table records the same and even labels it:
`promql/engine_test.go:1547` — `SamplesRead: 2, // subquery + outer` for
`sum_over_time(metricWith1SampleEvery10Seconds[30s:30s])` where `TotalSamples: 1`. And
`promql/engine_test.go:1707` records `SamplesRead: 102` against `TotalSamples: 78` for
`avg_over_time(metricWith3SampleEvery10Seconds[73s:17s])[5m:43s]` — `samplesRead >
totalQueryableSamples` on an instant query, which the shipped docs say cannot happen.

Counter-argument, stated for the record: the merge is clearly deliberate (the new doc comment at
`engine.go:1861-1863` describes it, and the test comment names the two contributions). But
"deliberate" does not reconcile it with the metric's stated meaning (I/O) or with the invariant
the same commit writes into the public API docs, so the intent needs to be decided rather than
assumed.

**Fix:** Pick one attribution and make the docs match. Either (a) drop
`MergeSamplesReadFromSubquery` and let the outer range-vector counting stand as the single
accounting of subquery samples — preserving the original "counted in a later stage" rule and the
`samplesRead == totalQueryableSamples` invariant for non-range-vector-in-range-query cases; or
(b) keep the inner merge and suppress the outer `IncrementSamplesReadAtStep` when `selVS.Series`
came from a subquery (the `evalSubquery`-produced selector), since those points are not I/O.
Whichever is chosen, correct the sentence at `docs/querying/api.md:246` and
`docs/feature_flags.md:47`.

### #3 🟢 Low: new API assertions are tautological — they pass with `SamplesRead` never populated

| | |
|---|---|
| **File** | `web/api/v1/api_test.go:983` (and `:999`) |
| **Category** | tests |
| **Confidence** | 100 |
| **Verified** | traced |
| **Pre-existing** | no |
| **Found by** | solo-reviewer (Low) |

**Issue:** `require.GreaterOrEqual(t, qs.Samples.SamplesRead, int64(0))` cannot fail for the
defect it is placed to guard. `SamplesRead` is an `int64` counter that is only ever incremented
by non-negative amounts, so the assertion holds even if the field is never written at all — e.g.
if the engine stopped populating it, or if the JSON field were renamed and decoded to the zero
value. The sibling assertions on the adjacent lines
(`require.NotNil(qs.Samples.TotalQueryableSamples)`) at least distinguish present from absent.

**Evidence:** Traced. Deleting every `IncrementSamplesRead*` call would leave `SamplesRead == 0`,
and `0 >= 0` still passes. `TestStats` is the only `web/api/v1` coverage the change adds for the
new field.

**Fix:** Assert something the query actually produces — the test issues a query over known data,
so `require.Positive(t, qs.Samples.SamplesRead)` (or an exact expected count) would fail if the
field stopped being populated.

### #4 🟢 Low: the stats table records observed output rather than derived expectations, and says so

| | |
|---|---|

| **Category** | tests |
| **Confidence** | 100 |

**Issue:** A scratch note block was committed into the test table:

```
// IMPLEMENTATION NOTES:
// - Added comprehensive test coverage for subquery sample counting
// - Some sample count calculations may need refinement based on actual query execution
```

Several cases carry matching comments — `promql/engine_test.go:1543`
(`TotalSamples: 1, // Actual behavior: single step shows 1 effective sample`), `:1538`
(`- corrected values`). Roughly a thousand lines of new expectations whose author states they may
not be right is a weak regression net: a future change that alters the counts will be "fixed" by
re-snapshotting rather than investigated. Finding #2 above is an instance — the doubled value at
`:1547` is recorded as expected rather than questioned.

The same case, `sum_over_time(metricWith1SampleEvery10Seconds[30s:30s])` with identical fields,
appears three times (`:1541`, `:1590`, `:1639`), producing duplicate `t.Run` names; that is
consistent with the table having been assembled from captured output.

**Evidence:** Read. Lines quoted above are verbatim from the committed test file. All cases pass
(`go test ./promql -run TestQueryStatistics` → ok), which is the point: passing tells us nothing
about whether the numbers are the intended ones.

**Fix:** Remove the scratch block, drop the two duplicate cases, and for the subquery cases
replace the `// subquery + outer` style comments with a derivation of the expected count from the
fixture (samples per series × steps in window), so a future diff in the number is a question
rather than a re-snapshot.

### #5 🟢 Low: subquery children now allocate and write a `TotalSamplesPerStep` array that is never read

| | |
|---|---|
| **File** | `util/stats/query_stats.go:411` (callers `promql/engine.go:1869`, `:2397`) |
| **Category** | efficiency |
| **Confidence** | 100 |
| **Verified** | traced |
| **Pre-existing** | no |
| **Found by** | solo-reviewer (Low) |

**Issue:** `NewChildWithStepTracking` calls `InitStepTracking`, which allocates *both*
`TotalSamplesPerStep` and `SamplesReadPerStep`. Only the latter is consumed: the subquery's
`TotalSamples` is folded into the parent as a scalar at `engine.go:2424`
(`IncrementSamplesAtTimestamp(ev.endTimestamp, newEv.samplesStats.TotalSamples)`), and
`MergeSamplesReadFromSubquery` explicitly does not touch total-samples state. So every subquery
evaluation under `promql-per-step-stats` allocates one dead `[]int64` (outer step count in
`evalSubquery`, subquery step count in the `SubqueryExpr` case) and writes into it on every step.
Previously `NewChild()` allocated nothing.

**Evidence:** Traced, with instrumentation. `InitStepTracking` was temporarily instrumented
(restored byte-identically afterwards, verified with `cmp` and `git status`) and two extra
`InitStepTracking` calls per subquery per query were observed. Grep confirms
`TotalSamplesPerStep` on a subquery child is never read: the only readers are
`totalSamplesPerStepPoints`/`TotalSamplesPerStepMap`, which run on the top-level
`query.sampleStats`.

**Fix:** Give `InitStepTracking` a variant (or a flag) that allocates only `SamplesReadPerStep`,
and have `NewChildWithStepTracking` use it — the child never needs per-step totals.
