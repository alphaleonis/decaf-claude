## Findings

### #1 🔴 Critical: `NullPropagatedOperands` treats `AndAlso`/`OrElse` as NULL-propagating, contradicting the file's own rule and changing query results

| | |
|---|---|
| **File** | `src/EFCore.Relational/Query/SqlNullabilityProcessor.cs:626` |
| **Category** | correctness |
| **Confidence** | 75 |
| **Verified** | traced |
| **Pre-existing** | no |
| **Found by** | solo-reviewer (Critical) |

**Issue:** The binary arm recurses into `binary.Left` and `binary.Right` for *every* `SqlBinaryExpression` operator. `AndAlso` and `OrElse` do not propagate NULL under three-valued logic (`FALSE AND NULL = FALSE`, `TRUE OR NULL = TRUE`), so an operand reached only through a logical connective must not license dropping its `IS NOT NULL` test. This same file already states the rule explicitly, 1700 lines further down, in `ProcessNullNotNull`:

```csharp
case SqlBinaryExpression sqlBinaryOperand
    when sqlBinaryOperand.OperatorType != ExpressionType.AndAlso
    && sqlBinaryOperand.OperatorType != ExpressionType.OrElse:
{
    // in general:
    // binaryOp(a, b) == null -> a == null || b == null
    // ...
    // for AndAlso, OrElse we can't do this optimization
```
(`SqlNullabilityProcessor.cs:2313-2321`). The new helper omits exactly that guard.

**Evidence:** Failure scenario — a predicate-position variant of the existing `Null_propagation_optimization3` (`test/EFCore.Specification.Tests/Query/GearsOfWarQueryTestBase.cs:879-883`):

```csharp
ss.Set<Gear>().Where(g => (g.LeaderNickname != null
    ? g.LeaderNickname.Length > 3 || g.HasSoulPatch
    : null) == true)
```

Trace: `(case) == true` in a predicate is stripped at `SqlNullabilityProcessor.cs:1274-1277` (`allowOptimizedExpansion` is `true` for `SelectExpression.Predicate`, line 310), so the `CASE` becomes the predicate. `clause.Result` is `OrElse(GreaterThan(Convert(LEN([g].[LeaderNickname])), 3), [g].[HasSoulPatch])`. `NullPropagatedOperands` walks `OrElse` → `GreaterThan` → `Convert` → `LEN(...)` → `[g].[LeaderNickname]`. That the `CAST(LEN(...))` chain *is* matched is not inference — this change's own updated baseline (`GearsOfWarQuerySqlServerTest.cs:1023`, now `WHERE CAST(LEN([g].[LeaderNickname]) AS int) = 5`) proves it. `DropNotNullChecks` therefore returns `null` and line 587 returns the bare `OrElse`.

- Before: `WHERE CASE WHEN [g].[LeaderNickname] IS NOT NULL THEN <cond> ELSE NULL END` — a row with `LeaderNickname IS NULL` yields NULL → not matched.
- After: `WHERE CAST(LEN([g].[LeaderNickname]) AS int) > 3 OR [g].[HasSoulPatch] = CAST(1 AS bit)` — a row with `LeaderNickname IS NULL` and `HasSoulPatch = 1` yields `NULL OR TRUE` = TRUE → **matched**.
- C# expectation: `(null) == true` → `false` → row excluded. EF now returns rows it must not.

This is provider-independent (SQLite: `NULL OR 1` = `1` likewise). The same defect in a projection flips `null` to `true`:
`Select(x => x.NullableIntA != null ? (bool?)(x.NullableIntA > 5 || x.BoolA) : null)` returns `true` instead of `null` for rows where `NullableIntA IS NULL` and `BoolA = 1`.

A second route into the same fault does not even need `||` in the user's query — the null-semantics rewrite *manufactures* the `OrElse`, using the very non-nullability knowledge that is about to be dropped. For
`Select(x => x.NullableStringA != null ? (bool?)(x.NullableStringA != x.NullableStringB) : null)`, the result is visited with `[A]` in `_nonNullableColumns` (deliberately — see the comment at line 512), so `ExpandNullableEqualNullable` produces `A = B AND B IS NOT NULL` and then DeMorgans it (line 1896 → `OptimizeNonNullableNotExpression`, line 2005-2023) into `[A] <> [B] OR [B] IS NULL`, recording `nullable = false` at line 1880 on the strength of "`[A]` is non-null". Dropping `[A] IS NOT NULL` invalidates that premise: for `A IS NULL, B IS NULL` the expression is `NULL <> NULL OR TRUE` = TRUE, so the projection yields `true` where `null` is expected.

Not executed: the SQL Server functional tests need a live instance, and probe-test authoring was forbidden by the review constraint. Every step above is anchored on committed code or on a baseline already in the repo.

**Fix:** Exclude the non-propagating connectives in `NullPropagatedOperands`, mirroring the guard at line 2313:

```csharp
else if (expression is SqlBinaryExpression binary
    && binary.OperatorType is not (ExpressionType.AndAlso or ExpressionType.OrElse or ExpressionType.Coalesce))
```

Note that this alone does not make the optimization sound for boolean results — see #2. The deeper invariant worth writing down next to line 576 is that `clause.Result` was visited *under the assumption the test holds*, so any conjunct dropped from the test must be one the result's simplification did not consume.

### #2 🟠 High: dropping the `ELSE NULL` destroys the NULL of a boolean when-clause result on SQL Server (`null` becomes `false`)

| | |
|---|---|
| **File** | `src/EFCore.Relational/Query/SqlNullabilityProcessor.cs:578` |
| **Category** | correctness |
| **Confidence** | 75 |
| **Verified** | traced |
| **Pre-existing** | no |
| **Found by** | solo-reviewer (High) |

**Issue:** The optimization's soundness argument is "if the operand is NULL the result is NULL, so the `CASE` is redundant". For a *scalar* result that holds. For a **search condition** result it does not, because a NULL search condition does not survive its conversion to a value: the enclosing `CASE ... ELSE NULL` was the only carrier of the NULL. The guard at line 578 does not distinguish the two, so the optimization fires on boolean results.

`SqlNullabilityProcessor` runs strictly before SQL Server's search-condition conversion — `SqlServerParameterBasedSqlProcessor.Optimize` calls `base.Optimize` (which runs `ProcessSqlNullability`) and only then `new SearchConditionConvertingExpressionVisitor(...).Visit(...)` (`src/EFCore.SqlServer/Query/Internal/SqlServerParameterBasedSqlProcessor.cs:40-45`). And `RelationalSqlTranslatingExpressionVisitor.VisitConditional` (line 615-625) does no boolean wrapping, so at `VisitCase` time `clause.Result` really is a raw condition. That converter is lossy by design:

```csharp
private SqlExpression ConvertToValue(SqlExpression sqlExpression, bool condition)
    => condition
        ? _sqlExpressionFactory.Case(
            new[] { new CaseWhenClause(SimplifyNegatedBinary(sqlExpression), ...Constant(true)) },
            _sqlExpressionFactory.Constant(false))
        : sqlExpression;
```
(`SearchConditionConvertingExpressionVisitor.cs:41-51`) — `CASE WHEN c THEN 1 ELSE 0 END`, so NULL collapses to `false`. Projections are visited with `_isSearchCondition = false` (`ibid.:286-288`), so this is the path taken.

**Evidence:** Failure scenario:

```csharp
ss.Set<NullSemanticsEntity1>().Select(
    x => x.NullableIntA != null ? (bool?)(x.NullableIntA > 5) : null)
```

`(bool?)` is stripped at `RelationalSqlTranslatingExpressionVisitor.cs:1253-1256` (`UnwrapNullableType` match), so `clause.Result` is `GreaterThan([NullableIntA], 5)`. `NullPropagatedOperands` adds `[NullableIntA]`; the test is dropped; line 587 returns the bare comparison.

- Should produce (and does today): `SELECT CASE WHEN [e].[NullableIntA] IS NOT NULL THEN CASE WHEN [e].[NullableIntA] > 5 THEN CAST(1 AS bit) ELSE CAST(0 AS bit) END ELSE NULL END`. This exact nested shape is already pinned by `NullSemanticsQuerySqlServerTest.cs:3765-3771` (`Nullable_column_info_propagates_inside_conditional`), which confirms both the nesting and the ordering of the two visitors.
- Now produces: `SELECT CASE WHEN [e].[NullableIntA] > 5 THEN CAST(1 AS bit) ELSE CAST(0 AS bit) END`.
- Row with `NullableIntA IS NULL`: expected `null` (the ternary guard), actual `false`. Silent — no exception, since a `bit` reads fine into `bool?`.

Scope: SQL Server and any provider performing search-condition conversion. SQLite emits the condition directly (see the existing SQLite baseline `GearsOfWarQuerySqliteTest.cs:1559-1562`, `WHEN "g"."LeaderNickname" IS NOT NULL THEN "g"."LeaderNickname" LIKE '%us' ELSE NULL END`) and would return `null` correctly. That same SQLite baseline is also the reason the change did not break any existing test: a `LikeExpression` result is not walked by `NullPropagatedOperands`, so the optimization narrowly misses it. Extending the walker to `LikeExpression` later would break that test — which is the warning sign that the boolean case is unhandled rather than deliberately excluded.

**Fix:** Do not apply the optimization when `clause.Result` is a search condition. A type check is the cheapest gate at this layer (`clause.Result.Type != typeof(bool)`), though it also blocks the legitimate `bit`-column case; alternatively gate on the result not being a boolean `SqlBinaryExpression`/`SqlUnaryExpression{Not}`/`LikeExpression`/`InExpression`/`ExistsExpression`. Whichever gate is chosen, state the reason in a comment — the constraint comes from a different assembly and is invisible here.

### #3 🟡 Medium: the new tests exercise only the always-safe shapes; both defect classes above are uncovered

| | |
|---|---|
| **File** | `test/EFCore.Relational.Specification.Tests/Query/NullSemanticsQueryTestBase.cs:2250-2294` |
| **Category** | tests |
| **Confidence** | 100 |

**Issue:** All five added tests project a **scalar** result (`~int`, `int + int`, string concat) through operators that genuinely propagate NULL. Nothing projects a boolean result, and nothing routes the null-checked operand through `AndAlso`/`OrElse` — the two shapes where the optimization is unsound. The suite therefore passes with the defect present, which is why the baseline sweep came back clean.

**Evidence:** Concretely absent, in order of value:

1. A boolean-result case — `Select(x => x.NullableIntA != null ? (bool?)(x.NullableIntA > 5) : null)` — would fail on SQL Server today (`false` vs `null`) per #2.
2. A logical-connective case — `Select(x => x.NullableIntA != null ? (bool?)(x.NullableIntA > 5 || x.BoolA) : null)` — would fail on every provider (`true` vs `null`) per #1.
3. A null-semantics-generated connective — `Select(x => x.NullableStringA != null ? (bool?)(x.NullableStringA != x.NullableStringB) : null)` — covers the `_nonNullableColumns` interaction, which is the subtlest part of the design and currently has no test at all.
4. Negative assertions that the optimization stays off: a `COALESCE` result (`x.NullableIntA != null ? (x.NullableIntA ?? 0) : null`) and an `IsNullable: false` function result. Both are correctly handled by the current code, and nothing pins that.

Uncovered code branches: `ExpressionType.Negate` (line 622 — the `~` test hits `Not`, not `Negate`), the `right is null ? left` arm of line 607-609 (needs the null check on the *right* of the `&&`: `x.BoolA && x.NullableStringA != null ? ...`), the `binary.Update(left, right)` arm (needs three conjuncts where two survive), and `InstancePropagatesNullability` (line 633).

**Fix:** Add cases 1-3 as failing tests first — they are the specification for #1 and #2 — then 4 as regression pins for the parts that are right.
