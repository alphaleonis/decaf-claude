## Findings

### #1 🟠 High: Validation inside the shared deserializer makes the Go SDK reject the server's own successful responses

| | |
|---|---|
| **File** | `server/public/model/command_response.go:72` |
| **Category** | design / error-handling |
| **Confidence** | 100 |
| **Found by** | quick-reviewer (High), adversarial-reviewer (High) |
| **Screen** | 75 · **Validation** | confirmed |

**Issue:** The change puts validation *inside* `CommandResponseFromJSON`:

```go
if err := o.IsValid(); err != nil {
    return nil, err
}
```

That deserializer is not only the ingest path for untrusted third-party integration payloads. It is also how the Mattermost Go SDK parses **the server's own API response** — `server/public/model/client4.go:5961` (`Client4.ExecuteCommand`) and `:5982` (`ExecuteCommandWithTeam`).

There is no matching check on the write path. `server/channels/api4/command.go:428` does `json.NewEncoder(w).Encode(response)` on whatever `App.ExecuteCommand` returned, with no sanitization. Nothing upstream constrains the value either:

- A plugin's `ExecuteCommand` hook (`server/public/plugin/hooks.go:129`, dispatched at `server/channels/app/plugin_commands.go:165`) returns a raw `*model.CommandResponse` across a **gob/net-rpc** boundary (`server/public/plugin/client_rpc_generated.go:136-171`) — the new JSON-path validation never runs on it.
- `CreateCommandPost` (`server/channels/app/command.go:73-84`) silently falls through **both** branches for an unrecognized `ResponseType` and returns `post, nil` — success.

Concrete failure: a plugin returns `ResponseType: "comment"`. The command executes, the server returns HTTP 200 with `"response_type":"comment"` in the body, and `Client4.ExecuteCommand` returns `(nil, "failed to decode command response: ...")`. The type cannot round-trip its own serialized output. `Client4.ExecuteCommand`/`ExecuteCommandWithTeam` are exercised throughout the server's own integration tests (`server/channels/api4/commands_test.go`, `command_help_test.go`), so this is not a dead SDK path.

**Reachability**: no in-tree built-in command sets an out-of-allowlist `ResponseType` today, so nothing breaks immediately. It requires a plugin (first- or third-party) to set one — which the type system, the RPC boundary, and the app layer all permit.

**Fix:** Keep `IsValid()` exported but do not call it from the deserializer. Call it at the untrusted ingress points only:

```go
// server/channels/app/command.go:595 — outgoing integration response
response, err := model.CommandResponseFromHTTPBody(resp.Header.Get("Content-Type"), body)
if err == nil && response != nil {
    if appErr := response.IsValid(); appErr != nil { /* handle */ }
}
```

Alternatively enforce the same invariant on the producer side before `api4/command.go:428` encodes, so ingest and egress agree. A parse function that rejects output its own package produces is an asymmetry the type system cannot catch.

### #2 🟠 High: Hardcoded 65535-byte cap duplicates an exported constant, counts bytes not runes, and overrides a configurable limit

| | |
|---|---|
| **File** | `server/public/model/command_response.go:85` |
| **Category** | correctness / conformance |
| **Confidence** | 100 |
| **Found by** | broad-reviewer (High), adversarial-reviewer (High), go-reviewer (Low — dissent) |
| **Screen** | 65 · **Validation** | confirmed (validator argued for Medium — see below) |

**Issue:** Three defects in four lines:

```go
maxLength := 65535
if len(o.Text) > maxLength {
```

1. **Undeclared literal duplicating an exported constant in the same package.** `model.PostMessageMaxBytesV2 = 65535` already exists at `server/public/model/post.go:72`. It is also a local `var`, not a `const`.
2. **Bytes, not runes.** Every sibling validator in this package measures runes against an exported constant — `post.go:508` (`utf8.RuneCountInString(o.Message) > maxPostSize`), `terms_of_service.go:32`, `channel.go:324`. The constant that actually governs post text is `PostMessageMaxRunesV2 = PostMessageMaxBytesV2 / 4` = 16383 (`post.go:73`).
3. **A hardcoded ceiling placed upstream of a configurable one.** The real post-text limit is computed at runtime from the DB column size — `server/channels/store/sqlstore/post_store.go:2658`: `maxPostSize := max(int(maxPostSizeBytes)/4, model.PostMessageMaxRunesV2)`, with the comment at ~2640 stating the `Posts.Message` column "may be manually enlarged to support longer posts". On an install that enlarged that column past ~262 140 characters, an `in_channel` response that reaches `Post.IsValid` and posts successfully today is now hard-rejected at parse time, and there is **no admin override for the new cap**.

Additionally, ephemeral responses were never bounded at all: `SendEphemeralPost` (`server/channels/app/post.go:692-737`) performs no length check and never calls `Post.IsValid`, and `CreateCommandPost` (`server/channels/app/command.go:82-84`) routes ephemeral text straight there. Those responses are now capped at 65535 bytes.

**Severity dissent, recorded:** the validator argued for Medium rather than High — sub-claim 3 needs two conditions to co-occur (an enlarged column *and* a response long enough to matter), it never affects a default install, and sub-claim 2 in isolation is a net *loosening* for ASCII text (65535 chars allowed vs. 16383 under the rune convention), since `16383 × 4 = 65532 ≤ 65535`. Reported at High per the highest-finder-severity rule; the reader should weigh the validator's scoping.

**Fix:** Drop the literal. Either match the sibling convention:

```go
if utf8.RuneCountInString(o.Text) > PostMessageMaxRunesV2 {
```

or omit the `Text` check entirely and let `Post.IsValid(maxPostSize)` enforce the store's real, configurable limit — it is the only limit that knows the actual column size. If a strict byte cap is intentional, name it as an exported constant and document why this type deviates.

### #3 🟡 Medium: One invalid nested `extra_responses` entry discards the entire response, including the valid main message

| | |
|---|---|
| **File** | `server/public/model/command_response.go:95` |
| **Category** | error-handling |
| **Confidence** | 75 |
| **Found by** | adversarial-reviewer (Medium) |
| **Screen** | 78 · **Validation** | confirmed |

**Issue:** `IsValid()` recurses into `ExtraResponses` and propagates any nested failure, so `CommandResponseFromJSON` returns `nil` for the whole payload:

```go
for _, resp := range o.ExtraResponses {
    if resp == nil {
        continue
    }
    if err := resp.IsValid(); err != nil {
        return err
    }
}
```

Before this change, a bad nested `ResponseType` fell through both branches of `CreateCommandPost` (`server/channels/app/command.go:73-84`), returning `post, nil` — only the bad nested entry was dropped, while the main post was created and HTTP 200 returned. Now the parse fails first, so `HandleCommandResponse` never runs: `server/channels/app/command.go:597` maps it to a generic `api.command.execute_command.failed.app_error` HTTP **500** with no post at all, and `server/channels/web/webhook.go:113-116` maps it to HTTP **400**.

This all-or-nothing contract directly contradicts the deliberate design of `HandleCommandResponse` (`server/channels/app/command.go:605-637`), which processes the main response and each `ExtraResponses` entry independently and only accumulates `lastError`, so one failing entry does not sink the others. That tolerant contract is untouched by this diff — the new gate simply runs before it can apply.

Neither the `IsValid()` error nor the wrapping `AppError`s identify **which** nested entry failed, so neither the user nor the operator gets a usable diagnostic.

The new test at `server/public/model/command_response_test.go:171-182` encodes the behavior: a payload with a valid main message `"main ok"` / `response_type: "in_channel"` is expected to be rejected outright because a sibling entry has `response_type: "invalid_nested_type"`.

**Note on intent**: rejecting malformed data loudly is defensible and is plainly what the commit title intends. The defect is narrower — recursing into a *best-effort, per-entry-tolerant* collection turns an optional convenience feature into an all-or-nothing gate that destroys valid content.

**Fix:** Validate only the top-level response in the deserializer and skip invalid `ExtraResponses` entries, mirroring the existing per-entry `if resp == nil { continue }` tolerance at lines 65-70. Or keep the recursion but have `HandleCommandResponse` apply `IsValid()` per entry, so one bad nested response degrades to a skipped post rather than a lost command. Either way, include the failing entry's index in the error detail.
