## Findings

### #1 🟠 High: `SamplesRead` double-counts every subquery, so "samples read" exceeds "samples loaded" and contradicts its own documentation

| | |
|---|---|
| **File** | `promql/engine.go:1874` |
| **Category** | correctness |
| **Confidence** | 100 |
| **Verified** | executed |
| **Pre-existing** | no |
| **Found by** | solo-reviewer (High) |

**Issue:** `evalSubquery` now merges the subquery child's `SamplesRead` into the parent (`MergeSamplesReadFromSubquery`), but the outer `*parser.Call` range-vector loop *also* walks the materialized subquery output matrix and adds `samplesReadCount` at every step (`promql/engine.go:2184`). The same data is therefore counted twice — once as real storage reads, once again as synthesized points. The deleted comment on the old line (`// Avoid double counting samples when running a subquery, those samples will be counted in later stage.`) is describing precisely the guard that was removed.

The consequence is that for any query containing a subquery under a range-vector function — which is most recording rules and alerts that use `[5m:1m]` — `samplesRead` and `prometheus_engine_query_samples_read_total` over-report by 2× (and more when subqueries nest). It also produces `samplesRead > totalQueryableSamples`, i.e. the counter documented as "samples read (I/O)" is larger than the counter documented as "samples loaded (full window per step)", which is backwards.

This directly falsifies three statements shipped in this same diff:
- `docs/feature_flags.md:48` — "For other query types, this equals totalQueryableSamples."
- `docs/querying/api.md:247` — "for other queries this equals `totalQueryableSamples`."
- `util/stats/query_stats.go:281-283` — "elsewhere it equals TotalSamples."

**Evidence:** Executed against the checked-out head, per-step stats on, instant queries (so the "for other query types, this equals totalQueryableSamples" clause applies verbatim):

```
q=m3[60s:5s]                            Total=  36 Read=  36   <- bare subquery, correct
q=max_over_time(m3[60s:5s])             Total=  36 Read=  72   <- 2x
q=sum_over_time(m1[60s:10s])            Total=   6 Read=  12   <- 2x
q=sum(sum_over_time(m1[60s:10s]))       Total=   6 Read=  12   <- 2x
q=rate(sum_over_time(m1[30s])[1m:30s])  Total=   2 Read=   8   <- 4x, nesting multiplies
```

Causation confirmed by mutation probe in a throwaway worktree at the same SHA: commenting out the single line `parentSamplesStats.MergeSamplesReadFromSubquery(ev.samplesStats)` makes every one of those cases report `Read == Total` (36/36, 6/6, 6/6, 2/2), with no other change. The worktree was removed afterwards; the reviewed checkout was never modified (`git status --porcelain` empty at start and end).

The committed tests do not catch this — they *pin* the doubled values (`promql/engine_test.go:1184` expects `SamplesRead: 72` against `TotalSamples: 36`; `:1810`, `:1825`, `:1840`, `:1874` follow the same 2× pattern). So the ~1100 lines of new test cases lock in the defect rather than guarding against it.

**Fix:** Pick one accounting model and apply it consistently. Either (a) drop the `MergeSamplesReadFromSubquery` call in `evalSubquery` and let the outer step loop be the sole accountant for subquery output, matching the existing `TotalSamples` model and the documented invariant; or (b) keep the inner-read merge and suppress the outer loop's `IncrementSamplesReadAtStep` when the matrix arg came from `evalSubquery` (the call site at `promql/engine.go:2008` already knows). Whichever is chosen, the expectations at `promql/engine_test.go:1184` and the ~20 sibling subquery cases need to change, and the docs claim needs to be either made true or reworded.

### #2 🟠 High: `countSamplesAfter` adds an unconditional ~35% latency regression to long-window range-vector queries

| | |
|---|---|
| **File** | `promql/engine.go:2164` |
| **Category** | production |
| **Confidence** | 100 |
| **Verified** | executed |
| **Pre-existing** | no |
| **Found by** | solo-reviewer (High) |

**Issue:** `countSamplesAfter` (`promql/value.go:195`) does a full linear scan of the window slice at every step of every series, on the hottest path in the PromQL engine. It is not gated on the `promql-per-step-stats` feature flag or on `stats=` being requested — `SamplesRead` feeds the always-registered `prometheus_engine_query_samples_read_total` counter, so every user pays for it on every range-vector query. The cost is O(window points) per step, i.e. it re-scans the entire window to find the small tail of new points.

**Evidence:** `go test -bench 'BenchmarkRangeQuery/expr=rate(a_one[1d]),steps=1000' -benchtime=10x -count=6`, same machine, back to back:

| revision | ns/op (6 runs) |
|---|---|
| base `efbdc3f88` | 7.53 / 7.60 / 7.62 / 7.69 / 7.72 / 8.00 M |
| head `ec7157593` | 10.10 / 10.24 / 10.29 / 10.36 / 10.44 / 10.66 M |

≈ **+35%**. Attribution confirmed by mutation probe in a throwaway worktree at head: replacing the `countSamplesAfter(...)` call with a constant `0` returns the benchmark to 7.44–7.68 M ns/op — i.e. this one call accounts for the entire delta. (Worktree removed; reviewed checkout untouched.)

The regression scales with `window / step`: it is negligible for `rate(x[1m])` and severe for the long-window, many-step shape (`[1d]`, 1000 steps) that dashboards and `/api/v1/query_range` produce.

**Fix:** `floats` and `histograms` come out of `matrixIterSlice` sorted ascending by `T`, so the linear scan is unnecessary. Use `sort.Search` to locate the first index with `T > cutoff` and count from there — `len(floats)-idx` for floats, and sum `h.size()` over only the tail for histograms. That turns the per-step cost from O(window) into O(log window + new points), which is the size of the delta the function is trying to measure anyway.

### #3 🟠 High: `TotalSamples` / `prometheus_engine_query_samples_total` silently drops to a quarter of its previous value for `@`-modified range selectors under non-step-invariant calls

| | |
|---|---|
| **File** | `promql/engine.go:2145` |
| **Category** | correctness |
| **Confidence** | 100 |
| **Verified** | executed |
| **Pre-existing** | no |
| **Found by** | solo-reviewer (High) |

**Issue:** The refactor moved the sample count out of the `IncrementSamplesAtStep` call site and into `fullWindowCount`, which is assigned **inside** the `if ts == ev.startTimestamp || selVS.Timestamp == nil` block (`promql/engine.go:2149-2160`). When an `@` modifier causes the window to be reused across steps, that block is skipped for `step > 0`, so `fullWindowCount` stays `0` and `IncrementSamplesAtStep(step, 0)` is recorded. The old code passed `int64(len(floats)+totalHPointSize(histograms))` computed from the *retained* buffers, so it counted the full window at every step.

This is an undocumented, untested change to a long-stable user-visible statistic and to the `prometheus_engine_query_samples_total` counter. The in-diff comment at `promql/engine.go:2143` explicitly asserts the opposite: `// Full window count for TotalSamples (unchanged semantics)`. It also breaks the contract documented on `TotalSamplesPerStep` ("same as TotalSamples when a step is run as an instant query"), because running each step as an instant query does re-read the full `@`-pinned window.

Most `@` expressions are wrapped in `StepInvariantExpr` by the preprocessor and are unaffected, which is why the test suite stays green. But `predict_linear` is in `AtModifierUnsafeFunctions` (`promql/functions.go:2251`), so it is **never** step-invariant and always takes this path — a completely ordinary query is affected. Any range function with a step-varying scalar argument (`quantile_over_time(scalar(x), y[5m] @ t)`) hits it too.

**Evidence:** Executed on both revisions (base `efbdc3f88` in a temp worktree, head `ec7157593` in place), same storage, range query 201s→220s @ 5s step:

```
BASE  predict_linear(m3[60s] @ 30, 3600)   Total=48  perStep={201000:12 206000:12 211000:12 216000:12}
HEAD  predict_linear(m3[60s] @ 30, 3600)   Total=12  perStep={201000:12 206000:0  211000:0  216000:0}

BASE  quantile_over_time(scalar(m1), m3[60s] @ 30)  Total=52  perStep={201000:13 206000:13 211000:13 216000:13}
HEAD  quantile_over_time(scalar(m1), m3[60s] @ 30)  Total=16  perStep={201000:13 206000:1  211000:1  216000:1}
```

Control: `max_over_time(m3[60s] @ 30)` (step-invariant, wrapped) reports `Total=48` on both revisions, confirming the divergence is specific to the non-step-invariant `@` path.

No new or existing test case exercises this combination, which is why `go test ./promql/... ./util/stats/... ./web/api/v1/...` passes clean (it was run: all `ok`).

**Fix:** Compute the full-window count outside the reuse guard so it reflects the retained buffers, e.g. move `fullWindowCount = int64(len(floats) + totalHPointSize(histograms))` to just before `ev.samplesStats.IncrementSamplesAtStep(step, fullWindowCount)` at line 2183, keeping only `samplesReadCount` inside the guard. If the drop is actually intended, it needs a test, a changelog entry, and removal of the "unchanged semantics" comment — and the `prometheus_engine_query_samples_total` HELP text change at `promql/engine.go:422` ("full window per step for range-vector") is then also wrong, since it is no longer full-window-per-step for `@`.

### #4 🟢 Low: New assertions in `TestStats` are tautological and cannot fail

| | |
|---|---|
| **File** | `web/api/v1/api_test.go:983` |
| **Category** | tests |
| **Confidence** | 100 |
| **Verified** | traced |
| **Pre-existing** | no |
| **Found by** | solo-reviewer (Low) |

**Issue:** `require.GreaterOrEqual(t, qs.Samples.SamplesRead, int64(0))` at lines 983 and 999 asserts that a monotonically-accumulated `int64` sample count is non-negative. There is no code path that can make it negative — every writer (`IncrementSamplesReadAtStep`, `IncrementSamplesReadAtTimestamp`, `MergeSamplesReadFromSubquery`) only adds non-negative counts. The assertion passes identically whether `SamplesRead` is correctly populated, always zero, or never touched by the engine at all, so it guards nothing about the feature it was added for.

**Failure scenario:** Delete every `IncrementSamplesReadAtStep`/`IncrementSamplesReadAtTimestamp` call from `promql/engine.go`; `SamplesRead` becomes 0 for all queries; both assertions still pass and `TestStats` stays green. The neighboring `require.NotNil(t, qs.Samples.SamplesReadPerStep)` at line 1000 is the only one of the three that actually pins anything.

**Fix:** Assert the value against the query the test issues — `require.Positive(t, qs.Samples.SamplesRead)` for a query known to read samples, or better `require.Equal(t, qs.Samples.TotalQueryableSamples, qs.Samples.SamplesRead)` for the simple instant query this test runs, which would additionally pin the documented equality invariant that finding #1 breaks.

## Specialist Notes

### Considered But Not Flagged (solo-reviewer)

- **Division by zero / negative `numSteps` in `NewChildWithStepTracking` → `InitStepTracking`** (`util/stats/query_stats.go:298`). Traced all callers: `evalSubquery` passes `ev.interval`, which is `1` for instant queries (`promql/engine.go:805`) and `durationMilliseconds(s.Interval)` for range queries, never 0; the `SubqueryExpr` branch passes `subqInterval`, which is `> 0` by construction. For the negative case, `subqEnd - subqStart ≥ (ev.end-ev.start) + range - interval > -interval`, so Go's truncating division yields `int(x/interval) ≥ 0` and `numSteps ≥ 1`. Not a real defect — anchor 0.
- **`nil`-vs-non-nil asymmetry between the two arms of the `SubqueryExpr` merge** (`promql/engine.go:2426-2446`). Traced: `newEv.samplesStats` is built from `ev.samplesStats.StepTrackingEnabled()`, and `EnablePerStepStats == true` always implies `InitStepTracking` allocated a non-nil `SamplesReadPerStep`, so "parent non-nil, child nil" is unreachable and the reverse falls into the `else` arm which handles it correctly. Not a real defect — anchor 0.
- **Extra allocation in `NewChildWithStepTracking`** — two `[]int64` of `numSteps` per subquery node, where previously `NewChild()` allocated none. Bounded by the outer/subquery step count, one per `Call` node (not per series or per step), and only when the experimental `promql-per-step-stats` flag is on. Minor, out of reach under `narrow`.
- **`IncrementSamplesReadAtTimestamp` truncates a `t < StartTimestamp` index to 0** rather than rejecting it (`util/stats/query_stats.go:359`) — an exact copy of the pre-existing behavior of `IncrementSamplesAtTimestamp` directly above it. Pre-existing pattern, out of reach.
- **`smoothSeries` performs no sample-stats accounting at all** (`promql/engine.go:1718`), so `Smoothed` vector selectors are invisible to both `TotalSamples` and the new `SamplesRead`. Pre-existing, out of reach.
- **Plain vector selectors in range queries count the same physical sample once per step** when lookback re-serves it, so `SamplesRead` is not literal I/O there either. This one matches what the docs say ("for other query types, this equals totalQueryableSamples"), so it is a naming/framing question, not a defect against the stated contract. Minor, out of reach.
- **`docs/feature_flags.md:50-52` documents `peakSamples` and both engine counters inside the `promql-per-step-stats` flag section**, though all three exist regardless of the flag. Minor, out of reach.
- **Probe decided against:** a repro for `numOuterSteps == 0` in the subquery→outer-step mapping. `InitStepTracking` cannot produce a zero-length slice on any reachable path (see above), so the `outerStep = numOuterSteps - 1` clamp cannot yield `-1`.
