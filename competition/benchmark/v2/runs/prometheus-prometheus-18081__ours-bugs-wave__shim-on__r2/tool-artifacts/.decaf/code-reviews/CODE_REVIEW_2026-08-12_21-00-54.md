## Findings

### #1 🔴 Critical: Subquery per-step arrays are sized from the user-controlled subquery grid — unbounded allocation

| | |
|---|---|
| **File** | `promql/engine.go:2397` (with `util/stats/query_stats.go:306-308`) |
| **Category** | resource-management |
| **Confidence** | 100 |
| **Found by** | adversarial-reviewer (Critical) |
| **Validation** | confirmed |

**Issue:** In the `*parser.SubqueryExpr` case of `evaluator.eval`, the child stats object is now built on
the **subquery's own step grid**:

```go
subqSamplesStats := stats.NewChildWithStepTracking(ev.samplesStats.StepTrackingEnabled(), subqStart, subqEnd, subqInterval)
```

`InitStepTracking` (`util/stats/query_stats.go:306-308`) then allocates **two** `[]int64` of
`numSteps = (subqEnd-subqStart)/subqInterval + 1`:

```go
numSteps := int((end-start)/interval) + 1
qs.TotalSamplesPerStep = make([]int64, numSteps)
qs.SamplesReadPerStep = make([]int64, numSteps)
```

The outer query's step count is capped by the API at 11 000 points, but **the subquery's resolution is
not capped anywhere** — `[30d:1ms]` is accepted by the parser. Before this change the subquery child came
from `ev.samplesStats.NewChild()`, which returns `NewQuerySamples(false)` — per-step tracking disabled, so
nothing was allocated on the subquery grid at all.

The allocation happens **before any series is read**, so it precedes the `query.max-samples` limit, and it
completes fast enough that the query timeout does not intervene.

**Measured** (`runtime.MemStats` around `qry.Exec`, per-step stats enabled, metric matching **zero**
series, `max-samples` = 5×10⁷; scratch test since removed):

| Query | base `efbdc3f88` | HEAD `ec7157593` | result |
|---|---|---|---|
| `max_over_time(nonexistent_metric[10m:1ms])` | 13,068,304 B | 22,640,464 B | `err=<nil>` |
| `max_over_time(nonexistent_metric[1h:1ms])` | 13,056,984 B (flat) | 57,626,680 B | `err=<nil>` |
| `max_over_time(nonexistent_metric[3h:1ms])` | — | 172,821,736 B | `err=<nil>` |
| `max_over_time(nonexistent_metric[6h:1ms])` | — | 345,618,640 B | `err=<nil>` |

Growth is exactly linear at 16 bytes per subquery step (2 arrays × 8 bytes). Extrapolating the same
`make` calls, `[30d:1ms]` ≈ 2.6×10⁹ steps ≈ **41 GB allocated up front** — an OOM-kill of the Prometheus
process from a single request. Base is flat, so this is introduced by the change.

**Precondition:** the server must run `--enable-feature=promql-per-step-stats` and the request must pass
`stats=all`. That is a non-default experimental flag — but it is the very flag this change extends and
documents, so any deployment adopting the feature is exposed.

**Fix:** Do not materialize an array on the subquery resolution. Either cap the child's step count and
fall back to the whole-query `IncrementSamplesReadAtTimestamp` path above the cap, or attribute subquery
reads onto outer steps incrementally without a subquery-grid array at all. Note the sibling call at
`promql/engine.go:1869` is *not* affected — it passes the outer layout, which the API bounds.

### #2 🟠 High: `@` modifier data-reuse path now reports zero `totalQueryableSamples` for every step after the first

| | |
|---|---|
| **File** | `promql/engine.go:2145` (declaration) and `:2183` (use) |
| **Category** | correctness — regression in existing behavior |
| **Confidence** | 100 |
| **Found by** | adversarial-reviewer (High) |
| **Validation** | waived — screened 100; independently re-measured by the orchestrator against the base commit |

**Issue:** `fullWindowCount` is declared **inside** the per-step loop and assigned **only** inside the
`if ts == ev.startTimestamp || selVS.Timestamp == nil` branch:

```go
// promql/engine.go:2143-2145
// Full window count for TotalSamples (unchanged semantics); delta for SamplesRead.
// When we reuse data (@ modifier), we don't increment either.
var fullWindowCount, samplesReadCount int64
...
// promql/engine.go:2183
ev.samplesStats.IncrementSamplesAtStep(step, fullWindowCount)
```

When a matrix selector carries an `@` modifier, `selVS.Timestamp != nil`, so for every step after the
first the branch is skipped, `floats`/`histograms` are **reused** from the previous step, and
`fullWindowCount` stays at its zero value. The previous code computed the count at the increment site
from the retained slices:

```go
ev.samplesStats.IncrementSamplesAtStep(step, int64(len(floats)+totalHPointSize(histograms)))
```

so it counted the reused window at every step. `totalQueryableSamples` therefore drops by a factor of
`numSteps`, and so does the `prometheus_engine_query_samples_total` counter fed from it
(`promql/engine.go:685`).

The in-line comment at `:2143` says *"Full window count for TotalSamples (unchanged semantics)"* and
`docs/feature_flags.md` in this same change says *"each step counts the full window (the same point may
be counted in multiple steps)"* — both are false on this path.

**Measured**, range query `Start=201s End=220s Interval=5s` over three series at 1 sample/10s:

| Query | base `efbdc3f88` | HEAD `ec7157593` |
|---|---|---|
| `predict_linear(metricWith3SampleEvery10Seconds[60s] @ end(), 3600)` | `TotalSamples=72`, perStep `{201000:18, 206000:18, 211000:18, 216000:18}` | `TotalSamples=18`, perStep `{201000:18, 206000:0, 211000:0, 216000:0}` |
| `predict_linear(metricWith3SampleEvery10Seconds[60s] @ 30, 3600)` | `TotalSamples=48`, perStep `{…:12, 12, 12, 12}` | `TotalSamples=12`, perStep `{201000:12, 206000:0, 211000:0, 216000:0}` |
| `max_over_time(metricWith3SampleEvery10Seconds[60s] @ 30)` *(control)* | `TotalSamples=48` | `TotalSamples=48` — unchanged |

The control case is why CI does not catch this: `max_over_time(x[60s] @ 30)` **is** step-invariant, so it
is wrapped in a `StepInvariantExpr` and never reaches this loop — which is exactly what the existing test
at `promql/engine_test.go:1345` exercises. `predict_linear` is in `AtModifierUnsafeFunctions`
(`promql/functions.go:2247`), so it is never wrapped and the reuse branch runs for real. No test in the
changeset covers a non-step-invariant function over an `@`-modified matrix selector.

**Fix:** Keep the full-window count across reused steps — hoist it out of the per-step loop (compute once
when `matrixIterSlice` runs, retain across reuse), or restore the original inline
`int64(len(floats)+totalHPointSize(histograms))` at the increment site and gate **only**
`samplesReadCount` on the reuse branch.

### #3 🟠 High: `samplesRead` is counted twice when a subquery is a range-vector function argument

| | |
|---|---|
| **File** | `promql/engine.go:1874` |
| **Category** | correctness — API contract |
| **Confidence** | 100 |
| **Found by** | adversarial-reviewer (High) |
| **Validation** | confirmed |

**Issue:** `evalSubquery` evaluates a subquery into a materialized `Matrix`, merges the subquery's
`SamplesRead` into the parent, and returns a synthetic `*parser.MatrixSelector` whose
`VectorSelector.Series` are already in memory:

```go
// promql/engine.go:1874
parentSamplesStats.MergeSamplesReadFromSubquery(ev.samplesStats)
```

The caller then walks that synthetic selector through the range-vector branch, which increments
`SamplesRead` again over the same points (`promql/engine.go:2184`). The comment deleted by this change —
*"Avoid double counting samples when running a subquery, those samples will be counted in later stage."* —
was guarding precisely this.

Two statements introduced by this same change are therefore false:

- `docs/querying/api.md`: *"**samplesRead**: … for other queries this equals `totalQueryableSamples`."*
- `util/stats/query_stats.go:279-281`: *"SamplesRead … elsewhere it equals TotalSamples."*

It also inflates `prometheus_engine_query_samples_read_total`, whose stated purpose is to approximate
actual I/O — subquery output points are computed in memory, never read from storage.

**Measured**, instant queries at `t=201s` over `load 10s / m1 1+1x100`:

| Query | `TotalSamples` | `SamplesRead` | |
|---|---|---|---|
| `max_over_time(m1[60s:5s])` | 12 | 24 | ← exceeds |
| `max_over_time(max_over_time(m1[30s:10s])[60s:5s])` | 12 | 30 | ← exceeds (nesting compounds) |
| `m1[60s:5s]` (bare subquery, no later stage) | 12 | 12 | correct |
| `max_over_time(m1[60s])` (no subquery) | 6 | 6 | correct |

Identical with per-step stats on and off, so both the API field and the counter are affected.

**The new tests pin the doubled value rather than catch it** — `promql/engine_test.go:1175-1200`:

```go
Query:        "max_over_time(metricWith3SampleEvery10Seconds[60s:5s])",
TotalSamples: 36,
SamplesRead:  72,
...
Query:        "sum(max_over_time(...[60s:5s])) + sum(max_over_time(...[60s:5s]))",
TotalSamples: 72,
SamplesRead:  144,
```

So code, tests, and documentation disagree with each other inside a single change. Whichever semantics is
intended, two of the three must be corrected.

**Fix:** Drop the `MergeSamplesReadFromSubquery` call in `evalSubquery` (the caller's later-stage walk
already counts these points), or suppress the later-stage `IncrementSamplesReadAtStep` for selectors
produced by `evalSubquery` — they carry pre-populated `Series` and perform no I/O. Then update the pinned
test expectations and add an invariant assertion that `SamplesRead <= TotalSamples` for instant queries.

### Considered But Not Flagged

**adversarial-reviewer** (each attacked and abandoned with a stated reason):
- `ev.interval == 0` in the matrix-selector delta (`maxt - ev.interval`) — instant queries are constructed
  with `interval: 1` and `start == end`, so the loop only reaches `step == 0` and the subtraction is never
  used.
- Range `<` step (disjoint windows), e.g. `max_over_time(x[10s])` at `step=60s` — verified correct: every
  point satisfies `T > maxt - interval`, so `countSamplesAfter` returns the full window.
- Empty-window `continue` losing counts — step 1's slice is a subset of step 0's empty window, so the
  skipped increments are both zero.
- `numOuterSteps == 0` → `SamplesReadPerStep[-1]` panic at `promql/engine.go:2441` — reaching
  `numSteps == 0` requires `range <= 0`. Unreachable.
- Division by zero for a sub-millisecond subquery step (`subqInterval == 0`) — the identical division
  exists at the base commit and executes before the new call. **Pre-existing, out of reach** under
  `reach=narrow`.
- Subquery steps past the outer window folded onto the last outer step
  (`outerStep = numOuterSteps - 1`) — deliberate and commented; skews the final step's
  `samplesReadPerStep` but leaves the total correct. Attribution-quality question, not a defect.
- Double registration of `prometheus_engine_query_samples_read_total` / nil `q.sampleStats` — new unique
  metric name in the same `MustRegister` block; the preceding line already dereferences `q.sampleStats` at
  the base commit.

**quick-reviewer**:
- Division-by-zero in the subquery re-attribution formula — instant queries use `interval = 1`

- `IncrementSamplesReadAtTimestamp` silently skipping out-of-range timestamps while still adding to the
  total — appears intentional; total stays correct.
- `MergeSamplesReadFromSubquery` merging only the common prefix when slice lengths differ — safe at the
  single call site, where parent and child share a layout.

**broad-reviewer**:
