### #1 🔴 Critical: `override_flags_definitions` lets any public-token holder substitute a flag definition

| | |
|---|---|
| **File** | `rust/feature-flags/src/handler/flags.rs:152` (forwarded at `rust/feature-flags/src/handler/mod.rs:196`) |
| **Category** | security / missing authorization |
| **Confidence** | 100 |
| **Validation** | confirmed |
| **Found by** | broad (Critical), security (Critical), rust (Critical), knowledge (Critical), quick (High), design (High) |

**Issue:** This change adds `override_flags_definitions` to the **public** `/flags` request body
(`rust/feature-flags/src/flags/flag_request.rs`). `process_request_inner` forwards it to
`fetch_and_filter` **unconditionally**, which applies it by wholesale-replacing the DB-loaded flag:

```rust
match serde_json::from_value::<FeatureFlag>(override_def.clone()) {
    Ok(override_flag) => { *flag = override_flag; ... }
```

The sibling capability added by the *same* change is gated — `if context.meta.detailed_analysis
.unwrap_or(false) && authentication::is_internal_request(&context)` — so the author plainly modeled
these as internal-only, but the gate landed on only one of the three new knobs.

`/flags` is registered publicly under `ServiceMode::All | ServiceMode::Flags` and authenticates
solely via `request.extract_token()` → the **public project API token**, which ships in client-side
SDK code and is not a secret. So any holder of that token can submit an arbitrary definition for any
of that team's flag keys and receive an evaluation computed from it, presented as the authoritative
server-side result.

**Fix:** Gate `override_flags_definitions` on `authentication::is_internal_request(&context)` exactly
as `detailed_analysis` is, and reject (4xx) rather than silently ignore an override on a non-internal
request. Better: move the capability onto a separate internal-only route so a public caller cannot
reach the code path at all.

### #2 🟠 High: `only_use_override_person_properties` is also ungated on the public endpoint

| | |
|---|---|
| **File** | `rust/feature-flags/src/handler/mod.rs:223` |
| **Category** | security / missing authorization |
| **Confidence** | 100 |
| **Found by** | broad (Critical), security (High), rust (High), adversarial (High), knowledge (Critical) |

**Issue:** `context.meta.only_use_override_person_properties` is passed straight through, on the line
immediately after the one that *does* gate `detailed_analysis`. It makes the matcher discard database
person properties entirely (`rust/feature-flags/src/flags/flag_matching.rs:1696`). This is strictly
more powerful than the pre-existing merge semantics: previously overrides could only *add* or replace
supplied keys, so absence-based conditions (`is_not_set`) still consulted the database. A public
caller can now satisfy conditions that were previously unreachable via overrides, and force
`skip_writes = true` for the whole request.

**Fix:** Gate it behind `is_internal_request` together with `detailed_analysis`.

### #3 🟠 High: Overrides replace the whole struct, including `id`, and can reach the write path

| | |
|---|---|
| **File** | `rust/feature-flags/src/handler/flags.rs:166` and `:336` |
| **Category** | security / input validation |
| **Confidence** | 100 (screen 90) |
| **Found by** | security (High), design (High), adversarial (Medium) |

**Issue:** `*flag = override_flag` accepts every field from client JSON with no allowlist and no
reconciliation against the flag being replaced. Two consequences were confirmed in code:

- **`id` is client-controlled.** Results are recorded as `add_flag_evaluation_result(flag.id, ...)`
  and flag-dependency filters resolve by that same `i32` key
  (`rust/feature-flags/src/flags/flag_matching_utils.rs:671-675`), so a forged `id` writes into
  another flag's dependency-result slot — forging the value that gates a dependent flag.
- **An override with `ensure_experience_continuity: true` can reach a real Postgres write.**
  `skip_writes` (`flags.rs:336`) is set only from `detailed_analysis`, `only_use_override_person_properties`,
  and the global config — **not** from the presence of `override_flags_definitions`. So an
  override-only request reaches `set_feature_flag_hash_key_overrides` when a hash-key override param
  is also supplied, persisting a variant pin for a flag that has no continuity in the database.

**Refuted sub-claim:** the reviewers also claimed `team_id` is attacker-controlled in a
security-relevant way. It is accepted from the payload, but downstream it is only ever read in
`tracing` log fields — every DB access uses the authenticated `self.team_id`. That is log pollution,
not a bypass.

**Fix:** Apply overrides field-by-field onto the DB-loaded flag (e.g. only `filters` and `active`),
keeping `id`, `team_id`, `key`, and `ensure_experience_continuity` from the database; and force
`skip_writes = true` for any request carrying overrides.

### #4 🟠 High: `only_use_override_person_properties` skips cohort and group loading, not just person properties

| | |
|---|---|
| **File** | `rust/feature-flags/src/flags/flag_matching.rs:827` |
| **Category** | correctness / composition |
| **Confidence** | 100 |
| **Found by** | design (High), adversarial (High) |

**Issue:** The new `||` clause short-circuits `prepare_evaluation_state_if_needed` entirely:

```rust
if flags_requiring_db_preparation.is_empty() || self.only_use_override_person_properties {
    self.flag_evaluation_state.skip_person_properties();
    return false;
}
```

But `prepare_flag_evaluation_state` does far more than fetch person properties — it also calls
`set_cohorts(...)`, collects static cohort IDs, initializes group type mappings, and prepares group
data. `requires_db_preparation` is `requires_db_properties(...) || requires_cohort_filters()`
precisely so cohort flags trigger it; the new clause discards that signal. With
`flag_evaluation_state.cohorts == None`, condition matching returns `(false, NoConditionMatch)`.

Because the new endpoint sets this flag on **every** timestamped call, any flag with a cohort or
group condition is reported as not matching regardless of real membership — and the accompanying
`conditions[].explanation` says "did not match properties", with no hint that cohort data was never
loaded.

**Fix:** Keep calling `prepare_flag_evaluation_state` and suppress only the person-properties
assignment (the existing skip mechanism), so cohorts, static membership, and group mappings still
load. Alternatively reject the parameter for flags whose conditions reference cohorts or groups
rather than silently returning a wrong answer.

### #5 🟠 High: `rollout_excluded` is only ever true for a 0% rollout, so ordinary partial rollouts are misexplained

| | |
|---|---|
| **File** | `rust/feature-flags/src/api/types.rs:652-687` |
| **Category** | correctness |
| **Confidence** | 100 |
| **Found by** | broad (High), design (High), adversarial (High), knowledge (SHOULD) |

**Issue:** `is_zero_rollout = rollout_percentage == 0.0` gates both arms of the
`this_condition_rollout_excluded` decision — including the arm that has *already* positively
identified the excluded condition via `flag_match.condition_index`. But `check_rollout`
(`flag_matching.rs:1931-1945`) returns `OutOfRolloutBound` for **any** `rollout_percentage < 100.0`
whose hash falls outside the bucket, not only for 0%.

Trace the most common real configuration — one condition at 50%, properties match, the user's hash
misses: `matches == false`, `reason == OutOfRolloutBound`, `condition_index == Some(0)`. Then
`this_condition_rollout_excluded = (0 == 0) && false = false`, and since `condition_matched` is false
for every condition, the explanation falls through to:

> "Condition 0 matched properties but was not evaluated due to an earlier condition matching"

which names a nonexistent earlier condition, while `rollout_excluded: false` directly contradicts the
flag-level `reason.code == "out_of_rollout_bound"` in the same response. This is the flagship feature
of the change producing a plausible-looking wrong answer with no error signal.

**Fix:**
```rust
let this_condition_rollout_excluded = if properties_matched_but_rollout_failed {
    if let Some(match_condition_index) = flag_match.condition_index {
        index == match_condition_index          // drop the && is_zero_rollout
    } else {
        is_zero_rollout && all_properties_matched
    }
} else {
    is_zero_rollout && all_properties_matched
};
```
Better still: have the matcher record the per-condition outcome during evaluation and hand it to the
analysis builder, instead of reconstructing it post hoc from the aggregate reason.

### #6 🟠 High: The analysis runs `match_property` on cohort and flag-dependency filters, which it is documented not to support

| | |
|---|---|
| **File** | `rust/feature-flags/src/api/types.rs:605` |
| **Category** | error-handling / correctness |
| **Confidence** | 100 |
| **Found by** | rust (High), knowledge (SHOULD), design (Medium), adversarial (Medium) |

**Issue:** `build_condition_analysis` calls `match_property(property, props, false).unwrap_or(false)`
for **every** property in the group, against the merged **person** property map. But `match_property`
deliberately returns `Err(ValidationError)` for exactly the operators used by cohort and
flag-dependency filters:

```rust
OperatorType::In | OperatorType::NotIn => Err(FlagMatchingError::ValidationError(
    "In/NotIn operators should be handled by cohort matching".to_string())),
OperatorType::FlagEvaluatesTo => Err(FlagMatchingError::ValidationError(
    "FlagEvaluatesTo operator should be handled by flag dependency matching".to_string())),
```

The same loop enumerates `PropertyType::{Person, Group, Cohort, Flag}` twenty lines above, so all
four variants are known to reach this code. `unwrap_or(false)` converts the "you called the wrong
function" error into a **definitive** `matched: false`, which is then rendered as confident prose
("Property 'id' does not equal 42"). `all_properties_matched` is computed from those wrong verdicts,
so a flag that genuinely matched via a cohort condition returns `enabled: true` alongside
`conditions[i].matched: false` — the tool built to explain the verdict contradicts it.

**Fix:** Branch on `prop_type` and operator: evaluate person filters against person properties;
resolve group filters against the group property bag for the condition's
`aggregation_group_type_index`; for cohort/flag filters emit an explicit "not analyzed at property
level" marker. Replace `unwrap_or(false)` with an explicit `Err` arm carrying the error text, so
"could not evaluate" is never rendered as "did not match".

### #7 🟠 High: `ConditionAnalysis.matched` does not mean what the published schema says it means

| | |
|---|---|

| **Found by** | quick (High), design (High), knowledge (SHOULD), adversarial (Medium) |

**Issue:** Rust sets `matched: all_properties_matched` — rollout ignored, winning-condition status

same way — see #5.

**Fix:** Emit both facts as separate fields (`properties_matched` and `is_matching_condition`,

### #8 🟠 High: The override payload is not JSON-serializable for any flag with an analytics dashboard

| | |
|---|---|
| **File** | `posthog/api/feature_flag.py:3521` |
| **Category** | correctness / crash |
| **Confidence** | 100 |
| **Found by** | broad-reviewer (promoted from its Considered-But-Not-Flagged section — dismissed there with incorrect reasoning) |

**Issue:** The override payload is built as

```python
flag_dict = model_to_dict(evaluation_flag, exclude=["created_by", "last_modified_by", "team", "usage_dashboard"])
```

`model_to_dict` iterates `chain(opts.concrete_fields, opts.private_fields, opts.many_to_many)`, and
`FeatureFlag.analytics_dashboards` is a `ManyToManyField` that is **not** in the exclude list. Django's
`ManyToManyField.value_from_object` is:

```python
return [] if obj.pk is None else list(getattr(obj, self.attname).all())
```

`evaluation_flag` is constructed with `id=feature_flag.id`, so `pk` is set. The call therefore (a)
issues an extra DB query through `FeatureFlagDashboards`, and (b) puts a **list of `Dashboard` model
instances** into `flag_dict`. That dict is handed to `get_flags_from_service`, which passes it to
`requests` as `json=payload` — and `json.dumps` raises `TypeError: Object of type Dashboard is not
JSON serializable`.

Crucially, that raise happens at the `post()` call, **outside** the inner `try` that would have set
`override_definitions = None`, so it is caught by the method's blanket `except Exception` and returned
as `HTTP 500 {"error": "Failed to evaluate flag"}`. Net effect: for any flag that has at least one
analytics dashboard attached, every timestamped call to this endpoint returns 500.

`broad-reviewer` did notice `analytics_dashboards` but dismissed it as "silently dropped by serde on
the Rust side (no `deny_unknown_fields`), so it's wasteful but not incorrect" — the payload never
reaches serde.

**Fix:** Stop deriving the cross-service payload from `model_to_dict`. Build an explicit dict keyed to
the Rust struct's fields (`id`, `team_id`, `key`, `name`, `filters`, `active`, `deleted`, `version`,
`ensure_experience_continuity`, `bucketing_identifier`, `evaluation_runtime`), which also fixes #9 and
removes the dead `updated_at` branch (#36).

### #10 🟠 High: `value` rejects the `null` the Rust service emits for `is_set` filters, yielding HTTP 500

| | |
|---|---|
| **File** | `posthog/api/feature_flag.py:1961` |
| **Category** | api-contract |
| **Confidence** | 100 |
| **Found by** | design (Medium), adversarial (High) |

**Issue:** `FeatureFlagConditionPropertyAnalysisSerializer.value` is declared
`serializers.JSONField(help_text="Expected property value")` with no `allow_null=True`. But Rust emits
JSON `null` for value-less filters: `value: property.value.clone().unwrap_or(serde_json::Value::Null)`,
and `PropertyFilter.value` is `Option<serde_json::Value>` with the explicit comment:

> `// NB: if a property filter is of type is_set or is_not_set, the value isn't used, and if it's a filter made by the API, the value is None.`

DRF's `Field.validate_empty_values` fails a `None` input when `allow_null` is false. So
`response_serializer.is_valid(raise_exception=True)` raises, that `ValidationError` is swallowed by
the method's blanket `except Exception`, and the caller gets `HTTP 500 {"error": "Failed to evaluate
flag"}` for **any** flag whose condition uses `is_set` / `is_not_set`, or any filter stored without a
value. The sibling `actual_value` field on the same serializer correctly declares `allow_null=True`,
which shows the omission is unintentional.

**Fix:** Add `allow_null=True` to `value`. Separately, stop swallowing `serializers.ValidationError`
in the broad `except Exception` — a response-contract violation should not surface as an opaque 500.

## Specialist Notes

### Threat Model Notes (security-reviewer)

- **Trust boundaries crossed.** (1) Browser/SDK → Rust `/flags`, authenticated only by the **public**
  project API token — the weakest boundary in the system, and the one that gained two new privileged
  parameters plus an unbounded body map. (2) Django → Rust, authenticated by a static shared secret in
  `Authorization`. (3) Authenticated PostHog user/API key → Django REST, gated by DRF scopes. The
  change's gating logic protects boundary (2)'s marker on only one of the three new capabilities.
- **`is_internal_request` is authorization, not authentication.** `/flags` resolves the team from the
  body token; the `Authorization` header is unused for team resolution on this route. The internal
  token therefore adds a privilege bit on top of an otherwise public request — which is exactly why
  every capability it is meant to unlock must consult it.
- **Data sensitivity.** The Django endpoint returns person property dictionaries (arbitrary
  customer-defined PII). Historical mode reconstructs those from the raw `events` stream, which can
  resurface property values later overwritten or removed on the person record — worth a deliberate
  decision against the product's data-deletion commitments. (Note: this reconstruction behavior is
  inherited unchanged from the shared helper already used by `properties_at_time`, so it is not new
  here.)
- **Attack-surface delta.** Public `/flags` gained one unbounded body map that rewrites server-side
  flag definitions and two query parameters. Authenticated REST gained one unthrottled POST action
  that fans out to two unbounded ClickHouse queries and a 10k-row Postgres materialization.

### Considered But Not Flagged

**Refuted during validation (2 clusters removed from findings):**

- **`model_to_dict` omits the `id` AutoField, so the override always fails to parse** — *refuted*, and
  this was a three-reviewer consensus (`knowledge-reviewer` Critical, `design-reviewer` Critical,
  `adversarial-reviewer` High). Django's `Field.__init__` defaults `editable=True`, and `AutoFieldMixin`
  never overrides it — only `BinaryField` and `DateField`/`DateTimeField` with `auto_now`/`auto_now_add`
  force `editable=False`. `FeatureFlag` declares no explicit pk and `id` is not in the `exclude` list,
  so `id` **is** in the payload with the correct value. `FlagFilters` additionally has
  `#[serde(default)]` on every field, so the override parses. The validator confirmed this both from
  source and by building a minimal Django 4.2 app. Two things survived from this cluster: the dead
  `updated_at` branch (now finding #36) and the M2M serialization crash (now finding #8, a different
  and real defect in the same lines).
- **`reconstruct_flag_at_timestamp` issues two overlapping activity-log queries** (`performance-reviewer`)
  — *refuted*. The two windows are complementary, not overlapping: the first is bounded by
  `created_at__lte=timestamp`, and the second walks backward from *now* and `break`s at exactly the
  newest entry with `created_at <= timestamp` — the same boundary row the first query used to derive
  `target_version`. Intersection is at most one row. The second query also genuinely streams and
  early-exits (so it is not a 10,000-row scan), and `reconstruct_flag_at_version` short-circuits
  entirely when `target_version == current_version`, the common case for recent timestamps. A smaller
  observation (two round trips instead of one, when the target really is historical) is available but
  is not what was reported.
