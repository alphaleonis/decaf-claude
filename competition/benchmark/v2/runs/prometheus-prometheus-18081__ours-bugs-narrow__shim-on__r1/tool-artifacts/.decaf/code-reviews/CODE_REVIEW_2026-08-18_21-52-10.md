### #1 🟠 High: `SamplesRead` double-counts every subquery used as a range-vector function argument

| | |
|---|---|
| **File** | `promql/engine.go:1874` |
| **Category** | correctness |
| **Confidence** | 100 |
| **Verified** | executed |
| **Found by** | solo-reviewer (High) |
| **Pre-existing** | no |

**Issue:** `evalSubquery` now merges the subquery's `SamplesRead` into the parent (`MergeSamplesReadFromSubquery`), but the enclosing `*parser.Call` loop *then also* counts the materialized subquery matrix into `SamplesRead` at `promql/engine.go:2184`. For `TotalSamples` only the second contribution happens — the child's `TotalSamples` is deliberately discarded ("those samples will be counted in later stage") — which is precisely why the two axes now disagree. Result: `samplesRead` / `samplesReadPerStep` / `prometheus_engine_query_samples_read_total` over-report by the size of the materialized subquery output, and `samplesRead` can exceed `totalQueryableSamples`, contradicting the change's entire framing (loaded ≥ read).

This hits an extremely common shape: `max_over_time(x[1h:1m])`, `rate(sum(x)[5m:1m])`, `histogram_quantile(0.9, avg_over_time(h[2m:30s]))`.

**Evidence:** Executed against the `TestQueryStatistics` fixture (`load 10s`, `metricWith3SampleEvery10Seconds`, 3 series) at HEAD with per-step stats on:

```
metricWith3SampleEvery10Seconds[60s:5s]                 TotalSamples=36  SamplesRead=36   <- bare subquery, correct
max_over_time(metricWith3SampleEvery10Seconds[60s:5s])  TotalSamples=36  SamplesRead=72   <- exactly 2x
rate(sum_over_time(metricWith1SampleEvery10Seconds[30s])[1m:30s])
                                                        TotalSamples= 2  SamplesRead= 8
```

For the third query the true storage reads were traced: `subqStart=210000`, `subqEnd=240000`, `subqInterval=30000` → 2 subquery steps; the inner `sum_over_time(m1[30s])` reads 3 points at step 0 and 3 new points at step 1 = **6**. Reported: 8 (6 merged + 2 materialized output points). For the second query the true read count is 36 (12 subquery steps × 3 series) and 72 is reported. A range query shows the inflation landing in the per-step array too: `max_over_time(m1[60s:10s])`, start=300 end=360 step=30s → `SamplesRead=24 readPerStep=[12 6 6]`, where the true subquery read count is 12. The equivalent non-subquery query is correct: `sum_over_time(m1[60s])` over the same range → `SamplesRead=12 readPerStep=[6 3 3]`.

**Fix:** The materialized subquery matrix is not I/O, so the `Call` loop must not add to `SamplesRead` when its matrix argument came from a subquery. Have `evalSubquery` signal that the replacement `*parser.MatrixSelector` is materialized (e.g. return a flag alongside `totalSamples`, or track it on the evaluator for the duration of the call) and pass `0` for `samplesReadCount` at `promql/engine.go:2184` in that case, keeping `IncrementSamplesAtStep(step, fullWindowCount)` unchanged. Merging in `evalSubquery` is the right place to capture the real reads; it is the second increment that is spurious.

### #2 🟠 High: `TotalSamples` semantics silently change for `@`-modified range selectors inside non-step-invariant calls

| | |
|---|---|
| **File** | `promql/engine.go:2160` |
| **Category** | correctness |
| **Confidence** | 100 |
| **Verified** | executed |
| **Found by** | solo-reviewer (High) |
| **Pre-existing** | no |

**Issue:** `fullWindowCount` is declared inside the per-step loop (`promql/engine.go:2145`) and only assigned inside the `if ts == ev.startTimestamp || selVS.Timestamp == nil` block. When an `@` modifier is present, that block runs only at step 0, so from step 1 on `IncrementSamplesAtStep(step, fullWindowCount)` adds **0**. The previous code passed `int64(len(floats)+totalHPointSize(histograms))` unconditionally, i.e. the retained window at every step.

This silently changes the existing, externally consumed `totalQueryableSamples`, `totalQueryableSamplesPerStep` and `prometheus_engine_query_samples_total` — contrary to the change's stated intent that `TotalSamples` keeps unchanged semantics, and contrary to the doc comment kept in place at `util/stats/query_stats.go:271` ("Each step should be identical to the `TotalSamples` when a step is run as an instant query, which means we intentionally do not account for optimizations that happen inside the range query engine that reduce the actual work"). Downstream projects use `totalQueryableSamples` for per-query cost accounting and limits; under-reporting by a factor of the step count can let a query slip under such a limit.

**Evidence:** `*parser.MatrixSelector` is explicitly *not* wrapped in a `StepInvariantExpr` (`promql/engine.go:4364-4367`, "We don't need to wrap a MatrixSelector because functions over range vectors evaluate those directly"), so the arm is reachable across multiple steps whenever the enclosing `Call` has a non-step-invariant non-matrix argument. Executed on the same fixture, range query start=201s end=220s step=5s:

```
predict_linear(metricWith3SampleEvery10Seconds[60s] @ 30, scalar(metricWith1SampleEvery10Seconds))
  base efbdc3f88 : TotalSamples=52  perStep=[13 13 13 13]
  HEAD ec7157593 : TotalSamples=16  perStep=[13  1  1  1]
```

(Base measured in a throwaway `git worktree` at `efbdc3f88`, since removed; HEAD unchanged throughout.) The same shape applies to `quantile_over_time`, `double_exponential_smoothing` and `holt_winters` with a non-invariant scalar argument. No existing test covers it — the closest case, `max_over_time(metricWith3SampleEvery10Seconds[60s] @ 30)` (`promql/engine_test.go:1352`), is fully step-invariant and so takes the `StepInvariantExpr` arm, keeping `TotalSamples: 48`.

**Fix:** Keep `TotalSamples` on its old path and only gate the new axis. Restore the unconditional argument, e.g. leave `IncrementSamplesAtStep(step, int64(len(floats)+totalHPointSize(histograms)))` as it was and compute only `samplesReadCount` inside the `if` block (initialised to 0 per step, which already gives the intended "reused data is not re-read" behavior for `SamplesRead`).

### #3 🟡 Medium: Documented invariant "`samplesRead` equals `totalQueryableSamples` for other query types" is false in both directions

| | |
|---|---|
| **File** | `docs/feature_flags.md:48` |
| **Category** | production |
| **Confidence** | 100 |
| **Verified** | executed |
| **Found by** | solo-reviewer (Medium) |
| **Pre-existing** | no |

**Issue:** Both new doc blocks (`docs/feature_flags.md:48` and `docs/querying/api.md:247`) state that outside range-vector functions in range queries, `samplesRead` equals `totalQueryableSamples`. The code violates this for two distinct, non-exotic shapes. Operators sizing dashboards or alerts against `prometheus_engine_query_samples_read_total` will draw wrong conclusions from a contract the implementation does not hold.

**Evidence:** Executed on the `TestQueryStatistics` fixture:

- Step-invariant plain selector in a range query — `metricWith3SampleEvery10Seconds{a="1"} @ 19`, start=201s end=220s step=5s → `TotalSamples=4 SamplesRead=1`, `perStep=[1 1 1 1]` vs `readPerStep=[1 0 0 0]`. Not a range-vector function, yet the two disagree, because `promql/engine.go:2472` adds the step-invariant subtree's `SamplesRead` once at step 0 while `TotalSamples` is replicated per step at `promql/engine.go:2470`.
- Subquery under a range-vector function — `max_over_time(metricWith3SampleEvery10Seconds[60s:5s])` instant → `TotalSamples=36 SamplesRead=72`, i.e. `samplesRead` exceeds `totalQueryableSamples` (see finding #1).

**Fix:** After fixing #1, state the invariant as it actually holds — `samplesRead <= totalQueryableSamples`, with equality only when no expression in the query is evaluated once and attributed to multiple steps (range-vector functions, `@`/`start()`/`end()` step-invariant subexpressions, and subqueries all break equality). Naming the step-invariant case explicitly is worth the extra sentence, since `@ end()` is common in recording rules and dashboards.

**Issue:** Several new `TestQueryStatistics` cases record `SamplesRead` values that are strictly greater than the same case's `TotalSamples`, with comments that rationalize the number rather than derive it. These expectations were evidently read off the implementation's output, so the test table cannot distinguish "delta accounting works" from "subquery reads are counted twice" — the single most important property of the new axis is unguarded.

**Evidence:** Executed and cross-checked against hand-derived read counts:

| line | query | asserted `SamplesRead` | `TotalSamples` | true storage reads |
|---|---|---|---|---|
| `promql/engine_test.go:1184` | `max_over_time(m3[60s:5s])` | 72 | 36 | 36 |
| `promql/engine_test.go:1908` | `histogram_quantile(0.9, max_over_time(h[20s:10s]))` | 52 | 26 | 26 |
| `promql/engine_test.go:1989` | `rate(sum_over_time(m1[30s])[1m:30s])` | 8 | 2 | 6 |
| `promql/engine_test.go:1955` | `sum by (a) (rate(m3[2m:30s]))[15m:5m]` | 108 | 36 | — |

The comments at `promql/engine_test.go:1955` and `:1970` ("subquery SamplesRead merged into outer") describe the merge but not the second, redundant count. By contrast the bare-subquery case at `promql/engine_test.go:1155` correctly asserts `SamplesRead: 12` equal to `TotalSamples: 12`, which is exactly the pair that should have made the inconsistency visible.

**Fix:** Add an invariant assertion to the shared test body next to `promql/engine_test.go:2430` — `require.LessOrEqual(t, stats.Samples.SamplesRead, stats.Samples.TotalSamples)` — and derive each subquery case's expected value from the subquery step count times the series count rather than from observed output. That assertion alone fails today on at least six cases and would have surfaced #1.
