## Findings

### #1 🔴 Critical: `NullPropagatedOperands` treats `AndAlso`/`OrElse` operands as null-propagating, so `IS NOT NULL` guards are dropped from CASE expressions that do not actually propagate NULL — silently wrong query results

| | |
|---|---|
| **File** | `src/EFCore.Relational/Query/SqlNullabilityProcessor.cs:626` |
| **Category** | correctness |
| **Confidence** | 100 |
| **Verified** | executed |
| **Pre-existing** | no |
| **Found by** | solo-reviewer (Critical) |

**Issue:**

```csharp
else if (expression is SqlBinaryExpression binary)
{
    NullPropagatedOperands(binary.Left, operands);
    NullPropagatedOperands(binary.Right, operands);
}
```

This accepts *every* operator `SqlBinaryExpression` admits. But `SqlBinaryExpression.IsValidOperator`
(`SqlBinaryExpression.cs:81-105`) admits `AndAlso`, `OrElse` and `Coalesce`, none of which propagate
NULL over their operands: SQL's three-valued logic absorbs NULL (`FALSE AND NULL = FALSE`,
`TRUE OR NULL = TRUE`), and `COALESCE` exists precisely to swallow it.

So for `CASE WHEN a IS NOT NULL THEN (a AND b) ELSE NULL END`, `a` lands in
`nullPropagatedOperands`, `DropNotNullChecks` (`:597`) deletes the guard, and the CASE collapses to
`a AND b` — which yields `FALSE` where the original yielded `NULL`.

This is not an exotic shape. The dominant way to reach it is the ordinary null-semantics rewrite:
`VisitSqlBinary` turns `a == b` on nullable columns into `a = b AND b IS NOT NULL` and `a != b` into
`a <> b OR b IS NULL` (`:1393`, `RewriteNullSemantics`). Any
`x.Nullable != null ? x.Nullable == x.Other : (bool?)null` — a very common LINQ idiom — is therefore
miscompiled.

The exact rule this violates is already written down in the same file, ten lines of comment at
`:2314-2321`, where the mirror-image transform deliberately excludes these operators:

```csharp
case SqlBinaryExpression sqlBinaryOperand
    when sqlBinaryOperand.OperatorType != ExpressionType.AndAlso
    && sqlBinaryOperand.OperatorType != ExpressionType.OrElse:
{
    // binaryOp(a, b) != null -> a != null && b != null
    // for AndAlso, OrElse we can't do this optimization
```

The new helper is essentially `ProcessNullNotNull`'s traversal with that exclusion missing.

Consequences are silent and of two kinds: **wrong projected values** (`null` becomes `false`/`true`)
and **wrong rows returned** (predicates using such a ternary admit rows they must exclude). No
exception is raised.

**Evidence:** *(executed)*

A self-contained SQLite probe was built against the repo's own `EFCore.Sqlite.Core` and run at HEAD
`afcfba2e9` and at the merge base `051c33a79` (via `git worktree`; HEAD never moved), over a 3×3
null/false/true × null/0/1 seed, comparing SQL results row-by-row against the same LINQ evaluated in
memory.

**Base commit `051c33a79`: 17 / 17 MATCH. HEAD `afcfba2e9`: 10 MISMATCH.**

Representative cases (all `MATCH` at base):

| LINQ | SQL after change | Row | Expected | Actual |
|---|---|---|---|---|
| `sA != null ? sA == sB : (bool?)null` | `sA = sB AND sB IS NOT NULL` | sA=null, sB=null | `null` | **`False`** |
| `iA != null ? iA == iB : (bool?)null` | `iA = iB AND iB IS NOT NULL` | iA=null, iB=null | `null` | **`False`** |
| `iA != null ? iA != iB : (bool?)null` | `iA <> iB OR iB IS NULL` | iA=null, iB=null | `null` | **`True`** |
| `iA != null ? !(iA == iB) : (bool?)null` | `iA <> iB OR iB IS NULL` | iA=null, iB=null | `null` | **`True`** |
| `A != null ? A & B : null` | `A AND B` | A=null, B=false | `null` | **`False`** |
| `A != null ? A \| B : null` | `A OR B` | A=null, B=true | `null` | **`True`** |
| `iA != null && BoolA ? iA == iB : (bool?)null` | `CASE WHEN BoolA THEN iA = iB AND iB IS NOT NULL ELSE NULL END` | iA=null, iB=null | `null` | **`False`** |

The partial-drop path is affected too (last row): the `BoolA` conjunct survives while the
semantically load-bearing `iA IS NOT NULL` is removed.

Predicate contexts return **wrong row sets**, not just wrong values:

```
WHERE ("e"."NullableIntA" = "e"."NullableIntB" AND "e"."NullableIntB" IS NOT NULL) = 0
  expected Ids [2,3,4,6]   actual Ids [2,3,4,6,9]   <- extra row

WHERE ("e"."NullableBoolA" AND "e"."NullableBoolB") = 0
  expected Ids [1,2,3,4]   actual Ids [1,2,3,4,7]   <- extra row
```

At the base commit each of these emitted the intact
`CASE WHEN "e"."NullableIntA" IS NOT NULL THEN ... ELSE NULL END` and produced correct results.

`Coalesce` is the same class of bug and is currently latent rather than live:
`SqlBinaryExpression.IsValidOperator` admits it and `SqlExpressionFactory.MakeBinary` would construct
it, but relational EF routes `??` through `SqlExpressionFactory.Coalesce`
(`SqlExpressionFactory.cs:485`) into a `SqlFunctionExpression`, and `QuerySqlGenerator` has no
`Coalesce` binary operator mapping. A provider or future rewrite that produces a `Coalesce`
`SqlBinaryExpression` would hit the identical unsoundness, so the fix should be an allow-list rather
than a two-operator deny-list.

Why CI would not have caught this: none of the five new tests uses a boolean or comparison result —
they cover `~int?`, `int? + int?`, and string concatenation only, all of which are genuinely
null-propagating (all three were verified to still produce correct results). And `grep` finds no
existing `NullableBoolA != null ? …` ternary anywhere in `NullSemanticsQueryTestBase.cs`. So every
added and updated baseline in this changeset is consistent with the defect being present.

On SQL Server the same shapes go through `SearchConditionConvertingExpressionVisitor`
(`src/EFCore.SqlServer/Query/Internal/SqlServerParameterBasedSqlProcessor.cs:45`), which runs *after*
nullability processing and rewrites a bare condition to `CASE WHEN cond THEN 1 ELSE 0 END`
(`SearchConditionConvertingExpressionVisitor.cs:41-51`) — which also cannot yield NULL, so the same
`null → false` corruption applies. This could not be executed: SQL Server functional tests need a
live server, and the test projects do not compile in this environment
(`test/EFCore.Specification.Tests` fails with 9 errors, e.g.
`CustomConvertersTestBase.cs(1202,49): error CS0023`, under the SDK 10.0.203 that rolls forward from
the pinned 9.0 preview). **No test in this repository's suites was executed** — the evidence above is
from a standalone probe built against the repo's own source, removed afterwards.

**Fix:** Restrict the binary recursion to operators that actually propagate NULL over both operands,
mirroring the existing rule at `:2314-2316`. An allow-list is safer than excluding
`AndAlso`/`OrElse`, because it also covers `Coalesce` and any operator added to `IsValidOperator`
later:

```csharp
else if (expression is SqlBinaryExpression
         {
             OperatorType: ExpressionType.Add or ExpressionType.Subtract
                 or ExpressionType.Multiply or ExpressionType.Divide or ExpressionType.Modulo
                 or ExpressionType.And or ExpressionType.Or or ExpressionType.ExclusiveOr
                 or ExpressionType.Equal or ExpressionType.NotEqual
                 or ExpressionType.LessThan or ExpressionType.LessThanOrEqual
                 or ExpressionType.GreaterThan or ExpressionType.GreaterThanOrEqual
         } binary)
{
    NullPropagatedOperands(binary.Left, operands);
    NullPropagatedOperands(binary.Right, operands);
}
```

Note `And`/`Or` (bitwise, non-boolean) do propagate NULL and stay in; `AndAlso`/`OrElse` (boolean) do
not and are excluded — that is exactly the `isBooleanExpression` split made at
`RelationalSqlTranslatingExpressionVisitor.cs:442-443`. Worth adding a test with a `bool?` result and
one with a comparison result (`x.NullableIntA != null ? x.NullableIntA == x.NullableIntB : (bool?)null`)
— both fail today and pass with this change.
