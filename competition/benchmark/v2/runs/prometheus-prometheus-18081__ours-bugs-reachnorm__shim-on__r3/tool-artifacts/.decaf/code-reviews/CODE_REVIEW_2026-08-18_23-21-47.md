## Findings

### #1 🟠 High: `samplesRead` double-counts every subquery, reporting ~2× the samples actually read

| | |
|---|---|
| **File** | `promql/engine.go:1874` (and `promql/engine.go:2184`) |
| **Category** | correctness |
| **Confidence** | 100 |
| **Verified** | executed |
| **Pre-existing** | no |
| **Found by** | solo-reviewer (High) |

**Issue:** `evalSubquery` merges the subquery's real `SamplesRead` into the parent (`MergeSamplesReadFromSubquery`), and then the outer range-vector-function loop counts the *materialized subquery matrix* a second time via `IncrementSamplesReadAtStep(step, samplesReadCount)`. The materialized matrix is not storage I/O — it is the subquery's own output, already counted. Because the subquery produces exactly one point per inner step, and the outer windows tile the subquery range, the inflation is almost exactly a factor of two for any `<range_fn>(expr[range:step])`. This directly contradicts the feature's stated purpose and the contract documented in three places (`util/stats/query_stats.go:279-281`, `docs/feature_flags.md:48`, `docs/querying/api.md:247`: "for other queries this equals `totalQueryableSamples`").

**Evidence:** Executed against the post-change tree with per-step stats enabled:

| query | actual storage reads | reported `samplesRead` | `totalQueryableSamples` |
|---|---|---|---|
| `sum_over_time(m[1m:10s])` @300, instant | 6 (6 inner steps × 1 sample) | **12** | 6 |
| `sum_over_time(m[1m:10s])` 300→400 step 50s | 16 (16 inner steps) | **32** | 18 |
| `max_over_time(metricWith3SampleEvery10Seconds[60s:5s])` (test case) | 36 | **72** | 36 |

The change's own tests enshrine the doubling — `promql/engine_test.go:1548` reads `SamplesRead: 2, // subquery + outer` for a query whose real read count is 1, and `promql/engine_test.go:1163` reads `SamplesRead: 72` against `TotalSamples: 36`. The author's comment shows the addition was deliberate, but it makes the metric measure something other than what all three documentation sites promise, and it is the counter (`prometheus_engine_query_samples_read_total`) operators will use to size disk I/O.

**Fix:** Suppress one of the two contributions. The cleanest is to skip the outer `IncrementSamplesReadAtStep` when the matrix selector originated from `evalSubquery` (the synthetic `*parser.MatrixSelector` returned at `promql/engine.go:1878` is already distinguishable — e.g. thread a flag through, or have `evalSubquery` return the read count and let the caller elide it). If the doubling is genuinely intended, the three documentation sites and the `SamplesRead` field comment must say so explicitly, because "equals `totalQueryableSamples`" is false today for every subquery.

### #2 🟠 High: `countSamplesAfter` re-scans the whole window every step, costing 30–60% on range queries — and it runs even when stats are not requested

| | |
|---|---|
| **File** | `promql/value.go:195` (called from `promql/engine.go:2164`) |
| **Category** | efficiency |
| **Confidence** | 100 |
| **Verified** | executed |
| **Pre-existing** | no |
| **Found by** | solo-reviewer (High) |

**Issue:** `countSamplesAfter` iterates the *entire* `floats`/`histograms` window from index 0 on every step, for every series, to count the O(step-delta) points at the tail. Both slices are sorted ascending by `T`, so this is an O(window) scan where O(new points) suffices. The old code needed only `len(floats)`. Critically, `q.sampleStats` always exists and `ng.metrics.querySamples.Add(...)` always runs (`promql/engine.go:685-686`), so this cost is paid by every range query with a range-vector function on a default Prometheus — the per-step-stats feature flag does not gate it. The regression scales with the range-selector window, and it is asymptotic for cheap functions such as `last_over_time`/`first_over_time`, whose own per-step work is O(1).

**Evidence:** Executed. Range query 4000→100000 step 15s over a 15s-resolution series, `-benchtime 100x -count 3` / `-benchtime 300x -count 5`, base `efbdc3f88` vs `ec7157593`:

| benchmark | base | this change | delta |
|---|---|---|---|
| `last_over_time(m[1h])` | 1.28 ms | 1.71 ms | **+33%** |
| `count_over_time(m[1h])` | 1.32 ms | 1.73 ms | **+31%** |
| `rate(m[1h])` | 1.69 ms | 2.09 ms | **+24%** |
| `last_over_time(m[6h])` | 3.55 ms | 5.72 ms | **+61%** |

Attribution confirmed by mutation: short-circuiting `countSamplesAfter` to `return 0` on the post-change tree restored `last_over_time(m[6h])` to 3.53/3.60/3.55 ms — i.e. the entire regression is this function. `promql/value.go` was restored byte-identically afterwards (sha256 `75eae2b1…` before and after; `git diff --stat` empty; `TestQueryStatistics` green).

**Fix:** Walk backwards from the tail and stop at the first point with `T <= cutoff`:

```go
for i := len(floats) - 1; i >= 0 && floats[i].T > cutoff; i-- { n++ }
for i := len(histograms) - 1; i >= 0 && histograms[i].T > cutoff; i-- { n += int64(histograms[i].size()) }
```

This is exactly equivalent given ascending `T` order and makes the cost proportional to the step delta rather than the window.

### #3 🟡 Medium: `totalQueryableSamples` silently drops ~11× for `predict_linear(x[r] @ t, s)` range queries

| | |
|---|---|
| **File** | `promql/engine.go:2143-2184` |
| **Category** | production |
| **Confidence** | 100 |
| **Verified** | executed |
| **Pre-existing** | no |
| **Found by** | solo-reviewer (Medium) |

**Issue:** The old code called `IncrementSamplesAtStep(step, int64(len(floats)+totalHPointSize(histograms)))` *outside* the `ts == ev.startTimestamp || selVS.Timestamp == nil` guard, so when an `@` modifier caused the window to be reused across steps, the retained window was still counted at every step. The new code initializes `fullWindowCount` to 0 and only assigns it inside the guard, so reused steps now contribute 0 to `TotalSamples`. This changes an existing public API field (`totalQueryableSamples`) and an existing engine counter (`prometheus_engine_query_samples_total`), despite the inline comment at `promql/engine.go:2143` asserting "unchanged semantics", and despite the retained field comment at `util/stats/query_stats.go:271-275` that explicitly states "we intentionally do not account for optimizations that happen inside the range query engine that reduce the actual work that happens".

Most `<range_fn>(x[r] @ t)` shapes are unaffected because `preprocessExprHelper` wraps them in a `StepInvariantExpr`. The exception is range-vector functions listed in `AtModifierUnsafeFunctions` (`promql/functions.go:2244`), where `isStepInvariant` is forced false and the `MatrixSelector` argument is deliberately left unwrapped (`promql/engine.go:4364`). `predict_linear` is the one such function.

**Evidence:** Executed on both trees, query `predict_linear(m[1m] @ 100, 60)`, range 100→300 step 20s, 10s-resolution series:

- base `efbdc3f88`: `TotalSamples=66`, per-step `{100000:6, 120000:6, …, 300000:6}`
- this change: `TotalSamples=6`, per-step `{100000:6, 120000:0, …, 300000:0}`

`predict_linear(m[1m], 60)` (no `@`) is unchanged at 66 on both, confirming the `@`-reuse branch is the cause. No test in the 1135-line test diff covers this shape, which is why the suite stays green.

**Fix:** If the reduction is unintended, restore the old accounting by hoisting the full-window count out of the guard (keep `samplesReadCount` at 0 for reused steps, which is correct for the new metric):

```go
if ts == ev.startTimestamp || selVS.Timestamp == nil {
    ...
    floats, histograms = ev.matrixIterSlice(...)
    if step == 0 { samplesReadCount = int64(len(floats) + totalHPointSize(histograms)) } else { samplesReadCount = countSamplesAfter(...) }
}
fullWindowCount = int64(len(floats) + totalHPointSize(histograms)) // outside the guard, as before
```

If it *is* intended, it needs a changelog entry, an update to the `TotalSamplesPerStep` comment it contradicts, and a test pinning the new value.

### #5 🟢 Low: subquery children allocate a `TotalSamplesPerStep` slice that is never read

| | |
|---|---|
| **File** | `util/stats/query_stats.go:411` (`NewChildWithStepTracking` → `InitStepTracking`) |
| **Category** | efficiency |
| **Confidence** | 100 |
| **Verified** | traced |
| **Pre-existing** | no |
| **Found by** | solo-reviewer (Low) |

**Issue:** `InitStepTracking` (`util/stats/query_stats.go:307-308`) allocates both `TotalSamplesPerStep` and `SamplesReadPerStep`. For subquery children created at `promql/engine.go:1869` and `:2397`, only `SamplesRead`/`SamplesReadPerStep` are ever consumed — `MergeSamplesReadFromSubquery` copies only the read slice, and `TotalSamples` is merged as a scalar at `:2424`. The child's `TotalSamplesPerStep` is written to and then discarded. Before this change these children were created via `NewChild()` (per-step disabled), so both slices were nil and neither was allocated.

**Evidence:** Traced through both call sites. Sizing: with `--enable-feature=promql-per-step-stats` and `stats=all`, a subquery `foo[7d:15s]` gives `numSteps = 40321`, so `InitStepTracking` allocates 2 × 322 KB per subquery evaluation where the previous code allocated nothing; half of that is dead. Gated behind the feature flag, so exposure is limited.

**Fix:** Give the subquery child only the read slice — either add a variant of `InitStepTracking` that skips `TotalSamplesPerStep`, or allocate it lazily on first `IncrementSamplesAtStep`.
