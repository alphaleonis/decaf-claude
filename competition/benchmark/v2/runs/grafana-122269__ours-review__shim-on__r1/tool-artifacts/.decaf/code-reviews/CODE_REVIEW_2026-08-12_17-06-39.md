### #1 🟠 High: `grafana-cli` credential path ignores the feature flag that is documented to gate it

| | |
|---|---|
| **File** | `pkg/cmd/grafana-cli/utils/command_line.go:111` |
| **Category** | correctness / security |
| **Confidence** | 100 |
| **Found by** | quick-reviewer (High), broad-reviewer (High), adversarial-reviewer (High), design-reviewer (High), security-reviewer (Medium) |

**Issue:** `ContextCommandLine.GrafanaComProxyAPIToken()` re-implements the `proxy_token` → `sso_api_token` fallback but never evaluates `grafana.dedicatedGrafanaComProxyAPIToken`:

```go
func (c *ContextCommandLine) GrafanaComProxyAPIToken() string {
	cfg, err := c.Config()
	if err != nil { /* ... */ return "" }
	if cfg.GrafanaComProxyAPIToken != "" {
		return cfg.GrafanaComProxyAPIToken   // <- no flag check
	}
	return cfg.GrafanaComSSOAPIToken
}
```

The server path (`pkg/setting/setting.go:762`, called from `cli.go:113` and `target.go:99`) *is* gated. `grafana-cli` has no OpenFeature initialization at all — there is no `InitOpenFeature*` call anywhere under `pkg/cmd/grafana-cli`, so it could not evaluate the flag as written.

Two concrete consequences:

1. **Split-brain configuration.** With `proxy_token` set and the flag off — the shipped default (`Expression: "false"`, `registry.go:2256`) — `grafana-server`'s gnet proxy and Wire-provided plugin config use `sso_api_token`, while `grafana-cli plugins install` uses `proxy_token`. The same grafana.com API is contacted with two different credentials from one installation, and an auth failure is attributable to neither.
2. **The kill switch does not cover the surface it names.** The toggle description is "Use a dedicated auth token for Grafana.com proxy requests **and plugin installs**". If the dedicated token turns out to be unprovisioned or wrongly scoped, turning the flag off rolls back the server but not the CLI — so container entrypoints and provisioning that install plugins at boot keep failing, with no documented way to revert short of editing the config file.

This also directly contradicts the documentation added in this same commit (`docs/sources/setup-grafana/configure-grafana/_index.md:2322-2325`), which states that `proxy_token` — described as covering "plugin catalog browsing and plugin installs via `grafana-cli`" — "Requires the `dedicatedGrafanaComProxyAPIToken` feature toggle to be enabled."

**Fix:** Make both surfaces agree on one resolution authority. Either initialize OpenFeature in the CLI and call the shared resolver, or (simpler, and it also fixes #5) pass the evaluated boolean into a single flag-agnostic resolver used by both:

```go
// one authority, flag supplied by the caller that can evaluate it
func (cfg *Cfg) EffectiveGrafanaComProxyToken(dedicatedEnabled bool) string {
	if dedicatedEnabled && cfg.GrafanaComProxyAPIToken != "" {
		return cfg.GrafanaComProxyAPIToken
	}
	return cfg.GrafanaComSSOAPIToken
}
```

If gating the CLI is genuinely not intended, the docs must say so instead.

### #2 🟠 High: Token resolution is an out-of-band mutation that not every `Cfg`-construction path performs — the unresolved default is *no* credential

| | |
|---|---|
| **File** | `pkg/setting/setting.go:762`, `pkg/tests/testinfra/testinfra.go:143` |
| **Category** | correctness / design |
| **Confidence** | 100 |
| **Found by** | broad-reviewer (High), adversarial-reviewer (High), design-reviewer (High), security-reviewer (High) |

**Issue:** `ResolveGrafanaComProxyAPIToken()` mutates `Cfg` in place and its "must be called after OpenFeature is initialized" contract is enforced only by a doc comment and two hand-written call sites. `parseINIFile` (`setting.go:1677`) populates `GrafanaComProxyAPIToken` from `proxy_token`, which is `""` in every existing deployment. Both consumers read the field directly:

- `pkg/api/grafana_com_proxy.go:54` → `ReverseProxyGnetReq(...)`, which at line 43 attaches `Authorization` **only if the token is non-empty**
- `pkg/services/pluginsintegration/pluginconfig/config.go:39`

So on any bootstrap that builds a `Cfg` and wires those consumers without calling the resolver, the field stays `""` and the outbound request carries **no `Authorization` header at all** — where before this change it carried `GrafanaComSSOAPIToken`. grafana.com then serves the anonymous catalog rather than returning an error, so private/enterprise plugins silently disappear instead of failing loudly.

This is not hypothetical — it is already true in-tree. `pkg/tests/testinfra/testinfra.go:124` calls `featuremgmt.InitOpenFeatureWithCfg(cfg)` but never the new resolver, then calls `server.InitializeForTest` at line 143. I verified that `InitializeForTest` (`pkg/server/wire_gen.go:1013`) wires `pluginconfig.ProvidePluginManagementConfig(cfg, ...)` at `wire_gen.go:1073`. `testinfra.GrafanaOpts` exposes `GrafanaComSSOAPIToken` (`testinfra.go:960`), which writes `sso_api_token` into the ini (`testinfra.go:702`) — that option no longer reaches the gnet proxy or the plugin config at all. There is no `proxy_token` knob in `GrafanaOpts` either. Every Go integration test now exercises a credential state production never has.

Out-of-tree bootstraps (notably Grafana Enterprise, which builds its own server entry point) carry the same risk and cannot be verified from this repo.

**Fix:** Remove the possibility of forgetting the call rather than adding it in more places. Preferred: keep the parsed value immutable and expose the effective token as a derived read at the two consumption sites (see #1's sketch), or inject the resolved value as a distinct Wire-provided type so an unresolved token is unobtainable by construction. If the imperative step is kept, fold it into `featuremgmt.InitOpenFeatureWithCfg` (or one shared bootstrap helper that `cli.go`, `target.go`, and `testinfra.go` all call) so it cannot drift, and add a `proxy_token` knob to `testinfra.GrafanaOpts`.

### #3 🟠 High: New docs name the feature toggle without its registered `grafana.` prefix, so following them enables nothing

| | |
|---|---|
| **File** | `docs/sources/setup-grafana/configure-grafana/_index.md:2325` |
| **Category** | documentation / correctness |
| **Confidence** | 100 (validator: confirmed) |
| **Found by** | security-reviewer (High), design-reviewer (Medium) |

**Issue:** The docs say `proxy_token` "Requires the `dedicatedGrafanaComProxyAPIToken` [feature toggle] to be enabled." The registered name is `grafana.dedicatedGrafanaComProxyAPIToken` (`pkg/services/featuremgmt/registry.go:2253`), and `pkg/setting/setting.go:763` evaluates that exact fully-qualified string.

I traced the lookup chain and confirmed no prefix normalization anywhere in it: `setting.ReadFeatureTogglesFromInitFile` uses ini keys verbatim, and `buildStaticFlagsMap` (`pkg/services/featuremgmt/static_provider.go:20-32`) keys registry flags by `flag.Name` and then `maps.Copy`s the ini flags in under *their* keys. `dedicatedGrafanaComProxyAPIToken` and `grafana.dedicatedGrafanaComProxyAPIToken` are therefore two distinct map entries.

An operator who follows the docs and sets `dedicatedGrafanaComProxyAPIToken = true` under `[feature_toggles]` creates an unused flag. The real toggle keeps its registry default of `false`, and `ResolveGrafanaComProxyAPIToken` silently overwrites the configured `proxy_token` with `sso_api_token`. No error, no warning — the credential-separation control the operator believes they enabled is not engaged, and (per #6) nothing in the running system reveals that.

**Fix:** Write the fully-qualified name `grafana.dedicatedGrafanaComProxyAPIToken` in the docs. Separately, consider whether the `grafana.` prefix is wanted at all here — the three earlier names for this toggle visible in `toggles_gen.json` were unprefixed, which suggests the prefix was a late rename the docs did not follow.

### #4 🟡 Medium: Toggle is latched at boot but registered as not requiring a restart

| | |
|---|---|
| **File** | `pkg/services/featuremgmt/registry.go:2252`, `pkg/setting/setting.go:762` |
| **Category** | operability |
| **Confidence** | 75 (validator: confirmed) |
| **Found by** | adversarial-reviewer (High), design-reviewer (Medium) |

**Issue:** The flag is evaluated exactly once, during startup, and the result is baked into `cfg.GrafanaComProxyAPIToken`. Consumers read the baked-in field, never the flag. With a dynamic provider (`cfg.OpenFeature.ProviderType`, e.g. OFREP with a cache TTL — see `pkg/setting/setting_openfeature.go`), flipping the toggle at runtime changes nothing for the gnet proxy or plugin installs until every instance restarts. That matters most in the rollback direction: switching the flag off during an incident does not stop the dedicated token from flowing.

The registry entry does not set `RequiresRestart`, and `pkg/services/featuremgmt/toggles_gen.csv:265` records `RequiresRestart=false` (CSV header: `Created,Name,Stage,Owner,requiresDevMode,RequiresRestart,FrontendOnly`). The declared metadata tells operators the opposite of the implementation — and `RequiresRestart` is precisely the field they consult to decide whether a rollback needs one.

Related, from the same destructive-overwrite shape: after a flag-off boot the field holds the SSO token, so a hypothetical second call to `ResolveGrafanaComProxyAPIToken` sees a non-empty field and early-returns, treating the SSO token as the dedicated one. There is only one call per process today, so this is latent rather than live — but it is a trap for whoever adds the third call site (see #2).

**Fix:** Set `RequiresRestart: true` on the registry entry, or — better, and consistent with #1/#2 — evaluate the flag at the consumption sites so the toggle behaves dynamically like the rest of the codebase's flags.

### #5 🟡 Medium: Flag key hardcoded as a string literal, bypassing the generated constant

| | |
|---|---|
| **File** | `pkg/setting/setting.go:763` |
| **Category** | consistency / maintainability |
| **Confidence** | 100 (validator: confirmed) |
| **Found by** | design-reviewer (Medium), security-reviewer (Low) |

**Issue:** The evaluation uses a bare literal `"grafana.dedicatedGrafanaComProxyAPIToken"` rather than the generated `featuremgmt.FlagGrafanaDedicatedGrafanaComProxyAPIToken` (`pkg/services/featuremgmt/toggles_gen.go:727`). Every other OpenFeature call site in the backend uses the generated constant (`pkg/expr/graph.go:242`, `pkg/services/accesscontrol/resourcepermissions/service.go:418`, `pkg/services/ngalert/api/prometheus/api_prometheus.go:344`, and others). This one cannot: `pkg/services/featuremgmt` imports `pkg/setting`, so the reverse import would cycle.

The consequence is a silent-failure trap. Renaming the toggle in `registry.go` regenerates the constant and updates every constant-using call site, but leaves this literal stale. The code still compiles; the provider returns `FLAG_NOT_FOUND` and the `.Boolean(...)` convenience method discards that error and returns the supplied default `false` — so the gate becomes permanently off with no compile error and no runtime signal. This toggle was renamed four times during this PR's own development (visible in `toggles_gen.json`), so the rename risk is demonstrated rather than theoretical. It is the same class of string drift that already produced #3.

**Fix:** Move the flag evaluation out of `pkg/setting` into a layer that may import `featuremgmt` — the startup command, or the consumption sites — and pass the boolean in. This composes with the fix for #1 and #2.

### #6 🟡 Medium: Credential fallback is silent and unobservable after startup

| | |
|---|---|
| **File** | `pkg/setting/setting.go:766` |
| **Category** | observability |
| **Confidence** | 75 (validator: confirmed) |
| **Found by** | adversarial-reviewer (Medium), security-reviewer (Medium) |

**Issue:** `cfg.GrafanaComProxyAPIToken = cfg.GrafanaComSSOAPIToken` overwrites the field with no log line at any level, and neither call site logs before or after. Nothing records that the fallback was taken, or which of the two reasons caused it (flag off vs. `proxy_token` unset). Because the overwrite is destructive, the configured-vs-effective distinction is destroyed along with it.

`/api/admin/settings` does not fill the gap: `OSSImpl.Current()` (`pkg/setting/provider.go:118-129`) iterates `o.Cfg.Raw.Sections()` — the raw ini — not the resolved struct fields. An operator who has configured `proxy_token` sees it present and redacted in the settings API even when the SSO token is what is actually being sent to grafana.com.

The failure this enables is concrete: an operator enables the flag and `proxy_token`, confirms catalog browsing works, then revokes `sso_api_token` as cleanup. Any instance that restarted before the flag reached it, any container whose config lacks `proxy_token`, and any provider evaluation that fell back to the default all quietly resolve to the now-revoked credential — and the gnet proxy and plugin installs start returning 401 with nothing in the logs saying which credential was chosen or why. `cfg.Logger` is initialized well before the resolver runs (`setting.go:1284`), so the log line is available to write.

**Fix:** Log the resolution outcome once at startup — which source won and why, never the value (`RedactedValue` already covers `PROXY_TOKEN$`). Keep the resolved choice in a separate field from the configured one so the distinction survives into diagnostics.

## Specialist Notes

### Threat Model Notes (security-reviewer)

**Trust boundaries touched.** Two outbound boundaries carry the credential: the `/api/gnet/*` reverse proxy (`pkg/api/grafana_com_proxy.go`), which forwards a user-controlled path and method to grafana.com with an instance-level bearer token; and the plugin repo client (`pkg/plugins/repo/client.go`), reachable from both the server and `grafana-cli`. The inbound boundary is `pkg/api/api.go:587`, guarded only by `reqSignedIn`.

**Data sensitivity.** `sso_api_token` is a high-value shared credential — it authenticates unified SSO with grafana.com (`pkg/services/auth/gcomsso/gcom_logout_hook.go:50`) and unified storage (`pkg/storage/unified/sql/backend.go:57`). Reusing it for the plugin/proxy path is exactly the exposure this change sets out to remove, and the goal is sound.

**Attack-surface change.** The inbound surface is unchanged. The credential attached to it becomes narrower — but only when the flag is on *and* `proxy_token` is set *and* the resolver ran. The flag ships as `Expression: "false"`, so the default deployment posture is byte-for-byte the pre-change posture. The benefit is entirely opt-in, and opts in through three independently fragile strings (the ini key, the toggle name in docs, the literal in `setting.go`).

**Assessment of the stated goal.** Credential separation is achieved on the happy path and only there. Every failure mode of the mechanism — flag default, provider unavailability, the docs/registry name mismatch (#3), a missing resolver call at a new entry point (#2) — resolves toward either the more privileged credential or no credential, and none of them is logged (#6). The fallback does not merely fail to help; it makes the control's engagement unverifiable from the running system.

**Assumptions and limits.** OSS entry points only. Grafana Enterprise builds its own server bootstrap outside this repo and would independently need the `ResolveGrafanaComProxyAPIToken()` call — unverifiable from here. The intended grafana.com-side scope of `proxy_token` versus `sso_api_token` is also unverifiable from this repo.

### Considered But Not Flagged (all agents)

**Tiered down by the evidence screen:**

- *No "strict mode" — the fallback fails open to the higher-privilege credential* (security-reviewer, `setting.go:762`, screened 35). An operator who deliberately provisions a scoped `proxy_token` cannot express "never send the SSO token here"; every negative path resolves to the SSO credential. Tiered down because the fallback is explicitly intentional and stated as such in the commit message ("Falls back to sso_api_token when proxy_token is not configured, preserving backward compatibility"), making this a design-posture request rather than a defect. The sharp, actionable edges of the same concern are captured in #3, #4 and #6.

**Examined and found sound:**

- **`PROXY_TOKEN$` redaction coverage** — traced every `RedactedValue` invocation and the pattern holds on all of them. Env overrides (`setting.go:900`, `964`, `1867`) pass `GF_GRAFANA_COM_PROXY_TOKEN`; command-line overrides (`setting.go:1139`) pass `default.grafana_com.proxy_token`, which uppercases to a string ending in `PROXY_TOKEN`; `/api/admin/settings` builds the key via `EnvKey("grafana_com", "proxy_token")` → the same form. The `$`-anchored pattern matches all three, consistent with how `sso_api_token` is covered by `API_TOKEN$`. Covered by a new test case. No gap.
- **Call ordering at the two production entry points** — `cli.go` and `target.go` both sequence ini-parse → `InitOpenFeatureWithCfg` → `ResolveGrafanaComProxyAPIToken` → `server.Initialize`/`InitializeModuleServer`. The flag is readable and the mutation lands before any consumer captures the value. Correct.
- **Data race on the mutated `Cfg`** — both call sites run strictly before the server starts, i.e. before any goroutine holds the pointer. No race today; the mutate-in-place contract that would make a future late call a race is covered by #2.
- **`Cfg.Load` re-parsing wiping the resolution** — no runtime config-reload path re-runs `parseINIFile` on a live `Cfg` (only `setting.go:1388` and `1423`, both during construction). The resolution cannot be silently undone.
- **`InitializeForCLI` (`wire_gen.go:1721`) missing the resolver** — it does not wire `ProvidePluginManagementConfig` (only lines 367 and 1073 do), so the runner path is unaffected. Not a defect.
- **`openfeature.EvaluationContext{}` discarding global targeting context** — the OpenFeature Go SDK merges API-, client-, and invocation-level contexts rather than replacing them, so an empty invocation context does not strip targeting attributes.
- **Token leaking to a non-grafana.com host via `--pluginUrl`** — `pkg/plugins/repo/client.go:240` only attaches `Authorization` when the URL is prefixed by the configured grafana.com API URL. A custom `--repo` mirror does still receive it, but the caller of `grafana-cli` already has read access to the config file holding the token, so this is not a privilege boundary. Pre-existing and unchanged in shape by this diff.
- **`skipStaticRootValidation = true` in `TestResolveGrafanaComProxyAPIToken`** — duplicates the existing pattern at `setting_test.go:30`; the flag is monotonic and no test in the package exercises the validation-failure path. Harmless.
- **Global OpenFeature provider swap in the new tests** — each subtest registers its own `t.Cleanup` resetting to `NoopProvider{}`, no subtest calls `t.Parallel()`, and the only parallel tests in the package (`TestDynamicSection`) do not touch OpenFeature. Confirmed by a clean full-package run.
- **Do the three new subtests actually discriminate?** Traced each mutation of the production logic: inverting the flag check fails subtest 1; dropping `&& cfg.GrafanaComProxyAPIToken != ""` fails subtest 3; removing the flag check entirely fails subtest 1.
