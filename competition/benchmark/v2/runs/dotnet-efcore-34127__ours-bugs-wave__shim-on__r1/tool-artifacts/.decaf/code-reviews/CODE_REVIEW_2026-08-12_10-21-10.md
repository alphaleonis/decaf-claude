## Findings

### #1 🔴 Critical: `NullPropagatedOperands` treats every binary operator as null-propagating, so the optimization drops guards it must keep and returns wrong data

| | |
|---|---|
| **File** | `src/EFCore.Relational/Query/SqlNullabilityProcessor.cs:626` (block introduced at `:576`) |
| **Category** | correctness |
| **Confidence** | 100 |
| **Found by** | adversarial-reviewer (Critical, anchor 100), broad-reviewer (Critical, anchor 75) |
| **Validation** | confirmed by `finding-validator`; independently reproduced by the orchestrator against base and head builds |

**Issue:**

The new block at `SqlNullabilityProcessor.cs:576-590` rewrites

```
CASE WHEN <expr> IS NOT NULL THEN <result> ELSE NULL END   →   <result>
```

whenever `NullPropagatedOperands(<result>)` contains `<expr>`. That is sound only if `<result>`
evaluates to NULL on every row where `<expr>` is NULL. The helper infers this structurally, and at
`:626-630` it recurses unconditionally into **both** operands of **every** `SqlBinaryExpression`:

```csharp
else if (expression is SqlBinaryExpression binary)
{
    NullPropagatedOperands(binary.Left, operands);
    NullPropagatedOperands(binary.Right, operands);
}
```

`SqlBinaryExpression` legally carries `AndAlso`, `OrElse`, `And`, `Or` and `Coalesce` — see the
operator whitelist at `src/EFCore.Relational/Query/SqlExpressions/SqlBinaryExpression.cs:95-107`.
None of these propagates NULL from its operands under SQL three-valued logic:

- `NULL OR TRUE` = `TRUE`
- `NULL AND FALSE` = `FALSE`
- `COALESCE(NULL, 5)` = `5`

So the operand lands in the set, `DropNotNullChecks` deletes the `IS NOT NULL` conjunct, and the
query silently returns a non-NULL value on rows the original returned NULL for. There is no
exception and no diagnostic — only wrong data.

**Two manifestation families, one root cause.**

*(a) Boolean connectives written directly in the THEN branch.* `x.NullableBoolA.Value || x.BoolB`
compiles to SQL `OR`, whose operands are then walked.

*(b) Comparisons in the THEN branch — much wider blast radius.* The WHEN test is visited with
`preserveColumnNullabilityInformation: true` (`:511`), so its `IS NOT NULL` fact lands in
`_nonNullableColumns`; the THEN branch is then compiled under that fact (`:534`) and a comparison
comes out **as an AND/OR**:

- `A == B` → `A = B AND B IS NOT NULL`
- `A != B` → `A <> B OR B IS NULL`

Those synthesized top-level `AND`/`OR` nodes are walked by the same unconditional recursion, `A`
enters the operand set, and the guard is dropped — keeping a THEN branch whose shape is valid only
while the guard holds. This means the ordinary null-conditional comparison pattern
`x.Nullable != null ? (bool?)(x.Nullable == y) : null` is affected, not just boolean columns.

**Reproduction — base vs. head, identical LINQ over identical SQLite data.**

Base commit `051c33a79` was exported and built separately; both builds ran the same probes,
comparing each against LINQ-to-Objects. **Base: 0 mismatches on all 7 probes** (every one emits the
intact `CASE`). **Head: mismatches on 6 of 7.**

| Probe | Head SQL | Example row | Base | Head |
|---|---|---|---|---|
| A `nbA != null ? (bool?)(nbA.Value \|\| BoolB) : null` | `SELECT nbA OR BoolB` | nbA=NULL, BoolB=true | `null` | `True` |
| B `nbA != null ? (bool?)(nbA.Value && BoolB) : null` | `SELECT nbA AND BoolB` | nbA=NULL, BoolB=false | `null` | `False` |
| C `nsA != null ? (bool?)(nsA == nsB) : null` | `SELECT nsA = nsB AND nsB IS NOT NULL` | nsA=NULL, nsB=NULL | `null` | `False` |
| D `nsA != null ? (bool?)(nsA != nsB) : null` | `SELECT nsA <> nsB OR nsB IS NULL` | nsA=NULL, nsB=NULL | `null` | `True` |
| E `niA != null ? (bool?)(niA == niB) : null` | `SELECT niA = niB AND niB IS NOT NULL` | niA=NULL, niB=NULL | `null` | `False` |
| F *(control)* `niA != null ? niA + 1 : null` | `SELECT niA + 1` | — | OK | OK |
| G `Where(((nbA != null ? (bool?)(nbA.Value \|\| BoolB) : null) ?? false))` | `WHERE COALESCE(nbA OR BoolB, 0)` | — | 18 rows | **24 rows** |

Probe G is the worst case: the defect escapes the projection and changes the **result set** of a
`Where`, returning 6 rows that do not satisfy the predicate.

**Why the shipped tests do not catch it:** all five new `Is_not_null_optimizes_*` tests use THEN
branches that genuinely propagate NULL — arithmetic `+`, string `+`, `~`, `LEN`, `COALESCE`. None
has a boolean-valued THEN, and none puts a comparison in the THEN branch. Every one passes.

**Fix:** Gate the `SqlBinaryExpression` recursion on operators that genuinely propagate NULL from
both operands, and exclude the connectives:

```csharp
else if (expression is SqlBinaryExpression binary
    && binary.OperatorType is not (ExpressionType.AndAlso
        or ExpressionType.OrElse
        or ExpressionType.Coalesce)
    && !(binary.Type == typeof(bool)
        && binary.OperatorType is ExpressionType.And or ExpressionType.Or))
{
    NullPropagatedOperands(binary.Left, operands);
    NullPropagatedOperands(binary.Right, operands);
}
```

Notes on the exclusion list:

- **`AndAlso` / `OrElse` and boolean-typed `And` / `Or`** — the demonstrated failures. Bitwise
  `And`/`Or` on *integers* do propagate (`NULL | 1` is NULL), hence the `Type == typeof(bool)`
  qualifier rather than a blanket exclusion.
- **`Coalesce`** — not reachable through the in-box providers today, because
  `SqlExpressionFactory.Coalesce` (`SqlExpressionFactory.cs:485`) builds a `SqlFunctionExpression`
  for `COALESCE` with `argumentsPropagateNullability: [false, false]`, which the helper already
  refuses to descend into. It is still a legal `SqlBinaryExpression` operator that a third-party
  provider can hand-build, so excluding it costs nothing and closes the hole.
- **`ExclusiveOr`** — newly relevant after `051c33a79` (XOR-based `NOT` translation). `NULL ^ x` is
  NULL, so it propagates; keep recursing.

Beyond the operator gate, consider whether family (b) warrants a stronger guard: the THEN branch is
deliberately compiled into a form that is valid *only while the test holds*, and this optimization
deletes the test afterwards. The operator gate is sufficient for every shape reproduced here — with
`AndAlso`/`OrElse` excluded, probes C/D/E keep their `CASE` — but the coupling is worth a
deliberate decision rather than an accident, e.g. re-visiting `whenClause.Result` with
`_nonNullableColumns` / `_nullValueColumns` restored to their pre-test snapshot before deciding to
drop a check.

Whatever the fix, add regression tests with a **boolean-valued THEN** and with a **comparison in the
THEN**, in both projection and predicate position — the current test set cannot fail on either.
