### #1 🔴 Critical: `NullPropagatedOperands` treats `AndAlso`/`OrElse` as null-propagating, producing wrong query results and wrong row sets

| | |
|---|---|
| **File** | `src/EFCore.Relational/Query/SqlNullabilityProcessor.cs:626` |
| **Category** | correctness / silently-wrong-results |
| **Confidence** | 100 — **executed before/after against SQLite by the orchestrator** |
| **Found by** | adversarial-reviewer (Critical), broad-reviewer (Critical), quick-reviewer (Critical), dotnet-reviewer (Critical), design-reviewer (Critical), security-reviewer (High) |
| **Pre-existing** | no |

**Issue:**

```csharp
else if (expression is SqlBinaryExpression binary)
{
    NullPropagatedOperands(binary.Left, operands);
    NullPropagatedOperands(binary.Right, operands);
}
```

This recurses into **every** `SqlBinaryExpression` operator with no filter. `SqlBinaryExpression.IsValidOperator` (`src/EFCore.Relational/Query/SqlExpressions/SqlBinaryExpression.cs:83-107`) admits `AndAlso` and `OrElse` alongside the arithmetic and comparison operators, and under SQL three-valued logic neither propagates NULL:

- `NULL OR TRUE = TRUE`
- `NULL AND FALSE = FALSE`

The optimization is sound only when `result` is guaranteed NULL whenever the checked operand is NULL. For an operand reachable only *through* a logical connective that guarantee fails, so `DropNotNullChecks` (line 597) deletes a guard that was load-bearing, and `VisitCase` returns `clause.Result` bare (line 587).

It is reachable because `SearchConditionConvertingExpressionVisitor` — which wraps boolean expressions into `CASE WHEN … THEN CAST(1 AS bit)` — runs **after** `SqlNullabilityProcessor` (`src/EFCore.SqlServer/Query/Internal/SqlServerParameterBasedSqlProcessor.cs:41-45`). At the time `VisitCase` runs, a boolean-valued CASE result is still a raw `AndAlso`/`OrElse` node.

**Executed evidence.** I built `src/EFCore.Sqlite` at both commits and ran identical queries through each (scratch app under `/tmp`; no tracked file was touched, tree verified clean afterwards). Rows: `{Id=1, NullableIntA=null, NullableIntB=null, BoolA=true}`, `{Id=2, NullableIntA=5, NullableIntB=5, BoolA=false}`, `{Id=3, NullableIntA=null, NullableIntB=7, BoolA=true}`.

**A — `OrElse` result:** `Select(x => x.NullableIntA != null ? (bool?)(x.NullableIntA > 1 || x.BoolA) : null)`

| | SQL | result |
|---|---|---|
| parent `051c33a79` | `CASE WHEN "e"."NullableIntA" IS NOT NULL THEN "e"."NullableIntA" > 1 OR "e"."BoolA" ELSE NULL END` | `null, True, null` ✅ |
| this change | `SELECT "e"."NullableIntA" > 1 OR "e"."BoolA"` | **`True, True, True`** ❌ |
| LINQ-to-Objects (truth) | — | `null, True, null` |

**B — equality result, where EF injects the `AndAlso` itself** (no `&&` in the user's LINQ): `Select(x => x.NullableIntA != null ? (bool?)(x.NullableIntA == x.NullableIntB) : null)`

| | SQL | result |
|---|---|---|
| parent | `CASE WHEN "e"."NullableIntA" IS NOT NULL THEN "e"."NullableIntA" = "e"."NullableIntB" AND "e"."NullableIntB" IS NOT NULL ELSE NULL END` | `null, True, null` ✅ |
| this change | `SELECT "e"."NullableIntA" = "e"."NullableIntB" AND "e"."NullableIntB" IS NOT NULL` | **`False, True, null`** ❌ |

**D — wrong row set, not merely a wrong projected value:** `Where(x => (x.NullableIntA != null ? (bool?)(x.NullableIntA > 1 || x.BoolA) : null) == true)`

| | predicate | rows |
|---|---|---|
| parent | `WHERE CASE WHEN … IS NOT NULL THEN … ELSE NULL END` | **1** (Id 2) ✅ |
| this change | `WHERE "e"."NullableIntA" > 1 OR "e"."BoolA"` | **3** (Ids 1,2,3) ❌ |

**C — control:** an arithmetic result (`x.NullableIntA != null ? x.NullableIntA + 1 : null`) is optimized correctly on both commits — the optimization's intended cases work; only the operator filter is missing.

Scenario B matters most for blast radius: the user writes no boolean operator at all. EF's own `RewriteNullSemantics` (`SqlNullabilityProcessor.cs:1879-1891`) injects the `AndAlso`/`OrElse`, so any `==`/`!=` comparison inside a null-guarded conditional is exposed.

**[Inference]** On SQL Server the outcome is worse rather than better: because `SearchConditionConvertingExpressionVisitor` runs afterwards, the bare condition becomes `CASE WHEN <cond> THEN CAST(1 AS bit) ELSE CAST(0 AS bit) END`, a total function — so the value materialized into `bool?` is `true`/`false` and NULL becomes unrepresentable. Not executed (no SQL Server instance available); the pipeline ordering is verified from source.

**Fix:** replace the unconditional recursion with an **allow-list** of genuinely null-propagating operators, so any operator added to `IsValidOperator` later fails closed:

```csharp
else if (expression is SqlBinaryExpression
    {
        OperatorType: ExpressionType.Add or ExpressionType.Subtract or ExpressionType.Multiply
            or ExpressionType.Divide or ExpressionType.Modulo
            or ExpressionType.And or ExpressionType.Or or ExpressionType.ExclusiveOr
            or ExpressionType.Equal or ExpressionType.NotEqual
            or ExpressionType.LessThan or ExpressionType.LessThanOrEqual
            or ExpressionType.GreaterThan or ExpressionType.GreaterThanOrEqual
    } binary)
```

`ExpressionType.Coalesce` is excluded by construction under an allow-list, which also closes the latent hole below. A deny-list (`is not (AndAlso or OrElse or Coalesce)`) fixes today's defect but reopens on the next operator added — the sibling unary arm at line 621 is already written as an allow-list, so this also restores internal symmetry.

**Latent, same fix:** `SqlBinaryExpression` also permits `ExpressionType.Coalesce` (`SqlBinaryExpression.cs:102`) and `ISqlExpressionFactory.MakeBinary` will construct it. `COALESCE(NULL, x) = x` does not propagate NULL. No in-box code builds that node today — `SqlExpressionFactory.Coalesce` (`SqlExpressionFactory.cs:502-509`) emits a `SqlFunctionExpression` with `argumentsPropagateNullability: [false, false]`, which the function branch handles correctly — but a provider or precompiled-query path could.

### #3 🟠 High: The soundness invariant the whole optimization rests on is written nowhere

| | |
|---|---|
| **File** | `src/EFCore.Relational/Query/SqlNullabilityProcessor.cs:576-577`, `:617-649` |
| **Category** | knowledge-preservation |
| **Confidence** | 100 |
| **Found by** | knowledge-reviewer (MUST), broad-reviewer (High) |
| **Pre-existing** | no |

**Issue:** The only documentation is `// optimize expressions such as expr != null ? expr : null` — which describes the trivial `result == x` case, not the general case the code implements (`x` nested arbitrarily deep inside `result`). The invariant is never stated:

> `NullPropagatedOperands(result)` must contain only sub-expressions `x` for which `x IS NULL ⇒ result IS NULL` under the target database's three-valued logic.

Three consequences of the omission are visible in the code itself:

1. The `SqlUnaryExpression` arm admits exactly `Not`/`Negate`/`Convert` and silently excludes `Equal`/`NotEqual` — the only other members of `SqlUnaryExpression.AllowedOperators`. That exclusion is **load-bearing** (`x IS NULL` never evaluates to NULL) and unexplained.
2. `SqlBinaryExpression` is recursed unconditionally while `SqlFunctionExpression` is carefully gated on `IsNullable` / `InstancePropagatesNullability` / `ArgumentsPropagateNullability`. Nothing says whether the author verified all 17 binary operators and judged the reachable subset safe, or simply did not consider the boolean ones. Finding #1 is what that unexplained asymmetry already cost.
3. The in-code `// TODO: optimize expr == null ? null : expr` explicitly invites a future contributor to extend this traversal — with no stated rule to check a new node kind against.

The failure mode is not a crash or a compile error. It is silently wrong rows, invisible in the SQL baselines and invisible to a positive-only suite.

**Fix:** state the invariant above `NullPropagatedOperands` (line 617), name the excluded operators and why (`NULL AND FALSE = FALSE`, `NULL OR TRUE = TRUE`, `COALESCE(NULL, x) = x`, `IS NULL` never yields NULL), and note that unhandled node kinds are safe because they only forgo optimization.

### #5 🟡 Medium: `HashSet<SqlExpression>` makes structural equality load-bearing for a correctness decision, and the base `Equals` is over-inclusive

| | |
|---|---|
| **File** | `src/EFCore.Relational/Query/SqlNullabilityProcessor.cs:580` (set), `:598` (`Contains`) |
| **Category** | type-safety |
| **Confidence** | 75 — confirmed by validator; latent (no in-box trigger) |
| **Found by** | dotnet-reviewer (Medium) — **unique** |
| **Pre-existing** | no |

**Issue:** The decision to **delete a null check** now hinges on `HashSet<SqlExpression>.Contains`. `SqlExpression.Equals`/`GetHashCode` (`src/EFCore.Relational/Query/SqlExpressions/SqlExpression.cs:61-74`) compare only `Type` and `TypeMapping`, with **no runtime-type check** — `HashCode.Combine(Type, TypeMapping)`. Every in-box subclass overrides both with a runtime-type gate (the validator checked all 44 in `EFCore.Relational` plus the provider-specific ones — zero exceptions), but `SqlExpression` is a public extensibility point and nothing enforces the override, unlike `VisitChildren`, which throws `RelationalStrings.VisitChildrenMustBeOverridden` if omitted.

**Failure scenario:** a provider defines `class MyFuncExpression : SqlExpression` without overriding `Equals`/`GetHashCode`. For `CASE WHEN MyFunc(a) IS NOT NULL THEN MyOtherFunc(b) ELSE NULL END`, `Contains(MyFunc(a))` returns true — both are the same CLR `Type` with the same `TypeMapping` — the guard is dropped, and the query returns a value where NULL was required.

**The failure direction is two-way, not one-way.** The validator specifically adjudicated the counter-claim (raised independently by adversarial-reviewer and design-reviewer) that any equality mismatch can only cost a *missed* optimization: `HashSet<T>.Contains` invokes `comparer.Equals(storedElement, probe)`, i.e. it dispatches on the **stored** node — which comes from `clause.Result`. When that stored node is the non-overriding provider type, the base `Equals` is *weaker* than any override, so the miss goes toward a **false positive**, which is the unsound direction.

**Fix:** pass a comparer that requires `GetType()` equality, or add a `Check.DebugAssert` plus a comment recording that this set relies on every reachable node type overriding structural equality. Note that `ReferenceEqualityComparer` is **not** a safe substitute here — see #9.

### #7 🟢 Low: `IsNull(elseResult)` misses the absent-`ELSE` form, so identical semantics optimize inconsistently

**Issue:** `IsNull` (line 1633) matches only a null `SqlConstantExpression` or a null-valued `SqlParameterExpression`. **⚠️ Ordering matters:** this widens the set of expressions the optimization fires on, and therefore widens the blast radius of #1. **Land the allow-list fix from #1 first.**

### #8 🟢 Low: `func.Instance!` is a null-forgiving dereference of an invariant the type system does not enforce

| | |
|---|---|
| **File** | `src/EFCore.Relational/Query/SqlNullabilityProcessor.cs:633-636` |

### #9 🟢 Low: The result subtree is walked and structurally hashed unconditionally, before anything checks the test

| | |
|---|---|
| **File** | `src/EFCore.Relational/Query/SqlNullabilityProcessor.cs:580-583` |
| **Category** | efficiency |
| **Confidence** | 75 — confirmed by validator; severity corrected down from Medium |
| **Found by** | performance-reviewer (Low), broad-reviewer (Medium), security-reviewer (Low) |
| **Pre-existing** | no |

**Issue:** Two compounding costs on the query-compilation path.

1. **No early-out.** `NullPropagatedOperands(clause.Result, …)` (line 582) walks the entire THEN subtree before `DropNotNullChecks` (line 583) looks at whether the test contains a single `IS NOT NULL`. For a qualifying CASE whose test is not a null check — `x.BoolA ? someExpr : null` — 100% of the walk is discarded.
2. **Hashing is recursive and uncached.** Verified directly: `SqlBinaryExpression.GetHashCode` (line 172-173) = `HashCode.Combine(base.GetHashCode(), OperatorType, Left, Right)`; `ColumnExpression.GetHashCode` (line 108-109) = `HashCode.Combine(base.GetHashCode(), Name, TableAlias, IsNullable)`. Neither memoizes. Hashing a node therefore costs O(its subtree), so inserting all *n* nodes costs Θ(Σ subtree sizes) — Θ(n log n) balanced, Θ(n²) for the left-deep chains that string-concat and arithmetic chains produce. `Contains` at line 598 re-hashes on top.

Mitigating: this is per distinct query shape at compile time, not per row, and realistic result expressions in this pattern are small. Hence Low, not Medium.

**Fix (validator-adjudicated):** scan the test's `AndAlso` spine first for any `SqlUnaryExpression { OperatorType: NotEqual }`; if there is none, skip the result walk entirely. **Do not** "fix" this by swapping in `ReferenceEqualityComparer` — this file's own convention is structural matching (`_nonNullableColumns` is a `List<ColumnExpression>` relying on structural `Equals` at lines 677, 1657, 2280), because the same logical column appears as structurally-equal-but-distinct instances on the test side and the result side. Reference identity would silently disable the optimization.

### #10 🟢 Low: The analysis is unreachable to providers — `static` local functions inside a `protected virtual` method

| | |
|---|---|
| **File** | `src/EFCore.Relational/Query/SqlNullabilityProcessor.cs:595`, `:617` |
| **Category** | evolution-readiness |
| **Confidence** | 75 — confirmed by validator; severity corrected down from High |
| **Found by** | design-reviewer (High) — **unique** |

**Issue:** `SqlNullabilityProcessor` is a provider extension point, and every other dialect- or provider-variant decision in it is `protected virtual` — `VisitCustomSqlExpression` (466), `PreferExistsToInWithCoalesce` (1629), `OptimizeNonNullableNotExpression` (1966), `TryMakeNonNullable` (2120), `IsCollectionTable` (2226). `SqlServerSqlNullabilityProcessor` actively overrides four of them. **Why Low rather than High (validator's adjudication, which I accept):**

For the base pattern `x IS NOT NULL ? x : NULL` that leaf membership is a tautological identity, so it is sound for any node type.
- The "cannot suppress it" half is speculative. There is no `CONCAT_NULL_YIELDS_NULL` handling anywhere in `src/`, and `AddNullConcatenationProtection` — itself a non-virtual local function nested in `VisitSqlBinary` (line ~1438) — already applies unconditionally regardless of provider. Non-overridable null-semantics helpers are pre-existing convention in this file, not a deviation this change introduces.

**Issue:** `DropNotNullChecks` returns `SqlExpression?` where `null` inverts the conventional reading — everywhere else in this file a nullable `SqlExpression?` means "absent" (`operand`, `elseResult` in this very method). Here it means "everything was dropped; the remaining condition is TRUE". The only signal is `return null; // true` at line 600, which is not where the decisions are made:

- the caller's `if (test is null) { return clause.Result; }` reads as "there is no test, so discard";
- `left is null ? right : right is null ? left : binary.Update(left, right)` reads as "skip the missing side" rather than "`TRUE AND y ≡ y`".

**Failure mode:** a maintainer extending the folding to `OrElse` — where the same sentinel would have to mean *absorbing* TRUE, i.e. drop the whole condition rather than keep the other side — will carry over the wrong reading and produce a predicate that matches every row.

**Fix:** document the contract above line 595 (`…or null when nothing is left, meaning the test has become unconditionally TRUE — not "no test"`), or return `_sqlExpressionFactory.Constant(true)` and let the existing `IsTrue` path collapse it.

## Specialist Notes

### Threat Model Notes (security-reviewer)

- **Trust boundary**: LINQ→SQL compilation. No untrusted-byte parsing; input is a developer-authored expression tree. The security-relevant property is **semantic equivalence of the rewrite** — the query compiler is the enforcement point for every row filter an application expresses, including tenancy and ownership predicates.
- **Data sensitivity**: indirect but real. An application whose authorization filter is written as `x.SomeNullable != null ? <boolean> : (bool?)null` gets a predicate admitting extra rows — the executed scenario D above returns 3 rows where the parent returns 1. Rated High rather than Critical on the security lane because it requires that specific tri-state filter idiom, which could not be established as common.
- **Verified clean**: query-cache reuse across differing parameter nullability. `RelationalCommandCache.CommandCacheKey.Equals` (`src/EFCore.Relational/Query/Internal/RelationalCommandCache.cs:121-152`) compares `(value == null) != (otherValue == null)` per parameter, so a plan compiled with a null parameter is never reused for a non-null one. The comment at line 1632 is accurate and `IsNull(elseResult)`'s parameter-value dependence introduces no new assumption.
- **Verified out of scope**: SQL injection — no line in the diff concatenates non-constant text.

### Considered But Not Flagged

**Refuted by the validation wave:**

- **`COALESCE` produces wrong results via `x.NullableIntA != null ? (x.NullableIntA ?? 0) : null`** (quick-reviewer, Critical) — **refuted, empirically**. `??` routes through `SqlExpressionFactory.Coalesce` (`SqlExpressionFactory.cs:485-511`), which builds a `SqlFunctionExpression` with `argumentsPropagateNullability: [false, false]` — never a `SqlBinaryExpression`. The function branch at line 631 correctly declines to descend. The validator compiled and ran the exact query against this commit's assemblies: `CASE WHEN "e"."NullableIntA" IS NOT NULL THEN COALESCE("e"."NullableIntA", 0) ELSE NULL END`, returning NULL (not 0), matching LINQ-to-Objects exactly. quick-reviewer correctly traced `??` to `SqlExpressionFactory.Coalesce` but mis-concluded what that method returns. The *latent* binary-`Coalesce` observation survives and is folded into #1's allow-list fix.
- **`out bool nullable` is stale / `return clause.Result` erases the CASE's Type and TypeMapping** (design-reviewer Low, broad-reviewer Low) — **refuted, both sub-claims**. (a) `nullable` is unconditionally `true` on that path, but that is *accurate*, not conservative padding: whenever the branch fires, `clause.Result` genuinely evaluates to NULL exactly when the dropped guard would have been false. (b) `CaseExpression.Type`/`TypeMapping` are derived from `whenClauses[0].Result` at construction (`CaseExpression.cs:33,48`), and `RelationalSqlTranslatingExpressionVisitor.VisitConditional` (615-625) builds the CASE straight from the translated `ifTrue` branch — so in the cited `Null_propagation_optimization5` baseline `caseExpression.Type` was *already* `int`. No erasure occurs. The one theoretical mismatch (a multi-clause CASE whose first clause is pruned) exists unchanged at the pre-existing early return on line 547.

**Analyzed and dismissed by reviewers:**

- **Unary operator allow-list `Not`/`Negate`/`Convert`** — sound. `NOT NULL`, `~NULL`, `-NULL`, `CAST(NULL AS t)` are all NULL. Critically, `Equal`/`NotEqual` (`IS NULL`/`IS NOT NULL`) are correctly excluded; recursing into them would be unsound.
- **`func.ArgumentsPropagateNullability[i]` / `func.Arguments[i]` index mismatch** — not reachable. The `SqlFunctionExpression` constructor throws `InconsistentNumberOfArguments` when the counts differ (`SqlFunctionExpression.cs:217-226`), and `[MemberNotNullWhen(false, …)]` on `IsNiladic` makes both dereferences provably safe (0-warning build confirms).
- **Unbounded recursion depth / stack overflow on compile** — not change-introduced. `SqlNullabilityProcessor.Visit` and every other visitor in the pipeline already recurse over the same tree at equal or greater depth, and the new helpers run *after* that visit has succeeded. Attributing an EF-wide property to this diff would be wrong.
- **Unhandled node kinds** (`CaseExpression`, `CollateExpression`, `AtTimeZoneExpression`, `JsonScalarExpression`, `LikeExpression`, `InExpression`, `ExistsExpression`, `ScalarSubqueryExpression`, provider-custom) — the fallthrough adds only the node itself, which is trivially null-propagating to itself. Missed optimizations, not defects. `LikeExpression` in particular *must* stay excluded: `VisitLike` gives LIKE false-on-null semantics.
- **`DropNotNullChecks` descends only `AndAlso`, not `OrElse`, in the test** — conservative and correct. Verified by execution: `(x.NullableIntA != null || x.BoolB) ? … : null` retains the whole CASE.
- **Aggregates** (`SUM`, `MAX`) — relational aggregate translators pass `argumentsPropagateNullability: [false]`, correctly blocking the "SUM over a NULL row ⟹ SUM is NULL" fallacy. `SqlServerAggregateFunctionExpression` derives from `SqlExpression`, not `SqlFunctionExpression`, so it falls to the conservative default.
- **`static` local functions declared after the `return`** — matches this file's convention (`TryNegate`, line 2095). Style, no defect.
- **`// TODO:` with no issue number** — 41 of 55 TODOs in `src/EFCore.Relational` carry no issue reference. Consistent with the repo; flagging it would be inventing a standard.
- **Missing release-note / breaking-change entry** — this repo has no in-repo release-notes artifact (conceptual docs live in `dotnet/EntityFramework.Docs`). No standard to violate.
- **Baseline symmetry** — a repo-wide grep for remaining `CASE WHEN X IS NOT NULL THEN <expr containing X> ELSE NULL END` baselines that should also have simplified found only shapes where the tested operand differs from the result expression (e.g. `WHEN [t1].[Exists] IS NOT NULL THEN [t1].[Id]`). No missed baseline updates.
