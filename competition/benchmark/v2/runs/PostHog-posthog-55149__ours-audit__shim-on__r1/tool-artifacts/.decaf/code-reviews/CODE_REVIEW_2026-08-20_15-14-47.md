### #1 🔴 Critical: Two of the three new evaluation-override capabilities reach the public `/flags` endpoint with no authorization gate

| | |
|---|---|
| **File** | `rust/feature-flags/src/handler/mod.rs:196`, `:218-223` |
| **Category** | security |
| **Confidence** | 100 |
| **Found by** | quick-reviewer (High), broad-reviewer (Critical), knowledge-reviewer (MUST), consistency-reviewer (High), design-reviewer (High), security-reviewer (High), adversarial-reviewer (High), rust-reviewer (High) |

**Issue:** The change introduces three new evaluation-shaping inputs and gates exactly one of them:

```rust
// mod.rs:196 — override_flags_definitions: no check at all
request.override_flags_definitions.as_ref(),
...
// mod.rs:218 — detailed_analysis IS gated
if context.meta.detailed_analysis.unwrap_or(false) && authentication::is_internal_request(&context) {
    Some(true)
} else {
    Some(false)
},
context.meta.only_use_override_person_properties,   // mod.rs:223 — NOT gated
```

`/flags` is authenticated by the *public* project API token, which is embedded in every page that loads a PostHog SDK. So any anonymous holder of that token can:

- **Substitute an arbitrary flag definition** for any key. `flags.rs:172` does `*flag = override_flag;`, replacing the whole struct — `id`, `team_id`, `key`, `filters`, `ensure_experience_continuity`, variants — not just the evaluation-relevant fields (see #20 for what the identity replacement enables downstream).
- **Force `skip_writes = true`** for any distinct_id by setting `only_use_override_person_properties=true` (`flags.rs:336-338`), suppressing experience-continuity hash-key persistence for that evaluation.
- **Discard all server-side person properties**, which does more than shadow them — negated predicates (`is_not_set`, `is_not`, "not in cohort X") that normally fail against real DB values can be made to pass.

The asymmetry is itself the strongest evidence: the same change establishes that an internal-only boundary is required here and then applies it to one input of three. Whether the other two are deliberately self-serve or an oversight cannot be determined from the code, and both readings lead to a wrong future edit.

**Fix:** Compute the gate once and apply it to all three, rejecting rather than silently ignoring the fields on a non-internal request so misuse is visible:

```rust
let is_internal = authentication::is_internal_request(&context);
let filtered_flags = flags::fetch_and_filter(
    …,
    if is_internal { request.override_flags_definitions.as_ref() } else { None },
).await?;
…
if is_internal { context.meta.only_use_override_person_properties } else { Some(false) },
```

Better still, move override-bearing evaluation off the public `/flags` route onto a separately-routed internal endpoint that is not reachable from the edge.

### #2 🔴 Critical: `only_use_override_person_properties` skips cohort and group state loading, so cohort-targeted flags silently evaluate as "no match"

| | |
|---|---|
| **File** | `rust/feature-flags/src/flags/flag_matching.rs:827` |
| **Category** | correctness |
| **Confidence** | 100 |
| **Found by** | broad-reviewer (Critical), design-reviewer (High), adversarial-reviewer (High), rust-reviewer (High), security-reviewer (Medium) |

**Issue:** The mode is documented as "ignore database person properties", but it short-circuits the entire DB preparation step:

```rust
if flags_requiring_db_preparation.is_empty() || self.only_use_override_person_properties {
    self.flag_evaluation_state.skip_person_properties();
    return false;
}
```

`prepare_flag_evaluation_state` (`flag_matching.rs:1997-2057`) is the *only* place that calls `set_cohorts`, loads static-cohort membership, initializes group type mappings, and prepares group properties. Verified: with it skipped, `flag_evaluation_state.cohorts` stays `None`, and `flag_matching.rs:1592-1594` then returns unconditionally:

```rust
let cohorts = match &self.flag_evaluation_state.cohorts {
    Some(cohorts) => cohorts.clone(),
    None => return Ok((false, FeatureFlagMatchReason::NoConditionMatch)),
};
```

`test_evaluation` always sets `only_use_override_person_properties = timestamp is not None` (`feature_flag.py:3545`), so **every** historical evaluation of a cohort- or group-targeted flag returns `false` / `no_condition_match` — regardless of actual membership, with no error flag on the response. The endpoint reports a confident wrong answer for exactly the flags whose history is hardest to reason about by hand.

**Fix:** Narrow the skip to person properties only. Keep calling `prepare_flag_evaluation_state` and suppress only the person-property fetch — the correct behavior already exists at `flag_matching.rs:1696`, where `get_person_properties` starts from an empty map in this mode. If cohort/group state genuinely cannot be reconstructed historically, the endpoint must say so per-condition rather than returning a false negative.

### #5 🟠 High: A rejected override fails open — the present-day definition is returned as the historical answer

| | |
|---|---|
| **File** | `rust/feature-flags/src/handler/flags.rs:172-183`, `posthog/api/feature_flag.py:3533-3537` |
| **Category** | error-handling |
| **Confidence** | 100 |
| **Found by** | knowledge-reviewer (MUST), design-reviewer (Critical), adversarial-reviewer (Medium), rust-reviewer (High) |

**Issue:** Both halves of the override path fail open, and the resulting response is byte-identical to a successful historical evaluation.

- Rust: a `serde_json::from_value::<FeatureFlag>` failure only emits `tracing::warn!` and leaves the database flag in place. Evaluation proceeds against today's definition.
- Python: if `model_to_dict` raises, `override_definitions = None` and the request proceeds anyway.

Nothing in the response distinguishes "reconstructed" from "fell back to current" — there is no `is_historical` marker on the wire, and `flags_overridden` in the canonical log is the only signal, which no consumer of the endpoint reads.

**Failure scenario:** A user asks how a flag evaluated on a past date, the definition has since changed, and the endpoint confidently answers with today's definition applied to that date's person properties. The wrong answer is indistinguishable from a correct one, so the error is never detected.

**Fix:** Return `Err(FlagError::RequestParsingError(...))` at `flags.rs:176-183` when a supplied override cannot be applied, and return a 500 rather than `override_definitions = None` at `feature_flag.py:3533-3537`. Additionally surface the reconstructed version and `is_historical` on the response so the caller can see what was actually evaluated.

### #6 🟠 High: `build_condition_analysis` runs cohort, group, and flag-dependency filters through person-property matching

| | |
|---|---|
| **File** | `rust/feature-flags/src/api/types.rs:603-607` |
| **Category** | correctness |
| **Confidence** | 100 |
| **Found by** | broad-reviewer (High), knowledge-reviewer (SHOULD), design-reviewer (Medium), adversarial-reviewer (High), rust-reviewer (High) |

**Issue:** Every property in a group is matched against the merged **person** property map, regardless of `prop_type`:

```rust
let (property_matched, actual_value) = if let Some(props) = property_values {
    let actual = props.get(&property.key).cloned();
    let matched = match_property(property, props, false).unwrap_or(false);
    (matched, actual)
```

The real matcher routes `PropertyType::Cohort` through `evaluate_cohort_filters` (`flag_matching.rs:1591-1598`), group filters through the group property map, and `PropertyType::Flag` through the dependency result map. None of those keys exists in the person map, so all such filters report `matched: false`. The `.unwrap_or(false)` additionally converts a genuine `FlagMatchingError` into a confident "did not match".

**Failure scenario:** A flag whose only condition is a cohort filter matches. The response says `enabled: true`, `reason: "condition_match"` — and the analysis says *"Condition 0 did not match properties"*, with a fabricated per-property explanation. The analysis contradicts the result it exists to explain, and a reader has no way to tell which field is authoritative.

**Fix:** Branch on `property.prop_type`. Run `match_property` only for `PropertyType::Person`; for cohort, group, and flag-dependency filters emit an explicit not-analyzed state, and exclude them from the `all_properties_matched` fold at `types.rs:661-666` so they cannot corrupt the condition-level verdict.

### #7 🟠 High: `rollout_excluded` can only ever be true for a 0% rollout, and the fallthrough explanation is false

| | |
|---|---|
| **File** | `rust/feature-flags/src/api/types.rs:652`, `:675-694` |
| **Category** | correctness |
| **Confidence** | 100 |
| **Found by** | broad-reviewer (High), knowledge-reviewer (MUST), design-reviewer (High), rust-reviewer (Medium) |

**Issue:** `is_zero_rollout = rollout_percentage == 0.0` is a required conjunct in **both** arms of the `this_condition_rollout_excluded` computation. The central case the field exists to explain — properties matched, user hashed outside a partial rollout — never sets it.

```rust
let this_condition_rollout_excluded = properties_matched_but_rollout_failed

    && flag_match.condition_index.map_or(true, |i| index == i);
```

Drop `is_zero_rollout` from the decision, keeping it only to specialize the explanation string.

### #8 🟠 High: The person-existence gate and the property replay use different event predicates

| | |
|---|---|
| **File** | `posthog/api/feature_flag.py:3439`; `posthog/models/person/point_in_time_properties.py:227-272` |
| **Category** | correctness |
| **Confidence** | 100 (validator-confirmed) |
| **Found by** | adversarial-reviewer (sole finder) |

**Issue:** `person_existed_at_timestamp` matches **any** event (`WHERE team_id … AND distinct_id IN … AND timestamp <= …`, no event or property filter). `build_person_properties_at_time` selects only rows satisfying `event = '$set' OR event = '$set_once' OR JSONHas(properties, '$set')`. A person whose only pre-timestamp events carry no `$set` payload therefore passes the gate, and the replay returns `{}`.

The empty dict is then passed straight through with `only_use_override_person_properties=true`, which (verified at `flag_matching.rs:1696`) fully replaces DB properties rather than shadowing them. Every property condition fails and the endpoint reports the flag as historically off. There is no warning; the caller can only infer it from an empty `person_properties` field in the response body.

**Fix:** Distinguish "no property-bearing events found" from "person genuinely had no properties" — gate on the same predicate as the replay, or return an explicit warning field on the response when the replay produced zero properties.

### #9 🟠 High: `INTERNAL_REQUEST_TOKEN` is an undocumented cross-service precondition whose absence silently empties the response

| | |
|---|---|
| **File** | `posthog/api/feature_flag.py:3547`; `rust/feature-flags/src/config.rs:609-612`; `rust/feature-flags/src/handler/mod.rs:218` |

## Specialist Notes

### Threat Model Notes (security-reviewer)

- **Trust boundaries crossed.** (1) Public internet → Rust `/flags`, authenticated solely by the *public* project token, which now accepts three new evaluation-semantics inputs, only one of which is gated. (2) Authenticated PostHog API (personal/project keys with scopes) → the new Django action, which reaches ClickHouse event data and the activity log. (3) Django → Rust flags service, now carrying a privileged shared bearer credential.
- **Data sensitivity.** Person properties (emails, identifiers, arbitrary customer-set attributes) now flow out through a `feature_flag`-scoped endpoint, including historical reconstructions no other API surface exposes. Flag targeting definitions — which frequently embed customer identifiers — now reach INFO-level logs.
- **Attack-surface delta.** One new authenticated HTTP endpoint (unthrottled, two unbounded ClickHouse queries), three new request-controlled evaluation switches on an existing public endpoint, and one new global service credential.
- **Assumptions.** That `/flags` is reachable with a public, client-embedded project token; that no reverse proxy strips `override_flags_definitions` or the `only_use_override_person_properties` query parameter; that `FEATURE_FLAGS_SERVICE_URL` is not necessarily loopback in production. If any is false in a given deployment, the corresponding finding's severity drops but its structural validity does not.
- **Load-bearing defect.** The gating asymmetry at `mod.rs:218` versus `:196`/`:223`. Everything downstream — self-granted flag results, dependency-map poisoning, write-path triggering, log amplification — follows from that single omission.

## Residual Risks

- **Property reconstruction fidelity is not characterized anywhere.** `build_person_properties_at_time` replays `$set` and (partially — see #17) `$set_once`. It ignores `$unset`, person-API property writes, identify merges, and property deletions, and truncates the timestamp to whole seconds. Historical flag evaluation is only as accurate as this reconstruction, and nothing in the response tells the caller how approximate it is.
- **`find_version_at_timestamp` answers from at most the 10,000 most recent activity-log entries** at or before the timestamp. A soft-delete older than that window is invisible and the flag is reported as existing. Undocumented and untested.
- **`person_existed_at_timestamp` defines "existed" as "has ≥1 event at or before T"** over the `events` table. Under event TTL or retention, an old-but-real person yields a 400 telling the user the timestamp "may be too far in the past". The retention dependency is stated nowhere.
- **`skip_writes` forced on for analysis requests is a load-bearing interlock with no comment.** A maintainer simplifying `detailed_analysis.unwrap_or(false) || only_use_override_person_properties.unwrap_or(false) || *state.config.skip_writes` — it reads as redundant defensiveness — would reintroduce silent, irreversible variant reassignment for real users.
