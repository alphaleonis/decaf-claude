## Findings

### #1 🟠 High: One invalid nested `extra_response` now discards the valid main response and every valid sibling

| | |
|---|---|
| **File** | `server/public/model/command_response.go:90` |
| **Category** | resilience / error-handling |
| **Confidence** | 100 |
| **Found by** | design-reviewer (High), adversarial-reviewer (High) — screen 70, validator: confirmed |

**Issue:** `IsValid()` recurses into `ExtraResponses` and returns on the **first** nested failure, and `CommandResponseFromJSON` then returns `(nil, err)` for the whole payload. The consumer of that payload does the opposite: `HandleCommandResponse` (`server/channels/app/command.go:605-631`) posts the main response and then each extra response **independently**, tracking only `lastError`, so one bad entry never stopped the others.

The result is that a single malformed `extra_responses[1]` now destroys the valid main response and every valid sibling before any of them reach that loop, and `server/channels/app/command.go:597` turns it into an HTTP 500 (`api.command.execute_command.failed.app_error`). Before this change, `CreateCommandPost` (`command.go:73` and `:82`) silently skipped only the entry whose `response_type` matched neither branch, while everything else still posted.

The change's own new test demonstrates exactly this: a valid `in_channel` main response plus one nested `{"response_type": "invalid_nested_type"}` yields a nil response for the entire payload.

Note the counter-argument was weighed and does not dispose of the finding: trading a silent drop for a loud error is defensible on its own, but the claim here is that the **valid parts are now lost too**, and that holds.

**Fix:** Validate per-response at the point of use rather than aborting the parse — let parsing succeed and have `HandleCommandResponse` call `resp.IsValid()` per entry, logging and skipping invalid children while still posting the valid main response and valid siblings. If parse-time rejection really is intended, at minimum aggregate all child errors rather than returning on the first.

### #2 🟠 High: `Client4` now rejects command responses the server itself emits without validating

| | |
|---|---|
| **File** | `server/public/model/client4.go:5961` (and `:5982`), caused by `server/public/model/command_response.go:72-75` |
| **Category** | api-contract |
| **Confidence** | 100 |
| **Found by** | broad-reviewer (High), design-reviewer (High), adversarial-reviewer (High) — screen 60, validator: confirmed |

**Issue:** `CommandResponseFromJSON` sits on **both ends of a round trip**, but validation was added to only one of them.

Plugin commands construct `*model.CommandResponse` as a Go struct and reach `HandleCommandResponse` without ever passing through this parser (`server/channels/app/plugin_commands.go`). `server/channels/api4/command.go:427` then json-encodes that object with no validation and returns HTTP 200. `Client4.ExecuteCommand` / `ExecuteCommandWithTeam` re-parse that same body through the now-validating `CommandResponseFromJSON` and return `fmt.Errorf("failed to decode command response: %w", err)`. A slash command that fully executed server-side is reported as a failure to every Go consumer — mmctl, bots, integration tests, plugin authors.

The validator narrowed the reachable surface, which matters for sizing the fix:

- **`in_channel` is self-guarded** — that path runs `CreatePostMissingChannel` → `Post.IsValid`, so an oversized response already fails server-side and never reaches the encoder. Not a live instance.
- **`ephemeral` is not guarded** — `SendEphemeralPost` (`server/channels/app/post.go:692-734`) never calls `Post.IsValid`, so a plugin-authored ephemeral response with Text over 65535 bytes is returned as a 200 and rejected by the client.
- **Any `response_type` outside the set** — matches neither branch in `CreateCommandPost`, so no post is attempted and no error is raised, and the object is still encoded and returned.

Custom-command webhooks are *not* exposed: they already ingest through `CommandResponseFromJSON` and are validated on the way in. The exposure is specifically plugin-authored responses.

**Fix:** Make the two ends agree. Either validate on the producing side (in `HandleCommandResponse`, before api4 encodes) so the server cannot emit what its own client rejects, or keep the client parse lenient — the client is not the trust boundary this validation targets. A `CommandResponseFromJSON` variant that skips `IsValid()` for `Client4` is the smaller change.

[Unverified] The "a caller that retries re-executes a non-idempotent command" consequence was raised by the adversarial reviewer and explicitly **not** confirmed by the validator against actual mmctl/bot retry logic. Treat it as risk framing, not an established mechanism.

### #3 🟡 Medium: Hardcoded byte-based `65535` cap contradicts the configurable, rune-based limit enforced downstream

| | |
|---|---|
| **File** | `server/public/model/command_response.go:85-88` |
| **Category** | data-model / correctness |
| **Confidence** | 100 |
| **Found by** | broad, go, design, security, adversarial (5 finders; anchors High/Medium×4/Low) — screen 78, validator: confirmed, severity corrected High → Medium |

**Issue:** The new check is `maxLength := 65535; if len(o.Text) > maxLength` — byte count, hardcoded. The limit actually enforced on this same text is rune-based and DB-derived: `CreateCommandPost` copies `response.Text` into `post.Message` (`server/channels/app/command.go:56-59`), and `Post.IsValid` checks `utf8.RuneCountInString(o.Message) > maxPostSize` (`server/public/model/post.go:508`), where `maxPostSize = max(int(maxPostSizeBytes)/4, PostMessageMaxRunesV2)` (`server/channels/store/sqlstore/post_store.go:2658`), default 16383 runes.

Two consequences, and the validator separated them — this matters:

- **Too loose (not a regression).** Text between 16384 and 65535 bytes passes the new check and is still rejected downstream. It was rejected before this change too, so nothing got worse. This is a *coherence* defect — the new check gives false assurance about a limit it does not actually represent — not new breakage.
- **Too strict (a real regression).** `post_store.go:2641` states the `posts.message` column "may be manually enlarged to support longer posts". On such a deployment `maxPostSize` exceeds 65535 runes, and an ASCII response between 65,536 bytes and that limit **previously succeeded end-to-end** and now gets a hard rejection at parse time. Unlike incoming webhooks, the command path has no `splitWebhookPost` equivalent to fall back on. `MaxIntegrationResponseSize = 1024*1024` (`server/channels/app/webhook.go:31`) confirms responses well past 64 KB are inside the system's own anticipated envelope.

Severity was lowered from High to Medium because the only genuine regression requires a non-default, deliberately enlarged column.

The Slack-rewrite ordering sub-claim also holds but is minor: `ParseSlackLinksToMarkdown` runs *after* this validation, so the validated string is not the stored string — though the growth is a few bytes per link.

**Fix:** Do not enforce a post-length policy in the model parse layer, which has no access to the deployment's `maxPostSize`. Either drop the `Text` check and let the config-aware `Post.IsValid` own it, or move it to `HandleCommandResponsePost` / `CreateCommandPost` where `a.MaxPostSize()` is available and compare `utf8.RuneCountInString` against that value.

### #5 🟡 Medium: Content-Type, not content, decides whether the new validation applies

| | |
|---|---|
| **File** | `server/public/model/command_response.go:35-42` |
| **Category** | api-contract |
| **Confidence** | 100 |
| **Found by** | broad (Medium), design (Medium), security (High), adversarial (Medium) — screen 62, validator: confirmed, Medium sustained |

**Issue:** `CommandResponseFromHTTPBody` routes `application/json` to the now-validating `CommandResponseFromJSON` and every other content type to `CommandResponseFromPlainText`, which builds `&CommandResponse{Text: text}` and never calls `IsValid()`. The sender picks the Content-Type at both call sites — `server/channels/web/webhook.go:114` (unauthenticated `commandWebhook`, token in URL) and `server/channels/app/command.go:595`. So the identical oversized body is rejected as `application/json` and accepted as `text/plain`, and `IsValid()` is not an invariant of the type.

The asymmetry is **new**: before this change neither branch validated.

The validator narrowed the claim in two ways that keep it at Medium rather than High:

- The bypass reduces to the **Text-length rule alone** — the plaintext constructor can never set a `response_type`, and `""` already passes unconditionally.
- Because plaintext always yields `ResponseType == ""`, `CreateCommandPost` always routes it to `SendEphemeralPost`, which never persists a post. The harm is a transient, single-user, client-rendered oversized ephemeral message.

The bypass does admit materially more data: the plaintext path is bounded only by `MaximumPayloadSizeBytes` (default 300000) or `MaxIntegrationResponseSize` (1 MiB) — 4.6× to 16× the 65535-byte cap.

**Fix:** Apply the same check to both branches of `CommandResponseFromHTTPBody`, or move enforcement out of the parsers to the boundary where both branches converge. If the JSON-only scope is deliberate, say so in a comment at the `IsValid()` call site.

### #7 🟡 Medium: Validation is welded into the deserializer, against the package's prevailing separation

| | |
|---|---|
| **File** | `server/public/model/command_response.go:72-75` |
| **Category** | design / boundary |
| **Confidence** | 75 |
| **Found by** | consistency-reviewer (Medium), design-reviewer (Medium) — screen 45 |

**Issue:** `CommandResponseFromJSON` now calls `o.IsValid()` and rejects. A full sweep of every `*FromJSON` function in `server/public/model` found **no other case** of `IsValid` being called inside the parser: `IncomingWebhookRequestFromJSON` (`incoming_webhook.go:193-210`) and `ConfigFromJSON` (`config.go:4234`) both defer validation to the caller, and the one near-match, `websocket_client.go:257`, calls `IsValid` from the caller *after* `FromJSON` returns. The closest structural sibling — `OutgoingWebhookResponse` (`outgoing_webhook.go:69`), same `ResponseType`/`Text`/`Props` shape, same third-party-JSON trust boundary — has no `IsValid` at all, and its decode path (`server/channels/app/webhook.go:225-231`) does not validate.

Since `IsValid()` is exported and independently callable, the parse-time call adds no capability the app layer lacked, while removing the caller's ability to parse first and decide second — which is exactly what findings #1 and #2 need.

In fairness: there is a plausible justification for centralizing here, since two duplicate app-layer call sites (`command.go:595`, `web/webhook.go:114`) would otherwise each need the call.

**Fix:** Keep `IsValid()` exported but invoke it from the boundaries that own the policy — `DoCommandRequest` and `commandWebhook`, which can map the failure to an appropriate status — leaving `CommandResponseFromJSON` a pure deserializer.

### #8 🟢 Low: Nested `extra_responses` failure carries no positional context

| | |
|---|---|
| **File** | `server/public/model/command_response.go:90-97` |
| **Category** | error-handling |
| **Confidence** | 75 |
| **Found by** | broad-reviewer (Low), design-reviewer (Low) — screen 45 |

**Issue:** The failing child's `*AppError` is returned verbatim, carrying the same `Where` (`"CommandResponse.IsValid"`), the same message ID, and the same `DetailedError` as a top-level failure. Nothing marks which index or nesting level failed. Sibling precedent: `Post.IsValid` appends `"id="+o.Id` to locate the offending object (`server/public/model/post.go:510`).

The real cost is log-based debugging for engineers, since the chain does survive into `mlog`.

**Fix:** Carry the index in `DetailedError` or the error params when returning from inside the loop, e.g. `fmt.Sprintf("extra_responses[%d]", i)`.

## Specialist Notes

### Threat Model Notes (security-reviewer)

Two trust boundaries are touched, both genuinely untrusted:

1. `server/channels/web/webhook.go:114` — `POST /hooks/commands/{id}`, registered via `APIHandlerTrustRequester`, authenticated only by an unguessable ID in the URL. The body **is** transport-bounded: `http.MaxBytesReader` at `MaximumPayloadSizeBytes + bytes.MinRead` (default 300000) in `handlers.go:216`.
2. `server/channels/app/command.go:586` — a response from an admin-configured third-party integration server, capped at `MaxIntegrationResponseSize = 1 MiB` (`server/channels/app/webhook.go:31`) — **16×** the new 65535 `Text` limit, with no comment reconciling the two.

Net attack-surface change: narrowing on one axis (`Text` length, `response_type` values, JSON path only) and unchanged on every other. `Username`, `IconURL`, `ChannelId`, `GotoLocation`, `TriggerId`, `Type`, `Props`, `Attachments`, and the count and total size of `ExtraResponses` all remain unbounded by the new `IsValid()`. Since `server/public` is Mattermost's published Go module, exporting an `IsValid()` establishes a contract plugin and client authors will rely on; the gap between what the name promises and the two fields it checks is the systemic risk here.

### Probe Results (Step 4.5)

One probe was nominated by `test-reviewer` and run by the orchestrator after the review wave joined.

- **Probe:** neutralize the nested-result propagation in `IsValid()` (replace `if err := resp.IsValid(); err != nil { return err }` with a discard) and run `TestCommandResponseFromJSON`.
- **Expected:** the `invalid response type inside extra_responses` case fails.
- **Result: failed as predicted.** `assert.Error` reported "An error is expected but got nil" and the response came back non-nil. The nested-validation test is a genuine guard, not a tautology. This raised confidence on finding #1 and refuted two of the three masking scenarios claimed in the `err.Id` minor finding.
- **Restore verified:** file sha256 restored to `4e4491ff…`, `git status --porcelain` empty, `git diff --stat` empty, tests pass.

### Considered But Not Flagged (all agents)

**Empirically refuted — recursion depth / stack exhaustion via nested `extra_responses`.** Three reviewers independently suspected that the new unbounded recursion over attacker-controlled `extra_responses` could be driven to stack exhaustion from the unauthenticated `commandWebhook` endpoint. All three probed it with throwaway programs in `/tmp` rather than reasoning about it, and all three found it bounded: `encoding/json`'s scanner enforces `maxNestingDepth = 10000` scanner levels, and each `extra_responses` level costs two, so `json.Unmarshal` fails with "exceeded max depth" at 5000 nested responses — **before** `IsValid()` ever runs. Binary search put the exact boundary at depth 4999 succeeding and 5000 failing. 4999 frames of a function with no large stack locals is far from Go's 1 GB max goroutine stack. Worth recording that this bound is an `encoding/json` implementation constant, not a documented API guarantee.

**Refuted — typed-nil `*AppError` returned through the `error` interface.** `if err := o.IsValid(); err != nil { return nil, err }` compares the concrete `*AppError` **before** the interface conversion, so the classic non-nil-interface-wrapping-a-nil-pointer trap does not fire. The final `return &o, nil` returns a true nil interface. Both call sites likewise only use the error inside `if err != nil` guards. Correct as written.

**Screened 32 — strict `response_type` rejection as a compatibility break (security-reviewer, Medium).** Two parts. (1) "Existing integrations sending a non-standard `response_type` break outright with a 500." A search of `server/`, `webapp/`, and git history found **no producer or documentation** of any value outside `{in_channel, ephemeral, ""}` — the only near-hits are the unrelated `OutgoingWebhookResponse` (`"comment"`, a different struct and flow) and OAuth `response_type` fields. The claim is unverified speculation, and the counter-argument is strong: trading a silent no-op for a loud error is arguably the improvement this change was written to make. (2) A genuine but narrow observation that survives: `IsValid()` recurses into `ExtraResponses` at **all** depths, but `HandleCommandResponse` (`command.go:621-629`) only iterates the top level and never recurses. A payload can therefore be rejected over a second-level `response_type` the server would never read.

**Screened 35 — partial validation surface / false "parsed implies valid" contract (design-reviewer, Medium).** `IsValid()` bounds only `ResponseType` and `Text`, while `ChannelId` drives a membership lookup (`command.go:647-648`) and `Type` is rejected downstream for the system-message prefix (`command.go:64-66`). Both downstream checks are unconditional and independent of `IsValid()`, so no code path relies on the new method to enforce them and there is no exploitable bypass. A scope critique a reviewer can reasonably disagree with, not a defect. (`reach=norm` has no Residual Risks bucket, so it is recorded here.)

**Screened 10, pre-existing — unbounded `ExtraResponses` count as a post-amplification vector (security-reviewer, High).** The amplification path is real and was verified: `HandleCommandResponse` posts one entry per top-level extra response, each `in_channel` entry becoming a DB insert plus a websocket broadcast, with `TryUse(hook.Id, 5)` permitting 5 requests per token and a 300000-byte body cap. But `git diff bcf51196..e9ef9dbd` shows **zero** changes to `command.go`, `webhook.go`, or `handlers.go`; the vulnerable surface is byte-for-byte identical before and after, and no validation of any kind existed before. Under `reach=norm` this is a pre-existing gap the change neither created, worsened, nor claimed to close. The finder itself acknowledged the sink pre-dates the change. Worth filing separately if it matters; it is not this change's defect.

**Not promoted — `http.StatusBadRequest` on the new `AppError`.** Inert today: `command.go` discards it and wraps into `StatusInternalServerError`; `webhook.go` discards it and sets an explicit `StatusBadRequest`. 400 is nonetheless the semantically correct value.

**Not promoted — raw error text leaking to an untrusted caller.** `handleContextError` (`server/channels/web/handlers.go:426`) calls `WipeDetailed()` whenever `EnableDeveloper` is false, and the strings themselves ("invalid response type", "text is too long") carry no state or configuration data.

**Not promoted — loop-variable capture in `for _, resp := range o.ExtraResponses`.** `go.mod` declares Go 1.26, well past the 1.22 per-iteration semantics change, and no goroutines are spawned.

**Not promoted — the added `assert.Error(t, err)`.** Not redundant: before this change the `ShouldError` branch inspected only `response == nil` and never the error at all. This line closes a pre-existing gap.

**Step 5.5 cross-check:** dismissed items were cross-referenced against flagged findings across all eight agents. No promotions were warranted — every dismissal above rests on either an empirical probe or a traced code path, not on "probably fine" reasoning.
