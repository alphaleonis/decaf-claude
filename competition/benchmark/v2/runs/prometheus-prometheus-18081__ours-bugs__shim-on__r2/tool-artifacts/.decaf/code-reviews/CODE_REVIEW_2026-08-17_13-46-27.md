### #1 🟠 High: `@`-modifier steps no longer count toward `TotalSamples` — silent regression of an existing statistic and of `prometheus_engine_query_samples_total`

| | |
|---|---|
| **File** | `promql/engine.go:2145` |
| **Category** | correctness |
| **Confidence** | 100 |
| **Verified** | executed |
| **Pre-existing** | no |
| **Found by** | solo-reviewer (High) |

**Issue:** `fullWindowCount` is declared *inside* the per-step loop (`var fullWindowCount, samplesReadCount int64`, line 2145) and only assigned inside the `if ts == ev.startTimestamp || selVS.Timestamp == nil` block (line 2160). When an `@` modifier suppresses re-evaluation at steps > 0, `fullWindowCount` stays `0`, so `ev.samplesStats.IncrementSamplesAtStep(step, fullWindowCount)` (line 2183) adds nothing.

The code it replaced read the *retained* slices at the increment site:

```go
ev.samplesStats.IncrementSamplesAtStep(step, int64(len(floats)+totalHPointSize(histograms)))
```

`floats`/`histograms` persist across steps precisely because the `@` modifier skipped re-slicing, so the old code counted the full window at every step. The change therefore silently alters `totalQueryableSamples`, `totalQueryableSamplesPerStep` and the long-standing `prometheus_engine_query_samples_total` counter — which the PR's own comment on line 2143 and `util/stats/query_stats.go:266-268` claim are unchanged.

This is reachable whenever an `@`-modifier-unsafe function takes a range-vector argument, because `preprocessExprHelper` (`promql/engine.go:4332-4362`) refuses to wrap such a `Call` in a `StepInvariantExpr` and `*parser.MatrixSelector` never returns `shouldWrap=true` (line 4364-4367). `predict_linear` is such a function (`promql/functions.go:2248`).

**Evidence:** Ran the same probe against the base commit `efbdc3f88` in a temporary worktree and against `ec7157593`, range query `start=200s end=400s step=30s`:

```
                                          base (efbdc3f88)                 PR (ec7157593)
predict_linear(m1[60s] @ 300, 60)         total=42  perStep=[6,6,6,6,6,6,6]  total=6  perStep=[6,0,0,0,0,0,0]
predict_linear(m1[60s] @ start(), 60)     total=42  perStep=[6,6,6,6,6,6,6]  total=6  perStep=[6,0,0,0,0,0,0]
sum(predict_linear(m1[60s] @ 300, 60))    total=42  perStep=[6,6,6,6,6,6,6]  total=6  perStep=[6,0,0,0,0,0,0]
predict_linear(m1[60s], 60)               total=42                            total=42   (control, unchanged)
```

`PeakSamples` is unaffected (20 in both). No existing test covers `predict_linear` with `@`, which is why the suite stays green.

**Fix:** Keep `TotalSamples` accounting on the retained slices, independent of whether the window was re-sliced this step:

```go
var samplesReadCount int64
if ts == ev.startTimestamp || selVS.Timestamp == nil {
    ...
    floats, histograms = ev.matrixIterSlice(it, mint, maxt, floats, histograms)
    if step == 0 {
        samplesReadCount = int64(len(floats) + totalHPointSize(histograms))
    } else {
        samplesReadCount = countSamplesAfter(floats, histograms, maxt-ev.interval)
    }
}
...
ev.samplesStats.IncrementSamplesAtStep(step, int64(len(floats)+totalHPointSize(histograms)))
ev.samplesStats.IncrementSamplesReadAtStep(step, samplesReadCount)
```

and add a `predict_linear(...[60s] @ N, 60)` range-query case to `TestQueryStatistics`.

### #2 🟠 High: `countSamplesAfter` adds an unconditional O(window) pass per step — ~34% slowdown on `rate()` over wide windows

| | |
|---|---|
| **File** | `promql/engine.go:2164` |
| **Category** | production |
| **Confidence** | 100 |
| **Verified** | executed |
| **Pre-existing** | no |
| **Found by** | solo-reviewer (High) |

**Issue:** `countSamplesAfter(floats, histograms, maxt-ev.interval)` (`promql/value.go:195`) scans the *entire* retained window linearly at every step of every series. Before the change, the per-step accounting cost was `len(floats)` (O(1)) plus `totalHPointSize(histograms)` (O(#histograms)); for float-only series — the overwhelmingly common case — this turns an O(1) operation into O(window). It is not gated on whether stats were requested: `samplesReadCount` is computed on every range-vector step regardless of `EnablePerStepStats` or the `stats=` parameter.

**Evidence:** `go test ./promql/ -run XXX -bench 'BenchmarkRangeQuery/expr=rate\(a_one\[1d\]\),steps=1000' -benchtime 10x -count 8`, same machine, base commit built in a temporary worktree:

```
base (efbdc3f88): 7069499  7242826  7106510  7025879  7118516  7103821  6869508  6953482   ns/op
PR   (ec7157593): 9495656  9785719  9510800  9465647  9490904  9532496  9661056  9515032   ns/op
```

Median 7.10 ms → 9.51 ms, **+34%**, with no overlap between the two distributions. Allocations are unchanged (~880 KB, 393 allocs), confirming the cost is CPU in the scan and not allocation noise. The regression scales with window size as expected: `rate(a_hundred[1m]),steps=10000` shows ~81 ms → ~86 ms (+5%).

**Fix:** `floats` and `histograms` are sorted ascending by `T`, and only a suffix can be newer than the cutoff. Walk backwards and stop at the first point with `T <= cutoff` (or binary-search the cutoff), making the cost O(new points) instead of O(window):

```go
func countSamplesAfter(floats []FPoint, histograms []HPoint, cutoff int64) int64 {
    var n int64
    for i := len(floats) - 1; i >= 0 && floats[i].T > cutoff; i-- {
        n++
    }
    for i := len(histograms) - 1; i >= 0 && histograms[i].T > cutoff; i-- {
        n += int64(histograms[i].size())
    }
    return n
}
```

### #3 🟡 Medium: subquery I/O is counted twice, making `samplesRead` exceed `totalQueryableSamples` and contradicting the new docs

| | |
|---|---|
| **File** | `promql/engine.go:1874` |
| **Category** | correctness |
| **Confidence** | 100 |
| **Verified** | executed |
| **Pre-existing** | no |
| **Found by** | solo-reviewer (Medium) |

**Issue:** `evalSubquery` now merges the subquery's own `SamplesRead` into the parent (`parentSamplesStats.MergeSamplesReadFromSubquery`, line 1874). The materialized subquery result is then returned as a `MatrixSelector` and re-counted by the range-vector path at `engine.go:2184` (`IncrementSamplesReadAtStep`) as the outer function's window is walked. Both amounts land in `SamplesRead`, so a subquery's points are billed once as raw reads and again as outer-window points.

The consequence is that `samplesRead` becomes *larger* than `totalQueryableSamples` for any function over a subquery, and `prometheus_engine_query_samples_read_total` exceeds `prometheus_engine_query_samples_total` on subquery-heavy workloads. That directly contradicts both new doc paragraphs, which describe `samplesRead` as a deduplicated subset ("only *new* points per step are counted … For other query types, this equals totalQueryableSamples", `docs/feature_flags.md:47-48`, `docs/querying/api.md:246-247`), and undercuts the metric's stated meaning as I/O.

**Evidence:** Executed, range query `start=200s end=400s step=30s` over a single series:

```
max_over_time(m1[60s:10s])  totalQueryableSamples=42  samplesRead=50
max_over_time(m1[60s])      totalQueryableSamples=42  samplesRead=24   (no subquery — behaves as documented)
```

The 50 decomposes exactly as 26 (subquery vector-selector reads over steps 150s…400s at 10s) + 24 (outer delta count over the 26 output points). The PR's own test expectations record the doubling rather than flagging it — `promql/engine_test.go:1181-1187` expects `TotalSamples: 36, SamplesRead: 72` for `max_over_time(metricWith3SampleEvery10Seconds[60s:5s])`, and `engine_test.go:1546` carries the comment `SamplesRead: 2, // subquery + outer`. So the doubling is deliberate; the counter-argument is that it is deliberate but leaves `samplesRead > totalQueryableSamples`, which no reader of the two new doc sections would expect. Either the outer re-count of synthesized subquery points should be suppressed, or the docs and metric help text must state that subquery points are counted at both levels.

**Fix:** Either (a) do not merge the subquery's `SamplesRead` into the parent (mirroring the existing `TotalSamples` treatment, whose original comment "Avoid double counting samples when running a subquery" at the pre-change `engine.go:1861` was removed by this change), or (b) suppress the outer window re-count for matrix selectors synthesized by `evalSubquery`. If (a)/(b) are both rejected, update `docs/feature_flags.md:48` and `docs/querying/api.md:247` to say explicitly that subquery points are counted both as inner reads and as outer-window reads, and that `samplesRead` can therefore exceed `totalQueryableSamples`.

### #4 🟡 Medium: subquery per-step attribution ignores the subquery `offset`, piling reads onto the wrong outer steps

| | |
|---|---|
| **File** | `promql/engine.go:2434-2438` |
| **Category** | correctness |
| **Confidence** | 100 |
| **Verified** | executed |
| **Pre-existing** | no |
| **Found by** | solo-reviewer (Medium) |

**Issue:** In the merge loop, `tk := newEv.startTimestamp + int64(k)*newEv.interval` is a timestamp in *subquery* time — already shifted back by `offsetMillis` via `subqEnd := ev.endTimestamp - offsetMillis` and `subqStart` (lines 2385, 2392). It is then compared against `ev.startTimestamp`, which is in *outer* time, and `offsetMillis` is never added back:

```go
outerStep = int((tk - ev.startTimestamp + ev.samplesStats.Interval - 1) / ev.samplesStats.Interval)
```

The outer step that actually reads `tk` is the smallest `Ts` with `Ts >= tk + offsetMillis`. With a non-zero offset every subquery step is attributed `offset/interval` steps too early (or too late for a negative offset), and the `outerStep = 0` / `numOuterSteps - 1` clamps then absorb the overflow. `samplesRead` (the total) stays correct; only `samplesReadPerStep` — the whole point of the feature — is wrong.

**Evidence:** Executed, range query `start=200s end=400s step=30s`, one series; the plain range-vector control shows offset correctly has no effect on the distribution, while the subquery version degrades monotonically with offset:

```
max_over_time(m1[60s:10s])              read=50  perStep=[12, 6, 6, 6, 6, 6, 8]
max_over_time(m1[60s:10s] offset 60s)   read=50  perStep=[18, 6, 6, 6, 6, 5, 3]
max_over_time(m1[60s:10s] offset 120s)  read=50  perStep=[24, 6, 6, 5, 3, 3, 3]
max_over_time(m1[60s:10s] offset 300s)  read=50  perStep=[32, 3, 3, 3, 3, 3, 3]   <- 64% of reads on step 0
max_over_time(m1[60s:10s] offset -60s)  read=50  perStep=[ 6, 6, 6, 6, 6, 6, 14]
max_over_time(m1[60s])                  read=24  perStep=[ 6, 3, 3, 3, 3, 3, 3]   (control)
max_over_time(m1[60s] offset 120s)      read=24  perStep=[ 6, 3, 3, 3, 3, 3, 3]   (control, identical — correct)
```

The expected distribution for all offsets is the offset-free one, `[12, 6, 6, 6, 6, 6, 8]`. The existing test cases that combine a subquery with `offset` (`engine_test.go:1165`, `1420`, `1547`) are all instant queries or single-step, so the misattribution is invisible to the suite.

Related and worth noting in the same loop: `outerStep >= numOuterSteps → numOuterSteps - 1` (line 2440) attributes subquery steps between the last outer step and `ev.endTimestamp` to the last step even though no outer window consumes them — that is why the offset-free case shows `8` rather than `6` at step 6. That clamp is stated in the comment and preserves the total, so it is a defensible choice; the offset omission is not.

**Fix:** Map back into outer time before bucketing: `t := tk + offsetMillis` and use `t` in the `tk > ev.startTimestamp` test and the `outerStep` division. Add a range-query test with a subquery `offset` (e.g. `max_over_time(m1[60s:10s] offset 120s)` over a multi-step range) asserting the same per-step distribution as the offset-free query.
