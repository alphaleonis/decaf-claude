## Findings

### #1 🔴 Critical: `NullPropagatedOperands` treats every `SqlBinaryExpression` as propagating NULL from both operands, but `AndAlso`/`OrElse` do not — queries silently return wrong values and wrong rows

| | |
|---|---|
| **File** | `src/EFCore.Relational/Query/SqlNullabilityProcessor.cs:626` |
| **Category** | correctness |
| **Confidence** | 100 |
| **Verified** | executed |
| **Pre-existing** | no |
| **Found by** | solo-reviewer (Critical) |

**Issue:** The binary arm

```csharp
else if (expression is SqlBinaryExpression binary)
{
    NullPropagatedOperands(binary.Left, operands);
    NullPropagatedOperands(binary.Right, operands);
}
```

does not inspect `binary.OperatorType`. `SqlBinaryExpression.IsValidOperator` (`SqlBinaryExpression.cs:83-108`) admits `AndAlso` and `OrElse`, and under SQL's three-valued logic neither propagates NULL from both operands: `NULL AND FALSE = FALSE`, `NULL OR TRUE = TRUE`. So when the WHEN result is a boolean expression, the premise "operand is in the null-propagated set ⟹ result is NULL whenever the operand is NULL" is false, the `IS NOT NULL` guard is dropped anyway, and the whole CASE collapses to a result that returns `false`/`true` where the CASE returned NULL.

This is not a projection-only cosmetic difference — it changes the row set of `WHERE` clauses, because `NULL` and `FALSE`/`TRUE` are filtered differently once the CASE value is compared.

Critically, this does **not** require the user to write `&&`/`||`: EF's own null-semantics compensation injects `OR x IS NULL` into equality/inequality translations, so a plain `a != null ? (bool?)(a != b) : null` hits the bug.

**Evidence:** Built the change (`dotnet build src/EFCore.Sqlite/EFCore.Sqlite.csproj`, succeeded) and ran a standalone Sqlite repro against both `afcfba2e9` and the base `051c33a79` (via a temporary `git worktree`, since removed). Identical program, identical data (4 rows).

Projection, `x.NullableBoolA != null ? (bool?)(x.NullableBoolA.Value || x.BoolB) : null`:

```
change SQL : SELECT "e"."NullableBoolA" OR "e"."BoolB" FROM "Es" AS "e"
base   SQL : SELECT CASE WHEN "e"."NullableBoolA" IS NOT NULL
                         THEN "e"."NullableBoolA" OR "e"."BoolB" ELSE NULL END ...
change db  : True, <null>, True, <null>      <-- row 1 wrong
expected   : <null>, <null>, True, <null>    (base matches)
```

Projection, `x.NullableIntA != null ? (bool?)(x.NullableIntA > 5 && x.BoolB) : null`:

```
change SQL : SELECT "e"."NullableIntA" > 5 AND "e"."BoolB" ...
change db  : <null>, False, False, False     <-- rows 2 and 4 wrong
expected   : <null>, <null>, False, <null>   (base matches)
```

No user-written boolean operator, `x.NullableIntA != null ? (bool?)(x.NullableIntA != x.NullableIntB) : null`:

```
change SQL : SELECT "e"."NullableIntA" <> "e"."NullableIntB" OR "e"."NullableIntB" IS NULL ...
change db  : <null>, <null>, True, True      <-- row 4 (both columns NULL) wrong
expected   : <null>, <null>, True, <null>    (base matches)
```

Row-set divergence in `WHERE`:

```
.Where(x => (x.NullableBoolA != null ? (bool?)(x.NullableBoolA.Value || x.BoolB) : null) == true)
   change: ids 1,3      base: id 3       in-memory: id 3
.Where(x => (x.NullableIntA != null ? (bool?)(x.NullableIntA > 5 && x.BoolB) : null) == false)
   change: ids 2,3,4    base: id 3       in-memory: id 3
```

All four scenarios pass on `051c33a79` and fail on `afcfba2e9`, so the regression is introduced by this change.

**Fix:** Gate the binary recursion on operators that genuinely propagate NULL from both operands, and fall through to no recursion otherwise:

```csharp
else if (expression is SqlBinaryExpression
    {
        OperatorType: ExpressionType.Add or ExpressionType.Subtract or ExpressionType.Multiply
            or ExpressionType.Divide or ExpressionType.Modulo
            or ExpressionType.And or ExpressionType.Or or ExpressionType.ExclusiveOr
            or ExpressionType.Equal or ExpressionType.NotEqual
            or ExpressionType.LessThan or ExpressionType.LessThanOrEqual
            or ExpressionType.GreaterThan or ExpressionType.GreaterThanOrEqual
    } binary)
```

`AndAlso`, `OrElse` and `Coalesce` must be excluded. (`Coalesce` is not currently produced as a `SqlBinaryExpression` by the built-in factory, but it is a legal operator that a provider or future refactor can produce, and it is unconditionally non-propagating — excluding it costs nothing.) The operator whitelist deserves a comment stating the soundness premise, so the next reader does not re-widen it.

### #2 🟡 Medium: No test covers a boolean-typed WHEN result, which is exactly where the optimization's premise breaks

|---|---|

**Issue:** All five new tests use results built exclusively from unconditionally NULL-propagating operators: bitwise `~` (unary), integer `+`, and string concatenation. None uses a boolean result, a `&&`/`||` result, a comparison result, or a `WHERE`-clause position. The optimization's whole risk surface — non-propagating operators and row-set effects — is untested, which is why the defect in #1 passed the suite. This is an absence created by the change itself.

**Evidence:** Read all five tests at `NullSemanticsQueryTestBase.cs:2252-2294` and their SQL assertions at `NullSemanticsQuerySqlServerTest.cs:4504-4560`. The full added test surface is `~NullableIntA`, `NullableIntA + NullableIntB`, `NullableStringA + NullableStringB + NullableStringC`, a nested variant of the same, and a mixed test with `BoolA`. The `BoolA` in `Is_not_null_optimizes_binary_op_with_mixed_checks` appears only in the *test*, not in the result, so it does not exercise the binary arm on a boolean. The repro in #1 demonstrates that each of the missing shapes fails.

**Fix:** Add at least three cases alongside the existing ones, all of which fail today and pass with #1's fix:

- `x => x.NullableBoolA != null ? (bool?)(x.NullableBoolA.Value || x.BoolB) : null` (OrElse)
- `x => x.NullableIntA != null ? (bool?)(x.NullableIntA > 5 && x.BoolB) : null` (AndAlso)
- `x => x.NullableIntA != null ? (bool?)(x.NullableIntA != x.NullableIntB) : null` (EF's own `OR ... IS NULL` compensation — no user boolean operator)

Plus one `Where(...)` variant, since #1 changes row sets and not just projected values, and a SQL baseline asserting the CASE is *retained* in these cases.

### #3 🟢 Low: The operand set is built for every eligible CASE, including those whose test contains no `IS NOT NULL` check at all

| | |
|---|---|
| **File** | `src/EFCore.Relational/Query/SqlNullabilityProcessor.cs:578-584` |
| **Category** | efficiency |
| **Confidence** | 75 |
| **Verified** | traced |
| **Pre-existing** | no |
| **Found by** | solo-reviewer (Low) |

**Issue:** `NullPropagatedOperands(clause.Result, …)` walks the entire result subtree and inserts every node into a `HashSet<SqlExpression>` before `DropNotNullChecks` has established that the test contains any `IS NOT NULL` node to drop. `SqlExpression` hashing is structural and uncached — `SqlBinaryExpression.GetHashCode` is `HashCode.Combine(base.GetHashCode(), OperatorType, Left, Right)` (`SqlBinaryExpression.cs:173`), which recurses into children. Inserting all N subexpressions therefore costs O(N × depth) node visits, degrading toward O(N²) on deep expression trees, and it is paid for every single-WHEN-clause CASE with a NULL else, including the majority whose test is a plain comparison and can never yield a drop.

**Evidence:** Traced `GetHashCode`/`Equals` in `SqlBinaryExpression.cs:160-173` and the call order at `SqlNullabilityProcessor.cs:580-581`. This runs during query compilation (cached per query), so it is not a per-execution hot path — hence Low, not higher.

**Fix:** Cheap-check the test first, e.g. return early unless `clause.Test` contains a `SqlUnaryExpression { OperatorType: ExpressionType.NotEqual }` at the top level or in an `AndAlso` chain, and only then build the operand set. Alternatively invert the direction: collect the checked operands from the test (usually one or two nodes) and probe the result tree for them.

## Minor Findings

### Consistency

- `src/EFCore.Relational/Query/SqlNullabilityProcessor.cs:578` — the guard requires `IsNull(elseResult)`, but a `CaseExpression` with no ELSE at all (`elseResult is null`) is semantically identical to `ELSE NULL`, and `IsNull(null)` returns `false` (`SqlNullabilityProcessor.cs:1633`). The optimization silently does not apply to that equivalent shape. Consider `(elseResult is null || IsNull(elseResult))`. (solo-reviewer)
- `src/EFCore.Relational/Query/SqlNullabilityProcessor.cs:576-577` — the block carries no rationale for *why* membership in the null-propagated operand set is sufficient for equivalence. Given that the premise is currently unsound (#1), a one-line statement of the invariant ("the result is NULL for every row where the checked operand is NULL, hence the guard is redundant") would prevent the operator whitelist from being widened again. (solo-reviewer)
- `src/EFCore.Relational/Query/SqlNullabilityProcessor.cs:595` and `:617` — `DropNotNullChecks` and `NullPropagatedOperands` are local functions inside a `protected virtual` method, so a provider overriding `VisitCase` cannot reuse them and will duplicate (and likely re-introduce) the propagation logic. Consider `protected static` methods if provider reuse is intended. (solo-reviewer)
