### #1 🟠 High: EXIF/sidecar extraction still clamps rating to [1,5], so a `-1` rating is silently wiped on the next metadata pass

| | |
|---|---|
| **File** | `server/src/services/metadata.service.ts:308` |
| **Category** | correctness |
| **Confidence** | 75 |
| **Verified** | traced |
| **Pre-existing** | no (made reachable by this change) |
| **Found by** | solo-reviewer (High) |

**Issue:** `99281de` narrowed the extraction range to `validateRange(exifTags.Rating, 1, 5)`; this
change did not revert it. A rating of `-1` set through the API now survives only until the next
metadata extraction, at which point it is silently reset to `NULL`. The user's "rejected" mark
disappears with no error and no log line.

**Evidence:** Traced the complete round trip through code read in full:

1. `PUT/PATCH /assets/:id { rating: -1 }` → `asset.service.ts:520` `upsertExif` with
   `updateLockedColumns`, so `asset_exif.rating = -1` and `'rating'` is added to `lockedProperties`;
   `asset.service.ts:527` queues `SidecarWrite`.
2. `metadata.service.ts:509` — `rating: asset.exifInfo.rating ?? 0` keeps `-1` (the `?? 0` only fires
   for `null`), and `:523` writes `Rating: -1` into the XMP sidecar.
3. `metadata.service.ts:539` — `unlockProperties(asset.id, lockedProperties)` **removes** the lock
   once the value is in the sidecar.
4. Next `MetadataExtraction` (manual "refresh metadata", file/sidecar change, external-library
   rescan) reads `Rating: -1` → `validateRange(-1, 1, 5)` returns `null` (`validation` at `:112`:
   `val < min` → `null`) → `upsertExif` at `:384` with `lockedPropertiesBehavior: 'skip'`, which no
   longer protects `rating` because step 3 unlocked it. `asset_exif.rating` becomes `NULL`.

The same clamp also discards `-1` on *import*: `-1` is the standard XMP "rejected" value written by
Lightroom/Bridge, so those files still land as unrated. `99281de` deleted the test that guarded this
exact case (`'should handle valid negative rating value'`, `metadata.service.spec.ts`); it was not
restored, so nothing fails.

Confidence 75 rather than 100 because the job pipeline could not be executed end-to-end (no
Postgres/Docker in this environment); every individual step is read directly from source.

**Fix:** Restore `validateRange(exifTags.Rating, -1, 5)` at `metadata.service.ts:308` (the
`exifTags.Rating === 0 ? null` guard already handles `0`), and restore the deleted
`'should handle valid negative rating value'` test.

### #2 🟠 High: Search/filter DTOs still reject `-1`, so assets marked rejected cannot be found — and their published history contradicts the new update DTO

| | |
|---|---|
| **File** | `server/src/dtos/search.dto.ts:38` |
| **Category** | api-design |
| **Confidence** | 100 |
| **Verified** | executed |
| **Pre-existing** | no (the contradiction is created by this change) |
| **Found by** | solo-reviewer (High) |

**Issue:** `BaseSearchSchema.rating` is still `z.int().min(1).max(5).nullish()`, inherited by
`MetadataSearchDto`, `SmartSearchDto`, `RandomSearchDto` and `StatisticsSearchDto`. After this change
a user can mark an asset `-1` but **no** search, smart-search or statistics request can filter for
it — `rating: -1` returns HTTP 400. "Rejected" becomes a write-only state, which defeats the point
of re-allowing it.

Worse, `search.dto.ts:46-47` still publishes
`"Using -1 as a rating is deprecated and will be removed in the next major version."` **and**
`"Using -1 as a rating is no longer valid."` while `asset.dto.ts` now documents `-1` as valid. The
generated spec ships both claims side by side: `UpdateAssetDto.rating` says `"-1 (rejected)"`,
`MetadataSearchDto.rating` says `"Using -1 as a rating is no longer valid."`

**Evidence:** Executed. `search.dto.ts:37-40` is shape-identical to the pre-change `asset.dto.ts`
schema, which was run directly:

```
{"rating":-1}  | old: ERR ["Too small: expected number to be >=1"]  | new: OK {"rating":-1}
```

The contradictory descriptions are in the committed spec, confirmed to be exactly what the code
generates (`MetadataSearchDto.rating.x-immich-history` retains both the `v2.6.0` and `v3` `-1`
entries).

**Fix:** Revert `search.dto.ts:38` to `.min(-1)` (with `0` excluded, matching the update DTO) and
update its `x-immich-history` in the same way as `asset.dto.ts` — or, if search deliberately will
not support `-1`, say so explicitly in both descriptions instead of leaving them mutually
contradictory.

### #3 🟠 High: Deleting an already-applied migration file makes the server refuse to start on any DB that ran it

| | |
|---|---|
| **File** | `server/src/schema/migrations/1780592070031-ConvertNegativeRatingToNull.ts:1` (deleted) |
| **Category** | production |
| **Confidence** | 75 |
| **Verified** | traced |
| **Pre-existing** | no |
| **Found by** | solo-reviewer (High) |

**Issue:** The migration was merged to `main` in `99281de` (2026-06-04). `.github/workflows/docker.yml`
publishes images on every push to `main`, so any instance tracking `main` — plus every developer's
local DB — has `1780592070031-ConvertNegativeRatingToNull` recorded in `kysely_migrations`. Deleting
the file means Kysely's Migrator finds an executed migration with no corresponding file and throws;
`runMigrations()` rethrows and bootstrap fails. Those instances cannot start at all until
`DB_SKIP_MIGRATIONS` is set.

**Evidence:** Traced through the exact installed versions:

- `server/src/repositories/database.repository.ts:511-522` —
  `new Migrator({ ..., provider: new FileMigrationProvider({ migrationFolder: join(__dirname, '..', 'schema/migrations') }) })`,
  i.e. the file list is the on-disk folder.
- `node_modules/.pnpm/kysely@0.28.17/.../migration/migrator.js:447` — `#getState` calls
  `#ensureNoMissingMigrations(migrations, executedMigrations)` **unconditionally**, *before* the
  `allowUnorderedMigrations` branch at `:448`. At `:491-497` it throws
  `` `corrupted migrations: previously executed migration ${executed} is missing` ``.
  `allowUnorderedMigrations` (set to `isDev()` at `database.repository.ts:514`) does not suppress it.
- `server/src/services/database.service.ts:116` — `await this.databaseRepository.runMigrations()`
  inside bootstrap; `database.repository.ts:371` rethrows on error.

Counter-argument, stated for the record: there is precedent — `0975b15` ("fix: remove stray
migration") deleted `1773175313374-Test.ts` four days after it merged to `main`, and the same
breakage would have applied. That precedent does not make the failure mode go away; it just means
the team may have accepted it before. This could not be executed (no Postgres/Docker available),
hence 75.

**Fix:** Keep the file and its name, and make it inert:

```ts
export async function up(): Promise<void> {
  // Previously converted rating = -1 to NULL; -1 is valid again, so this is intentionally a no-op.
}
export async function down(): Promise<void> {
  // not supported
}
```

That satisfies Kysely's name check for upgraded DBs and does nothing on fresh installs.

### #4 🟡 Medium: The refinement is invisible to JSON Schema, so the OpenAPI contract loses the rating bounds entirely

| | |
|---|---|
| **File** | `server/src/dtos/asset.dto.ts:17-21` (spec effect at `open-api/immich-openapi-specs.json:16605-16607`, `:26428-26430`) |
| **Category** | api-design |
| **Confidence** | 100 |
| **Verified** | executed |
| **Pre-existing** | no |
| **Found by** | solo-reviewer (Medium) |

**Issue:** `.refine()` cannot be expressed in JSON Schema, so replacing `.min(1).max(5)` with a
refinement drops the constraint from the emitted spec: `UpdateAssetDto.rating` and
`AssetBulkUpdateDto.rating` now advertise `minimum: -9007199254740991, maximum: 9007199254740991` —
i.e. *any* integer. Every spec consumer (client generators, gateway request validators, mock servers,
contract tests) now believes `rating: 0`, `rating: 42`, `rating: -7` are legal; the server rejects
them with 400. The generated Dart client documents the nonsense range to users, and the constraint
is now asymmetric with the sibling search DTOs, which still declare `minimum: 1, maximum: 5`.

**Evidence:** Executed.

- `z.toJSONSchema` on the exact new chain emits
  `{"type":"integer","minimum":-9007199254740991,"maximum":9007199254740991}`; on the old chain,
  `{"type":"integer","minimum":1,"maximum":5}`.
- Regenerating the spec from the built server reproduces the committed file byte-identically, so this
  is the real output, not a stale artifact.
- Visible in the generated client: `mobile/openapi/lib/model/update_asset_dto.dart` now reads
  `/// Minimum value: -9007199254740991` / `/// Maximum value: 9007199254740991` where it previously
  read `1` / `5`.

**Fix:** Keep the bounds representable and use the refinement only for the `0` hole. This variant was
verified to execute identically to the proposed one while preserving the spec bounds:

```ts
rating: z
  .int()
  .min(-1)
  .max(5)
  .nullable()
  .refine((v) => v !== 0, { error: 'Must be -1, a number from 1 to 5, or null' })
  .optional()
```

Emits `{"type":"integer","minimum":-1,"maximum":5}` and rejects `-2`, `0`, `7`, `3.5` exactly as the
current code does. (A `z.union([z.literal(-1), z.int().min(1).max(5)])` also works and is even
tighter, but produces a nested `anyOf` in the spec.)

### #6 🟡 Medium: The `x-immich-history` edit deletes released history instead of superseding it, and never records that `-1` is re-permitted

| | |
|---|---|
| **File** | `server/src/dtos/asset.dto.ts:24-29` |
| **Category** | api-design |
| **Confidence** | 75 |
| **Verified** | traced |
| **Pre-existing** | no |
| **Found by** | solo-reviewer (Medium) |

**Issue:** Two problems in one hunk:

1. The `v2.6.0` entry —
   `"Using -1 as a rating is deprecated and will be removed in the next major version."` — is
   **deleted**, not superseded. v2.6.0 is a shipped release; that entry is a record of what that
   release documented. `HistoryBuilder` (`server/src/decorators.ts:199-267`) is a strictly
   append-only list: `push` only appends, there is no facility for amending an earlier entry, and
   `getExtensions()` derives the current state by scanning `items.toReversed()`. The evident intent
   of the structure is a changelog, and rewriting a released entry is the one operation it cannot
   express.
2. The surviving `v3` entry says only `"Using 0 as a rating is no longer valid."` Nothing anywhere
   tells a client that the v2.6.0 deprecation of `-1` has been rescinded. A consumer who read the
   v2.6.0 notice and migrated off `-1` has no signal to migrate back; a consumer who reads only
   current history has no idea `-1` was ever in question. Meanwhile `search.dto.ts:46-47` still
   carries both original `-1` entries (finding #2), so the API's own history is now
   self-contradictory across sibling DTOs.

Separately, attributing the `0` change to `v3` in *this* commit is odd bookkeeping: `0` stopped being
valid in `99281de`, which is already on `main` for v3 — this hunk documents someone else's change
while erasing the record of its own subject.

**Evidence:** Traced. Read `HistoryBuilder` in full (`decorators.ts:199-267`):
`added`/`updated`/`deprecated` all funnel into `push`, which only appends; there is no update-in-place
or removal API. Confirmed the deletion is reflected in the generated spec —
`UpdateAssetDto.rating.x-immich-history` now has three entries (`v1 Added`, `v2 Stable`,
`v3 Updated`) where it had four. No repo-level convention doc for `x-immich-history` exists (grepped
`docs/`), so this rests on the builder's shape and on the sibling DTOs' usage, hence 75 rather
than 100.

**Fix:** Keep `.updated('v2.6.0', ...)` and append a v3 entry that states both facts, e.g.
`.updated('v3', 'Using -1 as a rating is valid again; using 0 as a rating is no longer valid.')`.

### #7 🟢 Low: The web UI renders a `-1` rating as indistinguishable from unrated

| | |
|---|---|
| **File** | `web/src/lib/components/asset-viewer/DetailPanelStarRating.svelte:16` |
| **Category** | correctness |
| **Confidence** | 75 |
| **Verified** | traced |
| **Pre-existing** | no (made reachable by this change) |
| **Found by** | solo-reviewer (Low) |

**Issue:** `let rating = $derived(asset.exifInfo?.rating || null) as Rating;` — for `-1` the `||` does
not fire (`-1` is truthy), so `-1` is passed through and cast to `Rating`, whose declared type is
`1 | 2 | 3 | 4 | 5 | null` (`web/src/lib/elements/StarRating.svelte:9`). The `as Rating` assertion
silences the type error. In `StarRating.svelte:73`, `filled = (ratingSelection || 0) >= value`
evaluates `-1 >= 1` → false for every star, so a rejected asset displays exactly like an unrated one.
Before this change `-1` could not exist (the API rejected it and the migration cleared existing
rows), so the path was unreachable; it is reachable now, and there is no way for a web user to see or
clear a rejection.

**Evidence:** Traced by reading both components. `-1 || null` → `-1` (JS truthiness);
`(-1 || 0) >= 1` → `false`; `count = 5` so `value` ranges 1..5 and no star fills. Not executed — the
web app was not built.

**Fix:** Out of the server's scope, but the change should either land alongside web handling for `-1`
(a distinct "rejected" indicator) or state explicitly that web renders rejected as unrated for now.
At minimum, `as Rating` is now an active lie about the runtime domain and should widen to
include `-1`.
