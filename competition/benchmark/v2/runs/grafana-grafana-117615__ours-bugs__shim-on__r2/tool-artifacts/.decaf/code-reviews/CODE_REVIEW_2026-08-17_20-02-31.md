### #1 🟠 High: Empty `refIds` now throws a TypeError during render instead of producing a placeholder query

| | |
|---|---|
| **File** | `public/app/features/expressions/components/SqlExpressions/SqlExpr.tsx:81` |
| **Category** | correctness |
| **Confidence** | 100 |
| **Verified** | executed |
| **Pre-existing** | no |
| **Found by** | solo-reviewer (High) |

**Issue:** `vars` is `refIds.map((v) => v.value!)` (line 60), so `vars[0]` is `undefined` when the expression has no upstream queries. The old code interpolated that into the template and rendered the literal text `undefined`. The new call reaches `isValidIdentifier` (`public/app/plugins/datasource/mysql/sqlUtil.ts:54`), which does `identifier.toUpperCase()` on `undefined` and throws. `initialQuery` is computed unconditionally in the component body — not inside the `if (!query.expression)` effect — so this crashes the render even for an already-saved SQL expression, taking down the panel/rule editor rather than degrading gracefully.

Reachability: `ExpressionQueryEditor.tsx:117` builds `refIds` as `queries.filter((q) => query.refId !== q.refId)`, which is `[]` for a panel whose only remaining query is the SQL expression. `QueryEditorRow.tsx:457-462` renders the "Remove query" action unconditionally, so deleting the last data query while an expression exists is a supported UI path.

**Evidence:** Probe test (created, run, deleted) rendering `<SqlExpr refIds={[]} query={{refId:'expr1',type:'sql',expression:'SELECT 1 AS foo'}} … />`:
- against the commits under review: `TypeError: Cannot read properties of undefined (reading 'toUpperCase')` at `sqlUtil.ts:54`, thrown through React's commit phase (uncaught render error).
- against the same probe with `SqlExpr.tsx` restored to `bcca6eb9` (file swapped from a `/tmp` backup and restored byte-identically, md5 verified): **PASS**.

**Fix:** Guard the value before quoting, e.g. `const firstVar = vars[0] ?? ''; ... ${firstVar ? quoteIdentifierIfNecessary(firstVar) : ''}`, or make `quoteIdentifierIfNecessary` total by checking `identifier` in `isValidIdentifier` before `.toUpperCase()`.

### #2 🟠 High: Alerting's SQL dependency parser does not strip backticks, so quoted refIds no longer link in the rule DAG

| | |
|---|---|
| **File** | `public/app/features/alerting/unified/components/rule-editor/dag.ts:198` |
| **Category** | correctness |
| **Confidence** | 75 |
| **Verified** | executed (parse) + traced (consumers) |
| **Pre-existing** | no — the change is what makes the generated SQL contain backticks |
| **Found by** | solo-reviewer (High) |

**Issue:** `SqlExpr` is rendered with `alerting` in the rule editor, and alerting derives an expression's inputs by regex-parsing the SQL text (`getTargets` → `parseRefsFromSqlExpression`, `dag.ts:101-121`). `cleanTableName` strips `'`, `"` and parens but **not** backticks (`dag.ts:198`), and truncates at the first space (`dag.ts:203-204`). With the newly quoted table name, the parsed target no longer equals any refId:

- refId `order` (reserved word): before `["order"]` → linked; after `` ["`order`"] `` → no such node.
- refId `query-1` / `1` (any refId that is not a valid MySQL identifier): before `["query-1"]` → linked; after `` ["`query-1`"] `` → no such node.
- refId `gdp per capita` (the PR's target case): before `["gdp"]`, after `` ["`gdp"] `` — still broken, i.e. the fix does not carry through to alerting.

`Graph.link` throws `cannot link input node named X since it doesn't exist in graph` (`public/app/core/utils/dag.ts:160-176`) → `LinkError` → `createDagFromQueries` throws (`dag.ts:41`). Downstream: `AlertingQueryRunner.ts:76-79` renders the SQL expression as an error panel, and `prepareQueries` (`AlertingQueryRunner.ts:119-132`) drops every node missing from the clean graph, so the SQL expression is silently excluded from the preview run. `reducer.ts:205` calls `findDataSourceFromExpression` (which calls `createDagFromQueries` unguarded) with no try/catch, so a resample expression in the same rule turns this into a thrown reducer action.

**Evidence:** Probe test over the real `parseRefsFromSqlExpression` using this PR's exact generated template, run then deleted:

```
plain:              ["A"]
spaces-unquoted:    ["gdp"]        spaces-quoted:   ["`gdp"]
reserved-unquoted:  ["order"]      reserved-quoted: ["`order`"]
hyphen-unquoted:    ["query-1"]    hyphen-quoted:   ["`query-1`"]
```

**Fix:** Add backticks to the character class in `cleanTableName` and handle the quoted-with-spaces form before the space-splitting alias heuristic — e.g. extract `` `…` `` first and return its contents verbatim, only then apply the alias/`schema.table` logic. Add a `dag.test.ts` case for a backticked, space-containing table name.

### #3 🟡 Medium: Column autocomplete's consumer never sees the quoted name — the `metaSqlExpr` change is unreachable for the case it targets

| | |
|---|---|
| **File** | `public/app/features/expressions/utils/metaSqlExpr.ts:15` |
| **Category** | correctness |
| **Confidence** | 75 |
| **Verified** | executed (tokenizer) + traced (parser wiring) |
| **Pre-existing** | no (the inconsistency is created by quoting the produced identifier) |
| **Found by** | solo-reviewer (Medium) |

**Issue:** The only production caller of `fetchSQLFields` is `fetchFields` in `SqlExpr.tsx:334`, which passes `identifier.table` supplied by `@grafana/plugin-ui`. That value comes from `getTableToken` → `defaultTableNameParser` (`node_modules/@grafana/plugin-ui/dist/esm/components/SQLEditor/utils/tokenUtils.js:13-35`, wired at `components/SQLEditor.js:277-281,304-310`), which takes **the first non-whitespace Monaco token after `FROM`** and splits it on `.`. Monaco's MySQL tokenizer emits the backtick as its own `identifier.quote` token, so for a quoted table the parser yields `` { table: '`' } `` — never `gdp per capita`.

Consequences: (a) `quoteIdentifierIfNecessary(query.table)` can never receive the multi-word name the change is meant to handle; the reachable value is a lone backtick, producing `` SELECT * FROM ``` LIMIT 1 `` (invalid), and `queries.filter((q) => q.refId === query.table)` at `metaSqlExpr.ts:20` matches nothing. Column suggestions are therefore silently empty (swallowed by `catch { return [] }` at `sqlCompletionProvider.ts:39`) for exactly the refIds this PR enables. (b) The new test `metaSqlExpr.test.ts:28-41` asserts `table: 'table with spaces'`, an input the sole caller cannot produce, so it certifies behavior that never happens in the product. Note this is the pattern the MySQL datasource already solves: its own provider skips the quote token (`mysql/sqlCompletionProvider.ts:131-134`) and unquotes before use (`mySqlMetaQuery.ts:38-40`).

**Evidence:** Probe test (created, run, deleted) tokenizing with the real Monaco MySQL Monarch grammar:

```
SELECT * FROM `gdp per capita` LIMIT 10
→ [[9,"keyword.sql","FROM"],[13,"white.sql"," "],[14,"identifier.quote.sql","`"],
   [15,"identifier.sql","gdp per capita"],[29,"identifier.quote.sql","`"], …]
```

`getTableToken` returns the token at offset 14 (value `` ` ``), and `defaultTableNameParser` returns `` { table: '`' } ``.

**Fix:** Either supply a `parseName` on the `tables` provider config that reconstructs the quoted identifier from the quote/identifier token triple (as the MySQL datasource's custom `getTableName` does), or unquote at the boundary: `const table = unquoteIdentifier(query.table)` before both the `queries.filter` and the re-quoting. Then re-point the test at the value the real caller actually passes.
