## Findings

### #1 🔴 Critical: The re-permitted `rating: -1` is silently reverted to `null` by the standard job chain

| | |
|---|---|
| **File** | `server/src/services/metadata.service.ts:308` |
| **Category** | correctness / data-loss |
| **Confidence** | 100 |
| **Found by** | adversarial-reviewer (Critical), design-reviewer (Critical), broad-reviewer (High) |
| **Validation** | confirmed — independently re-traced, and the orchestrator verified the job chain directly |

**Issue:** Commit `99281de` narrowed the metadata *ingest* clamp in the same edit that narrowed the DTO:

```
git show 99281de^:server/src/services/metadata.service.ts → validateRange(exifTags.Rating, -1, 5)
git show 99281de :server/src/services/metadata.service.ts → validateRange(exifTags.Rating,  1, 5)
```

This change reverts the DTO but **not** the clamp. `validateRange` (`metadata.service.ts:107-115`) returns `null` when the value is below `min`, so `-1` becomes `null`.

The full chain, verified line by line — no unusual user action, no manual rescan required:

1. `PUT/PATCH /assets/:id {"rating": -1}` passes the new DTO refine → 200.
2. `asset.service.ts:520-527` — `upsertExif({ …, lockedPropertiesBehavior: 'append' })` locks `rating` (`rating` is in `lockableProperties`, `database.ts:506-513`), then **unconditionally** queues `JobName.SidecarWrite`.
3. `metadata.service.ts:498-539` — `handleSidecarWrite` writes `Rating: -1` into the `.xmp`, then calls `unlockProperties(asset.id, lockedProperties)` at line 539, **releasing the lock**.
4. `job.service.ts:75-81` — on `SidecarWrite` completion, **unconditionally** queues `JobName.AssetExtractMetadata`.
5. `metadata.service.ts:308` — extraction reads the sidecar's `Rating: -1` → `validateRange(-1, 1, 5)` → `null`; `upsertExif({ …, lockedPropertiesBehavior: 'skip' })` at line 389 applies it, the lock having just been released.

The same defect affects **ingest**: any imported file or sidecar carrying the widely-used `Rating: -1` "rejected" convention is stored as `null`. Note the asymmetry — `metadata.service.ts:509` writes `rating ?? 0` and line 308 maps `0 → null`, so the null round-trip is lossless while `-1` is not.

Nothing logs or fails; the value simply disappears. The unit test that would have caught this (`should handle valid negative rating value` in `metadata.service.spec.ts`) was deleted by `99281de` and is not restored here — see Finding #5.

**Fix:**
```ts
// server/src/services/metadata.service.ts:308
rating: exifTags.Rating === 0 ? null : validateRange(exifTags.Rating, -1, 5),
```
and restore the deleted `metadata.service.spec.ts` case asserting `mockReadTags({ Rating: -1 })` yields `rating: -1`.

### #2 🟠 High: Search and filter DTOs still reject `-1`, so `-1`-rated assets are unreachable

| | |
|---|---|
| **File** | `server/src/dtos/search.dto.ts:36-49` |
| **Category** | correctness / incomplete-revert |
| **Confidence** | 100 |
| **Found by** | quick-reviewer (High), adversarial-reviewer (High), design-reviewer (High) |
| **Validation** | waived — corroborated ×3 including two specialists, all at anchor 100 |

**Issue:** `BaseSearchSchema.rating` (backing `MetadataSearchDto`, `RandomSearchDto`, `SmartSearchDto`, `StatisticsSearchDto`) is untouched and still reads:

```ts
rating: z.int().min(1).max(5).nullish()
  .describe('Filter by rating [1-5], or null for unrated')
  .meta({ … .updated('v2.6.0', 'Using -1 as a rating is deprecated …')
            .updated('v3', 'Using -1 as a rating is no longer valid.') … })
```

`ZodValidationPipe` is registered globally (`app.module.ts:47`), so `rating: -1` on any search endpoint is a 400. `rating: null` compiles to `asset_exif.rating IS NULL`, which does not match `-1` either. Net effect: a user can mark an asset rejected but **no rating filter can find it again**.

The stale history text is the second half of the problem — the published OpenAPI document now asserts, in the same file, that at v3 `-1` both is and is not valid, depending on which DTO you read.

**Fix:** Apply the same value set to `BaseSearchSchema.rating` and reconcile its history entries with `asset.dto.ts`. Better: extract one shared `ratingSchema` constant consumed by the update, search, and response DTOs so this cannot drift again.

### #3 🟠 High: Moving the bound into `.refine()` erases it from the published OpenAPI contract

| | |
|---|---|
| **File** | `server/src/dtos/asset.dto.ts:19-21` |
| **Category** | api-contract |
| **Confidence** | 100 |
| **Found by** | typescript-reviewer (High), design-reviewer (High), consistency-reviewer (High), quick-reviewer (Medium), broad-reviewer (Medium), adversarial-reviewer (Medium) — 6 independent finders |
| **Validation** | waived — corroborated ×6, empirically reproduced against the repo's own `zod@4.3.6` |

**Issue:** Zod v4 schema-level checks (`.min()`/`.max()`) convert to JSON Schema `minimum`/`maximum`; `.refine()` predicates do not. The generated spec for both `UpdateAssetDto.rating` and `AssetBulkUpdateDto.rating` therefore went from

```json
"minimum": 1, "maximum": 5
```
to
```json
"minimum": -9007199254740991, "maximum": 9007199254740991
```

i.e. the safe-integer default — an effectively unbounded field. The server still rejects `0`, `6`, `42`; the contract no longer says so, and neither do the generated TS SDK or Dart models. The sibling `rating` fields elsewhere in the same document still correctly emit `minimum: 1, maximum: 5`, so the document is internally inconsistent about the same concept.

This is also a house-style break: `search.dto.ts:37-39` and `exif.dto.ts:32` both keep the bound in the schema, and this very field used `.min()/.max()` until this change.

**Fix:** Use a construct the JSON-Schema emitter can render — verified by `typescript-reviewer` to produce `anyOf: [{const: -1}, {type: 'integer', minimum: 1, maximum: 5}, {type: 'null'}]` with identical runtime accept/reject behavior:

```ts
rating: z.union([z.literal(-1), z.int().min(1).max(5)]).nullish()
```

### #4 🟠 High: Deleting an already-executed migration makes Kysely refuse to boot

| | |
|---|---|
| **File** | `server/src/schema/migrations/1780592070031-ConvertNegativeRatingToNull.ts:1` (deleted) |
| **Category** | data-migration / operability |
| **Confidence** | 100 (mechanism) · exposure narrow — see below |
| **Found by** | adversarial-reviewer (Critical), data-migration-reviewer (Critical) |
| **Validation** | confirmed — validator recommends **Medium**; kept at High, dissent recorded below |

**Issue:** Immich runs Kysely's stock `Migrator` + `FileMigrationProvider` over `schema/migrations`, table `kysely_migrations` (`database.repository.ts` `createMigrator()`). `Migrator.#getState` calls `#ensureNoMissingMigrations` (`kysely@0.28.17/dist/cjs/migration/migrator.js:447, 491-497`), which throws

```
corrupted migrations: previously executed migration 1780592070031-ConvertNegativeRatingToNull is missing
```

for any recorded migration with no file on disk. The check is **unconditional** — `allowUnorderedMigrations` gates `#ensureMigrationsInOrder`, a different check. `runMigrations()` re-throws with no catch, and `DatabaseService.onBootstrap()` calls it inline (guarded only by `DB_SKIP_MIGRATIONS`, default `false`). Any affected instance fails to start, every start, until repaired by hand.

**Exposure and dissent.** The validator established that no version-bump commit sits between `99281de` (2026-06-04) and this deletion (2026-06-07), so the migration never reached a numbered release — only the `:main` image, rebuilt on every push to `main` (`.github/workflows/docker.yml`). It also found a direct precedent: `0975b15` ("fix: remove stray migration", 2026-05-22) deleted a real DDL migration 4 days after it landed, with no recorded fallout. On that basis the validator recommends Medium. I am keeping **High**: `:main` is a real and commonly-tracked channel, the failure mode is a hard boot loop rather than a degraded feature, and "nobody filed it in this repo" is weak evidence that the precedent was harmless. The disagreement is genuine and recorded here rather than resolved silently.

**Fix:** Either keep `1780592070031` in the chain with an inert `up()` (a one-line comment explaining why it is a no-op), or ship the operational step with the change:
```sql
DELETE FROM kysely_migrations WHERE name = '1780592070031-ConvertNegativeRatingToNull';
```

## Specialist Notes

### Migration safety notes (data-migration-reviewer)

- Runner: Kysely `Migrator` + `FileMigrationProvider`, table `kysely_migrations`, lock table `kysely_migrations_lock` (`database.repository.ts` `createMigrator()`). `allowUnorderedMigrations` is enabled only in dev.

- Diagnostic worth running on any real deployment before and after: `SELECT name FROM kysely_migrations WHERE name = '1780592070031-ConvertNegativeRatingToNull';` and `SELECT count(*) FROM asset_exif WHERE rating = -1;`.

### Considered But Not Flagged (all agents)

**Verified correct, no defect:**
- **Zod chain semantics** — `.int().nullable().refine(…).optional()` infers `number | null | undefined`, identical to the previous `.nullish()`. `ZodOptional` short-circuits on `undefined` before the refine runs, so `v >= 1` never sees `undefined`. `z.int()` rejects `NaN`/`Infinity`/`3.5` before the refine. Empirically checked against the repo's `zod@4.3.6` via untracked scratch scripts. (typescript-reviewer)
- **`.describe()` / `.meta()` after `.refine()`** — both attach to the correct node; the `description` and `x-immich-history` extension appear correctly in the generated spec. (typescript-reviewer)
- **Accepted value set** — `null`, `-1`, `1..5` accept; `0`, `-2`, `6`, `3.5` reject. Matches the stated intent exactly. (adversarial-reviewer)
- **`x-immich-state: "Stable"`** — unchanged and still correct; `getExtensions()` derives it from the last non-`Added`/`Updated` entry, so removing an `Updated` entry does not affect it. (design-reviewer)
- **Updated test error messages** — the shared refine message is correctly expected for both `rating: 7` and `rating: -2`; 42/42 pass. (consistency-reviewer, test-reviewer)
- **Dart client diff** — doc-comment/bounds only; the Dart generator emits no runtime validation from these bounds. (consistency-reviewer)
- **`SyncAssetExifV1.rating`** — carries no bounds in the spec, so the sync surface already tolerates `-1`; no drift introduced. (design-reviewer)
- **Duplicate-resolution scoring** (`utils/duplicate.ts`) — counts truthy exif fields; `-1` is truthy like any rating, outcome unchanged. (adversarial-reviewer)
