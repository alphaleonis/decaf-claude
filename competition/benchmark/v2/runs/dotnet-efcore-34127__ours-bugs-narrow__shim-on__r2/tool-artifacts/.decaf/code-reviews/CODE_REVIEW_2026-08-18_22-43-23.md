## Findings

### #1 🔴 Critical: `NullPropagatedOperands` treats *every* `SqlBinaryExpression` as NULL-propagating, so `AND`/`OR` results lose their null guard and return `true`/`false` where the query must return `null`

| | |
|---|---|
| **File** | `src/EFCore.Relational/Query/SqlNullabilityProcessor.cs:626` |
| **Category** | correctness |
| **Confidence** | 100 |
| **Verified** | executed |
| **Pre-existing** | no |
| **Found by** | solo-reviewer (Critical) |

**Issue:**

```csharp
else if (expression is SqlBinaryExpression binary)
{
    NullPropagatedOperands(binary.Left, operands);
    NullPropagatedOperands(binary.Right, operands);
}
```

This arm is unconditional on `OperatorType`. `SqlBinaryExpression.IsValidOperator` (`src/EFCore.Relational/Query/SqlExpressions/SqlBinaryExpression.cs:83-107`) admits `AndAlso`, `OrElse` and `Coalesce` alongside the arithmetic/bitwise/comparison operators, and `QuerySqlGenerator.GetOperator` (`src/EFCore.Relational/Query/QuerySqlGenerator.cs:1089-1090`) maps them to SQL `AND` / `OR`. Under SQL three-valued logic **`AND` and `OR` do not propagate NULL from an operand**: `NULL AND FALSE = FALSE`, `NULL OR TRUE = TRUE`.

So when `clause.Result` is a boolean expression such as `A OR B`, the operand `A` is added to `nullPropagatedOperands`, `DropNotNullChecks` deletes `A IS NOT NULL` from the test (lines 597-601), the whole `CASE` collapses (line 587), and the query returns a non-NULL boolean for rows where `A IS NULL` — rows for which the C# expression evaluates to `null`. Silent wrong data, no exception.

The same defect has a second face on SQL Server. `SearchConditionConvertingExpressionVisitor` runs *after* `SqlNullabilityProcessor` (`src/EFCore.SqlServer/Query/Internal/SqlServerParameterBasedSqlProcessor.cs:38-45`) and rewrites any condition that lands in value position as `CASE WHEN <cond> THEN 1 ELSE 0 END` (`SearchConditionConvertingExpressionVisitor.cs:41-51`, with `condition` true for `Equal`, `NotEqual`, `<`, `<=`, `>`, `>=`, `AndAlso`, `OrElse` — lines 350-357). That rewrite maps UNKNOWN to `false`, i.e. a comparison sitting in `CASE`-result position is **not** NULL-propagating on SQL Server either, even though the generic arm assumes it is.

**Evidence (executed):**

The tree at `afcfba2e9` was built and, in a scratch console app outside the repo, generated SQL and actual results were compared against the same probes built from a read-only `git worktree` at the parent commit `051c33a79`. The working tree was untouched throughout; `git status --porcelain` is empty and the worktree has been removed.

SQL Server (`ToQueryString`), `x => x.NullableBoolA != null ? (bool?)(x.NullableBoolA.Value || x.BoolB) : null`:

```
-- 051c33a79 (before)
SELECT CASE
    WHEN [e].[NullableBoolA] IS NOT NULL THEN CASE
        WHEN [e].[NullableBoolA] = CAST(1 AS bit) OR [e].[BoolB] = CAST(1 AS bit) THEN CAST(1 AS bit)
        ELSE CAST(0 AS bit) END
    ELSE NULL
END
-- afcfba2e9 (after)
SELECT CASE
    WHEN [e].[NullableBoolA] = CAST(1 AS bit) OR [e].[BoolB] = CAST(1 AS bit) THEN CAST(1 AS bit)
    ELSE CAST(0 AS bit)
END
```

Executed against real SQLite data (rows: `{NullableBoolA=null, BoolB=true}`, `{null, false}`, `{true, false}`), `db` = server result, `mem` = the same lambda evaluated in memory (this is exactly what `AssertQuery` compares):

| probe | LINQ | `db` after the change | `db` at `051c33a79` | correct (`mem`) |
|---|---|---|---|---|
| A | `NullableBoolA != null ? (bool?)(NullableBoolA.Value \|\| BoolB) : null` | **True**, NULL, True | NULL, NULL, True | NULL, NULL, True |
| B | `NullableBoolA != null ? (bool?)(NullableBoolA.Value && BoolB) : null` | NULL, **False**, False | NULL, NULL, False | NULL, NULL, False |
| C | `NullableIntA != null ? (bool?)(NullableIntA == NullableIntB) : null` | **False**, NULL, True | NULL, NULL, True | NULL, NULL, True |

Emitted SQL for A after the change: `SELECT "e"."NullableBoolA" OR "e"."BoolB" FROM "Entities" AS "e"`. For C: `SELECT "e"."NullableIntA" = "e"."NullableIntB" AND "e"."NullableIntB" IS NOT NULL` — note that C reaches the bug through the `AndAlso` produced by EF's own null-semantics expansion of `==`, so ordinary equality comparisons under a null guard are affected too (`G`, the `string` version of C, reproduces identically). All three match at the parent commit and diverge only after the change.

Not affected, and confirmed so by the same probes: `x.NullableIntA ?? x.IntA` in the result (COALESCE is a `SqlFunctionExpression` with `argumentsPropagateNullability: [false, false]`), `x.NullableIntA > x.NullableIntB` (the translator already wraps that branch in a nested `CASE`, which the recursion does not descend), and the navigation shape `p.Child != null ? (bool?)(p.Child.Flag1 || p.Child.Flag2) : null` (the guard is on `c.Id`, a column absent from the result). None of the six updated baselines exercise a boolean result, which is why the existing suite stays green.

**Fix:** Make the `SqlBinaryExpression` arm operator-aware — a whitelist rather than the current catch-all, so a newly admitted operator fails closed:

```csharp
else if (expression is SqlBinaryExpression
    {
        OperatorType: ExpressionType.Add or ExpressionType.Subtract or ExpressionType.Multiply
            or ExpressionType.Divide or ExpressionType.Modulo
            or ExpressionType.And or ExpressionType.Or or ExpressionType.ExclusiveOr
    } binary)
```

That excludes `AndAlso`, `OrElse` and `Coalesce` (the last is legal per `IsValidOperator` even though `SqlExpressionFactory.Coalesce` currently routes to the `COALESCE` function). It also excludes the comparison operators, which is required for the SQL Server search-condition case described above — dropping only `AndAlso`/`OrElse` fixes probes A, B, C and G, but leaves a bare comparison in `CASE`-result position unsound on SQL Server. No LINQ query could be constructed that puts a *bare* comparison there (the translator wraps it), so treat that part as traced rather than executed; the whitelist covers it either way at no cost.

Whichever shape the fix takes, regression coverage for the boolean-result shape is needed (probe A is the smallest reproducer and fits `NullSemanticsQueryTestBase` unchanged) — a SQL-baseline assertion alone would not have caught this, but `AssertQuery` does.
