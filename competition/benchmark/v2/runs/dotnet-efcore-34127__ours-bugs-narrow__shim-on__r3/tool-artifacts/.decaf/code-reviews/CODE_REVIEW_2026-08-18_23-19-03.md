## Findings

### #1 🔴 Critical: `NullPropagatedOperands` treats `AndAlso`/`OrElse` as null-propagating, so a load-bearing `IS NOT NULL` guard is deleted

| | |
|---|---|
| **File** | `src/EFCore.Relational/Query/SqlNullabilityProcessor.cs:626` |
| **Category** | correctness |
| **Confidence** | 100 |
| **Verified** | executed |
| **Pre-existing** | no |
| **Found by** | solo-reviewer (Critical) |

**Issue:** Line 626 recurses into `binary.Left` and `binary.Right` for **every** `SqlBinaryExpression`
operator type. `SqlBinaryExpression.IsValidOperator`
(`src/EFCore.Relational/Query/SqlExpressions/SqlBinaryExpression.cs:87-104`) admits `AndAlso`,
`OrElse` and `Coalesce`, none of which propagate NULL: `NULL OR TRUE` is `TRUE` and `NULL AND FALSE`
is `FALSE`. Any operand reached only through such a node is therefore wrongly recorded as
null-propagating, and `DropNotNullChecks` deletes its `IS NOT NULL` test — after which the CASE
wrapper is removed entirely and the query silently returns wrong scalar values and wrong rows.

This is not a hypothetical operator set. EF's own null-semantics rewrite of `==`/`!=` **produces**
`OrElse`/`AndAlso` containing an `IS NULL` / `IS NOT NULL` on the *other* operand
(`SqlNullabilityProcessor.cs:1866-1897`), and because `whenClause.Result` is visited with the tested
column already in `_nonNullableColumns` (`:533-535`), the guard on the tested column is elided
*inside* the result too. Dropping the outer test then removes the last remaining null check.

The same file already states the rule this violates, at `:2315-2321`:

```csharp
case SqlBinaryExpression sqlBinaryOperand
    when sqlBinaryOperand.OperatorType != ExpressionType.AndAlso
    && sqlBinaryOperand.OperatorType != ExpressionType.OrElse:
    // binaryOp(a, b) != null -> a != null && b != null
    // for AndAlso, OrElse we can't do this optimization
```

**Evidence:** Executed. `src/EFCore.Sqlite` was built at head (`afcfba2e9`) and at base (`051c33a79`,
via `git worktree`, since `test/EFCore.Specification.Tests` does not compile with the installed SDK
10.0.400 — 18 `CS` errors at base too, so the repo suites could not be run) and both were driven
through an out-of-tree console harness that compares SQL results against LINQ-to-objects over five
rows `(NullableStringA, NullableStringB)` = `("x","x") ("x","y") ("x",NULL) (NULL,"y") (NULL,NULL)`.

Three of six probes regress at head; **all six match at base**:

| Query | base SQL / result | head SQL / result |
|---|---|---|
| `Select(e => e.NullableStringA != null ? (bool?)(e.NullableStringA != e.NullableStringB) : null)` | `CASE WHEN A IS NOT NULL THEN A <> B OR B IS NULL ELSE NULL END` → `False, True, True, null, null` ✅ | `A <> B OR B IS NULL` → `False, True, True, null, **True**` ❌ |
| `Select(e => e.NullableStringA != null ? (bool?)(e.NullableStringA == e.NullableStringB) : null)` | CASE retained → `True, False, False, null, null` ✅ | `A = B AND B IS NOT NULL` → `True, False, False, null, **False**` ❌ |
| `Where(e => (e.NullableStringA != null ? (bool?)(e.NullableStringA != e.NullableStringB) : null) == true)` | ids `2,3` ✅ | `WHERE A <> B OR B IS NULL` → ids `2,3,**5**` ❌ |
| `Where(e => (e.NullableIntA != null ? (bool?)(e.NullableIntA > 0 \|\| e.NullableIntB > 0) : null) == true)` | ids `1,2,3` ✅ | `WHERE A > 0 OR CASE WHEN B > 0 THEN 1 ELSE 0 END` → ids `1,2,3,**4**` ❌ |

Row 5 (`A=NULL, B=NULL`): `NULL OR (B IS NULL)` → `TRUE` instead of `NULL`;
`NULL AND (B IS NOT NULL)` → `FALSE` instead of `NULL`. The fourth row shows the plain user-written
`||` case, so the defect does not depend on the null-semantics rewrite at all.

The repro is in provider-agnostic code (`SqlNullabilityProcessor` is shared by all relational
providers); verified on SQLite because no SQL Server instance was reachable — the SQL Server path was
not executed.

No test in the changeset or in the existing suite covers this shape: the five added tests only
exercise `Not` (`~`), `Add` and nested/partial `Add` results, and grepping
`NullSemanticsQueryTestBase.cs` for `!= null ?` finds only `:1708` (whose `ELSE` is `BoolA`, so the
block is skipped) plus the two new ones. CI would therefore go green on this regression.

**Fix:** Exclude the non-propagating operators, mirroring the guard already used at `:2315-2316`:

```csharp
else if (expression is SqlBinaryExpression binary
    && binary.OperatorType is not (ExpressionType.AndAlso or ExpressionType.OrElse or ExpressionType.Coalesce))
{
    NullPropagatedOperands(binary.Left, operands);
    NullPropagatedOperands(binary.Right, operands);
}
```

(An allow-list of arithmetic/bitwise/comparison operators would be safer still against future
additions to `IsValidOperator`.) This restriction still permits every shape the new tests assert:
the walker keeps adding the root node itself, so `Add`/`Not`/`Convert`/function results continue to
optimize, while the four regressing shapes retain their CASE. Regression tests for
`x != null ? (bool?)(x != y) : null` and `x != null ? (bool?)(x > 0 || y > 0) : null`, in both
projection and predicate position, should be added alongside.
