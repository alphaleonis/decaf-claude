## Findings

### #1 🔴 Critical: `NullPropagatedOperands` recurses through `AndAlso`/`OrElse`, which do not propagate NULL — silently wrong query results

| | |
|---|---|
| **File** | `src/EFCore.Relational/Query/SqlNullabilityProcessor.cs:626` |
| **Category** | correctness |
| **Confidence** | 100 |
| **Verified** | executed |
| **Pre-existing** | no |
| **Found by** | solo-reviewer (Critical) |

**Issue:** `NullPropagatedOperands` recurses into `Left` and `Right` of *every* `SqlBinaryExpression`, regardless of operator. Arithmetic, bitwise, and comparison operators do propagate NULL, but SQL's logical `AND`/`OR` do not: `NULL AND FALSE` = `FALSE` and `NULL OR TRUE` = `TRUE`, both non-NULL. So an operand reachable only underneath an `AndAlso`/`OrElse` is wrongly registered as null-propagating, `DropNotNullChecks` deletes its `IS NOT NULL` test, and the CASE collapses to an expression that returns `TRUE`/`FALSE` on exactly the rows where the original returned `NULL`.

This is not a corner case. EF's own null-semantics rewrite (`RewriteNullSemantics`, lines 1882-1897) is what manufactures the `AndAlso`/`OrElse`: with the left operand known non-null from the test, `a == b` becomes `a = b AND b IS NOT NULL` and `a != b` becomes `a <> b OR b IS NULL`. So **every** `nullableA != null ? (nullableA <op> nullableB) : null` — the single most idiomatic use of this CASE shape — regresses. The very non-nullability assumption the test injects is what makes the result non-propagating, so the analysis is looking at an expression the test itself made unsafe to strip.

The bug produces wrong *rows*, not just wrong projected values: `Where` predicates over such a conditional return extra rows.

**Evidence:** Executed. `src/EFCore.Sqlite.Core` was built from three trees (this checkout at `afcfba2e9`; a temp worktree at the pre-change parent `051c33a79`; a temp worktree at `afcfba2e9` plus the candidate fix below) and a standalone SQLite probe run over the exact 27-row `NullSemanticsData` model, comparing SQL results against in-memory LINQ row by row. All worktrees and probe files were removed; `git status --porcelain` is empty and `git worktree list` shows only the review checkout.

Seven independent shapes pass pre-change and fail post-change:

| Probe | Post-change SQL | Failure |
|---|---|---|
| `A != null ? (bool?)(A != B) : null` | `A <> B OR B IS NULL` | 3 rows: expected `null`, got `True` |
| `A != null ? (bool?)(A == B) : null` | `A = B AND B IS NOT NULL` | 3 rows: expected `null`, got `False` |
| `sA != null ? (bool?)(sA == sB) : null` | `sA = sB AND sB IS NOT NULL` | 3 rows: expected `null`, got `False` |
| `nbA != null ? (bool?)(nbA != nbB) : null` | `nbA <> nbB OR nbB IS NULL` | 3 rows: expected `null`, got `True` |
| `nbA != null ? (bool?)(nbA.Value \|\| BoolB) : null` | `NullableBoolA OR BoolB` | 6 rows: expected `null`, got `True` |
| `nbA != null ? (bool?)(nbA.Value && BoolB) : null` | `NullableBoolA AND BoolB` | 3 rows: expected `null`, got `False` |
| `Where((A != null ? (bool?)(A != B) : null) == true)` | `WHERE A <> B OR B IS NULL` | returns ids `[…,25,26,27]`, expected `[…,18]` — **3 extra rows** |

Pre-change, every one of these emitted `CASE WHEN "NullableIntA" IS NOT NULL THEN … ELSE NULL END` and matched all 27 rows.

Worked case for the first row, `NullableIntA = NULL, NullableIntB = NULL` (ids 25-27):

- Result after visiting = `A <> B OR B IS NULL` (`OrElse`).
- `NullPropagatedOperands` adds the `OrElse` node, then (line 626) recurses into both sides; the left `A <> B` is a `SqlBinaryExpression`, so `A` and `B` are added.
- `DropNotNullChecks(A IS NOT NULL, …)` finds `A` in the set (line 598) → returns `null` → line 587 returns the bare result.
- Runtime: `NULL <> NULL OR NULL IS NULL` = `NULL OR TRUE` = `TRUE`. The CASE would have returned `NULL`.

The five tests added in this change all happen to use genuinely null-propagating results (`~A`, `A + B`, string concat), so none of them can fail for this defect.

Same-line secondary hole: `ExpressionType.Coalesce` is an admitted `SqlBinaryExpression` operator (`src/EFCore.Relational/Query/SqlExpressions/SqlBinaryExpression.cs:102`) and also does not propagate NULL. Relational's own `SqlExpressionFactory.Coalesce` (line 485) builds a `SqlFunctionExpression` with `argumentsPropagateNullability: [false, false]`, so no relational construction site reaching this today was found — but it is legal per `IsValidOperator`, providers and the precompiled-query constructor can build it, and it costs nothing to exclude.

**Fix:** Restrict the `SqlBinaryExpression` recursion to operators that actually propagate NULL — i.e. exclude the logical/short-circuit and coalescing operators:

```csharp
else if (expression is SqlBinaryExpression binary
    && binary.OperatorType is not (ExpressionType.AndAlso or ExpressionType.OrElse or ExpressionType.Coalesce))
{
    NullPropagatedOperands(binary.Left, operands);
    NullPropagatedOperands(binary.Right, operands);
}
```

Exactly this was applied in a throwaway worktree and the full probe set re-run: all seven failing shapes return to correct results, **and** all five optimizations the change is trying to introduce are retained unchanged (`SELECT sA || sB || COALESCE(sC,'')`, `SELECT sA || sB`, `SELECT CASE WHEN BoolA THEN sA || COALESCE(sB,'') ELSE NULL END`, `SELECT ~A`, `SELECT A + B`). Consider inverting the check to an explicit allow-list of propagating operators so a future addition to `IsValidOperator` fails closed rather than open. Worth adding regression tests for at least `a != null ? (a == b) : null` and `a != null ? (a != b) : null` with `b` nullable — those are the shapes real user code hits.

- **`NullPropagatedOperands` ignores the `HashSet.Add` return value (line 619)**, so shared subtrees are re-traversed; `if (!operands.Add(expression)) return;` would both dedupe and prune. No realistic query was constructible where this is more than a constant factor — `RewriteNullSemantics` duplicates operands into `IS NULL`/`IS NOT NULL` nodes, and recursion stops at those — so the exponential-blowup concern is anchor 25. `minor, out of reach` regardless.

No SQL Server instance was available to check whether `NULL / 0` raises there. Anchor 25 — [Unverified].
