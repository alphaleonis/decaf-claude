## Findings

### #1 🔴 Critical: `NullPropagatedOperands` treats `AndAlso`/`OrElse` operands as null-propagating, so a live `IS NOT NULL` guard is deleted

| | |
|---|---|
| **File** | `src/EFCore.Relational/Query/SqlNullabilityProcessor.cs:626` |
| **Category** | null-safety / silent-wrong-results |
| **Confidence** | 100 — confirmed by executed differential probe |
| **Found by** | adversarial-reviewer (High), broad-reviewer (Critical), quick-reviewer (High) |

**Issue:**

The optimization added at line 578 is sound only under this contract:

> dropping `X IS NOT NULL` from the test is valid **iff** `X IS NULL` implies `<result> IS NULL`.

`NullPropagatedOperands` is what decides which `X` satisfy that, and at lines 626-630 it recurses into **both operands of every `SqlBinaryExpression`**, unconditionally:

```csharp
else if (expression is SqlBinaryExpression binary)
{
    NullPropagatedOperands(binary.Left, operands);
    NullPropagatedOperands(binary.Right, operands);
}
```

`SqlBinaryExpression.IsValidOperator` (`src/EFCore.Relational/Query/SqlExpressions/SqlBinaryExpression.cs:93,95,102`) admits `AndAlso`, `OrElse`, and `Coalesce` alongside the arithmetic, bitwise, and comparison operators. Under SQL three-valued logic neither logical operator propagates NULL:

- `UNKNOWN AND FALSE` → `FALSE`
- `UNKNOWN OR TRUE` → `TRUE`

So an operand buried under an `AndAlso`/`OrElse` lands in `nullPropagatedOperands` even though its NULL-ness does **not** force the result to NULL. `DropNotNullChecks` then deletes the guard that was the only thing producing NULL.

This is not a theoretical shape. EF's own null-semantics rewrite *produces* `AndAlso`/`OrElse` inside when-clause results — `RewriteNullSemantics` (same file, ~line 1878) turns `A == B` into `A = B AND B IS NOT NULL` when `A` is known non-nullable (which it is, because the very test being dropped registered it in `_nonNullableColumns`). The optimization therefore attacks precisely the expressions its own precondition creates.

**Confirmed failure** (executed — see [Probe Evidence](#probe-evidence)):

```csharp
ss.Set<Ent>().Select(x => x.NullableIntA != null ? (bool?)(x.NullableIntA == x.NullableIntB) : null)
```

| | Sqlite SQL | row `A=NULL, B=NULL` |
|---|---|---|
| base `051c33a79` | `CASE WHEN "NullableIntA" IS NOT NULL THEN "NullableIntA" = "NullableIntB" AND "NullableIntB" IS NOT NULL ELSE NULL END` | `null` ✅ |
| this change | `"NullableIntA" = "NullableIntB" AND "NullableIntB" IS NOT NULL` | **`False`** ❌ |

`NULL = NULL` → UNKNOWN; `UNKNOWN AND FALSE` → FALSE. The guard that produced `null` is gone.

The same rewrite lands on SQL Server (`CASE WHEN [NullableIntA] = [NullableIntB] AND [NullableIntB] IS NOT NULL THEN CAST(1 AS bit) ELSE CAST(0 AS bit) END`), so this is provider-independent.

**Fix:** restrict the recursion to operators that genuinely propagate NULL from operand to result, and exclude `AndAlso`, `OrElse`, and `Coalesce`:

```csharp
else if (expression is SqlBinaryExpression
         {
             OperatorType: ExpressionType.Add or ExpressionType.Subtract
                 or ExpressionType.Multiply or ExpressionType.Divide or ExpressionType.Modulo
                 or ExpressionType.And or ExpressionType.Or or ExpressionType.ExclusiveOr
                 or ExpressionType.Equal or ExpressionType.NotEqual
                 or ExpressionType.LessThan or ExpressionType.LessThanOrEqual
                 or ExpressionType.GreaterThan or ExpressionType.GreaterThanOrEqual
         } binary)
{
    NullPropagatedOperands(binary.Left, operands);
    NullPropagatedOperands(binary.Right, operands);
}
```

An allow-list rather than a deny-list is the right shape here: a future `ExpressionType` added to `IsValidOperator` then fails closed (missed optimization) instead of open (wrong data).

Note the comparison operators in that list are only safe once finding #2 is also fixed — see below.

### #2 🟠 High: boolean-valued results are not null-propagating in a value position; the enclosing `CASE` is the only thing producing NULL

| | |
|---|---|
| **File** | `src/EFCore.Relational/Query/SqlNullabilityProcessor.cs:578` (guard absent), reached via `:621` and `:626` |
| **Category** | null-safety / silent-wrong-results |
| **Confidence** | 100 — confirmed by generated-SQL inspection against the base commit |
| **Found by** | adversarial-reviewer (High) |

**Issue:**

`NullPropagatedOperands` reasons purely about the SQL expression tree, and walks into the operands of comparison binaries (`Equal`, `NotEqual`, `LessThan`, …) and of `SqlUnaryExpression { OperatorType: Not }` (line 621) on the assumption "operand is NULL ⇒ result is NULL/UNKNOWN". That assumption is true *at the SQL level* but is destroyed by the **next stage of the pipeline**.

SQL Server cannot project a predicate as a value, so `SearchConditionConvertingExpressionVisitor` materializes one. `VisitCase` sets `_isSearchCondition = false` for the when-clause result (`src/EFCore.SqlServer/Query/Internal/SearchConditionConvertingExpressionVisitor.cs:118-127`), and `ConvertToValue` (same file, lines 41-51) then emits:

```csharp
CASE WHEN <predicate> THEN CAST(1 AS bit) ELSE CAST(0 AS bit) END
```

**UNKNOWN maps to `0` (false), never to NULL.** The outer `CASE WHEN X IS NOT NULL … ELSE NULL END` was the *only* construct carrying NULL out to the `bool?` projection. The new optimization deletes it, and nothing downstream restores it.

**Confirmed failure** (generated SQL, executed — see [Probe Evidence](#probe-evidence)):

```csharp
ss.Set<Ent>().Select(x => x.NullableStringA != null ? (bool?)(x.NullableStringA != x.StringA) : null)
```

base `051c33a79`:
```sql
SELECT CASE
    WHEN [e].[NullableStringA] IS NOT NULL THEN CASE
        WHEN [e].[NullableStringA] <> [e].[StringA] THEN CAST(1 AS bit)
        ELSE CAST(0 AS bit)
    END
    ELSE NULL
END
FROM [Ents] AS [e]
```

this change:
```sql
SELECT CASE
    WHEN [e].[NullableStringA] <> [e].[StringA] THEN CAST(1 AS bit)
    ELSE CAST(0 AS bit)
END
FROM [Ents] AS [e]
```

The emitted SQL now has **no NULL branch at all** — the projection can never yield `null` for any row. For `NullableStringA IS NULL` the predicate is UNKNOWN, falls to `ELSE`, and materializes as `false`; the correct answer is `null`. This is provable from the SQL text alone, no server required.

The same holds for a bare comparison against a constant — `x.NullableIntA != null ? (bool?)(x.NullableIntA > 0) : null` becomes `CASE WHEN [NullableIntA] > 0 THEN 1 ELSE 0 END`, `false` where `null` is required — and for the `Not` arm at line 621 when its operand is boolean (`NOT` over integers, i.e. bitwise `~`, is fine; `Negate` and `Convert` are fine).

This is distinct from finding #1 and survives fixing it: here the SQL-level operator *does* propagate NULL correctly; the loss happens in the provider's predicate-to-value conversion.

**Fix:** exclude search-condition results from the optimization entirely, at the entry guard on line 578:

```csharp
if (testIsCondition
    && whenClauses is [var clause]
    && IsNull(elseResult)
    && clause.Result.Type.UnwrapNullableType() != typeof(bool))
```

The optimization is correct for value-typed results (which is what every updated baseline in this changeset exercises — `CAST(LEN(...) AS int)`, string concatenation, `~`, `+`) and wrong for boolean ones. Nothing in the new code currently distinguishes them.

An alternative — re-visiting the result with the `_nonNullableColumns` assumption removed — is more general but substantially more invasive; the type guard is the cheap correct fix.

## Specialist Notes

### Considered But Not Flagged (all agents)

**adversarial-reviewer** — scenarios constructed and collapsed:

- **`Coalesce` as a `SqlBinaryExpression`.** `SqlBinaryExpression.IsValidOperator` permits it and `COALESCE(a,b)` is emphatically not null-propagating, so the line 626 recursion would be unsound. Collapsed on reachability: `RelationalSqlTranslatingExpressionVisitor` routes every `Coalesce` to `SqlExpressionFactory.Coalesce`, which builds a `SqlFunctionExpression` with `argumentsPropagateNullability: [false, false]` (`src/EFCore.Relational/Query/SqlExpressionFactory.cs:502-509`) — correctly handled by the function branch at line 631. Verified independently by the orchestrator. A third-party provider constructing `MakeBinary(ExpressionType.Coalesce, …)` directly would still hit it; folded into finding #1's allow-list at zero cost.
- **`SqlBinaryExpression { And, Or, ExclusiveOr }`.** Boolean `And`/`Or` are converted to `AndAlso`/`OrElse` before reaching here, so these only arrive as integer bitwise ops, which do propagate NULL. Sound.
- **String `Add`.** `AddNullConcatenationProtection` wraps nullable operands in `COALESCE(x, '')`, whose `argumentsPropagateNullability` is `[false, false]`, so the wrapped operand is correctly *not* collected. The `Is_not_null_optimizes_binary_op_with_partial_checks` baseline is correct.
- **`HashSet<SqlExpression>` equality.** `ColumnExpression`, `SqlBinaryExpression` and `SqlUnaryExpression` all override `Equals`/`GetHashCode` structurally; a mismatch could only cause a *missed* optimization, never an unsound one.
- **`nullable` out-parameter after the early `return clause.Result`.** `elseResult` is a null constant, so `nullable` is already `true` at that point. Over-reporting nullability is conservative.
- **Type mapping / collation loss on `return clause.Result`.** `CaseExpression`'s constructor derives `Type` and `TypeMapping` from `whenClauses[0].Result`, and `ApplyTypeMappingOnCase` pushes the mapping down into each result, so both are preserved.
- **`ArgumentsPropagateNullability` / `Arguments` count mismatch** at lines 640-645. The `SqlFunctionExpression` constructor throws `InconsistentNumberOfArguments` unless the counts match, so the indexed loop cannot go out of range.
- **`func.Instance!` NRE** at line 635, and `func.ArgumentsPropagateNullability` NRE when `niladic: false, arguments: null`. Both require constructor argument combinations no in-tree caller produces. Recorded `pre-existing, out of reach`.

**test-reviewer** — no findings. Verified the `NullSemanticsData` seed is a 3×3×3 matrix (27 rows) over `[0, 1, null]` / `["Foo", "Bar", null]`, which does exercise the NULL combinations the five new tests need; the `public virtual` + provider-override pattern matches siblings in the same file; and the updated GearsOfWar baselines still assert meaningful behavior.

Worth noting against finding #2: every one of the five new tests and every updated baseline in this changeset uses a **value-typed** result (`~int`, `int + int`, string concatenation, `CAST(LEN(...) AS int)`). The boolean-result shape is not covered anywhere in the changeset, which is why the test suite is green despite the defect. Under `reach=narrow` a coverage gap is not reportable as a finding, but it explains the absence of a failing test.

**quick-reviewer / broad-reviewer** — both dismissed expression-identity and `HashSet` equality concerns on the same (correct) reasoning: those can only suppress the optimization, never make it unsound.
