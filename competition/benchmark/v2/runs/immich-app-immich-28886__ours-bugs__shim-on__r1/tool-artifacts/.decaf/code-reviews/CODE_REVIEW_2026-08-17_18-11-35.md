### #1 🟠 High: Deleting an already-merged migration aborts server startup for every database that ran it

| | |
|---|---|
| **File** | `server/src/schema/migrations/1780592070031-ConvertNegativeRatingToNull.ts:1` (deleted) |
| **Category** | production |
| **Confidence** | 75 |
| **Verified** | traced |
| **Pre-existing** | no |
| **Found by** | solo-reviewer (High) |

**Issue:** Kysely's `Migrator` refuses to run when a migration recorded in `kysely_migrations` has no corresponding file. `ConvertNegativeRatingToNull` was merged to `main` in `99281de` on 2026-06-04 and HEAD is 2026-06-07 — three days during which every `main`/nightly deployment and every contributor's local database applied it. Those databases now fail at boot with `corrupted migrations: previously executed migration 1780592070031-ConvertNegativeRatingToNull is missing`, and there is no recovery path short of hand-editing `kysely_migrations`.

**Evidence:** `server/src/repositories/database.repository.ts:371-394` calls `migrator.migrateToLatest()` and rethrows any error, and `:510-523` constructs the `Migrator` with `FileMigrationProvider` over `schema/migrations`. In `server/node_modules/kysely/dist/cjs/migration/migrator.js:447` the missing-file check runs **unconditionally**:

```js
this.#ensureNoMissingMigrations(migrations, executedMigrations);
if (!this.#allowUnorderedMigrations) {
    this.#ensureMigrationsInOrder(migrations, executedMigrations);
}
```

and at `:491-497` it throws `corrupted migrations: previously executed migration ${executed} is missing`. `allowUnorderedMigrations` (set from `isDev()` at `database.repository.ts:514`) guards only the *ordering* check, so dev environments are not exempt. No Postgres was stood up to reproduce the abort; the mechanism is settled by the library source. Note also that the data damage is not undone by deleting the file — ratings already nulled to `NULL` on nightly databases stay lost, and this change ships no compensating migration.

**Fix:** Do not delete the file. Replace its body with a no-op (`export async function up(): Promise<void> {}`) so the recorded migration still resolves, or — if the intent is to also stop the data loss for databases that have *not* yet migrated — keep the file and make `up()` a no-op in place. The precedent at `0975b15` ("remove stray migration") deleted a migration named `Test`, which is a different situation from one that shipped on `main` and did real work.

**Issue:** `BaseSearchSchema.rating` still carries `.min(1)` from `99281de`. With `-1` re-admitted on the write path, a user can mark an asset "rejected" but every attempt to filter for rejected assets — metadata search, random search, smart search, statistics — returns HTTP 400. The "rejected" state becomes write-only and invisible.

**Evidence:** Executed against the real DTOs in a scratch spec (since removed):

```
UpdateAssetDto    rating=-1  OK  -> {"rating":-1}
MetadataSearchDto rating=-1  ERR -> too_small, minimum 1, "Too small: expected number to be >=1"
```

The same asymmetry is baked into the published contract: `UpdateAssetDto.rating` and `AssetBulkUpdateDto.rating` now describe `-1 (rejected)`, while `MetadataSearchDto`/`RandomSearchDto`/`SmartSearchDto`/`StatisticsSearchDto` all still declare `minimum: 1` in `open-api/immich-openapi-specs.json`. A client reading the spec gets two contradictory accounts of `-1`.

**Fix:** Apply the same allowance to `server/src/dtos/search.dto.ts:36-49` — accept `-1` alongside `1-5` and `null` — and reconcile its `HistoryBuilder` chain with `asset.dto.ts:24-29` so both fields tell the same story about `-1`. Regenerate the spec afterward.

### #3 🟠 High: XMP `Rating: -1` is still discarded on import, so "rejected" does not round-trip

| | |
|---|---|
| **File** | `server/src/services/metadata.service.ts:308` |
| **Category** | correctness |
| **Confidence** | 100 |
| **Verified** | traced |
| **Pre-existing** | no |
| **Found by** | solo-reviewer (High) |

**Issue:** Metadata extraction clamps to `[1, 5]`, so a `-1` in a sidecar or embedded XMP is silently converted to `NULL`. `-1` is the XMP convention for "rejected" (Lightroom/Bridge), which is the reason the value exists at all — so re-enabling `-1` in the API while the ingest path still drops it means the feature only half-works. Worse, immich *writes* `-1` back out: `metadata.service.ts:509,523` puts `Rating: asset.exifInfo.rating ?? 0` into the sidecar. Immich therefore emits a `-1` it will refuse to read back.

**Evidence:** `metadata.service.ts:308` reads `rating: exifTags.Rating === 0 ? null : validateRange(exifTags.Rating, 1, 5)`, and `validateRange` at `:107-117` returns `null` when `val < min`. For `Rating = -1`: `-1 < 1` → `null`. Import of a rejected photo lands `rating = NULL`.

Whether an existing user-set `-1` gets clobbered by a *refresh* was checked: it does not. `asset.service.ts:518-526` calls `updateLockedColumns(...)` with `lockedPropertiesBehavior: 'append'`, `rating` is in `lockableProperties` (`server/src/database.ts:506-514`), and extraction upserts with `lockedPropertiesBehavior: 'skip'`. So the damage is confined to the ingest path — real, but narrower than a full data-loss scenario. `99281de` deleted the test that covered exactly this (`metadata.service.spec.ts`, "should handle valid negative rating value"), and it has not been restored.

**Fix:** Restore `validateRange(exifTags.Rating, -1, 5)` at `metadata.service.ts:308`. The `exifTags.Rating === 0 ? null` guard already ahead of it keeps `0` out, so `-1` and `1-5` are the only values that survive.

### #4 🟡 Medium: The generated API contract loses its rating bounds entirely (avoidable)

| | |
|---|---|
| **File** | `server/src/dtos/asset.dto.ts:17-21` |
| **Category** | api-design |
| **Confidence** | 100 |
| **Verified** | executed |
| **Pre-existing** | no |
| **Found by** | solo-reviewer (Medium) |

**Issue:** Moving the bounds from `.min()/.max()` checks into a `.refine()` predicate makes them invisible to the JSON-Schema emitter. `UpdateAssetDto.rating` and `AssetBulkUpdateDto.rating` now publish `minimum: -9007199254740991, maximum: 9007199254740991` — `z.int()`'s bare safe-integer range. Spec-driven consumers (validating gateways, mock servers, contract tests, code generators) will now accept `rating: 4096` and only discover the rejection at runtime. The noise propagates into the generated Dart client, which documents `Minimum value: -9007199254740991`.

**Evidence:** Confirmed in the committed spec (`node -e` over `open-api/immich-openapi-specs.json`): `UpdateAssetDto` and `AssetBulkUpdateDto` show `{"minimum":-9007199254740991,"maximum":9007199254740991}`, while every other rating field still shows `{"minimum":1,"maximum":5}`. Also visible in `mobile/openapi/lib/model/update_asset_dto.dart` and `asset_bulk_update_dto.dart`.

This is avoidable. `z.toJSONSchema` was run on three formulations:

```
current  -> {"type":"integer","minimum":-9007199254740991,"maximum":9007199254740991}
bounded  -> {"type":"integer","minimum":-1,"maximum":5}            // .min(-1).max(5).refine(v => v !== 0)
unioned  -> {"anyOf":[{"const":-1},{"type":"integer","minimum":1,"maximum":5}]}
```

**Fix:** Keep the structural bounds and use the refine only for the hole at `0`:

```ts
rating: z
  .int()
  .min(-1)
  .max(5)
  .refine((v) => v !== 0, { error: 'Must be -1, a number from 1 to 5, or null' })
  .nullish()
```

This preserves `minimum: -1, maximum: 5` in the spec, restores the `.nullish()` idiom used by every sibling field in this file, and still rejects `0`, `6`, `-2`. Regenerate the spec and clients afterward.

**Issue:** `99281de` tightened the *response* schema to `z.int().min(1).max(5)`. **Evidence:** `open-api/immich-openapi-specs.json` `ExifResponseDto.properties.rating` = `{"minimum":1,"maximum":5,"type":"integer","nullable":true}`. **Fix:** Widen `exif.dto.ts:32` to admit `-1` in step with the write path (e.g. `z.int().min(-1).max(5).nullish().default(null)`), and regenerate the spec.
