## Findings

### #1 🟠 High: Parse-time rejection discards responses that previously delivered posts, breaking existing integrations

| | |
|---|---|
| **File** | `server/public/model/command_response.go:72` |
| **Category** | api-design |
| **Confidence** | 75 |
| **Verified** | traced |
| **Pre-existing** | no |
| **Found by** | solo-reviewer (High) |

**Issue:** Calling `IsValid()` inside `CommandResponseFromJSON` turns a previously lenient parser into an all-or-nothing gate on two live integration ingress paths, with no config flag, deprecation window, or fallback. The regression is not merely "invalid input now errors" — **valid parts of a response that used to be delivered are now dropped.**

Concretely, for `{"response_type": "in_channel", "text": "...", "extra_responses": [{"response_type": "comment", "text": "..."}]}`:

- **Before:** `CommandResponseFromHTTPBody` returned the struct. `HandleCommandResponse` (`server/channels/app/command.go:604-613`) posted the parent via `CreateCommandPost`, which matched the `in_channel` branch at `command.go:73` and created the post. The nested response matched neither branch at `command.go:73` nor `command.go:82`, so it silently produced nothing — but the parent post was delivered.
- **After:** the whole parse fails. `command.go:595` wraps it into `api.command.execute_command.failed.app_error` (HTTP 500) and `web/webhook.go:114` into `web.command_webhook.parse.app_error` (HTTP 400). **Nothing is posted at all**, and the user sees a command failure.

The same asymmetry applies to `Text` length: a >64 KiB parent previously failed at `Post.IsValid` while `HandleCommandResponse`'s loop still delivered every `extra_responses` entry (it accumulates into `lastError` rather than aborting). Now the parse aborts before any post is attempted.

**Evidence:** Traced end-to-end. Reachability of both callers confirmed: `server/channels/app/command.go:595` (outgoing slash commands) and `server/channels/web/webhook.go:114` (command webhooks) both route JSON bodies through `CommandResponseFromHTTPBody` → `CommandResponseFromJSON`. The pre-change fall-through in `CreateCommandPost` is at `server/channels/app/command.go:73` and `:82`; the extra-response loop that used to survive a bad sibling is at `server/channels/app/command.go:604-613`. Counter-argument considered: the pre-change behavior (silently no post) was itself poor, so hard-failing is arguably an improvement — but the fix as written converts a partial-delivery degradation into a total-delivery failure, which is strictly worse for the integrations that work today.

**Fix:** Do not validate in the parser. Either (a) validate at the use site — `HandleCommandResponsePost` / `CreateCommandPost` — so a bad nested response fails only itself and the parent still posts, matching the existing `lastError` accumulation pattern; or (b) if parse-time rejection is really wanted, scope it to the top-level response only and log-and-drop invalid `ExtraResponses` entries rather than failing the whole payload. Either way this needs a changelog entry, since it is a behavior change on a public integration contract.

### #3 🟡 Medium: The 65535 limit counts bytes while every limit that actually governs this text counts runes, so it neither matches nor protects the real constraint

| | |
|---|---|
| **File** | `server/public/model/command_response.go:85` |
| **Category** | correctness |
| **Confidence** | 100 |
| **Verified** | executed |
| **Pre-existing** | no |
| **Found by** | solo-reviewer (Medium) |

**Issue:** `len(o.Text)` is a byte count. The limit this text is ultimately subject to is `Post.IsValid`, which uses `utf8.RuneCountInString(o.Message) > maxPostSize` (`server/public/model/post.go:508`) against a **configurable, DB-derived** `maxPostSize` (`server/channels/app/post.go:2409` → `GetMaxPostSize`), whose reference value is `PostMessageMaxRunesV2 = 16383` (`server/public/model/post.go:73`). The two checks therefore disagree in both direction and unit:

- Text that passes the new check still fails downstream (multibyte text under 64 KiB but over the rune limit).
- Text that fails the new check may have been under the real limit had the deployment configured a larger post size.

The check also adds no resource protection, because both ingress paths already bound the payload: `io.LimitReader(resp.Body, MaxIntegrationResponseSize)` = 1 MiB at `server/channels/app/command.go:586`, and `http.MaxBytesReader` on `MaximumPayloadSizeBytes` at `server/channels/web/handlers.go:216`. And `65535` is written as a bare local literal despite `PostMessageMaxBytesV2 = 65535` already existing at `server/public/model/post.go:72`.

**Evidence:** Executed against the built package:

```
30000 CJK runes (90000 bytes): resp_nil=true  err=... text is too long
21845 CJK runes (65535 bytes): resp_nil=false err=<nil>   (PostMessageMaxRunesV2=16383)
```

The second line is the failure: 21845 runes sails through the new "validation" and is then rejected by `Post.IsValid` at the post layer anyway — the check does not enforce the constraint it appears to enforce.

**Fix:** Drop the length check here (the post layer already enforces the real, configurable limit), or, if a model-level bound is wanted, use `utf8.RuneCountInString` against a named constant and reconcile it with `GetMaxPostSize` so the two cannot disagree.

### #4 🟡 Medium: The length limit is bypassed entirely by sending `Content-Type: text/plain`

| | |
|---|---|
| **File** | `server/public/model/command_response.go:35` |
| **Category** | correctness |
| **Confidence** | 100 |
| **Verified** | executed |
| **Pre-existing** | no |
| **Found by** | solo-reviewer (Medium) |

**Issue:** `CommandResponseFromHTTPBody` routes only `application/json` bodies through `CommandResponseFromJSON`; anything else goes to `CommandResponseFromPlainText` (line 40), which never validates. The change therefore introduces an enforcement asymmetry that did not exist before: the same integration can evade the new `Text` limit by flipping one response header. Any caller reading this code will reasonably assume `CommandResponseFromHTTPBody` returns a validated response — it does so only for half its inputs.

**Evidence:** Executed:

```
text/plain body: len=100000 err=<nil>
plaintext len=200000 IsValid=CommandResponse.IsValid: ... text is too long
```

A 100 000-byte `text/plain` body parses with no error, while the identical text fails `IsValid()` when reached through the JSON path — proving the check exists but is not on the path.

**Fix:** Call `IsValid()` in `CommandResponseFromHTTPBody` (or in `CommandResponseFromPlainText`) so both branches enforce the same contract — or drop the length check per #3, which makes the asymmetry moot.

### #5 🟡 Medium: The Go client now rejects valid 200 responses from the server, including plugin-produced ones

| | |
|---|---|
| **File** | `server/public/model/command_response.go:72` |
| **Category** | api-design |
| **Confidence** | 50 |
| **Verified** | traced |
| **Pre-existing** | no |
| **Found by** | solo-reviewer (Medium) |

**Issue:** `CommandResponseFromJSON` is not only a server-side ingestion helper — `Client4.ExecuteCommand` (`server/public/model/client4.go:5961`) and `Client4.ExecuteCommandWithTeam` (`:5982`) use it to decode the *server's own* response. That response is produced by `App.ExecuteCommand` and JSON-encoded verbatim at `server/channels/api4/command.go:427`, and it includes responses returned by plugins through the `ExecuteCommand` hook (`server/public/plugin/hooks.go:129`), which is free to set any `ResponseType` and is never validated server-side.

Consequence: a plugin returning a non-standard `response_type` produces a successful HTTP 200 that the webapp renders fine, but that `Client4` — and therefore `mmctl` and every third-party Go consumer of the published `server/public` module — fails to decode, reporting `failed to decode command response`. The strictness is also inherited silently by every existing consumer of that module on upgrade, with no opt-out, because it lives in the parser rather than at a call site.

Note also that the closest sibling parse function, `IncomingWebhookRequestFromJSON` (`server/public/model/incoming_webhook.go:193-211`), deliberately does *not* validate — it parses, stringifies attachments, and returns. This change departs from that convention.

**Evidence:** Traced through `api4/command.go:421-429` (`json.NewEncoder(w).Encode(response)` on the value returned by `App.ExecuteCommand`) and `client4.go:5961`. Anchor is 50 rather than 75 because whether any deployed plugin actually emits a non-standard `response_type` is outside the diff and could not be confirmed; the decode path itself is certain.

**Fix:** Move validation out of the shared parser to the server-side ingestion sites, so the client keeps parsing whatever the server sends. If client-side validation is genuinely wanted, make it an explicit opt-in (a separate `CommandResponseFromJSONStrict`, or an `IsValid()` call at the call site) rather than a behavior change to an existing published function.

### #6 🟢 Low: A nested `extra_responses` failure is indistinguishable from a top-level one

| | |
|---|---|
| **File** | `server/public/model/command_response.go:95` |
| **Category** | production |
| **Confidence** | 100 |
| **Verified** | read |
| **Pre-existing** | no |
| **Found by** | solo-reviewer (Low) |

**Issue:** The recursive call returns the child's `*AppError` verbatim. Because the child constructs it with the same `Where` (`"CommandResponse.IsValid"`), the same `Id`, and the same `DetailedError` (`"invalid response type"`), the resulting error carries no index, path, or nesting marker. An integration author debugging a `400 web.command_webhook.parse.app_error` cannot tell whether the parent or the third `extra_responses` entry was at fault — which matters precisely because the whole payload is now rejected (#1).

**Evidence:** Read. Lines 82 and 87 hardcode `Where` and `DetailedError`; line 96 returns `err` unwrapped. The probe's rendered error for a nested failure is byte-identical to the top-level one.

**Fix:** Wrap the child error with the index, e.g. `return NewAppError("CommandResponse.IsValid", err.Id, nil, fmt.Sprintf("extra_responses[%d]: %s", i, err.DetailedError), http.StatusBadRequest)`, or pass a path prefix into a private `isValid(path string)` helper.

### #7 🟢 Low: The new length test cannot distinguish bytes from runes, leaving the ambiguity in #3 unguarded

| | |
|---|---|
| **File** | `server/public/model/command_response_test.go:167` |
| **Category** | tests |
| **Confidence** | 100 |
| **Verified** | read |
| **Pre-existing** | no |
| **Found by** | solo-reviewer (Low) |

**Issue:** The payload is `strings.Repeat("a", 65536)` — pure ASCII, where byte count and rune count are identical. The test therefore passes unchanged whether the implementation uses `len()` or `utf8.RuneCountInString()`, i.e. it does not pin the one property of this limit that is actually in question. Separately, all three new cases assert only `assert.Error` + `assert.Nil` and never check `AppError.Id`, so a case that started failing for an unrelated reason (a JSON syntax error in the fixture, say) would still be green — the third case's fixture at lines 173-179 is hand-indented multi-line JSON, exactly the kind that can acquire such a typo.

**Evidence:** Read. Each case does fail for the right defect today — removing the length check at line 86 makes case two return a non-nil response and trips `assert.Error` — so these are not tautological tests. The defect is that they under-specify: the assertions are weaker than the behavior being introduced.

**Fix:** Use a multibyte repeat (e.g. `strings.Repeat("中", …)`) so the unit is pinned, and assert the error identity, e.g. `var appErr *model.AppError; require.ErrorAs(t, err, &appErr); assert.Equal(t, "model.command_response.is_valid.text.app_error", appErr.Id)`. This would also have surfaced #2 during development.
