### #1 🔴 Critical: `NullPropagatedOperands` descends through `AndAlso`/`OrElse`, which do not propagate NULL — dropping the guard turns NULL results into `false`

| | |
|---|---|
| **File** | `src/EFCore.Relational/Query/SqlNullabilityProcessor.cs:626` |
| **Category** | correctness |
| **Confidence** | 100 |
| **Found by** | solo-reviewer (Critical) |
| **Verified** | executed (SQLite, real rows) + traced (SQL Server SQL text diffed against base commit) |

**Issue:** The `else if (expression is SqlBinaryExpression binary)` arm at line 626 treats *every*
binary operator as null-propagating and recurses into both operands. `AndAlso` and `OrElse` are not:
`NULL AND FALSE = FALSE` and `NULL OR TRUE = TRUE`. So for
`CASE WHEN x IS NOT NULL THEN (x AND y) ELSE NULL END`, `x` lands in `nullPropagatedOperands`,
`DropNotNullChecks` erases the guard, and the expression now yields `FALSE` where it previously
yielded `NULL`.

This is exactly the case the surrounding file already knows about: the long-standing
`ProcessNullNotNull` at `SqlNullabilityProcessor.cs:2314-2321` carries the guard
`when sqlBinaryOperand.OperatorType != ExpressionType.AndAlso && sqlBinaryOperand.OperatorType != ExpressionType.OrElse`,
with the comment *"for AndAlso, OrElse we can't do this optimization"*. The new helper omits that guard.

The `Not`/`Negate`/`Convert` unary arm (line 621) compounds it: `NOT` itself propagates, but recursing
through it reaches an `AndAlso`/`OrElse` underneath.

A second, subtler route into the same failure: `clause.Result` is visited with
`preserveColumnNullabilityInformation: true` and `_nonNullableColumns` seeded from the test, so the
result may have been *specialized under the assumption that the test holds*. `x.NIa == x.NIb` is
emitted as `NIa = NIb AND NIb IS NOT NULL` precisely because `NIa` was known non-null in that branch.
Dropping the guard invalidates the assumption the result was built on.

**Evidence:** SQLite, four rows (`Id=3: NB=NULL, B=false`; `Id=4: NB=NULL, B=true`), executed against
both commits via a standalone harness (see Session Metrics for probe method).

At base `051c33a79` — every case MATCH:
```
SELECT CASE WHEN "e"."NB" IS NOT NULL THEN "e"."NB" AND "e"."B" ELSE NULL END
db  : True, False, NULL, NULL      mem : True, False, NULL, NULL    MATCH
```
At `afcfba2e9`:
```
=== x.NB != null ? (bool?)(x.NB.Value && x.B) : null
SELECT "e"."NB" AND "e"."B"
db  : True, False, False, NULL     mem : True, False, NULL, NULL    *** MISMATCH ***   (row 3)

=== x.NB != null ? (bool?)(x.NB.Value || x.B) : null
SELECT "e"."NB" OR "e"."B"
db  : True, False, NULL, True      mem : True, False, NULL, NULL    *** MISMATCH ***   (row 4)

=== x.NB != null ? (bool?)!(x.NB.Value && x.B) : null
SELECT NOT ("e"."NB") OR NOT ("e"."B")
db  : False, True, True, NULL      mem : False, True, NULL, NULL    *** MISMATCH ***   (row 3)

=== x.NIa != null ? (bool?)(x.NIa == x.NIb) : null
SELECT "e"."NIa" = "e"."NIb" AND "e"."NIb" IS NOT NULL
db  : False, NULL, False, False    mem : False, NULL, False, NULL   *** MISMATCH ***   (row 4)
```
Four of six probes regress; the two controls (`NIa + NIb`, and the same expression used inside a
`WHERE ... IS NULL`) still match.

SQL Server (`ToQueryString()`, no server needed) shows the same regression and makes it starker — the
projection can no longer produce `NULL` at all:

- base → `SELECT CASE WHEN [e].[NB] IS NOT NULL THEN CASE WHEN [e].[NB] = CAST(1 AS bit) AND [e].[B] = CAST(1 AS bit) THEN CAST(1 AS bit) ELSE CAST(0 AS bit) END ELSE NULL END`
- after → `SELECT CASE WHEN [e].[NB] = CAST(1 AS bit) AND [e].[B] = CAST(1 AS bit) THEN CAST(1 AS bit) ELSE CAST(0 AS bit) END`

It also corrupts filtering, not just projection —
`Where(x => (x.NB != null ? (bool?)(x.NB.Value && x.B) : null) == false)` now matches rows where
`NB IS NULL`.

**Fix:** Mirror the existing `ProcessNullNotNull` guard — do not recurse into logical binaries:

```csharp
else if (expression is SqlBinaryExpression binary
    && binary.OperatorType is not (ExpressionType.AndAlso or ExpressionType.OrElse))
```

None of the five new `Is_not_null_optimizes_*` tests uses a boolean-typed result, which is why the
suite is silent about this. `x.NullableBoolA != null ? (bool?)(x.NullableBoolA.Value && x.BoolB) : null`
and `x.NullableIntA != null ? (bool?)(x.NullableIntA == x.NullableIntB) : null` against the
NullSemantics set both reproduce.

### #2 🔴 Critical: any boolean-typed `clause.Result` is unsafe on SQL Server, because search-condition conversion replaces the NULL branch with `CAST(0 AS bit)`

| | |
|---|---|
| **File** | `src/EFCore.Relational/Query/SqlNullabilityProcessor.cs:576` |
| **Category** | correctness |
| **Confidence** | 100 |
| **Found by** | solo-reviewer (Critical) |
| **Verified** | traced (SQL Server generated SQL diffed against base commit). Not executed — no SQL Server instance available in this environment. |

**Issue:** Fixing #1 is necessary but **not sufficient**. A plain comparison such as `x > 2` does
propagate NULL as a three-valued *condition*, so `NullPropagatedOperands` legitimately puts `x` in the
set and the guard is dropped. But on SQL Server the resulting search condition sits in a value
position, and `SearchConditionConvertingExpressionVisitor` (which runs *after* `SqlNullabilityProcessor`)
wraps it as `CASE WHEN <cond> THEN CAST(1 AS bit) ELSE CAST(0 AS bit) END`. SQL evaluates the `ELSE`
arm when the condition is UNKNOWN, so the three-valued NULL collapses to `false`. Under the old shape
the outer `ELSE NULL` guard preserved the NULL; without it, it is gone.

The invariant `NullPropagatedOperands` reasons about ("the value is NULL when `x` is NULL") does not
survive the boolean-to-bit lowering that happens downstream on SQL Server, and `SqlNullabilityProcessor`
has no visibility into that.

This is provider-dependent: SQLite emits the condition directly and is unaffected — so a SQLite-only
test run will not catch it.

**Evidence:** `ctx.Es.Select(x => x.NIa != null ? (bool?)(x.NIa > 2) : (bool?)null)`, `ToQueryString()`:

base `051c33a79`:
```sql
SELECT CASE
    WHEN [e].[NIa] IS NOT NULL THEN CASE
        WHEN [e].[NIa] > 2 THEN CAST(1 AS bit)
        ELSE CAST(0 AS bit)
    END
    ELSE NULL
END
FROM [Es] AS [e]
```
after `afcfba2e9`:
```sql
SELECT CASE
    WHEN [e].[NIa] > 2 THEN CAST(1 AS bit)
    ELSE CAST(0 AS bit)
END
FROM [Es] AS [e]
```
For `NIa IS NULL`, the base query returns `NULL`; the new query returns `0`. C# evaluation of the same
lambda returns `null`.

The same probe on SQLite (`SELECT "e"."NIa" > 2`) executed clean — `db: False, NULL, True, NULL`
matches in-memory — confirming this is specifically a SQL-Server-pipeline defect.

By contrast, `x.NS != null ? (bool?)x.NS.StartsWith("a") : null` is *not* optimized (the result is a
`LikeExpression`, which `NullPropagatedOperands` does not traverse), which is why the existing suite
stays green here — the hole is exactly `SqlBinaryExpression` comparisons.

**Fix:** Bail out of the optimization entirely when the result is a search condition. The cheapest
correct form is to require the result type not be boolean:

```csharp
if (testIsCondition
    && whenClauses is [var clause]
    && IsNull(elseResult)
    && clause.Result.Type != typeof(bool)
    && clause.Result.Type != typeof(bool?))
```

That also subsumes #1 for the `AndAlso`/`OrElse` cases on SQL Server, but #1 must still be fixed
independently — `NULL AND FALSE = FALSE` is wrong on SQLite too, where no bit conversion happens.

### #3 🟡 Medium: the null-propagation table is hardcoded in `EFCore.Relational` with no provider seam, but `+`/`||` concatenation is not NULL-strict in every SQL dialect

| | |
|---|---|
| **File** | `src/EFCore.Relational/Query/SqlNullabilityProcessor.cs:626` |
| **Category** | api-design |
| **Confidence** | 50 |
| **Found by** | solo-reviewer (Medium) |
| **Verified** | read only |

**Issue:** `NullPropagatedOperands` asserts a fixed, dialect-independent claim about arithmetic and
concatenation operators, and it lives in the shared relational base class that all providers —
including out-of-tree ones (Oracle, Firebird, and others built on `EFCore.Relational`) — inherit.
`Add` on string operands is the risky entry: [Inference, based on Oracle's documented treatment of the
empty string as NULL] on Oracle `'abc' || NULL` yields `'abc'`, not NULL. On such a provider the
newly-emitted `SELECT [A] + [B]` (see the `Select_null_propagation_optimization7` baseline) returns the
non-null operand where the old `CASE ... ELSE NULL END` returned NULL.

Unlike `SqlFunctionExpression`, where per-function nullability is provider-supplied metadata, the
binary-operator set here has no seam a provider can adjust short of overriding the whole of `VisitCase`.

**Evidence:** Read-only. `SqlNullabilityProcessor` is in `src/EFCore.Relational` and is the base for
every relational provider; the operator classification at line 626 admits no provider input. Oracle
behavior was not verified against a live database and cannot be from this environment — hence anchor 50.

**Fix:** Either restrict the binary arm to an explicit allow-list of numeric/comparison operators,
excluding `Add` when the operand type is `string`, or introduce a small
`protected virtual bool PropagatesNullability(SqlBinaryExpression)` seam so providers with non-strict
concatenation can opt out. The `TODO` on line 577 suggests more shapes are coming, which makes the seam
worth having now rather than later.

## Specialist Notes

### Strengths noted by the reviewer

- `SqlNullabilityProcessor.cs:631` — gating the function branch on `IsNullable: true` and reusing `InstancePropagatesNullability` / `ArgumentsPropagateNullability` is the right call. That metadata is already trusted by `ProcessNullNotNull` for the *stronger* biconditional `f(x) IS NULL ⟺ x IS NULL`; the new code only needs the weaker `x IS NULL ⟹ f(x) IS NULL`, so it inherits correctness rather than inventing a second null model.
- `SqlNullabilityProcessor.cs:638` — the `!func.IsNiladic` guard is genuinely load-bearing: for niladic functions `Arguments`/`ArgumentsPropagateNullability` are null, and `func.ArgumentsPropagateNullability.Count` would have thrown.
- `SqlExpressionFactory.cs:504` — the optimization is correct for `COALESCE` for a non-obvious reason: `Coalesce` never becomes a `SqlBinaryExpression` in the relational stack (`RelationalSqlTranslatingExpressionVisitor.cs:449` routes it to the factory), and the factory tags it `argumentsPropagateNullability: [false, false]`, so `NullPropagatedOperands` correctly refuses to descend.
- `SqlNullabilityProcessor.cs:595` — `DropNotNullChecks` deliberately handles only `AndAlso` and leaves `OrElse` intact, which is the conservative and correct choice for the *test* side.
- All five new `Is_not_null_optimizes_*` scenarios were executed against SQLite with null-bearing data and compared to in-memory evaluation — **all five match**, including the subtle `A || B || COALESCE(C, '')` shape in `Is_not_null_optimizes_binary_op_with_partial_checks`. The GearsOfWar baseline rewrites (`CAST(LEN(x) AS int) = 5`, `SELECT [c].[Name]`) are also semantically equivalent to what they replaced.

### Considered But Not Flagged (solo-reviewer)

- **`CONCAT_NULL_YIELDS_NULL` on SQL Server** (anchor 25) — the new `SELECT [A] + [B]` shape depends on the setting being ON, whereas the old `CASE ... ELSE NULL END` did not. Microsoft.Data.SqlClient sets `CONCAT_NULL_YIELDS_NULL ON` in its default connection options and the OFF setting is deprecated, so practical exposure is negligible. The reachable version of this concern is #3.
- **`HashSet<SqlExpression>` equality** (anchor 0) — `ColumnExpression.Equals` compares `Name`, `TableAlias`, `IsNullable`, plus `Type`/`TypeMapping` via `base.Equals`; `SqlBinaryExpression.Equals` is fully structural including `OperatorType`. Every constructible failure mode is a *missed* match (safe). No false-match path found.
- **`ExclusiveOr`, `And`, `Or` (bitwise) in the binary arm** (anchor 0) — T-SQL and SQLite bitwise operators are NULL-strict, and `RelationalSqlTranslatingExpressionVisitor.cs:441-442` rewrites boolean `And`/`Or` to `AndAlso`/`OrElse` before this code sees them, so the only non-strict operators reaching line 626 are the two named in #1.
- **`ExpressionType.Coalesce` as a `SqlBinaryExpression`** (anchor 0) — `SqlBinaryExpression.IsValidOperator` permits it, but it is never constructed in the relational stack (`RelationalSqlTranslatingExpressionVisitor.cs:449` routes `Coalesce` to the factory, which emits a `SqlFunctionExpression`). Cosmos has its own `SqlBinaryExpression` type and does not use this processor.
- **Aggregates in `clause.Result`** (anchor 25) — `NullPropagatedOperands` descends into `SqlFunctionExpression` arguments without distinguishing aggregates, so `CASE WHEN [Key] IS NOT NULL THEN SUM([Key]) ELSE NULL END` would collapse to `SUM([Key])`. Every constructible instance is equivalent (any column legally referenceable in the test is a grouping key, constant within the group); no valid-SQL counterexample found.
- **`nullable` out-parameter on the early `return clause.Result` (line 587)** (anchor 0) — `IsNull(elseResult)` implies the ELSE arm was visited as nullable, so `nullable` is already `true` on that path. Over-reporting nullability is the safe direction.
- **`RestoreNullValueColumnsList(currentNonNullableColumnsCount)` at line 539** — passes the *non-nullable* columns counter to the *null-value* columns restore. Present at `051c33a79` and untouched by this change: **pre-existing, out of reach** (`reach=narrow`).
- **Probe decided against**: mutation-testing the five new `Is_not_null_optimizes_*` tests by reverting the production hunk to confirm they fail. The repo's test projects do not build on the available SDK, so the probe could not have produced a signal; the five scenarios were validated end-to-end through the standalone harness instead.
