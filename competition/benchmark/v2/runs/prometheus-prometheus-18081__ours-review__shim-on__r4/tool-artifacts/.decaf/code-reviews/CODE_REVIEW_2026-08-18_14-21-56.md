## Findings

### #1 🔴 Critical: `@`-anchored range selectors stop counting toward the existing `totalQueryableSamples` and `prometheus_engine_query_samples_total`

| | |
|---|---|
| **File** | `promql/engine.go:2145` (comment at 2143; increment at 2183) |
| **Category** | correctness / regression in existing contract |
| **Confidence** | 100 |
| **Verified** | measured base-vs-HEAD on a clean clone of `efbdc3f88` |
| **Found by** | design-reviewer (Critical), broad-reviewer (High), knowledge-reviewer (MUST), adversarial-reviewer (High), quick-reviewer (Medium), performance-reviewer (noted, out of persona scope) |

**Issue:** The change replaces

```go
ev.samplesStats.IncrementSamplesAtStep(step, int64(len(floats)+totalHPointSize(histograms)))
```

with a loop-scoped `var fullWindowCount, samplesReadCount int64` (line 2145) that is assigned **only inside** `if ts == ev.startTimestamp || selVS.Timestamp == nil` (line 2149). `floats`/`histograms` are declared *outside* the per-step loop and are deliberately retained across steps when an `@` modifier lets the engine reuse the window. The old code read those retained slices at increment time, so every step counted the full window. The new locals reset to `0` each iteration, so every step after the first adds nothing.

This is reachable because `preprocessExprHelper` never wraps a `*parser.MatrixSelector` argument in a `StepInvariantExpr` (`promql/engine.go:4364` — "functions over range vectors evaluate those directly"). So whenever the *enclosing call* is not step-invariant — because the function is in `AtModifierUnsafeFunctions` (`predict_linear`), or because a sibling argument is not invariant — the `@`-carrying selector reaches this multi-step loop with `selVS.Timestamp != nil`.

Measured, range query `start=201s end=220s step=5s`, `m1 1+1x100` at `load 10s`:

| Query | base `totalQueryableSamples` | HEAD | perStep base → HEAD |
|---|---|---|---|
| `predict_linear(m1[60s] @ 30, 60)` | 16 | **4** | `[4,4,4,4]` → `[4,0,0,0]` |
| `quantile_over_time(scalar(m1), m1[60s] @ 30)` | 20 | **8** | `[5,5,5,5]` → `[5,1,1,1]` |
| `quantile_over_time(0.5, m1[60s] @ 30)` *(is step-invariant)* | 16 | 16 | unchanged |
| `quantile_over_time(0.5, m1[60s])` *(no `@`)* | 24 | 24 | unchanged |

Two structurally identical `@` queries now report 16 vs 4. The consequences reach past the stats object: `Engine.exec` adds `q.sampleStats.TotalSamples` to `prometheus_engine_query_samples_total` (`promql/engine.go:685`), so an operator's capacity and abuse dashboards under-report these queries by ~`numSteps`.

Three separate things now assert the opposite of what the code does:
- the comment added on line 2143 — "Full window count for TotalSamples (**unchanged semantics**)";
- the struct doc amended by this same change, `util/stats/query_stats.go:276` — "For range-vector functions, each step counts the full window at that step";
- the pre-existing recorded intent at `util/stats/query_stats.go:271-275` — per-step totals "intentionally do not account for optimizations that happen inside the range query engine that reduce the actual work".

No expectation in `promql/engine_test.go` was modified by this diff, and the suite has no case pairing an `@`-anchored range-vector argument with a non-invariant sibling — which is why CI is green.

**Fix:** compute the full-window count unconditionally, and gate only the new read count on whether a read actually happened:

```go
var fullWindowCount, samplesReadCount int64
if ts == ev.startTimestamp || selVS.Timestamp == nil {
    ...
    floats, histograms = ev.matrixIterSlice(it, mint, maxt, floats, histograms)
    if step == 0 {
        samplesReadCount = int64(len(floats) + totalHPointSize(histograms))
    } else {
        samplesReadCount = countSamplesAfter(floats, histograms, maxt-ev.interval)
    }
}
// Reused window (@ modifier): no new I/O, but the full window still counts
// toward TotalSamples — see util/stats/query_stats.go:271-275.
fullWindowCount = int64(len(floats) + totalHPointSize(histograms))
```

If reducing `TotalSamples` here is in fact wanted, it is a separate breaking change to a shipped API field and metric, and needs its own note in `docs/querying/api.md` plus removal of the "unchanged semantics" claim — not a side effect of adding a counter.

### #2 🟠 High: `SamplesRead` double-counts subqueries, compounds with nesting depth, and exceeds `TotalSamples` — which its own struct doc says is impossible

| | |
|---|---|
| **File** | `promql/engine.go:1874` |
| **Category** | correctness / data model |
| **Confidence** | 100 |
| **Verified** | measured on this checkout; causally isolated by a revert probe in a separate clone |
| **Found by** | design-reviewer (High), go-reviewer (High), adversarial-reviewer (High ×2), test-reviewer (Critical, on the encoded expectations) |
| **Validation** | confirmed |

**Issue:** `evalSubquery` merges the subquery child's `SamplesRead` into the parent (line 1874), then returns a synthetic, already-materialized `*parser.MatrixSelector`. The outer range-vector loop iterates that matrix per step and calls `IncrementSamplesReadAtStep` again over the same in-memory data (line 2184). `TotalSamples` deliberately avoids exactly this — the pre-change comment read "Avoid double counting samples when running a subquery, those samples will be counted in later stage", and `MergeSamplesReadFromSubquery` pointedly does not merge it.

Measured, instant query at `t=600s`:

| Query | `totalQueryableSamples` | `samplesRead` | ratio |
|---|---|---|---|
| `m1[1m:10s]` — bare `SubqueryExpr`, no enclosing call | 6 | 6 | 1.0× |
| `sum_over_time(m1[1m:10s])` — via `evalSubquery` | 6 | **12** | 2.0× |
| `sum_over_time(sum_over_time(m1[1m:10s])[2m:10s])` | 12 | **46** | 3.8× |
| `sum_over_time(m1[1m])` — plain matrix selector | 6 | 6 | 1.0× |

Revert probe (isolated clone at HEAD, line 1874 disabled): 12 → **6**, and 46 → **12**. Line 1874 is causally responsible; the merge is additive on top of accounting the outer loop already performs. Nesting compounds because each level pulls up an already-doubled child total — the adversarial reviewer measured 6.4× at depth 3, and the inflation is unbounded in nesting depth on a query whose real storage cost barely grows. Since `SamplesRead` feeds `prometheus_engine_query_samples_read_total` (`promql/engine.go:686`), this is user-controllable inflation of a global counter.

The author was aware of single-level doubling: `promql/engine_test.go:1548` asserts `SamplesRead: 2` with the comment `// subquery + outer`. That does not rescue it, and the validator was explicit about why: the contract this change itself adds at `util/stats/query_stats.go:279-281` says `SamplesRead` "is the number of samples read (I/O) … elsewhere it equals TotalSamples". For a single-step instant query the delta rule degenerates to the full window, so that contract requires equality here — 12 vs 6 breaks the change's *internal* documentation, not merely the prose docs. And the outer re-read is from memory, so calling it I/O is wrong on the merits. Nothing in the suite asserts the nested case, so the compounding was never validated against any expectation at all.

**Fix:** count the subquery's reads once. Either drop the merge at line 1874 (mirroring the existing `TotalSamples` decision — the subquery's points are re-counted at the outer stage anyway), or suppress the outer `IncrementSamplesReadAtStep` when the matrix argument came from `evalSubquery` — the `matrixArg` path already has a marker in the deferred `Series = nil` closure. Then add a nesting-depth-≥2 test case, which is the coverage that would have caught the compounding.

### #3 🟠 High: unconditional per-step window rescan costs 50–62% of range-query evaluation time, on a path the feature flag does not gate

| | |
|---|---|
| **File** | `promql/value.go:195` (call site `promql/engine.go:2164`) |
| **Category** | performance |
| **Confidence** | 100 |
| **Verified** | `BenchmarkRangeQuery`, base vs HEAD, on a quiet tree after the wave joined |
| **Found by** | performance-reviewer (High) |
| **Validation** | waived — measured base-vs-HEAD |

**Issue:** `countSamplesAfter` linearly scans the **entire** range-vector window on every step:

```go
func countSamplesAfter(floats []FPoint, histograms []HPoint, cutoff int64) int64 {
	var n int64
	for _, f := range floats { if f.T > cutoff { n++ } }
	...
}
```

It is called once per series per step for every range-vector function (`promql/engine.go:2164`), turning per-step accounting into O(window × steps) per series. The window is already sorted by timestamp and the answer is always a suffix, so the scan is avoidable.

Critically, **nothing gates this on `promql-per-step-stats`** (off by default). The scan feeds the always-on `SamplesRead` aggregate behind `prometheus_engine_query_samples_read_total`, so every Prometheus server pays it on every range query, whether or not anyone asked for stats.

Measured, `-benchtime 3x -count 3`, base `efbdc3f88` vs HEAD:

| Benchmark | base | HEAD | delta |
|---|---|---|---|
| `BenchmarkRangeQuery/expr=rate(a_one[1d]),steps=1000` | 5.73–6.55 ms/op | 9.02–9.14 ms/op | **+50–58%** |
| `BenchmarkRangeQuery/expr=rate(a_hundred[1d]),steps=1000` | 549–562 ms/op | 888–894 ms/op | **+58–62%** |

Allocations are unchanged (`~994 KB`/`406 allocs` and `~3.3 MB`/`25008 allocs` in both), so the cost is pure CPU from the added scan. The `steps=1` variants of the same expressions move ~0–2%, which matches the added per-step work exactly. This is the hottest loop in Prometheus, and the shape that regresses (`rate` over a long range at many steps) is the ordinary dashboard query.

**Fix:** exploit the sorted order — scan backward from the tail and stop at the first point at or before `cutoff`, making the cost O(new points) rather than O(window); or track the boundary index incrementally across steps; or binary-search it. Add a benchmark that isolates this (see Minor / Testing Gaps).

### #5 🟡 Medium: the documented contract for `samplesRead` is false, in all four places it is stated

| | |
|---|---|
| **File** | `docs/feature_flags.md:48`, `docs/querying/api.md:247`, `util/stats/query_stats.go:279`, `web/api/v1/openapi_schemas.go:593` |
| **Category** | doc-vs-code contradiction |

| **Found by** | knowledge-reviewer (MUST), design-reviewer (Medium) |

**Issue:** Two independent errors, repeated across all four sites.

1. **"For other query types, this equals totalQueryableSamples"** is false. Measured: instant `sum_over_time(m1[1m:10s])` gives `totalQueryableSamples=6`, `samplesRead=12`; the step-invariant path gives `totalQueryableSamples=16`, `samplesRead=4`. ### #6 🟡 Medium: subquery per-step arrays are sized by the subquery's step count, which no limit bounds — 153 MB measured for one instant query

| | |
|---|---|
| **File** | `promql/engine.go:2397` |
| **Category** | resource exhaustion |
| **Confidence** | 100 |
| **Verified** | measured on this checkout with the flag on and off |
| **Found by** | design-reviewer (High) |
| **Validation** | waived — measured directly |

**Issue:** `stats.NewChildWithStepTracking(..., subqStart, subqEnd, subqInterval)` reaches `InitStepTracking`, which allocates **two** `[]int64` of `numSteps = (end-start)/interval + 1`. Here `numSteps` is the *subquery's* step count, derived from a user-supplied resolution. The API's step guard (`web/api/v1/api.go:631`, `end.Sub(start)/step > 11000`) bounds only the outer query — nothing bounds a subquery's `[range:resolution]`. The previous code called `NewChild()`, which returns `NewQuerySamples(false)` and allocates nothing.

Measured, instant query `count_over_time(m1[10000s:1ms])` (10,000,001 subquery steps):

| `promql-per-step-stats` | cumulative alloc |
|---|---|
| disabled | 154 MB |
| enabled | **307 MB** |

The +153 MB matches `2 × 10,000,001 × 8 B` exactly. None of it is charged against `query.max-samples`. Half is dead weight: the child also allocates `TotalSamplesPerStep`, which `MergeSamplesReadFromSubquery` explicitly never merges and nothing else reads.

Severity is Medium rather than High only because the allocation *is* gated on `EnablePerStepStats`, so reaching it needs the flag enabled plus `stats=all`.

**Fix:** stop sizing the child by the subquery step count — accumulate subquery reads directly into the outer step buckets (`evalSubquery` already knows the outer layout), or bucket the child array to the outer step count. At minimum have the subquery child allocate only `SamplesReadPerStep`, and charge the allocation against the sample budget.

### #7 🟡 Medium: `samplesReadPerStep` misattributes across mismatched grids — outer steps between subquery grid points report zero reads

| | |
|---|---|
| **File** | `promql/engine.go:2436` (block at 2425-2446) |
| **Category** | data model |
| **Confidence** | 100 |
| **Found by** | knowledge-reviewer, design-reviewer, adversarial-reviewer |
| **Validation** | confirmed, with a correction (see below) |

**Issue:** The block maps each subquery step timestamp onto one outer step by ceiling division:

```go
outerStep = int((tk - ev.startTimestamp + ev.samplesStats.Interval - 1) / ev.samplesStats.Interval)
```

This is a **one-to-one point mapping**, not a proportional distribution across the steps whose windows actually consume the data. When the subquery grid is coarser than the outer grid, outer steps whose buckets fall strictly between two mapped timestamps receive nothing, even though real I/O occurred in their window. Measured: `sum_over_time(rate(m1[1m])[5m:1m])`, range 600→660s step 30s → `samplesReadPerStep = {600:35, 630:0, 660:7}` — the middle step reads zero because the subquery steps at 1m skip it.

Separately, the two boundary rules concentrate reads structurally: everything at or before `ev.startTimestamp` lands on step 0 (`if tk > ev.startTimestamp`, line 2436) and everything past the last outer step is clamped onto it (lines 2440-2442). Since a subquery window normally *precedes* the outer start by its range, step 0 inflation is the common case, not an edge case — `sum_over_time(m3[1m:10s] offset 5m)` over 600→900s step 60s gives `{600:126, 660:18, 720:18, 780:18, 840:18, 900:18}`, 7× the steady state at step 0. `docs/feature_flags.md:48` presents `samplesReadPerStep` as per-step I/O with no such caveat.

**Correction from validation** — the reviewers' "four different attribution rules" framing is overstated and is *not* part of this finding: `MergeSamplesReadFromSubquery` only ever runs on two objects that already share the outer grid, so it composes with this rule rather than competing with it; the else-branch at line 2446 is reachable only when per-step stats are off entirely; and `ev.samplesStats.Interval == ev.interval` holds by construction at every site (`engine.go:875`, `1869`, `2397`), so the "two sources of truth" concern is stylistic, not a hazard. What survives is the attribution behavior above.

**Fix:** distribute a subquery step's reads across the outer steps whose windows consume them, rather than pinning each to one step. If the pinning is kept for simplicity, document in `docs/feature_flags.md` and on the `SamplesReadPerStep` field that per-step values are *attributed*, not measured per step, and that the first and last buckets absorb out-of-window reads — otherwise the field's stated purpose (finding the expensive step) does not hold for any query containing a subquery.

### #8 🟢 Low: `NewChildWithStepTracking` is a package function while its sibling `NewChild` is a method, leaving the three child-creation sites inconsistent

| | |
|---|---|
| **File** | `util/stats/query_stats.go:411` |
| **Category** | api-design / convention |
| **Confidence** | 100 (quotable fact) |
| **Found by** | broad-reviewer (Low), consistency-reviewer (Low), design-reviewer (Medium) |

**Issue:** `NewChild` is `func (*QuerySamples) NewChild() *QuerySamples` (`query_stats.go:402`). Its new sibling is a bare package function taking the parent's setting as a `bool`, so callers must hand-copy it: `stats.NewChildWithStepTracking(parentSamplesStats.StepTrackingEnabled(), ...)`. func (qs *QuerySamples) NewChildWithStepTracking(start, end, interval int64) *QuerySamples {
```go
    child := NewQuerySamples(qs.StepTrackingEnabled())
    child.InitStepTracking(start, end, interval)   // no-ops when disabled
    return child
}
```

### #9 🟢 Low: `IncrementSamplesReadAtStep` bounds-checks only the upper end, giving the four increment helpers three different out-of-range contracts

| | |
|---|---|
| **File** | `util/stats/query_stats.go:352` |
| **Category** | consistency / api-contract |
| **Confidence** | 100 (quotable fact) |
| **Found by** | knowledge-reviewer, design-reviewer, go-reviewer |

**Issue:** Four helpers, three contracts, none documented:

| method | guard |
|---|---|
| `IncrementSamplesAtStep` (`:321`) | none — panics on any out-of-range index |
| `IncrementSamplesAtTimestamp` (`:334`) | none — panics |
| `IncrementSamplesReadAtStep` (`:347`) | `i < len(...)` only — **negative index still panics**, over-range silently dropped |
| `IncrementSamplesReadAtTimestamp` (`:358`) | `i >= 0 && i < len(...)` |

The same programming error therefore panics loudly for `TotalSamples` and vanishes silently for `SamplesRead`, breaking `sum(SamplesReadPerStep) == SamplesRead` with no signal. All current call sites pass in-range indices, so this is latent — but the asymmetry is what makes the invariant untrustworthy, and the half-guard reads as if someone knew of a legitimate out-of-range case without saying which.

**Fix:** add `i >= 0 &&` to the guard at line 352 and put a one-line comment above line 347 stating whether an out-of-range step is expected (then why) or a programming error (then drop the guards and match `IncrementSamplesAtStep`).

## Specialist Notes

### Considered But Not Flagged (all agents)

**Refuted by validation (1)**

- `util/stats/query_stats.go:423` — *"`MergeSamplesReadFromSubquery` has an undocumented index-alignment precondition and silently truncates the child's tail while adding its full total"* (knowledge-reviewer MUST, design-reviewer Medium, go-reviewer Low). **Refuted**: the engine maintains an invariant that every evaluator's `samplesStats` shares that evaluator's own `(start, end, interval)` — root at `engine.go:815`/`875`, subquery child at `2397` built from `newEv`'s own grid, and `evalSubquery`'s child at `1869` from the calling evaluator's fields. Since `InitStepTracking`'s length is a deterministic function of those three, parent and child always agree on `StartTimestamp`, `Interval`, and length however deeply nested. The validator measured `sum(SamplesReadPerStep) == SamplesRead` across a doubly- and triply-nested subquery and across subqueries both coarser and finer than the outer step — equal in every case. The two-different-layouts observation is real but concerns the *other* merge path (#7), not this method. Residual, not reported: the precondition is still unstated on an exported API, which matters only to a hypothetical direct external caller bypassing the engine.

**Dismissals cross-checked and upheld**

- **Division by zero on `Interval == 0`** in the new step-index arithmetic — examined independently by four agents and by the orchestrator; instant queries construct the evaluator with `interval: 1` (`engine.go:805`), subquery intervals always come from `durationMilliseconds` or `noStepSubqueryIntervalFn`, and `SamplesReadPerStep` is non-nil only via `InitStepTracking`, which sets `Interval` from the same non-zero value. No reachable path.
- **`numOuterSteps == 0` → `outerStep = -1` → index panic** — `numSteps = int((end-start)/interval) + 1` with Go's truncation toward zero gives `numSteps >= 1` even when `subqStart > subqEnd`, since `subqStart - subqEnd < subqInterval` always holds for `Range > 0`. Proven unreachable by three agents.
- **The delta rule undercounting when a step's window is empty and is `continue`d out** — refuted on the backward check: `mint` advances by `ev.interval` per step, so the region the next cutoff excludes, `(mint_{k+1}, maxt_k]`, is a strict subset of step *k*'s window; an empty window can hide nothing. Verified: `quantile_over_time(time()*0, m1[60s])` reports `readPerStep = {201:6, 206:0, 211:1, 216:0}`, total 7 — exactly the 7 distinct samples in 150s–210s.
- **Non-overlapping windows (`range < step`) losing points between windows** — not a defect: `maxt - ev.interval` falls before `mint`, so `countSamplesAfter` returns the full window; points between windows are genuinely never read.
- **`offset` shifting the delta cutoff out of alignment** — `maxt = ts - offset` shifts every step equally, so `maxt - ev.interval` remains exactly the previous step's `maxt`.
- **`ev.samplesStats` left swapped after a panic in `evalSubquery`** — `parentSamplesStats` is restored only on the normal return, so an `ev.error` panic unwinds with the child installed. Traced to no observable effect: `errRecover` catches far up the stack and the evaluator is discarded, never reused.
- **Double-add of the new counter on error / timeout / `ErrTooManySamples` paths** — `querySamplesRead.Add` sits in the same `defer` as the pre-existing `querySamples.Add` (`engine.go:685-686`) and runs once per `exec`; partial-stats behavior is identical to the existing counter.
- **`samplesRead` emitted without `omitempty`** — consistent with the existing `totalQueryableSamples`; additive JSON fields do not break normal consumers. Only the *documentation* of when it appears is wrong, folded into #5.
- **`countSamplesAfter`'s histogram sizing via `h.size()`** — consistent with `totalHPointSize` in the full-window count.
- **Removal of the unused `defaultEpsilon` const** (`promql/engine_test.go:51`) — mechanical cleanup, no coverage lost.
- **`docs/querying/api.md:258` anchor** `../feature_flags.md#per-step-stats` — verified against the `## Per-step stats` heading at `docs/feature_flags.md:40`; valid.

**Below the `evidence=norm` bar (tiered down, not dropped)**

- `promql/engine.go:2163` / `promql/value.go:192` — *the delta cutoff `maxt-ev.interval` relies on two unrecorded invariants*: that range windows are half-open `(mint, maxt]` (so "strictly after the previous `maxt`" is exactly "not in the previous window"), and that `mint`/`maxt` advance by exactly `ev.interval` including the `Anchored`/`Smoothed` adjustments. Both hold today and were verified; the request is only for a comment recording why `maxt-ev.interval` was chosen. Screen 50, single finder (knowledge-reviewer) — below the bar for a primary finding. Worth doing while this file is under active change.
