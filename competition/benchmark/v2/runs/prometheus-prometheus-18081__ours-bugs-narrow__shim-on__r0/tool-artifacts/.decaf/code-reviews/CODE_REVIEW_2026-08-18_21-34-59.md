## Findings

### #1 🟠 High: Subquery samples are counted twice in `SamplesRead`

| | |
|---|---|
| **File** | `promql/engine.go:1874` |
| **Category** | correctness |
| **Confidence** | 100 |
| **Verified** | executed |
| **Pre-existing** | no |
| **Found by** | solo-reviewer (High) |

**Issue:** `evalSubquery` now merges the subquery's own `SamplesRead` into the parent (`MergeSamplesReadFromSubquery`), but the caller then *also* counts the materialized subquery result again in the range-vector loop at `promql/engine.go:2184`. The same points are charged twice: once as real storage reads inside the subquery, once as in-memory re-reads of the subquery's output matrix. The result is a `samplesRead` value that exceeds `totalQueryableSamples` — the opposite of what the field is documented to mean (I/O ≤ loaded), and directly contradicting `docs/feature_flags.md:48` ("For other query types, this equals totalQueryableSamples"). This is the headline metric of the change, and every affected value is baked into the new tests (`promql/engine_test.go:1184` asserts `SamplesRead: 72` against `TotalSamples: 36`), so CI will never flag it.

**Evidence:** Executed. In an isolated worktree at HEAD the seat removed only the `MergeSamplesReadFromSubquery(...)` line and re-ran a probe (worktree destroyed afterwards; review tree never touched, `git status --porcelain` empty):

| query | `TotalSamples` | `SamplesRead` (HEAD) | `SamplesRead` (merge removed) |
|---|---|---|---|
| `max_over_time(m3[60s:5s])` instant @201 | 36 | **72** | 36 |
| `rate(m1[60s:10s])` 201→300 step 30s | 24 | **31** | 15 |

For the second query the true read count traces as: the inner evaluator runs 16 steps (150000…300000 at 10s), reading 1 sample each → 16 real reads. HEAD reports 31 = 16 (inner, attributed per step as `[6,3,3,4]`) + 15 (outer re-count of the materialized matrix, `[6,3,3,3]`). Per-step: HEAD `[12,6,6,7]` vs. `TotalSamplesPerStep` `[6,6,6,6]`.

**Fix:** Pick one accounting point, not both. Either keep `MergeSamplesReadFromSubquery` and suppress `IncrementSamplesReadAtStep` at `engine.go:2184` when the matrix selector is a materialized subquery result (`evalSubquery` already returns a synthetic `*parser.MatrixSelector` that can be flagged), or drop the merge in `evalSubquery` and accept the outer delta count. Note the second option under-counts (15 vs. the true 16), so the first is the more faithful choice. Then re-derive every subquery expectation in `TestQueryStatistics` from first principles rather than from the current output.

### #2 🟠 High: `TotalSamples` silently drops for `@`-modified range selectors in non-step-invariant calls

| | |
|---|---|
| **File** | `promql/engine.go:2143` |
| **Category** | api-design |
| **Confidence** | 100 |
| **Verified** | executed |
| **Pre-existing** | no |
| **Found by** | solo-reviewer (High) |

**Issue:** Previously `IncrementSamplesAtStep(step, int64(len(floats)+totalHPointSize(histograms)))` ran at *every* step, including steps that reuse the retained `floats`/`histograms` under an `@` modifier. The change moves that count into `fullWindowCount`, which is assigned only inside the `if ts == ev.startTimestamp || selVS.Timestamp == nil` block (`engine.go:2160`) and stays `0` on the reuse path. `totalQueryableSamples`, `totalQueryableSamplesPerStep`, and the existing counter `prometheus_engine_query_samples_total` therefore change value for any query where an `@`-modified matrix selector sits inside a call that is *not* step-invariant as a whole. The commit's own comment on line 2143 asserts "unchanged semantics", and the doc comment retained at `util/stats/query_stats.go:271` still promises "Each step should be identical to the TotalSamples when a step is run as an instant query … we intentionally do not account for optimizations … that reduce the actual work". Both are now false. The function still evaluates the full window at each step, so the work being charged for is real.

**Evidence:** Executed on both revisions with the same probe (base worktree at `efbdc3f88`, then HEAD):

| query (range 201→220, step 5s) | base `TotalSamples` / perStep | HEAD `TotalSamples` / perStep |
|---|---|---|
| `predict_linear(m3[60s] @ 30, time())` | 48 / `[12,12,12,12]` | **12** / `[12,0,0,0]` |
| `quantile_over_time(scalar(m1), m3[60s] @ 30)` | 52 / `[13,13,13,13]` | **16** / `[13,1,1,1]` |

Both queries are legal PromQL that escapes `StepInvariantExpr` wrapping because a sibling argument (`time()`, `scalar(m1)`) is not step-invariant. The full `./promql` package suite passes on HEAD (`go test ./promql/ -count=1` → ok, 6.4s), so no existing test covers this path.

**Fix:** Keep `TotalSamples` accounting exactly where it was — compute the full-window count from the live `floats`/`histograms` slices immediately before `IncrementSamplesAtStep`, outside the reuse guard, and only gate `samplesReadCount` on the guard:

```go
fullWindowCount := int64(len(floats) + totalHPointSize(histograms))
ev.samplesStats.IncrementSamplesAtStep(step, fullWindowCount)
ev.samplesStats.IncrementSamplesReadAtStep(step, samplesReadCount) // 0 on the reuse path
```

### #4 🟡 Medium: Documented equality `samplesRead == totalQueryableSamples` is false for step-invariant expressions

| | |
|---|---|
| **File** | `docs/feature_flags.md:48` |
| **Category** | production |
| **Confidence** | 100 |
| **Verified** | traced |
| **Pre-existing** | no |
| **Found by** | solo-reviewer (Medium) |

**Issue:** Both new doc blocks state that outside range-vector functions in range queries, `samplesRead` equals `totalQueryableSamples` (`docs/feature_flags.md:48`, and the same sentence in `docs/querying/api.md`). The `StepInvariantExpr` branch at `promql/engine.go:2472` deliberately adds `SamplesRead` once at step 0 while `TotalSamples` is fanned out across every step in the loop just above, so the two diverge by the step count for any step-invariant subexpression in a range query. Operators reading the docs will treat a 4× discrepancy as a bug in one of the two counters.

**Evidence:** Traced, and confirmed by the change's own test at `promql/engine_test.go:1364`: `max_over_time(m3[60s] @ 30)` over 4 steps asserts `TotalSamples: 48` with `SamplesRead: 12` and per-step `[12, 0, 0, 0]`. The divergence is intentional in the code (comment at `engine.go:2471`), but the documentation added in the same commit denies it exists.

**Fix:** Reword both doc bullets to enumerate the divergences: range-vector functions in range queries (delta), step-invariant subexpressions (counted once), and subqueries — rather than asserting equality for "other query types".

**Issue:** `require.GreaterOrEqual(t, qs.Samples.SamplesRead, int64(0))` (repeated at line 999) can never fail: `SamplesRead` is a monotonically incremented `int64` counter with no subtraction path anywhere in `util/stats/query_stats.go`. The assertion passes identically whether `SamplesRead` is correct, zero, or double-counted. The neighbouring `require.NotNil(t, qs.Samples.SamplesReadPerStep)` on line 1000 is meaningful; this one is not.

**Evidence:** Read. Every writer of `SamplesRead` (`IncrementSamplesReadAtStep:347`, `IncrementSamplesReadAtTimestamp:358`, `MergeSamplesReadFromSubquery:423`, and `engine.go:2419`) adds non-negative sample counts only. `≥ 0` is therefore a type-level fact, not a behavioral one.

**Fix:** Assert the value the fixture actually produces (the `TestStats` fixture is deterministic), e.g. `require.Equal(t, qs.Samples.TotalQueryableSamples, qs.Samples.SamplesRead)` for the non-range-vector query used there — which would also have caught Finding #1 had a subquery fixture been added.
