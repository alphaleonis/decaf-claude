## Findings

### #1 🟠 High: Previously-tolerated slash-command responses now fail the whole execution, and one bad `extra_responses` entry discards the valid main response

| | |
|---|---|
| **File** | `server/public/model/command_response.go:72` |
| **Category** | api-design |
| **Confidence** | 75 |
| **Verified** | executed + traced |
| **Pre-existing** | no |

**Issue:** `CommandResponseFromJSON` was a lenient parser sitting directly on the third-party integration ingress path. Adding a hard `IsValid()` gate converts payloads that previously worked (or degraded silently) into hard runtime failures for existing integrations:

- `server/channels/app/command.go:595` — an outgoing slash-command whose HTTP endpoint returns an unrecognized `response_type` now makes the entire command fail. The parse error is wrapped as `api.command.execute_command.failed.app_error` with `http.StatusInternalServerError` (line 596), so an integration's malformed field is reported to the end user as a **500**, discarding the `text`, `attachments`, `goto_location`, and `props` that were previously delivered. Before the change, `CreateCommandPost` (`command.go:73` and `command.go:82`) simply matched neither branch and returned `post, nil` — no post, no error.
- `server/channels/web/webhook.go:114` — `POST /hooks/commands/{id}` now returns 400 for the same payloads.
- `server/public/model/client4.go:5961` and `:5982` — `Client4.ExecuteCommand` / `ExecuteCommandWithTeam` now fail to decode a server response produced by a plugin that sets a non-standard `response_type`. The server does **not** validate the `CommandResponse` it emits, so the server can now generate a response its own Go client refuses to parse; the webapp (which does not use this decoder) is unaffected, so client behavior diverges.

The all-or-nothing recursion at lines 90-98 is the sharpest part. `App.HandleCommandResponse` (`server/channels/app/command.go:614-628`) is deliberately written to post each `ExtraResponses` entry independently and only *log* per-response errors, keeping a partial failure partial. Rejecting the whole document because one nested entry is bad defeats that design: a five-message response where message #4 has a typo'd `response_type` now delivers zero messages instead of four.

The concrete scenario is not hypothetical: `OutgoingHookResponseTypeComment = "comment"` (`server/public/model/outgoing_webhook.go:80`) is a real `response_type` value in this same codebase for the sibling outgoing-webhook integration. An integration reusing that value, or a shared handler serving both integration types, previously produced a working (if post-less) 200 and now produces a 500.

**Evidence:** Mutation probe under the snapshot protocol — with lines 72-74 removed, `{"text":"hello","response_type":"shliapa_type"}` and `{"text":"main ok","response_type":"in_channel","extra_responses":[{"text":"nested bad","response_type":"invalid_nested_type"}]}` both parse successfully; the second returns a fully populated `&model.CommandResponse{ResponseType:"in_channel", Text:"main ok", ExtraResponses:[...]}`. Tree restored byte-identical afterwards (`git status --porcelain` empty, `git diff --stat` empty, tests re-run green). Downstream tolerance traced statically in `CreateCommandPost`: with an unrecognized `ResponseType`, neither the `== CommandResponseTypeInChannel` branch (line 73) nor the `== "" || == Ephemeral` branch (line 82) is taken, and the function returns `post, nil`.

**Fix:** Decide explicitly whether this is a breaking change worth taking, and if so scope it:
- Do not fail the parse on a nested `ExtraResponses` entry — validate the top-level response and either drop or log invalid extra responses, preserving `HandleCommandResponse`'s partial-delivery contract.
- Keep `CommandResponseFromJSON` lenient (it is a shared decoder used to parse the *server's own* responses in `client4.go`) and put the strict gate in the ingress handlers (`app/command.go:595`, `web/webhook.go:114`) where a policy decision belongs.
- If a hard rejection on `response_type` is genuinely wanted, map it to a 4xx on the outgoing-command path rather than 500, and flag it as a breaking change in the release notes.

The two IDs are also invisible to the translation pipeline, so no locale can ever localize them.

**Evidence:** Executed — extracted every `"model.*.app_error"` literal from `server/public/model/*.go` (516 unique IDs) and checked each against `server/i18n/en.json`. Exactly three are absent, two of which are introduced by this change:

### #3 🟡 Medium: Hardcoded 65535-*byte* text cap ignores the configurable post size and can reject responses that previously posted fine

| | |
|---|---|
| **File** | `server/public/model/command_response.go:85` |
| **Category** | correctness |
| **Confidence** | 50 |
| **Verified** | traced |
| **Pre-existing** | no |

**Issue:** `maxLength := 65535` is a hardcoded byte count, but every downstream limit on this text is a *rune* count derived from the database at runtime. `Post.IsValid` checks `utf8.RuneCountInString(o.Message) > maxPostSize` (`server/public/model/post.go:508`), and `maxPostSize` comes from `determineMaxPostSize` (`server/channels/store/sqlstore/post_store.go:2640-2662`):

```go
maxPostSize := max(int(maxPostSizeBytes)/4, model.PostMessageMaxRunesV2)
```

whose own comment states the `Posts.Message` column "may be manually enlarged to support longer posts". On an installation that has enlarged the column (a supported operation), `maxPostSize` scales with it — e.g. a `varchar(1000000)` column yields 250,000 runes. A slash-command integration that legitimately returned a 200 KB report and had it posted successfully before this change will now be rejected outright by the fixed 65535-byte gate, with the whole command failing (see #1).

Two secondary problems in the same line: the value duplicates the existing `model.PostMessageMaxBytesV2 = 65535` constant (`server/public/model/post.go:72`) as an unnamed local rather than referencing it, and the byte/rune mismatch means the check is also *too loose* in the default configuration — a 20,000-rune ASCII response passes `IsValid` and then fails post creation with a different, unrelated error, so the guard doesn't actually shield the caller from the failure it appears to be guarding.

**Evidence:** Traced. `determineMaxPostSize` reads `character_maximum_length` for `posts.message` from `information_schema.columns` and divides by 4, flooring at `PostMessageMaxRunesV2` (16383). In the default configuration the new cap never rejects a post the store would accept (16383 runes ≤ 65532 bytes < 65536), so the regression is confined to installations with an enlarged column — which is why this is anchored at 50 rather than 75.

**Fix:** Either drop the length check from `IsValid` and let the existing post validation own the limit (it already knows the real value), or make the bound a named exported constant and thread the configured `MaxPostSize()` through the ingress handler instead of hardcoding it in the shared model package. If a byte cap really is the intent, reference `PostMessageMaxBytesV2` and say so in a comment.

### #4 🟢 Low: The text cap is bypassed entirely for non-JSON content types

| | |
|---|---|
| **File** | `server/public/model/command_response.go:72` |
| **Category** | correctness |
| **Confidence** | 100 |
| **Verified** | traced |
| **Pre-existing** | no |

**Issue:** The validation was added to `CommandResponseFromJSON`, not to `CommandResponseFromHTTPBody`. The plain-text branch (`command_response.go:39-41`) calls `CommandResponseFromPlainText`, which builds a `CommandResponse` with no validation at all. Both server ingress points go through `CommandResponseFromHTTPBody`, so whether the new `Text` length cap applies depends purely on the integration's `Content-Type` header:

- `server/channels/web/webhook.go:114` — a `text/plain` body up to `MaximumPayloadSizeBytes` (default 300,000 — `server/public/model/config.go:1035`) sails through unchecked.
- `server/channels/app/command.go:586,595` — a `text/plain` response body up to `MaxIntegrationResponseSize` (1 MB — `server/channels/app/webhook.go:31`) sails through unchecked.

So the same 100 KB of text is rejected as JSON and accepted as plain text. The check does not achieve the bound it states, and the inconsistency is confusing for integration authors debugging why one encoding works and the other doesn't.

**Evidence:** Traced through `CommandResponseFromHTTPBody` (lines 35-43): the `application/json` branch delegates to `CommandResponseFromJSON` (now validating); the fallthrough branch calls `CommandResponseFromPlainText` and returns directly, never touching `IsValid`. Existing test `TestCommandResponseFromHTTPBody` (`command_response_test.go:19-20`) exercises both content types and confirms the plain-text path is live.

**Fix:** Call `IsValid()` in `CommandResponseFromHTTPBody` after both branches (or in `CommandResponseFromPlainText` as well), so validation is a property of the ingress point rather than the encoding. This interacts with #1 — pick the layer deliberately.
