## Findings

### #1 🟠 High: `SamplesRead` double-counts every subquery feeding a range-vector function

| | |
|---|---|
| **File** | `promql/engine.go:1874` (and the second count at `promql/engine.go:2184`) |
| **Category** | correctness |
| **Confidence** | 100 |
| **Verified** | executed |
| **Pre-existing** | no |
| **Found by** | solo-reviewer (High) |

**Issue:** `evalSubquery` merges the subquery's own `SamplesRead` into the parent (`parentSamplesStats.MergeSamplesReadFromSubquery(ev.samplesStats)`), and then replaces the `SubqueryExpr` argument with a `MatrixSelector` over the *materialized* result (`engine.go:2008-2010`). The range-vector loop subsequently counts every point of that materialized matrix a second time via `ev.samplesStats.IncrementSamplesReadAtStep(step, samplesReadCount)` at `engine.go:2184`. The result is that `samplesRead` / `prometheus_engine_query_samples_read_total` reports roughly **2× the true value** for the single most common subquery shape (`rate(x[5m:1m])`, `max_over_time(x[1h:1m])`, …), compounding further with nesting — and it reports a value *larger* than `totalQueryableSamples`, which the docs added in this same PR say cannot happen (`docs/feature_flags.md:47`: "For other query types, this equals totalQueryableSamples"; `docs/querying/api.md:246`).

**Evidence:** executed against the tree at HEAD (probe test, since removed):

```
q=metricWith1SampleEvery10Seconds[5m]                                 total=  30 read=  30
q=rate(metricWith1SampleEvery10Seconds[5m])                           total=  30 read=  30
q=rate(metricWith1SampleEvery10Seconds[5m:1m])                        total=   5 read=  10   <-- 2x
q=sum_over_time(rate(metricWith1SampleEvery10Seconds[5m:1m])[10m:1m]) total=  10 read=  38   <-- 3.8x
q=max_over_time(metricWith3SampleEvery10Seconds[60s:5s])              total=  36 read=  72   <-- 2x
q=metricWith3SampleEvery10Seconds[60s:5s]   (bare subquery)           total=  36 read=  36   <-- 1x
```

The bare-subquery row is the control: without the enclosing range-vector function, the same subquery is counted once. `read = total + (subquery's own reads)` holds exactly in every case. The counter-argument is that this is encoded deliberately — `promql/engine_test.go:1548` asserts `SamplesRead: 2, // subquery + outer` — but re-reading a matrix the engine just built in memory is not I/O, which is what the new metric's help string (`engine.go:428`) and both doc sections claim it measures.

**Fix:** the outer re-count is the wrong one, since the materialized points involve no storage access. Track that `e.Args[matrixArgIndex]` came from `evalSubquery` (the call site at `engine.go:2008` already has that information) and skip `IncrementSamplesReadAtStep` for that case, leaving the merged child value as the only contribution. Then update the `max_over_time(...[60s:5s])`-style expectations (72 → 36, 12 → 6, …) accordingly.

### #2 🟠 High: `TotalSamples` silently regresses for `@`-modifier range-vector reuse

| | |
|---|---|
| **File** | `promql/engine.go:2145` |
| **Category** | production |
| **Confidence** | 100 |
| **Verified** | executed |
| **Pre-existing** | no |
| **Found by** | solo-reviewer (High) |

**Issue:** `var fullWindowCount, samplesReadCount int64` is declared **inside** the per-step loop and only assigned inside the `if ts == ev.startTimestamp || selVS.Timestamp == nil` block. Previously the increment used the live `floats`/`histograms` slices, which persist across steps, so a matrix selector with an `@` modifier contributed its full window to `TotalSamples` at *every* step. Now steps > 0 contribute 0. This changes the existing, documented `totalQueryableSamples` field and the existing `prometheus_engine_query_samples_total` counter — the exact opposite of the in-line comment on `engine.go:2143` ("Full window count for TotalSamples (unchanged semantics)") and of the doc text this PR adds (`docs/querying/api.md:243`: "For range-vector functions over multiple steps, each step counts the full window").

The trigger is a range query where the `@`-annotated matrix selector is *not* wrapped in a `StepInvariantExpr` — `preprocessExprHelper` deliberately does not wrap `MatrixSelector`/`SubqueryExpr` arguments, so any multi-arg range-vector call with a non-invariant sibling argument reaches it: `quantile_over_time(scalar(y), x[5m] @ t)`, `predict_linear(x[1h] @ t, y)`, `double_exponential_smoothing(x[5m] @ t, sf, tf)`.

**Evidence:** executed. Same probe query and data run at the base commit `efbdc3f88` (in a temporary `git worktree`, since removed) and at HEAD `ec7157593`, range query `start=201s end=261s step=30s`:

```
quantile_over_time(scalar(metricWith1SampleEvery10Seconds), metricWith3SampleEvery10Seconds[60s] @ 30)
  base (efbdc3f88): total=39  perStep=map[201000:13 231000:13 261000:13]
  HEAD (ec715759): total=15  perStep=map[201000:13 231000:1  261000:1 ]
```

12 samples per step disappear from `TotalSamples` at every step after the first. No test in the changeset covers this shape, which is why the existing `TestQueryStatistics` expectations did not need updating.

**Fix:** keep the full-window accounting unconditional and zero only the read count on reuse steps, e.g. hoist `fullWindowCount = int64(len(floats) + totalHPointSize(histograms))` to after the `if` block (it then naturally uses the retained slices), leaving `samplesReadCount` at 0 when the `@` reuse path is taken. If the drop *is* intended, it needs to be stated in the commit message and the docs, and covered by a test.

**Issue:** The ~900 added table rows carry an in-file disclaimer that their values were not independently derived:

- `engine_test.go:1539` "corrected values", `:1544` "TotalSamples: 1, // **Actual behavior**: single step shows 1 effective sample".

Because the numbers were captured from the implementation rather than computed from the specification, the suite cannot fail for a wrong implementation — and demonstrably does not: it pins finding #1's 2× overcount as the expected value (`:1548` `SamplesRead: 2, // subquery + outer`; `:1184` `SamplesRead: 72` against `TotalSamples: 36`). Delete the duplicate rows, the duplicated banner, and the "IMPLEMENTATION NOTES" block before merge.

### #4 🟢 Low: `countSamplesAfter` rescans the whole window on every step of every series

| | |
|---|---|
| **File** | `promql/value.go:195` |
| **Category** | efficiency |
| **Confidence** | 100 |
| **Verified** | read |
| **Pre-existing** | no |
| **Found by** | solo-reviewer (Low) |

**Issue:** `countSamplesAfter` walks the full `floats` and `histograms` slices from the front, but is only ever asked about the tail (`T > maxt-ev.interval`). It runs at `engine.go:2164`, i.e. once per step per series in the range-vector hot path. For a wide window and a small step — `rate(x[1h])` at 15s resolution over 1s-resolution data is ~3600 points per window — this is a new full-length scan per step where only the last few points can qualify.

**Evidence:** both slices are strictly ascending in `T` (they come from `matrixIterSlice`, which appends in iterator order), so the qualifying suffix is contiguous and can be located without touching the head.

**Fix:** iterate backwards and stop at the first point with `T <= cutoff`, or use `sort.Search` on `T` (O(log n)); the histogram sizes still need summing over the suffix only.

### #5 🟢 Low: subquery children now allocate a per-step array that is never read

| | |
|---|---|
| **File** | `util/stats/query_stats.go:411` |
| **Category** | efficiency |
| **Confidence** | 100 |
| **Verified** | traced |
| **Pre-existing** | no |
| **Found by** | solo-reviewer (Low) |

**Issue:** `NewChildWithStepTracking` calls `InitStepTracking`, which allocates **both** `TotalSamplesPerStep` and `SamplesReadPerStep` (`query_stats.go:306-307`). Only `SamplesReadPerStep` is ever consumed from a child: `evalSubquery` reads `SamplesRead`/`SamplesReadPerStep` (`engine.go:1873-1874`), and the `SubqueryExpr` case reads `TotalSamples`, `SamplesRead` and `SamplesReadPerStep` (`engine.go:2424-2444`). The child's `TotalSamplesPerStep` is written on every `IncrementSamplesAtStep` and then discarded. Previously children came from `NewChild()` and allocated nothing.

**Evidence:** traced all consumers of a child `*QuerySamples` — `UpdatePeakFromSubquery`, `MergeSamplesReadFromSubquery`, `.TotalSamples`, `.SamplesRead`, `.SamplesReadPerStep`. None reads `TotalSamplesPerStep`. Size is `8 × numSteps` bytes per array; for the `SubqueryExpr` child `numSteps` is the *subquery* step count, so `x[1h:1s]` inside a 24h range query allocates ~90k entries (~700 KB) of write-only memory in addition to the ~700 KB that is actually used. Only reachable with `--enable-feature=promql-per-step-stats` and `stats=all`.

**Fix:** give the child a variant that initializes only `SamplesReadPerStep` (plus `StartTimestamp`/`Interval`), or make `InitStepTracking` take a flag for which arrays to allocate.
