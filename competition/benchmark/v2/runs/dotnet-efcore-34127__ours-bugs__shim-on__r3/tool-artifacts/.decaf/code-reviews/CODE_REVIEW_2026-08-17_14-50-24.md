## Findings

### #1 🔴 Critical: `NullPropagatedOperands` treats `AND` / `OR` as NULL-strict, producing silently wrong query results

| | |
|---|---|
| **File** | `src/EFCore.Relational/Query/SqlNullabilityProcessor.cs:626` |
| **Category** | correctness |
| **Confidence** | 100 |
| **Verified** | executed |
| **Pre-existing** | no |
| **Found by** | solo-reviewer (Critical) |

**Issue:** `NullPropagatedOperands` recurses into *both* operands of *every* `SqlBinaryExpression`:

```csharp
else if (expression is SqlBinaryExpression binary)
{
    NullPropagatedOperands(binary.Left, operands);
    NullPropagatedOperands(binary.Right, operands);
}
```

`SqlBinaryExpression.IsValidOperator` admits `AndAlso` and `OrElse` (`src/EFCore.Relational/Query/SqlExpressions/SqlBinaryExpression.cs:88-91`), and SQL's three-valued logic is **not** strict for them: `NULL AND FALSE = FALSE`, `NULL OR TRUE = TRUE`. So for a result like `x OR y`, the helper wrongly records `x` as an operand from which the result propagates NULL, `DropNotNullChecks` then deletes `x IS NOT NULL` from the test, and the `CASE` collapses to an expression that returns `TRUE`/`FALSE` where the original returned `NULL`.

This is not a corner case: the null-semantics expansion of an equality comparison *is* an `AndAlso`/`OrElse`. Because the WHEN-clause result is visited with the test's columns already pushed into `_nonNullableColumns` (lines 512-514), `x.NullableIntA == x.NullableIntB` under a `NullableIntA IS NOT NULL` test expands to `A = B AND B IS NOT NULL` — which is non-strict in `A` precisely because the test guaranteed `A` non-null. Dropping the test then invalidates the assumption the result was simplified under.

Consequence: wrong scalar values (`false`/`true` instead of `null`) in projections, and wrong row sets in `WHERE`.

**Evidence:** Built `src/EFCore.Sqlite.Core` at head (`afcfba2e9`) and at base (`051c33a79`, via a temporary `git worktree`), and ran an identical probe against a real SQLite database, comparing each query's DB result to the same lambda evaluated in memory. **All 10 probes pass on the base commit; 7 of 10 return wrong results after the change.** Selected results (head):

| Query | Emitted SQL (head) | Failing row | DB | Expected |
|---|---|---|---|---|
| `A != null ? (bool?)(A == B) : null` | `A = B AND B IS NOT NULL` | A=NULL, B=NULL | `false` | `null` |
| `A != null ? (bool?)(A != B) : null` | `A <> B OR B IS NULL` | A=NULL, B=NULL | `true` | `null` |
| `NB != null ? (bool?)(NB.Value \|\| BoolA) : null` | `NullableBoolA OR BoolA` | NB=NULL, BoolA=true | `true` | `null` |
| `NB != null ? (bool?)(NB.Value && BoolA) : null` | `NullableBoolA AND BoolA` | NB=NULL, BoolA=false | `false` | `null` |
| `A != null ? (bool?)(A > 0 \|\| B > 0) : null` | `A > 0 OR CASE WHEN B > 0 ...` | A=NULL, B=1 | `true` | `null` |
| `A != null ? (bool?)(A > 0 && B > 0) : null` | `A > 0 AND CASE WHEN B > 0 ...` | A=NULL, B=NULL | `false` | `null` |

And in predicate position, `Where(x => (x.NullableBoolA != null ? (bool?)(x.NullableBoolA.Value || x.BoolA) : null) == true)` becomes `WHERE "e"."NullableBoolA" OR "e"."BoolA"` and returns **36 rows instead of 27** — 9 rows that should have been excluded. The same query on the base commit emits the full `CASE ... ELSE NULL END` and returns the correct 27.

The five new theories in `test/EFCore.Relational.Specification.Tests/Query/NullSemanticsQueryTestBase.cs:2250-2294` all use arithmetic/string/unary results, so none of them exercises a logical-connective result; the suite would go green on this change.

**Fix:** Make the binary arm an explicit allow-list of NULL-strict operators rather than a default-allow, e.g.

```csharp
else if (expression is SqlBinaryExpression binary
         && binary.OperatorType is ExpressionType.Add or ExpressionType.Subtract
             or ExpressionType.Multiply or ExpressionType.Divide or ExpressionType.Modulo
             or ExpressionType.And or ExpressionType.Or or ExpressionType.ExclusiveOr
             or ExpressionType.Equal or ExpressionType.NotEqual
             or ExpressionType.LessThan or ExpressionType.LessThanOrEqual
             or ExpressionType.GreaterThan or ExpressionType.GreaterThanOrEqual)
```

(excluding `AndAlso`, `OrElse` and `Coalesce` — see #2). Note this deliberately gives up the `A == B` case above; recovering it would require also invalidating the `_nonNullableColumns` facts the result was simplified under, which is a larger change. Theories with boolean/comparison results (both projection and `Where`) covering the `A=NULL, B=NULL` and `NB=NULL, BoolA=true` rows are needed — the current tests cannot fail for this defect.

### #2 🟡 Medium: `ExpressionType.Coalesce` is a legal `SqlBinaryExpression` operator and is mishandled as NULL-strict

| | |
|---|---|
| **File** | `src/EFCore.Relational/Query/SqlNullabilityProcessor.cs:626` |
| **Category** | correctness |
| **Confidence** | 50 |
| **Verified** | read |
| **Pre-existing** | no |
| **Found by** | solo-reviewer (Medium) |

**Issue:** The same catch-all binary arm also matches `ExpressionType.Coalesce`, which `SqlBinaryExpression.IsValidOperator` admits (`src/EFCore.Relational/Query/SqlExpressions/SqlBinaryExpression.cs:102`) and which `SqlExpressionFactory.MakeBinary` will happily construct (`SqlExpressionFactory.cs:400-421` — it only rejects operators `IsValidOperator` rejects). `COALESCE(a, b)` is the archetypal *non*-strict operator: it is NULL only when *all* arguments are NULL. Recording `a` as a null-propagated operand of `COALESCE(a, '')` would let `DropNotNullChecks` delete `a IS NOT NULL`, turning `CASE WHEN a IS NOT NULL THEN COALESCE(a, '') || b ELSE NULL END` (which is NULL when `a` is NULL) into `COALESCE(a, '') || b` (which is `b`).

**Evidence:** Traced, not executed. `RelationalSqlTranslatingExpressionVisitor.cs:450` routes `Coalesce` to `SqlExpressionFactory.Coalesce`, which builds a `SqlFunctionExpression` with `argumentsPropagateNullability: [false, false]` (`SqlExpressionFactory.cs:502-509`) — correctly handled by the function arm at line 631. So no in-tree translator produces the binary form today, and a SQLite probe of `COALESCE`-bearing concatenations (`COALESCE("NullableStringA", '') || "NullableStringB"`) came out correct. But the operator is legal on the public `SqlBinaryExpression` type and on the public `ISqlExpressionFactory.MakeBinary` surface that providers use, so a provider-built tree hits the wrong arm — a silent wrong-results failure rather than an exception.

**Fix:** Covered by the allow-list in #1 — `Coalesce` must not be in it. If a deny-list is preferred instead, spell it out (`is not (AndAlso or OrElse or Coalesce)`) and add a comment saying why those three are excluded, so a future operator addition to `IsValidOperator` is a conscious decision here.
