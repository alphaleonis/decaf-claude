## Findings

### #1 🔴 Critical: `NullPropagatedOperands` treats `AndAlso`/`OrElse` operands as null-propagating; queries return wrong values and wrong rows

| | |
|---|---|
| **File** | `src/EFCore.Relational/Query/SqlNullabilityProcessor.cs:626-630` |
| **Category** | correctness |
| **Confidence** | 100 (verified by execution) |
| **Found by** | solo-reviewer (Critical) |

**Issue:** The `SqlBinaryExpression` arm descends into `binary.Left` and `binary.Right` for *every* operator type. `ExpressionType.AndAlso` and `ExpressionType.OrElse` do not propagate SQL `NULL` — under three-valued logic `NULL AND FALSE = FALSE` and `NULL OR TRUE = TRUE`. So for `CASE WHEN x IS NOT NULL THEN (x OR y) ELSE NULL END`, `x` lands in `nullPropagatedOperands`, `DropNotNullChecks` deletes the guard, and the whole `CASE` collapses to `x OR y`, which yields `TRUE` (not `NULL`) on exactly the rows the guard was protecting.

This is not an exotic shape. EF's own null-semantics compensation emits `AndAlso`/`OrElse` at the top of a rewritten comparison — `a == b` becomes `a = b AND b IS NOT NULL`, `a != b` becomes `a <> b OR b IS NULL` (`SqlNullabilityProcessor.RewriteNullSemantics`). Any `x != null ? (x <cmp> y) : (bool?)null`, in a projection *or* a predicate, hits this. The `WHERE` case changes the returned row set.

**Evidence (executed):** `EFCore.Relational`/`EFCore.Sqlite.Core` were built at `afcfba2e9` and at `051c33a79` (read-only `git worktree`, since removed) and identical queries run over identical SQLite data, each compared against the LINQ-to-Objects oracle for the same lambda. Five rows; `NullableBoolA` is `null` on rows 1, 3, 4.

`x.NullableBoolA != null ? (bool?)(x.NullableBoolA.Value || x.BoolB) : null`

```
HEAD    sql: SELECT "e"."NullableBoolA" OR "e"."BoolB" FROM "Entities" AS "e"
        db : True,True,<null>,<null>,True     <-- row 1 wrong
        c# : <null>,True,<null>,<null>,True
PARENT  sql: SELECT CASE WHEN "e"."NullableBoolA" IS NOT NULL THEN "e"."NullableBoolA" OR "e"."BoolB" ELSE NULL END ...
        db : <null>,True,<null>,<null>,True   <-- matches c#
```

`x.NullableBoolA != null ? (bool?)(x.NullableBoolA.Value && x.BoolB) : null` → HEAD `<null>,True,False,False,False` vs C# `<null>,True,<null>,<null>,False` (rows 3, 4 wrong). Parent matches.

`x.NullableIntA != null ? (bool?)(x.NullableIntA == x.NullableIntB) : null` → the compensated result is `A = B AND B IS NOT NULL`; HEAD gives `<null>,False,False,False,True` vs C# `<null>,False,False,<null>,True` (row 4, where both are `null`, wrong). Parent matches. Same for `!=` via the `OrElse` compensation.

Predicate context — wrong row set, not just a wrong scalar:

```
Where((x.NullableBoolA != null ? (bool?)(x.NullableBoolA.Value || x.BoolB) : null) == true)
HEAD    sql: ... WHERE "e"."NullableBoolA" OR "e"."BoolB"        db: 1,2,5   c#: 2,5
PARENT  sql: ... WHERE CASE WHEN ... IS NOT NULL THEN ... END    db: 2,5     c#: 2,5
```

SQL Server generation (same commit pair, `ToQueryString`, no server needed) shows the same collapse with a worse shape — the projection becomes `CASE WHEN [NullableBoolA] = CAST(1 AS bit) OR [BoolB] = CAST(1 AS bit) THEN CAST(1 AS bit) ELSE CAST(0 AS bit) END`, which can never produce `NULL` at all, so the `bool?` projection returns `false` for every null row.

**Fix:** Make the `SqlBinaryExpression` arm operator-aware, preferring an allow-list/deny-list that fails closed for future operators:

```csharp
else if (expression is SqlBinaryExpression
    {
        OperatorType: not (ExpressionType.AndAlso or ExpressionType.OrElse or ExpressionType.Coalesce)
    } binary)
```

(`Coalesce` is unreachable today in the relational tree but is legal per `SqlBinaryExpression.IsValidOperator`, `src/EFCore.Relational/Query/SqlExpressions/SqlBinaryExpression.cs:102`.) This alone does **not** fix #2. The added tests all use arithmetic/string operators, which is why the defect escapes them; coverage for a logical-operator and a comparison result belongs with the fix.

### #2 🔴 Critical: dropping the guard around a boolean *search-condition* result loses `NULL`, because `UNKNOWN` materializes as `false`

| | |
|---|---|
| **File** | `src/EFCore.Relational/Query/SqlNullabilityProcessor.cs:626-630` |
| **Category** | correctness |
| **Confidence** | 100 (SQL generation executed at both commits; runtime consequence from standard SQL semantics — no SQL Server instance available) |
| **Found by** | solo-reviewer (Critical) |

**Issue:** Comparison operators (`Equal`, `NotEqual`, `LessThan`, …) do propagate `NULL` as a *value*, so descending into them looks sound. But on SQL Server (and any provider running a search-condition converter after `SqlNullabilityProcessor`) a bare boolean `SqlBinaryExpression` in value position is materialized as `CASE WHEN <pred> THEN CAST(1 AS bit) ELSE CAST(0 AS bit) END`. That mapping folds `UNKNOWN` into the `ELSE` branch — `false`, not `NULL`. The outer `CASE … ELSE NULL END` this change deletes was the only thing preserving the `NULL`.

This is a distinct defect from #1 with a distinct fix: excluding `AndAlso`/`OrElse` does not help, because the offending result here is a plain `Equal` node.

**Evidence:** `ctx.Entities.Select(x => x.NullableIntA != null ? (bool?)(x.NullableIntA == x.Id) : null)`, `UseSqlServer`, `ToQueryString`:

```sql
-- PARENT (051c33a79) — correct
SELECT CASE
    WHEN [e].[NullableIntA] IS NOT NULL THEN CASE
        WHEN [e].[NullableIntA] = [e].[Id] THEN CAST(1 AS bit)
        ELSE CAST(0 AS bit)
    END
    ELSE NULL
END
FROM [Entities] AS [e]

-- HEAD (afcfba2e9) — cannot produce NULL
SELECT CASE
    WHEN [e].[NullableIntA] = [e].[Id] THEN CAST(1 AS bit)
    ELSE CAST(0 AS bit)
END
FROM [Entities] AS [e]
```

For a row with `NullableIntA IS NULL`, `[NullableIntA] = [Id]` is `UNKNOWN`, the `ELSE` fires, and the `bool?` projection reads `false` where the C# ternary specifies `null`. The same query executed on SQLite is unaffected (`db: <null>,False,False,<null>,False` — matches C#), because SQLite has no bit type and EF emits the bare comparison, which yields `NULL`. So this is a provider-dependent silent wrong answer, invisible to the Sqlite functional tests.

**Fix:** The optimization is sound only when the collapsed result is a *value* expression. Gate the whole block at `SqlNullabilityProcessor.cs:578` on the result not being a boolean search condition (e.g. skip when `clause.Result.Type == typeof(bool)` and the result is a `SqlBinaryExpression`/`SqlUnaryExpression` predicate node), or restrict `NullPropagatedOperands` to descend only into operators whose result is a value (arithmetic, bitwise, string concatenation, `Convert`/`Negate`) and never into comparison or logical operators. The existing `Is_not_null_optimizes_*` baselines are all non-boolean and would be unaffected by that restriction.
