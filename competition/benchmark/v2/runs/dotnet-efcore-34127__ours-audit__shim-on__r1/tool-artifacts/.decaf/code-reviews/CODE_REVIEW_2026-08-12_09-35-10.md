## Findings

### #1 🔴 Critical: `NullPropagatedOperands` treats every binary operator as null-propagating, producing silently wrong query results

| | |
|---|---|
| **File** | `src/EFCore.Relational/Query/SqlNullabilityProcessor.cs:626` |
| **Category** | correctness / data-loss |
| **Confidence** | 100 — **confirmed by executed probe at both commits** |
| **Found by** | quick-reviewer (Critical), broad-reviewer (Critical), dotnet-reviewer (Critical), adversarial-reviewer (Critical ×2 chains), design-reviewer (Critical), knowledge-reviewer (MUST), security-reviewer (High), test-reviewer (High, as a coverage gap on the same shape) |

**Issue**

The optimization's soundness premise is: for `CASE WHEN <test> THEN <result> ELSE NULL END`, an `X IS NOT NULL` conjunct of `<test>` may be dropped only if `X IS NULL` **implies** `<result> IS NULL`. `NullPropagatedOperands` is what decides which `X` satisfy that. Its binary arm applies no operator filter at all:

```csharp
else if (expression is SqlBinaryExpression binary)
{
    NullPropagatedOperands(binary.Left, operands);
    NullPropagatedOperands(binary.Right, operands);
}
```

`SqlBinaryExpression.IsValidOperator` (`SqlBinaryExpression.cs:82-105`) admits `AndAlso`, `OrElse`, `Coalesce`, and all six comparison operators alongside the arithmetic and bitwise ones. Under SQL three-valued logic none of those propagate NULL:

- `NULL AND FALSE` = `FALSE`, `NULL OR TRUE` = `TRUE` — the operand's nullness is absorbed.
- `NULL > 5` and `NULL = 5` yield `UNKNOWN`, not `NULL`; in value position `UNKNOWN` materializes as `false` (on SQL Server via `SearchConditionConvertingExpressionVisitor`, which `SqlServerParameterBasedSqlProcessor.Optimize` runs **after** `ProcessSqlNullability`, so a bare boolean `SqlBinaryExpression` is exactly what `VisitCase` sees).

Two independent routes reach the bad shape, both observed in the probes:

1. **`_nonNullableColumns` seeding.** `VisitCase` deliberately visits the result with the test's non-nullability facts in scope (lines 511-514). That makes `nullable` false, so the guard at `VisitSqlBinary` line ~1410 that would normally wrap a lifted comparison in `CASE WHEN expr THEN TRUE ELSE FALSE` does **not** fire, leaving a bare comparison as `clause.Result`. The new block then deletes the very test the result was rewritten under.
2. **Null-semantics expansion.** `(A + IntB) IS NOT NULL` expands via `ProcessNullNotNull` to `A IS NOT NULL AND IntB IS NOT NULL`, and `A == C` expands to a disjunction of conjunctions. The unfiltered recursion walks straight through both and reaches `A`.

**This exact exception is already documented 1700 lines below, in this same file.** `ProcessNullNotNull` at lines 2314-2321 guards the analogous rule with `when sqlBinaryOperand.OperatorType != ExpressionType.AndAlso && sqlBinaryOperand.OperatorType != ExpressionType.OrElse` and the comment *"for AndAlso, OrElse we can't do this optimization"*. The new arm reintroduces precisely the generalization that guard exists to prevent.

The WHERE-position probe is the most serious consequence: the query returns a row it must not. EF global query filters (`HasQueryFilter`) are ordinary LINQ predicates that flow through this code path, so for applications implementing tenancy or row-level authorization that way, this is a row-leak, not merely a wrong scalar.

**Fix**

Restrict the arm to operators that are genuinely strict in both operands, as an **allowlist** so a future addition to `IsValidOperator` fails closed:

```csharp
else if (expression is SqlBinaryExpression
         {
             OperatorType: ExpressionType.Add or ExpressionType.Subtract or ExpressionType.Multiply
                 or ExpressionType.Divide or ExpressionType.Modulo
                 or ExpressionType.And or ExpressionType.Or or ExpressionType.ExclusiveOr
         } binary)
{
    NullPropagatedOperands(binary.Left, operands);
    NullPropagatedOperands(binary.Right, operands);
}
```

Comparison operators must be excluded along with `AndAlso`/`OrElse`/`Coalesce`: they yield `UNKNOWN`, which is not `NULL` once the provider materializes the condition as a value. The unary arm (`Not`/`Negate`/`Convert`, line 622) is correct as written and needs no change — it matches `ProcessNullNotNull`'s own list at lines 2290-2296, and correctly omits `Equal`/`NotEqual`.

### #2 🟠 High: No negative test pins the soundness boundary — the whole failing region is uncovered

| | |
|---|---|
| **File** | `test/EFCore.Relational.Specification.Tests/Query/NullSemanticsQueryTestBase.cs:2250` |
| **Category** | test-coverage |
| **Confidence** | 100 |
| **Found by** | broad-reviewer (High), test-reviewer (High), adversarial-reviewer (High), dotnet-reviewer (Medium), knowledge-reviewer (SHOULD), security-reviewer (Medium) |

**Issue**

All five new tests assert the optimization **fires**, and all five use result expressions built only from operators where NULL propagation is total: `~` (`Not`), `+` on ints, and string concatenation. `Is_not_null_optimizes_binary_op_with_mixed_checks` looks like a negative case but is not one — its surviving conjunct (`x.BoolA`) sits in the CASE **test**, which `DropNotNullChecks` walks; it says nothing about what `NullPropagatedOperands` may descend into.

There is therefore no test asserting that the CASE is **preserved** when the premise does not hold. Every one of the five wrong-result shapes proven above sits entirely inside the untested region, which is why the change ships green. Equally, any future widening of `NullPropagatedOperands` would produce *greener-looking* baselines (more CASEs collapsed) with nothing failing.

The seed data is not the problem — `NullSemanticsData.cs:44-49` builds a 3×3×3 cross product including `null` for every nullable column, and `AssertQuery` compares against the in-memory model, so a test of the right shape **would** have caught this. The gap is that none was written.

**Fix**

Add negative cases alongside the five, each with a provider baseline asserting the `CASE` survives:

```csharp
// must NOT optimize — AndAlso/OrElse absorb the operand's nullness
ss.Set<NullSemanticsEntity1>().Select(x => x.NullableIntA != null ? (bool?)(x.NullableIntA > 5 && x.IntB > 100) : null)
ss.Set<NullSemanticsEntity1>().Select(x => x.NullableIntA != null ? (bool?)(x.NullableIntA > 5 || x.BoolA)     : null)
// must NOT optimize — comparison yields UNKNOWN, not NULL
ss.Set<NullSemanticsEntity1>().Select(x => x.NullableIntA != null ? (bool?)(x.NullableIntA > 5)                : null)
// must NOT optimize — operand reachable only through a non-propagating argument
ss.Set<NullSemanticsEntity1>().Select(x => x.NullableIntA != null ? x.NullableIntB                             : null)
```

Add the WHERE-position variant too — the projection tests would not have caught the row-leak on their own.

### #4 🟡 Medium: Populate-then-check ordering plus quadratic structural hashing on the query-compilation path

| | |
|---|---|
| **File** | `src/EFCore.Relational/Query/SqlNullabilityProcessor.cs:580`, `:619` |
| **Category** | efficiency |
| **Confidence** | 100 (mechanism verified against the `GetHashCode` implementations) |
| **Found by** | performance-reviewer (Medium ×2), broad-reviewer (Low), design-reviewer (Low) |

**Issue**

Two compounding costs, both paid before anything is known to be droppable:

1. **Wrong order of work.** For *every* single-when-clause CASE with an explicit `ELSE NULL`, a `HashSet` is allocated (line 580) and the entire result tree is walked and hashed (line 582) **before** `DropNotNullChecks` (line 583) is consulted about whether the test even contains an `IS NOT NULL`. Measured against this repo's own baselines, `ELSE NULL` occurrences drop from 223 to 199 — so roughly 80% of the CASEs entering this block pay the full walk for nothing. The change's own `Is_not_null_optimizes_binary_op_with_mixed_checks` is an example: its surviving test is `[e].[BoolA] = CAST(1 AS bit)`, containing no null check, yet the result tree is walked in full.

2. **Structural hashing is recursive and unmemoized.** Verified: `SqlBinaryExpression.GetHashCode => HashCode.Combine(base.GetHashCode(), OperatorType, Left, Right)` (`SqlBinaryExpression.cs:173`) and `SqlUnaryExpression.cs:137` likewise; only `ColumnExpression.cs:109` is O(1). Hashing one node therefore costs O(its subtree). Since `NullPropagatedOperands` inserts every node on the propagating paths, population costs the sum of all subtree sizes — **quadratic for a left-deep chain**, which is exactly the shape of `a + b + c + …`, the shape `Is_not_null_optimizes_binary_op_with_partial_checks` exercises.

Bounded by `RelationalCommandCache` (keyed on query expression + per-parameter null signature), so this is per-compilation, not per-execution — which is why it is Medium and not higher.

**Fix**

Scan `clause.Test`'s top-level `AndAlso` spine for any `SqlUnaryExpression { OperatorType: NotEqual }` before allocating anything; skip straight to `caseExpression.Update(...)` when there is none. If the set is still hot after that, give it an explicit comparer with a shallow `GetHashCode` (e.g. `HashCode.Combine(e.GetType(), e.Type)`) delegating `Equals` to `x.Equals(y)` — same lookup results, linear population. Do **not** substitute `ReferenceEqualityComparer`: test and result subtrees are visited separately and are not guaranteed reference-identical.

### #5 🟡 Medium: The soundness invariant is unstated, and the steering comment describes a much narrower optimization than the code performs

| | |
|---|---|
| **File** | `src/EFCore.Relational/Query/SqlNullabilityProcessor.cs:576`, `:617` |
| **Category** | knowledge-preservation |
| **Confidence** | 100 |
| **Found by** | knowledge-reviewer (MUST + SHOULD), broad-reviewer (Medium), design-reviewer (Medium) |

**Issue**

The block's only commentary is `// optimize expressions such as expr != null ? expr : null`, which describes the degenerate identity case. The code actually handles conjunctions of guards, *partial* removal with reconstruction, and propagation through unary operators, binary operators, and function arguments and instances — none of it hinted at. A maintainer triaging "why did my `a != null && b != null && f(c) ? … : null` lose only two of its guards?" will read the comment, conclude this block cannot be responsible, and look elsewhere.

More consequentially, the theorem `NullPropagatedOperands` depends on — *"collects every sub-expression `X` of `expression` for which `X IS NULL` implies `expression IS NULL`"* — is written down nowhere. `ExpressionType.Not or Negate or Convert` reads as an arbitrary trio, and the unfiltered binary arm reads as though all binary operators were intended. This gap is causally connected to finding #1: the missing invariant is exactly what the binary arm violates, and the `// TODO: optimize expr == null ? null : expr` on line 577 invites the next maintainer to extend the same unsound arm believing it is the established pattern.

**Fix**

Replace line 576 with a statement of what the block does, and add the invariant at the `NullPropagatedOperands` declaration together with the rule for extending it — *only descend through nodes that yield `NULL` (not `UNKNOWN`) when the operand is `NULL`; search-condition-producing operators are excluded because a provider may later materialize them as `CASE WHEN cond THEN 1 ELSE 0 END`.*

### #6 🟡 Medium: `DropNotNullChecks` overloads `null` to mean "statically true", documented only by a trailing `// true`

| | |
|---|---|
| **File** | `src/EFCore.Relational/Query/SqlNullabilityProcessor.cs:595` (sentinel produced at `:600`, consumed at `:585` and `:607-609`) |
| **Category** | comprehension-risk / null-safety |
| **Confidence** | 100 |
| **Found by** | knowledge-reviewer (SHOULD), dotnet-reviewer (Low) |

**Issue**

In a nullable-annotated codebase, `SqlExpression?` reads as "absent/failed" — the opposite polarity to the intended "the condition folded away to TRUE". Both consuming sites reinforce the misreading: `if (test is null) return clause.Result;` at line 585 looks like a missing-value guard, and the ternary chain `left is null ? right : right is null ? left : binary.Update(left, right)` at lines 607-609 looks like ordinary null-coalescing of an absent operand rather than constant-folding of `TRUE AND e ⟹ e`.

The natural defensive edit — `DropNotNullChecks(clause.Test, ops) ?? clause.Test`, or an added null-guard — would silently disable the optimization, and the compiler cannot flag it because both readings type-check.

**Fix**

Either document it at the declaration (*"returns the test with all redundant `IS NOT NULL` conjuncts removed, or `null` when every conjunct was removed — i.e. the test is statically TRUE and the CASE collapses to its result"*), or make the sentinel explicit: `static bool TryDropNotNullChecks(SqlExpression, HashSet<SqlExpression>, out SqlExpression? remaining)`.

### #8 🟢 Low: `CASE WHEN t THEN r END` (no `ELSE`) is never optimized, though it is semantically identical to `ELSE NULL`

| | |
|---|---|
| **File** | `src/EFCore.Relational/Query/SqlNullabilityProcessor.cs:578` |
| **Category** | missed-optimization / consistency |
| **Confidence** | 100 |
| **Found by** | broad-reviewer, knowledge-reviewer, adversarial-reviewer, design-reviewer, dotnet-reviewer, performance-reviewer, test-reviewer |

`IsNull` (line 1633) matches only `SqlConstantExpression { Value: null }` or a null-valued parameter; it returns `false` for a C# `null` `elseResult`. So a `CaseExpression` built with `elseResult: null` — which `SqlExpressionFactory.Case` produces for any translator that omits the else — silently skips the optimization, while the same tree built with an explicit NULL constant does not.

This contradicts how `VisitCase` models the same thing six lines earlier: line 572 returns `elseResult ?? _sqlExpressionFactory.Constant(null, …)`, i.e. absent-ELSE is canonically null. Two semantically identical trees emit different SQL depending on their provenance.

**Fix**: gate on `(elseResult is null || IsNull(elseResult))`. Note the `nullable` out-parameter stays correct on that path — line 562 already sets `nullable |= elseResult == null`. Expect baseline churn; if none appears, the shape does not occur in the corpus and the fix is cosmetic.

### #9 🟢 Low: `SqlBinaryExpression` with `Coalesce` is constructible and would be mis-handled (latent, not currently reachable in-box)

| | |
|---|---|
| **File** | `src/EFCore.Relational/Query/SqlNullabilityProcessor.cs:626` |
| **Category** | correctness (latent) |
| **Confidence** | 75 |
| **Found by** | broad-reviewer, adversarial-reviewer, dotnet-reviewer, security-reviewer |

Recorded separately from #1 because its reachability is different, and because one reviewer overstated it.

**Verified**: `SqlExpressionFactory.Coalesce` (lines 485-511) emits a `SqlFunctionExpression("COALESCE", …, argumentsPropagateNullability: [false, false])`, **not** a `SqlBinaryExpression`. `NullPropagatedOperands`'s function arm handles that correctly and does not recurse. So the in-box `??` path is safe today — the security-reviewer's claim that `??` produces a `SqlBinaryExpression{Coalesce}` reaching the unfiltered arm is **incorrect** (see Refuted, below).

**But**: `SqlBinaryExpression.IsValidOperator` admits `Coalesce`, and `SqlExpressionFactory.MakeBinary` does not special-case it — `MakeBinary(ExpressionType.Coalesce, …)` returns a `SqlBinaryExpression{Coalesce}`. A provider or a future in-box change taking that route would hit the unfiltered arm and rewrite `CASE WHEN A IS NOT NULL THEN COALESCE(A, 'x') ELSE NULL END` to `COALESCE(A, 'x')`, returning `'x'` where `NULL` is required.

**Fix**: the allowlist in #1 closes this as a side effect. No separate work needed.

## Specialist Notes

### Threat Model Notes (security-reviewer)

- The security-relevant asset is the **WHERE clause**. EF global query filters (`HasQueryFilter`) are the idiomatic mechanism for multi-tenancy and row-level authorization, and they are ordinary LINQ predicates flowing through this exact rewrite. The WHERE-position probe above returns a row that must be excluded, so for those applications finding #1 is an access-control defect, not only a correctness bug.
- **Parameter-value dependence is safe** — checked, no finding. `IsNull` (line 1633) reads `ParameterValues[parameterName]`, but `RelationalCommandCache.CommandCacheKey.Equals` (`Internal/RelationalCommandCache.cs:139`) compares `(value == null) != (otherValue == null)` per parameter, so parameter *nullability* is part of the cache key. A plan built when the else-parameter was null cannot be reused for a non-null value. The invariant stated in the comment at line 1632 holds, and the new rewrite sits inside the nullability-keyed region.
- **No injection, secrets, crypto, or network surface** in this diff. Generated SQL stays parameterized; the change never builds a literal from user data.

### Considered But Not Flagged

**Refuted by the validation wave** (2 validators dispatched, both returned `refuted` with evidence):

- *"The optimization silently strengthens the contract of `SqlFunctionExpression.ArgumentsPropagateNullability`/`InstancePropagatesNullability`"* (design-reviewer, High) — **refuted**. The premise that `VisitSqlFunction` was the only prior consumer and read the flags only forward is wrong. `VisitUnary`'s `SqlFunctionExpression` case at lines 2392-2429 already uses the reverse direction, unconditionally rewriting `function(a,b) IS NULL → a IS NULL || b IS NULL` and `IS NOT NULL → a IS NOT NULL && b IS NOT NULL`. That is an equivalence, requiring both directions, and it predates this change (confirmed via `git show 4e1a381ca~1`). Verified independently by reading lines 2388-2432. The XML-doc ambiguity is real but pre-existing.
- *"Null-propagation knowledge in local static functions gives providers no extension seam"* (design-reviewer + adversarial-reviewer, High) — **refuted**. Non-virtual private helpers are this file's norm, not a deviation: `VisitSqlBinary` already delegates its core rewriting to the private `OptimizeComparison` (:1706), `RewriteNullSemantics` (:1825), `SimplifyLogicalSqlBinaryExpression` (:1902), and `ProcessNullNotNull` (:2242). `VisitCase` is itself `protected virtual` (:499), so a coarse seam exists. The "silent fall-through for provider node types" sub-claim is also wrong in direction: both helpers default conservatively (keep the check / don't add the operand), so an unhandled node yields a missed optimization, never wrong SQL.

**Dismissed on verification:**

- **Stack-overflow DoS from unbounded recursion** (security-reviewer, Medium; raised and self-dismissed by dotnet-reviewer and performance-reviewer) — no *new* risk. `SqlNullabilityProcessor.Visit` already recurses over the same tree to the same depth with larger frames before these helpers run; a tree deep enough to overflow here has already overflowed in `Visit`. Tiered down.
- **`??` reaches the unfiltered binary arm in-box** (security-reviewer) — incorrect; see finding #9. `SqlExpressionFactory.Coalesce` emits a `SqlFunctionExpression`.
- **`ArgumentsPropagateNullability.Count` index/NRE risk** (raised by broad, dotnet, adversarial, design) — ruled out by all four independently. `IsNiladic` carries `[MemberNotNullWhen(false, nameof(Arguments), nameof(ArgumentsPropagateNullability))]` (`SqlFunctionExpression.cs:242`) and the constructor rejects a count mismatch (lines 216-224).
- **`HashSet<SqlExpression>` relying on structural rather than reference equality** — correct as written; every relevant subclass overrides `Equals`/`GetHashCode` structurally, and the same SQL text denoting the same value is the intended semantics. Had it been reference-only, the lookup would fail and the optimization would simply not fire — the safe direction. (Its *cost* is finding #4.)
- **`return clause.Result` discarding `caseExpression.Type`/`TypeMapping`** — sound. `CaseExpression`'s constructors derive both from `whenClauses[0].Result` (`CaseExpression.cs:33`, `:48`), and `ApplyTypeMappingOnCase` pushes the mapping into each when-clause result. The identical collapse already exists pre-change at line 546.
- **`nullable` out-parameter wrong after the early return** — sound. `nullable |= elseResultNullable` runs before the new block, and the NULL constant in the ELSE sets it true.
- **Divide-by-zero / arithmetic errors from removing a guard** — no new error surface. Only `IS NOT NULL` conjuncts are dropped, and SQL Server returns NULL rather than erroring for `NULL / 0`.
- **`allowOptimizedExpansion` not consulted by the new block** — correct to ignore; the rewrite claims an unconditional equivalence and does not need the weaker "null == false" licence.
- **Bare `// TODO:` without an issue number** (line 577) — checked against house style and *not* a violation: `SqlNullabilityProcessor.cs:2173`, `:2181`, `:2208` and roughly half the TODOs under `src/EFCore.Relational/Query/` carry no issue number.
- **No release-note artifact for the SQL shape change** — no such directory exists in this repo (user-facing docs live in `dotnet/EntityFramework.Docs`), and comparable optimizer commits on this file carried none.
- **`VisitCase` now ~150 lines with two trailing local functions** — real but with no nameable consequence beyond what #5 and #6 already cover.
- **Stale baselines elsewhere in the tree** — searched and found **none**. The only two non-updated `CASE WHEN … IS NOT NULL … ELSE NULL END` baselines are `AdHocMiscellaneousQuerySqlServerTest.cs:1678` and `:2399`, and in both the tested column differs from the result column, so they correctly must not collapse.
- **`LikeExpression` not handled by `NullPropagatedOperands`** — a missed optimization (`Null_propagation_optimization3` keeps its CASE on SQLite), not a defect. Worth noting if the visitor is later extended, since that baseline would then need updating.

### Positive Observations

- The optimization is correctly gated on `testIsCondition && single when clause && null else` — precisely the shape where CASE collapse can be sound.
- `DropNotNullChecks` decomposes `AndAlso` (safe, since both conjuncts must hold) and deliberately does **not** decompose `OrElse` (unsafe). That half of the change is right, and the partial-drop reconstruction via `binary.Update` avoids allocating when nothing changed.
- Delegating function nullability to `InstancePropagatesNullability`/`ArgumentsPropagateNullability` reuses the model's authoritative encoding rather than re-deriving it — which is why `COALESCE` is handled correctly.
- The unary arm's operator list is exactly right, and matches `ProcessNullNotNull`'s own list at lines 2290-2296.
- Baselines were regenerated across all five affected suites (SqlServer, TPC, TPT, Temporal, Sqlite) and the SQL diffs are a clear, reviewable improvement.
- **The benefit is real.** `SELECT CASE WHEN [c].[Name] IS NOT NULL THEN [c].[Name] ELSE NULL END` → `SELECT [c].[Name]` removes a per-row branch evaluation, and a bare column is sargable and index-coverable where a CASE wrapper is neither. Where such an expression lands in a predicate or join key this can convert a scan into a seek. The findings above are about *how* the rewrite is computed and bounded, not about whether it is worth doing.
