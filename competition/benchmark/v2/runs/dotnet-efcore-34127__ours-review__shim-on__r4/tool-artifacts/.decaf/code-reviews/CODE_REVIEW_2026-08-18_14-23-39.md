## Findings

### #1 🔴 Critical: `NullPropagatedOperands` treats `AndAlso`/`OrElse` as null-propagating, so the `IS NOT NULL` guard is deleted from a CASE whose result is a boolean `AND`/`OR` — query returns `true`/`false` where it must return `null`

| | |
|---|---|
| **File** | `src/EFCore.Relational/Query/SqlNullabilityProcessor.cs:626-629` |
| **Category** | correctness / silent-wrong-result |
| **Confidence** | 100 |
| **Verified** | CONFIRMED — executed on SQLite (wrong rows returned) and confirmed by generated-SQL diff on SQL Server; base commit is correct on the same inputs |
| **Found by** | quick-reviewer (Critical), broad-reviewer (Critical), dotnet-reviewer (Critical), adversarial-reviewer (Critical), consistency-reviewer (High), test-reviewer (High, coverage angle) |

**Issue:** `NullPropagatedOperands` recurses into `Left` and `Right` of **every** `SqlBinaryExpression`, regardless of `OperatorType`:

```csharp
else if (expression is SqlBinaryExpression binary)
{
    NullPropagatedOperands(binary.Left, operands);
    NullPropagatedOperands(binary.Right, operands);
}
```

That is only valid for operators where "an operand is NULL ⟹ the whole expression is NULL". `ExpressionType.AndAlso` and `ExpressionType.OrElse` — rendered as SQL `AND` and `OR` (`src/EFCore.Relational/Query/QuerySqlGenerator.cs:1090`) — do not satisfy it under three-valued logic: `NULL AND FALSE = FALSE` and `NULL OR TRUE = TRUE`. Registering their operands as null-propagating lets `DropNotNullChecks` delete the guard that was carrying the `NULL` result.

**This file already documents the exact carve-out the new code omits.** `ProcessNullNotNull`'s binary case is guarded `when sqlBinaryOperand.OperatorType != ExpressionType.AndAlso && sqlBinaryOperand.OperatorType != ExpressionType.OrElse`, with the comment `// for AndAlso, OrElse we can't do this optimization` (`SqlNullabilityProcessor.cs:2314-2321`); `OptimizeNonNullableNotExpression` special-cases them under `// optimizations below are only correct in 2-value logic` (`SqlNullabilityProcessor.cs:2003-2009`).

**Confirmed failure — executed against SQLite** with data replicating `NullSemanticsData`:

| query | row | expected (LINQ-to-Objects) | actual (this change) | actual (base commit) |
|---|---|---|---|---|
| `x.NullableBoolA != null ? (bool?)(x.NullableBoolA == true \|\| x.BoolB) : null` | `NullableBoolA = NULL, BoolB = true` | `null` | **`True`** | `null` ✓ |
| `x.NullableBoolA != null ? (bool?)(x.NullableBoolA == true && x.BoolB) : null` | `NullableBoolA = NULL, BoolB = false` | `null` | **`False`** | `null` ✓ |

Generated SQLite SQL under this change — the guard is gone entirely:

```sql
SELECT "e"."NullableBoolA" OR "e"."BoolB"   FROM "Entities1" AS "e"
SELECT "e"."NullableBoolA" AND "e"."BoolB"  FROM "Entities1" AS "e"
```

SQL Server shows the same loss (`ToQueryString()`, this change vs. base):

```sql
-- this change
SELECT CASE WHEN [e].[NullableBoolA] = CAST(1 AS bit) OR [e].[BoolB] = CAST(1 AS bit)
            THEN CAST(1 AS bit) ELSE CAST(0 AS bit) END
FROM [Entities1] AS [e]

-- base commit 051c33a79
SELECT CASE WHEN [e].[NullableBoolA] IS NOT NULL
            THEN CASE WHEN [e].[NullableBoolA] = CAST(1 AS bit) OR [e].[BoolB] = CAST(1 AS bit)
                      THEN CAST(1 AS bit) ELSE CAST(0 AS bit) END
            ELSE NULL END
FROM [Entities1] AS [e]
```

**Fix:**
```csharp
else if (expression is SqlBinaryExpression
    { OperatorType: not (ExpressionType.AndAlso or ExpressionType.OrElse) } binary)
{
    NullPropagatedOperands(binary.Left, operands);
    NullPropagatedOperands(binary.Right, operands);
}
```
Note this fix alone does **not** address finding #2.

### #2 🔴 Critical: Dropping the guard on a **boolean-typed** result loses the `NULL` on SQL Server even for genuinely null-propagating operators — `SearchConditionConvertingExpressionVisitor` re-wraps the bare condition with `ELSE CAST(0 AS bit)`

| | |
|---|---|
| **File** | `src/EFCore.Relational/Query/SqlNullabilityProcessor.cs:576-591` |
| **Category** | correctness / silent-wrong-result |
| **Confidence** | 100 |
| **Verified** | CONFIRMED — generated-SQL diff on SQL Server against the base commit |
| **Found by** | adversarial-reviewer (Critical) — sole finder |

**Issue:** This is a second, independent defect: it survives the fix for #1 because the operator involved (`GreaterThan`) genuinely *does* propagate NULL.

On SQL Server a boolean expression is a *search condition*, not a value. `SqlNullabilityProcessor` runs before `SearchConditionConvertingExpressionVisitor` (`src/EFCore.SqlServer/Query/Internal/SqlServerParameterBasedSqlProcessor.cs:40-45` — the converter is applied to the result of `base.Optimize`, which is what performs nullability processing). When the new optimization strips the surrounding `CASE … ELSE NULL END` and hands back the bare condition, the converter later lifts it into the value domain with `ConvertToValue` (`SearchConditionConvertingExpressionVisitor.cs:40-50`), which emits only a two-arm `CASE WHEN <cond> THEN 1 ELSE 0 END`. There is no `NULL` arm, so `UNKNOWN` collapses to `false`.

The removed `CASE … ELSE NULL END` was the only thing carrying the three-state result across that boundary.

**Confirmed — SQL Server `ToQueryString()` for `x.NullableIntA != null ? (bool?)(x.NullableIntA > x.IntB) : null`:**

```sql
-- this change  →  NullableIntA = NULL yields 0 (false); must be NULL
SELECT CASE WHEN [e].[NullableIntA] > [e].[IntB] THEN CAST(1 AS bit) ELSE CAST(0 AS bit) END
FROM [Entities1] AS [e]

-- base commit 051c33a79  →  correct
SELECT CASE WHEN [e].[NullableIntA] IS NOT NULL
            THEN CASE WHEN [e].[NullableIntA] > [e].[IntB] THEN CAST(1 AS bit) ELSE CAST(0 AS bit) END
            ELSE NULL END
FROM [Entities1] AS [e]
```

The same query on SQLite is unaffected (SQLite emits the bare comparison, which evaluates to `NULL`) — this is a provider-specific loss confined to providers that run a search-condition converter.

**Fix:** do not apply the optimization when `clause.Result` is a boolean *condition* rather than a value — i.e. bail out when the result's `Type` is `bool`/`bool?` and it is a `SqlBinaryExpression` comparison/logical node or a `SqlUnaryExpression { OperatorType: Not }`. Alternatively, make the optimization conditional on a provider hook (see the related note in Minor Findings about extensibility), since only providers with a search-condition converter are affected.

## Specialist Notes

### Considered But Not Flagged (all agents, plus orchestrator probe results)

**Refuted by probe — reported by four reviewers, disproved by evidence:**

- **`COALESCE` treated as null-propagating** (quick-reviewer Critical, broad-reviewer Critical, dotnet-reviewer Critical, adversarial-reviewer Medium). All four asserted that `x.A != null ? (x.A ?? x.B) : null` loses its guard. **Refuted three ways:** (1) `??` is translated by `SqlExpressionFactory.Coalesce` into a `SqlFunctionExpression` with `argumentsPropagateNullability: [false, false]` (`SqlExpressionFactory.cs:503-509`), which the new code's `SqlFunctionExpression` branch correctly declines to recurse into; (2) a relational `SqlBinaryExpression` with `ExpressionType.Coalesce` is never constructed — every relational path routes through the factory, and this file contains no `ExpressionType.Coalesce` binary handling at all; (3) the probe emits an **identical, correctly guarded** `CASE WHEN [NullableIntA] IS NOT NULL THEN COALESCE(...) ELSE NULL END` on both SQLite and SQL Server, matching the base commit exactly, and the executed rows match LINQ-to-Objects.
- **Bitwise `And`/`Or` treated as unsound** (dotnet-reviewer, part of its Critical). Refuted: `ExpressionType.And`/`Or` render as `&`/`|` (`QuerySqlGenerator.cs:1090,1097`), which do propagate NULL. Only `AndAlso`/`OrElse` are affected.

**Examined and correctly dismissed:**

- `HashSet<SqlExpression>` default-comparer semantics — `ColumnExpression`, `SqlUnaryExpression`, `SqlBinaryExpression` and `SqlFunctionExpression` all override `Equals`/`GetHashCode` with structural equality, so `Contains` matches as the author intends. (broad-reviewer, dotnet-reviewer)
- `ArgumentsPropagateNullability`/`Arguments` index or length mismatch — the constructor throws on a count mismatch (`SqlFunctionExpression.cs:216-225`) and `IsNiladic` carries `[MemberNotNullWhen(false, …)]` (`:242`), so the `!func.IsNiladic` guard is compiler-verified. (dotnet-reviewer)
- `nullable` out-parameter on the early `return clause.Result;` path — `elseResult` is a null constant, so `nullable` is already conservatively `true`. Sound. (broad-reviewer, adversarial-reviewer)
- Returning `clause.Result` in place of the whole `CaseExpression` (type/type-mapping bypass) — mirrors the unmodified pre-existing pattern at `SqlNullabilityProcessor.cs:547`. Not introduced here. (broad-reviewer)
- `ExclusiveOr` left unrestricted in the same recursion — sound; XOR has no absorbing element in three-valued logic. (broad-reviewer)
- Aggregates, `EXISTS`, `IN`, nested `CaseExpression`, subqueries and window functions in the result — `NullPropagatedOperands` has no recursion branch for these node types, so their operands never enter the set; no false drop constructible. (adversarial-reviewer)
- `SqlUnaryExpression { Not }` over `IS NULL` — the recursion reaches the `IS NULL` node but does not descend through `Equal`/`NotEqual`, so the inner operand never enters the set. Sound. (adversarial-reviewer)
- Unbounded recursion depth in both helpers — the enclosing `Visit` already recurses to the same depth over the same tree, so no new maximum is introduced. (broad-reviewer, dotnet-reviewer, adversarial-reviewer)
- Compile-time cost of building the operand `HashSet` unconditionally, with recursive uncached `GetHashCode` — real but query-plan-cached, so a first-execution latency effect only; anchor 50, no nameable production consequence. (adversarial-reviewer)
- Bare `// TODO: optimize expr == null ? null : expr` without an issue link — this file and the wider codebase contain TODOs both with and without issue numbers, so there is no convention to violate. (consistency-reviewer)
- `return null; // true` as a sentinel in an `SqlExpression?` signature — readability smell only; both call sites handle it consistently. (dotnet-reviewer)
- Placement of the helpers as local `static` functions rather than private methods — matches the sibling `TryNegate` local static at `:2095`. (consistency-reviewer) *(The separate extensibility concern is recorded under Minor Findings.)*
- New test naming and `[ConditionalTheory]`/`[MemberData(nameof(IsAsyncData))]` structure — matches the adjacent tests; no drift. (consistency-reviewer)
- Mechanical GearsOfWar/Sqlite baseline updates — all correspond to genuinely null-propagating, non-boolean results; each is a correct simplification. (test-reviewer, broad-reviewer, confirmed by probe case E)
