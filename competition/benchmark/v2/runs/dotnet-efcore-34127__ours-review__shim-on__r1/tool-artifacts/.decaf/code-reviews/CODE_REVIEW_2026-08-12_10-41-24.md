## Findings

### #1 🔴 Critical: `NullPropagatedOperands` treats `AndAlso`/`OrElse` as null-propagating, so the optimization returns wrong rows on every provider

| | |
|---|---|
| **File** | `src/EFCore.Relational/Query/SqlNullabilityProcessor.cs:626` |
| **Category** | correctness / null-semantics |
| **Confidence** | 100 — reproduced by executing probes 2, 3 and 5 against SQLite; all three pass at the base commit |
| **Found by** | quick-reviewer (Critical), broad-reviewer (Critical), adversarial-reviewer (Critical), dotnet-reviewer (Critical), test-reviewer (High), knowledge-reviewer (MUST) |

**Issue:** `NullPropagatedOperands` recurses into both operands of *every* `SqlBinaryExpression` without inspecting `OperatorType`:

```csharp
else if (expression is SqlBinaryExpression binary)
{
    NullPropagatedOperands(binary.Left, operands);
    NullPropagatedOperands(binary.Right, operands);
}
```

The whole rewrite rests on the invariant that every operand placed in `nullPropagatedOperands` forces the *entire* result to NULL when that operand is NULL, regardless of the other operands' values. `AndAlso` and `OrElse` — both sanctioned operators per `SqlBinaryExpression.IsValidOperator` (`src/EFCore.Relational/Query/SqlExpressions/SqlBinaryExpression.cs:93-96`) — violate it under SQL three-valued logic: `NULL AND FALSE = FALSE` and `NULL OR TRUE = TRUE`, not NULL. `DropNotNullChecks` therefore deletes a guard that is not redundant, and the `CASE` collapses to a bare expression that yields a definite `TRUE`/`FALSE` where the original yielded NULL.

This same exclusion already exists a few hundred lines away in this file, with a comment saying exactly why — `ProcessNullNotNull`'s binary branch guards `sqlBinaryOperand.OperatorType != ExpressionType.AndAlso && ... != ExpressionType.OrElse` ("for AndAlso, OrElse we can't do this optimization", `SqlNullabilityProcessor.cs:2313-2321`) for the inverse transformation. The new code omits it.

**Reproduced (probe 3, SQLite):**

```csharp
ss.Set<Entity>().Select(x => x.NullableBoolA != null ? (bool?)(x.NullableBoolA.Value && x.BoolB) : null)
```

| | SQL |
|---|---|
| base `051c33a79` | `SELECT CASE WHEN "e"."NullableBoolA" IS NOT NULL THEN "e"."NullableBoolA" AND "e"."BoolB" ELSE NULL END` |
| this change | `SELECT "e"."NullableBoolA" AND "e"."BoolB"` |

Row `NullableBoolA = NULL, BoolB = false`: LINQ-to-Objects and the base commit both return `null`; this change returns `false`. 9 of 54 seeded rows disagree. Probe 2 (`||`, row `A = NULL, B = true` → `true` instead of `null`) and probe 5 (`A > 5 && B`, row `A = NULL, B = false` → `false` instead of `null`) fail identically.

Nothing raises an error — applications silently receive different data. When such a conditional feeds a predicate rather than a projection, the row set itself changes.

**Fix:** Gate the binary recursion on the operator, and exclude the operators that are not unconditionally null-propagating:

```csharp
else if (expression is SqlBinaryExpression
         {
             OperatorType: not (ExpressionType.AndAlso or ExpressionType.OrElse or ExpressionType.Coalesce)
         } binary)
{
    NullPropagatedOperands(binary.Left, operands);
    NullPropagatedOperands(binary.Right, operands);
}
```

(`Coalesce` is included for the reason given in finding #5; it is latent rather than currently reachable.) Note this fix does **not** address finding #2 — probe 4 contains no `AndAlso`/`OrElse` anywhere and still miscompiles.

### #2 🔴 Critical: collapsing a `CASE` whose result is a search condition drops the NULL arm, so SQL Server returns `false` instead of `null`

| | |
|---|---|
| **File** | `src/EFCore.Relational/Query/SqlNullabilityProcessor.cs:578` |
| **Category** | correctness / null-semantics |
| **Confidence** | 100 — the generated T-SQL, captured from a build of this commit, provably cannot produce NULL; base-commit T-SQL for the same query does |
| **Found by** | adversarial-reviewer (Critical) — sole finder |

**Issue:** This is a **second, independent** defect. When the when-clause test is `<col> IS NOT NULL`, `VisitSqlUnary` adds that column to `_nonNullableColumns`, so while visiting the result `VisitSqlBinary` sees a non-nullable operand and skips the protective `CASE WHEN <cmp> THEN 1 ELSE 0 END` wrap (`SqlNullabilityProcessor.cs:1411`). `clause.Result` is therefore left as a bare SQL *search condition*, not a value. The new block then deletes the test and returns that search condition as the whole expression. Afterwards `SearchConditionConvertingExpressionVisitor` — which runs after `SqlNullabilityProcessor` (`SqlServerParameterBasedSqlProcessor.Optimize`) — converts it to a value with `CASE WHEN <cond> THEN CAST(1 AS bit) ELSE CAST(0 AS bit) END`. That form has **no NULL arm**: an UNKNOWN condition falls to `ELSE` and yields `0`.

A SQL condition has no NULL *value*, so `ELSE NULL` is not redundant for a condition-typed result even when the condition is UNKNOWN — which is the assumption the new block makes.

**Reproduced (probe 4, SQL Server T-SQL generated from each build):**

```csharp
ss.Set<Entity>().Select(x => x.NullableIntA != null ? (bool?)(x.NullableIntA > 5) : null)
```

base `051c33a79`:
```sql
SELECT CASE
    WHEN [e].[NullableIntA] IS NOT NULL THEN CASE
        WHEN [e].[NullableIntA] > 5 THEN CAST(1 AS bit)
        ELSE CAST(0 AS bit)
    END
    ELSE NULL
END
FROM [Entities] AS [e]
```

this change:
```sql
SELECT CASE
    WHEN [e].[NullableIntA] > 5 THEN CAST(1 AS bit)
    ELSE CAST(0 AS bit)
END
FROM [Entities] AS [e]
```

For `NullableIntA IS NULL`, the base query returns `NULL`; this one returns `0` → `false`. Probe 7 (`x.NullableStringA != null ? (bool?)(x.NullableStringA.Length == 1) : null`, i.e. the exact shape of the existing `Select_null_propagation_negative1` test but with the checked and used column being the same) miscompiles the same way.

**Why the test suite is green:** SQLite emits the bare comparison (`SELECT "e"."NullableIntA" > 5`), which *does* return NULL, so probes 4 and 7 agree on SQLite. The defect is confined to providers that run `SearchConditionConvertingExpressionVisitor` — SQL Server among them — and no existing or newly-added test projects a boolean conditional whose `ELSE` is NULL and whose result references the checked column. `Select_null_propagation_negative1` escapes only because it null-checks `LeaderNickname` and uses `Nickname`.

I could not execute against a SQL Server instance in this environment; the finding rests on the generated T-SQL, where `CASE WHEN <unknown> THEN CAST(1 AS bit) ELSE CAST(0 AS bit) END` returning `0` is unambiguous SQL semantics.

**Fix:** Restrict the collapse to results that are *values*, not search conditions — bail out when `clause.Result` is a condition (a `SqlBinaryExpression` with a comparison or logical operator, a `SqlUnaryExpression` `Not`, `LikeExpression`, `InExpression`, `ExistsExpression`), or equivalently when `clause.Result.Type` is `bool`/`bool?` and the result is not already a value-shaped expression. Whichever guard is chosen, add a test asserting the SQL Server baseline for probe 4's shape, since SQLite cannot detect this class of regression.

### #3 🟠 High: the soundness invariant the whole rewrite depends on is never stated

| | |
|---|---|
| **File** | `src/EFCore.Relational/Query/SqlNullabilityProcessor.cs:576-648` |
| **Category** | knowledge-preservation |
| **Confidence** | 100 (quotable fact — the comments are the only documentation present) |
| **Found by** | broad-reviewer (High), knowledge-reviewer (SHOULD) |

**Issue:** The only documentation for the new optimization is:

```csharp
// optimize expressions such as expr != null ? expr : null
// TODO: optimize expr == null ? null : expr
```

Nothing states the precondition the transformation actually needs — that an operand may be added to `nullPropagatedOperands` only when the containing expression is guaranteed to evaluate to NULL whenever that operand is NULL, *for any values of its other operands*. Nor is it recorded why the unary set is exactly `Not`/`Negate`/`Convert`, nor (per finding #2) that the result must be a value rather than a search condition.

That the unary branch is operator-filtered while the binary branch is not shows the criterion was applied inconsistently, which is what findings #1 and #2 are. A maintainer extending `NullPropagatedOperands` to a new node type has no written criterion to check the extension against.

**Fix:** Document the invariant above `NullPropagatedOperands`, naming the excluded cases and why:

```csharp
// Collects the sub-expressions of `expression` for which the following holds: if the
// sub-expression is NULL then `expression` as a whole is NULL, whatever the other operands
// evaluate to. That is what makes an enclosing `x IS NOT NULL` check redundant. Do not add an
// operator or function shape here unless the guarantee is unconditional: AndAlso/OrElse do NOT
// qualify (NULL AND FALSE = FALSE), and neither does COALESCE.
```

### #4 🟠 High: no test covers a boolean-typed or three-valued-logic result, and there are no negative tests

| | |
|---|---|
| **File** | `test/EFCore.Relational.Specification.Tests/Query/NullSemanticsQueryTestBase.cs:2250-2296` |

| **Found by** | test-reviewer (High), broad-reviewer (Medium), adversarial-reviewer (noted) |

**Issue:** All five added theories use results that are arithmetic (`~A`, `A + B`) or string concatenation — operator classes where SQL propagates NULL unconditionally, i.e. precisely the cases where the optimization is sound. None uses a boolean result, a comparison, `&&`/`||`, or any shape where the optimization must *not* fire. `Is_not_null_optimizes_binary_op_with_mixed_checks` has `&&` in the *test*, not in the result, so it does not exercise the defective path either.

There is also no negative test — no case asserting that a `CASE` is *retained*. For a rewrite this aggressive, the tests that matter most are the ones proving it declines to fire.

`AssertQuery` compares against LINQ-to-Objects over the seeded `NullSemanticsData` (a full 3×3×3 cartesian product of null/non-null), so a test in any of these shapes would have caught findings #1 and #2 at the row level, not merely as a SQL-shape diff.

```csharp
[ConditionalTheory]
[MemberData(nameof(IsAsyncData))]
public virtual Task Is_not_null_does_not_optimize_andalso_result(bool async)
```

### #5 🟢 Low: `ExpressionType.Coalesce` as a binary operator is a sanctioned shape that the recursion would mis-handle

| | |
|---|---|
| **File** | `src/EFCore.Relational/Query/SqlNullabilityProcessor.cs:626` |
| **Category** | correctness / latent |
| **Confidence** | 75 — the shape is sanctioned by `IsValidOperator`; probe 6 confirms nothing in-box constructs it |
| **Found by** | adversarial-reviewer (Medium), broad-reviewer (Critical — repro refuted, see below) |

**Issue:** `SqlBinaryExpression.IsValidOperator` accepts `ExpressionType.Coalesce` (`SqlBinaryExpression.cs:102`), and `COALESCE(a, b)` is by definition not null-propagating in `a`. Any provider or third-party translator that builds `new SqlBinaryExpression(ExpressionType.Coalesce, a, b, ...)` directly would have `a` marked null-propagating, and `a IS NOT NULL ? COALESCE(a, b) : null` would collapse to `COALESCE(a, b)` — returning `b` where NULL is required.

**Refuted as an in-box repro:** `broad-reviewer` reported this as Critical with the repro `x.NullableIntA != null ? (x.NullableIntA ?? 0) + x.NullableIntB : null`. Probe 6 ran that exact query and it is **correct** — `SqlExpressionFactory.Coalesce` (`SqlExpressionFactory.cs:485-509`) emits a `SqlFunctionExpression("COALESCE", …, argumentsPropagateNullability: [false, false])`, not a binary node, and the existing `SqlFunctionExpression` branch correctly declines to recurse into it. The generated SQL retains the CASE and all 54 rows agree. Severity is therefore Low (latent, not reachable through in-box translation), not Critical.

**Fix:** Covered by finding #1's operator whitelist, which excludes `Coalesce`.
