## Findings

### #1 🟠 High: Parse-time rejection discards the whole payload, destroying valid content that the app layer was designed to still deliver

| | |
|---|---|
| **File** | `server/public/model/command_response.go:72` (and `:90-98`) |
| **Category** | correctness / api-design |
| **Confidence** | 75 |
| **Verified** | traced |
| **Pre-existing** | no |
| **Found by** | solo-reviewer (High) |

**Issue:** `CommandResponseFromJSON` now returns `(nil, err)` for the *entire* response if any one field of any one nested response fails validation. Downstream, `App.HandleCommandResponse` (`server/channels/app/command.go:603-635`) was deliberately built to tolerate per-response failures — it posts the main response and each `ExtraResponses` entry independently, accumulating errors in `lastError` so a bad sibling does not suppress the good ones. Moving validation to parse time bypasses that design entirely: one bad extra response now suppresses the main post as well.

Second half of the same break: for an unknown `response_type`, the previous behavior in `CreateCommandPost` (`server/channels/app/command.go:72-84`) was to fall through *both* branches — not `in_channel`, not `""`/`ephemeral` — so the offending response was silently dropped and the command still completed. After this change the integration's whole reply is rejected at `server/channels/app/command.go:595` and re-wrapped as `api.command.execute_command.failed.app_error` with HTTP 500, so the user sees "Command with a trigger of '/x' failed" and gets no post at all.

**Evidence:** Traced the two call sites of `CommandResponseFromHTTPBody` — `server/channels/app/command.go:595` (outgoing slash command) and `server/channels/web/webhook.go:114` (delayed command webhook) — plus `Client4.ExecuteCommand`/`ExecuteCommandWithTeam` at `server/public/model/client4.go:5961,5982`.

Concrete before/after for `{"text":"main ok","response_type":"in_channel","extra_responses":[{"text":"extra","response_type":"comment"}]}`:
- Before: `"main ok"` posted in channel; the `"comment"` extra falls through both branches of `CreateCommandPost` and is silently dropped; command returns 200.
- After: `IsValid` recursion at line 95 returns the `response_type` error, `CommandResponseFromJSON` returns `nil`, and the command fails with 500. **`"main ok"` is lost.**

`"comment"` is not a hypothetical value: it is the valid `response_type` for the sibling outgoing-webhook contract (`OutgoingHookResponseTypeComment`, `server/public/model/outgoing_webhook.go:81`, exercised by `e2e-tests/cypress/webhook_serve.js:493`), so integration authors copying between the two doc pages land exactly here.

**Fix:** Do not fail the parse on a nested/soft validation problem. Either (a) keep `IsValid()` out of `CommandResponseFromJSON` and call it at the app layer per-response, inside the existing `lastError` loop in `HandleCommandResponse`, so a bad extra response only drops that response; or (b) if parse-time rejection is intended, restrict it to the top-level response and normalize/drop invalid `ExtraResponses` entries rather than failing the whole body. Either way, treat this as a documented behavior change for existing integrations.

### #2 🟡 Medium: Hard-coded 65535-*byte* text cap contradicts the server's configurable, rune-based post size limit

| | |
|---|---|
| **File** | `server/public/model/command_response.go:85-88` |
| **Category** | correctness / production |
| **Confidence** | 50 |
| **Verified** | traced |
| **Pre-existing** | no |
| **Found by** | solo-reviewer (Medium) |

**Issue:** Two mismatches against the limit this cap is presumably standing in for:

1. **Unit.** `len(o.Text)` counts bytes; the real limit applied to the resulting post is runes — `Post.IsValid` uses `utf8.RuneCountInString(o.Message) > maxPostSize` (`server/public/model/post.go:508`). So the effective new ceiling is 65535 characters of ASCII but ~16383 characters of 4-byte text, for no stated reason.
2. **Configurability.** `maxPostSize` is not a constant. `SqlPostStore.determineMaxPostSize` (`server/channels/store/sqlstore/post_store.go:2640-2662`) reads `character_maximum_length` from the `posts.message` column and computes `max(columnBytes/4, PostMessageMaxRunesV2)` runes, with the comment explicitly stating the column "may be manually enlarged to support longer posts." On such a server, posts of e.g. 250,000 runes are valid, but a slash-command response carrying 100,000 ASCII characters is now rejected in the model layer before the app ever consults the configured limit.

**Evidence:** Read `determineMaxPostSize` and `Post.IsValid`. With stock settings the cap is inert (16383 runes ≤ 65532 bytes always), so it rejects nothing that would not already have failed post validation — it only bites on servers with an enlarged `posts.message` column, which is why confidence is 50 rather than 75. Separately, `65535` already exists as a named constant, `PostMessageMaxBytesV2` (`server/public/model/post.go:72`); the magic literal duplicates it and will silently diverge.

**Fix:** If a model-layer cap is wanted, count runes and use the existing `PostMessageMaxBytesV2`/`PostMessageMaxRunesV2` constant rather than a bare `65535`. If the intent is to enforce the *actual* post limit, do it at the app layer where `a.MaxPostSize()` (`server/channels/app/post.go:2409`) is reachable, and let `Post.IsValid` remain the single source of truth.

### #3 🟡 Medium: New i18n message IDs are not registered in `server/i18n/en.json`, so the raw ID is rendered as the message

| **Verified** | executed |
| **Pre-existing** | no |

**Issue:** `model.command_response.is_valid.response_type.app_error` and `model.command_response.is_valid.text.app_error` do not exist in the translation bundle. `AppError.Translate` (`server/public/model/utils.go:281-296`) sets `er.Message = T(er.Id)`, and go-i18n returns the ID verbatim for an unknown key, so `AppError.Message` — which is what `Error()` renders (`utils.go:255-257`) and what ends up in the wrapping error's `DetailedError`, in server logs, and in `Client4`'s `fmt.Errorf("failed to decode command response: %w", err)` at `client4.go:5962` — reads `CommandResponse.IsValid: model.command_response.is_valid.text.app_error, text is too long`.

**Evidence:** Executed `grep -c "model.command_response" server/i18n/en.json` → `0`. Every sibling model validator does register its IDs; e.g. the structurally identical `model.authorize.is_valid.response_type.app_error` is at `server/i18n/en.json:10922`. This will not be caught in CI: `.github/workflows/i18n-ci-template.yml` only asserts that non-English files were not hand-edited, and `server/Makefile:342-345` (`i18n-check`) runs `clean-empty` / `check-empty-src`, neither of which detects an ID present in code but absent from `en.json`.

**Fix:** Add both IDs to `server/i18n/en.json` with English translations (only `en.json` may be edited; Weblate handles the rest), keeping the file's sorted-by-id ordering.

### #4 🟢 Low: The plain-text response path bypasses the new validation entirely, so neither invariant is actually enforced

| | |
|---|---|
| **File** | `server/public/model/command_response.go:72` |
| **Category** | api-design |
| **Confidence** | 100 |
| **Verified** | traced |
| **Pre-existing** | no |
| **Found by** | solo-reviewer (Low) |

**Issue:** `IsValid()` is called from exactly one place — the JSON decoder. `CommandResponseFromHTTPBody` (line 35) routes any non-`application/json` content type to `CommandResponseFromPlainText` (line 45), which constructs the struct directly and returns it unvalidated. So the same integration that is now rejected for a 100 KB JSON `text` succeeds by sending the identical 100 KB body as `text/plain`. The same applies to every in-process producer: built-in slash commands (`server/channels/app/slashcommands/*.go`) and plugin commands build `model.CommandResponse` values in Go and never touch `IsValid()`.

The result is an invariant that is enforced on one arbitrary ingress path and nowhere else — the stricter contract now advertised by a public `IsValid()` on `server/public` is not one callers can rely on.

**Evidence:** Read all four constructors in `command_response.go` and grepped every producer of `model.CommandResponse` under `server/channels/`. `TestCommandResponseFromHTTPBody` at `command_response_test.go:13-31` confirms the `text/plain` route returns a response with no validation step.

**Fix:** Pick one layer. Either validate in `CommandResponseFromHTTPBody` (covering both content types) — or, preferably and consistently with #1, at the app layer in `HandleCommandResponse`/`HandleCommandResponsePost`, where every producer converges regardless of origin.
