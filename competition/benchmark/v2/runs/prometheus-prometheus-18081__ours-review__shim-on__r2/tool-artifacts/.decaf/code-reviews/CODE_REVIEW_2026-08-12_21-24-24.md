### #1 🔴 Critical: Subquery per-step allocation is sized by the *subquery's* step count, giving a query-triggerable unrecoverable OOM

| | |
|---|---|
| **File** | `promql/engine.go:2397`, allocation at `util/stats/query_stats.go:306-310` |
| **Category** | resource-management / availability |
| **Confidence** | 100 — reproduced base vs. head |
| **Found by** | adversarial-reviewer (Critical), design-reviewer (Low — allocation cost only) |

**Issue:** The `*parser.SubqueryExpr` case now builds the child stats object over the **subquery's own step layout**:

```go
subqSamplesStats := stats.NewChildWithStepTracking(ev.samplesStats.StepTrackingEnabled(), subqStart, subqEnd, subqInterval)
```

`InitStepTracking` then does `make([]int64, numSteps)` **twice**, where `numSteps = (subqEnd-subqStart)/subqInterval + 1`. A subquery's resolution and range are attacker-chosen and, unlike a range query's step count, are **not** bounded by the API's 11 000-point limit. The allocation happens *before* any sample is read, so `-query.max-samples` (which counts samples during evaluation) never engages.

Previously this site called `ev.samplesStats.NewChild()` → `NewQuerySamples(false)`, which allocated no per-step slices at all. The cost is therefore entirely new.

Measured on a storage holding **11 samples**, instant query, per-step stats on vs. off, comparing base `efbdc3f88` against head `ec7157593`:

| query | base (head equal, per-step OFF) | head, per-step ON |
|---|---|---|
| `count_over_time(metric[100d:1s])` | 0.0 MiB | **132.0 MiB** in 0.14 s |
| `count_over_time(metric[1d:1ms])` | 22.9 MiB | **1341.3 MiB** in 1.3 s |

Both queries return **no error**. Scaling is linear in subquery step count. Extrapolating to `[100d:1ms]` gives `numSteps = 8.64e9` → a 69 GB request per slice; the Go runtime's response to that `make` was confirmed separately:

```
numSteps = 8640000000  bytes needed = 69120000000
fatal error: runtime: out of memory
runtime.throw(...)
```

This is `runtime.throw`, **not** a panic — a `recover()` in the same goroutine did not catch it, so the engine's existing recover-based error handling cannot intercept it either. The process dies.

Reachability requires the server to run `--enable-feature=promql-per-step-stats` and the client to pass `stats=all` — an opt-in experimental flag, which is why this is Critical rather than a release blocker for every deployment. But `stats=all` is a plain query parameter available to any user who can query, so on a flag-enabled server this is remote, unauthenticated-within-the-query-tier process termination.

**Fix:** Do not size a per-step array by the subquery's own step count. Either keep the child non-per-step (as before) and attribute the subquery's `SamplesRead` in aggregate, or allocate the child array at the **outer** step count and map subquery steps onto outer steps incrementally during evaluation rather than buffering one slot per subquery step. If the subquery layout is genuinely required, bound `numSteps` before the `make` and reject or aggregate above the limit.

### #2 🔴 Critical: `samplesRead` double-counts every subquery, compounding with nesting depth — the new metric reports more "reads" than samples loaded

| | |
|---|---|
| **File** | `promql/engine.go:1874` (`evalSubquery`), interacting with `promql/engine.go:2184` |
| **Category** | correctness / API contract |
| **Confidence** | 100 — reproduced, and visible in the change's own committed test data |
| **Found by** | adversarial-reviewer (High), design-reviewer (Critical), knowledge-reviewer (as deleted-rationale) |

**Issue:** `evalSubquery` now merges the child's read count into the parent:

```go
parentSamplesStats.MergeSamplesReadFromSubquery(ev.samplesStats)
```

and then returns a synthesized `MatrixSelector` that the **same** `*parser.Call` step loop immediately counts again via `IncrementSamplesReadAtStep(step, samplesReadCount)`. The same data is booked twice.

The deleted comment at this exact site warned about precisely this hazard for the sibling field:

> `// Avoid double counting samples when running a subquery, those samples will be counted in later stage.`

That guard was removed and no equivalent was added for `SamplesRead`.

Measured on head, instant queries, 1 sample / 10 s, real storage reads ≤ 12 in all three cases:

| query | `TotalSamples` | `SamplesRead` | actual reads |
|---|---|---|---|
| `metric[60s:5s]` (bare subquery, no `evalSubquery`) | 12 | 12 ✓ | 12 |
| `max_over_time(metric[60s:5s])` | 12 | **24** | 12 |
| `max_over_time(max_over_time(metric[60s:5s])[60s:5s])` | 12 | **58** | 12 |

This inverts the relationship the feature exists to express. `samplesRead` is documented as *"Total number of samples **read** (I/O)"* and `TotalSamples` as samples *loaded* — reads cannot exceed loads. Here `samplesRead` is 2× to ~5× `totalQueryableSamples`. The same inflation flows into `prometheus_engine_query_samples_read_total`, so any capacity model built on the new counter over-attributes I/O to subquery-heavy tenants.

The values are **already baked into the new test expectations**, e.g. `promql/engine_test.go:1176-1188`:

```go
Query:        "max_over_time(metricWith3SampleEvery10Seconds[60s:5s])",
TotalSamples: 36, // 3 sample per query * 12 queries (60/5)
SamplesRead:  72,
```

Contrast the bare-subquery row at `promql/engine_test.go:1150-1162` (`12` / `12`), which isolates the wrapper as the source of the doubling. Because the expectations encode the defect, the test suite will defend it rather than catch it.

**Fix:** Pick a single owner for subquery read attribution, as `TotalSamples` already does. Either (a) drop the `MergeSamplesReadFromSubquery` call in `evalSubquery` and let the outer `Call` loop be the sole counter, or (b) keep the merge and suppress the outer loop's read increment when the matrix argument came from a subquery (e.g. a flag on the synthesized selector set by `evalSubquery`). Then state the invariant `SamplesRead <= TotalSamples` in the `QuerySamples` doc comment and assert it in the stats tests so a future call site cannot silently break it.

### #3 🟠 High: `totalQueryableSamples` (pre-existing, user-visible) silently under-reports 4× for `@`-modified range-vector functions

| | |
|---|---|
| **File** | `promql/engine.go:2145` (declaration) and `:2183` (use) |
| **Category** | correctness / regression |
| **Confidence** | 100 — reproduced base vs. head |
| **Found by** | quick-reviewer (High), broad-reviewer (High), adversarial-reviewer (Medium), knowledge-reviewer (MUST) |

**Issue:** `fullWindowCount` is declared fresh (zero) inside the per-step loop and assigned **only** inside the recompute branch:

```go
var fullWindowCount, samplesReadCount int64
if ts == ev.startTimestamp || selVS.Timestamp == nil {
    ...
    floats, histograms = ev.matrixIterSlice(it, mint, maxt, floats, histograms)
    fullWindowCount = int64(len(floats) + totalHPointSize(histograms))
    ...
}
...
ev.samplesStats.IncrementSamplesAtStep(step, fullWindowCount)   // 0 on reuse steps
```

When the matrix selector carries an `@` modifier (`selVS.Timestamp != nil`) and `ts != ev.startTimestamp`, the branch is deliberately skipped — `floats`/`histograms` are *reused* from step 0. The pre-change code read `int64(len(floats)+totalHPointSize(histograms))` **unconditionally** after the `if`, so reused steps still counted the full window. Now they contribute `0`.

The comment immediately above asserts the opposite of what the code does:

```go
// Full window count for TotalSamples (unchanged semantics); delta for SamplesRead.
```

Reachable because `predict_linear` is in `AtModifierUnsafeFunctions`, so `preprocessExprHelper` never hoists it into a `StepInvariantExpr`, and a bare `MatrixSelector` argument is never wrapped either — the loop runs per outer step with `selVS.Timestamp != nil`.

Measured, range query 201s→231s at 10s (4 steps):

| | `TotalSamples` | `totalQueryableSamplesPerStep` |
|---|---|---|
| base `efbdc3f88` — `predict_linear(metric[60s] @ 200, 60)` | 24 | `{201000:6, 211000:6, 221000:6, 231000:6}` |
| head `ec7157593` — same query | **6** | `{201000:6, 211000:0, 221000:0, 231000:0}` |
| both — `predict_linear(metric[60s], 60)` (control, no `@`) | 24 | `{201000:6, 211000:6, 221000:6, 231000:6}` |

The control isolates the `@`-reuse branch as the cause. This is a silent 4× under-report of a long-standing API field and of `prometheus_engine_query_samples_total`, on which operators build query-cost dashboards and alerts. `-query.max-samples` is unaffected (it uses `ev.currentSamples`), so this is stats/metric fidelity only — but nothing in the new ~1140 lines of tests covers it.

**Fix:** Compute `fullWindowCount` from the current (possibly reused) `floats`/`histograms` unconditionally, exactly as the pre-change code did, while keeping `samplesReadCount` gated to the recompute branch:

```go
var samplesReadCount int64
if ts == ev.startTimestamp || selVS.Timestamp == nil {
    ...
    floats, histograms = ev.matrixIterSlice(it, mint, maxt, floats, histograms)
    if step == 0 {
        samplesReadCount = int64(len(floats) + totalHPointSize(histograms))
    } else {
        samplesReadCount = countSamplesAfter(floats, histograms, maxt-ev.interval)
    }
}
fullWindowCount := int64(len(floats) + totalHPointSize(histograms)) // reused or recomputed
```

Add a `TestQueryStatistics` case for `predict_linear(metric[60s] @ …, …)` over a multi-step range so the reuse path is guarded.

### #4 🟠 High: `countSamplesAfter` adds a full-window rescan per step, costing ~35% on long-window `rate()` range queries — paid even when the stats are disabled

| | |
|---|---|
| **File** | `promql/engine.go:2164`, helper at `promql/value.go:192-206` |
| **Category** | performance |
| **Confidence** | 100 — measured base vs. head, 4 runs each |
| **Found by** | performance-reviewer (High); adversarial-reviewer measured a different query shape and concluded "within noise" — resolved below |

**Issue:** `countSamplesAfter` linearly scans the **entire** window on every step > 0:

```go
samplesReadCount = countSamplesAfter(floats, histograms, maxt-ev.interval)
```

The points are timestamp-sorted ascending and the newly-added points are always at the tail, so only the tail is relevant — but the scan walks from the front over all `W` points, every step. It runs **unconditionally**, with no check on whether per-step stats or even `SamplesRead` collection is wanted, so the cost lands on every user of `rate`/`increase`/`*_over_time` in range queries.

Measured with the repository's own benchmark, `-benchtime=5x -count=4 -cpu=1`, on this machine:

| commit | `BenchmarkRangeQuery/expr=rate(a_hundred[1d]),steps=1000` | B/op | allocs/op |
|---|---|---|---|
| base `efbdc3f88` | 688.1 / 687.0 / 682.2 / 683.9 ms/op | 3 290 003 | 25 002 |
| head `ec7157593` | 932.3 / 929.8 / 928.5 / 927.4 ms/op | 3 290 035 | 25 001 |

**+35.6%**, with non-overlapping ranges across four runs each and *identical* allocation counts — so the regression is pure CPU in the new scan, not allocation. The engine used here has per-step stats **off** (benchmark default), confirming the cost is unconditional.

*Conflict resolution:* the adversarial reviewer measured `count_over_time(m[24h])` × 20 000 steps and saw ~5%, concluding the scan was lost in `matrixIterSlice`'s existing per-step `copy`. That is a different query shape with a different window-to-step-count ratio; on the repository's own `rate(a_hundred[1d]),steps=1000` case the effect is unambiguous. The orchestrator re-ran the benchmark on both commits to settle it.

**Fix:** Avoid the second full pass. Either scan backward from the tail and stop at the first point `<= cutoff` (O(new points) instead of O(W), valid because the slices are sorted ascending), or have `matrixIterSlice` return the count of newly-appended points from its own append loop — it already knows this and no extra pass is needed. Either fix also removes the duplicated `h.size()` computation that `countSamplesAfter` repeats for histograms.

### #5 🟡 Medium: The documented rule for `samplesRead` is false in at least three ways, in four synchronized copies

| | |
|---|---|
| **File** | `docs/querying/api.md:246`, `docs/feature_flags.md:48`, `util/stats/query_stats.go:280-283`, `web/api/v1/openapi_schemas.go:593-595` |
| **Category** | documentation / API contract |
| **Confidence** | 100 — verified against measured behavior |
| **Found by** | design-reviewer (High), knowledge-reviewer (MUST) |

**Issue:** All four locations state the same rule: *"For range-vector functions in range queries, only new points per step are counted; for other queries this equals `totalQueryableSamples`."* Measured counterexamples:

1. **Instant query with a subquery argument** — `max_over_time(metric[60s:5s])`: `totalQueryableSamples` 12, `samplesRead` **24** (finding #2). Not a range query; not equal.
2. **Step-invariant expressions** — `sum(metric @ 200)` as a range query over 4 steps: `totalQueryableSamples` 4 (replicated per step), `samplesRead` **1** (booked once at step 0, `promql/engine.go:2471`). No range-vector function involved; a 4:1 divergence.
3. **`@`-modified range-vector functions** — divergence there too, though currently for the wrong reason (finding #3).

Because the claim is stated as a rule rather than an approximation, consumers will treat a legitimate divergence as a bug, or build capacity models on an equality that does not hold. The real rule is closer to *"the two diverge wherever the engine evaluates a subexpression fewer times than there are steps"* — which is an engine-implementation detail being promoted to a stable public API field with no stability caveat.

**Fix:** Replace the equality claim in all four copies with the actual rule, and state explicitly what relation to `totalQueryableSamples` a consumer may rely on (after #2 is fixed, `samplesRead <= totalQueryableSamples`). Note whether the value is stable across engine versions.

### #6 🟡 Medium: `MergeSamplesReadFromSubquery` carries an unstated step-layout precondition and truncates silently; its constructor's doc contradicts one of its two call sites

| | |
|---|---|
| **File** | `util/stats/query_stats.go:406-433`; call sites `promql/engine.go:1869` and `promql/engine.go:2397` |
| **Category** | correctness-hazard / knowledge preservation |
| **Confidence** | 100 |
| **Found by** | knowledge-reviewer (MUST), design-reviewer (as boundary violation) |

**Issue:** `MergeSamplesReadFromSubquery` merges `child.SamplesReadPerStep[i]` into `qs.SamplesReadPerStep[i]` **index-wise**. That is only meaningful because `evalSubquery` happens to construct the child with the *parent's* `(start, end, interval)`. The doc comment never states this precondition, and the loop bound

```go
for i := 0; i < len(qs.SamplesReadPerStep) && i < len(child.SamplesReadPerStep); i++ {
```

silently truncates on mismatch — after `qs.SamplesRead` has already been incremented by the full child total, so `sum(SamplesReadPerStep) != SamplesRead` with no error.

Compounding this, `NewChildWithStepTracking`'s doc says it initializes *"with the given outer query step layout"*, but the other call site (`engine.go:2397`) passes the **subquery's** `subqStart/subqEnd/subqInterval` — the opposite layout. That is exactly why that site cannot use the index-wise merge and hand-rolls timestamp remapping inline instead. The result is three different merge behaviors for one concept: index-wise in the stats package, timestamp-remapped inline at `engine.go:2426`, and whole-total in the `else` fallback at `engine.go:2446`.

The inline remap at `engine.go:2426` also reaches directly into stats internals (`ev.samplesStats.SamplesRead +=`, hand-indexing `SamplesReadPerStep`, reading `ev.samplesStats.Interval`) while the change simultaneously adds helpers whose whole purpose is to encapsulate that. Any future change to the per-step representation would silently corrupt the engine's inline arithmetic instead of failing to compile.

**Fix:** Move the timestamp-remapping merge into `util/stats` as the single subquery-merge entry point (give it the child's start/interval so it can remap, falling back to whole-total attribution when per-step is off), and have the engine call one function at both sites. Replace the `&&`-truncating loop bound with a length check that returns early or panics rather than silently dropping the tail. Document the precondition on whichever API survives.

### #7 🟡 Medium: `StepInvariantExpr` still uses the old `NewChild()`, so nested subqueries under it lose per-step read attribution

| | |
|---|---|
| **File** | `promql/engine.go:2458` |
| **Category** | consistency / correctness |
| **Confidence** | 100 |
| **Found by** | consistency-reviewer (Medium) |

**Issue:** The change converts two of the three child-stats construction sites to `stats.NewChildWithStepTracking(...)` (`evalSubquery` at `:1869`, `SubqueryExpr` at `:2397`) but leaves the structurally parallel `StepInvariantExpr` case on `ev.samplesStats.NewChild()`, which hardcodes `EnablePerStepStats = false` regardless of the parent. A subquery evaluated under a step-invariant wrapper therefore produces a child with no `SamplesReadPerStep` at all, so its reads are attributed only in aggregate at step 0 while the two sibling paths give per-step detail.

Either behavior may be defensible; what is not defensible is that three parallel paths now disagree with nothing recording why.

**Fix:** Either use `NewChildWithStepTracking(ev.samplesStats.StepTrackingEnabled(), …)` here to match the sibling sites, or add a comment stating why step-invariant children are intentionally excluded from per-step read tracking.

## Specialist Notes

### Considered But Not Flagged (all agents)

**Traced and found safe (multiple independent agents concurred):**
- **`countSamplesAfter`'s `maxt - ev.interval` cutoff with strict `>`** — adversarial constructed range < step, range == step, range == 2×step, `offset`, `Anchored`, and `Smoothed` variants and measured each; `matrixIterSlice`'s left-open `(mint, maxt]` convention makes `maxt_s - interval == maxt_{s-1}` exactly the right boundary. No drop or double-count. Broad and go-reviewer reached the same conclusion statically.
- **Divide-by-zero via `Interval == 0`** in `IncrementSamplesReadAtTimestamp` / `InitStepTracking` / the inline merge — every caller traced by three agents. Instant queries pass `interval: 1` (`engine.go:815`); subquery intervals come from `durationMilliseconds(e.Step)` or `noStepSubqueryIntervalFn` and cannot be 0 (the PromQL duration lexer's smallest unit is whole milliseconds); the inline merge is gated on `SamplesReadPerStep != nil`, which implies `InitStepTracking` already set `Interval`. Unreachable.
- **`outerStep = numOuterSteps - 1` indexing `SamplesReadPerStep[-1]`** — would require a zero-length non-nil per-step array. All `InitStepTracking` callers yield `numSteps >= 1`; for the subquery child, `subqEnd - subqStart > -subqInterval` bounds it. Unreachable.
- **Negative `numSteps`** when a subquery's aligned start exceeds its end (`foo[1s:1h]`) — the gap is always `< interval`, so Go's truncating division yields 0, never negative.
- **Ceiling-division outer-step attribution** (`engine.go:2426`) — traced against aligned, unaligned, before-start, and after-end cases by three agents; computes the correct index in each. Its *rationale* being unrecorded is carried under Residual Risks.
- **Unpaired increment call sites** — consistency-reviewer enumerated all eight `IncrementSamplesAt*` calls in `engine.go` (`:1817`, `:1840`, `:2183`, `:2424`, `:2446`, `:2469`, `:2472`, `:2577`, `:2746`); every one has a matching `IncrementSamplesReadAt*`. `functions.go` and `quantile.go` contain no `samplesStats` references. No missed instrumentation.
- **Nil-receiver guards** on the new methods — consistent with the file's existing `if qs == nil { return }` idiom; defensive rather than load-bearing (`ev.samplesStats` is never nil in practice). The guard *added* to `InitStepTracking` moves toward the convention rather than away.
- **Metric registration / cardinality / error paths** — `querySamplesRead` is label-free, registered under the same `opts.Reg != nil` guard as its sibling, and incremented in the same `defer` on both success and error paths. No new hazard.
- **Concurrency** — `QuerySamples` remains per-query state owned by a single evaluator goroutine; the only cross-query surface is the atomic `Counter.Add` in the `exec` defer.
- **`samplesRead` lacking `omitempty` while `samplesReadPerStep` has it** — exactly mirrors the `totalQueryableSamples` / `totalQueryableSamplesPerStep` pair; the scalar is always meaningful, the array must vanish when tracking is off. Adding a member to an existing JSON object is backward compatible.
- **OpenAPI schema vs. Go struct** — field names, types, and `minItems`/`maxItems` match what `querySamples`/`stepStat` emit; both golden files were regenerated consistently.
