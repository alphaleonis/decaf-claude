### #1 🟠 High: `grafana-cli` path ignores the feature flag that gates the server path

| | |
|---|---|
| **File** | `pkg/cmd/grafana-cli/utils/command_line.go:111` |
| **Category** | correctness / behavior-mismatch |
| **Confidence** | 100 (anchor 75, promoted one step on 3-way independent agreement) |
| **Screen score** | 82 |
| **Found by** | quick-reviewer (High), broad-reviewer (High), adversarial-reviewer (High) |
| **Validation** | confirmed |

**Issue:** The change routes `grafana-cli plugins install` through a new `ContextCommandLine.GrafanaComProxyAPIToken()` that prefers `proxy_token` over `sso_api_token` **without ever consulting** the `grafana.dedicatedGrafanaComProxyAPIToken` feature flag. The server-side equivalent, `Cfg.ResolveGrafanaComProxyAPIToken()` (`pkg/setting/setting.go:762`), *does* gate on that flag.

Verified: the grafana-cli entry point never calls `featuremgmt.InitOpenFeatureWithCfg`, and `ContextCommandLine.Config()` never calls `ResolveGrafanaComProxyAPIToken`. The CLI has no access to flag state at all.

Concrete divergence — same host, same `grafana.ini`, flag at its default OFF, `proxy_token` set:

| surface | credential sent to grafana.com |
|---|---|
| server (`/api/gnet/*` proxy, plugin catalog) | `sso_api_token` — flag OFF, so `Resolve` overwrites the field |
| `grafana-cli plugins install` | `proxy_token` — no flag check |

The token does reach an `Authorization` header on both paths (`pkg/plugins/repo/client.go:240`), so the divergence is externally observable.

Two consequences:

1. **A staged rollout breaks the CLI first.** The natural rollout order is "deploy the config, flip the flag later". During that window CLI installs silently switch to a credential that is not yet authorized, while the catalog UI keeps working — which points diagnosis away from the token. This path includes container startup (`packaging/docker/run.sh`, the `custom/Dockerfile` plugin-install step).
2. **The flag is not a kill switch.** Turning the flag back OFF does not revert the CLI half.

The docs added by this same commit state the toggle is required for "plugin catalog browsing **and plugin installs via `grafana-cli`**" — so the CLI being ungated contradicts the change's own documentation.

**Fix:** Make both surfaces flip together. Either extract one shared resolver the CLI also uses (initializing OpenFeature in the plugin-command path), or — if the CLI intentionally cannot evaluate flags — drop the `proxy_token` preference there until the flag graduates:

```go
func (c *ContextCommandLine) GrafanaComProxyAPIToken() string {
	cfg, err := c.Config()
	if err != nil {
		logger.Debug("Could not parse config file", err)
		return ""
	}
	// Until grafana.dedicatedGrafanaComProxyAPIToken graduates, the CLI cannot
	// evaluate flags; keep it on the same credential the flag-gated server uses.
	return cfg.GrafanaComSSOAPIToken
}
```

If the asymmetry *is* deliberate, the docs line must say so explicitly rather than promising the toggle gates CLI installs.

### #2 🟡 Medium: Documented feature-toggle name omits the `grafana.` prefix — following the docs silently no-ops

| | |
|---|---|
| **File** | `docs/sources/setup-grafana/configure-grafana/_index.md:2325` |
| **Category** | correctness / doc-vs-code contradiction |
| **Confidence** | 100 (quotable fact — two strings in the same commit that must match) |
| **Screen score** | 80 |
| **Found by** | adversarial-reviewer (Medium) |
| **Validation** | confirmed |

**Issue:** The docs paragraph added by this commit says:

> Requires the `dedicatedGrafanaComProxyAPIToken` [feature toggle] to be enabled.

The flag registered by the same commit is `grafana.dedicatedGrafanaComProxyAPIToken` (`pkg/services/featuremgmt/registry.go:2253`), and `pkg/setting/setting.go:762` looks up that literal prefixed string. The commit message records the rename landing after the docs line was written: *"ref: rename feature flag to grafana.dedicatedGrafanaComProxyAPIToken"*.

Toggle names are matched **literally**. `ReadFeatureTogglesFromInitFile` (`pkg/setting/setting_feature_toggles.go:151-174`) keys the in-memory flag by whatever string the operator wrote, for both the `enable = a,b,c` list and the `key = value` form. Both the validator and I searched for any normalization that strips or adds a `grafana.` prefix — in the INI paths, `GF_FEATURE_TOGGLES_ENABLE`, the static provider, and the registry lookup. There is none.

So an operator who copies the documented name creates a flag nothing reads:

- a flag `dedicatedGrafanaComProxyAPIToken` is registered in the provider and is `true`
- the code asks for `grafana.dedicatedGrafanaComProxyAPIToken`, gets the registry default `false`
- `Resolve` overwrites `GrafanaComProxyAPIToken` with the SSO token
- the newly documented `proxy_token` appears inert

**No error or warning is emitted for the unknown toggle name** — this is the part that makes it more than a typo. The operator's only symptom is that a setting they configured does nothing.

**Fix:** Use the fully-qualified name in the docs line, matching the registry:

```markdown
Requires the `grafana.dedicatedGrafanaComProxyAPIToken` [feature toggle]({{< relref "#feature_toggles" >}}) to be enabled.
```

### Residual Risks

*Normally absent at `reach=narrow` — surveying for residual risk is a `wide` activity. This item is included because it was found in the changed lines themselves, not surveyed for.*

- `pkg/setting/setting.go:762` — **`ResolveGrafanaComProxyAPIToken` is a self-overwriting read-then-write with no observability.** Three linked weaknesses: (a) `Client.Boolean(...)` returns the `false` default on *evaluation error*, indistinguishable from "flag is off", so a degraded flag service at boot silently downgrades that process to the SSO token for its lifetime — though the screener established this only bites on non-default remote-provider (OFREP) deployments, not the default static provider; (b) the function is not idempotent across an off→on transition, since once it writes the SSO token the field is non-empty and a second call would "keep" it — currently theoretical, as both call sites run exactly once per process before any consumer reads the field; (c) nothing logs which credential source ended up active, so the two states are operationally indistinguishable. Storing the configured value in a separate field and deriving the effective one would make the operation idempotent and reversible. (adversarial-reviewer — screen 55, single finder; tiered down by the `evidence=strong` bar)
