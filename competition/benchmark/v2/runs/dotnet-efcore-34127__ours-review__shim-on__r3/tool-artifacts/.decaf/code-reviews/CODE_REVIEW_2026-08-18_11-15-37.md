## Findings

### #1 🔴 Critical: `NullPropagatedOperands` treats `AndAlso`/`OrElse` as null-propagating, producing silently wrong query results

| | |
|---|---|
| **File** | `src/EFCore.Relational/Query/SqlNullabilityProcessor.cs:626` |
| **Category** | correctness / null-safety |
| **Confidence** | 100 |
| **Verified** | **Yes — reproduced by execution, plus a control run.** See "Probe results" below |
| **Found by** | quick-reviewer (Critical), broad-reviewer (Critical), adversarial-reviewer (Critical), knowledge-reviewer (MUST), dotnet-reviewer (High) |

**Issue:**

The new optimization at `SqlNullabilityProcessor.cs:576-591` drops an `X IS NOT NULL` conjunct from a
single-WHEN `CASE ... ELSE NULL` test whenever `X` appears in the set collected by
`NullPropagatedOperands`. That set is only sound if it satisfies the invariant *"`X` IS NULL implies
the whole result IS NULL"*.

Three of the four recursion arms are deliberately selective — the unary arm (line 622) admits only
`Not`/`Negate`/`Convert`, and the function arm (line 631) is gated on `IsNullable` plus the explicit
`InstancePropagatesNullability`/`ArgumentsPropagateNullability` flags. The binary arm is not:

```csharp
else if (expression is SqlBinaryExpression binary)   // line 626 — no operator filter
{
    NullPropagatedOperands(binary.Left, operands);
    NullPropagatedOperands(binary.Right, operands);
}
```

`SqlBinaryExpression.IsValidOperator` (`src/EFCore.Relational/Query/SqlExpressions/SqlBinaryExpression.cs:82`)
permits `AndAlso` and `OrElse`, through which SQL NULL provably does **not** propagate:
`NULL OR TRUE = TRUE` and `NULL AND FALSE = FALSE`. The optimization therefore deletes a load-bearing
guard and the CASE collapses to a bare boolean expression that returns `TRUE`/`FALSE` where it must
return `NULL`.

**This exact exception is already documented in the same file**, ~1700 lines away in
`ProcessNullNotNull` (`SqlNullabilityProcessor.cs:2314-2321`):

```csharp
case SqlBinaryExpression sqlBinaryOperand
    when sqlBinaryOperand.OperatorType != ExpressionType.AndAlso
    && sqlBinaryOperand.OperatorType != ExpressionType.OrElse:
{
    // in general:
    // binaryOp(a, b) == null -> a == null || b == null
    // binaryOp(a, b) != null -> a != null && b != null
    // for AndAlso, OrElse we can't do this optimization
```

The new code carries no equivalent guard and no comment recording the invariant.

**Probe results (SQLite, EF Core built from this changeset):**

Query: `x => x.NullableBoolA != null ? (bool?)(x.NullableBoolA.Value || x.BoolA) : null`

Generated SQL — the guard is gone:
```sql
SELECT "e"."Id", "e"."NullableBoolA", "e"."BoolA", "e"."NullableBoolA" OR "e"."BoolA" AS "V"
FROM "Entities1" AS "e"
```

| row | `NullableBoolA` | `BoolA` | database | correct (LINQ-to-Objects) | |
|---|---|---|---|---|---|
| 3 | NULL | true | **True** | NULL | ❌ **MISMATCH** |

The `&&` mirror (`x.NullableBoolA.Value && x.BoolA`) diverges symmetrically:

| row | `NullableBoolA` | `BoolA` | database | correct | |
|---|---|---|---|---|---|
| 4 | NULL | false | **False** | NULL | ❌ **MISMATCH** |

**Control run** — with the operator guard added at line 626 and nothing else changed, the SQL reverts
to the `CASE ... IS NOT NULL ... ELSE NULL END` form, both mismatches disappear, and the intended
optimization for `Add` (`NullableIntA + NullableIntB`) still collapses correctly. The working tree was
restored byte-identical afterwards (verified by checksum and `git status`).

**Blast radius.** The optimized CASE is not confined to projections — the regenerated baselines
`Null_propagation_optimization5/6` (`GearsOfWarQuerySqlServerTest.cs:1020`,
`GearsOfWarQuerySqliteTest.cs:7538`) show it landing in `WHERE`. A predicate that flips from `NULL` to
`TRUE` changes which rows match, which reaches `ExecuteDelete`/`ExecuteUpdate` — wrong rows deleted or
updated, silently, with no error.

**Fix:**

Restrict the binary arm to operators that provably propagate NULL, mirroring the selective style
already used in the unary arm:

```csharp
else if (expression is SqlBinaryExpression binary
    && binary.OperatorType is not (ExpressionType.AndAlso
        or ExpressionType.OrElse
        or ExpressionType.Coalesce))
{
    NullPropagatedOperands(binary.Left, operands);
    NullPropagatedOperands(binary.Right, operands);
}
```

Prefer an explicit **allow-list** (`Add`, `Subtract`, `Multiply`, `Divide`, `Modulo`, `And`, `Or`,
`ExclusiveOr`, `Equal`, `NotEqual`, `LessThan`, `LessThanOrEqual`, `GreaterThan`,
`GreaterThanOrEqual`) over a deny-list, so a future operator added to
`SqlBinaryExpression.IsValidOperator` fails closed rather than open.

On `Coalesce`: I probed `x.NullableIntA != null ? (x.NullableIntA ?? x.NullableIntB) : null` and the
guard was **correctly preserved** — `SqlExpressionFactory.Coalesce` emits a COALESCE
`SqlFunctionExpression` with `argumentsPropagateNullability: [false, false]`, which the function arm
declines to recurse into. `ExpressionType.Coalesce` on a `SqlBinaryExpression` is nonetheless
permitted by `IsValidOperator` and constructible via `SqlExpressionFactory.MakeBinary`, so excluding it
costs nothing and closes a latent provider/plugin path. (quick-reviewer's Coalesce counterexample as
stated is refuted; its `AndAlso`/`OrElse` reasoning stands.)

Add a comment above `NullPropagatedOperands` (line 617) stating the invariant verbatim, and a
regression test whose WHEN result contains a logical operator over the null-checked column.

### #3 🟡 Medium: `NullPropagatedOperands` encodes an unstated soundness invariant with no comment

| | |
|---|---|
| **File** | `src/EFCore.Relational/Query/SqlNullabilityProcessor.cs:617` |
| **Category** | knowledge-preservation |
| **Confidence** | 100 |
| **Found by** | knowledge-reviewer (MUST), broad-reviewer (High) |

**Issue:** The function's contract — *"collects sub-expressions `E` of `expression` for which `E IS
NULL` implies `expression IS NULL` under SQL three-valued logic"* — is written down nowhere. There is
no summary comment, no reference to 3VL, no explanation of why the unary arm admits exactly
`Not`/`Negate`/`Convert`, and no signal that adding an operator to
`SqlBinaryExpression.IsValidOperator` obliges a maintainer to revisit this function. `VisitCase` is
`protected virtual` provider-extensibility surface, so a provider overriding `VisitSqlBinary` can
invalidate the assumption from outside this assembly with no warning.

This is the root cause of #1 rather than a separate defect in effect, but it remains actionable after
#1 is fixed: without the stated invariant, the next operator addition reintroduces the same class of
bug.

**Fix:** Add above line 617:

```csharp
// Collects sub-expressions E of `expression` for which `E IS NULL` implies `expression IS NULL`
// under SQL three-valued logic. Operators added to SqlBinaryExpression.IsValidOperator must be
// checked against this invariant before being admitted here — see ProcessNullNotNull for the
// AndAlso/OrElse exception.
```

### #4 🟢 Low: `null` return of `DropNotNullChecks` overloads "absent" with "vacuously TRUE"

| | |
|---|---|
| **File** | `src/EFCore.Relational/Query/SqlNullabilityProcessor.cs:595` |
| **Category** | maintainability |
| **Confidence** | 75 |
| **Found by** | knowledge-reviewer (SHOULD) |

**Issue:** `DropNotNullChecks` returns `SqlExpression?` where `null` means "the remaining test is the
constant TRUE", carried solely by a trailing `// true` at line 600. The recursive merge at lines
604-609 reads as ordinary null-coalescing rather than as identity-element absorption for boolean AND,
and the call site at line 587 has no comment. Thirty lines earlier in the same method (lines 565-572)
`null` carries the *opposite* meaning — a `null` `elseResult` means "no ELSE, therefore possibly NULL".

A maintainer extending `DropNotNullChecks` to handle `OrElse` tests — the natural next step — will
reach for `null` as the "nothing left" value and silently invert the predicate, because under OR the
identity element is FALSE, not TRUE.

**Fix:** Add one line above line 595: `// Returns null when the test reduces to the constant TRUE (the
identity element of AND) — i.e. every conjunct was a redundant IS NOT NULL check.` and a matching
comment at the call site (line 587).

### Considered But Not Flagged

**Refuted by probe:**
- *`Coalesce` reachable as a `SqlBinaryExpression` from `??` (quick-reviewer, Critical).* Probed
  directly: `x.NullableIntA != null ? (x.NullableIntA ?? x.NullableIntB) : null` emits
  `CASE WHEN "NullableIntA" IS NOT NULL THEN COALESCE(...) ELSE NULL END` — the guard is preserved,
  because `??` becomes a COALESCE `SqlFunctionExpression` with `argumentsPropagateNullability:
  [false, false]`. Folded into #1's fix as a fail-closed recommendation rather than reported.

**Examined and found sound (multiple reviewers, concurring):**
- Unary arm `Not`/`Negate`/`Convert` (line 622) — all three propagate NULL in SQL; no
  provider/type-mapping combination found where `CAST(NULL AS T)`, `-NULL`, or `~NULL` is non-NULL.
- `SqlFunctionExpression` arm (line 631) — correctly reuses the already-vetted
  `IsNullable`/`InstancePropagatesNullability`/`ArgumentsPropagateNullability` metadata, whose
  documented implication direction is exactly what the optimization needs. `IsNiladic` guard is
  necessary (`Arguments`/`ArgumentsPropagateNullability` are `[MemberNotNullWhen(false, ...)]` and
  genuinely null when niladic); the `Count` invariant is enforced in the constructor
  (`SqlFunctionExpression.cs:217-225`), so the indexed loop is safe.
- `DropNotNullChecks` descending only `AndAlso` — conservative, therefore safe. Matching only
  `SqlUnaryExpression { NotEqual }` correctly mirrors EF's `IS NOT NULL` representation.
- `nullable` out-parameter after `return clause.Result` — already forced `true` by
  `nullable |= elseResultNullable`; a safe over-approximation. `CaseExpression` takes its CLR `Type`
  and `TypeMapping` from `whenClauses[0].Result`, so returning the result preserves both — no shaper
  mismatch.
- `_nonNullableColumns` / `_nullValueColumns` restore calls execute unconditionally before the new
  block; no scope leak introduced.
- Query-plan caching — `IsNull(elseResult)` may be true because a `SqlParameterExpression`'s current
  value is null, but plans are already keyed by parameter nullability, and `DoNotCache()` is reserved
  for value-content dependence. Consistent with 17 existing uses in this file.
- `allowOptimizedExpansion` interaction — the rows newly admitted by a dropped `X IS NOT NULL` are
  exactly `X IS NULL ∧ rest`; NULL-as-FALSE rewriting of `rest` cannot change that set membership.
  Collapses into #1 rather than being an independent hole (adversarial-reviewer, traced both
  directions).

**Noted, not reported:**
- *`IsNull(elseResult)` is false for an absent ELSE* (line 578). `CASE WHEN t THEN r END` is
  semantically `CASE WHEN t THEN r ELSE NULL END`, so the optimization silently does not fire for
  ELSE-less CASEs. A missed optimization, not a soundness defect. `[minor]`
- *Compile-time cost.* `NullPropagatedOperands` eagerly builds a `HashSet` of every sub-expression of
  the result before checking whether the test contains any droppable `IS NOT NULL`, and
  `SqlExpression.GetHashCode` is recursive and uncached — O(m·depth) per single-WHEN CASE. A cheap
  early-out (bail unless `clause.Test` is an `IS NOT NULL` or an `AndAlso` chain) would remove it. No
  failure chain; `performance-reviewer` was not on the roster. `[minor]`
- *Unbounded recursion* in both local functions — every visitor in this 2000-line file recurses the
  same way; no new risk introduced. `[pre-existing]`
- *Bare `// TODO:` at line 577 without an issue link* — checked empirically: bare TODOs are the
  dominant convention in `src/EFCore.Relational/Query/` (roughly 20 of 24 sampled, including four
  pre-existing ones in this same file). Not a convention violation. `[false]`
- *`func.Instance!` null-forgiving operator* (line 635) — only reachable via the
  `[EntityFrameworkInternal]` constructor, not any standard public API path. `[unverified]`
- *`else if` chain style vs. pattern matching elsewhere in the file* — idiom preference with no
  nameable consequence. `[minor]`
