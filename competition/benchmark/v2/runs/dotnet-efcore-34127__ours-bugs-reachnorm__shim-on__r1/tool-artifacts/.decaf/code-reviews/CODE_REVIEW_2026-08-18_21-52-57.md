## Findings

### #1 🔴 Critical: `NullPropagatedOperands` treats `AndAlso`/`OrElse` operands as null-propagating, so a load-bearing `IS NOT NULL` guard is deleted and queries silently return wrong values and wrong rows

| | |
|---|---|
| **File** | `src/EFCore.Relational/Query/SqlNullabilityProcessor.cs:626` |
| **Category** | correctness |
| **Confidence** | 100 |
| **Verified** | executed |
| **Pre-existing** | no |
| **Found by** | solo-reviewer (Critical) |

**Issue:** The soundness condition for the rewrite is: the guard `expr IS NOT NULL` may be dropped
from the test only if `expr IS NULL` implies `result IS NULL`. `NullPropagatedOperands` recurses into
`binary.Left` and `binary.Right` for **every** `SqlBinaryExpression` operator type:

```csharp
else if (expression is SqlBinaryExpression binary)
{
    NullPropagatedOperands(binary.Left, operands);
    NullPropagatedOperands(binary.Right, operands);
}
```

`IsValidOperator` (`src/EFCore.Relational/Query/SqlExpressions/SqlBinaryExpression.cs:87-103`) admits
`AndAlso`, `OrElse` and `Coalesce`, none of which propagate NULL: `NULL OR TRUE = TRUE`,
`NULL AND FALSE = FALSE`. Any operand reached through such a node is added to the set and its guard
is then deleted by `DropNotNullChecks`. When every conjunct is deleted, `VisitCase` returns
`clause.Result` (line 587) and the `CASE` disappears entirely.

This is not an exotic shape. It is hit by any ternary whose result is a boolean expression, and —
worse — by EF Core's **own** null-semantics expansion, which rewrites `a == b` into
`a = b AND b IS NOT NULL` and `a != b` into `a <> b OR b IS NULL` when the left operand is known
non-null. Those rewrites are themselves only valid under the assumption the dropped guard
establishes.

**Failure scenario:** `ss.Set<NullSemanticsEntity1>().Select(x => x.NullableBoolA != null ? (bool?)(x.NullableBoolA.Value || x.BoolB) : null)`
generates `SELECT "NullableBoolA" OR "BoolB"` after the change. For a row with `NullableBoolA = NULL`
and `BoolB = true`, the database returns `True` where the LINQ semantics require `null`.

**Evidence (executed):** Both `051c33a79` (base, in a temporary `git worktree`) and `afcfba2e9`
(this change) were built, and identical queries were run through a SQLite `DbContext`, comparing
database results to LINQ-to-Objects over the same seeded rows (the same contract `AssertQuery`
enforces). Base matched on every probe; the change did not.

| LINQ | SQL after the change | Result |
|---|---|---|
| `x.NullableBoolA != null ? (bool?)(x.NullableBoolA.Value \|\| x.BoolB) : null` | `SELECT "NullableBoolA" OR "BoolB"` | MISMATCH 6 of 36 rows (db `True`, expected `null`) |
| `x.NullableBoolA != null ? (bool?)(x.NullableBoolA.Value && x.BoolB) : null` | `SELECT "NullableBoolA" AND "BoolB"` | MISMATCH 6 of 36 (db `False`, expected `null`) |
| `x.NullableIntA != null ? (bool?)(x.NullableIntA == x.NullableIntB) : null` | `SELECT "NullableIntA" = "NullableIntB" AND "NullableIntB" IS NOT NULL` | MISMATCH 6 of 36 (db `False`, expected `null`) |
| `x.NullableIntA != null ? (bool?)(x.NullableIntA != x.NullableIntB) : null` | `SELECT "NullableIntA" <> "NullableIntB" OR "NullableIntB" IS NULL` | MISMATCH 1 of 9 |
| `A != null && B != null ? (bool?)(A > 0 \|\| B > 0) : null` | `SELECT "NullableIntA" > 0 OR "NullableIntB" > 0` | MISMATCH 2 of 9 |
| `Where((x.NullableBoolA != null ? (bool?)(x.NullableBoolA.Value \|\| x.BoolB) : null) == true)` | `WHERE "NullableBoolA" OR "BoolB"` | **row count 24, expected 18** |

The last row is the most damaging: the guard removal changes the returned row set of a `WHERE`, not
just a projected value. On the base build every one of these reported `MATCH`, and each generated the
guarded `CASE WHEN ... IS NOT NULL THEN ... ELSE NULL END`.

`Coalesce` as a `SqlBinaryExpression` is a latent instance of the same hole. No reachable case could
be constructed (the factory emits a `SqlFunctionExpression` instead), but the operator is legal per
`IsValidOperator:102`, so a provider or future rewrite that constructs one inherits the same silent
corruption.

**Fix:** Invert the binary arm from default-include to an explicit allowlist of null-propagating
operators, so a newly added operator fails closed rather than open:

```csharp
else if (expression is SqlBinaryExpression binary
    && binary.OperatorType is ExpressionType.Add or ExpressionType.Subtract
        or ExpressionType.Multiply or ExpressionType.Divide or ExpressionType.Modulo
        or ExpressionType.And or ExpressionType.Or or ExpressionType.ExclusiveOr
        or ExpressionType.Equal or ExpressionType.NotEqual
        or ExpressionType.LessThan or ExpressionType.LessThanOrEqual
        or ExpressionType.GreaterThan or ExpressionType.GreaterThanOrEqual)
```

This excludes `AndAlso`, `OrElse` and `Coalesce`. It costs the `binary_op` shapes nothing (arithmetic
and string `+` remain covered) and fixes all six probes above. The invariant the helper maintains
should also be stated in a comment — see Minor Findings.

Separately, consider whether the rewrite is safe at all for a result subtree that `VisitCase`
produced *under* the guard: the result is visited with `preserveColumnNullabilityInformation: true`
(line 514), which seeds `_nonNullableColumns` from the test's own `IS NOT NULL` checks. The equality
and inequality rows above are exactly that — the result was simplified assuming the operand is
non-null, and dropping the guard exposes it to rows where it is not. The allowlist fix closes every
instance constructed here, but the dependency is worth an explicit note so a future change does not
reopen it.

### #2 🟡 Medium: none of the five new tests exercises a boolean-valued `THEN` result, so the failing shape class is entirely uncovered

| | |
|---|---|
| **File** | `test/EFCore.Relational.Specification.Tests/Query/NullSemanticsQueryTestBase.cs:2250-2295` |
| **Category** | tests |
| **Confidence** | 100 |
| **Verified** | executed |
| **Pre-existing** | no |
| **Found by** | solo-reviewer (Medium) |

**Issue:** The five added tests cover `~int?` (unary `Not`), `int? + int?`, and three
string-concatenation variants. Every one has a *value*-typed result, so `NullPropagatedOperands` only
ever walks `Add`/`Not` nodes. No test has a boolean result, which is the only way to reach the
`AndAlso`/`OrElse` arms — the arms that are wrong. The suite therefore passes with finding #1 fully
present.

**Failure scenario:** A reviewer or CI run sees five green null-propagation tests and concludes the
rewrite is validated. `Is_not_null_optimizes_binary_op` and friends would still pass byte-for-byte
after the fix in #1, because none of them touches the changed code path.

**Evidence:** The SQLite functional suite could not be run — `test/EFCore.Specification.Tests` fails
to compile under the installed SDK 10.0.400 (nine pre-existing `CS0023`/`CS8604` errors in
`CustomConvertersTestBase.cs` and `InjectWhereExpressionMutator.cs`, unrelated to this diff). The
coverage claim was verified instead by reading each of the five LINQ expressions and by driving the
same shapes through a standalone `DbContext` built against the changed assemblies. The SQL baselines
in the diff corroborate it: all five expected strings are arithmetic or concatenation, none contains
`AND`/`OR` inside a `THEN`.

**Fix:** Add tests over `NullSemanticsEntity1` for at least: a boolean `THEN`
(`x.NullableBoolA != null ? (bool?)(x.NullableBoolA.Value || x.BoolB) : null`), an
equality/inequality `THEN` that triggers null-semantics expansion
(`x.NullableIntA != null ? (bool?)(x.NullableIntA == x.NullableIntB) : null`), and one in `Where`
position so a wrong row count is caught, not just a wrong projected value. Each must fail before the
#1 fix and pass after.

## Minor Findings

### Consistency

- `src/EFCore.Relational/Query/SqlNullabilityProcessor.cs:578` — `IsNull(elseResult)` is `false` when `elseResult` is a C# `null` reference, that is, when the `CaseExpression` has no `ELSE` clause at all. Since SQL treats a missing `ELSE` as `ELSE NULL`, `CASE WHEN x IS NOT NULL THEN x END` is semantically identical to the optimized shape but is skipped. The optimization applies inconsistently depending on how the tree was built. Consider `(elseResult is null || IsNull(elseResult))`. (solo-reviewer)
- `src/EFCore.Relational/Query/SqlNullabilityProcessor.cs:587` — when the whole test is dropped and `clause.Result` is returned, the `nullable` out-parameter still carries `true` from the null `ELSE` constant, even if `clause.Result` is itself non-nullable. Conservative and therefore safe, but it can cost a downstream null-compensation that is no longer needed. (solo-reviewer)
- `src/EFCore.Relational/Query/SqlNullabilityProcessor.cs:617` — `NullPropagatedOperands` has no comment stating the invariant it maintains ("`e` is in the set only if `e IS NULL` implies the root expression `IS NULL`"). That invariant is the entire correctness argument for the feature and is not written down anywhere, which is a direct contributor to finding #1. The name reads as "operands that participate in the expression", not "operands whose nullness forces the result null". (solo-reviewer)

### Testing Gaps

- `test/EFCore.SqlServer.FunctionalTests/Query/NullSemanticsQuerySqlServerTest.cs:4504-4560` — the new baselines assert SQL text only for SQL Server. Since the rewrite lives in the shared relational processor and changes result semantics rather than just formatting, at least one of the new cases would be worth a SQLite baseline too, where `||` concatenation and `AND`/`OR` render differently. (solo-reviewer)
