## Findings

### #1 🟠 High: Parse-time rejection turns previously-successful command executions into hard failures for existing integrations

| | |
|---|---|
| **File** | `server/public/model/command_response.go:72-74` |
| **Category** | error-handling / backward-compatibility |
| **Confidence** | 75 |
| **Screen score** | 68 |
| **Validation** | confirmed |
| **Found by** | adversarial-reviewer (High) |

**Issue:** `CommandResponseFromJSON` now returns an error for any response the new `IsValid()` rejects, and both production callers translate that into a failure of the whole command. Two concrete instances of the same root cause, both verified against the code:

**(a) Unknown `response_type`.** Before this change, a response carrying an unrecognized `response_type` parsed successfully and reached `CreateCommandPost` (`server/channels/app/command.go:73-84`), where neither the `in_channel` branch nor the `"" || ephemeral` branch matched — the function fell through and returned `(post, nil)`. The command reported success and simply created no post. After this change, `doCommandRequest` (`server/channels/app/command.go:595-597`) wraps the parse error into `api.command.execute_command.failed.app_error` and returns HTTP 500 — *after* the third-party integration has already performed its side effect.

**(b) Over-length ephemeral text.** `SendEphemeralPost` (`server/channels/app/post.go:692`) never calls `post.IsValid()` and applies no length gate anywhere on its path; ephemeral posts are never persisted. An integration returning e.g. 80 KB of ephemeral text worked before, bounded only by `MaxIntegrationResponseSize` = 1 MB (`server/channels/app/webhook.go:31`). The same response is now rejected at parse time and the command 500s. The 65535-byte cap mirrors `PostMessageMaxBytesV2`, a **persisted-post DB-size** constant that has no prior basis on the ephemeral path at all.

The validator also checked whether this is defensible as deliberate hardening and found against it: there is no linked issue or design doc, and the project's own analogous parser for outgoing-webhook message responses (`doOutgoingWebhookRequest` / `OutgoingWebhookResponse`, `server/channels/app/webhook.go:202-208`) still decodes leniently with no `IsValid` gate — so this is not a precedented pattern in this codebase.

**Note on one sub-claim:** the reviewer's retry-amplification argument (user sees the failure, retries, the integration's side effect repeats) is real but rests on a *human* clicking again, not an automatic client retry. It should not carry the severity on its own; instances (a) and (b) do.

**Fix:** Decide what the failure mode should be and make it explicit rather than incidental. Options, in decreasing order of compatibility:
- Coerce rather than reject — unknown `response_type` → treat as ephemeral, over-length `Text` → truncate at the real downstream limit — and log a warning. This keeps working integrations working while eliminating the silent no-post bug in (a).
- Keep `IsValid()` out of `CommandResponseFromJSON` and let each caller decide, so the client-decode path (finding #2) is unaffected.
- If rejection is genuinely wanted, return an error that `doCommandRequest` surfaces as "the integration returned an invalid response" rather than a generic 500, and drop the ephemeral length rule (b), which protects nothing.

### #2 🟠 High: Strict validation is applied to the client-side decode of the server's own unvalidated response

| | |
|---|---|
| **File** | `server/public/model/command_response.go:72-74` (affects `server/public/model/client4.go:5961`, `:5982`) |
| **Category** | api-design / error-handling |
| **Confidence** | 75 |
| **Screen score** | 62 |
| **Validation** | confirmed (validator advises Medium — see dissent below) |
| **Found by** | broad-reviewer (High), adversarial-reviewer (Medium) |

**Issue:** `CommandResponseFromJSON` serves two very different roles, and the new validation does not distinguish them. Besides parsing untrusted third-party payloads, `Client4.ExecuteCommand` / `ExecuteCommandWithTeam` use it to decode the Mattermost **server's own** response body to `POST /commands/execute`.

The producer side of that response is entirely unvalidated. Verified chain: `server/channels/app/plugin_commands.go:163` returns a `*model.CommandResponse` straight from a plugin's `ExecuteCommand` RPC hook with no normalization of `ResponseType` or `Text` (`server/public/plugin/hooks.go:129` imposes no constraint); it flows through `HandleCommandResponse` / `HandleCommandResponsePost`, **which already creates the post**; and `server/channels/api4/command.go:428` then writes it out with `json.NewEncoder(w).Encode(response)` — `IsValid()` is never called on the way out.

So a plugin that sets a non-canonical `ResponseType` (or >65535-byte `Text`) now makes `ExecuteCommand` return `nil, err` to every Go consumer of the published `server/public` module — mmctl, e2e tests, third-party Go integrations — for a command that already succeeded and whose post already exists. Validation is enforced on the reader while the writer stays unconstrained.

**Scope narrowing the validator established:** webhook-backed custom commands are *not* affected — their responses already pass through this same `IsValid()` server-side at `server/channels/app/command.go:595`, so they cannot reach Client4 in a non-canonical state. The reachable risk is the **plugin `ExecuteCommand` hook** path specifically. No in-repo built-in command or test emits a non-canonical `ResponseType`, so nothing in this repository breaks today; the exposure is to out-of-tree plugins.

**Severity dissent:** broad-reviewer rated High, adversarial-reviewer Medium, and the validator argued for Medium on the grounds that the consequence is a wrong/incomplete API response to a Go caller rather than data loss or a security issue, and requires an out-of-tree plugin to emit a non-canonical field. Recorded as High per the highest-severity rule; treat Medium as a defensible reading.

**Fix:** Make producer and consumer agree. Either validate on the way out (`app.ExecuteCommand`, or before `api4/command.go` encodes), so a plugin's non-canonical response is caught where it originates and can be reported meaningfully — or have `Client4` decode without the strict validation, since a client should not reject a payload its own server chose to emit. Splitting the strict path from the lenient one (e.g. an unexported `commandResponseFromJSON(strict bool)`) is the smallest change that does this.

### #3 🟠 High: New AppError translation ids are not registered in `server/i18n/en.json`

| | |
|---|---|
| **File** | `server/public/model/command_response.go:82`, `:87` |
| **Category** | convention-violation / knowledge-loss |
| **Confidence** | 100 |
| **Screen score** | 55 |
| **Validation** | confirmed |
| **Found by** | quick-reviewer (Medium), broad-reviewer (High) |

**Issue:** `IsValid()` raises `model.command_response.is_valid.response_type.app_error` and `model.command_response.is_valid.text.app_error`. Neither exists in `server/i18n/en.json` — verified, grep count is 0 for `model.command_response` — whereas the sibling `Command.IsValid` (`server/public/model/command.go`) registers all 14 of its `model.command.is_valid.*` ids. `NewAppError` translates immediately via `AppError.Translate` (`server/public/model/utils.go:281-296`), and go-i18n's fallback returns the raw translation id when the key is missing, so the `AppError.Message` becomes the literal id string.

**Where it actually surfaces** (the screen initially scored this lower on the belief the leak was log-only; the validator corrected that):

- `server/channels/web/webhook.go:114` and `server/channels/app/command.go:595` both wrap the inner error under a separately-registered outer id, so there the raw id reaches server logs always, and the client's `DetailedError` JSON field only when `ServiceSettings.EnableDeveloper` is true (`handlers.go:424-427` calls `WipeDetailed` otherwise).
- **`Client4.ExecuteCommand` / `ExecuteCommandWithTeam` (`server/public/model/client4.go:5950-5987`) do not.** They call `CommandResponseFromJSON` directly and propagate the `*AppError` unwrapped via `fmt.Errorf`, with no outer translation wrapper and no `EnableDeveloper` gate. Any Go SDK consumer hitting this validation sees the literal untranslated id in its returned error.

That third path is a genuine caller-visible leak, not just a log entry — which is why High stands over the Medium the screen's partial trace suggested.

No CI gate in this repo appears to catch the omission: the i18n workflows (`.github/workflows/i18n-ci-pr.yml`, `i18n-ci-template.yml`) only block non-Weblate edits to non-English translation files, and the `server/Makefile` `i18n-check` / `i18n-extract` targets are not wired into a visible PR workflow. So this will not be caught for you.

**Fix:** Add both ids to `server/i18n/en.json`, following the existing `model.command.is_valid.*` entries' format:

```json
{
  "id": "model.command_response.is_valid.response_type.app_error",
  "translation": "Invalid response type."
},
{
  "id": "model.command_response.is_valid.text.app_error",
  "translation": "Text exceeds the maximum allowed length."
}
```

### #4 🟡 Medium: The 65535-byte text limit is the wrong value in the wrong unit and duplicates an existing constant

| | |
|---|---|
| **File** | `server/public/model/command_response.go:85-88` |
| **Category** | correctness / duplication |
| **Confidence** | 75 |
| **Screen score** | 82 |
| **Validation** | confirmed (all three sub-claims) |
| **Found by** | quick-reviewer (Low), broad-reviewer (Medium), adversarial-reviewer (Medium) |

**Issue:** Three defects in the same three lines, all independently re-derived by the validator:

**(a) Unexplained duplicate constant.** `maxLength := 65535` is a bare local literal that silently re-derives `PostMessageMaxBytesV2 = 65535` (`server/public/model/post.go:72`) — same package, same value, no reference. A future change to the post limit will not propagate here, and a maintainer has no way to know the number is not arbitrary.

**(b) Bytes where the codebase counts runes.** `len(o.Text)` counts bytes. Every sibling *message-body* field in this package — `Post.Message`, `Draft.Message`, `ScheduledPost` via `BaseIsValid`, `TermsOfService.Text` — validates with `utf8.RuneCountInString` against a runes-based constant. `len()` is used in this package only for short, DB-column-bound fields (`DisplayName`, `Description`, `Username`), not message bodies. The consequence is a locale-dependent limit: CJK or emoji text is cut off at roughly 16,383 characters while identical ASCII text gets 65,535.

**(c) The limit does not match the boundary it appears to protect.** For `in_channel` responses the real gate is downstream: `CreateCommandPost` → `CreatePostMissingChannel` → `post.IsValid(maxPostSize)` in `server/channels/store/sqlstore/post_store.go:174/405/463`, where `determineMaxPostSize()` (`post_store.go:2640-2662`) floors at `model.PostMessageMaxRunesV2` = **16383 runes** by default. A 40,000-character ASCII response passes the new check (40,000 bytes ≤ 65535) and is still rejected at post creation. On the ephemeral path `SendEphemeralPost` never calls `Post.IsValid` at all, so the new byte-based check is the *only* length gate there and nothing downstream catches its unit mismatch.

So the check neither prevents the downstream failure it looks like it is preventing, nor applies a limit that is meaningful on the path where it is the only limit.

**Severity dissent:** quick-reviewer rated Low; broad- and adversarial-reviewer rated Medium. Recorded as Medium.

**Fix:** Decide which boundary this is protecting and derive the limit from it rather than restating a number:

```go
if utf8.RuneCountInString(o.Text) > PostMessageMaxRunesV2 {
    return NewAppError(...)
}
```

If the intent is instead to bound the payload rather than the eventual post, say so in a comment and reuse `PostMessageMaxBytesV2` explicitly — but note that (c) means a bytes-based bound does not stop an over-long post from failing later. Better still, gate at the app layer against `a.MaxPostSize()`, where the configured limit is actually known.

### #5 🟡 Medium: The new invariant is enforced on only one branch of `CommandResponseFromHTTPBody`, and the third party picks the branch

| | |
|---|---|
| **File** | `server/public/model/command_response.go:35-42` (dispatcher) vs. `:72-74` (where `IsValid` is called) |
| **Category** | design / inconsistent-enforcement |
| **Confidence** | 100 |
| **Screen score** | 85 |
| **Validation** | waived — screened clear of the `evidence=norm` bar by more than 15 points |
| **Found by** | adversarial-reviewer (Medium) |

**Issue:** `IsValid()` is called only from `CommandResponseFromJSON`. The dispatcher is unchanged:

```go
func CommandResponseFromHTTPBody(contentType string, body io.Reader) (*CommandResponse, error) {
	if strings.TrimSpace(strings.Split(contentType, ";")[0]) == "application/json" {
		return CommandResponseFromJSON(body)                 // now validates
	}
	if b, err := io.ReadAll(body); err == nil {
		return CommandResponseFromPlainText(string(b)), nil   // never validates
	}
	return nil, nil
}
```

`Content-Type` is chosen by the very third party whose response is being validated. The same over-length body is rejected as `application/json` and accepted as `text/plain`, on both production call sites (`server/channels/app/command.go:595` for outgoing-webhook responses, `server/channels/web/webhook.go:114` for `POST /hooks/commands/{id}`). Only compliant JSON integrations are constrained.

The screen established the practical shape precisely: plain-text responses always have `ResponseType == ""`, so the *response-type* half of the invariant is vacuously satisfied on that branch — the bypass is specific to the **length** half. And because `ResponseType == ""` always routes to `SendEphemeralPost`, which has no length check, a plain-text response of up to `MaxIntegrationResponseSize` (1 MB) passes through entirely ungated. This is inconsistent enforcement of a rule with no downstream backing, not a bypassed security control — hence Medium, not High.

**Fix:** Put the check where the invariant is supposed to hold. Validate in `CommandResponseFromHTTPBody` (or inside `CommandResponseFromPlainText`) so both branches produce responses satisfying the same contract — or accept that the length invariant cannot hold at this layer and drop it in favor of a limit at the app layer, per finding #4.

## Minor Findings

### Consistency

- `server/public/model/command_response.go:90-98` — **Validation recurses deeper than processing.** `IsValid()` recurses through every nesting level of `ExtraResponses`, but `App.HandleCommandResponse` (`server/channels/app/command.go:605-632`) posts only the top-level response plus each *first-level* extra, and the attachment-stringification loop 20 lines above `IsValid` likewise handles one level only. A bad `response_type` at nesting level 2 — content the server would never render — therefore vetoes the entire payload, discarding a valid main post and valid first-level extras. Real and newly introduced, but tiered down from a primary finding: the screen scored it **45** (below the `evidence=norm` bar of 60 for a single finder) because nothing in this repo, its tests, or the documented slash-command format ever produces a second level of nesting. Make validation depth match processing depth — validate `o` and its direct `ExtraResponses` only, or make processing recursive too. *(adversarial-reviewer)*

### Considered But Not Flagged

**Routed out by `reach=narrow`:**

- **New nil-guard branch has no covering test** (test-reviewer, anchor 100) — `command_response.go:90-93`'s `if resp == nil { continue }` is new in this commit, and no test case in the file supplies a `null` entry inside `extra_responses` (the pre-existing "null array items" case nulls entries in `attachments` only). If the guard were later dropped or inverted, `resp.IsValid()` on a nil receiver would panic and nothing here would catch it. This is a change-introduced absence, which `reach=norm` would report as a Testing Gap; under `narrow`, reviewers are told not to hunt for absences, so it is recorded rather than reported. **Worth fixing anyway** — one table row: `{"null entry inside extra_responses", `{"text": "ok", "extra_responses": [null, {"text": "also ok"}]}`, &CommandResponse{...}, false}`.

**Examined and refuted:**

- **Typed-nil interface hazard on `IsValid()`'s `*AppError` return** — checked independently by quick-, broad-, and adversarial-reviewer, all reaching the same conclusion. In `CommandResponseFromJSON:72` the `err :=` declares a concrete `*AppError` and is returned only when the pointer is non-nil, so no nil `*AppError` is ever boxed into a non-nil `error`. `app/command.go:595` and `web/webhook.go:114` both `.Wrap()` an already-non-nil value. Safe.
- **Unbounded recursion / stack exhaustion via nested `extra_responses`** — constructed and refuted empirically by adversarial-reviewer with a standalone program: `encoding/json` caps nesting at depth 10000 (~4999 `CommandResponse` levels); depth 4990 unmarshals and recurses cleanly, depth 5001 fails with `exceeded max depth` before `IsValid` is ever reached. Go's growable stacks absorb 5000 small frames.
- **Retry/hook-consumption cascade on `/hooks/commands/{id}`** — a rejected payload returns 400 before `CommandWebhook().TryUse` is called, so the hook is not consumed and a retrying integration can re-attempt; but the hook has a hard 5-use cap and expires, so there is no self-amplifying loop.

**Pre-existing, out of reach (`reach=narrow`):**

- `CommandResponseFromPlainText` applies no validation of its own — the *asymmetry this change creates* is finding #5; the function's own leniency predates the diff.
- `CommandResponseFromHTTPBody` returns `(nil, nil)` when `io.ReadAll` fails (`command_response.go:41`) — a silent-failure path the new code does not make more reachable.
- `CommandResponseFromJSON`'s `io.ReadAll(data)` with no `io.LimitReader` of its own (callers supply the bound).
- Nested level-2 `ExtraResponses` never get their attachments stringified — the one-level loop predates this diff.
- Every `ShouldError: true` row asserts only that *an* error occurred, never which validation produced it — the file's pre-existing convention. Not currently misleading: each new payload can only fail one way, confirmed by the probes above. Asserting on `AppError.Id` would make the cases robust to future validation being added.

**Regression check on existing test rows** (test-reviewer, verified against `git show bcf51196:...`): all three pre-existing `ShouldError: true` rows already produced non-nil errors from JSON unmarshal failures — none reach `IsValid()` — so the added `assert.Error` changes no existing outcome. All pre-existing `ShouldError: false` rows have an empty or legal `response_type` and short text, so none newly fails validation. No silent expectation change in either direction.
