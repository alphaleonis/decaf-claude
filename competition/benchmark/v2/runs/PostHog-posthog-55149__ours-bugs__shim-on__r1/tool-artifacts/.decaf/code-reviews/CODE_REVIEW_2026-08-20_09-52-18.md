### #1 🔴 Critical: `override_flags_definitions` and `only_use_override_person_properties` are reachable with only a public project token

| | |
|---|---|
| **File** | `rust/feature-flags/src/handler/mod.rs:196`, `:223`; `rust/feature-flags/src/handler/flags.rs:152-176` |
| **Category** | security |
| **Confidence** | 75 |
| **Verified** | traced |
| **Pre-existing** | no |
| **Found by** | solo-reviewer (Critical) |

**Issue:** The change gates `detailed_analysis` behind `authentication::is_internal_request(&context)` (`mod.rs:218`) but passes `request.override_flags_definitions` (`mod.rs:196`) and `context.meta.only_use_override_person_properties` (`mod.rs:223`) through with no gate at all. `/flags` is authenticated only by the project API token from the request body (`handler/authentication.rs:14-15`), which is public and embedded in every web client. Any caller can therefore replace an existing flag's entire definition in-memory for their own request — and choose the `distinct_id` freely, since `/flags` never proves ownership of it.

Because DB person properties are still loaded when `only_use_override_person_properties` is absent, an attacker gets a general predicate oracle over another user's person properties: override an existing flag with `{"filters": {"groups": [{"properties": [{"key": "email", "operator": "icontains", "value": "acme", "type": "person"}], "rollout_percentage": 100}]}}`, send `distinct_id: "<victim>"`, and read `flags["<key>"].enabled`. Repeating with different predicates (`is_set`, `icontains`, `regex`, `gt`) extracts arbitrary person-property values character by character. Today a caller can only observe the predicates the customer happens to have defined; this makes the predicate set attacker-chosen.

**Evidence:** `flags.rs:152-176` applies overrides unconditionally to the cached flag list, before `filtered_out_flag_ids` is built (`flags.rs:197-201`), so the attacker also controls `active`/`deleted` and escapes runtime/tag filtering (`evaluation_tags` deserializes to `None`, which `collect_excluded_by_runtime`/`collect_excluded_by_tags` never filter). `*flag = override_flag` (`flags.rs:174`) replaces `id` and `team_id` too; `id` must match the cached value or the flag is silently dropped from `evaluation_stages` (`utils/graph_utils.rs:592-644`), and `id` is public — it is returned in `metadata.id` of every v2 response (`api/types.rs:428-430`). `flag.team_id` is only used for logging (`flag_matching.rs:1341`, `:1382`), so this does not cross the team boundary, but all person data of the token's own project is exposed. Secondary: `tracing::info!` at `flags.rs:154-166` logs attacker-controlled keys and full filter JSON at info level on every such request.

**Fix:** Gate both inputs the same way `detailed_analysis` is gated — reject the request (or ignore the fields) unless `is_internal_request(&context)` is true; ideally validate once at the top of `process_request_inner` and return `FlagError::Unauthorized` when `override_flags_definitions`/`only_use_override_person_properties` are present without the internal token, rather than silently ignoring them. Also drop the per-request `info!` logging of filter bodies.

### #2 🟠 High: historical flag override never applies — `model_to_dict` omits `id`, so the Rust service rejects it and evaluates the *current* definition

| | |
|---|---|
| **File** | `posthog/api/feature_flag.py:3521-3531` |
| **Category** | correctness |
| **Confidence** | 100 |
| **Verified** | traced (key facts re-verified by orchestrator against source) |
| **Pre-existing** | no |
| **Found by** | solo-reviewer (High) |

**Issue:** `model_to_dict` only emits fields with `editable=True` (Django skips `if not getattr(f, "editable", False)`), and `AutoField` forces `editable=False`. So `flag_dict` has no `id`. The Rust `FeatureFlag` struct requires it — `pub id: FeatureFlagId` (`= i32`) with no `#[serde(default)]` (`rust/feature-flags/src/flags/flag_models.rs:199`, `:219-221`). `serde_json::from_value::<FeatureFlag>` therefore fails with `missing field 'id'`, and `flags.rs:177-184` logs a `warn!` and **keeps the flag from cache**. The request still succeeds, so `POST /test_evaluation` with a `timestamp` returns an evaluation of the flag's *present-day* definition, presented as the definition at that timestamp — the central feature of this change silently does not work, and produces a confidently wrong historical answer.

**Evidence:** The dead code at `:3527-3528` corroborates that this dict shape was never inspected: `updated_at` is `auto_now=True` (`posthog/models/feature_flag/feature_flag.py:55`) hence non-editable and never present, so that branch can never fire. (`created_at` at `:54` is `default=timezone.now`, i.e. editable, so `:3525-3526` does fire.) A second, independent gap: evaluation contexts live in the related `flag_evaluation_contexts` table, not a model field, so `evaluation_tags`/`evaluation_contexts` is absent from the override and the reconstructed flag escapes context filtering. Even with `id` supplied, note that an `id` not present in the cached `dependency_stages` causes the flag to be dropped from evaluation entirely (`utils/graph_utils.rs:592`, `:634-641`) — i.e. this must be the real flag id.

**Fix:** Build the override payload explicitly instead of via `model_to_dict` — emit exactly the keys the Rust `FeatureFlag` contract needs (`id`, `team_id`, `key`, `name`, `filters`, `active`, `deleted`, `version`, `ensure_experience_continuity`, `evaluation_runtime`, `evaluation_contexts`, `bucketing_identifier`). Then make the failure loud: `flags.rs:177-184` should return a `FlagError` (or at minimum set a response flag) rather than warn-and-continue, so a malformed override can never be reported as a successful historical evaluation. A round-trip test (Django payload → Rust deserialization) would have caught this.

### #3 🟠 High: `test_evaluation` returns person properties under a `feature_flag:read` scope

### #4 🟠 High: `rollout_excluded` only fires at 0% rollout, so the common rollout exclusion is labelled with a false explanation

| | |
|---|---|
| **File** | `rust/feature-flags/src/api/types.rs:652`, `:675-687`, `:689-706` |
| **Category** | correctness |
| **Confidence** | 100 |
| **Verified** | traced |
| **Pre-existing** | no |
| **Found by** | solo-reviewer (High) |

**Issue:** `this_condition_rollout_excluded` is gated on `is_zero_rollout = rollout_percentage == 0.0` in *every* branch (`:679`, `:682`, `:686`). Rollout exclusion happens for any rollout below 100%, so the ordinary case — properties match, user's hash falls outside a partial rollout — reports `rollout_excluded: false` and picks the `all_properties_matched && !condition_matched` branch, emitting **"Condition N matched properties but was not evaluated due to an earlier condition matching"**. For a single-condition flag there is no earlier condition; the statement is simply false, and it points the user at the wrong cause of the very thing this endpoint exists to explain.

**Evidence:** Trace a flag with one condition, `rollout_percentage: 30`, properties matching, user out of bucket. `is_condition_match` returns `(false, OutOfRolloutBound)` via `check_rollout` (`flags/flag_matching.rs:1601-1607`), and the final `FeatureFlagMatch` carries `matches: false, reason: OutOfRolloutBound, condition_index: Some(0)` (`flag_matching.rs:1509-1515`). In `build_condition_analysis`: `condition_matched = false` (`:557-566`, guarded by `flag_match.matches`), `all_properties_matched = true` (`:662-667`), `properties_matched_but_rollout_failed = true` (`:671`), then `:679` → `0 == 0 && false` → `false`. Explanation falls to `:699-703`. Both the boolean and the prose are wrong; the Python serializer documents the field as "matched properties but was excluded due to rollout" (`posthog/api/feature_flag.py:1976`).

**Fix:** Derive exclusion from the match reason and index, not from the percentage: `rollout_excluded = matches!(flag_match.reason, OutOfRolloutBound) && flag_match.condition_index == Some(index) && all_properties_matched` (keeping `rollout_percentage == 0.0` as an additional sufficient condition when properties matched). Add the "single condition, partial rollout, out of bucket" case as a unit test — the current tests only assert `conditions: None`.

### #7 🟡 Medium: condition analysis evaluates group/cohort/flag filters against person properties and overloads `matched`

| | |
|---|---|
| **File** | `rust/feature-flags/src/api/types.rs:603-608`, `:662-667`, `:713` |
| **Category** | correctness |
| **Confidence** | 75 |
| **Verified** | traced |
| **Pre-existing** | no |
| **Found by** | solo-reviewer (Medium) |

**Issue:** Two defects in the per-property analysis:

1. `match_property(property, props, false)` is called for *every* filter with `props` = merged **person** properties only (`flag_matching.rs:1003-1012` supplies `get_person_properties(...)`). `match_property` is type-agnostic (`properties/property_matching.rs:54-93`) — it looks up `property.key` in whatever map it is given. A `type: "group"` filter is therefore tested against person properties, and a `type: "cohort"` filter is tested against a person property literally named `id`. Both come back `false`, so `all_properties_matched` is `false` and the condition is reported as **"Condition N did not match properties"** even when the real evaluation matched it via group properties or cohort membership (`flag_matching.rs:1574-1599`). Every flag targeting groups or cohorts gets a wrong analysis.
2. `matched: all_properties_matched` (`:713`) is serialized into a field documented as "Whether this condition was the one that matched" (`posthog/api/feature_flag.py:1970`). For a rollout-only condition `all_properties_matched` is hard-coded `true` (`:665-667`), so such a condition always reports `matched: true` even when the flag evaluated to `false`.

**Evidence:** `property_context.resolve_for_filter(filter)` in the real matcher (`flag_matching.rs:1584`) picks the property source per filter type; `build_condition_analysis` has no equivalent and no access to group properties. Cohort filters in the real path go through `evaluate_cohort_filters` (`flag_matching.rs:1592-1598`), which `build_condition_analysis` never calls.

**Fix:** Skip (or mark "not analysed") filters whose `prop_type` is not `Person`, or thread the group properties and cohort-match map into `build_condition_analysis` so each filter is evaluated against the same source the matcher used. Rename the condition-level field (e.g. `properties_matched`) or set it to `condition_matched` so it agrees with its documented meaning.

### #9 🟡 Medium: bulk-deleted flags are not treated as deleted, contradicting the function's documented contract

| | |
|---|---|
| **File** | `posthog/models/feature_flag/version_history.py:242-250` |
| **Category** | correctness |
| **Confidence** | 75 |
| **Verified** | traced |
| **Pre-existing** | no |
| **Found by** | solo-reviewer (Medium) |

**Issue:** The docstring states a flag is non-existent if it "was soft-deleted at or before the timestamp (without subsequent restoration)" (`:187-189`), but `flag_was_deleted` is only updated inside `if version_after is not None` (`:243-250`). The bulk-delete path logs `activity="deleted"` with `Detail(changes=[])` and updates the rows via `queryset.update()` without bumping `version` (`posthog/api/feature_flag.py:2836-2846`, `:2865-2870`) — so its entries are skipped and the flag is reported as alive for the entire deleted window. `reconstruct_flag_at_timestamp` then returns the pre-delete definition and the endpoint answers with an evaluation result instead of "did not exist at the specified timestamp".

**Evidence:** `bulk_log_activity` receives `Detail(changes=[], name=old_key)` (`feature_flag.py:2845`), and the `FeatureFlag.objects.filter(...).update(deleted=True, ...)` at `:2867-2870` sets no `version`. Reachability: a currently-deleted flag cannot be fetched by `self.get_object()`, but a bulk-deleted-then-restored flag can — a restore is a normal PATCH, logged as `"restored"` with a version change (`feature_flag.py:3710-3715`) — and every timestamp inside the deleted window then reports the flag as live. Note also the asymmetry: an unversioned `"restored"` entry would likewise fail to clear the flag.

**Fix:** Track delete/restore state from the `activity` value regardless of whether the entry carries a version change (keep the version-extraction guard only for `most_recent_version`). Alternatively have the bulk-delete path bump `version` and log the change so both readers agree.
