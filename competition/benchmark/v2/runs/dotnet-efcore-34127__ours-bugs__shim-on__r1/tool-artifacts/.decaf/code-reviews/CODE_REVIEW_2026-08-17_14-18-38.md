## Findings

### #1 🔴 Critical: `NullPropagatedOperands` recurses into `AndAlso`/`OrElse` operands, which do not propagate SQL null — the optimization then deletes a needed `IS NOT NULL` guard and silently changes query results and result sets

| | |
|---|---|
| **File** | `src/EFCore.Relational/Query/SqlNullabilityProcessor.cs:626` |
| **Category** | correctness |
| **Confidence** | 100 |
| **Verified** | executed |
| **Pre-existing** | no |
| **Found by** | solo-reviewer (Critical) |

**Issue:** `NullPropagatedOperands` recurses into `SqlBinaryExpression.Left`/`.Right` for *every*
operator type:

```csharp
else if (expression is SqlBinaryExpression binary)
{
    NullPropagatedOperands(binary.Left, operands);
    NullPropagatedOperands(binary.Right, operands);
}
```

`SqlBinaryExpression.IsValidOperator` (`src/EFCore.Relational/Query/SqlExpressions/SqlBinaryExpression.cs:88-104`)
admits `AndAlso`, `OrElse` and `Coalesce` alongside the arithmetic/comparison operators. Under SQL
three-valued logic `AndAlso` and `OrElse` are *not* null-propagating: `NULL AND FALSE` is `FALSE`,
`NULL OR TRUE` is `TRUE`. So an operand reached through an `AND`/`OR` node is wrongly recorded as
one whose nullness propagates to the result, and `DropNotNullChecks` then deletes the `IS NOT NULL`
test that was guarding it.

This is not a corner case: `SqlNullabilityProcessor` itself *produces* `AndAlso`/`OrElse` results,
because that is the shape of the null-semantics rewrite of a nullable comparison
(`RewriteNullSemantics`, reached from `VisitSqlBinary` at line 1394). Any
`x.Nullable != null ? (bool?)(<comparison involving another nullable>) : null` — the standard C#
null-propagation idiom over an optional navigation or a nullable column — lands exactly on it. The
resulting CASE loses its `ELSE NULL` arm entirely, so the expression now returns `TRUE`/`FALSE`
where it used to return `NULL`.

Consequence: silently wrong projected values **and** silently wrong rows, on every relational
provider (the rewrite lives in the shared `EFCore.Relational` processor). No exception, no warning.

**Evidence:** Executed. The seat built `src/EFCore.Sqlite.Core` at `afcfba2e9` and at the parent
`051c33a79` (throwaway `git worktree`s, both removed; the review checkout was never touched — the
in-repo test projects do not compile under the installed SDK 10.0.203 for pre-existing reasons, so a
standalone console probe was driven against the built providers instead).

Data: 5 rows, `(Id, A, B)` = `(1,null,null) (2,null,5) (3,5,null) (4,5,5) (5,5,6)`.

Projection, `Select(x => x.A != null ? (bool?)(x.A == x.B) : null)`:

| | SQL | result |
|---|---|---|
| parent `051c33a` | `CASE WHEN "e"."A" IS NOT NULL THEN "e"."A" = "e"."B" AND "e"."B" IS NOT NULL ELSE NULL END` | `null, null, False, True, False` ✅ matches LINQ-to-objects |
| this change | `SELECT "e"."A" = "e"."B" AND "e"."B" IS NOT NULL` | `False, null, False, True, False` ❌ row 1 is `False`, should be `null` |

Same failure for `!=` (`"e"."A" <> "e"."B" OR "e"."B" IS NULL` → row 1 yields `True`), for `string`
comparison, and for `!(x.A == x.B)`.

Wrong **rows**, `Where(x => (x.A != null ? (bool?)(x.A != x.B) : null) == true)`:

| | SQL | ids returned |
|---|---|---|
| parent `051c33a` | `WHERE CASE WHEN "e"."A" IS NOT NULL THEN "e"."A" <> "e"."B" OR "e"."B" IS NULL ELSE NULL END` | `3,5` ✅ |
| this change | `WHERE "e"."A" <> "e"."B" OR "e"."B" IS NULL` | `1,3,5` ❌ extra row |

Same for the `?? false` variant. SQL Server is affected identically — with the change,
`Select(x => x.A != null ? (bool?)(x.A == x.B) : null)` generates

```sql
SELECT CASE WHEN [e].[A] = [e].[B] AND [e].[B] IS NOT NULL THEN CAST(1 AS bit) ELSE CAST(0 AS bit) END
```

(the `ELSE NULL` arm present at the parent commit is gone; `A IS NULL` now yields `0`, not `NULL`).
`SearchConditionConvertingExpressionVisitor` runs *after* `SqlNullabilityProcessor`
(`src/EFCore.SqlServer/Query/Internal/SqlServerParameterBasedSqlProcessor.cs:41-45`), which is why a
raw boolean `SqlBinaryExpression` can sit in a CASE result at this point.

The existing suite does not catch it: none of the five new tests
(`test/EFCore.Relational.Specification.Tests/Query/NullSemanticsQueryTestBase.cs:2250-2295`) has a
boolean-typed WHEN result.

`Coalesce` is the same class of unsoundness (`COALESCE(a, b)` is not null-propagating in `a`) but is
unreachable today: `RelationalSqlTranslatingExpressionVisitor.cs:450` routes `??` to
`SqlExpressionFactory.Coalesce`, which emits a `SqlFunctionExpression`, and
`QuerySqlGenerator.GetOperator` (line 1081) would throw on a `SqlBinaryExpression`-shaped
`Coalesce`. It is still worth excluding, since a provider may construct one.

**Fix:** Restrict the binary recursion to operators that actually propagate null (`Add`/`Subtract`/
`Multiply`/`Divide`/`Modulo`, the comparisons, and the bitwise `And`/`Or`/`ExclusiveOr` — all of
which yield `NULL` for a `NULL` operand):

```csharp
else if (expression is SqlBinaryExpression binary
    && binary.OperatorType is not (ExpressionType.AndAlso or ExpressionType.OrElse or ExpressionType.Coalesce))
{
    NullPropagatedOperands(binary.Left, operands);
    NullPropagatedOperands(binary.Right, operands);
}
```

Verified in a scratch worktree at `afcfba2e9` + this patch (worktree removed afterwards): all four
failing probe shapes return to matching LINQ-to-objects and to the parent commit's SQL, while every
optimization the new tests assert still fires — `~"e"."A"`, `"e"."A" + "e"."B"`,
`"e"."S" || "e"."T" || COALESCE("e"."U", '')`, and the nested-check `"e"."S" || "e"."T"` are all
still emitted without the `CASE`.

A regression test with a boolean-typed WHEN result (e.g.
`x => x.NullableIntA != null ? (bool?)(x.NullableIntA == x.NullableIntB) : null`, and the
`Where(... == true)` variant) would close the exact hole the current five tests leave open.

  divide-by-zero guards are not dropped.
