### #1 🟠 High: `SamplesRead` double-counts subquery samples, so the "samples read" counter exceeds the samples actually loaded

| | |
|---|---|
| **File** | `promql/engine.go:1874` (with `promql/engine.go:2184`) |
| **Category** | correctness |
| **Confidence** | 100 |
| **Found by** | broad-reviewer (High), adversarial-reviewer (High), design-reviewer (High), go-reviewer (High), test-reviewer (Critical), knowledge-reviewer (MUST) |

**Issue:** For any range-vector function applied directly to a subquery — `rate(foo[5m:1m])`, `max_over_time(foo[60s:5s])`, `sum_over_time(...)`, and the same shapes nested or wrapped in aggregations — the subquery's samples are counted twice:

1. `evalSubquery` evaluates the subquery into a child stats object, then merges the child's reads into the parent at `promql/engine.go:1874` via `MergeSamplesReadFromSubquery`.
2. `evalSubquery` then hands the *already materialized* result back as a synthetic `MatrixSelector`. The enclosing range-vector function's step loop treats it exactly like a raw storage series and counts it again at `promql/engine.go:2184`.

The pre-change code avoided precisely this. The comment deleted from `evalSubquery` read: *"Avoid double counting samples when running a subquery, those samples will be counted in later stage."* That rationale still applies — it is why `TotalSamples` is deliberately not merged from the child — and the change breaks the symmetry for `SamplesRead` only.

**Measured** (instant query at t=201s, out-of-tree build of `ec7157593`):

| query | `TotalSamples` | `SamplesRead` | ratio |
|---|---|---|---|
| `metricWith3SampleEvery10Seconds[60s:5s]` (bare subquery, control) | 36 | 36 | 1.00× |
| `max_over_time(metricWith3SampleEvery10Seconds[60s:5s])` | 36 | 72 | 2.00× |
| `max_over_time(max_over_time(m[30s:10s])[60s:10s])` (nested) | 6 | 22 | 3.67× |

The inflation compounds with nesting. A static audit of the change's own expected-value table finds **48 of 97 cases with `SamplesRead > TotalSamples`**, the worst being `rate(histogram_sum(metricWith1HistogramEvery10Seconds)[2m:30s])` at 56 vs 4 — a factor of **14**.

This is not merely a cosmetic inconsistency. `samplesRead` is documented as "samples *read* (I/O)" and the counter help string says "The total number of samples read by all queries". A quantity described as I/O cannot exceed the samples loaded. `prometheus_engine_query_samples_read_total` is incremented unconditionally in `exec` — not behind `stats=all`, not behind the `promql-per-step-stats` flag — so every server exposing it reports an inflated value for subquery workloads.

**Fix:** Pick one owner for subquery reads. Either drop `MergeSamplesReadFromSubquery` at `promql/engine.go:1874` and let the outer window over the subquery result be the only count (mirroring how `TotalSamples` already avoids this), or suppress `IncrementSamplesReadAtStep` at `promql/engine.go:2184` when the matrix argument is the synthetic `VectorSelector` produced by `evalSubquery`. Whichever is chosen, add an assertion to `TestQueryStatistics` that `SamplesRead <= TotalSamples` for every case — that invariant is what makes the two counters jointly interpretable — and re-derive the 48 affected expectations (finding #6).

### #2 🟠 High: `TotalSamples` regresses for `@`-modified range vectors, despite an adjacent comment asserting unchanged semantics

| | |
|---|---|
| **File** | `promql/engine.go:2145` (consumed at `promql/engine.go:2183`) |
| **Category** | correctness — regression in pre-existing public surface |
| **Confidence** | 100 |
| **Found by** | quick-reviewer (High), adversarial-reviewer (Medium), design-reviewer (Critical), knowledge-reviewer (MUST) |

**Issue:** `fullWindowCount` is declared fresh inside the per-step loop and assigned only inside the guard `if ts == ev.startTimestamp || selVS.Timestamp == nil`. On steps where the window is *reused* rather than re-read — an `@`-pinned matrix argument — it therefore stays 0, and `IncrementSamplesAtStep(step, fullWindowCount)` at line 2183 charges nothing.

Before the change, that line read `IncrementSamplesAtStep(step, int64(len(floats)+totalHPointSize(histograms)))` and sat *outside* the guard, so it charged the retained window at every step.

`TotalSamples` is not new. It feeds `totalQueryableSamples` in the HTTP API and `prometheus_engine_query_samples_total`, both long-standing public surface. The comment two lines above the change says *"Full window count for TotalSamples (unchanged semantics)"* — that claim is false, and it is exactly the sentence a future maintainer auditing this counter would stop at.

**Reachability.** `preprocessExprHelper` returns `shouldWrap = false` for a bare `*parser.MatrixSelector`, so an `@`-pinned range selector inside a call that is *not* step-invariant overall is evaluated across every outer step with `selVS.Timestamp != nil`. A non-invariant sibling argument is enough: `quantile_over_time(scalar(other), foo[60s] @ 30)`.

**Measured** — same query, range 201s→231s at 10s, built from each commit:

| | `TotalSamples` | `totalQueryableSamplesPerStep` |
|---|---|---|
| base `efbdc3f88` | **52** | `[13, 13, 13, 13]` |
| head `ec7157593` | **16** | `[13, 1, 1, 1]` |
| control: `max_over_time(m3[60s])`, both commits | 72 | `[18, 18, 18, 18]` |

A 3.25× silent drop in an existing metric. No test covers this shape — the `@`-with-`_over_time` cases in `promql/promqltest/testdata/at_modifier.test` are all `eval instant`, and `promqltest` does not assert `TotalSamples` at all — so the full pre-flight suite passes.

**Fix:** Keep `TotalSamples` byte-for-byte: pass `int64(len(floats)+totalHPointSize(histograms))` unconditionally at line 2183 as before, and let the new guard govern `samplesReadCount` only. If the drop is intentional, say so explicitly in place of "unchanged semantics", reconcile it with the `StepInvariantExpr` path at `promql/engine.go:2467-2469` (which still replicates `TotalSamples` across steps, so the two `@` paths now disagree), and pin it with a range-query `TestQueryStatistics` case.

### #3 🟠 High: Subquery per-step tracking allocates two slices sized by the *subquery's own* step count, unbounded by `query.max-samples`

| | |
|---|---|
| **File** | `promql/engine.go:2397` (via `util/stats/query_stats.go:411`, `:299`) |
| **Category** | resource-management |
| **Confidence** | 100 |
| **Found by** | adversarial-reviewer (Critical) — sole finder |
| **Validation** | confirmed; severity corrected Critical → High for flag gating |

**Issue:** `NewChildWithStepTracking(..., subqStart, subqEnd, subqInterval)` calls `InitStepTracking`, which computes `numSteps := int((end-start)/interval) + 1` and then `make([]int64, numSteps)` **twice**. Here `numSteps` is the *subquery's* step count, which the client controls through the subquery step in `[range:step]`. Before the change the subquery child was `NewChild()` → `NewQuerySamples(false)`, allocating no per-step arrays at all.

The allocation happens before any sample is read, so `query.max-samples` — which is checked per sample inside `evalSeries` — cannot bound it. The validator confirmed there is no other guard: the API's 11,000-point resolution cap applies only to the outer range query's request-level `step` parameter, never to a subquery step embedded in the query string, and no parser or engine restriction on subquery step granularity exists.

**Measured** — instant query `count_over_time(m[<range>:1ms])` with `MaxSamples = 1`, so the query aborts with "too many samples" and *still* allocates. `runtime.MemStats.TotalAlloc` delta:

| range | head `ec7157593` | base `efbdc3f88` |
|---|---|---|
| 1m | 1.1 MB | 0.1 MB |
| 10m | 9.7 MB | 0.1 MB |
| 1h | 57.7 MB | 0.1 MB |
| 1d | **1382.5 MB** (HeapAlloc 1394 MB) | 0.1 MB |

Growth is exactly linear in the subquery step count (86,400,001 steps × 8 B × 2 = 1382 MB), so `[7d:1ms]` extrapolates arithmetically to ~9.7 GB from one request.

**Gating** (traced by the validator, and the reason severity is High rather than Critical): reaching this requires **both** the server-side experimental flag `--enable-feature=promql-per-step-stats` and a client-supplied `stats=all`. The rule and alerting path passes `opts = nil` → `NewPrometheusQueryOpts(false, 0)`, so it cannot reach this. The flag is off by default; on a server that has opted in, any client with query-API access can trigger it.

**Fix:** Do not size the child's per-step arrays by the subquery's own step count. Either keep `NewChild()` for the subquery child and attribute its reads with `IncrementSamplesReadAtTimestamp` (accepting coarser per-step attribution), or skip step tracking — falling back to timestamp attribution — when the subquery step count exceeds a bound comparable to the API's existing 11,000-point resolution limit. Note also that the merge loop at `promql/engine.go:2429` is O(subquery steps) even when every entry is zero.

### #4 🟠 High: `countSamplesAfter` adds an unconditional O(steps × window) rescan to the query evaluation hot path

| | |
|---|---|
| **File** | `promql/value.go:195` (called at `promql/engine.go:2164`) |
| **Category** | performance |
| **Confidence** | 100 |
| **Found by** | performance-reviewer (High) — sole finder |
| **Validation** | waived — `screened 90`, and measured directly by benchmark |

**Issue:** `countSamplesAfter` linearly scans the *entire* range-vector window on every step, for every series, inside the `*parser.Call` loop. `matrixIterSlice` already maintains the window incrementally — it keeps the retained prefix and appends only the new tail, amortizing to O(new points) per step. `countSamplesAfter` discards that and re-walks the full slice from the front, turning O(steps + window) total work into O(steps × window).

It runs **unconditionally**. `IncrementSamplesReadAtStep` always updates the scalar `SamplesRead`; only the per-step array write is flag-gated. So every range query using a range-vector function pays this whether or not anyone reads the new counter.

**Measured** — `go test -bench BenchmarkRangeQuery -benchtime=3x -count=3`, base and head built from the two commits and run sequentially on the same host after the review wave had joined:

| benchmark | base ns/op | head ns/op | change |
|---|---|---|---|
| `absent_over_time(a_hundred[1d]), steps=1000` | 342.4 / 342.7 / 344.0 M | 618.1 / 619.5 / 619.6 M | **+80%** |
| `changes(a_hundred[1d]), steps=1000` | 4009 / 4010 / 4028 M | 4633 / 4677 / 4684 M | **+16%** |

Allocations are unchanged (`countSamplesAfter` does not allocate), and within-group spread is under 1%, so this is not contention noise. The regression is worst for functions whose per-call cost is O(1) — `absent_over_time`, `present_over_time`, `last_over_time` — where the per-step cost changes complexity class.

**Fix:** Have `matrixIterSlice` report how many points it newly appended this step, and derive `samplesReadCount` from that in amortized O(1) — no rescan. Failing that, reverse-scan from the tail and stop at the first point at or before `cutoff`, which is O(new points) rather than O(window), since the slices are time-ordered. Independently, consider gating the whole computation on `EnablePerStepStats` so queries that never inspect the counter do not pay for it.

### #7 🟡 Medium: `samplesReadPerStep` folds out-of-window subquery reads onto the first and last steps, so it is not comparable to `totalQueryableSamplesPerStep`

| | |
|---|---|
| **File** | `promql/engine.go:2434` |
| **Category** | data-model |
| **Confidence** | 100 |
| **Found by** | design-reviewer (Medium), knowledge-reviewer (partially) |
| **Validation** | confirmed (line corrected 2426 → 2434) |

**Issue:** In the subquery merge loop, subquery steps at or before the outer `startTimestamp` all receive `outerStep = 0`, and any step past the last outer step is clamped to `numOuterSteps - 1`. The first and last points of the series therefore absorb all out-of-window reads and are not comparable to the interior points, nor to `totalQueryableSamplesPerStep` at the same timestamp.

The validator isolated a distortion **independent of the double count in #1**, which was the obvious alternative explanation: `max_over_time(metricWith3SampleEvery10Seconds[60s:5s])` over 201s→220s at 5s yields `SamplesReadPerStep = [72, 6, 6, 9]`. The last bucket's 9-versus-6 excess comes specifically from the `outerStep >= numOuterSteps` clamp folding an out-of-window subquery step onto it — the uniform double count and the "full window at step 0" convention do not account for it. The clamp is reachable in the change's own tests (`promql/engine_test.go:2213`: `380000: 24, // steps after last outer → last step`).

A dashboard plotting the two per-step series together, or dividing them, is misleading at the window edges, and the skew grows with the subquery range.

**Fix:** Either publish the edge rule as part of the contract — documenting that the first and last points absorb out-of-window reads and are not comparable to the interior — or emit the out-of-window reads as a separate scalar so the per-step series stays interpretable. Note that simply dropping the clamp is not an option: `SamplesReadPerStep` is a fixed-length slice, so removing it produces an out-of-bounds panic (see #12).

### #8 🟢 Low: `IncrementSamplesReadAtStep` omits the `i >= 0` guard its own sibling has — three different out-of-range policies across four sibling functions

| | |
|---|---|
| **File** | `util/stats/query_stats.go:352` |
| **Category** | consistency / defensive-coding |
| **Confidence** | 100 (quotable fact) |
| **Found by** | design-reviewer (Medium), go-reviewer (Low), knowledge-reviewer (SHOULD), consistency-reviewer (Medium) |

**Issue:** Four sibling functions, three policies:

| function | guard |
|---|---|
| `IncrementSamplesAtStep` (`:321`) | none — indexes unguarded, panics on any bad index |
| `IncrementSamplesAtTimestamp` (`:334`) | none |
| `IncrementSamplesReadAtStep` (`:347`) | `i < len(...)` only — **still panics on a negative index**, and silently drops the per-step contribution when the index is too large while `SamplesRead` still counts it |
| `IncrementSamplesReadAtTimestamp` (`:358`) | `i >= 0 && i < len(...)` |

The first two are called back-to-back with the *same* index as the last two at `promql/engine.go:2183-2184`, so a reader cannot tell whether an out-of-range index is a real scenario the read counter must tolerate or defensive noise. If it is real, the `TotalSamples` twin panics on the very input the read counter absorbs. If it is not, the guard hides a future bug and lets `sum(SamplesReadPerStep) != SamplesRead` ship undetected. No agent found a currently reachable negative or over-range index.

**Fix:** Pick one policy for the family and apply it to all four. At minimum add the `i >= 0` guard to `IncrementSamplesReadAtStep` so the two new functions at least agree with each other, and document the chosen policy on the type.

### #12 🟢 Low: The subquery attribution rule has no stated rationale or invariant, and the clamp that makes it safe is undocumented

| | |
|---|---|
| **File** | `promql/engine.go:2425` |
| **Category** | knowledge-preservation |
| **Confidence** | 100 |
| **Found by** | knowledge-reviewer (MUST) — sole finder |
| **Validation** | confirmed; severity corrected High → Low (the off-by-one suspicion was refuted) |

**Issue:** The loop attributes each subquery step onto an outer step by ceiling division, with two *different* out-of-window rules — steps at or before `ev.startTimestamp` fall to step 0, steps past the last outer step are clamped to `numOuterSteps - 1`. The only rationale present is the fragment "so all disk reads are counted". Nothing records why ceiling rather than floor, why clamping rather than dropping, or the invariant being protected. The commit message is one line with no body.

The validator confirmed the documentation gap and refuted the accompanying correctness suspicion: the visible 4-versus-5 asymmetry for `max_over_time(m[20s:10s])` is forced by parity (5 subquery instants cannot divide evenly across 2 outer buckets under *any* monotonic scheme) plus a separate symmetric outer-level count — not an off-by-one.

The validator also established a fact worth recording in the code: **the clamp is load-bearing, not cosmetic.** `SamplesReadPerStep` is a fixed-length slice, so removing the clamp produces an out-of-bounds panic on any subquery step past the last outer step — not merely a silent undercount. Nothing in the comment conveys that.

**Fix:** Replace the comment at `promql/engine.go:2425` with a block stating (1) the invariant — every subquery step's count lands in exactly one outer bucket, so `sum(SamplesReadPerStep) == SamplesRead`; (2) the rule — a subquery step at `tk` is charged to the first outer step at or after `tk`, because that is the first outer step whose window consumes it; (3) that the clamp prevents an out-of-bounds index, not just an accounting gap. Add an explicit `sum(SamplesReadPerStep) == SamplesRead` assertion to `TestQueryStatistics`.

## Specialist Notes

### Considered But Not Flagged (all agents)

**Refuted by validators (2):**

- **Ceiling-versus-floor rounding divergence between the two merge branches** (`promql/engine.go:2426`, design-reviewer Medium, knowledge-reviewer SHOULD). *Refuted:* the claim that the two branches disagree on which step a timestamp belongs to is vacuous. The `else` arm runs only when `SamplesReadPerStep` is nil, and `IncrementSamplesReadAtTimestamp` computes its floor index *inside* `if qs.SamplesReadPerStep != nil` — so in the only state where the `else` arm executes, no bucket index is ever computed. The two rules never act on live state simultaneously. Ceiling at line 2437 also solves a different problem (which outer step consumes `tk`) than the floor helper's bucket-of-own-step semantics.
- **`MergeSamplesReadFromSubquery`'s unexpressed index-alignment invariant** (`util/stats/query_stats.go:423`, design-reviewer Medium, knowledge-reviewer SHOULD). *Refuted as stated:* the method has exactly one caller in the repo (`promql/engine.go:1874`), whose child is built at `:1869` from the same `startTimestamp`/`endTimestamp`/`interval` that define the parent's layout — so parent and child are identical **by construction**, not by luck. The differently-laid-out child at `:2397` never reaches this method; its results go through the separate mapping loop at `:2424-2447`. The tail-drop scenario is unreachable. The exported-API argument is further undercut by `docs/stability.md`, which lists "Go APIs of packages that are part of the server" as explicitly unstable. The residual doc-scope issue is carried as a Minor finding.

**Dismissed with sound reasoning, cross-checked across agents (kept dismissed):**

- **Division by zero when `interval == 0`** in `InitStepTracking` / the outer-step computation — dismissed independently by adversarial, broad, go and knowledge reviewers with consistent reasoning: instant queries force `interval: 1` (`promql/engine.go:805`), range queries use the request step, and the pre-existing `subqStart` computation divides by the same value one line earlier, so this change cannot be the first to panic. Pre-existing at worst.
- **`outerStep = numOuterSteps - 1` yielding index −1** — requires `len(SamplesReadPerStep) == 0`, but `InitStepTracking` computes `int((end-start)/interval)+1`, which is ≥ 1 for every construction site under Go's truncating division. Dismissed by adversarial and go reviewers.
- **`countSamplesAfter`'s cutoff under `Anchored`/`Smoothed` selectors** — dismissed by five agents with the same reasoning: the lookback-delta shift is a per-query constant, so `maxt - ev.interval` still equals the previous step's `maxt`. Correct today; the fragility is carried as a Minor finding rather than a defect.
- **`evalSubquery`'s restore not being deferred** — if `ev.eval` panics via `ErrTooManySamples`, the merge and restore are skipped, leaving `ev.samplesStats` pointing at the discarded child. Go-reviewer traced it: the panic is recovered only at the top-level `Eval`, which aborts the whole query, and `exec`'s deferred metric increments read the original top-level object. Harmless.
- **`samplesRead` lacking `omitempty`** — sound as written: `totalQueryableSamples` and `peakSamples` are also unconditional, the whole `stats` object is built only when the client passes `stats`, and additive fields are permitted. Presence rules match `totalQueryableSamplesPerStep`'s.
- **OpenAPI integer-versus-number typing and golden-file drift** — `samplesRead: integer` matches the JSON `int64`; `samplesReadPerStep` items typed `number` mirror the existing `totalQueryableSamplesPerStep` entry, and the tuple genuinely mixes a float timestamp with an integer count. `TestOpenAPI` passes.
- **Metric registration completeness** — `NewEngine` is the only engine construction path, and `querySamplesRead` is added to the same `MustRegister` list under the same guard. Naming follows the `_total` convention.
- **Removal of `defaultEpsilon` from `promql/engine_test.go:51`** — verified genuinely unused in that file; the live copy is `promql/promqltest/test.go:59`, a different package. Harmless cleanup.
- **`int(s.V)` truncation in `SamplesReadPerStepMap`** — identical pre-existing pattern in `TotalSamplesPerStepMap`. Not new.
- **Concurrency** — `promql/engine.go` contains no goroutines, errgroups or waitgroups; `samplesStats` ownership is strictly single-goroutine with explicit save/restore. No synchronization gap to report.

**Reviewer dismissal overridden (Step 5.5):** `consistency-reviewer` examined the comment "Full window count for TotalSamples (unchanged semantics)" at `promql/engine.go:2143-2145` and concluded it "agree[s] with each other and with the code — no mismatch". Four other agents flagged it, and a base-versus-head measurement shows the comment is false (finding #2). The dismissal is recorded here as incorrect; the item is reported as a primary finding.
