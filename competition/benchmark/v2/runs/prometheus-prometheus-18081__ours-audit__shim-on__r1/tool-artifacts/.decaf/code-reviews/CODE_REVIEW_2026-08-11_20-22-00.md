## Findings

### #1 🔴 Critical: `@`-modifier window reuse silently zeroes the pre-existing `totalQueryableSamples` / `prometheus_engine_query_samples_total` for every step after the first

| | |
|---|---|
| **File** | `promql/engine.go:2183` (declaration at `:2145`) |
| **Category** | correctness — unintended behavior change to a shipped public metric |
| **Confidence** | 100 — probe-confirmed by execution |
| **Found by** | design-reviewer (Critical), quick-reviewer (High), broad-reviewer (High), adversarial-reviewer (High), go-reviewer (High), security-reviewer (Medium) |

**Issue:** The old code incremented `TotalSamples` unconditionally from the retained slices:

```go
ev.samplesStats.IncrementSamplesAtStep(step, int64(len(floats)+totalHPointSize(histograms)))
```

The change hoists that into `fullWindowCount`, which is declared **inside** the per-step loop (`:2145`) and only assigned inside the load guard `if ts == ev.startTimestamp || selVS.Timestamp == nil` (`:2149`). When an `@`-pinned matrix selector causes the window to be loaded once and reused, that block is skipped for every step ≥ 1, so `fullWindowCount` keeps its zero value and `:2183` adds **0** — even though `call()` runs on the reused non-empty window and produces a real result for that step.

The in-code comment added on the same lines asserts the opposite: `// Full window count for TotalSamples (unchanged semantics)`. It also breaks a property deliberately documented in a file this same commit edits — `util/stats/query_stats.go:271-276`: *"we **intentionally do not account for optimizations** that happen inside the range query engine that reduce the actual work that happens."* `@`-window reuse is exactly such an optimization.

**Reachability.** `preprocessExprHelper` never wraps a `*parser.MatrixSelector` (`promql/engine.go:4363-4366`, `return isStepInvariant, false`) and `predict_linear` is in `AtModifierUnsafeFunctions` (`promql/functions.go:2248`), so `predict_linear(m[60s] @ 30, 3600)` is not wrapped in a `StepInvariantExpr` and reaches this loop with `selVS.Timestamp != nil` across all outer steps.

**Probe result** (range query 201s→220s, step 5s, 3 series at 10s resolution):

| | `TotalSamples` | `TotalSamplesPerStep` |
|---|---|---|
| pre-change accounting line restored | **48** | `{201000:12, 206000:12, 211000:12, 216000:12}` |
| HEAD | **12** | `{201000:12, 206000:0, 211000:0, 216000:0}` |
| control, no `@`: `predict_linear(m[60s], 3600)` | 72 (both) | `{18,18,18,18}` (both) |

The query returns 3 valid series at all 4 steps in both runs — only the reported cost changed, by 4×. The control confirms the regression is specific to the `@`-reuse path.

**Not covered by any test:** with the pre-change line restored, `go test ./promql` passes in full (6.4s), including all 1140 new test lines. Nothing pins the new behavior, so the fix is test-compatible today.

**Fix:** keep `TotalSamples` byte-identical and let only the new dimension carry delta semantics.

```go
outVec, annos := call(vectorVals, inMatrix, e.Args, enh)
warnings.Merge(annos)
// Counts the (possibly reused) window at every step — unchanged from before.
ev.samplesStats.IncrementSamplesAtStep(step, int64(len(floats)+totalHPointSize(histograms)))
ev.samplesStats.IncrementSamplesReadAtStep(step, samplesReadCount)
```

Add a `TestQueryStatistics` case for `predict_linear(metricWith3SampleEvery10Seconds[60s] @ 30, 3600)` over 201→220 at 5s pinning `TotalSamplesPerStep` at `{12,12,12,12}`.

### #2 🔴 Critical: `SamplesRead` double-counts every subquery, so the new metric exceeds the counter it is documented to be a subset of

| | |
|---|---|
| **File** | `promql/engine.go:1874` (`evalSubquery`), with `promql/engine.go:2184` |
| **Category** | correctness — the change's primary deliverable is wrong by 2–14× |
| **Confidence** | 100 — probe-confirmed by execution |
| **Found by** | test-reviewer (Critical), broad-reviewer (High), adversarial-reviewer (High), go-reviewer (High), design-reviewer (High), knowledge-reviewer (MUST), security-reviewer (Medium) |

**Issue:** `evalSubquery` now merges the child's `SamplesRead` into the parent —

```go
parentSamplesStats.MergeSamplesReadFromSubquery(ev.samplesStats)
```

— and then the *same data* is counted a second time. `evalSubquery` rewrites the `SubqueryExpr` into a synthetic `MatrixSelector` whose `VectorSelector.Series` holds the materialized subquery output (`engine.go:2008-2015`), and the enclosing range-vector loop re-scans exactly those in-memory points and counts them at `engine.go:2184`. No storage read happens the second time.

The deleted comment said precisely this:

```go
// Avoid double counting samples when running a subquery, those samples will be counted in later stage.
ev.samplesStats = ev.samplesStats.NewChild()
```

That "later stage" still exists. The rewrite kept the suppression for `TotalSamples` and dropped it for `SamplesRead`, with nothing recording that the invariant was abandoned or why — the new comment states only the mechanism.

**Probe result.** Removing only the `MergeSamplesReadFromSubquery` call makes instant-query subquery `SamplesRead` land exactly on `TotalSamples`:

| query (instant, t=201) | expected in table | with merge removed | `TotalSamples` |
|---|---|---|---|
| `max_over_time(metricWith3SampleEvery10Seconds[60s:5s])` | 72 | **36** | 36 |
| `sum(…[60s:5s]) + sum(…[60s:5s])` | 144 | **72** | 72 |
| `sum_over_time(metricWith1SampleEvery10Seconds[30s:30s])` | 2 | **1** | 1 |
| `sum(max_over_time(metricWith3SampleEvery10Seconds[20s:10s]))` | 12 | **6** | 6 |

That is an exact 2× factor, and it compounds with nesting — the table pins `sum_over_time(m3[30s:10s])[2m:1m]` at `TotalSamples: 18, SamplesRead: 45` (2.5×) and `rate(histogram_sum(metricWith1HistogramEvery10Seconds)[2m:30s])` at `4` vs `56` (14×).

**The test table ratifies it.** Parsing all 97 `TestQueryStatistics` cases: **48 pin `SamplesRead > TotalSamples`**, and **38 of those are instant queries** — precisely the "other query types" the docs added in this same commit say must be equal. Since `TotalSamples` counts the full window at every step, it is by construction an over-count of I/O, so `SamplesRead <= TotalSamples` should hold unconditionally. One case even names the mechanism in its comment: `SamplesRead: 2, // subquery + outer`.

**Consequence:** `prometheus_engine_query_samples_read_total` exceeds `prometheus_engine_query_samples_total` on subquery-bearing workloads, inverting the "read ≤ loaded" relationship that is the only reason to have both counters, and `samplesRead` in an API response exceeds `totalQueryableSamples` in the same object.

**Fix:** pick one owner for subquery-derived points and record the choice. Minimal — stop re-counting the materialized matrix:

```go
parentSamplesStats.UpdatePeakFromSubquery(ev.samplesStats)
-parentSamplesStats.MergeSamplesReadFromSubquery(ev.samplesStats)
```

If the *raw* storage reads are the intended definition instead (the more useful one), keep the merge and suppress the outer attribution for selectors whose `Series` came from `evalSubquery` — e.g. a flag on the synthesized `VectorSelector`. Either branch requires re-deriving the ~46 affected expectations from the number of samples the fixture actually serves, and adding a loop-level `require.LessOrEqual(t, stats.Samples.SamplesRead, stats.Samples.TotalSamples)` so this cannot recur.

### #3 🟠 High: `countSamplesAfter` adds a full forward scan of the range-vector window per step per series, unconditionally — measured +61% wall-clock

| | |
|---|---|
| **File** | `promql/value.go:192-207`, called from `promql/engine.go:2164` |
| **Category** | performance — hot path |
| **Confidence** | 100 — measured |
| **Found by** | performance-reviewer (High), adversarial-reviewer (High), broad-reviewer (Medium), quick-reviewer (noted) |

**Issue:** `countSamplesAfter` iterates *all* of `floats` and *all* of `histograms` to count those with `T > cutoff`, once per step per series, inside the engine's hottest loop. The slices are timestamp-ascending and the counted set is always a strict suffix, so the answer is O(k) where k is the per-step delta (typically 1–4), not O(W) where W is the window size.

The cost is **unconditional**: it is gated by neither the `stats` request parameter nor `EnablePerStepStats`, because `SamplesRead` feeds the always-on `prometheus_engine_query_samples_read_total`. Every range query with a range-vector function on every Prometheus pays it by default. For range functions whose per-step body is O(1) — `absent_over_time`, `count_over_time`, `present_over_time`, `last_over_time`, `first_over_time` — this is an asymptotic change, not a constant factor: `matrixIterSlice` is amortized O(k) per step and the pre-change accounting was `len(floats) + totalHPointSize(histograms)`, i.e. O(1) for float-only series.

**Measurement** — the repo's own `BenchmarkRangeQuery/expr=absent_over_time(a_hundred[1d]),steps=1000`, `-benchtime 3x -count=3`, same machine, same session:

| variant | ns/op (3 runs) |
|---|---|
| HEAD (forward scan) | 639.1M, 634.0M, 635.0M |
| scan removed (isolates its cost) | 397.2M, 391.9M, 392.9M |
| reverse-scan fix applied | 394.4M, 390.0M, 393.5M |

The accounting scan is **~38% of total query time** on this case (+61% relative to the same query without it). The reverse-scan fix recovers essentially all of it, and `go test ./promql` passes in full with it applied — every existing `SamplesRead`/`SamplesReadPerStep` expectation is unchanged, so the sortedness assumption holds and the fix is behavior-preserving.

**Fix** (verified):

```go
// countSamplesAfter returns the number of sample equivalents with timestamp strictly
// after cutoff. floats and histograms are timestamp-ascending, so only the tail is new.
func countSamplesAfter(floats []FPoint, histograms []HPoint, cutoff int64) int64 {
	var n int64
	for i := len(floats) - 1; i >= 0 && floats[i].T > cutoff; i-- {
		n++
	}
	for i := len(histograms) - 1; i >= 0 && histograms[i].T > cutoff; i-- {
		n += int64(histograms[i].size())
	}
	return n
}
```

Better still: `matrixIterSlice` already knows the exact append count, so returning it removes both the scan and the fragile assumption that `maxt - ev.interval` equals the previous step's window edge (see #16). It also removes the third full pass over `histograms`, four lines after `totalHPointSize(histograms)` already walked the same slice.

### #4 🟠 High: subquery step-tracking allocation is sized by the subquery's own step count — unbounded by any validation and invisible to `query.max-samples`

| | |
|---|---|
| **File** | `promql/engine.go:2397`, via `util/stats/query_stats.go:306-308` |
| **Category** | resource exhaustion |
| **Confidence** | 100 — probe-confirmed by measurement |
| **Found by** | performance-reviewer (High), security-reviewer (High), design-reviewer (Medium) |

**Issue:** `stats.NewChildWithStepTracking(..., subqStart, subqEnd, subqInterval)` reaches `InitStepTracking`, which does `numSteps := int((end-start)/interval) + 1` and then `make([]int64, numSteps)` **twice**. `subqInterval` is the subquery step, which the parser only requires to be > 0 (i.e. 1ms), and `web/api/v1/api.go:631`'s 11,000-point rule applies **only to the outer `step`** — subquery resolution is validated nowhere. The allocation happens before any sample is read, so `query.max-samples` cannot bound it: that limit counts sample payload via `ev.currentSamples`, not bookkeeping.

Before this change the same path used `ev.samplesStats.NewChild()` → `NewQuerySamples(false)` → no per-step slice at all.

This is the hazard the same file already guards against elsewhere: `maxPointsSliceSize = 5000` (`promql/engine.go:74`) exists so that step-count-derived preallocation can never be driven by the query text. The new code reintroduces it with no clamp.

**Probe result** — instant query `count_over_time(m[1h:1ms])` (3.6M subquery steps), `runtime.MemStats` TotalAlloc delta:

| variant | allocated | query outcome |
|---|---|---|
| per-step stats OFF | 0.5 MiB | `ErrTooManySamples` |
| per-step stats ON (HEAD) | **55.4 MiB** | `ErrTooManySamples` |
| per-step ON, child forced non-tracking (emulates pre-change) | 0.5 MiB | `ErrTooManySamples` |

The query is *rejected* for too many samples and 55.4 MiB was allocated anyway — the limiter never sees it. The relation is linear in `numSteps`, so `[1d:1ms]` is ~1.4 GB and `[365d:1ms]` is far past any host's memory.

**Gating:** reached only with `--enable-feature=promql-per-step-stats` plus a client-supplied `stats=all` (`engine.go:603`; `extractQueryOpts` turns the request parameter directly into per-query `EnablePerStepStats`). That flag requirement is why this is High rather than Critical — but on a server with the flag on, the query text alone drives process-wide memory on an endpoint that is unauthenticated by default.

**Fix:** never size a structure from a subquery's own step count. The child's per-step data is only ever collapsed into outer step buckets by the merge at `:2426-2445`, so either allocate at the **outer** width and attribute at increment time, or clamp the child allocation and fall back to whole-query attribution — the `else` branch at `:2447` already implements exactly that fallback.

### #5 🟠 High: `samplesRead` is named, helped, and documented as "samples read (I/O)" but counts per-step selections — ~9× the physical reads in the most common query shape

| | |
|---|---|
| **File** | `promql/engine.go:427` (metric Help), `promql/engine.go:1818`/`:1841` (`evalSeries`), `util/stats/query_stats.go:279`, `web/api/v1/openapi_schemas.go:593-596` |
| **Category** | api-design — misleading permanent public metric |
| **Confidence** | 100 — probe-confirmed by execution |
| **Found by** | broad-reviewer (High), knowledge-reviewer (MUST) |

**Issue:** `evalSeries` increments `SamplesRead` once per *step per series*, so a stored point returned at several steps under lookback is counted several times. For the dominant query shape — a plain selector, or an aggregation over one, in a range query with step < scrape interval — `SamplesRead == TotalSamples` and both are step counts, not read counts.

**Probe result:** the range query `m` over 0→100s at 1s step, against a series at 10s resolution (11 stored samples in that interval), reports `TotalSamples=101, SamplesRead=101` — a 9.2× over-count of "I/O". At the 1s-step / 60s-scrape ratios real dashboards use the factor is 60×.

Meanwhile the counter is named `prometheus_engine_query_samples_read_total` with Help "The total number of samples read by all queries", `util/stats/query_stats.go:279` says "the number of samples read (**I/O**)", and the OpenAPI schema — shipped in both regenerated golden YAMLs, i.e. the contract clients generate against — says "Total number of samples read (I/O)."

Metric names and Help strings are effectively permanent; correcting this after release breaks every dashboard built on it. And because the new counter differs from the existing `query_samples_total` *only* for range-vector selectors, for most traffic it is a duplicate of an existing metric wearing a label for something it is not.

**Fix:** either narrow the claim in all four places (drop "(I/O)"; Help = "The total number of samples counted by all queries, counting each range-vector window point once per query step in which it first appears"), **or** make instant-vector selectors count real reads — `vectorSelectorSingle` already returns `origT`, so `evalSeries` can increment only when `origT` differs from the previously counted timestamp for that series. The first is docs-only; the second changes the numbers and needs the table regenerated. Regenerate both golden YAMLs either way.

### #7 🟠 High (pre-existing): `@` modifier is silently ignored, and step-invariance is misjudged, when an aggregation has a non-step-invariant `Param`

| | |
|---|---|
| **File** | `promql/engine.go:4310-4312` (`preprocessExprHelper`, `*parser.AggregateExpr` case) |
| **Category** | correctness — wrong query results |
| **Confidence** | 100 — probe-confirmed by execution |
| **Found by** | broad-reviewer (High) |
| **Pre-existing** | **yes** — introduced with the `@` modifier. Reported under `reach=wide` because it is a live defect in the step-invariance machinery this change extends (`engine.go:2450-2472`). |

**Issue:** the case calls `unwrapParenExpr(&n.Param)` but then `return preprocessExprHelper(n.Expr, start, end)` — `n.Param` is never preprocessed. So (a) an aggregation is judged step-invariant on `Expr` alone and evaluated **once** even when `Param` varies per step, and (b) `@ start()` / `@ end()` inside a `Param` never has its `Timestamp` resolved and is silently ignored.

**Probe result** (`k` = 1,2,3,3 at 10s steps; `m3` = 3 series; range query 0→30s at 10s step; series returned per step):

| query | got | expected |
|---|---|---|
| `topk(scalar(k), m3 @ 30)` | **1, 1, 1, 1** | 1, 2, 3, 3 |
| `topk(scalar(k), m3)` (control) | 1, 2, 3, 3 | 1, 2, 3, 3 |
| `topk(scalar(k @ start()), m3)` | **1, 2, 3, 3** | 1, 1, 1, 1 |
| `topk(scalar(k @ 0.000), m3)` (control) | 1, 1, 1, 1 | 1, 1, 1, 1 |

Wrong results, returned silently with no annotation, for legal PromQL. The controls isolate the `Param`-preprocessing gap as the cause.

**Fix:** preprocess `n.Param` too and wrap each side independently:

```go
case *parser.AggregateExpr:
	unwrapParenExpr(&n.Expr)
	unwrapParenExpr(&n.Param)
	isInvariantExpr, shouldWrapExpr := preprocessExprHelper(n.Expr, start, end)
	if n.Param == nil {
		return isInvariantExpr, shouldWrapExpr
	}
	isInvariantParam, shouldWrapParam := preprocessExprHelper(n.Param, start, end)
	if isInvariantExpr && isInvariantParam {
		return true, true
	}
	if shouldWrapExpr {
		n.Expr = newStepInvariantExpr(n.Expr)
	}
	if shouldWrapParam {
		n.Param = newStepInvariantExpr(n.Param)
	}
	return false, false
```

This changes the wrapped-AST shape, so it needs verifying against `promql/testdata/at_modifier.test` and `TestStepInvariantExpr`. A maintainer should confirm whether it belongs in this PR or a separate one — it is out of the change's blast radius.

### #8 🟡 Medium: outer-step attribution index overflows to negative on 32-bit builds — remotely reachable panic

| | |
|---|---|
| **File** | `promql/engine.go:2437`, with `util/stats/query_stats.go:352` |
| **Category** | availability |
| **Confidence** | 100 — probe-confirmed by execution under `GOARCH=386` |
| **Found by** | security-reviewer (Medium) |

**Issue:** `outerStep := int((tk - ev.startTimestamp + ev.samplesStats.Interval - 1) / ev.samplesStats.Interval)` computes an `int64` quotient and truncates it to `int`. For an instant query `InitStepTracking(start, start, 1)` (`engine.go:815`) makes `Interval == 1`, so the quotient is a raw millisecond difference. `EnableNegativeOffset` is set unconditionally (`cmd/prometheus/main.go:944`), so `subqEnd = ev.endTimestamp - offsetMillis` can exceed `ev.startTimestamp` by tens of days; past 2^31 ms (~24.9 days) the `int` truncation goes negative. The clamp at `:2439` guards only the **upper** bound, and `IncrementSamplesReadAtStep` likewise checks `i < len(...)` with no `i >= 0` (unlike its timestamp sibling at `:365`), so `SamplesReadPerStep[negative]` is written.

**Probe result** — instant query `sum_over_time(m[5m:1m] offset -30d)` with per-step stats on, query instant 30 days before the data:

| build | outcome |
|---|---|
| `GOARCH=amd64` (maxint 9.2e18) | no error; `samplesRead=10`, all clamped to step 0 |
| `GOARCH=386` (maxint 2.1e9) | `unexpected error: runtime error: index out of range [-1703207296]` |

Prometheus ships linux-386 and armv6/armv7 artifacts. `evaluator.recover` (`engine.go:1181`) converts the panic into a query error, so the impact is an HTTP 500 plus a stack trace in the server log per request — remotely driven query failure and log amplification, not a crash. Requires `--enable-feature=promql-per-step-stats` + `stats=all`, which is why this is Medium.

### #16 🟡 Medium: three load-bearing accounting decisions ship with mechanism-only comments and no recorded rationale or consequence

| | |
|---|---|
| **File** | `promql/engine.go:2160-2166`, `:2425`, `:2439`, `:2471` |
| **Category** | knowledge-preservation |
| **Confidence** | 75 — verified by reading |
| **Found by** | knowledge-reviewer (SHOULD ×2), broad-reviewer (Medium), design-reviewer (Medium) |

**Issue:** three policy choices are made here, each with a one-line comment stating *what* happens and never *why* or *at what cost*:

1. **The `maxt - ev.interval` cutoff.** This is correct only because every per-step adjustment to the window's right edge (`offset` at `:2151`, the `Smoothed` `maxt += lookbackDelta` at `:2159`) is step-independent, so consecutive windows overlap by exactly `ev.interval`. ## Specialist Notes

### Threat Model Notes (security-reviewer)

- **Trust boundary.** `/api/v1/query` and `/api/v1/query_range` are unauthenticated in a default deployment. Every input this change consumes is attacker-controlled: the PromQL text (subquery `range`, `step`, `offset`, `@`), the outer `start`/`end`/`step`, and the `stats` parameter — `extractQueryOpts` (`web/api/v1/api.go:600`) turns `stats=all` directly into per-query `EnablePerStepStats`, so the *client*, not the operator, decides whether the new per-step paths execute.
- **Gating.** All per-step paths additionally require `--enable-feature=promql-per-step-stats` (`engine.go:603`). Not a default — which is why #4 is High rather than Critical; with the flag on, its impact is process-wide availability, not one query.
- **Existing controls and where they stop.** `query.max-samples` (via `ev.currentSamples`) is the only memory bound in the engine and it counts *sample payload only*, so per-query bookkeeping allocations are invisible to it (#4 demonstrates this directly). `maxPointsSliceSize = 5000` exists precisely because the engine authors already decided step counts must never size an allocation. `query.max-concurrency` (default 20) multiplies rather than limits per-request memory. `evaluator.recover` converts index panics into 500s (#8); allocation failures are runtime throws and are **not** recoverable.
- **Resource-limit integrity: verified unaffected.** `UpdatePeakFromSubquery` still receives the same child in both `evalSubquery` and the `SubqueryExpr` case; `ev.currentSamples = newEv.currentSamples` propagation, the `> ev.maxSamples` checks, and `UpdatePeak` call sites are untouched. The two added `evalSeries` increments do not feed `currentSamples`. `PeakSamples` and `ErrTooManySamples` behavior is unchanged.
- **Information disclosure: no finding.** Any client that can pass `stats=` already receives `totalQueryableSamples` and, with the flag, `totalQueryableSamplesPerStep` — strictly finer-grained. `samplesRead` reveals nothing about storage layout, block boundaries, or series identity that per-step totals do not.
- **Counter monotonicity: no finding.** Every path feeding `SamplesRead` adds a non-negative count; `countSamplesAfter` cannot return negative, so `Counter.Add` never sees a negative value.

### Considered But Not Flagged (all agents)

Items examined and dismissed with reasoning that held up on review:

- **Division by zero on `ev.samplesStats.Interval` or `subqInterval`** (raised and dismissed independently by quick, adversarial, go, knowledge, security). The attribution branch is gated on `SamplesReadPerStep != nil`, which only `InitStepTracking` creates and which also sets a non-zero `Interval`; instant queries get `Interval: 1` (`engine.go:815`) and range queries a validated `step > 0`. The parser rejects non-positive durations (`generated_parser.y:510`), and the `subqStart` alignment division is byte-identical to the pre-change code. No new panic surface.
- **Negative or zero `numSteps` → `make` panic in `InitStepTracking`**, now that it is called with the *subquery* layout (adversarial, go, design, security all worked the arithmetic independently). `subqStart - subqEnd < subqInterval` always, so Go's truncating division yields 0 and `numSteps >= 1`. Safe — but only via a non-obvious argument; a defensive `max(numSteps, 1)` would make it locally evident.
- **`countSamplesAfter` cutoff correctness** for non-overlapping windows (`range < step`), sparse data, `offset`, and `anchored`/`smoothed`. Traced by adversarial, go, knowledge and broad independently and confirmed correct: `maxt` is read *after* the anchored/smoothed adjustment so the cutoff stays exactly one interval behind the previous adjusted `maxt`; for `range < interval` all window points are genuinely new. Only the cost (#3) and the unstated invariant (#16) survive.
- **`SamplesRead != sum(SamplesReadPerStep)` divergence being live.** Verified holding across all 97 table cases and 27 additional probe shapes. Latent only — recorded as #10/#15 rather than as a live defect.
- **`samplesRead` lacking `omitempty` while `samplesReadPerStep` has it.** Mirrors the existing `totalQueryableSamples` pair exactly, so it follows the convention rather than breaking it (design-reviewer; the downstream-embedder consequence is recorded as a residual risk under #17).
- **Feature-flag coupling of the *scalar* `samplesRead`.** Both branches of the `SubqueryExpr` merge add the same total (`SamplesRead += child.SamplesRead` in the `if`, `IncrementSamplesReadAtTimestamp` in the `else`), and every other increment site adds unconditionally. The scalar is flag-invariant; only the per-step distribution depends on the flag. Verified across 27 shapes.
- **Missed accounting sites.** Every `samplesStats.Increment*` call in `engine.go` was enumerated (`:1817/1818`, `:1840/1841`, `:2183/2184`, `:2424/2446`, `:2469/2472`, `:2577/2578`, `:2746/2747`) and all are paired; the `SubqueryExpr` and `StepInvariantExpr` cases use a deliberate different mechanism. No dimension unaccounted.
- **Missing CHANGELOG entry.** Checked before asserting: `git log -- CHANGELOG.md` shows it is edited **only** at release-cut commits, and 30 sampled feature commits touched it zero times. Not a convention here — asserting a violation would have been wrong.
- **OpenAPI / golden YAML drift, and `required` entries.** The new entries mirror the existing `totalQueryableSamples*` shape in description style, `MinItems`/`MaxItems`, nested `Items` description and absence of a `format`; both goldens are regenerated consistently and `TestOpenAPI` passes. The `samples` object declares no `required` list, so an always-emitted field introduces no schema/response mismatch. (The *content* of the new descriptions is #5.)
- **Web UI types.** `web/ui` does not consume the samples stats — grepped for `totalQueryableSamples`; nothing to update.
- **Doc link and anchor style.** `../feature_flags.md#per-step-stats` matches `docs/querying/functions.md`; both that anchor and `#query-statistics` resolve against real headings. The long single-line bullets are not a violation — the file has no consistent wrap convention to deviate from.
- **`countSamplesAfter`'s placement in `promql/value.go`.** Its sibling `totalHPointSize` already lives there and it operates purely on `[]FPoint`/`[]HPoint`. Consistent with the existing seam.
- **Slice aliasing between `countSamplesAfter` and `call(...)`.** Both counts are computed at `:2160-2165`, immediately after `matrixIterSlice` and *before* `call(...)` at `:2181`. No aliasing or reuse hazard.
- **`HPoint.size()` cost.** Verified O(1) (`model/histogram/float_histogram.go:648` sums `len()` of five slices plus a constant), so the cost inside `countSamplesAfter` is the traversal, not the elements — folded into #3.
- **Second `Counter.Add` in `exec`'s defer.** One uncontended atomic add per query. Negligible; explicitly not a finding.
- **`int64` → `int` truncation on 64-bit.** Bounded by step count; no realistic truncation. (32-bit is #8.)
- **Struct field ordering / alignment** in `querySamples`. `.golangci.yml` enables `govet` but not `fieldalignment`, and the new `[]stepStat`/`int64` pair adds no padding on 64-bit. The `stats_test.go` JSON regexps are order-insensitive.
- **`SamplesReadPerStepMap` / `samplesReadPerStepPoints` used only from tests.** The pre-existing `TotalSamplesPerStepMap` has the same property — an established test-accessor pattern, not new dead API.
- **Goroutines, channels, context.** The change adds and touches none.
- **`e.Args[i] = val` AST mutation and the `defer` inside the `e.Args` loop** (`engine.go:2009`, `:2011`). Pre-existing, bounded (the loop `break`s immediately), untouched.
- **Nested-subquery exponential blowup.** Traced: each nesting level adds exactly one materialized-matrix delta, linear per level, not multiplicative. Already covered by #2.
- **`NewChild` / `NewChildWithStepTracking` naming incoherence beyond readability.** Real but no nameable consequence was found; recorded in the Minor/Consistency bucket rather than as a primary finding.

Nothing was suppressed by the confidence gate: under `evidence=any` every cluster above score 25 is carried, and no cluster scored below it.

### Positive observations

Worth recording, because two of these are load-bearing and unusually well done:

- **The per-step-disabled re-run in the test harness** (`engine_test.go:2435-2441`) — re-running every case with per-step stats off and asserting the totals match — is exactly the right guard for this feature, and is why the enabled/disabled paths agree across all 97 table cases and 27 additional probe shapes. Very few stats features get this.
- **The core delta arithmetic is genuinely correct and genuinely pinned.** Neutralizing the `step == 0` / `countSamplesAfter` branch fails 17 cases; flipping `countSamplesAfter`'s `>` to `>=` fails 9; deleting the `StepInvariantExpr` read increment fails 10. The non-obvious cases — `mint`/`maxt` adjustment for `anchored`/`smoothed`, non-overlapping windows, `offset`, native-histogram sizing via `HPoint.size()` — all check out by hand.
- `StepTrackingEnabled()`'s nil-receiver tolerance is load-bearing and correctly placed for its `engine.go:2397` call site.
- The `TotalSamples`/`TotalSamplesPerStep` doc comments were sharpened ("loaded" vs "scanned", plus the explicit multi-step note) — a real readability gain independent of the feature.
- The docs additions are unusually thorough for a stats change (a new `### Query statistics` section, an expanded per-step section, both counters named with their differing semantics). The problem is that the code does not match them (#5, #9) — not that they are absent.
