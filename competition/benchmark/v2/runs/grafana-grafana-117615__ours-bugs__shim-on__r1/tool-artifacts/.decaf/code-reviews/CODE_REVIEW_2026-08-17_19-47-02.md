### #1 🟠 High: `quoteIdentifierIfNecessary(vars[0])` throws a `TypeError` when the SQL expression is the only query

| | |
|---|---|
| **File** | `public/app/features/expressions/components/SqlExpressions/SqlExpr.tsx:81` |
| **Category** | correctness |
| **Confidence** | 75 |
| **Verified** | executed |
| **Pre-existing** | no |
| **Found by** | solo-reviewer (High) |

**Issue:** `vars` is `refIds.map((v) => v.value!)` (`SqlExpr.tsx:61`), and `refIds` is built by excluding the current query (`ExpressionQueryEditor.tsx:118`, `alerting/.../Expression.tsx:101-103`). When no other query exists, `refIds` is `[]` and `vars[0]` is `undefined`. `isValidIdentifier` (`public/app/plugins/datasource/mysql/sqlUtil.ts:52-56`) evaluates `RESERVED_WORDS.includes(identifier.toUpperCase())` **unconditionally**, which throws on `undefined`. `initialQuery` is computed in the component body on every render (`SqlExpr.tsx:78-83`), so the throw happens during render.

Before the change the same state produced the harmless string `SELECT * FROM undefined LIMIT 10`. The `v.value!` non-null assertion means TypeScript cannot catch this (`tsconfig.json` has `strict` but not `noUncheckedIndexedAccess`).

**Evidence:** Executed a faithful copy of `isValidIdentifier`/`quoteIdentifierIfNecessary`:

```
OLD template with undefined: FROM undefined
NEW throws: TypeError - Cannot read properties of undefined (reading 'toUpperCase')
```

Reachability traced: `QueryEditorRows.onRemoveQuery` (`public/app/features/query/components/QueryEditorRows.tsx:53-55`) simply filters the query out with no guard against removing the last data query, and the trash-can action at `QueryEditorRow.tsx:457-462` is rendered unconditionally. Deleting the last data query from a panel that still contains a SQL expression re-renders `SqlExpr` with `refIds === []` and throws.

**Fix:** Guard the value before quoting, e.g. `const firstVar = vars[0] ?? ''` and skip quoting when empty (`''` also produces a bare `` `` `` pair — see #5), or make `isValidIdentifier` defensive. Add a test rendering `SqlExpr` with `refIds={[]}`.

### #2 🟠 High: Backtick-quoted table names are mis-parsed by the alerting DAG, breaking expression→query links

| | |
|---|---|
| **File** | `public/app/features/expressions/components/SqlExpressions/SqlExpr.tsx:81` |
| **Category** | correctness |
| **Confidence** | 75 |
| **Verified** | executed |
| **Pre-existing** | no |
| **Found by** | solo-reviewer (High) |

**Issue:** The generated expression text is parsed back into refIds by `parseRefsFromSqlExpression` (`public/app/features/alerting/unified/components/rule-editor/dag.ts:121`) to build the alert rule's DAG. Its `cleanTableName` helper (`dag.ts:194-212`) strips `'`, `"`, `(`, `)` — **but not backticks** — and then splits on the first space. So the newly emitted `` FROM `my-query` `` yields the ref `` `my-query` ``, which is not a node in the graph. `Graph.link` throws `cannot link input node named ... since it doesn't exist in graph` (`public/app/core/utils/dag.ts:170-177`), `createDagFromQueries` collects it into a `DAGError` (`dag.ts:53-59`), and `createDAGFromQueriesSafe` responds by *rejecting the SQL expression query entirely* from the graph (`dag.ts:63-69`).

This is a regression, not merely an unfixed case. Query names are freely user-editable — `QueryEditorRowHeader` (`public/app/features/query/components/QueryEditorRowHeader.tsx:35-70`) validates only non-empty and uniqueness. For any refId that `quoteIdentifierIfNecessary` decides to quote but that contains **no space** (e.g. `my-query`, `2024`, or a MySQL reserved word such as `left`), the DAG worked before the change and breaks after it. Downstream, `findDataSourceFromExpression` (`.../query-and-alert-condition/reducer.ts:35-38`) calls the throwing `createDagFromQueries` with no `try`/`catch`.

**Evidence:** Executed a faithful replica of `cleanTableName` + the `fromRegex` from `dag.ts:143` against the exact `initialQuery` template:

```
old my-query           ["my-query"]      <- node exists, link succeeds
new my-query           ["`my-query`"]    <- node missing, graph.link throws
old gdp per capita     ["gdp"]
new gdp per capita     ["`gdp"]
old A                  ["A"]             <- unchanged, common case unaffected
```

The same applies to names inserted via the completion provider (`sqlCompletionProvider.ts:27`).

**Fix:** Teach `cleanTableName` to strip/handle backtick-quoted identifiers (including quoted names containing spaces, which it currently truncates at the first space) as part of this change — otherwise the stated goal, "support table names with spaces", is not achieved for alert rules even when the SQL itself is now valid.

**Issue:** Both new imports (`SqlExpr.tsx:13` and `sqlCompletionProvider.ts:9`) reach into `app/plugins/datasource/mysql/sqlUtil`. That directory is a **separately-built, separately-tested Yarn workspace** (`@grafana-plugins/mysql`, `public/app/plugins/datasource/mysql/package.json`; listed under `workspaces` in the root `package.json`; excluded from core Jest via `jest.config.js:90`; named in the "decoupled plugins" eslint block at `eslint.config.js:463`). The repo explicitly enforces the reverse direction — `eslint.config.js:479-492` forbids these plugins from importing core — but has no rule for core → plugin, so this passes lint while inverting the intended dependency direction.

Consequences: (a) `sqlUtil.ts` is a plugin internal with no public-API contract, so a MySQL-squad change to `RESERVED_WORDS` or `isValidIdentifier` silently changes SQL-expression behavior; (b) when the mysql plugin is extracted from the core repo — the stated purpose of decoupling — the core build breaks; (c) the module's `RESERVED_WORDS` list is explicitly "Copied from MySQL 8.0.31 INFORMATION_SCHEMA.KEYWORDS" (`sqlUtil.ts:73-75`), which is a different engine from the SQL-expressions backend (dolthub/vitess + go-mysql-server, see `pkg/expr/sql/parser.go:9`).

**Evidence:** Read `public/app/plugins/datasource/mysql/package.json` (own workspace, own deps, own `jest.config.js`), `jest.config.js:80-94` ("Decoupled plugins run their own tests so ignoring them here"), and `eslint.config.js:450-492`. Existing `app/plugins/...` imports from `public/app/features` are almost entirely type-only or shared constants (`MIXED_DATASOURCE_NAME`); this is behavioral logic.

**Fix:** Move the helper into a location core owns — e.g. next to the existing local copy in `public/app/features/expressions/utils/metaSqlExpr.ts` (see #6) or into `@grafana/sql` — and have both the expressions code and, if desired, the mysql plugin consume it from there.

### #5 🟢 Low: Backticks inside an identifier are not escaped, producing malformed SQL

| | |
|---|---|
| **File** | `public/app/features/expressions/components/SqlExpressions/SqlExpr.tsx:81` |
| **Category** | correctness |
| **Confidence** | 100 |
| **Verified** | executed |
| **Pre-existing** | no |
| **Found by** | solo-reviewer (Low) |

**Issue:** `quoteIdentifierIfNecessary` (`public/app/plugins/datasource/mysql/sqlUtil.ts:44-46`) wraps the value in backticks without doubling any backtick it already contains, which is what MySQL quoting requires. Query names are user-editable with only non-empty/unique validation (`QueryEditorRowHeader.tsx:52-69`), so a name such as ``a`b`` now yields ``FROM `a`b` `` — an unbalanced quoted identifier that the backend parser rejects. The same value is the only thing separating a user-authored query name from generated SQL at all three call sites (`SqlExpr.tsx:81`, `sqlCompletionProvider.ts:27`, `metaSqlExpr.ts:15`).

**Evidence:** Executed the helper: ``quoteIdentifierIfNecessary('a`b')`` → `` `a`b` `` (not `` `a``b` ``). Also `quoteIdentifierIfNecessary('')` → `` `` `` (an empty backtick pair), relevant to the `|| ''` fallbacks at `sqlCompletionProvider.ts:26-27` and to #1.

**Fix:** Escape before wrapping: `` `\`${value.replace(/`/g, '``')}\`` ``. Since #3 recommends owning this helper in core anyway, fix it there.

**Issue:** The change routes identifiers through `quoteIdentifierIfNecessary` from `app/plugins/datasource/mysql/sqlUtil` at the other two call sites, but no import was added to `metaSqlExpr.ts` — line 15 resolves to the **file-local** helper at `metaSqlExpr.ts:114-116`, which is `/^[a-zA-Z_][a-zA-Z0-9_$]*$/` only, with **no reserved-word check**. The two predicates therefore disagree. For a query named e.g. `Values`, `Left`, or `Rank`, the editor text becomes `` FROM `Values` `` while the column-autocomplete meta query becomes `SELECT * FROM Values LIMIT 1` — a parse error on the backend, swallowed by the `catch { return []; }` at `sqlCompletionProvider.ts:39-41`, so column autocomplete silently returns nothing with no user-visible reason.

**Evidence:** `grep -rn "quoteIdentifierIfNecessary" public packages` shows `metaSqlExpr.ts` has no import of the symbol; the only definition in scope is the local one at line 114. Read both predicates side by side.

**Fix:** Use one helper for all three sites (in a core-owned location per #3) and delete the duplicate.
