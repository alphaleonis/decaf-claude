### #1 🔴 Critical: `quoteIdentifierIfNecessary(vars[0])` throws when the SQL expression has no other query to reference

| | |
|---|---|
| **File** | `public/app/features/expressions/components/SqlExpressions/SqlExpr.tsx:81` |
| **Category** | null-safety |
| **Confidence** | 100 |
| **Verified** | Yes — reproduced with a temporary jest render; stack trace below |
| **Found by** | quick-reviewer (Critical), broad-reviewer (Critical), adversarial-reviewer (High) |

**Issue:** `vars` is `refIds.map((v) => v.value!)` (`SqlExpr.tsx:61`), and both call sites build `refIds` by excluding the expression itself — `ExpressionQueryEditor.tsx:118` (`queries!.filter((q) => query.refId !== q.refId)`) and `Expression.tsx:101-103`. When the SQL expression is the only query left (the user deletes the data query — `QueryEditorRows.onRemoveQuery` at `public/app/features/query/components/QueryEditorRows.tsx:53` has no guard against removing the last one), `refIds` is `[]` and `vars[0]` is `undefined`. The `!` in `v.value!` is a compile-time assertion only.

`quoteIdentifierIfNecessary` (`public/app/plugins/datasource/mysql/sqlUtil.ts:44`) calls `isValidIdentifier`, which does `identifier.toUpperCase()` unconditionally at `sqlUtil.ts:54` — a `TypeError` on `undefined`. Because `initialQuery` is computed in the component body, the throw happens during React render.

Before this change the same position was a plain interpolation (`${vars[0]}`), which stringified to `"undefined"` — wrong SQL, but no crash. The change converts a benign edge case into an unhandled render-time exception.

Reproduced (temporary untracked test, since removed; working tree verified byte-identical afterwards):

```
TypeError: Cannot read properties of undefined (reading 'toUpperCase')
  at isValidIdentifier (public/app/plugins/datasource/mysql/sqlUtil.ts:54:61)
  at quoteIdentifierIfNecessary (public/app/plugins/datasource/mysql/sqlUtil.ts:45:10)
  at SqlExpr (public/app/features/expressions/components/SqlExpressions/SqlExpr.tsx:81:31)
  at renderWithHooks (node_modules/react-dom/cjs/react-dom.development.js:15486:18)
```

**Fix:** guard the value at the call site, mirroring the `|| ''` pattern the same change already uses in `sqlCompletionProvider.ts:26-27`:

```ts
const table = vars[0] ?? '';
const initialQuery = `SELECT
  *
FROM
  ${table && quoteIdentifierIfNecessary(table)}
LIMIT
  10`;
```

(or make `isValidIdentifier` defensive — but that helper is shared with the MySQL datasource and outside this changeset's ownership.)

### #2 🟠 High: The backticked `FROM` target is not understood by the alerting DAG parser, so the SQL expression stops being evaluated

| | |
|---|---|
| **File** | `public/app/features/expressions/components/SqlExpressions/SqlExpr.tsx:81` |
| **Category** | correctness — cross-component cascade |
| **Confidence** | 100 |
| **Verified** | Yes — parser output reproduced by probe; chain re-verified by an independent validator |
| **Found by** | adversarial-reviewer (High) |

**Issue:** Alerting rebuilds the rule's dependency graph by re-parsing the SQL text. `parseRefsFromSqlExpression` (`public/app/features/alerting/unified/components/rule-editor/dag.ts:121`) hands the `FROM` clause to `cleanTableName` (`dag.ts:196-212`), which strips `['"()]` — **not backticks**. Measured output (probe, tree restored clean):

| editor text | parsed refs | linkable? |
|---|---|---|
| ``FROM `left` `` | `["`left`"]` | ❌ no such node |
| ``FROM `gdp per capita` `` | `["`gdp"]` | ❌ no such node |
| `FROM left` (pre-change) | `["left"]` | ✅ |
| `FROM A` | `["A"]` | ✅ |

An unresolvable target makes `graph.link(target, source)` throw at `dag.ts:31-38`; the collected `DAGError` (`dag.ts:41`) causes `createDAGFromQueriesSafe` (`dag.ts:52-70`) to reject the SQL expression query, and `AlertingQueryRunner.prepareQueries` (`state/AlertingQueryRunner.ts:119, 128-134`) then excludes it from `queriesToRun`, with `run()` (`AlertingQueryRunner.ts:76-79`) overwriting its result with a link-error panel. The expression is never evaluated in the rule preview.

Two distinct consequences, both confirmed:

1. **Regression.** RefIds that need quoting but contain no space — MySQL reserved words from `sqlUtil.ts` `RESERVED_WORDS` (`LEFT`, `VALUES`, `RANK`, `ROW`, …), or names with `-`, `.`, or a leading digit — previously produced a linkable ref and now do not. Reachability confirmed: the alerting refId rename input (`Expression.tsx:390-398`, `QueryAndExpressionsStep.tsx:237`) validates only non-emptiness and uniqueness, never the character set, so `LEFT` or `cpu-usage` are legal refIds today.
2. **The stated bug is not fixed on the alerting path.** For the space-containing refIds this PR targets, the DAG yielded a broken ref before (`gdp`) and still does after (`` `gdp ``) — quoting the identifier does not make the alerting expression run.

**Fix:** land the parser change with this one — teach `cleanTableName` (or `parseRefsFromSqlExpression`) to unquote backticked identifiers and not to split on spaces inside them:

```ts
function cleanTableName(tableName: string): string {
  let name = tableName.replace(/['"()]/g, '');
  const backticked = name.match(/^`([^`]*)`/);
  if (backticked) {
    return backticked[1].trim();
  }
  // …existing alias/space/schema handling
}
```

Anchored at `SqlExpr.tsx:81` because that is the changed line that starts emitting backticks; the repair belongs in `dag.ts`.

### #4 🟡 Medium: `fetchSQLFields` never unquotes the identifier it reads back from the editor, so column autocomplete builds a garbage meta query

| | |
|---|---|
| **File** | `public/app/features/expressions/utils/metaSqlExpr.ts:15` (and `:20`) |
| **Category** | correctness — round-trip composition |
| **Confidence** | 100 |
| **Verified** | Yes — confirmed by an independent validator against the installed `monaco-editor` and `@grafana/plugin-ui` sources |
| **Found by** | quick-reviewer (High, plus a separate Medium for the `:20` filter), adversarial-reviewer (Medium) |

**Issue:** the change makes the editor text contain backticked identifiers, but the read-back path was not updated. Column autocomplete extracts the table name from the editor: `@grafana/plugin-ui` `SQLEditor.js:278-280` calls `getTableToken` then `defaultTableNameParser`, and the expressions provider supplies no custom `tables.parseName`. Monaco's MySQL Monarch grammar (`monaco-editor/esm/vs/basic-languages/mysql/mysql.js:866-870`) emits the opening backtick as its **own** token (`identifier.quote`), and `getTableToken` (`tokenUtils.js:13-24`) only rejects variables and `keyword(` — so it returns that lone backtick, and `defaultTableNameParser` yields `{ table: '`' }`.

That value reaches `fetchSQLFields` via `SqlExpr.tsx:357`. Nothing unquotes it:

- `metaSqlExpr.ts:15` re-wraps it → `` SELECT * FROM `` ` `` LIMIT 1 `` — invalid SQL;
- `metaSqlExpr.ts:20` `queries.filter((q) => q.refId === query.table)` matches nothing, so the meta query is sent with empty query context.

The failure is silent: `sqlCompletionProvider.ts:36-41` wraps the call in `try { … } catch { return []; }`, so the user just gets no column suggestions. The sibling MySQL datasource solves exactly this with `quoteIdentAsLiteral = quoteLiteral(unquoteIdentifier(value))` (`mySqlMetaQuery.ts:38-39`).

**Scope note (from validation):** the path is gated on `config.featureToggles.sqlExpressionsColumnAutoComplete`, which `pkg/services/featuremgmt/registry.go:878-884` declares Experimental with `Expression: "false"` (default off). The validator also traced pre-change behavior and found **no** table name for which this path worked before and is broken now — unquoted `gdp per capita` already extracted the wrong token. So this is the PR's fix being incomplete at a line it changed, not a regression against working behavior; that is why it is Medium rather than High despite quick-reviewer's rating.

**Fix:**

```ts
import { quoteIdentifierIfNecessary, unquoteIdentifier } from 'app/plugins/datasource/mysql/sqlUtil';

const table = unquoteIdentifier(query.table);
const queryString = `SELECT * FROM ${quoteIdentifierIfNecessary(table)} LIMIT 1`;
// …
queries.filter((q) => q.refId === table)
```

Note this only helps once the token actually carries the full quoted name; a `tables.parseName` override on the completion provider is likely needed alongside it.

### #5 🟡 Medium: The new call at `metaSqlExpr.ts:15` resolves to the file's own weaker quoting helper, not the one the other two call sites import

| | |
|---|---|
| **File** | `public/app/features/expressions/utils/metaSqlExpr.ts:15` |
| **Category** | correctness / convention divergence |
| **Confidence** | 100 |
| **Verified** | Yes — quotable fact; `metaSqlExpr.ts` adds no import, and defines the symbol locally at line 114 |
| **Found by** | broad-reviewer (High), adversarial-reviewer (Medium) |

**Issue:** `sqlCompletionProvider.ts` and `SqlExpr.tsx` both added `import { quoteIdentifierIfNecessary } from 'app/plugins/datasource/mysql/sqlUtil'`. `metaSqlExpr.ts` did not — its new call at line 15 binds to the module-private copy at `metaSqlExpr.ts:114-116`:

```ts
function quoteIdentifierIfNecessary(value: string) {
  return /^[a-zA-Z_][a-zA-Z0-9_$]*$/g.test(value) ? value : `\`${value}\``;
}
```

The shared version additionally rejects MySQL reserved words (`sqlUtil.ts:52-56`, `RESERVED_WORDS`). So for a refId that is a legal bare identifier but a reserved word — `values`, `left`, `rank`, `row` — the three call sites now disagree: the editor text and the completion say `` `values` ``, while the meta query says `SELECT * FROM values LIMIT 1`, which the backend parser rejects. The new test `metaSqlExpr.test.ts` cannot catch this because it only exercises the space case, where both implementations agree.

Same reachability caveat as #4: this path is behind the default-off `sqlExpressionsColumnAutoComplete` toggle, and the failure is swallowed by the same `catch { return [] }` — which is why it is Medium rather than broad-reviewer's High.

**Fix:** import the shared helper in `metaSqlExpr.ts`, delete the local copy at lines 114-116, and point the column-name call at line 29 at the imported one too, so all quoting decisions in the feature go through one implementation.
