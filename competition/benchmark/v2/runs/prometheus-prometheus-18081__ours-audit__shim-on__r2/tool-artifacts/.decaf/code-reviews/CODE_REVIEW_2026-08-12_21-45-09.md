### #1 🔴 Critical: `@`-modifier reuse steps silently stop counting toward `TotalSamples`, changing an existing public metric

| | |
|---|---|
| **File** | `promql/engine.go:2145` (declaration), `promql/engine.go:2160` (assignment), `promql/engine.go:2183` (effect) |
| **Category** | correctness / regression in pre-existing public contract |
| **Confidence** | 100 — A/B probe (Probe 1) |
| **Found by** | design-reviewer (Critical), broad-reviewer (High), adversarial-reviewer (High), go-reviewer (High), security-reviewer (High), knowledge-reviewer (MUST), test-reviewer (High), quick-reviewer (High) |

**Issue:** `var fullWindowCount, samplesReadCount int64` is declared *inside* the per-step loop at line 2145 and assigned **only** inside the `if ts == ev.startTimestamp || selVS.Timestamp == nil` block. When an `@` modifier makes the loop reuse the previous step's window, that block is skipped and `fullWindowCount` stays at its zero value, so line 2183 executes `IncrementSamplesAtStep(step, 0)`.

The pre-change code (`git show efbdc3f88:promql/engine.go`, same site) computed the count **outside** the block, from the retained `floats`/`histograms`, and incremented on every step.

`TotalSamples` feeds `totalQueryableSamples` in the `/api/v1/query{,_range}` response and the long-standing `prometheus_engine_query_samples_total` counter — a signal downstream systems (Cortex/Mimir/Thanos per-tenant cost accounting, capacity alerts) build on. This change is not mentioned in the docs or the commit message, and the inline comment at line 2143 asserts the opposite: `// Full window count for TotalSamples (unchanged semantics)`.

**Reachability is not theoretical.** `preprocessExprHelper` returns `shouldWrap = false` for `*parser.MatrixSelector` (`promql/engine.go:4364`, *"functions over range vectors evaluate those directly"*), and a `Call` whose function is in `AtModifierUnsafeFunctions` is never step-invariant. So `predict_linear(foo[60s] @ 30, 60)` reaches this loop multi-step with `selVS.Timestamp != nil`. `quantile_over_time(scalar(bar), foo[60s] @ 30)` gets there by a second route (non-step-invariant first argument). The `@` modifier is unconditionally enabled (`cmd/prometheus/main.go`), so no feature flag gates this.

Probe 1 measured **16 → 4** with per-step going from `[4 4 4 4]` to `[4 0 0 0]`. No test in the +1131 lines covers it — `grep predict_linear promql/engine_test.go` returns nothing, and the existing `@` case at `engine_test.go:1352` takes the `StepInvariantExpr` path, which is unaffected.

**Fix:** Keep `TotalSamples` byte-for-byte as before; gate only the new counter.

```go
var samplesReadCount int64
if ts == ev.startTimestamp || selVS.Timestamp == nil {
    ...
    floats, histograms = ev.matrixIterSlice(it, mint, maxt, floats, histograms)
    if step == 0 {
        samplesReadCount = int64(len(floats) + totalHPointSize(histograms))
    } else {
        samplesReadCount = countSamplesAfter(floats, histograms, maxt-ev.interval)
    }
}
...
ev.samplesStats.IncrementSamplesAtStep(step, int64(len(floats)+totalHPointSize(histograms)))
ev.samplesStats.IncrementSamplesReadAtStep(step, samplesReadCount)
```

Add a `TestQueryStatistics` case for `predict_linear(metricWith1SampleEvery10Seconds[60s] @ 30, 60)` over a multi-step range pinning `TotalSamplesPerStep`. If the reduction *is* intended, it is a separate breaking change needing its own justification, docs, and an update to the `TotalSamplesPerStep` doc comment at `util/stats/query_stats.go:271-275`, which currently documents the opposite contract ("we intentionally do not account for optimizations … that reduce the actual work").

### #2 🔴 Critical: `SamplesRead` is double-counted for every range-vector function over a subquery

| | |
|---|---|
| **File** | `promql/engine.go:1874` (merge) + `promql/engine.go:2184` (re-count) |
| **Category** | correctness / data integrity |
| **Confidence** | 100 — isolating probe (Probe 2) |
| **Found by** | design-reviewer (Critical), test-reviewer (Critical), broad-reviewer (High), adversarial-reviewer (High), go-reviewer (High), knowledge-reviewer (MUST) |

**Issue:** `evalSubquery` now merges the subquery child's `SamplesRead` into the parent (`parentSamplesStats.MergeSamplesReadFromSubquery(ev.samplesStats)`). The change also **deleted** the comment that explained why the old code discarded the child:

> `// Avoid double counting samples when running a subquery, those samples will be counted in later stage.`

That "later stage" still runs. `evalSubquery` returns a synthetic `MatrixSelector` over the *materialized, in-memory* subquery result, and the ordinary range-vector loop then counts those same points again at line 2184. `TotalSamples` still avoids this (it never merges the child); `SamplesRead` no longer does, and is counted twice.

Probe 2 confirms: `max_over_time(m[60s:5s])` reports `SamplesRead=72` against `TotalSamples=36` — there are only 36 samples to be had — and removing *only* the merge line drops it to 36. The bare subquery `m[60s:5s]` (which does not go through `evalSubquery`) correctly reports 36/36.

This is the most common subquery shape and exactly the case the feature exists to measure. `prometheus_engine_query_samples_read_total` is a **counter**, so the inflation is written permanently into TSDB history and cannot be distinguished from real load after a later fix.

**The new tests encode the doubling rather than catching it** — `promql/engine_test.go:1184` (`SamplesRead: 72` vs `TotalSamples: 36`), `:1197` (`144` vs `72`), and ~46 further rows assert `SamplesRead > TotalSamples`, including on **instant** queries where a single step makes the delta optimization impossible by construction.

**Fix:** Pick one owner for subquery samples-read. Either drop the merge in `evalSubquery` and let the outer loop's delta accounting stand, or keep the merge and suppress `IncrementSamplesReadAtStep` in the range-vector loop when the matrix argument came from `evalSubquery` (a flag set where the subquery is replaced, ~`engine.go:2008`). Then rewrite the affected expectations and add a table-wide invariant guard:

```go
require.LessOrEqual(t, stats.Samples.SamplesRead, stats.Samples.TotalSamples)
require.Equal(t, c.SamplesRead, sumOf(c.SamplesReadPerStep))
```

### #3 🔴 Critical: unbounded per-step allocation on the subquery path — remote memory-exhaustion lever

| | |
|---|---|
| **File** | `util/stats/query_stats.go:306` (allocation), reached from `promql/engine.go:2397` and `promql/engine.go:1869` |
| **Category** | resource exhaustion / availability |
| **Confidence** | 100 — measured A/B (Probe 3) |
| **Found by** | adversarial-reviewer (Critical), security-reviewer (Critical), broad-reviewer (High), go-reviewer (High) |

**Issue:** `InitStepTracking` does `make([]int64, numSteps)` **twice** with `numSteps := int((end-start)/interval) + 1`. This change newly reaches it from subquery evaluation via `NewChildWithStepTracking`, sized by the **subquery's own** `[range:step]` — values taken verbatim from the query string. The pre-existing `NewChild()` allocated nothing.

Nothing bounds a subquery's step count:
- the 11,000-point guard at `web/api/v1/api.go:631` bounds only the **outer** range query;
- `-query.max-samples` is enforced against `ev.currentSamples` *during* evaluation, so it cannot fire before the `make`;
- the engine's own precedent for step-derived preallocation, `maxPointsSliceSize = 5000` (`promql/engine.go:74`), is not applied here.

Probe 3 measured exactly 16 B per subquery step, linear, zero at base — and every probe query **returned successfully in milliseconds** with `-query.max-samples=100`, confirming the allocation precedes any limit check. Extrapolating the measured constant: `[1d:1ms]` ≈ 1.4 GB, `[30d:1ms]` ≈ 41 GB, per request, from a query that returns an empty result and therefore looks free in the query log. A Go allocation failure of that size is `fatal error: runtime: out of memory` — a `throw`, not a recoverable panic, so `evaluator.recover` does not catch it.

**Gating:** requires `--enable-feature=promql-per-step-stats` **and** `stats=all`. That is a real mitigation, but it is a documented, production-used flag (it is what Grafana's query inspector relies on), and the Prometheus HTTP API is very commonly exposed without authentication.

**Fix:** Bound the arrays before allocating — skip per-step tracking for a subquery child whose `numSteps` exceeds an explicit cap (the 11,000-point API convention, or the outer query's step count) and fall back to totals-only. The `else` branch at `engine.go:2446` already handles a child with no per-step array, so the fallback is exercised code. Also guard `numSteps <= 0`.

```go
const maxStepTrackingSteps = 11000 // matches the API range-query resolution limit

func NewChildWithStepTracking(enablePerStepStats bool, start, end, interval int64) *QuerySamples {
	qs := NewQuerySamples(enablePerStepStats)
	if enablePerStepStats && int((end-start)/interval)+1 <= maxStepTrackingSteps {
		qs.InitStepTracking(start, end, interval)
	}
	return qs
}
```

**Issue:** Four independent artifacts state the same claim — *"For other query types, this equals totalQueryableSamples"* / *"elsewhere it equals TotalSamples"* — and the code satisfies it in neither direction:

### #5 🟠 High: `countSamplesAfter` adds an unconditional O(window) scan to the innermost PromQL loop

| | |
|---|---|
| **File** | `promql/value.go:195`, called from `promql/engine.go:2164` |
| **Category** | performance |
| **Confidence** | 100 |
| **Found by** | performance-reviewer (High), broad-reviewer (Medium), design-reviewer (Medium), security-reviewer (Medium) |

**Issue:** `countSamplesAfter` scans **all** of `floats` and `histograms` front-to-back to count the usually-tiny suffix of new points. It runs once per series per step, in the hottest loop of the engine, and it is **not gated on stats being requested** — `SamplesRead` feeds the always-registered `query_samples_read_total` counter (`engine.go:686`), so every query on every server pays it. The pre-existing line computed `len(floats)` in O(1) for the float-only case.

Both slices are strictly time-ordered and `cutoff = maxt - ev.interval` is exactly the previous step's `maxt`, so only trailing points can qualify — the answer is obtainable in O(new points).

Scale, using shapes already in `BenchmarkRangeQuery` (10s scrape, 1 day of data): `rate(a_hundred[1d])` at 1000 steps is 100 series × 1000 steps × 8640 window points ≈ **8.6 × 10⁸** added comparisons. Worse, this is an *asymptotic* regression, not a constant factor, for the O(1)-per-step range functions — `last_over_time`, `first_over_time`, `count_over_time`, `present_over_time` — whose per-step body is O(1): `last_over_time(a_X[1d])` at a 10s step goes from ~O(1) to O(8640) per series per step, making stats accounting ~1000× the cost of the evaluation it measures. `matrixIterSlice`'s own comment justifies its linear drop-scan precisely because it stays proportional to the overlap delta; this new scan breaks that discipline.

The diff adds no benchmark and reports no before/after numbers.

**Fix:** Scan backwards and stop at the first point at or below the cutoff (O(new points)) — or better, have `matrixIterSlice` return the count it already computes, since it records `len(floats)` before appending and already accumulates each newly appended histogram's `size()` into `ev.currentSamples`:

```go
func countSamplesAfter(floats []FPoint, histograms []HPoint, cutoff int64) int64 {
	var n int64
	for i := len(floats) - 1; i >= 0 && floats[i].T > cutoff; i-- {
		n++
	}
	for i := len(histograms) - 1; i >= 0 && histograms[i].T > cutoff; i-- {
		n += int64(histograms[i].size())
	}
	return n
}
```

Document the ascending-order precondition the reverse form depends on, and add `last_over_time(a_X[1d])` / `count_over_time(a_X[1d])` to `rangeQueryCases()` in `promql/bench_test.go:158` so the asymptotic shape is covered.

### #8 🟡 Medium: subquery `offset` is ignored when mapping subquery steps to outer steps

| | |
|---|---|
| **File** | `promql/engine.go:2437` |
| **Category** | correctness (per-step attribution) |
| **Confidence** | 100 — probe-confirmed (Probe 4) |
| **Found by** | adversarial-reviewer (Medium) |

**Issue:** `subqStart` / `subqEnd` are shifted by `offsetMillis` (`engine.go:2385-2394`), but the outer-step mapping `outerStep = ceil((tk - ev.startTimestamp) / ev.samplesStats.Interval)` uses the shifted `tk` against the **unshifted** outer origin. outerStep = int((tk + offsetMillis - ev.startTimestamp + ev.interval - 1) / ev.interval)

Add a range-query case with an offset subquery pinning `SamplesReadPerStep`.

### #9 🟡 Medium: the subquery remap mutates `QuerySamples` fields directly, bypassing its own setter and mixing two sources of truth

### #10 🟡 Medium: the subquery attribution policy is three load-bearing decisions recorded as twelve words of comment

| | |
|---|---|
| **File** | `promql/engine.go:2425`, `:2435-2441` |
| **Category** | knowledge preservation |
| **Confidence** | 100 |
| **Found by** | broad-reviewer (Medium), knowledge-reviewer (SHOULD), design-reviewer (Medium) |

**Issue:** Three unexplained choices:

1. Subquery steps at or before the outer start all collapse onto outer step 0 (`outerStep := 0` when `tk <= ev.startTimestamp`). Because a subquery necessarily begins one full `Range` before the outer start, this is *structurally* the majority of reads — Probe 4 shows `[12 2 2 2 2 2]`, i.e. 55% on step 0; `engine_test.go:1414` shows `{201000: 72, 206000: 6, 211000: 6, 216000: 9}`, i.e. 77%.
2. Steps past the last outer step are clamped rather than dropped — the comment says *what* ("so all disk reads are counted") but not *why* clamping beats dropping (it preserves `sum(perStep) == SamplesRead`) nor what it costs (per-step numbers stop being causally attributable).
3. The mapping uses ceiling division — bill each point to the first outer step *at or after* it — with no statement of why that direction rather than floor.

Nothing outside this comment says step 0 is an outlier by construction, and `docs/feature_flags.md` describes `samplesReadPerStep` as "delta per step" with no mention of the boundary lumping. ## Specialist Notes

### Threat Model Notes (security-reviewer)

- **Trust boundary**: `/api/v1/query` and `/api/v1/query_range`. `query` (arbitrary PromQL including subquery `[range:step]` literals), `start`, `end`, `step`, `timeout`, and `stats` are all attacker-controlled, and Prometheus is very commonly deployed with no authentication in front of these endpoints.
- **Existing controls and where they stop**: `web/api/v1/api.go:631` caps the *outer* range query at 11,000 points; `-query.max-samples` caps samples materialized *during* evaluation; `-query.timeout` and `-query.max-concurrency` cap wall time and slots. None bounds subquery step count, and none fires before `InitStepTracking`'s `make` — confirmed by Probe 3, where every query succeeded with `-query.max-samples=100` after allocating tens of MiB.
- **Attack surface change**: two new remote-visible response fields, one new unlabeled engine counter, and — the material change — a new pre-evaluation allocation whose size is a direct function of user-supplied duration literals, on a path that previously allocated nothing.
- **Information disclosure**: none new. `samplesRead` is gated identically to `totalQueryableSamples` (emitted whenever `stats` is non-empty); `samplesReadPerStep` is additionally gated on `EnablePerStepStats`, matching `totalQueryableSamplesPerStep`. The exposed information (sample density of matched series) is already derivable from `totalQueryableSamples` and the returned data. The gating is correct as written; only its *documentation* is wrong (#14).
- **`query.max-samples` enforcement is not weakened**: `ev.currentSamples`, `UpdatePeak`, `UpdatePeakFromSubquery` and every `ErrTooManySamples` site are untouched, and `MergeSamplesReadFromSubquery` deliberately merges only `SamplesRead`.
