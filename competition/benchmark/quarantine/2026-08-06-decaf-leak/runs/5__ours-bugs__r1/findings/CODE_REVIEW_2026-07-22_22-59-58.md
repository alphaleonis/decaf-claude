### #1 🔴 Critical: False-positive test — "consumer break releases the underlying reader lock" cannot fail even if the cleanup it names is removed

| | |
|---|---|
| **File** | `extensions/copilot/src/platform/networking/test/node/streamIdleTimeout.spec.ts:142` |
| **Category** | test (false-positive test) |
| **Confidence** | 100 |
| **Found by** | test-reviewer (Critical) |
| **Validation** | confirmed — validator independently re-derived the full mechanism |

**Issue:** The test's only post-break checks are `assert.deepStrictEqual(collected, ['a','b'])` (fully populated *before* the break, so it cannot detect cleanup loss) and `await stream.destroy()` not throwing. `DestroyableStream.destroy()` (`fetcherService.ts:284-296`) resolves cleanly in **both** the correct and the regressed implementation: if `await iterator.return?.()` in `withStreamIdleTimeout`'s `finally` (`fetcherService.ts:368`) were removed, the inner generator's `finally` (`releaseLock(); this.reader = undefined`) never runs, `this.reader` stays a valid locked reader, and `destroy()` takes the `this.reader.cancel()` branch — which, per WHATWG semantics, succeeds on a reader that still holds its own lock (`cancel()` only rejects after `releaseLock()`). The test passes identically with the lock-release code deleted; it cannot detect the regression it names.

**Fix:** Assert lock state directly, **before** calling `destroy()` (after `destroy()` resolves, both paths converge and the check no longer discriminates):

```ts
assert.deepStrictEqual(collected, ['a', 'b']);
assert.strictEqual(stream.toReadableStream().locked, false, 'reader lock should be released after early break');
await stream.destroy();
```

`toReadableStream()` exists at `fetcherService.ts:253-255`.

**Probe note:** test-reviewer nominated a revert-probe (remove `fetcherService.ts:368`, expect the test to still pass); it could not be run (no dependencies installed) — the validator confirmed the claim statically instead.

### #2 🔴 Critical: Watchdog correctness rests on an undocumented Web Streams invariant (destroy → pending read resolves `{done: true}`)

| | |
|---|---|
| **File** | `extensions/copilot/src/platform/networking/common/fetcherService.ts:342` |
| **Category** | knowledge-preservation / comprehension-risk |
| **Confidence** | 75 |
| **Found by** | knowledge-reviewer (MUST → Critical) |
| **Validation** | confirmed |

**Issue:** The entire error-surfacing mechanism depends on a non-obvious chain: timer fires → `stream.destroy()` → `reader.cancel()` → per WHATWG Streams semantics the pending `read()` **resolves** `{done: true}` (never rejects) → the loop exits as if the stream ended normally → the `timedOut` flag converts that clean completion into a thrown `StreamIdleTimeoutError` after the loop. This invariant is why `timedOut` and the post-loop throw exist, but no comment states it (the two existing comments cover only timer scope). Failure mode: a maintainer generalizes the wrapper to any `AsyncIterable` or swaps the backing to a Node `Readable` — where destroy mid-read **rejects** with `ERR_STREAM_PREMATURE_CLOSE` — and the rejection bypasses the post-loop throw; `chatMLFetcher.ts:1973-1983` classifies `'Premature close'` as `ChatFetchResponseType.Canceled`, so timeouts silently become "user canceled" and the hung-stream fix regresses invisibly. The validator confirmed the invariant, the absence of documentation, and the coherence of the failure path.

**Fix:** Add a comment at `startTimer` (or above the loop): "destroy() cancels the reader; per Web Streams semantics the pending read() resolves `{done: true}` — it never rejects. The loop therefore exits as if the stream ended normally, and `timedOut` distinguishes watchdog destruction from genuine end-of-stream so the error can be thrown after the loop. This holds only for ReadableStream-backed DestroyableStream; a source whose cancellation rejects the pending read would bypass the timeout error."

### #3 🟠 High: Fixed idle-timeout policy risks destroying healthy-but-silent streams — the 2-minute TTFT budget in practice collapses to 60s after the first (administrative) transport chunk; no configurability or kill switch

| | |
|---|---|
| **File** | `extensions/copilot/src/platform/networking/common/fetcherService.ts:303` (constants), `:362` (`isFirstChunk` flip) |
| **Category** | async / design |
| **Confidence** | 75 (promoted from 50 by 4-finder agreement) |
| **Found by** | adversarial-reviewer (High), quick-reviewer (Medium — dissenting), broad-reviewer (Medium — dissenting), design-reviewer (Medium — dissenting) |
| **Validation** | confirmed (external backend keep-alive behavior remains unverifiable from the repo — labeled as such) |

**Issue (merged facets):**
- **TTFT collapse** (adversarial-reviewer): `isFirstChunk = false` is set unconditionally after *any* chunk. `stream.ts:409` documents that CAPI sends "an initial chunk … with an empty choices array and no id, to hold `prompt_filter_results`" — an administrative chunk preceding real content — and `messagesApi.ts:687` special-cases Anthropic's early `message_start`. So the documented 2-minute allowance ("The model's TTFT is often longer … slightly more time") never actually budgets *model* TTFT; after the near-immediate administrative chunk, a reasoning model silent >60s is killed.
- **Uniform fixed policy** (quick/broad/design): the constants apply identically to all three call sites (Anthropic extended thinking, OpenAI reasoning, SSEProcessor) with no options parameter, no experiment/config wiring (contrast the sibling `RetryNetworkErrors` experiment gate, `chatMLFetcher.ts:575` / `configurationService.ts:855`), and no kill switch — remediation for a bad value requires a code release.
- **Dissent recorded:** security-reviewer's considered-items note asserts both providers send periodic SSE ping/comment events that would reset the timer (they arrive as raw transport bytes). The validator found SSE comment handling in the parsers but **nothing in-repo establishing providers emit pings during silent reasoning phases** — the risk is narrowed, not eliminated. [Unverified] external backend behavior.

**Fix (both finders' variants):** decide first-chunk state on model-output content rather than any transport chunk (or keep the long timeout for a fixed initial window regardless of chunk count); and/or accept optional `{ firstChunkTimeoutMs, idleTimeoutMs }` and gate the values through the existing experiment-config machinery so the policy can be tuned or disabled without shipping code. At minimum, add telemetry on `StreamIdleTimeoutError` occurrences broken out by model to detect false kills.

### #4 🟡 Medium: Watchdog-triggered destruction is recorded in fetch telemetry as `outcome: 'cancel'`, indistinguishable from a benign user cancellation

| | |
|---|---|
| **File** | `extensions/copilot/src/platform/networking/common/fetcherService.ts:346` (no-reason destroy) → `:104-107` (outcome classification) |
| **Category** | error-handling / observability |
| **Confidence** | 100 |
| **Found by** | quick-reviewer (Medium), broad-reviewer (Medium), security-reviewer (Low — dissenting), adversarial-reviewer (Low — dissenting) |
| **Validation** | confirmed — validator empirically reproduced the cascade with Node's built-in Streams implementation, for both the single-level (`messagesApi`/`responsesApi`) and two-level `pipeThrough(TextDecoderStream)` (`stream.ts`) shapes |

**Issue:** The timer callback calls `stream.destroy()` with no reason; `DestroyableStream.destroy()` forwards to `reader.cancel()`/`stream.cancel()` with no argument. The cancellation propagates to the `Response` constructor's counting-TransformStream `cancel` handler: `const outcome = reason && !isAbortError(reason) ? 'error' : 'cancel';` — with `reason === undefined`, every watchdog kill is reported to `onDidFetch`/`responseStreaming` FetchEvent telemetry as `outcome: 'cancel'`, exactly like a user cancellation. The hung-stream events this PR exists to surface are systematically misfiled; nobody can use fetch telemetry to validate the fix, tune the constants, or alert on hang rates. (The thrown error separately reaches exception telemetry in `chatMLFetcher` — the gap is specifically the fetch-layer stream-outcome classification.)

**Fix:** Extend `DestroyableStream.destroy(reason?)` to forward the reason to `reader.cancel(reason)`/`stream.cancel(reason)` and pass a `StreamIdleTimeoutError` (truthy, non-abort) from the timer callback; the validator verified reason propagation through the same cascade flips the outcome to `'error'`.

**Probe note:** security-reviewer nominated a telemetry-classification probe (spy `ReportFetchEvent` test); not runnable here — the validator settled it empirically instead.

### #5 🟡 Medium: `StreamIdleTimeoutError` is classified only by accident — users get a misleading "check your firewall rules" message for a server-side hang, and the intended contract is undocumented

| | |
|---|---|
| **File** | `extensions/copilot/src/extension/prompt/node/chatMLFetcher.ts:1949` (processError); `extensions/copilot/src/platform/networking/common/fetcherService.ts:312` (error definition) |
| **Category** | error-handling |
| **Confidence** | 75 |
| **Found by** | knowledge-reviewer (MUST → Critical — see validation note), adversarial-reviewer (Medium), quick-reviewer (Medium), design-reviewer (Medium), broad-reviewer (Low — dissenting) |
| **Validation** | confirmed **with corrections** — severity re-derived Critical → Medium (see below) |

**Issue (mechanism as validated):** The new error type is handled explicitly nowhere. The finders disagreed on the downstream mechanism, and the validator resolved it: the error is thrown inside the `AsyncIterableObject` executors, rejected through `chatMLFetcher`'s `for await` consumption, which unconditionally tags `err.fetcherId` (`chatMLFetcher.ts:1295/1302`) before rethrowing — for **all three** call sites. `fetcherServiceImpl.isFetcherError` (`fetcherServiceImpl.ts:196`: `!!e?.fetcherId || …`) therefore intercepts it, mapping it to `ChatFetchResponseType.NetworkError` with the fetcher-fallback template: *"Please check your firewall rules and network connection then try again. Error Code: SSE stream timed out after 60000ms of inactivity."* (`nodeFetcher.ts:146-147` / `baseFetchFetcher.ts:121-122`) — misattributing a server-side hang to the user's network — and it **is** retry-eligible under the `RetryNetworkErrors` config. The classification, message, and retry behavior are accidental byproducts of generic `fetcherId` tagging, not a designed contract; no test or documentation covers the intended handling.

**Validation note (severity):** The Critical rating came from finders whose factual account ("falls through to generic `Failed`, excluded from retry" — adversarial anchor 100, knowledge MUST) was **refuted** by the validator's trace. The surviving, confirmed account is design-reviewer's original Medium: accidental-but-semantically-reasonable classification with a misleading message. Per the validator's explicit recommendation, severity was re-derived to Medium. This exceeds the standard line/file/pre_existing correction scope and is recorded as an anomaly.

**Fix:** Add an explicit `err instanceof StreamIdleTimeoutError` (or `err?.name === 'StreamIdleTimeoutError'`) branch in `processError` returning `NetworkError` (or a dedicated type) with an accurate hung-connection message (e.g. "The response stream stalled. Please try again."), making retry-eligibility deliberate; document the intended classification contract in the error class's JSDoc.
