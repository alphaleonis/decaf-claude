## Findings

### #1 🟡 Medium: A timed-out hung stream surfaces to the user as a misleading "check your firewall" network error, by accident of generic error tagging

| | |
|---|---|
| **File** | `extensions/copilot/src/platform/networking/common/fetcherService.ts:373` (throw site); consequence in `chatMLFetcher.ts:1295/1997/2000` |
| **Category** | error-handling / design |
| **Confidence** | 90 (classification path directly verified) |
| **Found by** | adversarial-reviewer (Medium), design-reviewer (Medium) |

**Issue:** `StreamIdleTimeoutError` is a named error type introduced precisely so a hung-stream timeout can be identified — but nothing anywhere catches, `instanceof`-checks, or name-matches it (full grep: only its definition and throw site in `fetcherService.ts`). Its downstream handling is therefore incidental, not designed:

1. The error propagates out of the wrapped `for await` and is caught in `chatMLFetcher.ts:1291-1299`, which tags `err.fetcherId = response.fetcher` and rethrows.
2. `processError` (`chatMLFetcher.ts:1949`) uses `fetcher = this._fetcherService`. At line 1997, `fetcher.isFetcherError(err)` resolves to `fetcherServiceImpl.ts:196` — `return !!e?.fetcherId || …` — which is **true** solely because `fetcherId` was tagged in step 1.
3. It is therefore classified as `ChatFetchResponseType.NetworkError` (line 2000) with `userMessage = getUserMessageForFetcherError(err)` → the primary fetcher's fallback (`baseFetchFetcher.ts:122` / `nodeFetcher.ts:147`): **"Please check your firewall rules and network connection then try again. Error Code: SSE stream timed out after 60000ms of inactivity."** — misattributing a *server-side* stall to the user's firewall/network.
4. Because it lands in `NetworkError`, it **is** retry-eligible (`retryNetworkError`, `chatMLFetcher.ts:575`), gated on `enableRetryOnError` + `ConfigKey.TeamInternal.RetryNetworkErrors`.

None of classification, message, or retry-eligibility is a deliberate contract — all three ride the generic `fetcherId` side-channel. A future refactor of that tagging would silently change hung-stream behavior, and today the user-facing message is actively misleading.

> **Correction note:** The two finders' original downstream account ("falls through to the generic `Failed` bucket; not retried on the HTTP path") was **incorrect** — and a first-pass validator confirmed that incorrect trace because it read `processError` in isolation and missed the upstream `fetcherId` tagging. The orchestrator re-verified directly against `chatMLFetcher.ts:1295/1997`, `fetcherServiceImpl.ts:196`, `baseFetchFetcher.ts:122`, and `chatMLFetcher.ts:575`. The finding stands, but its mechanism and severity are the corrected ones above. [Verified by direct code reading; retry actually firing additionally depends on caller flags/experiment config.]

**Fix:** Add an explicit branch in `processError` (name-based, matching the `isAbortError` convention) mapping `StreamIdleTimeoutError` to a deliberate category with an accurate message, e.g. *"The response stream stalled while receiving data. Please try again."*, and decide retry-eligibility on purpose rather than via `fetcherId`. Document the intended classification contract in the `StreamIdleTimeoutError` JSDoc.

### #2 🟡 Medium: Hardcoded, non-configurable idle timeouts applied unconditionally to every SSE stream — inconsistent with the sibling ConfigKey/experiment convention

| | |
|---|---|
| **File** | `extensions/copilot/src/platform/networking/common/fetcherService.ts:303-310` (constants; applied at `stream.ts:323`, `messagesApi.ts:596`, `responsesApi.ts:537`) |
| **Category** | design / production-reliability |
| **Confidence** | 75 (factual basis confirmed by validator; false-timeout premise unverified) |
| **Found by** | broad-reviewer (High), design-reviewer (Low) — severity dissent |

**Issue:** `SSE_FIRST_CHUNK_TIMEOUT_MS` (2 min) and `SSE_IDLE_TIMEOUT_MS` (60 s) are fixed module-level constants. `withStreamIdleTimeout` takes no options object and is applied unconditionally at all three call sites — no per-endpoint variation, no `ConfigKey`/`IExperimentationService` gate, no kill switch. This is inconsistent with the established local convention: sibling numeric tunables in these exact files are experiment-gated (`ConfigKey.AnthropicThinkingBudget` in `messagesApi.ts`; `ConfigKey.ResponsesApiReasoningSummary`, `ConfigKey.Advanced.UseResponsesApiTruncation`, `ConfigKey.TeamInternal.ResponsesApiReasoningEffort` in `responsesApi.ts` — validator-confirmed). If a legitimately-progressing stream ever exceeds a 60 s inter-chunk gap (large reasoning/"extended thinking" budgets, or BYOK/local models with long time-to-first-token), the watchdog destroys it and there is no deploy-free lever to tune or disable it for that endpoint without weakening it globally.

**Why Medium (not High):** The factual basis — fixed constants, unconditional application, deviation from the sibling config convention, and the resulting hard failure mode with no mitigation knob — is confirmed. The High rating rested on the *unverified* premise that legitimate streams do idle >60 s in practice, which could not be established from the diff (a design specialist independently rated it Low). Medium reflects "worth addressing before this ships widely," not "provably breaks."

**Fix:** Accept an optional `{ firstChunkTimeoutMs?, idleTimeoutMs? }` (defaulting to the constants) and/or gate the values via the existing experiment-config machinery, so the policy can be tuned per endpoint or disabled without a code release — and so tests can inject small values instead of importing the production constants. Consider adding telemetry on `StreamIdleTimeoutError` occurrences broken out by model to detect false kills.

### #3 🟡 Medium: False-positive test — "consumer break releases the underlying reader lock" cannot fail even if the cleanup it names is removed

| | |
|---|---|
| **File** | `extensions/copilot/src/platform/networking/test/node/streamIdleTimeout.spec.ts:142-158` |
| **Category** | test-quality (false-positive test) |
| **Confidence** | 100 (empirically reproduced by finder) |
| **Found by** | test-reviewer |

**Issue:** The test's comment claims to prove that after an early `break`, "destroy() should still work without a dangling reader lock" — the property guarded by `withStreamIdleTimeout`'s `finally { … await iterator.return?.(); }` (`fetcherService.ts:366-369`). But the only trailing statement is a bare `await stream.destroy();` with **no assertion at all**. `DestroyableStream.destroy()` succeeds whether or not the reader lock was released (if a reader is still held it takes the `reader.cancel()` branch; if released it takes `stream.cancel()`), so the test passes identically in both worlds. The test-reviewer confirmed by isolated reproduction (untracked scratch copy, deleted afterward) that removing `await iterator.return?.();` from the production `finally` leaves this test **green** — it cannot catch the regression it is named for.

**Fix:** Assert the lock state directly, using the accessor `DestroyableStream` already exposes:
```ts
assert.deepStrictEqual(collected, ['a', 'b']);
assert.strictEqual(stream.toReadableStream().locked, false, 'reader lock should be released after break');
await stream.destroy();
```

## Minor Findings

### Testing Gaps

- `extensions/copilot/src/platform/networking/test/node/streamIdleTimeout.spec.ts` — no test asserts the stream is actually **destroyed/canceled on timeout**; both timeout tests check only the thrown error type/message, so dropping the `void stream.destroy()` side effect from the timer callback would still pass while leaking the connection (test-reviewer, Medium).
- `streamIdleTimeout.spec.ts:68,93` — the timeout-error assertions use `err.message.includes('first chunk')` / `includes('inactivity')` and never check the interpolated `${timeoutMs}` value; a constant-swap regression (wrong timeout fed to the error within the same branch) would still pass. Tighten to `includes(\`${SSE_FIRST_CHUNK_TIMEOUT_MS}ms\`)` / `includes(\`${SSE_IDLE_TIMEOUT_MS}ms\`)` (test-reviewer, Medium).
- No test exercises the production composition `SSEProcessor` uses — `response.body.pipeThrough(new TextDecoderStream())` then `withStreamIdleTimeout(this.body)` — so the `pipedHead`/`maybeCancel` forwarding interaction with the watchdog's teardown is unpinned against refactoring (broad-reviewer, Medium; traced correct today).
- No test covers a consumer `break` while the outer generator is still **awaiting a chunk with an armed timer** (the existing break test breaks between iterations); this `finally`/timer-clear/`iterator.return()` path is unexercised (test-reviewer, Low).

### Residual Risks

- `fetcherService.ts:346` — `void stream.destroy().catch(() => { })` swallows every `destroy()`/`cancel()` rejection with no logging; a genuine cleanup-path failure (the one case where diagnostics matter) is invisible in production. Log at debug/warn instead of an empty catch (typescript-reviewer, Medium). *(The `void` + `.catch` combination is correct and not redundant — both serve distinct purposes.)*
- `stream.ts` `processSSEInner` — a mid-stream `StreamIdleTimeoutError` makes the `for await` **throw**, bypassing the existing graceful-finalize fallback (lines ~596-614) that yields accumulated partial `solutions` on a non-`[DONE]` exit; any partially-streamed completion is discarded rather than finalized. The discard mechanism is pre-existing, but this PR newly routes a *post-progress* failure mode through it. Document the hard-fail-vs-finalize choice or catch the timeout and route through the fallback (broad-reviewer, Medium, partially pre-existing).
- `fetcherService.ts:372` — `isFirstChunk` is a single mutable flag used both to select each iteration's timeout and to reconstruct the error's `timeoutMs`/message after the loop; correct today only because it flips exactly once, but the post-loop re-derivation can silently desync from the timer that actually fired if the loop later gains a continue/retry path. Capture the fired phase at the timer instead (design-reviewer, Low).

## Specialist Notes

### Considered But Not Flagged (all agents)

Convergent negative verification — these were traced by multiple reviewers (quick, broad, design, typescript, adversarial) against WHATWG Streams + JS microtask/macrotask ordering and cleared:

- **Chunk-at-deadline race** (a real chunk arriving as the idle timer fires, causing a spurious `StreamIdleTimeoutError` after data was delivered): **not reachable.** A resolved `reader.read()` and its `clearTimer()` continuation run in one microtask checkpoint; a `setTimeout` macrotask cannot interleave between them. If the timer fires first, `reader.cancel()` clears the queue and resolves the pending read as `{done:true}` — no real value is delivered on a `timedOut` iteration.
- **Raw cancel error masking the typed error**: per spec, `reader.cancel()` **resolves** the pending read `{done:true}` (does not reject), so the loop breaks cleanly and the typed `StreamIdleTimeoutError` is thrown after the `finally`. Corroborated by the shipped timeout tests.
- **Error-message correctness on first-chunk vs subsequent-chunk timeout**: `isFirstChunk` is mutated only *after* the `result.done` check, so a timed-out iteration never changes it before the throw — the reported `timeoutMs`/message always matches the timer that fired.
- **Consumer break / consumer throw with an armed timer**: the timer is cleared in `finally` before `iterator.return?.()`; `.return()` on a generator suspended at `yield` runs its `finally` (releasing the reader lock) with no pending read, so no `releaseLock`-with-pending-read `TypeError` and no double-cancel.
- **Double `destroy()`/`cancel()`** from the watchdog + `maybeCancel` + the outer `finally`: idempotent — once the reader is released and nulled, `destroy()` degrades to `stream.cancel()`, a no-op on an already-cancelled stream.
- **Genuine (non-timeout) underlying error mid-read**: propagates unchanged; `timedOut` stays false so the trailing throw does not mask it.
- **`ReturnType<typeof setTimeout>` typing** and **`DestroyableStream<T>` (not `AsyncIterable<T>`) parameter**: both correct — the concrete type is required to reach `.destroy()`, the escape hatch a bare `AsyncIterable` cannot express.

Whether a hung-stream timeout *should* auto-retry (vs. surface immediately) is a genuine product decision surfaced by finding #1, not a defect in itself.
