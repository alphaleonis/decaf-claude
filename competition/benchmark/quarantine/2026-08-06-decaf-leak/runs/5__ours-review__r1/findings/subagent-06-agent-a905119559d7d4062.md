### Why the flagged scenarios do NOT reproduce (traced, for the record)

- **Scenario 1 (message correctness):** `isFirstChunk` at throw time always equals `isFirstChunk` at the `startTimer` of the *same* iteration — `isFirstChunk=false` is set only after the `result.done` check, so a timed-out iteration never mutates it before the throw. First-chunk stall → `FIRST_CHUNK` timer + "first chunk" message; post-chunk stall → `IDLE` timer + "inactivity" message. Reported `timeoutMs` always matches the timer that actually fired. Correct.

- **Scenario 2 (typed error vs raw cancel):** Per WHATWG Streams, `reader.cancel()` resolves the pending `read()` with `{done:true}` (confirmed by the code comment and spec) and clears the queue — it does not reject. So the `DestroyableStream` generator breaks cleanly, `withStreamIdleTimeout`'s `finally` runs, and the typed `StreamIdleTimeoutError` is thrown from after the `finally`. The raw cancel/Abort error is never surfaced. Correct.

- **Scenario 3/4 (consumer break / consumer throw):** At a consumer `break`/`return`, `withStreamIdleTimeout` is suspended at `yield`, and the inner `DestroyableStream` generator is suspended at *its* `yield` — no outstanding `read()`. `finally` → `clearTimer()` (no window: timer is cleared before the throw and re-armed only at loop top) → `iterator.return?.()` → `releaseLock()` is safe (no pending read). A later `destroy()` sees `reader === undefined` and takes the `stream.cancel()` branch — no double-cancel. Correct.

- **Scenario 5 (spurious error after a real final chunk):** Not reachable. For a real chunk to be *yielded*, `reader.read()` must fulfill; its fulfillment, the generator's `yield`, and `withStreamIdleTimeout`'s `clearTimer()` continuation are all in one microtask checkpoint. A `setTimeout` callback is a macrotask and cannot interleave between them, so it cannot fire *after* a value is read but *before* that iteration's timer is cleared. Conversely, if the timer fires first, `reader.cancel()` clears the internal queue and resolves the pending/next `read()` as `done` — buffered chunks are dropped, so no real value is delivered on a `timedOut` iteration. Therefore `timedOut === true` ⇒ no further real chunks ⇒ throw is never "after partial success" within the same generator. Backward check confirms: the final loop-breaking `next()` resolved `done`, so any prior yielded value came from an iteration whose timer was cleared.

### Considered But Not Flagged

- **Deadline-boundary chunk drop (ADV_ABUSE, ~25):** A chunk whose network I/O callback lands in the same loop iteration as the timer, but in the *poll* phase after the *timers* phase, is dropped by `reader.cancel()`'s queue-clear and converted into a timeout. Failing step: the outcome ("a chunk ≥60s late is treated as a timeout") is arguably correct behavior, not a defect; window is astronomically narrow. Not a bug.

- **`onReturn` double-destroy unhandled rejection (ADV_CASCADE, ~25):** In messagesApi/responsesApi, the `AsyncIterableObject` `onReturn` does `await response.body.destroy()` un-try/caught, and the producer also destroys on timeout. Failing step: the second `destroy()` hits `reader === undefined` → `stream.cancel()` on an already-cancelled stream, which the spec resolves as a no-op; the transform's `cancel` handler only emits telemetry and does not throw. No rejection materializes.

- **`releaseLock()` with outstanding read (ADV_COMPOSITION, ~25):** Would throw `TypeError` if `iterator.return()` ran while a `read()` was pending. Failing step: `.return()` on an async generator suspended at `await` is deferred until the awaited promise settles, and consumer-initiated returns only occur at `yield` points — so `releaseLock` never runs with a pending read.

- **stream.ts `maybeCancel` → `response.body.destroy()` cancelling `withStreamIdleTimeout`'s live reader (ADV_COMPOSITION, ~25):** Verified this is the intended cross-cancel path; `pipeThrough` set `response.body.pipedHead`, so `destroy()` forwards to the decoded `this.body` reader rather than hitting `cancel()` on the pipe-locked upstream `ReadableStream`. No locked-stream `TypeError`.
