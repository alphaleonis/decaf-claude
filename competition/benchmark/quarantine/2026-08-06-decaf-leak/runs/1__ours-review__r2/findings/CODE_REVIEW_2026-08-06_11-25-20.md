## Findings

### #1 🔴 Critical: Re-added `Debug.Assert(rowIdForOrdinal != null)` fires on the legitimate "no rowid" path

| | |
|---|---|
| **File** | `src/Microsoft.Data.Sqlite.Core/SqliteDataRecord.cs:393` |
| **Category** | error-handling / broken invariant |
| **Confidence** | 100 |
| **Found by** | broad-reviewer (Critical), prior-feedback-reviewer (Critical), quick-reviewer (High), dotnet-reviewer (Medium) |
| **Validation** | confirmed |

**Issue:** Before this PR, `_rowidOrdinal` (`int?`) was seeded to the sentinel `-1` *before* the scan loop, so `Debug.Assert(_rowidOrdinal.HasValue)` was a tautology and could never fire. The refactor to `Dictionary<string, RowIdInfo> RowIds` removed that unconditional sentinel assignment: `rowIdForOrdinal` starts `null` and is assigned **only** inside the two success branches that also call `RowIds.Add` (the `columnName == "rowid"` break and the single-INTEGER-PK break). When the blob's table has no discoverable rowid — a `WITHOUT ROWID` table, a **composite** primary key, or no primary key — the loop completes with `rowIdForOrdinal` still `null`, and the re-added `Debug.Assert(rowIdForOrdinal != null)` fires. This is not an error condition: the very next line, `if (rowIdForOrdinal == null) return new MemoryStream(GetCachedBlob(ordinal), false);`, is written to handle exactly this case.

This is directly exercised by an **existing** test: `GetStream_works_when_composite_pk` (`test/Microsoft.Data.Sqlite.Tests/SqliteDataReaderTest.cs:516`) selects `Id1, Id2, Data` from a table with `PRIMARY KEY (Id1, Id2)` and calls `GetStream(2)` expecting a `MemoryStream`. Under the new code `pkColumns` never reaches 1 and no column is named `rowid`, so the assert trips.

`Debug.Assert` is `[Conditional("DEBUG")]`, so this manifests only in **Debug** builds — which is the default configuration for `dotnet test` and typical CI/local runs. In Release the assert compiles out and behavior is correct, which is why the change still functions. The prior-feedback angle: `ErikEJ` asked to "Re-add Assert" and the author restored it verbatim, but into a control flow it no longer matches — the request was honored literally while silently defeating the invariant the original sentinel design guaranteed.

**Fix:** Remove the assert (the `if (rowIdForOrdinal == null)` fallback below is the real, intended handling for "no rowid"), or represent "known: no rowid" distinctly from "not yet computed" and assert on the lookup outcome rather than on whether a rowid was found. The cleanest fix also resolves finding #2 — see below.

### #2 🟠 High: Negative rowid-lookup result is no longer memoized — full metadata scan (and a nested SQL query) re-runs on every blob read for tables without a discoverable rowid

| | |
|---|---|
| **File** | `src/Microsoft.Data.Sqlite.Core/SqliteDataRecord.cs:328-394` |
| **Category** | performance / scalability |
| **Confidence** | 100 |
| **Found by** | performance-reviewer (High), broad-reviewer (High), quick-reviewer (Medium) |
| **Validation** | confirmed — recommended severity High |

**Issue:** The old field `private int? _rowidOrdinal;` memoized **both** outcomes: the scan set `_rowidOrdinal = -1` unconditionally, then possibly overwrote it with the found ordinal, and every later call short-circuited via `_rowidOrdinal.HasValue`. The new `Dictionary<string, RowIdInfo> RowIds` calls `RowIds.Add(...)` **only** on the two success `break` branches. When the scan finds no rowid (composite PK, `WITHOUT ROWID` table, view, computed/aggregate blob expression), nothing is cached; the next `GetStream`/`GetBytes` call for that same `{db}_{table}` misses the dictionary again and re-runs the **entire** `O(FieldCount)` scan — per-field native `sqlite3_column_database_name`/`table_name`/`origin_name`/`sqlite3_table_column_metadata` calls, plus, for any INTEGER-PK candidate, a fresh `SELECT COUNT(*) FROM pragma_table_info($table) WHERE pk != 0;` command (the local `pkColumns` resets to `-1` each call).

Since a single `SqliteDataRecord` instance persists across all rows of a result set (`Read()` reuses it; only `NextResult()` makes a new one), and `GetStream`/`GetBytes` runs once per blob cell, streaming such a column over N rows becomes **O(N) repeated metadata scans plus up to O(N) nested SQL executions** where the previous code was O(1) after the first row. The validator explicitly confirmed the multi-row persistence and preferred High over Medium precisely because of the repeated real SQL round-trips.

**Fix:** Cache the negative outcome too — add the key to `RowIds` with a `null`/sentinel `RowIdInfo?` value (making the dictionary `Dictionary<string, RowIdInfo?>`) even when no rowid is found, and short-circuit straight to `GetCachedBlob` on a repeat miss. This restores the original memoization guarantee and simultaneously removes the basis for the #1 assert defect.

### #3 🟡 Medium: rowid cache key does not uniquely identify the rowid source (underscore-collision + self-join)

| | |
|---|---|
| **File** | `src/Microsoft.Data.Sqlite.Core/SqliteDataRecord.cs:328` |
| **Category** | correctness / data |
| **Confidence** | 50 |
| **Found by** | quick-reviewer (Medium), broad-reviewer (Medium) |
| **Validation** | confirmed — Medium appropriate |

**Issue:** `string rowidkey = $"{blobDatabaseName}_{blobTableName}";` builds the cache key by raw underscore concatenation with no escaping, and the scan matches candidate rowid columns purely by `sqlite3_column_database_name`/`sqlite3_column_table_name` string equality. Two distinct failure modes follow from one root cause (the key is insufficient):

1. **Underscore-separator ambiguity** — (db `"main"`, table `"foo_bar"`) and (db `"main_foo"`, table `"bar"`) both produce the key `"main_foo_bar"`, so two distinct blob columns could share a cache entry and receive the wrong table's rowid ordinal. Underscores are legal and common in attached-database and table names.
2. **Self-join** — `sqlite3_column_table_name` returns the underlying table name, not the query alias. For `SELECT a.blob, b.blob FROM T a JOIN T b ON ...`, both blob columns key to `"main_T"`; the second lookup reuses the first alias's cached `RowIdInfo`, applying alias `a`'s rowid to `b`'s blob — a narrower recurrence of the very cross-table mixup (#32747) this PR fixes.

Both are real and derivable from the code, but require uncommon query/name shapes, hence Medium at confidence 50 (not verdict-driving on its own, but it is a residual correctness limitation of the chosen fix).

**Fix:** Key the cache unambiguously — e.g. a `ValueTuple<string,string>`-keyed dictionary (no delimiter to collide) — and, for the self-join case, disambiguate by the rowid-defining column's result-set position rather than table name alone, or document the self-join limitation and lock current behavior with a regression test.

## Specialist Notes

### Test regression-guard verification (test-reviewer)

The new `GetBytes_works_streaming_join` test was traced statically as a **genuine** regression guard for #32747: without the fix, the second `GetBytes(3, …)` reuses table A's cached rowid ordinal (value `1`), so `SqliteBlob` opens against table `B` with rowid `1` — which does not exist (B's only row has `ID=1000`) — and `sqlite3_blob_open` returns a non-OK code, throwing a `SqliteException` before the second assertion. With the fix, B's own rowid (1000) is resolved and `[0x06,0x07]` is returned. The test fails pre-fix (via exception) and passes post-fix — not a false positive.

### Considered But Not Flagged (all agents)

- **Stray blank line with trailing whitespace** inserted after `namespace Microsoft.Data.Sqlite {` (line ~17) — pure formatting noise; flagged by several as too trivial to report.

Recorded as consistency/API preference (captured under Residual Risks for the setters), not a defect.
