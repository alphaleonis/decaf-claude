## Considered But Not Flagged

- **Repeated `pragma_table_info` query / full column scan on every `GetStream` call when no rowid is found (composite PK / WITHOUT ROWID tables).** In the old code, the negative outcome (`_rowidOrdinal = -1`) was cached forever on the single field, so a table with no usable rowid only paid the scan+query cost once per `SqliteDataRecord` instance. In the new code, the dictionary is only populated on the *positive* branches (`RowIds.Add(...)` happens only inside the two `break` cases); the negative case is never cached, so the full `FieldCount` scan and the `SELECT COUNT(*) FROM pragma_table_info(...)` command re-run on every single `GetStream` call for such tables. This is a real behavioral regression, but it's a repeated-query/hot-path performance concern at scale, which per the review taxonomy belongs to `performance-reviewer`, not this generalist pass — flagging it here for awareness/cross-check.
- **Thread-safety of `RowIds` dictionary.** Same non-thread-safe profile as the field it replaces (`_rowidOrdinal`); `SqliteDataRecord` was never documented/used as thread-safe, and `NextResult()` in `SqliteDataReader.cs` allocates a fresh `SqliteDataRecord` per statement, so this isn't a new issue introduced by the diff.
- **Cache lifetime across result sets / rows.** Verified `SqliteDataReader.NextResult()` creates a brand-new `SqliteDataRecord` per prepared statement, so the per-instance `RowIds` cache is correctly scoped to a single statement's fixed column schema (same invariant the removed single-field cache relied on); no stale-cache issue across `Read()` calls or `NextResult()`.
- **`SqliteDataReaderTest.GetBytes_works_streaming_join` test correctness.** Verified expected byte-offset math (`x'01020304'` sliced at offset 1, length 2 → `[0x02,0x03]`; `x'05060708'` → `[0x06,0x07]`) is correct, and the test uses proper `using` disposal — no issues found.
