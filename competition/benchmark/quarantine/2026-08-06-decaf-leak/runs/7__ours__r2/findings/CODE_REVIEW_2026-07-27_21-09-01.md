## Findings

### #1 🔴 Critical: Chunk querier closed before its lazily-iterated `ChunkSeriesSet` is consumed → use-after-munmap of on-disk block chunks

| | |
|---|---|
| **File** | `storage/remote/read_handler.go:247` (the `defer querier.Close()` in `getChunkSeriesSet`), consumed at `storage/remote/codec.go:235-296` |
| **Category** | resource-management / memory-safety (use-after-close race) |
| **Confidence** | 100 (anchor) |
| **Found by** | quick (Critical), broad (Critical), design (Critical), adversarial (Critical), go (Critical), knowledge (assumption facet) |
| **Validation** | **confirmed** — validator independently re-derived the full chain; corrected the mechanism to a *race*, not a deterministic crash |

**Issue:** The refactor extracts querier creation + `Select` into `getChunkSeriesSet` (`read_handler.go:242-266`). Its `defer querier.Close()` (line 247) fires when the helper **returns** the `storage.ChunkSeriesSet` (line 265) — i.e. *before* `StreamChunkedReadResponses` (`codec.go:235`) iterates it. That consumption is **lazy**: `ss.Next()` → `series.Iterator()` → `chk.Chunk.Bytes()`.

Traced through the concrete TSDB path (`h.queryable.ChunkQuerier` → `tsdb.DB.ChunkQuerier` → `storage.NewMergeChunkQuerier` over one `blockChunkQuerier` per on-disk block + head):

- `querier.Close()` → `mergeGenericQuerier.Close()` (`storage/merge.go:255-263`) → each `blockBaseQuerier.Close()` (`tsdb/querier.go:103`) → `q.chunks.Close()`.
- `q.chunks` is a `blockChunkReader{ChunkReader: pb.chunkr, b: pb}` (`tsdb/block.go:436-441`), whose `Close()` (`tsdb/block.go:567-570`) does **only** `r.b.pendingReaders.Done()` — it does **not** unmap anything.
- The chunk bytes returned during iteration **alias the block's memory-mapped segment file without a copy** (`tsdb/chunks/chunks.go` `Reader.ChunkOrIterable` → `sgmBytes.Range(...)`).
- The actual `munmap` happens in `Block.Close()` (`tsdb/block.go:378-390`): `pendingReaders.Wait()` **then** `pb.chunkr.Close()`. `Block.Close()` is invoked by compaction/retention block deletion (`deleteBlocks`, `db.go:1656-1665`; doc at :1658 — a block "needs to be closed first as it might need to wait for pending readers to complete").

So `pendingReaders` is the sole guard that keeps the mmap valid while a query reads it. Before the PR, `defer querier.Close()` ran only **after** `StreamChunkedReadResponses` finished, holding `pendingReaders` throughout streaming. The PR releases that guard **early** (on helper return), so a concurrent compaction/retention `Block.Close()` can `munmap` + delete an in-range block's segment file **while streaming is still reading its chunk bytes** → **use-after-munmap**: a SIGSEGV that crashes the whole process (Go cannot recover a hardware fault; `debug.SetPanicOnFault` is not set on this path), or corrupted bytes streamed to the remote-read client.

**Characterization (corrected during validation):** This is a **race**, not a deterministic every-request crash. The `blockChunkReader.Close()` does not itself munmap — the crash requires a concurrent compaction/retention `Block.Close()` on an in-range block to land inside the streaming window. (Two reviewers rated it conf 100 on an "immediate munmap" reading; source shows the munmap is deferred to `Block.Close()`.) The window is realistically hit: compaction/retention run periodically in every production Prometheus, and streamed reads of historical data are exactly the long-running / slow-client requests the PR targets. Severity remains **Critical** (process crash or silent data corruption).

**Why the test suite didn't catch it:** `TestStreamReadEndpoint` (`storage/remote/read_handler_test.go`) uses `promql.LoadedStorage`, which keeps data in the in-memory head — never exercising `blockChunkQuerier`/mmap'd block segments — so the pre-flight "tests PASS" gives no signal on this path (see Minor → Testing Gaps).

**Fix:** Keep the querier open until the `ChunkSeriesSet` is fully consumed. Options:
1. Revert to closing after `StreamChunkedReadResponses` returns — return the querier alongside the set and `defer querier.Close()` in `remoteReadStreamedXORChunks` after streaming (restores the pre-PR ordering), **or** pass the stream into the helper so streaming happens before the deferred Close fires.
2. If early release is genuinely required to bound memory, make the set self-contained by copying chunk bytes out of the mmap before Close (as the head path already does) — but that negates most of the memory benefit.

```go
// Return querier alongside the set; caller closes after streaming.
chunks, querier, err := h.getChunkSeriesSet(ctx, query, filteredMatchers)
if err != nil { return err }
defer func() {
    if err := querier.Close(); err != nil {
        level.Warn(h.logger).Log("msg", "Error on chunk querier close", "err", err.Error())
    }
}()
ws, err := StreamChunkedReadResponses(NewChunkedWriter(w, f), int64(i), chunks, ...)
```

### #2 🟡 Medium: Head-path variant — isolation state released early exposes in-flight streamed reads to concurrent head truncation/GC

| | |
|---|---|
| **File** | `storage/remote/read_handler.go:247` — via `tsdb/head_read.go:318-323` (`headChunkReader.Close()` → `isoState.Close()`) and `tsdb/isolation.go:36-41` |
| **Category** | race-condition / correctness |
| **Confidence** | 75 (anchor) |
| **Found by** | broad (High), adversarial (Critical), go (High) |
| **Validation** | **confirmed** — validator ruled out a memory UAF on the head path; consequence is an isolation/consistency race, so severity corrected High → Medium |

**Issue:** Same root cause as #1, for the Head (recent-data) path. `querier.Close()` fans out to `headChunkReader.Close()`, which closes the read's `isolationState` (`tsdb/isolation.go:36-41`). That isolation state is what registers the read with `Head.iso.readsOpen`; `Head.truncateMemory`'s gate `WaitForPendingReadersInTimeRange` (`tsdb/head.go:1141-1158`) only considers currently-linked isolation states. Because the querier is closed on helper return (before the set is drained), a concurrent head truncation/GC can advance past this now-unregistered read while iteration is still resolving chunks.

**Consequence (corrected during validation):** *Not* a memory use-after-free. Head chunk bytes are **copied** out of the mmap under `cdm.readPathMtx` in `ChunkDiskMapper.Chunk()` (`tsdb/chunks/head_chunks.go` — comment: copy "to prevent a panic … while the chunk is still in use"), the open head chunk is deep-copied via `ChunkWithCopy`, and series-level truncation shifts are bounds-checked (`ix < 0` / `ix > len-1` → `storage.ErrNotFound`, `head_read.go:417-419`). So the reachable outcome is confined to **snapshot-consistency breakage**: a mid-stream `ErrNotFound` that fails the request, or a result that mixes pre- and post-truncation state — a correctness/reliability regression under a concurrent-truncation race, not a crash.

**Fix:** Same as #1 — the querier (and its isolation state) must outlive consumption of the returned `ChunkSeriesSet`. One structural change (stream while the querier is still open) resolves both #1 and #2.

### #3 🟡 Medium: Lifetime-ownership contract is undocumented and the new helper comment asserts early close as safe

| | |
|---|---|
| **File** | `storage/remote/read_handler.go:239-241` (helper doc comment) + `storage/interface.go` (`ChunkQuerier`/`ChunkSeriesSet` contract) |
| **Category** | knowledge-preservation / evolution-readiness |
| **Confidence** | 75 (anchor) |
| **Found by** | knowledge (undocumented assumption + misleading comment), design (evolution-readiness) |
| **Validation** | **confirmed** — mixed pre-existing: the comment is new to this diff; the interface.go doc gap is pre-existing |

**Issue:** The helper comment — *"executes a query to retrieve a ChunkSeriesSet, encapsulating the operation in its own function to ensure timely release of the querier resources"* — frames early Close purely as a benefit and omits the load-bearing hazard: the returned set is consumed lazily *after* Close, which is only safe if the storage implementation guarantees the set is self-contained post-Close. The `storage.ChunkQuerier` / `ChunkSeriesSet` contract in `storage/interface.go` does **not** document whether post-`Close` consumption is permitted; the nearest documented rule points the other way — `LabelValues` (interface.go:161): results are "not safe to use … beyond the lifetime of the querier"; `Close` (interface.go:171): "releases the resources of the Querier." So the change encodes an undocumented, implementation-specific assumption, and the comment will mislead future maintainers/LLMs into treating consume-after-close as proven safe.

**Fix:** Two parts. (a) In `read_handler.go`, replace the reassuring comment with the actual invariant the code depends on (and once #1 is fixed, this comment largely disappears). (b) Independently of #1, document the lifetime/ownership invariant on `storage.ChunkQuerier`/`ChunkSeriesSet` in `storage/interface.go` — e.g. "the returned set and its chunks must not be consumed after the querier is closed unless the implementation guarantees self-containment" — so a future caller elsewhere cannot reintroduce the same class of bug. (The interface.go gap is pre-existing and lower urgency on its own; the comment half is entangled with #1.)

### #4 🟡 Medium: Change unpins compaction/GC refcounts early but does not bound per-connection memory of a stalled streaming write, so the OOM goal is only partially met

| | |
|---|---|
| **File** | `storage/remote/read_handler.go` (whole change) + `storage/remote/codec.go:283` (`stream.Write`) + `web/web.go` (no `WriteTimeout` on this path) |
| **Category** | performance / reliability / completeness |
| **Confidence** | 75 (anchor) |
| **Found by** | performance (only) |
| **Validation** | **confirmed** — severity corrected High → Medium (missing WriteTimeout is pre-existing; diff does not regress memory) |

**Issue:** The PR's stated goal is to "avoid OOM's" from "broken chunked remote read requests." The change legitimately unpins two refcounts sooner — `pendingReaders` for blocks and the isolation low-watermark for the head — letting concurrent compaction/retention/GC proceed. But the **primary per-connection cost** is untouched: the live `ChunkSeriesSet` state (postings iterator, in-flight chunk buffers) stays alive because `StreamChunkedReadResponses` blocks in `stream.Write()` (`codec.go:283`) to a slow/broken client, and the streaming loop has no `ctx.Err()` check or write deadline. The HTTP server (`web/web.go`) sets only `ReadTimeout` — no `WriteTimeout` on the remote-read path — so up to `remote-read-concurrency-limit` (default 10, `cmd/prometheus/main.go`) stalled clients can each hold this state indefinitely (the concurrency gate is held via `defer` for the whole streaming duration).

**Note:** This is a **completeness/efficacy** observation against the PR's broader OOM framing, not a regression in the changed code — the missing WriteTimeout is pre-existing infrastructure. Kept as Medium accordingly.

**Fix:** Bound the stall — set a write deadline via `http.ResponseController.SetWriteDeadline` around the streaming loop, and/or check `ctx.Err()` between frames in `StreamChunkedReadResponses` so a wedged client's query state is released. (Complementary to #1's fix, not a substitute.)

## Specialist Notes

### Considered But Not Flagged (all agents)

Consistently examined and soundly dismissed across reviewers (and re-confirmed by validators where relevant):

- **`chunks.Err()` timing (`read_handler.go:206`)** — checked before iteration, so it only surfaces construction-time errors (e.g. `ChunkQuerier`/`PostingsForMatchers` failure via `storage.ErrChunkSeriesSet`). It does *not* mask iteration-time errors, which still propagate through `StreamChunkedReadResponses` (`ss.Err()`/`iter.Err()`, `codec.go:292-296`). Faithful equivalent of the prior inline `if err != nil { return err }`. Not a bug.
- **`remoteReadSamples` (unstreamed sample path)** — uses the same `defer querier.Close()` shape but is safe: `ToQueryResult(querier.Select(...))` fully materializes the `SeriesSet` synchronously before the deferred Close fires. Unchanged and correctly left alone.
- **`storage.ErrChunkSeriesSet(err)` on `ChunkQuerier` failure (`read_handler.go:245`)** — the codebase's canonical pattern for propagating an error through a function returning a lazy set (cf. `tsdb/querier.go:138,187`, `storage/remote/read.go:165,170`). A concrete non-nil set wrapping a non-nil error — not a typed-nil trap. Correct, not drift.
- **Duplicated `hints` construction** (`remoteReadSamples` vs `getChunkSeriesSet`) — a stable field-for-field `prompb.Query.Hints` → `storage.SelectHints` mapping; the duplication pre-existed the PR (it merely relocated the chunk-path copy). DRY nit, not new drift.
- **`ctx` not re-checked during iteration** — pre-existing behavior; `Select(ctx, ...)` was only ever used for postings construction, not iteration cancellation. Not introduced by this diff (related to #4).
- **Head chunk mmap safety** — design/adversarial/performance dismissed a head-path memory UAF; validator confirmed head chunks are copied out of the mmap (see #2). Correct.
