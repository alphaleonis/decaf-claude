## Findings

### #1 🟠 High: `StreamIdleTimeoutError` is never classified downstream — no retry, spurious exception telemetry, generic user message

| | |
|---|---|
| **File** | `extensions/copilot/src/extension/prompt/node/chatMLFetcher.ts:1949-2015` (consequence); `extensions/copilot/src/platform/networking/common/fetcherService.ts:312` (source) |
| **Category** | error-handling |
| **Confidence** | 100 (classification path directly verified by the orchestrator: read of `processError` + repo-wide grep) |
| **Found by** | broad-reviewer (High), design-reviewer (Medium) |

**Issue:** `StreamIdleTimeoutError` is a plain `Error` subclass with `name = 'StreamIdleTimeoutError'`. A repo-wide grep confirms nothing outside its definition and its own spec references it — no `catch`, `instanceof`, or name-match anywhere. When it propagates into `processError` (`chatMLFetcher.ts:1949`), it matches none of the branches: `isAbortError` (1957), `isCancellationError` (1965), the `'Premature close'` / `ERR_STREAM_PREMATURE_CLOSE` string match (1973-1976), `isInternetDisconnectedError` (1989), or `isFetcherError` (1997). It therefore:
1. Hits `this._logService.error(...)` + `this._telemetryService.sendGHTelemetryException(err, ...)` at **1984-1985** — an *intentional, expected* timeout is logged and telemetered as an unexpected exception, polluting error monitoring.
2. Falls into the terminal `else` at **2007-2014** → `ChatFetchResponseType.Failed`, reason `'Error on conversation request. Check the log for more details.'` — a generic message that tells the user nothing about a stall.
3. Is not retried on the standard SSE/HTTP path: the retry gate at **575** requires `ChatFetchResponseType.NetworkError`; `Failed` only re-fires via `retryWithoutWebSocket` (576), which needs `useWebSocket` — not the path `messagesApi.ts`/`responsesApi.ts`/`stream.ts` exercise.

The typed error and its `isFirstChunk` discriminator carry zero downstream value: first-chunk vs. mid-stream timeouts are indistinguishable in telemetry, defeating a stated reason for introducing the typed error.

**Fix:** Add an explicit arm in `processError`, before the generic `else`, e.g.
```ts
if (err instanceof StreamIdleTimeoutError) {
	return {
		type: ChatFetchResponseType.NetworkError, // participates in the retry-on-network-error gate
		reason: 'The response stalled and was canceled. Please try again.',
		reasonDetail: err.message,
		requestId,
		serverRequestId: gitHubRequestId,
	};
}
```
and emit a categorized telemetry event surfacing `isFirstChunk` rather than a generic `sendGHTelemetryException`.

*Dissent:* design-reviewer rated this Medium (a design-completeness gap). Kept at High because it introduces a new failure mode the error layer treats as a bug (exception telemetry) and silently forgoes retry — a real degradation of the feature's own error path.

### #2 🟡 Medium: Idle timeout discards already-received response data instead of salvaging it

| | |
|---|---|
| **File** | `extensions/copilot/src/platform/networking/node/stream.ts:322,596-614`; `extensions/copilot/src/platform/endpoint/node/messagesApi.ts:596`; `extensions/copilot/src/platform/endpoint/node/responsesApi.ts:534` |
| **Category** | data-loss / error-handling |
| **Confidence** | 75 (validator: **confirmed** — mechanism verified against `AsyncIterableObject`) |
| **Found by** | broad-reviewer (High), adversarial-reviewer (Medium ×2) |

**Issue:** On timeout, `withStreamIdleTimeout` throws `StreamIdleTimeoutError` unconditionally after its loop, unwinding out of the consumer — discarding data already received before the stall. Two variants of one root cause:

- **(a) SSEProcessor partial-text loss** — `SSEProcessor.processSSEInner` (`stream.ts`) accumulates streamed text per choice index in `this.solutions`, with a fallback at **596-614** that yields still-incomplete solutions when the stream ends *without* a terminal marker (the comment there even says "This shouldn't happen in practice unless there was an error somewhere"). A thrown `StreamIdleTimeoutError` unwinds past that fallback, so partial generated text already accumulated is dropped.
- **(b) Completed-but-slow-to-close response lost** — in `messagesApi.ts`/`responsesApi.ts`, the loop reads to natural `done` with no early break on a terminal SSE event. If the server emits its terminal event (completion already handed to `feed.emitOne`) but holds the HTTP body open longer than `SSE_IDLE_TIMEOUT_MS` (60s) before closing, the idle timer fires on the terminal read and throws — even though the full response was parsed. The validator confirmed `AsyncIterableObject.next()` (`util/vs/base/common/async.ts`) checks its terminal-error state **before** returning buffered `_results`, so an emitted-but-undrained completion is discarded rather than delivered.

Compounds with #1: the discarded response is then surfaced as a non-retried `Failed`.

**Fix:** Before propagating `StreamIdleTimeoutError` out of `processSSEInner`, drain `this.solutions` (mirror the 596-614 fallback) so partial content is not silently dropped; and/or break the loop on the terminal SSE event so a completed-but-slow-to-close stream is not timed out after its completion was already parsed.

*Caveat:* variant (b)'s clear-bug case depends on abnormal server behavior (holding the body open post-completion); variant (a)'s "loss" is on a genuine-hang error path where failing may be defensible. Kept primary because the confirmed mechanism can lose a real, completed answer. Dissent: adversarial rated Medium; broad rated High.

### #3 🟡 Medium: Idle-only watchdog has no total-duration cap — a slow-drip stream is never timed out

| | |
|---|---|
| **File** | `extensions/copilot/src/platform/networking/common/fetcherService.ts:342-354` |
| **Category** | resilience / abuse-case |
| **Confidence** | 75 — **unvalidated** (validator: mechanism confirmed; defect-vs-intended is design-dependent) |
| **Found by** | adversarial-reviewer (Medium) |

**Issue:** `startTimer(...)` is re-armed on every loop iteration and cleared as soon as a chunk arrives; there is no absolute wall-clock ceiling. The reset is tied to *network-level* chunks from the `DestroyableStream` iterator, not to the SSE parser producing a completion. So a broken or hostile server that emits any byte more often than `SSE_IDLE_TIMEOUT_MS` — e.g. an SSE keep-alive `:` comment line the parser ignores — resets the timer indefinitely. The connection, reader, and generator are held open forever; only a *fully silent* (zero-byte) stream is actually caught. The feature's goal (kill hung streams) is defeated by a trivial slow-drip.

**Fix:** Add an absolute max-total-duration timer, armed once and independent of per-chunk resets, alongside the idle timer — so "progress that is not really progress" still terminates. At minimum, document that liveness is measured on raw transport chunks and that any wired endpoint must emit data/keepalives more often than `SSE_IDLE_TIMEOUT_MS`.

*Marked unvalidated:* the validator confirmed the mechanism but judged whether it is a defect vs. intended "idle watchdog" scope to be design-dependent — the JSDoc frames the feature around "gaps"/"inactivity", which arguably makes "some data still flowing" a legitimate reason not to time out. Reported so the design intent can be confirmed rather than assumed.

### #4 🟡 Medium: False-positive test — "consumer break releases the underlying reader lock" asserts nothing

| | |
|---|---|
| **File** | `extensions/copilot/src/platform/networking/test/node/streamIdleTimeout.spec.ts:142-158` |
| **Category** | test-quality (false-positive test) |
| **Confidence** | 100 — **probe-confirmed** (executed) |
| **Found by** | test-reviewer (Critical) |

**Issue:** The test is named for releasing the reader lock (bot-comment (c), the production fix at `fetcherService.ts:368` `await iterator.return?.()`), but its only post-break checks are `assert.deepStrictEqual(collected, ['a','b'])` (populated *before* the break) and `await stream.destroy()` not throwing. `DestroyableStream.destroy()` resolves cleanly whether or not the lock was released: with the fix removed, `this.reader` stays a valid locked reader and `destroy()` takes the `reader.cancel()` branch — which succeeds per WHATWG semantics on a reader still holding its lock. The test cannot distinguish "lock released" from "lock leaked."

**Probe (run during this review):** removed `fetcherService.ts:368` (`await iterator.return?.();`), ran the spec → **all 7 tests still passed**; restored the line byte-identical and re-ran → 7/7 pass. This directly confirms the test provides no coverage for the regression it names. (A prior review run could not execute this probe — no deps installed — and confirmed it only statically; this run executed it.)

**Fix:** Assert the observable lock state before destroying:
```ts
assert.deepStrictEqual(collected, ['a', 'b']);
assert.strictEqual(stream.toReadableStream().locked, false); // for-await awaits IteratorClose → return?.() ran
await stream.destroy();
```

*Downgraded* from test-reviewer's Critical to Medium per consolidation: the production code is correct; the defect is the missing regression guard (Medium+ false-positive test stays primary).

### P1 🟡 Medium: `AsyncIterableObject.next()` surfaces its terminal error before draining buffered results

| | |
|---|---|
| **File** | `extensions/copilot/src/util/vs/base/common/async.ts:~2047-2060` |
| **Category** | data-loss |
| **Found by** | broad-reviewer (Medium, `pre_existing`) |

`next()` checks `if (this._state === DoneError) throw this._error;` **before** returning any buffered `_results`. Any executor throw after `emitOne(...)` but before the consumer drains discards those buffered completions. This is the shared-utility mechanism behind finding #2 variant (b); it predates the PR and applies to every executor throw, but the PR materially increases how often the executor throws mid-stream. A follow-up would swap the two checks so buffered results are drained before the terminal error surfaces.

### P2 🟡 Medium: Hang protection applied to only the 3 CAPI SSE paths; sibling streaming paths remain unprotected

| | |
|---|---|
| **File** | `extensions/copilot/src/extension/completions-core/vscode-node/lib/src/openai/stream.ts:~293` (and `extChatEndpoint.ts`, `oaiLanguageModelServer.ts`) |
| **Category** | design / consistency |
| **Found by** | design-reviewer (Medium, `pre_existing`) |

The completions-core SSE loop is structurally identical ("arbitrarily sized chunks coming in from the network" over `this.body`) but is not wrapped; other network streaming consumers are likewise unguarded. The same hung-connection failure mode this PR targets is still reachable on those paths. Decide and document whether idle protection is a networking-layer default (extend it uniformly, e.g. inside `DestroyableStream` or a shared helper) or an intentional CAPI-only measure. (The wrapper only accepts `DestroyableStream`, so extending it needs an adapter — itself an implicit design decision.)

## Specialist Notes

### Considered But Not Flagged (all agents)

- **The three prior bot-comment fixes are all correct** (verified independently by broad, adversarial, typescript, and design): (a) the timer is cleared before `yield`, so consumer processing time is genuinely excluded (also guarded by the "consumer processing time longer than idle timeout" test — a real regression guard, unlike test #4); (b) `void stream.destroy().catch(() => { })` is the correct fire-and-forget idiom (the timeout signal is preserved via the `timedOut` flag regardless of whether `destroy()` succeeds); (c) `await iterator.return?.()` is properly awaited and releases the lock — production is correct, only its *test* is hollow (#4).
- **`reader.cancel()` rejecting instead of resolving-as-`done`** — refuted by three agents. Per WHATWG Streams, `ReadableStreamCancel` runs `ReadableStreamClose` (resolving pending reads as `{done:true}`) before the source's cancel steps, so the timeout path reliably reaches the post-`finally` `throw` and `StreamIdleTimeoutError` propagates. Corroborated by the passing "first chunk never arrives" / "subsequent chunk stalls" tests.
- **`iterator.return()` deadlock / double-cancel after a timeout-destroy** — traced apart by adversarial: on the timeout path the inner generator is already `done`, so `iterator.return?.()` is a no-op; call-site `destroy()`/`onReturn` cleanup converges on one reader (second `destroy()` hits the no-op `stream.cancel()`). Single-threaded ordering, no race.
- **Timeout silently swallowed by `SSEProcessor.maybeCancel` early-return** — refuted: `maybeCancel` is reached only after a `yield`; on timeout the wrapper yields nothing and throws directly.
- **`isFirstChunk` stale at throw time** — traced correct: it only flips `false` after a real chunk yields, and the post-loop `if (timedOut)` reads the same variable used to select the active timeout.
- **`setTimeout` not `.unref()`'d** (typescript-reviewer, confidence 50) — not flagged: the timer is always cleared on the happy path and the process is actively awaiting the stream, so it does not spuriously hold the event loop; a blind `.unref()` would also break the WebWorker (`tsconfig.worker.json`) build. Low value.
- **`destroy()` teardown recorded as `outcome:'cancel'` with no reason** (a prior run's Low finding) — an observability nit (idle timeout indistinguishable from user cancel in reliability telemetry), subsumed by the broader classification gap in finding #1.
