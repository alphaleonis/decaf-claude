### #1 🟠 High: `OnNodeChange` poisons its NodeIP baseline → spurious `os.Exit(1)` on transient IP loss then restore

| | |
|---|---|
| **File** | `pkg/proxy/node.go:145` (within `NodeManager.OnNodeChange`, ~lines 140–172) |
| **Category** | correctness / error-handling |
| **Confidence** | 75 · **validator: CONFIRMED** |
| **Found by** | adversarial-reviewer (High) |

**Issue:** `OnNodeChange` assigns `n.node = node` **before** the `GetNodeHostIPs(node)` error check. Trace (informer delivers events serially, so `n.node` persists between them):
1. Baseline = node with IP `A`.
2. An update arrives whose `Status.Addresses` has no parseable InternalIP/ExternalIP → `oldNodeIPs=[A]`, `n.node` is overwritten with the IP-less node (line 145), then `GetNodeHostIPs(node)` errors → the function logs and `return`s **without** exiting. The stored baseline is now the IP-less node.
3. The next update restores the same IP `A` → `oldNodeIPs` is re-derived from the stored IP-less node = `nil` (its error is discarded via `_`), `nodeIPs=[A]`, `reflect.DeepEqual(nil, [A]) == false` → `n.exitFunc(1)`.

The node's effective IP went `A → (none) → A` — unchanged across the two valid states — yet kube-proxy exits. `GetNodeHostIPs` returns `nil, err` when the node has zero parseable host IPs (`pkg/util/node/node.go:84-86`). Precondition (a node update transiently dropping *all* node IPs) is uncommon but possible; the whole block is attributed to this PR.

**Fix:** Only advance the comparison baseline after confirming the incoming node yields valid IPs — move `n.node = node` below the `GetNodeHostIPs(node)` success check, or keep a separate `lastGoodNodeIPs` field. Then step 3 compares `[A]` vs `[A]` → no exit.

### #2 🟡 Medium: Crash-on-NodeIP-change is new and unbounded (no debounce/normalization); rationale and delete-crash undocumented

| | |
|---|---|
| **File** | `pkg/proxy/node.go:41-43` (type doc), `:167` (IP-change exit), `:176-180` (`OnNodeDelete` exit) |
| **Category** | reliability / knowledge |
| **Confidence** | 75 |
| **Found by** | adversarial-reviewer (Critical, as a fleet-cascade), broad-reviewer (Medium), knowledge-reviewer (SHOULD) |

**Issue:** Exiting on any observed NodeIP change is **new** behavior (pre-PR, kube-proxy read node IPs once at startup and never crashed on change). `OnNodeChange` calls `os.Exit(1)` on any `reflect.DeepEqual` NodeIP difference with no debounce, no re-read confirmation, and no order/family normalization; `OnNodeDelete` now also exits. Blast radius: a controller/cloud provider that flaps node addresses (or reorders `Status.Addresses`) makes every affected node's kube-proxy exit; the DaemonSet restarts and each restart re-LISTs Nodes/Services/EndpointSlices simultaneously (thundering herd) while `NewNodeManager` may block up to 5 min. The type doc says it crashes "if there are any changes in NodeIPs or PodCIDRs" but does not record (a) *why* exit-vs-reconfigure was chosen (immutable startup inputs + supervisor restart), or (b) that node **deletion** is also a crash trigger. The old `NodePodCIDRHandler` carried an issue link (`https://issues.k8s.io/111321`) that this PR removed without replacement.

**Fix:** Consider requiring the change to persist across a re-read (debounce) and comparing a normalized primary-IP set before exiting; add startup LIST jitter to avoid synchronized re-list storms. At minimum, document in `OnNodeDelete` and the type doc that a delete is a crash trigger and *why* NodeIPs/PodCIDRs are treated as immutable startup inputs (re-cite issue 111321).

### #3 🟡 Medium: `newNodeManager` returns `err` (not `pollErr`) — fragile, and an explicit prior reviewer request was not applied

| | |
|---|---|
| **File** | `pkg/proxy/node.go:107-108` |
| **Category** | prior-feedback / robustness |
| **Confidence** | 75 |
| **Found by** | prior-feedback-reviewer (Medium); go-reviewer & adversarial-reviewer noted the same code (concluded currently-unreachable) |

**Issue:** The poll-timeout path is `if pollErr != nil { return nil, err }` — it returns the separately-captured condition `err` rather than `pollErr`. Reviewer danwinship explicitly asked to restructure this (*"This is weird. If you know `err` is going to be set in that case then just do `if err != nil { return nil, err }`"*); the final code did **not** adopt it. It is safe *today* only because `PollUntilContextCancel` runs with `immediate=true` (the condition runs ≥1 time and every non-success branch sets `err`), so `err` is non-nil whenever `pollErr` is. But if a future edit flips `immediate` to false or adds a `return false, nil` branch that forgets to set `err`, the function can return `(nil, nil)` → the caller `s.NodeManager.NodeIPs()` (server.go) nil-panics.

**Fix:** Adopt the reviewer's suggestion — gate on the captured error itself (`if err != nil { return nil, err }`), decoupling correctness from the "err is always set on failure" invariant.

### #4 🟡 Medium: `NewNodeConfig` omits `AddFunc` — an in-window NodeIP/PodCIDR change can be dropped until the next update (undocumented intentional omission)

| | |
|---|---|
| **File** | `pkg/proxy/config/config.go:288-294` |
| **Category** | async / knowledge |
| **Confidence** | 75 (corroborated ×4) |
| **Found by** | quick-reviewer (High), broad-reviewer (Low), adversarial-reviewer (Medium), knowledge-reviewer (SHOULD) |

**Issue:** `NewNodeConfig` registers only `UpdateFunc`+`DeleteFunc` — no `AddFunc` — while every sibling (`NewServiceConfig`, `NewEndpointSliceConfig`, and the new `newNodeTopologyConfig`) wires `AddFunc`. Because the handler is added to an already-started, already-synced shared informer (owned by `NodeManager`), client-go replays the current node as an **Add** event, which is silently dropped. Consequence: any NodeIP/PodCIDR change that happens in the window between `NewNodeManager`'s startup lister-poll and this handler registration in `Run()` is delivered only as the dropped Add — so `NodeManager.node`/`NodeIPs()`/`PodCIDRs()` (already consumed to configure the proxier) stay stale until the next genuine Update or resync. Self-correcting (kubelet heartbeats / `ConfigSyncPeriod` resync re-fire `UpdateFunc` against the stale baseline), so impact is bounded — but the omission is deliberate and **undocumented**, and a maintainer "adding `AddFunc` for symmetry" would replay the current node against the captured baseline and risk a spurious startup exit.

**Fix:** Add a comment at the registration explaining `AddFunc` is intentionally omitted (baseline captured by the poll; wiring `AddFunc` would replay the current node and risk a spurious startup exit), contrasting with `NodeTopologyConfig` which needs `AddFunc` to seed the initial zone. Optionally reconcile `NodeManager.node` against the lister once handlers are registered to close the window.

### #5 🟡 Medium: Startup now hard-fails (up to 5 min) if the node has no NodeIPs — replaces the old ~30-40s→loopback degraded start

| | |
|---|---|
| **File** | `pkg/proxy/node.go:60,87-109`, `cmd/kube-proxy/app/server.go:211-220` |
| **Category** | behavior-change / reliability |
| **Confidence** | 75 · **validator: CONFIRMED** |
| **Found by** | broad-reviewer (Medium) |

**Issue:** The removed `getNodeIPs` used exponential backoff (~6 steps ≈ 30-40s) and then returned whatever it had (possibly `nil`) **without failing**; `detectNodeIPs` then fell back to loopback/bind address ("Can't determine this node's IP, assuming loopback", server.go:681-682) and kube-proxy **started**. The new `NewNodeManager` polls until `GetNodeHostIPs` succeeds or a **5-minute** timeout, and the `GetNodeHostIPs` requirement is unconditional (applies to the common non-NodeCIDR case, not just LocalModeNodeCIDR). On timeout it returns an error that `newProxyServer` propagates → kube-proxy **fails to start / crash-loops**. Because `detectNodeIPs` (server.go:220) runs only after `NewNodeManager` succeeds, the loopback fallback is now unreachable in the no-IP case. For late cloud-IP assignment this is arguably better (waits for the real IP), but it is an undocumented contract change: kube-proxy now *requires* NodeIPs to start.

**Fix:** If intentional, add a comment at `newNodeManager` recording that the NodeIP requirement is now hard (supersedes the loopback fallback) so it isn't reintroduced or the timeout shortened unaware. If not, restore a degraded-start path for the no-IP case.

### #6 🟡 Medium: NodeManager's crash-on-change contract is not self-enforced — inert without external server.go wiring

| | |
|---|---|
| **File** | `pkg/proxy/node.go:64-117` (constructor), `cmd/kube-proxy/app/server.go:607-614` (handler wiring) |
| **Category** | design / robustness |
| **Confidence** | 75 · **validator: CONFIRMED** |
| **Found by** | design-reviewer (Medium) |

**Issue:** `newNodeManager` starts the informer, waits for cache sync, and polls the lister — but never calls `AddEventHandler` to register its own `OnNodeChange`/`OnNodeDelete`. The crash-detection only activates because `ProxyServer.Run` separately builds a `config.NodeConfig` from `s.NodeManager.NodeInformer()`, registers `s.NodeManager` as a handler, and runs it (guarded by `if s.NodeManager != nil`). Meanwhile `newProxyServer` consumes `NodeIPs()`/`PodCIDRs()` at construction, before any handler is wired. So the documented safety guarantee lives in caller wiring, not the type: a caller that builds a NodeManager only for its accessors, or between construction and `Run`, has crash-detection silently disabled.

**Fix:** Have `NodeManager` register itself as a handler on its own informer during construction (or via an explicit `Start()`/`Watch()` method it owns), so the contract is active for the object's lifetime rather than depending on external composition.

### #8 🟡 Medium: `TestNewNodeManager` uses sleep-based synchronization against the poll loop (flaky under load)

| | |
|---|---|
| **File** | `pkg/proxy/node_test.go:205-218` |
| **Category** | test-quality / flakiness |
| **Confidence** | 50 |
| **Found by** | test-reviewer (Medium) |

**Issue:** The test drives the informer/poll loop from a goroutine that sleeps `100ms`, then applies each node update separated by `time.Sleep(15ms)`, while `newNodeManager` polls every `10ms` with a `1s` timeout — the classic wall-clock coordination anti-pattern. It is **not** a false-positive (traced: the poll condition returns `true` only on the complete final state, so it cannot capture a wrong intermediate and pass by luck). The realistic failure mode is a spurious **failure** on a loaded CI host if the update goroutine is starved past the 1s poll budget. Also burns ~4s wall time (four sub-cases each wait the full 1s timeout).

**Fix:** No functional bug. If it ever flakes, replace fixed sleeps with informer-sync-based (`cache.WaitForCacheSync`) or event-driven coordination, or widen the poll-timeout budget.

### #A1 🟠 High: Node/topology handlers are registered on an already-started informer → data race on `eventHandlers` + possibly-lost initial topology label

| | |
|---|---|
| **File** | `pkg/proxy/config/config.go:288-304` (`NewNodeConfig`/`RegisterEventHandler`), `:618-644` (`newNodeTopologyConfig`), `cmd/kube-proxy/app/server.go:607-614` |
| **Category** | concurrency / data-race |
| **Confidence** | 100 · **verified by orchestrator; corroborated by 2 prior passes** |
| **Found by** | recurring cross-check (prior passes flagged as High); missed by this wave |

**Issue:** `NewNodeConfig` and `NewNodeTopologyConfig` call `nodeInformer.Informer().AddEventHandlerWithResyncPeriod(...)` inside their constructors. The informer is **already started and synced** (started in `NewNodeManager` via `thisNodeInformerFactory.Start(...)`), so client-go schedules delivery of existing objects (and future events) to the newly-registered listener on the listener's own goroutine, asynchronously. Only *after* the constructor returns does `server.go` call `RegisterEventHandler(...)`, which does an **unsynchronized `append` to `eventHandlers`** (config.go:303 / :642). Meanwhile the informer's delivery goroutine runs `handleChangeNode`/`handleNodeEvent`, which **range over `eventHandlers`** (config.go:333, :666) with no mutex. Concurrent slice append + range = a data race the Go race detector will flag. For `NodeTopologyConfig` (which *does* have an `AddFunc`), the cache-replay Add reliably fires: if it runs before `RegisterEventHandler(s.Proxier)`, the proxier misses its initial zone notification, and because `handleNodeEvent` still updates `n.topologyLabels`, a later same-zone event is deduped away — so the proxier can **permanently miss the initial topology zone** until an actual zone change. The old code guarded exactly this with "This has to start after the calls to NewNodeConfig because that must configure the shared informer event handler first" + a deferred `informerFactory.Start`; moving `Start` into `NewNodeManager` dropped that ordering guarantee.

**Fix:** Register the informer event handlers *after* the downstream `RegisterEventHandler` calls (restore the old ordering: build config, register handlers, then start/attach the informer handler), or guard `eventHandlers` with the config's mutex, or have the constructor take the handlers up front. Ensure the initial replayed Add is delivered only once all downstream handlers are registered.

| **Found by** | recurring cross-check; this wave's test-reviewer verified the channel sync but not the assertion gap |

**Issue:** The sub-cases whose stated intent is "handler should NOT receive a notification" assert only `require.Len(handler.topologyLabels, 1)` — i.e. the resulting map still has one entry. But the handler mock stores whatever map it last received and is never reset, and the prior sub-case already left `topologyLabels = {zone: us-east-1b}`. If the production dedup (`reflect.DeepEqual(n.topologyLabels, topologyLabels) { return }`, config.go:661) were removed so the handler *were* re-notified with the same-zone map, `handler.topologyLabels` would still be `{zone: us-east-1b}` (len 1) and the assertion would still pass. The test therefore cannot distinguish "not notified" from "re-notified with the same value" — it does not actually verify the no-notification behavior it is named for. (A prior pass removed the dedup line via a revert-probe and the test still passed, confirming this.)

**Fix:** Assert on notification *occurrence*, not the resulting map contents — e.g. count invocations and assert the count did not increase, or reset `handler.topologyLabels` to a sentinel before the event and assert it is unchanged. This matches reviewer danwinship's original "just track did-the-handler-get-invoked-again" suggestion.

### #A4 🟢 Low: `klog.Flush()` + `exitFunc(1)` replaces `klog.FlushAndExit(ExitFlushTimeout, 1)` on crash paths — lost bounded-flush timeout

| | |
|---|---|
| **File** | `pkg/proxy/node.go:154-155,170-171,178-179` |
| **Category** | robustness |
| **Confidence** | 75 · divergence from prior passes noted below |
| **Found by** | recurring cross-check (3 prior passes rated this High/Medium; this wave dismissed it) |

**Issue:** The crash paths now call `klog.Flush()` then `n.exitFunc(1)` instead of the old `klog.FlushAndExit(klog.ExitFlushTimeout, 1)`. **Honest divergence:** the prior passes framed this as "exit-reason logs can be lost," but `klog.Flush()` is *synchronous* — it blocks until pending log I/O is written — so the exit-reason line is in fact flushed before exit. The genuine (minor) regression is the loss of `FlushAndExit`'s **bounded** flush: if a log sink wedges, plain `Flush()` can block the intended crash indefinitely, whereas `FlushAndExit` caps the wait at `ExitFlushTimeout`. The injectable `exitFunc` (which necessitated splitting flush from exit) is a worthwhile testability gain, so this is Low, not High.

**Fix:** If bounded-flush behavior matters, flush with a timeout before `exitFunc(1)` (or route the exit through a helper that mirrors `FlushAndExit`'s bounded flush while remaining injectable). Otherwise document that the unbounded `Flush()` is intentional.
