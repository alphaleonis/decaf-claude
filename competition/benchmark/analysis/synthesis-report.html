Benchmark synthesis · 9 of 12 subjects

Every reviewer finds the bug. The difference is what else they say.

Five AI code-review tools, each run twice against nine real pull requests that shipped a regression and were later reverted. 90 isolated runs, 4,158 raw findings, every finding blind-graded against a frozen answer key. Catching the escaped bug turns out to be close to table stakes — the honest separation is in noise discipline, severity calibration, and cost, which span an order of magnitude.

The one genuinely discriminating subject is TypeScript / small, where four of five tools missed the bug in both repeats. That PR's defect was invisible in the diff: it changed the token stream a public API returns, and only crashed downstream consumers. The single tool that caught it did so by retrieving the revert commit from repository history — not by reading the code. The second, Go / large, split the field 6/10.

Read the recall column with that in mind: the ranking rests on two subjects, so treat 18/18 versus 12/18 as suggestive, not settled. What follows is measured across all 90 runs and is far better supported.

This is the single widest quality gap in the study. anthropic's top-of-list is trustworthy almost nine times in ten. pr-review-toolkit's is a coin flip — in one subject it stamped critical on a stale test comment while ranking the actual reverted bug as low severity. A tool that finds the bug but can't tell you it matters has moved the work, not done it.

An 8.6× spread for overlapping results

Sub-agent fan-out is the cost driver, and it earns surprisingly little. Across all subjects, roughly three-quarters of every fan-out tool's sub-agent findings restate a sibling's. superpowers, on a single agent, reached the same escaped bug as a fifteen-agent run on seven of nine subjects (14 of 18 runs). Where fan-out did pay was breadth of secondary findings on large diffs — not recall.

Volume scales sharply with diff size — 2.7× more findings per run from small to large — while the substantive share holds up (37% → 42%). That is the reassuring half: these tools do not drown in a big diff, and on the largest subject every tool still found the regression.

The cost half is less comfortable. A large PR costs about 65% more per run, and the absolute noise a reader must wade through roughly doubles. The medium row looks alarming, but it rests on only two subjects, one of which was deliberately constructed as a trap — read it as an artefact of composition, not a property of medium-sized PRs.

Conclusions

Which tool, for which job

Best overall

anthropic-code-review

The only tool that caught every escaped bug, with the best substantive share and by far the most trustworthy severity ranking. Mid-priced. Its weakness is a reliance on repository history: its sole unique catch came from retrieval, and that same channel produced its false positives — including one hallucinated claim that a maintainer had raised an issue.

18/18bug caught 0.88calibration $11.82per run

Best value

superpowers

A single agent at under a ninth the cost of the priciest tool, with the cleanest output in the study: lowest trivia share, lowest false-positive rate, fewest findings to read. It pays for that thrift in recall — it missed four of eighteen — and its severity labels are middling. The right default when review runs on every PR.

14/18bug caught 21%trivia $2.48per run

Depth at a price

ours

Strong recall (16/18) and the richest reasoning — its validator sub-agents repeatedly corrected their own findings downward rather than inflating them, and it was the only tool to verify historical review threads against merged code before re-raising them. But it is the most expensive run in the study and spends a third of its output on trivia.

16/18bug caught 31%trivia $21.33per run

Breadth, unranked

tag1-comprehensive-review

Produced the most unique true findings of any tool (5) and the highest substantive count per run, so its breadth is real. But 37% trivia and mediocre calibration mean that value arrives unsorted, at close to the top price.

15/18bug caught 5unique finds $16.72per run

Volume over judgement

pr-review-toolkit

Reports the most (21.3 per run) and the least useful: lowest substantive share, highest trivia, weakest recall, and a severity signal barely better than chance. It does find real defects — but leaves the ranking work entirely to the reader.

12/18bug caught 42%trivia 0.51calibration

If these tools are graded on finding the bug, four of five look equivalent. Graded on what a human then has to read, they differ by a factor of three — and that is the axis that decides whether a review tool is used twice.

Method & caveats

  • Design. Nine merged pull requests that each shipped a regression and were later reverted. Each tool reviewed each PR twice in an isolated session, pinned to the same model, with no knowledge of the revert.
  • Grading. Findings were normalised, clustered by underlying issue, then graded by a judge that saw the real diff and a frozen answer key but not which tool produced anything. Answer keys were written before any tool output was read, and verified against the merged code — in three subjects the fixture's own description turned out to be wrong, and the key follows the code.
  • Language comparison is deliberately omitted. One subject per language-size cell means a single idiosyncratic PR would masquerade as a language effect. Size pools three to four subjects and is reported instead.
  • Recall rests on two subjects. Seven of nine are saturated, so bug-catch rankings are weakly supported. Noise, calibration, and cost are measured across all 90 runs.
  • Cluster granularity varies between subjects (18 to 95 clusters), which inflates per-run counts on some subjects. All quality comparisons here use shares rather than raw counts for that reason.
  • Three subjects remain unrun (Go medium, Rust medium, Rust large), so the Rust and medium-size cells are thin. Conclusions may shift as those land.
  • Two judge verdicts were overridden by hand where the judge applied its own bar inconsistently; both are logged in the per-subject records, and neither changed a bug-catch result.
